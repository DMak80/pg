## Референс топологии (согласована)

Один etcd обслуживает НЕСКОЛЬКО независимых кластеров (систем): состояние
каждого — под префиксом `/clusters/<C>/`, системы друг про друга не знают
(watch своего префикса); Patroni каждого шарда живёт отдельно в
`/service/<scope>/`, где **scope = `<C>-<X>`** (`shop-shard1`) — уникален
глобально в общем etcd (не `<C>`: шардов в кластере много, и у каждого свой
Patroni-кластер).

```
нода кластера-шарда X:
  Patroni (агент, REST :8008) ──► PostgreSQL :5432 (локально)
      on_role_change ──► etcdctl put --lease /clusters/<C>/shards/X/master
      (единственный авторитет «кто мастер»; /primary потребляет health-check HAProxy)
  pg_doorman :6432 (sidecar) ──► 127.0.0.1:5432   # только локальный PG
  HAProxy :5432 ──► PG-ноды кластера (httpchk /primary)   # НЕ клиентский:
      вход репликационного трафика переездов (P2); per-node или пара LB на шард
  etcd-член :2379   # пока нод кластера ≤7; при росте — отдельный etcd (04-я)

приложение (роутер: etcd watch: бакет → шард → мастер-хост)
    → pg_doorman :6432 на ноде-мастере (sidecar)
        → 127.0.0.1:5432 (локальный PG)
bootstrap приложения: статикой — только адреса etcd + имя кластера <C>;
N и dbname — из /clusters/<C>/config; DSN конструируется на лету
(host из .../shards/X/master, port 6432, dbname из config)

etcd-контрол-плейн (кластер = шардированная система):
  /clusters/<C>/config              → {"buckets": 256, "dbname": "<C>"}   # константы init (P18: навсегда);
                                                                               # имя БД = имя кластера — ОДНО на все
                                                                               # шарды и ноды; бакеты — СХЕМЫ в ней
  /clusters/<C>/shards/X/dsn        → "host=n1,n2,n3 port=5432 dbname=<C> user=bucket_admin"
  /clusters/<C>/shards/X/replicas   → 2                 # декларативно (меняемо)
  /clusters/<C>/shards/X/master     → "10.0.1.11:6432"  # lease TTL 5с + продление, Patroni-callback
  /clusters/<C>/buckets/routing/N   → "shard1"          # владелец бакета
  /clusters/<C>/buckets/status/N    → {"state":"FROZEN",...}  # только при переезде; нет ключа = ACTIVE
  DSN в etcd — БЕЗ пароля (пароли в secrets env, P12/P17); dsn — статический
  multi-host вход (подписки/mover/админка), master — динамический (роутер приложений)

Жизненный цикл системы (11 §4.5): init-cluster.sh (N бакетов поровну
round-robin, константы config) → add-shard.sh (пустой шард) → move-bucket.sh
(миграция бакетов) → remove-shard.sh (только пустой шард, P23).

Переезд бакета: логическая репликация через HAProxy шардов (мимо пулеров;
подписка с multi-host conninfo host=node1,node2,... — HAProxy любой ноды
ведёт к мастеру), cutover = etcd-транзакция (routing/N + delete status/N).
HAProxy удалён из data path приложений; остаётся точкой входа репликационного
трафика переездов (см. P2).
```

Критичность: 🔴 потеря данных / простой записи кластера · 🟠 ошибки и риски операций ·
🟡 ограничения и эксплуатация · ⚪ второстепенное.

## 2. Переезды и репликация

### P1. Соединения-«призраки» после flip 🔴
**Сценарий.** После etcd-транзакции (routing/N → shard2) у инстансов приложения ещё живут
соединения в пуле к pg_doorman старой ноды. Транзакция, начатая/прилетевшая туда **после**
flip, реплицирована не будет: прямая подписка срезается (`DROP SUBSCRIPTION`) сразу после
переключения. Запись теряется молча.
**Усилители.** Длинные транзакции; инстанс, не увидевший FROZEN (см. P10); переходящие
соединения пула doorman, удерживающие сессии «на всякий случай».
**Детекция.** На старом мастере после flip: активные сессии приложений этого бакета
(`pg_stat_activity`; различимость — per-bucket роль, см. решение). Постфактум: сверка
counts/checksums таблиц.
**Решение (выбрано 2026-08-19): per-bucket read-only через REVOKE.** На старом шардЕ,
ещё в фазе FROZEN — **до capture LSN**:

```sql
-- на источнике: заморозка становится железной на уровне БД, а не договорённостью
BEGIN;
SET lock_timeout = '5s';
REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON ALL TABLES IN SCHEMA bucket_N FROM app_role;
REVOKE USAGE, UPDATE ON ALL SEQUENCES IN SCHEMA bucket_N FROM app_role;
-- nextval даёт И USAGE, И UPDATE — отбираем ОБЕ (проверено на стенде: отобранное
-- только UPDATE всё ещё позволяет nextval через USAGE)
-- mover-роль НЕ трогаем: обратная (rollback) репликация продолжает писать
-- при разморозке/откате — симметричный GRANT; после flip REVOKE держим до финализации
LOCK TABLE bucket_N.<все таблицы схемы> IN ACCESS EXCLUSIVE MODE;  -- вот барьер
COMMIT;
```

Свойства:
- призрак получает **громкую** `permission denied` вместо тихой потери; ретрай уводит
  его на новый шард через свежий роутер; защита живёт на стороне приёмника и не зависит
  от протокания кэша роутера (P10);
- ⚠️ **поправка по итогам стенда (PG 18.4)**: сам REVOKE барьером НЕ является — он
  берёт лишь `AccessShareLock` и при живом писателе проходит за доли секунды
  (замерено: 0.05с при открытой пишущей транзакции). Барьер — `LOCK TABLE ...
  IN ACCESS EXCLUSIVE MODE` той же транзакцией сразу после REVOKE: он физически
  ждёт завершения всех транзакций, державших блокировки на таблицах (включая
  долгие SELECT) — **после его COMMIT писателей доказательно нет**, capture LSN
  чист без надежды на честность приложения;
- порядок обязателен: REVOKE + барьер до capture LSN, иначе поздний писатель
  закоммитится уже после захвата позиции.

Требования и нюансы:
- приложение ходит **отдельной app-ролью, не владельцем схемы** (owner пишет вопреки
  REVOKE); per-bucket различимость сессий в `pg_stat_activity` — бонус той же роли;
- зависший `idle in transaction` заблокирует REVOKE → `lock_timeout` + terminate по
  `pg_stat_activity` + ретрай; `FREEZE_WAIT` ≥ p99 write-транзакций остаётся смягчением;
- опциональный второй слой — Pause пула бакета в pg_doorman — СНЯТ: при инварианте
  единой БД (P14) пул на ноду один, per-bucket Pause не существует; заморозка
  держится на REVOKE + LOCK (P1), от пулера не зависит.

**Отклонённые направления.**
- *Демиция Patroni (нода → реплика)*: даунтайм записи ВСЕХ бакетов шарда, и проблема не
  решается — шард-источник жив, призрак переподключится к новому мастеру того же шарда
  и продолжит писать в чужую схему. Уместна только при демонтаже шарда (переезд
  последнего бакета).
- *`default_transaction_read_only = on` + reload*: действует только на НОВЫЕ транзакции —
  уже открытая писающая закоммитится успешно.
- *Terminate сессий бакета + повторная проверка LSN перед `DROP SUBSCRIPTION`*:
  поглощается связкой REVOKE + LOCK-барьер; terminate остаётся инструментом разбора
  зависших `idle in transaction` (блокируют LOCK до `lock_timeout`).

### P2. Подписка не следует за мастером источника 🔴
**Сценарий.** `CREATE SUBSCRIPTION ... CONNECTION 'host=<мастер>'` содержит
**статический хост** конкретной ноды. Failover/switchover источника во время SYNCING →
подписчик продолжает ломиться в мёртвую/readonly ноду; репликация стоит.
**Последствия.** Вместе с P3 — полный re-copy; само по себе — простой репликации до
вмешательства.
**Детекция.** `pg_stat_subscription` на приёмнике: worker не активен / `latest_end_time`
стареет; алерт.
**Решение (выбрано 2026-08-19): подписки через HAProxy шарда.** HAProxy остаётся в
инфраструктуре каждого Patroni-кластера (docs 01–10) — используем его как точку входа
репликационного трафика переездов: conninfo прямой подписки (`sub_bucket_N`) указывает
на HAProxy :5432 шардА-источника, обратной (`sub_bucket_N_rb`) — на HAProxy нового
владельца. Health-check `/primary` сам переключает бэкенд при failover/switchover:
подписчик переподключается уже к новому мастеру, watcher'ы и `ALTER SUBSCRIPTION ...
CONNECTION` не нужны.
Границы решения:
- закрывает только **адресацию**. Выживание слота при failover — отдельный P3:
  подписка подключится к новому мастеру и не найдёт слот `sub_bucket_N`;
- HAProxy снова зависимость — но только репликационного трафика: его даунтайн влияет
  на переезды (SYNCING), не на рабочий трафик приложений (роутер + doorman);
- адреса HAProxy шардов — константы конфига mover'а (меняются редко); HA-вариант
  (пара HAProxy + keepalived VIP, 08-operations.md §7) — подключить при необходимости.
**Отклонённые направления.** Watcher с `ALTER SUBSCRIPTION ... CONNECTION` и DNS с
коротким TTL — избыточны при живом HAProxy; «мини-HAProxy только для репликации» —
поглощено использованием существующего HAProxy.

### P3. Логический слот теряется при failover источника 🟠
**Сценарий.** Слот живёт на мастере; на репликах его по умолчанию нет. Failover →
позиция подписки потеряна, даже если проблему P2 решить.
**Детекция.** Слот `sub_bucket_N` отсутствует на новом мастере.
**Решение (выбрано 2026-08-19): failover slots PG17+.** Включить в Patroni/Spilo-конфиг
(bootstrap/DCS) каждого шарда: `sync_replication_slots = on` (на репликах) +
`hot_standby_feedback = on` + `max_slot_wal_keep_size` (страховка, связка с P4).
Слоты синхронизируются на реплики; при promote подписка (через HAProxy — P2)
подключается к слоту на новом мастере.

**Проверено на стенде (PG 18.4, `arch/stand/`)**: слот `failover = true` в состоянии
`synced` на реплике пережил отказ мастера (`docker stop`) + promote; подписка
переподключилась через HAProxy без смены conninfo; replication origin пропустил
повторную доставку — 0 ошибок duplicate key, apply жив. Рецепт, без пунктов которого
не работает (все три обязательны, найдены на стенде):
- подписка создаётся сразу с `WITH (failover = true)`; включать потом — только
  вне транзакции и на отключённой подписке: `DISABLE` → `SET (failover)` →
  `ENABLE` тремя отдельными командами;
- у реплики физический слот от мастера: `primary_slot_name`
  (`pg_basebackup -C -S ...`) — без него `sync_replication_slots` молча не работает;
- в `primary_conninfo` реплики обязателен `dbname` — синхронизации слота нужна
  подключаемая БД.

Нюанс: сразу после initial copy слот на реплике может отставать (в логах реплики
`could not synchronize slot ...` — скачок `catalog_xmin`); промо в этом окне
**теряет слот** → перед допуском переезда к cutover проверять `synced = true`.
Остались непроверенными на стенде: возврат ноды через `pg_rewind` (слоты
пересоздаются через sync, не битые), плановый switchover; failover во время
initial copy — поведение мутное (промежуточные состояния `pg_subscription_rel`),
fallback — re-copy (drop sub → drop schema → повтор move, §7 доки 11).
Принятый риск (слотами не решается): при async-репликации и потере транзакций на
failover подписчик мог уже применить то, чего нет на новом мастере → расхождение.
Полное закрытие — `synchronous_mode` кластера-источника (цена: латентность записи
всего шарда) — отдельное решение по каждому шарду.

### P4. Слот держит WAL 🟠
**Сценарий.** Пока подписка жива, слот удерживает WAL на источнике. Initial copy большого
бакета + тишина на источнике не помогают: WAL копится до подтверждённого LSN. Диск
источника переполняется → кластер источника целиком встаёт (влияние на ВСЕ бакеты шарда).
**Детекция.** Алерты: `pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn) > X`,
размер `$PGDATA/pg_wal` > 80%.
**Решение (выбрано 2026-08-19).** Риск доступности, не данных: при любом исходе (срезали
подписку, слот инвалидировался, откат) бакет остаётся на источнике в ACTIVE и
консистентен — теряется только время. Четыре составляющие:
- **`max_slot_wal_keep_size` как изоляция взрыва** (уже включён в P3, здесь — главная
  роль): без лимита disk full кладёт ВЕСЬ шард со всеми бакетами; с лимитом PG
  инвалидирует слот — умирает только переезд. Лимит подобран так, чтобы хватало на
  штатные переезды, но он меньше диска;
- **детекция тихой инвалидации**: алерт по `safe_wal_size` ДО порога; в `status`/
  ожидании cutover проверять `wal_status = 'lost'` — иначе скрипт молча упирается
  в таймаут вместо понятной ошибки;
- **прогнозный префлайт** (не «место есть сейчас»): удержанный WAL ≈ write_rate ×
  длительность SYNCING (initial copy читает таблицы, WAL не генерируя; копится новая
  запись). Сэмпл скорости генерации WAL × оценка времени копирования (размер схем /
  скорость) × запас — против свободного места; место считать **на всех нодах шарда**
  (synced-слоты P3 удерживают WAL и на репликах);
- **мониторинг во время move** (лаг слота, размер `pg_wal` > 80%) + аварийная процедура
  срезания = `move-bucket.sh rollback` (уже есть; срезает подписку и слот, WAL
  освобождается).

**Проверено на стенде (PG 18.4, `arch/stand/`)**: при активном молчащем потребителе
(walsender жив, подтверждений нет) `wal_status` дошёл до `lost` за 1–3 пачки
несжимаемого WAL поверх лимита; инвалидировался слот, шард продолжил писать и
читать — изоляция работает. ⚠️ Нюанс: **неактивный** слот при плавной записи НЕ
инвалидируется — checkpoint'ы подтягивают его `restart_lsn`; лимит ловит реальный
сценарий «подписчик подключён и молчит» и всплески генерации. На стенде молчащего
потребителя эмулирует `slowconsumer.pl` (репликационный протокол без подтверждений;
`pg_recvlogical` не годится — отвечает на keepalive и подтверждает flush).

### P5. DDL не реплицируется 🟠
**Сценарий.** Логическая репликация не переносит DDL. Публикация `FOR TABLES IN SCHEMA`
подхватывает **новые таблицы** на публикаторе, но на подписчике их нет → apply падает.
Также: миграции между переездами обязаны применяться идентично на все шардЫ; пропуск шарда
создаёт дрейф, который взорвётся на следующем переезде этого бакета.
**Детекция.** Ошибка apply в `pg_stat_subscription`/логах подписчика; сверка
`pg_dump --schema-only` между шардами.
**Решение (выбрано 2026-08-19): запрет DDL в окне move + двойная сверка.**
- Мораторий становится техническим: `REVOKE CREATE ON SCHEMA bucket_N` на источнике
  **и** приёмнике (новых таблиц не появится — публикация не подхватит то, чего нет на
  приёмнике); `ALTER`/`DROP` существующих закрыты тем, что app-роль ≠ owner (синергия
  с P1); DDL выполняет только миграционная роль-владелец — для неё процедурный
  мораторий в окне move, правами владельца не остановить → страховка детекцией.
- Порядок: **запрет → сверка → move**. Пре-сверка до запуска initial copy: фактические
  схемы источника и приёмника против эталона (шаблон + журнал миграций).
- **Контрольная сверка перед flip** (после SYNCING): initial copy долгий, между
  префлайтом и cutover мог уехать DDL; расхождение → отказ cutover.
- Окно запрета = префлайт → **finalize** (не до flip): после flip схема источника ещё
  нужна обратной подписке, ALTER на ней сломал бы apply.
- Finalize = снять запрет (GRANT CREATE) + срезать артефакты + `DROP SCHEMA CASCADE` —
  данные источника больше не нужны (шаг уже есть в скрипте).
- Против дрейфа между переездами: миграция адресуется **бакету** и применяется на его
  текущем владельце (из etcd), журнал миграций обязателен.

### P6. Sequences 🟡
**Сценарий.** `setval(max(id)+margin)` — эвристика. Ломается, если sequence используется
не как инкремент PK (кастомные `nextval`, дыры, несколько sequence на таблицу), либо
margin выбран меньше, чем вставок успевает произойти между setval и открытием записи.
**Детекция.** Дубликаты PK после переезда/отката.
**Решение (выбрано 2026-08-19): синхронизация sequence→sequence + инвариант-проверка
перед flip.** Sequence — независимый объект: таблица может использовать его как угодно
или не использовать вовсе (явные значения, свои ограничения) ⇒ единственный авторитет
выданных значений — сам счётчик. **Никакой привязки к max(id) из таблиц.**
- `sync_sequences`: на приёмнике `setval(last_value источника)` — поимённо для всех
  sequence схемы. Margin не требуется: источник заморожен (REVOKE из P1 закрыл и
  nextval — privilege UPDATE), окно между setval и flip закрыто заморозкой;
- инвариант-проверка непосредственно перед flip: следующее выдаваемое значение на
  приёмнике **> последнего выданного на источнике** (читается `last_value`/`is_called`
  обычным SELECT — nextval не вызываем, значения не сжигаем). Расхождение или
  отсутствие sequence на приёмнике → отказ cutover с разморозкой: тихий будущий
  duplicate key становится громким отказом;
- при rollback — та же механика в обратную сторону: заморозить нового владельца →
  прочитать его `last_value` → `setval` на старом;
- перебор всех sequence схемы, не только привязанных к колонкам (`deptype 'a'/'i'`) —
  ловит отдельно созданные sequence и дрейф схем (P5).

### P7. Артефакты незавершённых переездов 🟡
**Сценарий.** Сорванный move оставляет pubs/subs/slots/схему в промежуточном состоянии;
следующий move упирается (скрипт отказывает — это хорошо, но разбираться руками).
`DROP SUBSCRIPTION` требует доступности источника (срезает слот удалённо).
**Детекция.** `abort-move.sh list` перед каждым move — статус-ключи `/buckets/status/*`
и есть реестр незавершённых переездов (нет ключа = ACTIVE); `abort-move.sh artifacts
<bucket>` — инвентаризация артефактов по всем шардам (read-only).
**Решение (выбрано 2026-08-19): `abort-move.sh abort` — отмена с журналом в etcd**
(состояние переезда читает из etcd-контрол-плейна). Порядок — journal-before-manipulations:
- **журнал до манипуляций**: прежде чем тронуть БД, скрипт переводит статус-ключ
  `/buckets/status/N` в `state=ABORTING` с планом уборки (что и на каком шарде
  будет удалено) и `phase`; крах уборки оставляет в etcd самодокументирующийся
  след (`phase=failed/blocked` + `last_error`), повторный запуск продолжает —
  все шаги идемпотентны, каждый перепроверяет существование объекта;
- **порядок уборки**: подписки (везде) → слоты → публикации → re-GRANT на владельце
  (снятие заморозки P1: DML + USAGE,UPDATE на sequences; и моратория P5: CREATE)
  → `DROP SCHEMA` на НЕ-владельцах (последним, с данными). Владелец определяется
  только по `/buckets/routing/N`, его схема не трогается никогда;
- **недоступный источник подписки** (`DROP SUBSCRIPTION` не может срезать слот
  удалённо): `DISABLE` → `SET (slot_name = NONE)` → `DROP` — слот-сирота добивается
  на источнике отдельно (terminate walsender'а + `pg_drop_replication_slot`);
  недоступен целый шард → журнал `phase=blocked`, уборка не начинается: с неполной
  инвентаризацией не работаем;
- **успех** = удаление статус-ключа (нет ключа = ACTIVE), routing не меняется:
  abort ≠ переезд, бакет остаётся у текущего владельца. Статус без routing и
  routing без статуса (остатки частичного flip) — определяются и обрабатываются;
- **routing уже указывает на target = flip прошёл** (статус-ключ завис —
  вырожденный случай неатомарного cutover; штатный cutover — атомарная
  etcd-транзакция, такого состояния не даёт): без `--force` — отказ без
  каких-либо действий; с `--force` abort работает как **доведение перевода**
  (finalize-семантика): владелец-приёмник не трогается, старый шард вычищается,
  sequences владельца **доводятся до последних выданных на старом шарде**
  (P6: последовательности не реплицируются — нештатный cutover без шага 4.5
  оставил бы у владельца гарантированные duplicate key; setval строго вперёд —
  пост-flip записи уже расходовали значения владельца). До flip (routing=старый
  владелец) всё сделанное обратимо — abort откатывает, записей на приёмнике
  до flip не бывает, потерь нет;
- **защита от убийства живого move**: отказ, если статус обновлён свежее
  `ABORT_MIN_AGE_SEC` секунд (mover ещё может работать); `--force` — осознанное
  решение оператора. Abort на бакете без статус-ключа отказывает и отправляет
  к `finalize` (пост-flip остатки — это не abort).

**Проверено на стенде (PG 18.4, `arch/stand/`, `checks/60-p7-abort.sh`, две фазы)**.
Фаза 1 — зависший FROZEN (REVOKE-заморозка на источнике, живая подписка + схема
на приёмнике, статус в etcd): отказы на ACTIVE-бакете и свежем статусе; недоступный
приёмник → журнал `phase=blocked`, БД не тронута (журнал строго до манипуляций);
повтор после возврата шарда → артефактов нет, данные владельца целы, права app-роли
возвращены (запись + CREATE), статус-ключ удалён, routing прежний. Фаза 2 —
routing==target (flip прошёл, статус завис, sequences у приёмника НЕ синхронизированы):
без `--force` отказ без каких-либо действий; с `--force` перевод доведён — приёмник
остался владельцем с данными, старый шард вычищен, sequences довинчены
(`setval(50)` при выданных 50 — следующее 51), запись app-роли работает. Для
этого в стенд добавлены одиночный etcd (контрол-плейн) и «ops-бокс»
(psql+etcdctl+jq, профиль `ops`) — скрипты работают по внутренней сети
стенда, хостовые бинарики не нужны.
**Отклонённые направления.** Автоуборка при старте следующего move («тихо почистить
и поехать») — молча съедает данные копии на приёмнике при ложном выводе о смерти
прошлого move; уборка без журнала в etcd — сбой посреди неё оставляет
недокументированный полуразобранный набор артефактов (ровно тот случай,
ради которого журнал введён).

### P8. Failover приёмника во время SYNCING 🔴
**Сценарий.** Подписка — объект каталога PG, физическая репликация перенесёт её на
нового мастера приёмника, соединение переустановится (conninfo ведёт на HAProxy
источника и не меняется — P2 не мешает). Но есть **тихая потеря данных**: apply-воркер
применяет транзакции на мастере приёмника и подтверждает их источнику сразу —
`confirmed_flush_lsn` (feedback) убегает вперёд физической репликации приёмника
на величину её лага. Failover приёмника в этом окне: standby повышен, а walsender
источника отдаёт изменения только от `confirmed_flush` → **срез изменений между
позицией standby и confirmed_flush пропускается МОЛЧА**. Стрим при этом «здоров»
(лаг слота 0, новые строки доезжают) — дефект невидим для лаг-метрик и проявится
позже как расхождение данных.
**Детекция.** В процессе — никак (метрики «здоровы»); перед flip — сверка строк
`count(*)` по всем таблицам схемы источник/приёмник; постфактум — сверка
counts/checksums.
**Решение (выбрано 2026-08-21): `synchronous_commit = remote_apply` у подписок
переезда + сверка строк перед flip.** Переезд по определению предполагает нормальную
работу обоих кластеров — используем это:
- подписки переезда (прямая и обратная) создаются с `synchronous_commit = remote_apply`:
  коммит применённой транзакции на мастере приёмника ждёт, пока standby приёмника её
  **проиграет** (видно как SyncRep-ожидание apply-воркеров) — feedback физически не
  может убежать вперёд replay-позиции standby → после failover срез изменений
  **пересылается и применяется**, а не пропускается;
- remote_apply работает только при живом sync-standby у мастера приёмника (без него
  синхронная фиксация тихо вырождается в асинхронную) → preflight `move` проверяет
  `synchronous_standby_names` и подключённый sync/quorum-standby в `pg_stat_replication`
  и **отказывает** без него («переезд требует здоровых обоих кластеров»);
- цена: применённые транзакции переезда ждут replay на standby приёмника — чуть
  медленнее репликация переезда; рабочий трафик приложений не затрагивается;
- mover транзиенто-толерантен: обрывы соединения к приёмнику (идёт failover) не убивают
  move — бюджет недоступности `CONN_FAIL_BUDGET_SEC` в циклах ожидания;
- failover посреди initial copy рестартует синхронизацию таблицы **новым**
  tablesync-слотом → старые остаются сиротами: `finalize` добивает неактивные
  `sub_bucket_N_sync_%`;
- **P8-барьер перед flip**: сверка строк по всем таблицам схемы — если защита не
  сработала и копия дефектна, cutover отказывает с разморозкой; лечение — `abort`
  (P7) и повторный move (свежий initial copy переприготовит копию).

**Проверено на стенде (PG 18.4, `arch/stand/checks/70-p8-receiver-failover.sh`)`,
две фазы одного сценария.** RED — подписка с дефолтным `synchronous_commit=off`:
standby отключён → W1 (100 строк) применяется на мастере приёмника и подтверждается
(confirmed_flush убегает) → мастер умирает, standby повышен → срез W1 пропущен
**молча** (лаг слота 0, post-failover строка доезжает — стрим «здоров»); вылечено
`abort-move.sh` (P7). GREEN — `move-bucket.sh` с remote_apply: replay-пауза standby →
W2 не подтверждается, apply-воркер висит в SyncRep → смерть мастера приёмника +
promote standby → W2 переслан и применён; mover пережил обрывы, initial copy большой
таблицы рестартовал на новом мастере, cutover прошёл со сверкой строк и атомарным
etcd-flip, finalize добил осиротевшие sync-слоты.
**Отклонённые направления.**
- *Ничего не делать* («подписка — объект каталога, переустановится сама»):
  адресация восстанавливается, но срез изменений между confirmed_flush и позицией
  standby теряется молча — риск повышен до 🔴.
- *Только сверка строк*: ловит дефект перед flip, но каждый failover приёмника
  посреди SYNCING заканчивается abort + полным re-copy.
- *`synchronous_commit = on`*: страхует диск мастера приёмника, но не отставание
  standby — feedback всё равно убегает; закрывает именно `remote_apply`.

## 3. Контроль-плейн etcd

Отказы самого контрол-плейна **алертятся внешними системами мониторинга** — это
вне скоупа данного реестра; здесь фиксируются поведение системы при отказах и
границы ответственности. Исключение — P11: внутренняя согласованность кластера
(«ключ /master ↔ фактический primary») — наш контур: сверяющий демон с
автокоррекцией; внешний мониторинг в нём только алертит.

### P9. Недоступность etcd 🟠
**Сценарий.** etcd недоступен (кворум потерян / сеть / обслуживание): watch'ы стоят,
новые маршруты не выдаются, переезды и смена мастер-ключей невозможны. Уже открытые
соединения приложений работают. **Мульти-кластерность**: один etcd — общий фонд
отказов ВСЕХ обслуживаемых систем (запас по квоте `--quota-backend-bytes` и
деплой отдельно от нагруженных сервисов); смягчение — префиксы изолируют
состояния, отказ бьёт по маршрутизации, не по данным.
**Открытый вопрос → решён. Политика роутера (выбрано 2026-08-22): fail-open —
работать по last-known-good кэшу без лимита времени.**
- Ключевое свойство: пока etcd лежит, контрол-плейн **заморожен** — mover не может
  сделать cutover (нужна etcd-транзакция), Patroni не может сделать failover
  (DCS тот же etcd) → кэш не может протухнуть из-за изменений контрол-плейна:
  последний известный маршрут консистентен с реальностью неограниченно долго;
- смерть мастера при лежащем etcd всё равно кладёт запись шарда (репликам не на чем
  взять лидерский lock без DCS) — простой до восстановления неизбежен при любой
  политике: fail-open не ухудшает, fail-closed не спасает;
- отказ координации не должен превращаться в простой приложений: уже открытые
  соединения и так работают, fail-open распространяет это на новые подключения
  (пулы на шард уже живут);
- границы: **новый/перезапущенный инстанс приложения забутстрапиться не может**
  (статика — только адреса etcd) — принятое ограничение, лечится восстановлением
  etcd; переезды в окне недоступности невозможны (mover откажет на etcd-операциях).
**Отклонённые направления.** Fail-closed (отказ в новых подключениях) — превращает
отказ координационного сервиса в простой ВСЕХ систем при живых данных; TTL кэша
с лимитом last-known-good — та же деградация, но резкая и по таймеру при длительном
отказе; локальный снапшет маршрутов на диск — закрывает только редкий составной
случай «рестарт инстанса при лежащем etcd», добавляя риск стейл-снапшота.
Детекция и восстановление etcd — внешний мониторинг, вне скоупа (см. шапку раздела).

### P10. Расходимость кэшей роутеров 🔴 — корневая причина P1
**Сценарий.** Инстансы приложения получают flip/FROZEN в разное время (задержка watch,
рваные реконнекты). В любой момент разные инстансы считают владельцем разные шарды.
Запись в SYNCING старому владельцу безопасна (репликация догонит), запись после flip
старому владельцу — это P1.
**Детекция.** Разброс версий/таймстампов маршрутов по инстансам (метрика приложения).
**Решение (выбрано 2026-08-22): расходимость не устраняем — гарантию даёт заморозка
старого владельца (P1) + контракт приложения.** Целостность обеспечивается не
консенсусом роутеров, а технической невозможностью записи в старого владельца:
- запись в старого владельца **невозможна по правам**: REVOKE + LOCK-барьер P1
  (проверено на стенде: app-роль получает `permission denied`, включая `nextval` —
  отобраны и USAGE, и UPDATE на sequences). Опоздавший инстанс не может записать
  в никуда молча — только громкая ошибка;
- контракт приложения: любая ошибка записи (FROZEN-retryable, `permission denied`
  призрака, обрыв соединения при failover) → сброс кэша маршрута (routing/bucket +
  shards/X/master) → refetch из etcd → ретрай. Обработка ошибок записи —
  **ответственность приложения**, ровно как при переезде бакета или шарда;
- watch + периодический refetch (§3 доки 11: «кэш с TTL секунды, инвалидация
  watch'ем») остаются как ускоритель конвергенции — смягчение, не гарантия.
**Отклонённые направления.** «Барьер подтверждений» перед flip (счётчик инстансов,
видевших FROZEN) — дорогая координация всех инстансов, не даёт гарантий сверх
REVOKE-барьера; закладка границы конвергенции в FREEZE_WAIT как гарантия — оценка
времени вместо механизма, остаётся смягчением в P1.

### P11. Писатель /clusters/<C>/shards/*/master 🟠
**Сценарий.** Ключ пишет Patroni-callback (`on_role_change`).
Подводят: упавший скрипт, пропущенное событие, истёкший lease, гонка «старый мастер
демотирован / новый повышен». Callback обязан знать **имя кластера `<C>` и шарда**
(конфигурация скрипта на ноде) — ошибка в ней пишет мастер-ключ в чужой префикс.
Отдельно: даже при исправном ключе между фактическим failover и обновлением ключа
есть окно (TTL Patroni ~30с + задержка писателя) — в этом окне приложения получают
ошибки записи (сравнимо с health-check-окном HAProxy, но теперь это наша зона
ответственности).
**Детекция.** Мониторинг: ключ есть, lease свежий, значение совпадает с `/primary`
Patroni; протухший lease = алерт.
**Решение (выбрано 2026-08-22): окно ~5с (Patroni `ttl=5/loop_wait=2`) + lease TTL 5с
с продлением от мастера; двойной контроль (сверка с Patroni REST + автокоррекция) —
наш сверяющий демон.** Три класса отказов писателя закрываются по-разному:
- **окно ошибок записи при failover** (было ~30–40с: ttl 30 + loop_wait 10 в
  `configs/postgres/pg.env`): Patroni подкручен до `ttl=5, loop_wait=2,
  retry_timeout=3` → типичное окно ~5–8с от смерти мастера до нового ключа,
  worst ~10с (обнаружение ≤ ttl+loop_wait + promote 1–3с + put ~1с). Честные ≤5с
  потребовали бы ttl=3 — не рекомендовано: лидерский lease переживает всего один
  потерянный heartbeat, растёт риск ложных failover при сетном дрожании. Цена
  подкрутки — heartbeat в DCS каждые 2с; Patroni на docker-стенде отсутствует —
  проверить на первом деплое (следить за ложными failover);
- **смерть ноды-мастера / гонка «старый демотирован, новый повышен»**: ключ живёт
  под lease TTL 5с, продлевается процессом на мастере (стартует `on_role_change`)
  не реже раза в 1–2с — переживает 2–3 потерянных продления. Нода умерла / сеть
  отвалилась / нода демотирована (событие role=replica останавливает продлеватель) →
  ключ гаснет сам ≤5с, роутер отказывает в новых подключениях к шарду, не тыкая
  в мёртвый адрес. Стендовая инкарнация механики — `stand/sidecar/rolecheck.py`
  (переведён на LEASE_TTL=5, KEEPALIVE=1с; механика регистрации/истечения
  проверялась чеком 68 при TTL 15с — после смены таймингов перепрогнать);
- **«писатель подводит»** (упавший скрипт, пропущенное событие, старая нода
  продолжает продлевать, не зная о демоушене): **двойной контроль — наш
  компонент, не внешняя система**: контроль внутренней согласованности кластера
  и приведение в согласованное состояние — обязанность кластера. Сверяющий
  демон (на нодах шарда) периодически опрашивает Patroni REST (:8008) нод
  и сравнивает с `/clusters/<C>/shards/X/master`: у кого роль primary — тот
  и должен стоять в ключе. Расхождение → **автоматическая коррекция**: демон
  восстанавливает ключ по фактическому primary (lease-put + продление).
  Закрывает: ключ протух при живом primary (callback упал) — пересоздаётся;
  ключ указывает на реплику или мёртвую ноду (пропущенное событие, гонка
  демоушена) — перезаписывается. Против гонки двух сверяющих демонов шарда:
  оба читают один источник правды (REST) и пишут одно значение, коррекция —
  только по расхождению (штатную запись callback'а не дублирует). Ошибка
  конфигурации callback'а «ключ в чужом префиксе» этим демоном не ловится
  (следит за своим префиксом) — внешний мониторинг; канареечная запись
  (INSERT+DELETE в служебную табличку по полному пути роутер → doorman → PG) —
  опциональный симптом-детектор: ловит невалидность маршрута любой природы,
  но не показывает причину.
**Детекция.** Сверка и автокоррекция — нашим сверяющим демоном; алерты
(коррекция произошла, ключ не сходится N секунд) — внешний мониторинг.
**Отклонённые направления.** «Второй регулярный писатель» (демон переписывает
ключ по расписанию параллельно callback'у) — источник гонок; принят корректор
по расхождению: источник правды REST, пишет только при рассинхроне. Опрос
Patroni REST из роутера — второй источник правды рядом с etcd, усложняет
P9/P10 вместо решения P11.

### P12. Потеря/restore etcd-контрол-плейна 🟡
**Сценарий.** Потеря etcd = потеря карты бакетов и мастер-ключей (данные на местах,
но маршрутизация неизвестна). Restore из бэкапа может быть устаревшим относительно
последнего flip/failover. Снапшот покрывает все кластеры сразу — и restore
возвращает ВСЕ системы к моменту снапшота. DSN в etcd без паролей: утечка снапшота
не раскрывает секреты, но раскрывает топологию (P17).
**Решение (выбрано 2026-08-22): все три направления + обязательные снапшоты
в точках переезда + `restore-cluster.sh` (restore → verify → heal).**
- **Снапшоты**: регулярные (`restore-cluster.sh snapshot`, cron ops-бокса;
  каталог SNAPSHOT_DIR — persistence-volume: `snapshot save` пишет файл на
  клиенте) + **обязательные в точках каждого переезда, снимает сам mover**:
  сразу после начала (SYNCING зафиксирован) и сразу после flip (транзакция
  атомарна, статус-ключа уже нет — снапшот согласован по построению). Это
  сужает сверку при восстановлении: ближайший снапшот точки даёт карту с
  известной фазой переезда, а не «неизвестно что»;
- **Сверка восстановленной карты с фактом** (`verify`): routing × фактические
  схемы `bucket_*` на шардах — список схем восстанавливает истину. Классы:
  routing без схемы при единственной схеме на другом шарде и схема без
  routing — однозначные (лечатся `heal`); схема на двух шардах — окно
  переезда (подсказка: `move --resume` / `abort`, P7); копия на не-владельце
  без статуса — `finalize`; зависший статус при routing==target — `abort
  --force`; схемы нет нигде — данных нет, восстановление шарда из бэкапа
  (08-operations.md), контрол-плейн не лечит;
- **Автовосстановление** (`heal`): переписывает routing ТОЛЬКО в однозначных
  случаях, журнал до манипуляции в `/clusters/<C>/heals/<bucket>` (по образцу
  P7), etcd-транзакция с compare — routing, изменившийся под руками, не
  трогается. Физический restore etcd — командой `restore`: на docker-стенде
  автоматически (stop → пересоздание data-dir из снапшота → start), на
  прод-хосте печатает процедуру (restore в НОВЫЙ data-dir → подмена → старт;
  кластер 3+ нод — restore на одной, остальные добавляются member add);
- **Порядок восстановления** (прод): поднять etcd из снапшота → `verify` →
  `heal` → `verify`. Дробить «на систему: config → shards → routing» не
  нужно — снапшот атомарен; мастер-ключи `shards/X/master` в restore не
  нуждаются — их заново пишут живые Patroni-callback'и (P11). Снапшот общий
  для всех кластеров etcd → `verify`/`heal` прогнать по каждому `--cluster`.
**Детекция.** Внешний мониторинг: свежесть последнего снапшота (алерт
«старше N часов» — регулярность сорвалась); после инцидента — `verify`
показывает расхождения поимённо.
**Отклонённые направления.** Восстанавливать routing только из снапшота без
сверки с фактом — устаревший снапшот молча направит трафик на шард без данных;
автоочистка схем-дублей в heal — окна переездов неоднозначны, их разбирают
штатные move/abort/finalize, а не restore-скрипт; побайтовое/по-ключевое
восстановление — снапшот атомарен, восстанавливается целиком.
**Проверено на стенде (PG 18.4, `arch/stand/checks/74-p12-restore.sh`, 2026-08-22)**:
кластер gamma — настоящий move снимает снапшоты обеих точек (`move-<b>-start`,
`flip-<b>-<X>`); stop etcd → hap1/hap2 продолжают обслуживать запись (P9
fail-open, hasync держит адреса); уничтожение data-dir → пустой etcd при живых
данных; `restore` из УСТАРЕВШЕГО (до-flip) снапшота с хоста вернул карту
(routing=bucket_0→s1 при схеме на s2); `verify` поймал расхождение поимённо →
`heal` переписал routing с журналом `/heals/*` → контрольный `verify` 4/4;
соседний кластер alpha вернулся из общего снапшота нетронутым. Полный цикл
чеков 00→74 зелёный.

## 4. Пулер и подключения

### P13. Ограничения transaction pooling 🟠
**Сценарий.** Сессионное состояние между транзакциями не сохраняется: `SET` (session),
temp tables, `LISTEN/NOTIFY`, **session-level advisory locks** (`pg_advisory_lock`),
курсоры между транзакциями. Приложение, не знающее про пул, ловит сюрпризы.
**Решение (2026-08-22): `pool_mode: "transaction"` в единственном пуле `<dbname>`
(имя = имя кластера, P14) — проверено по официальной документации, включаем.** Режим есть (аналог pgbouncer,
дефолт и рекомендованный режим doorman — фиксируем явно), именно он даёт
эффективность бюджета P15: pool_size 40 обслуживает тысячи клиентов при коротких
транзакциях. Что РАБОТАЕТ в transaction-режиме (снимает большую часть сценария):
prepared statements — именованные И анонимные (ремап в `DOORMAN_<N>`, кэш на пул;
pgx/Npgsql/asyncpg без настроек), COPY IN/OUT (оговорка doorman: поверх серверного
TLS не покрыт их BDD-сьютом), `SET LOCAL`, LISTEN внутри транзакции; зачистка на
возврате бэкенда — по факту мутаций (SET → RESET ALL + `pg_advisory_unlock_all`,
PREPARE → DEALLOCATE ALL, курсоры → CLOSE ALL). Остаточные ограничения → гайдлайны
«pool-aware code»: `SET`/`RESET` вне транзакции, advisory locks через транзакции
(→ `pg_advisory_xact_lock`), курсоры `WITH HOLD`, кросс-транзакционный LISTEN,
temp tables. Исключения-клиенты — нативный побег: per-user override
`pool_mode: "session"` малым `pool_size` (без отдельного пулера; в session-режиме
pool_size ≈ max клиентов). Попутное подтверждение архитектуры: replication
passthrough в doorman НЕТ — подписки переездов через HAProxy :5432 мимо пулера
(P2) — единственный путь.
**Детекция.** Аудит кода приложений на перечисленные паттерны.

### P14. Ключование пулов: dbname-алиасинг — СНЯТ инвариантом единой БД 🟠
**Сценарий (исторический).** Обсуждался план: клиент подключается с
`dbname=bucket_N`, пул doorman мапит его на серверную БД (алиасинг уровня
пулера; у doorman такой параметр есть — `server_database`). Предполагал
per-bucket пулы: изоляция «шумного бакета», Pause per-bucket, различимость
сессий для P1.
**Решение (2026-08-22): план снят — инвариант единой БД (пользователь).** БД
ОДНА на кластер: имя = имя кластера `<C>`, одинаковое на всех нодах и шардах;
бакеты `bucket_0..N-1` — **СХЕМЫ** в ней, НЕ базы. Подключение — с реальным
`dbname=<C>`; алиасинг/`server_database` не нужен; в doorman на ноде
ЕДИНСТВЕННЫЙ пул `<C>` → `127.0.0.1:5432`. Адресация бакета — схема:
квалифицированные имена (`bucket_N.table`) или `SET LOCAL search_path` в начале
транзакции (работает в transaction-режиме, P13).
**Следствия.** (а) `max_db_connections = 55` — кап единственного пула = ровно
бюджет ноды P15 (per-pool природа параметра перестаёт быть ограничением);
Pool Coordinator действует в рамках пула. (б) Per-bucket изоляция пулов
недоступна — «шумный бакет» ест общий бюджет: принято (честная FIFO-очередь
doorman; наблюдаемость per-bucket — `pg_stat_activity` по search_path /
application_name). (в) Pause пула бакета недоступен — опциональный слой
заморозки снят; P1 держится на REVOKE + LOCK, от пулера не зависит.
(г) P20: кросс-бакетные JOIN внутри шарда — работают (схемы одной БД);
между шардами — по-прежнему нет.
**Скрипты.** `init-cluster.sh --dbname` — конвенция: значение = имя кластера
(параметр остаётся). Стенд-чеки используют служебные dbname (postgres/beta) —
тестовая механика, к прод-конвенции отношения не имеет.

### P15. Бюджет соединений 🟡
**Сценарий.** `max_db_connections` (doorman, на ноду) + подписки при переездах
(walsender'ы и слоты) + админка + физическая репликация должны укладываться в
`max_connections`/`max_wal_senders` PG. Параллельные переезды умножают потребление.
**Решение (2026-08-22): `max_db_connections = 55`, `max_connections = 60`,
`max_wal_senders = max_replication_slots = 10`.**
Стороны пулера раздельно. Серверная (doorman → `127.0.0.1:5432`):
`max_db_connections = 55` — весь app-трафик ноды; рост числа бакетов бюджет
не меняет: cap общий на ноду, пулы не-владельцев пусты. Клиентская (приложения →
:6432) бюджетом PG не является: лимит 1000, если такой параметр в конфиге есть,
иначе без ограничений — клиентские соединения схлопываются пулом в 55 серверных.
`max_connections = 60` = 55 (doorman) + 2 (mover/админка, единовременно — впритык)
+ 3 (`superuser_reserved_connections`); walsender'ы с PG 13 НЕ занимают слоты
соединений — у них свои пулы. `max_wal_senders = max_replication_slots = 10`:
на переезд — 1 основной walsender + 2 tablesync (`max_sync_workers_per_subscription
= 2`, default) и столько же слотов, плюс 1 на реплику (физрепликация); запас — на
окно «зомби»-walsender'ов после failover приёмника (`wal_sender_timeout` 60с, P8)
и осиротевшие tablesync-слоты до finalize; лимит одновременных переездов с одного
источника — 3 (1 физслот + 3×3 = 10), ограничивает префлайт счётчиком слотов
(11 §5 шаг 0). Стенд держит собственные 16/16 — на его нодах несколько кластеров.
Значения внесены в [05](05-deploy-postgres.md) (плашка шарда) и
`configs/postgres/pg.env`.

### P16. Зрелость pg_doorman 🟡
**Сценарий.** Молодой проект: прод-использование есть (Ozon), но «war stories» мало.
Неизученные углы: поведение при таймаутах аутентификации, утечки памяти под нагрузкой,
граничные кейсы Pool Coordinator.
**Решение (2026-08-22): риск принят — проект считаем зрелым.** pg_doorman
эксплуатируется в проде (Ozon) на системах в тысячи раз более нагруженных, чем
планируемая здесь нагрузка: перечисленные «неизученные углы» (таймауты аутентификации,
утечки памяти, граничные кейсы Pool Coordinator) де-факто покрыты этой эксплуатацией.
Направления из сценария (стендовые нагрузочные тесты, откат на pgbouncer,
canary-бакеты) снимаются.

## 5. Сеть и безопасность

### P17. Порты нод наружу 🟡
**Сценарий.** Раньше наружу торчал только HAProxy. Теперь: 6432 (doorman) открыт всем
приложениям на каждой ноде, 5432 (PG) — нодам других шардов (подписки, mover) и админам.
Матрица firewall сложнее; компрометация ноды даёт прямой доступ к PG.
**Направления.** TLS на doorman; per-bucket роли с минимальными правами; firewall-матрица
в доке; решения по аутентификации doorman↔PG.

## 6. Модель шардирования

### P18. N — навсегда 🟡
**Сценарий.** Изменение N ломает хеш-маппинг всех тенантов. Выбранное без запаса N
ограничивает будущее число шардов (гранулярность баланса = 1/N ёмкости) и не даёт
«поделить» перегруженный бакет.
**Направления.** N из расчёта 16–32× от пикового числа шардов; фиксировать выбор N
с обоснованием в /buckets/config.

### P19. Hash-skew и крупные тенанты 🟡
**Сценарий.** hash(tenant) не гарантирует равномерность нагрузки; один гигантский тенант
перетягивает свой бакет (и шард). Внутри бакета не делим.
**Детекция.** Пер-бакетные метрики (QPS, размер) в мониторинге.
**Направления.** Карта исключений для «тяжёлых» тенантов (ключ в etcd, перекрывает
хеш — но тогда роутер обязан читать карту); консолидация мелких/крупных по метрикам.

### P20. Кросс-бакетные запросы 🟡
**Сценарий.** Между шардами — принято «нет». Внутри одного шарда JOIN схем bucket_A ×
bucket_B — обычный SQL: при инварианте единой БД (P14) все бакеты шарда — схемы
одной БД `<C>`, сессия подключена к ней напрямую.
**Направления.** Технически работает (P14 закрыт); осталось зафиксировать,
разрешены ли такие запросы в принципе (дизайн-решение приложения).

## 7. Эксплуатация

### P21. Наблюдаемость 🟡
**Сценарий.** Инцидент «куда сейчас пишет бакет N» решается etcd-ключами и
`move-bucket.sh status` — инструменты etcd должны быть в мышцах дежурных. Лаги слотов,
протухший lease мастера, зависшие не-ACTIVE статусы — всё должно алертиться.
**Направления.** Дашборд: бакеты × шарды × статусы × лаги; алерты из §9-11-дока;
runbook «где бакет» одной командой.

### P22. Бэкапы ⚪
**Сценарий.** Шарды бэкапятся независимо (рецепт в [08-operations.md](08-operations.md));
контрол-плейн etcd — отдельно (P12). Восстановление бакета = восстановление схемы на
шарде + ключ в etcd.
**Направления.** Свести в единый порядок восстановления (какая очередь восстановления:
etcd → шарды → каталог).

### P23. Жизненный цикл шарда: удаление непустого, гонки с переездами 🟡
**Сценарий.** Удаляется могут только пустые шарды — иначе:
(а) `remove-shard` шарда, на котором живут бакеты → routing указывает в никуда,
бакеты «теряются» из маршрутизации при живых данных;
(б) remove-shard параллельно с move, у которого `target` = этот шард → переезд
упирается в исчезающий шард посреди SYNCING;
(в) add-shard с именем существующего шарда → перекрытие dsn, тихая подмена адреса;
(г) крах init-cluster посередине → полуинициализированный префикс блокирует
повторный init (guard «префикс пуст»).
**Детекция.** Все сценарии — guard'ы скриптов (отказ до каких-либо действий);
контрольная сверка routing × фактические схемы на шардах (у validation переездов,
P21).
**Решение (выбрано 2026-08-21): guard'ы в скриптах жизненного цикла (§4.5 доки 11).**
- `remove-shard.sh`: отказ, если хоть один `routing` указывает на шард (список
  бакетов в отказе + подсказка мигрировать) или есть status с `target` = шард
  (незавершённый переезд). Удаляет только `dsn`/`replicas`; `master` гаснет сам
  по lease — мёртвый шард исчезает из роутинга без нашего участия;
- `add-shard.sh`: требует инициализированный `config` (нельзя добавить шард в
  несуществующую систему), отказывает при существующем `dsn`-ключе имени;
- `init-cluster.sh`: отказ при непустом префиксе `/clusters/<C>`; крах посередине
  безопасен — схемы пустые и идемпотентные, а полуинициализированный префикс
  чистится `etcdctl del /clusters/<C> --prefix` без риска для данных (бакетов
  ещё нет, при их наличии guard увидит непустой routing);
- `create-bucket.sh` в инициализированном кластере: только `bucket_0..N-1`
  (диапазон константы N, P18) — завести «лишний» бакет мимо init нельзя.
**Отклонённые направления.** Каскадное удаление «вместе с бакетами» — молча
теряет данные; перенос бакетов внутри remove-shard — смешение ответственностей
(переезд — отдельная команда с собственными гарантиями P1–P8).
