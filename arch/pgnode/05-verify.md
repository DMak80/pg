# PgNode: проверка полного (verify)

Уровень 3. Механика потоковой checksums-проверки полного на ноде.
Оркестрация verify (политика, статусы) —
[backups/01-full-backup.md](../backups/01-full-backup.md) §7; процесс —
[processes/c-verify.md](processes/c-verify.md); состояния —
[processes/enums.md](processes/enums.md).

## 1. Команда и реестр

`POST /api/ops/verify` от воркера на `alias:8080` ноды (`candidate.Node`;
S3-контекст read-списка — секреты ТОЛЬКО в POST, не в GET-статусах и не в
логах). Verify — ops-операция общего реестра: одна ops-операция на процесс;
полная операция (full) и ops-операция на одной ноде не блокируют друг друга.
Занятый реестр — 409 (воркер откладывает запуск; снимок 409 не различает
свою/чужую операцию).

## 2. Механика

Потоковый верификатор — без распаковки на диск и без staging:

1. Фаза `downloading`: фиксация endpoint'а чтения (первая нода read-списка,
   где HEAD находит объект) → Range-чтение хвоста объекта `full/<id>.tar`
   (последние 8 МиБ; manifest не найден и объект больше — удвоение диапазона,
   ограниченное числом попыток) → разбор tar-заголовков хвоста с валидацией
   checksum → `backup_manifest` (манифест — последняя запись данных
   tar-потока, предшествуя нулевой добивке). Исчерпание попыток при
   СУЩЕСТВУЮЩЕМ объекте (манифеста в хвосте нет; пустой объект) — permanent:
   снимок `failed` с фазой `verifying` (данные плохие; воркер пишет
   `verify: FAILED` — вечного PENDING нет).
2. Фаза `verifying`: единственный проход по объекту (GetObject-стрим с той
   же ноды): tar-записи → sha256 каждого файла, размеры; сверка с manifest:
   все файлы манифеста присутствуют с теми же размерами/хэшами, лишних
   файлов нет; сквозной sha256 объекта — против поля `sha256` etcd-статуса
   полного (если задано). Дополнительно проверяются: контрольная сумма
   самого манифеста (`Manifest-Checksum`: sha256 содержимого JSON с
   обнулённым значением поля) и присутствие в tar всех WAL-сегментов,
   заявленных диапазонами `WAL-Ranges` (Timeline/Start-LSN/End-LSN →
   непрерывный ряд имён `pg_wal/<segment>`; отсутствие — permanent).
   Манифест перечисляет все файлы набора, КРОМЕ себя (`backup_manifest`) и
   самих WAL-сегментов `pg_wal/<segment>`: записи `pg_wal/<segment>` в
   проходе побайтово не хэшируются (их целостность доказывается контролем
   WAL-Ranges и сквозным sha256 объекта), не считаются
   лишними/отсутствующими; `pg_wal/archive_status/*.done` сверяются
   пофайлово. У DR-орфана без etcd-поля `sha256` сквозная сверка объекта не
   выполняется — вердикт OK означает «все перечисленные манифестом файлы и
   WAL-Ranges сошлись».
3. Статус `GET /api/ops/verify` (фазы `downloading|verifying`,
   `started_unix`); воркер супервизит поллингом до итога.

Транспортный сбой чтения (S3/сеть) на ЛЮБОЙ фазе — transient: снимок
операции `failed` с фазой `downloading` (маркер транзиента); воркер держит
PENDING и повторяет POST следующим тиком (операция начнётся заново, резюмов
нет). Permanent (фаза `verifying`) — только суждение о данных: расхождение с
manifest (файл/хэш/перечень), отсутствующий/нечитаемый в объекте манифест
(исчерпание попыток хвоста), несовпадение `Manifest-Checksum`, отсутствие
сегментов `WAL-Ranges`, несовпадение сквозного sha256; `error` — причина.

## 3. Отмена и vanished

Операторская отмена идущей проверки (`POST /api/ops/cancel` — внешний канал
мимо воркера) — операция завершается снимком `state=cancelled` (НЕ failed):
отмена — не суждение о данных; воркер-супервиз по GET `cancelled` возвращает
кандидата в PENDING (`checked_unix=now` — перепроверка по расписанию
политики `verify.interval_sec`, лив-лок немедленных перезапусков исключён);
journal-факт `cancelled-by-operator`. GET 404 (операции нет — старт не
дошёл/рестарт приёмника) — transient: следующий тик повторяет POST; идущий
процесс приёмника жив под supervisord'ом ноды — «окна бута ephemeral-
контейнера» нет (стартовавшее приложение уже слушает API).
