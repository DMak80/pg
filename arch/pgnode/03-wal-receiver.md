# PgNode: приёмник WAL

Уровень 3. Механика online-WAL на ноде: физическая репликация, сборка
сегментов, дельта-куски, гвард чужой цепочки, подтверждение-по-доставке,
возобновление, TLI-процедура, `.history`, ре-доклад инвентаря. Политика и
контроль цепочки — [backups/02-wal-archive.md](../backups/02-wal-archive.md),
[backups/processes/b-wal-control.md](../backups/processes/b-wal-control.md);
процесс — [processes/a-wal-receiver.md](processes/a-wal-receiver.md);
состояния — [processes/enums.md](processes/enums.md).

## 1. Роль и идентичность

Приёмник — процесс ВНУТРИ контейнера КАЖДОЙ ноды шарда (программа `pgnode`;
приёмник живёт во всех нодах, стримят — только ноды-источники). Внутри —
собственный .NET-приёмник: физическая репликация (COPY-протокол
`START_REPLICATION ... PHYSICAL` по слоту, источник — `127.0.0.1:5432` своей
ноды), приём XLogData, сборка сегментов в памяти (буфер текущего незакрытого
сегмента размером `wal_segment_size`). При закрытии сегмента — put финального
объекта `wal/<segment>` (ключ = имя сегмента, байты — весь сегмент).

При старте приёмник знает только своё имя кластера/шарда/ноды (env
контейнера: `PGW_BACKUP_CLUSTER/SHARD/NODE`) и адреса etcd (`PGW_ETCD`); ВСЁ
«куда бэкапиться» резолвит сам из etcd: роль источника → S3-список
(`write_master`/`write_replica` policy + адреса/креды пула), креды
подключения (`/clusters/<C>/backup_password`, роль `backup_exec`), имя слота
(детерминизм ниже). Bucket per-install — env ноды (`PGW_BACKUP_S3_BUCKET`;
CA https — `PGW_BACKUP_S3_CA_PEM`).

## 2. Сегменты, дельта-куски, компакция и гвард чужой цепочки

ДО закрытия накопленный ВАЛИДНЫЙ префикс буфера (до конца последней полной
записи, без нулей-добивки) доотправляется ДЕЛЬТА-КУСКАМИ — отдельными
объектами с байтовыми диапазонами в имени:

```
wal/<segment>.partial_<start>_<end>_<life>_<role>_<md5>
```

- `<segment>` — 24 hex строчных (TLI+log+seg, как финал);
- `<start>`/`<end>` — LSN границ куска, РОВНО 16 hex строчных каждый;
  диапазон ПОЛУЗАКРЫТЫЙ `[start, end)`: размер объекта == end − start;
- `<life>` — номер жизни цепочки WAL шарда (u32, 8 hex строчных): значение
  etcd-счётчика `wal-life` per-shard
  ([../backups/05-etcd-contract.md](../backups/05-etcd-contract.md) §1;
  инкремент — ТОЛЬКО при разрыве цепочки, писатель — воркер); приёмник
  получает номер С КОНФИГУРАЦИЕЙ СЕССИИ (резолв целей из etcd на каждом
  цикле подключения — как креды/policy) и кладёт его в имя каждого куска и
  кумулятива; отсутствие счётчика = жизнь 0;
- `<role>` — роль источника на момент выкладки: `m` (primary) | `r`
  (sync-standby);
- `<md5>` — md5-128 байтов куска, 32 hex строчных (и Content-MD5 на put).

Все числовые поля фиксированной ширины zero-padded — лексикографическая
сортировка кусков сегмента = порядку по start; алфавит ключа
`[a-z0-9._-]`; худшая длина ключа ~170 байт при лимите S3 1024. Границы
кусков — только по целым WAL-записям (любая склейка кусков валидна для
postgres). Куски чужих номеров жизни (№ ≠ текущего номера сессии) в
покрытии/сборке/контроле не рассматриваются вовсе — фильтр листинга до
каскада кандидатов.

**Механика писателя** (одна сессия, на тик пампа): валидный префикс до
`end`; покрытие сегмента `coverage` = union(своё выложенное, лежащее по
list узкого префикса сегмента). Правила: лежащий ФИНАЛ `wal/<segment>`
означает закрытый сегмент — куски не выкладываются (мусор; поглощение/
чистка удаляют их); приёмник чужой жизни тоже не публикует куски по
сегментам с финалом, а гибнет на гварде финального put. `end ≤ coverage`
— skip (нулевым приростом куски не пере-clay'ются). Первый кусок
сегмента — кумулятивная БАЗА `[0..end)` (компак-кусок с start=0);
последующие — только прирост `[coverage..end)`. Dual-gate выкладки:
таймер `Wal:PartialIntervalSec` (дефолт 3 с) ИЛИ накопление неподтверждённого
прироста ≥ 4 МиБ (константа приёмника, не конфиг) — мгновенный сигнал.
Выкладка идёт параллельно приёму (фоновый памп сессии, вне hot-path).
**Компакция**: раз в `Wal:PartialCompactIntervalSec` (дефолт 1 ч, env
`PGW_WAL_PARTIAL_COMPACT_INTERVAL_SEC`) приёмник перезаливает кумулятивный
префикс одним базовым куском `[0..coverage)`, если после последней
компакции был хотя бы один инкремент; куски ниже базы/финала чистит
wal-sweeper (воркер), финал поглощает всё best-effort при закрытии.

Байты префикса у мастера и sync-реплики идентичны (физическая репликация,
strict-sync не даёт веткам расходиться) — куски обоих приёмников
взаимозаменяемы; failover/promote между дельтами номер жизни НЕ меняет
(timeline-скачок — та же жизнь, различается именем сегмента), куски обеих
ролей — одна жизнь. Пересечения диапазонов (одновременная выкладка обоих
приёмников, рестарт сессии, failover между дельтами) разрешает СБОРКА
читателя ([processes/g-wal-delta-assembly.md](processes/g-wal-delta-assembly.md)):
листинг фильтруется по номеру жизни (чужие отбрасываются до каскада),
порядок кандидатов — master над replica → более ранний start; побайтовое
совпадение в пересечении → union (источник с бóльшим end); несовпадение
байтов (у исправного PG невозможно) — алерт + режим выживания. Границы
записей и CRC `xl_crc` сборка проверяет ТОЛЬКО в области дифов: базы-компаки
и t14-версии доверены как полный бэкап (валидный префикс писателя +
Content-MD5/md5 транспорта) —
[processes/g-wal-delta-assembly.md](processes/g-wal-delta-assembly.md) §2/§5.
**Подтверждение слота и RPO-инварианты — ТОЛЬКО по финалам**:
куски никогда не двигают restart_lsn (дельты — ускоритель доставки
хвоста, не источник гарантий). `.history`-файлы ЗАГРУЖАЮТСЯ обязательно
(PITR через смену timeline).

**Гвард чужой цепочки (жизни)**: put объекта `wal/<segment>`
идемпотентен ТОЛЬКО для идентичных байтов — гвард действует на ОБОИХ путях
записи `wal/` (стрим приёмника и дубль `pg_wal` полного) и только на
ФИНАЛЬНЫХ объектах `wal/<segment>`; куски (базы и дельты) байт-сверкой не
гвардятся — конкурирующие байты исключает фильтр листинга по номеру жизни
и побайтовая сверка пересечений сборки читателя. Перед записью приёмник
сверяет уже лежащий объект (ETag одиночного put — md5 содержимого; сверка
с md5 сегмента). Совпало — put не повторяется (двойная
архивация/рестарт того же потока, канон идемпотентности); не совпало (или
идентичность доказать нельзя — ETag не md5) — объект НЕ перезаписывается,
сессия завершается `failed_permanent` с причиной «foreign WAL chain» в
`error`. Гвард теперь ещё и ФИКСИРУЕТ СМЕНУ ЖИЗНИ: воркер, наблюдая свежий
факт «foreign WAL chain» статус-ключа приёмника, инкрементирует счётчик
`wal-life` (причина `foreign-chain`, правила —
[../backups/05-etcd-contract.md](../backups/05-etcd-contract.md) §1), смена
номера — событие алерта панели; заморозка гварда сохраняется до
восстановления/демонтажа шарда. Префикс шарда общий для имени
кластера: после DR-пересоздания в `wal/` лежит цепочка ДРУГОЙ жизни —
источник восстановления; стрим «новой» жизни поверх неё уничтожил бы
restore-источник. Гвард замораживает новую жизнь до
восстановления/демонтажа шарда; после restore байты сегментов совпадают (та
же система) — put идемпотентен, стрим продолжается штатно.

## 3. Подтверждение-по-доставке (RPO) и возобновление

**Инвариант подтверждения-по-доставке**: приёмник подтверждает слот
(standby status update: write/flush = конец последнего ДОСТАВЛЕННОГО в S3
закрытого сегмента) ТОЛЬКО после успешного put объекта — `restart_lsn` слота
никогда не уходит за доставленный в S3 хвост. Пока S3 недоступен — приёмник
останавливает чтение потока (сервер сам ждёт подтверждения), ничего не
теряется: неподтверждённое удерживается слотом на источнике. Любой рестарт
приёмника (падение процесса/supervisord-рестарт, смена роли источника,
потеря docker-хоста в multi-host) возобновляет стрим ОТ ХВОСТА S3 и
досыпает дыру из удерживаемого слотом WAL — staging-потеря невозможна по
построению (тома нет, неподтверждённое не удалялось из источника).

**Возобновление**: старт/переподключение приёмника — от хвоста S3: list
`wal/` с первой доступной ноды read-списка (инвентарь-листинг — первая
доступная нода; перечитка сегментов выше хвоста идемпотентна по имени) →
последний сегмент цепочки → стартовая LSN = его конец (граница закрытого
сегмента; позиция передаётся в START_REPLICATION явно). Хвост НЕ выше
СОБСТВЕННОГО доставленного прогресса этой ноды (`last_delivered_segment`
статус-ключа прошлой сессии): соло-хвост чужой ноды (mesh-лаг/полный набор)
не может перевести сессию через свой недоставленный сегмент — при
расхождении старт от конца собственного `last_delivered`, перечитка у
источника и повторный put идемпотентны (двойная архивация — два ИСТОЧНИКА
одного потока, каждому свой доставленный прогресс; «числится на чужой ноде»
для приёмника НЕ значит «доставлено мной» — сегмент обязан доехать и с его
write-цели). Пустой префикс (первый старт) — от `restart_lsn` слота
(immediate+reserved держит текущую позицию; цепочка закрепится первым
upload). `restart_lsn` для старта ПОСЛЕ первого сегмента не используется —
слот выполняет только функцию удержания WAL.

## 4. Роль источника, S3-цель и слот

**Роль источника**: приёмник опрашивает свой Patroni REST loopback
(`https://127.0.0.1:8008/primary`, `/sync` — прецедент lease-скрипта
pgwnodetool; CA — REST-CA ноды): primary → write-список `write_master`,
sync-standby → `write_replica`; прочее (async-реплика, переходное окно) —
приёмник НЕ стримит (ожидание, периодический опрос роли). Смена ролей
(failover/promote) подхватывается самим приёмником — пересоздание
контейнеров воркером не выполняется. Приёмник пишет на первую доступную
ноду write-списка и перебирает при отказе текущей (per-попыточный таймаут
уже в S3-клиенте приёмника); исчерпание списка — ретрай-цикл (стрим стоит,
backpressure, слот держит — RPO-инвариант не меняется) + флаг
`pool_exhausted` в своём статус-ключе (контроль ставит маркер
`s3-pool-exhausted` в `error` DEGRADED-статуса — алерт панели; успешная put
после исчерпания флаг снимает). Флаг ставится и отказом ИНВЕНТАРНОГО
прохода: инвентарь периодически трогает пул S3 тем же write-списком — на
idle-источнике (put'ов нет) отказ прохода — положительное свидетельство
недостижимости пула, не ждущее закрытия сегмента; успешный проход после
исчерпания флаг снимает (симметрия с put). Флаг — факт СЕССИИ стрима, а не
вечный ярлык: на границе сессии (новая итерация цикла приёмника — смена
роли, reconnect) факт перепубликуется фактическим состоянием новой сессии —
исчерпания нет; при живом исчерпании факт возвращается первым же неудачным
put (или следующим отказом инвентаря).

**Слот**: per-instance, имя `pgw_bkp_<C>_<X>` ОДНО И ТО ЖЕ на каждой
ноде-источнике (слоты разных PG-инстансов независимы — конфликтов нет);
длиннее NAMEDATALEN(63) → `pgw_bkp_` + sha1(`<C>/<X>`)[:16]. Создаёт воркер
(ensure/recreate — [backups/processes/b-wal-control.md](../backups/processes/b-wal-control.md) §3);
приёмник слот находит/использует; отсутствие/`lost` — ожидание
`waiting_slot` (воркер дообеспечит). Подключение — роль `backup_exec`:
ключ `/clusters/<C>/backup_password` отсутствует (ensure не прошёл) →
приёмник в ожидании (`waiting_password`), стрима нет.

**Подключение**: приёмник подключается к источнику через `127.0.0.1:5432`
своей ноды (приёмник живёт в контейнере ноды — сеть для стрима не нужна;
нода усыновлена без приёмника внутри — WAL-архивация с неё невозможна,
ошибка конфигурации контура). Смена мастера/смена sync-standby
подхватывается самими приёмниками (REST-проба роли; write-список
перечитывается по факту роли): догон цепочки от хвоста S3, склейка timeline
через `.history`. Promote реплики: физический слот при promote сохраняется,
приёмник продолжает от хвоста S3 уже новой TLI (стартовая позиция явная,
restart_lsn для старта не используется). Креды/цели не «протухают» —
приёмник резолвит их заново на каждом цикле подключения (ротация
паролей/смена policy подхватываются без пересоздания чего-либо).

## 5. TLI-процедура 58P01

При отказе старта стрима 58P01 (хвост S3 ниже точки форка текущего
таймлайна сервера — запрошенный сегмент под именем нового TLI никогда не
существовал) приёмник выполняет tli-процедуру: `IDENTIFY_SYSTEM` →
(T, xlogpos); при T > TLI хвоста: `.history` T грузится немедленно, ДО
досыпки, затем досыпка — `START_REPLICATION … TIMELINE <TLI хвоста>` от
хвоста до точки переключения на СВЕЖЕМ replication-соединении (отказ старта
гасит прежнее — процедура открывает своё; CopyDone → переподключение от
выросшего хвоста, зазора нет, RPO=0; повторный 58P01 на досыпке — сегменты
срезаны) → прыжок-fallback: старт на текущем T от границы сегмента,
содержащего xlogpos; сегменты (хвост .. старт] в S3 не появятся —
осознанный RPO-зазор; факты tli-процедуры (`tli_backfill`/`tli_jump`) — в
статус-ключе приёмника (контроль воркера по факту `tli_jump` ставит поле
`gap` ключа `wal`); инвариант подтверждения-по-доставке не меняется; гонки
повторного промоута — конвергентны (каждая итерация с IDENTIFY_SYSTEM,
счётчиков нет).

## 6. `.history` и ре-доклад инвентаря

**`.history` при TLI-переходе**: приёмник, наблюдая первый сегмент нового
TLI, запрашивает history-файл у сервера (команда протокола
`TIMELINE_HISTORY`) и выгружает объект `wal/<TLI>.history`. Если рантайм
репликации не экспонирует запрос — приёмник читает файл
`pg_wal/<TLI>.history` ФАЙЛОВОЙ СИСТЕМЫ своей ноды (приёмник живёт в
контейнере ноды, доступ к PGDATA есть) и грузит его; недоступен и файл —
факт `history_missing` в статус-ключе (диагностика; воркер ничего не
докладывает). При tli-процедуре (58P01) `.history` нового TLI грузится
приёмником немедленно при детекте перехода (до досыпки) тем же порядком.
Переход, случившийся вне окна стрима приёмника (промоут, пока нода не
стримила), приёмник не наблюдает — его закрывает РЕ-ДОКЛАД ИНВЕНТАРЯ
history: при (ре)старте стрима и далее раз за цикл подключения приёмник
перечисляет `.history`-файлы `pg_wal` своей ноды и кладёт в `wal/`
отсутствующие (list read-списком, put идемпотентен — та же ФС ноды и тот
же канал, что и стрим-доклад; выполняется вне hot-path, отказ put —
diagnostic-log, следующий цикл повторяет). После промоута файл
`000000NN.history` лежит в `pg_wal` нового мастера, после restore — в
pgdata восстановленной ноды: переход вне окна стрима доезжает от любой
ноды, физически содержащей файл; нода без файла — прежний факт
`history_missing`. Новых etcd-ключей и docker-операций ре-доклад не
вводит, контроль воркера не меняется.

**Ре-доклад инвентаря СЕГМЕНТОВ**: закрытые сегменты `pg_wal` своей ноды,
продолжающие непрерывную часть цепочки `wal/`, кладутся в архив, если их
там нет (list read-списком — та же истина хвоста, что у старта стрима; put
идемпотентен). Механику требует исход «WAL физически есть на ноде, но
приёмник его не стримил»: промоут/restore восстановленной ноды открывает
новый TLI вне окна сессии, хвост S3 остаётся на прежнем таймлайне, и без
ре-доклада сегменты между хвостом архива и первым сегментом нового TLI не
попадают в S3 никогда (валидатор restore видит реальный разрыв). Правила:
старт — от конца последнего непрерывного сегмента S3, но НЕ выше конца
СОБСТВЕННОГО доставленного прогресса (`last_delivered_segment` — та же
граница недоверия чужому хвосту, что у старта сессии): локально закрытые
сегменты между собственным прогрессом и хвостом чужой ноды ДОНОСЯТСЯ
(дубль на чужой ноде безвреден — идемпотентный put того же содержимого; для
приёмника «числится на чужой ноде» не значит «доставлено»); при нескольких
таймлайнах на одну позицию грузится НОВЕЙШИЙ (живая ветка ноды); порядок
заливки — строго возрастающий по позициям, обрыв (нет локального закрытого
сегмента на ожидаемой позиции или отказ put) останавливает проход до
следующего повтора; открытый (текущий) сегмент своей ноды не грузится
(байты дописываются — объект был бы неполным), как и файл не штатного
размера сегмента. Выполняется вне hot-path при (ре)старте стрима и
ПОВТОРЯЕТСЯ в живой сессии периодом `Wal:InventoryPeriodSec` (60 c): сессия
без переподключений не консервирует дыру сегментами, закрывшимися после её
старта; отказ — diagnostic-log; новых etcd-ключей и docker-операций не
вводит.

## 7. Стоп-семантика

Стоп-семантика — через etcd, воркер контейнер ноды не трогает: глобальный
ключ `/pgworker/backups-disabled` (жив ⇒ `Backups:Enabled=false` — приёмник
замирает), wal-ключ шарда `STOPPED` (карантин) или `WAL_CHAIN_ERROR`
(разрыв — приёмник замирает, лечение пересъёмом) ⇒ пауза стрима;
`ACTIVE/DEGRADED`/отсутствие ключа ⇒ работает. Резюме запуска: при старте
стрима приёмник резолвит хвост S3 read-списком и слот на своей ноде.
