# G. WalDeltaAssembly (сборка сегмента из базы и дельт)

Уровень 4. Автомат сборки сегмента из кусков (базы-компаки + дельты) для
restore_command (fetch-wal) и drill: фильтр листинга по номеру жизни,
инвентаризация кусков, порядок кандидатов, побайтовая сверка пересечений,
конфликт-режим выживания, дыры, скан-валидация результата. Функция —
[03-wal-receiver.md](../03-wal-receiver.md) §2 (формат куска, механика
писателя); вызов — [06-restore-drill.md](../06-restore-drill.md) §2
(fetch-wal); чтение без байтов (контроль цепочки воркера) —
[../../backups/processes/b-wal-control.md](../../backups/processes/b-wal-control.md) §1.

## 1. Номер жизни, инвентаризация и фильтры

Вход процесса — ТЕКУЩИЙ номер жизни цепочки: у fetch-wal это номер жизни
выбранного полного из задания restore (поле `chain_life`
[../../backups/05-etcd-contract.md](../../backups/05-etcd-contract.md) §1,
доставлен в env вызова; отсутствие — DR-восстановление orphan-полного без
etcd-статуса: фильтр по номеру не активен), у контроля цепи — текущее
значение счётчика `wal-life`. Куски ЧУЖИХ номеров жизни (`<life>` ≠
входному номеру) НЕ рассматриваются вовсе — фильтр листинга ДО каскада
кандидатов и скачивания.

Листинг узкого префикса `wal/<segment>` ПО ВСЕМ нодам пула (union,
пагинация list-v2; транспортный отказ ноды пропускает ноду; ни одна не
ответила — транспортный отказ вызова, НЕ «конец WAL»). Из листинга
исключаются финал `wal/<segment>` (сборка не нужна — читается финал).
t14-версии `wal/<segment>.<endLsn>.partial` — БЕЗномерные legacy-базы
переходного окна t14→t15: учитываются ТОЛЬКО пока у сегмента нет кусков
текущего номера жизни (появился кусок текущего номера — безномерное
семейство сегмента больше не рассматривается и выметается wal-sweeper'ом).
Каждый кусок проходит фильтры ДО скачивания:

- разбор имени (`<start>/<end>/<life>/<role>/<md5>`, фиксированные ширины);
  неразбор — кусок отбрасывается (диагностический факт);
- сверка `end − start` с ФАКТИЧЕСКИМ размером объекта из листинга:
  несовпадение — битый кусок, отбрасывается (факт);
- диапазон внутри сегмента (`start ≥ границы сегмента`, `end ≤ конец
  сегмента`), `start < end` — иначе отброс.

После скачивания — сверка md5 байтов с `<md5>` имени (страховка от порчи при
хранении): несовпадение — битый кусок, отбрасывается (факт).

## 2. Порядок кандидатов и штатная сборка

Кандидаты упорядочиваются: (1) роль `m` над `r`, (2) более ранний
`<start>` (база-компак `start == 0` стартует первой в своей группе).

Штатная сборка — жадное применение кусков от начала сегмента в порядке
кандидатов: покрытие `coverage = 0`; очередной кусок применяется, если
закрывает непокрытую часть (`end > coverage`, стык `start ≤ coverage`) и
байты в пересечении `[start..coverage)` с уже собранным буфером
ПОБАЙТОВО СОВПАДАЮТ: совпало → coverage = end (union; «источник с бóльшим
end» — хвост берётся у длиннейшего); кусок, не закрывающий непокрытых
байтов (`end ≤ coverage`), пропускается молча. Несовпадение байтов в
пересечении — конфликт (у исправного PG невозможно): диагностический факт
(алерт) и переход в режим выживания (§3). Кусок со стыком `start >
coverage` — кандидат на дыру (§4): сборка не расширяется, фиксируется
минимальный такой `start`.

Скачивание кусков — параллельно сборке (пул 8), общий дедлайн вызова
fetch-wal прежний (`CallDeadline`); память — куски текущего сегмента
(десятки МиБ, короткоживущий процесс restore_command).

## 3. Конфликт байтов: режим выживания

Несовпадение байтов в пересечении — признак порчи/чужих данных; алерт:
факт в stderr вызова (docker-логи контейнера postgres — канал
диагностики) + сборка перезапускается в режиме выживания: кандидаты
переупорядочиваются ПО ВОЗРАСТАНИЮ `<md5>` (детерминизм), сборка строится
заново: каждый применяемый кусок немедленно проверяется сканером записей
(границы записей + CRC `xl_crc` — расширение сканера префикса) на
валидность затронутой области; кусок, дающий несовпадение байтов в
пересечении ИЛИ невалидные записи после применения, ОТБРАСЫВАЕТСЯ (без
ретрая в этом проходе); по исчерпании кандидатов побеждает первая
(единственная) полностью валидная сборка — медленно, но детерминированно.

## 4. Дыры и фолбэк последней надежды

«Хвост не дописан» (кусков выше `coverage` нет) — НЕ дыра: закрытое
покрытие `[0..coverage)` — обычный результат живого хвоста. ДЫРА —
непокрытый диапазон в середине (`start > coverage` у лучшего оставшегося
куска при наличии кусков выше): фолбэк последней надежды, применяется
только когда живой источник/полный бэкап недоступны (fetch-wal работает,
когда источник мёртв по определению restore): восстановить всё ДО дыры,
диапазоны ПОСЛЕ дыры отбросить + диагностический факт (алерт); результат
— закрытое покрытие до начала дыры.

## 5. Скан-валидация результата и выдача

Штатная сборка ВСЕГДА завершается скан-валидацией собранного префикса:
границы записей (страничная механика, long/short заголовки, продолжения
записей) И CRC каждой записи (`xl_crc` в порядке вычисления postgres:
`xloginsert.c` считает ТЕЛО записи при её сборке, когда prev-link ещё
неизвестен, `xlog.c` домешивает фиксированный заголовок после заполнения
prev-link — накопитель CRC-32C Castagnoli инициализируется, затем
логические байты `[SizeOfXLogRecord..xl_tot_len)`, затем `[0..xl_crc)`,
финал — XOR 0xFFFFFFFF; вставленные short-заголовки страниц и
MAXALIGN-добивка в образ не входят). Порядок «тело → заголовок»
обязателен: CRC-32C не коммутативна, перестановка не сходится ни на
одной реальной записи. Несовпадение — префикс усекается до конца
последней CRC-валидной записи, факт). Валидный префикс добивается нулями
до `wal_segment_size`
(postgres отвергает архивный файл иного размера; нули за концом
последней валидной записи — штатный конец WAL). Локальная копия набора
`full/<id>/pg_wal/` (если скачана в PGDATA) сравнивается с ПОКРЫТИЕМ
(не с одной версией): копия не короче покрытия — fetch-wal отвечает
«объекта нет» (postgres читает layout сам, останавливаясь на его
реальном конце).

## 6. Наблюдаемость

Все отбрасывания кусков (разбор/размер/md5/пересечение/CRC), конфликт
байтов, дыра и усечение — однострочные факты в stderr вызова fetch-wal
(транслируются postgres в его лог — канал диагностики restore/drill);
`restored_to_lsn` статуса операции честно отражает фактически собранный
конец. Новых etcd-ключей и метрик процесс не вводит.
