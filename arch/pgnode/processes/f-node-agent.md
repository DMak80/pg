# F. NodeAgent (статусная машина агента)

Уровень 4. Статусная машина загрузочного агента PgNode и хендшейк доставки
секретов. Функция — [08-operability.md](../08-operability.md) §1; секреты —
[pgworker/04-security.md](../../pgworker/04-security.md) §3–§4; ключ статуса —
[pgworker/00-etcd-contract.md](../../pgworker/00-etcd-contract.md) §4;
реакции надзора — [pgworker/processes/c-node-supervisor.md](../../pgworker/processes/c-node-supervisor.md) §9;
перечисления — [enums.md](enums.md).

Ключ `/pgworker/nodes/<C>/<X>/<N>/status` пишет ТОЛЬКО агент PgNode
lease-сессией TTL 15 c, воркер читает-мониторит; смерть процесса гасит
ключ — статус не «застревает» от мёртвого агента. Состояния:
`not_initialized` → `initializing` → `ready` | `start_failed`.

## 1. Переходы

- Агент при старте процесса, готовый принимать ключи, публикует
  `not_initialized` (листенер `:8081` уже поднят — серверный серт читает из
  bootstrap-ключа etcd сам).
- Воркер мониторит статус (poll-тик надзора): увидел `not_initialized` —
  доставляет ключи (put bootstrap-ключа при устаревании + команда доставки
  per-install паролей PG телом mTLS-запроса).
- Команда доставки (тело: `{su_password, standby_password,
  is_tool_start?}`): агент получает и ПРОВЕРЯЕТ все аргументы (пара
  per-install паролей + валидность bootstrap-ключа: серты парсятся, YAML
  непуст) и атомарно переводит состояние — txn etcd
  `[compare status==not_initialized] [put initializing]`. Compare проигран
  (состояние уже не `not_initialized`) — команда НЕ отрабатывает повторно:
  ответ `ok` («пинок состоялся»), действий нет. Неполные/невалидные
  аргументы — состояние остаётся `not_initialized` (ответ с диагностикой;
  воркер ретраит тиком).
- `initializing` — ДВЕ независимые фазы (не смешиваются):
  - **(а) старт процессов компонентов** — `is_tool_start=false`
    (умолчание): стартует агент (`supervisorctl start pg_doorman`, `start
    spilo`) с надзором старта: процесс упал при старте — перезапуск, ДО 3
    попыток на компонент; исчерпаны — компонент `failed`, ОСТАЛЬНЫЕ
    компоненты не блокируются. `is_tool_start=true` (tool-контур, напр.
    restore — команде предварительный запуск не нужен): агент ТОЛЬКО
    готовит параметры запуска (tmpfs-файлы), компоненты НЕ запускает —
    запуск и его ретраи выполняет сама tool-команда; терминальный успех
    ЭТОГО пути — подготовленность параметров: успешный рендер всех
    tmpfs-файлов → `ready` (компоненты `prepared`/не запущены; фаза (б)
    select 1 в этом пути агентом НЕ выполняется — контроль
    старта/готовности компонентов — зона tool-команды и её владельца, их
    статусы — штатные статусы ops-API/restore); ошибка рендера →
    `start_failed` (потребитель статуса — владелец tool-контура, не общий
    надзор: restore-шарды шагом надзора не пересоздаются). Штатный
    порядок — «сначала старт компонентов, потом доп tool-команды» (команды
    без `is_tool_start` идут по готовности компонентов).
  - **(б) ожидание готовности — БЕЗ бюджета**: проба `SELECT 1` со стороны
    ноды (живой процесс может инициализироваться долго — восстановление из
    бэкапа): PG — `127.0.0.1:5432` под postgres/SuPassword; doorman —
    клиентский вход `:6432` под app-ролью (app_password — ключ etcd
    кластера, sslmode=require) — проверяет и цепочку auth_query. Таймаута
    инициализации нет: select 1 ждёт готовности сколь угодно долго;
    бюджеты владельцев процессов (фазы provisioning/restore воркера) —
    свои, без изменений.
- Итог: все компоненты готовы → `ready`; компонент `failed` (исчерпание 3
  попыток старта в фазе (а) агентского запуска) → `start_failed`
  (+диагностика); при `is_tool_start=true` критерий готовности — ПАРАМЕТРЫ
  (п. (а)): ошибка рендера → `start_failed`, ошибки СТАРТА компонентов —
  зона tool-команды/её владельца (агент их не отслеживает).
- Все компоненты готовы → `ready` (готов к работе); в статусе —
  `applied_revision` (mod_revision применённого bootstrap-ключа).
- Компонент не стартовал (исчерпание попыток фазы (а)) → `start_failed`
  (+диагностика `error`); при `is_tool_start=true` `start_failed`
  выставляется только за ошибку ПОДГОТОВКИ параметров (рендер) — ошибки
  старта компонентов (зона tool-команды) агентом не отслеживаются.
- Реакция воркера на `start_failed` — пересоздание ноды С НОВЫМ ДИСКОМ
  (kill+remove контейнера, remove volume, ensure заново; данные ноды не
  сохраняются — шард восстанавливает реплику репликацией/бэкапом) с
  правилами [C. NodeSupervisor](../../pgworker/processes/c-node-supervisor.md) §9:
  failover-first для лидера и неприкосновенность scope живого кластера.
  Гварды: `object`-усыновлённые (R9) и restore/TO_REMOVE-шарды не
  пересоздаются (владелец — свои процессы).
- Рестарт контейнера/смерть агента: lease истёк → ключ исчез → новый
  процесс публикует `not_initialized` — хендшейк повторяется (данные PG в
  volume переживают; initializing завершается штатным стартом PG).
- Замены на ГОТОВОЙ ноде (ротации серта/`rest_password`) — отдельная
  команда применения (без тела): агент перечитывает bootstrap-ключ и
  точечно применяет изменения по материалу (rest-пароль — reload Patroni,
  rest-серт — рестарт Patroni-программы, doorman — рестарт пулера; мастер
  сертом не применяется агентом — его пересоздаёт воркер); машина
  состояний остаётся в `ready`, обновляется `applied_revision`.
  Bootstrap-хендшейк (первичная инициализация) и ротация — разные команды
  канала: доставка отрабатывает только из `not_initialized` (атомарный
  переход), применение — только на `ready`.

## 2. Инварианты

- Переход `not_initialized`→`initializing` — только txn с compare по
  value: повторная команда доставки не перезапускает инициализацию.
- Статус живёт lease-сессией агента: смерть процесса гасит ключ, воркер
  видит отсутствие ключа как transient (следующий тик — `not_initialized`).
- Проба `SELECT 1` — наблюдение, не гейт: отказ аутентификации app (28P01)
  в окне ротации — очередной цикл ожидания, `ready`-нода остаётся `ready`.
- `error` — однострочная диагностика БЕЗ значений секретов.
