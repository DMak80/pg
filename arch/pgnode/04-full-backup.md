# PgNode: исполнение полного бэкапа

Уровень 3. Механика операции полного на ноде: стриминговый клиент
`BASE_BACKUP`, перепаковка tar, multipart-заливка, WAL набора, статус,
отмена. Политика и планировщик — [backups/01-full-backup.md](../backups/01-full-backup.md);
процесс — [processes/b-full-backup.md](processes/b-full-backup.md);
состояния — [processes/enums.md](processes/enums.md).

## 1. Запуск

PgWorker подаёт `POST /api/backup/full` `{"id"}` на `alias:8080` ноды;
команда несёт ТОЛЬКО id — секреты (пароль `backup_exec`, креды пула S3)
приёмник резолвит сам из etcd, как для стрима. 503 стоп-гейтов —
`STOPPED`, `/pgworker/backups-disabled`, `Backups:Enabled=false`.
`WAL_CHAIN_ERROR` — НЕ гейт операции полного: POST отвечает 202, операция
начинается (разрыв — в архиве S3, не в данных нод; его лечение — пересъём).

Staging-каталога полного НЕТ: полный бэкап не пишет набор на диск — tar-поток
перепаковывается и льётся в S3 на лету; пик диска операции ≈ 0 сверх PGDATA
ноды, чистить нечего (при старте новой операции оборванных локальных
артефактов нет).

## 2. Клиент BASE_BACKUP (источник)

Собственный низкоуровневый клиент протокола PG (wire protocol v3) в процессе
приёмника — утилита `pg_basebackup` не используется (не имеет режима stdout;
запуск утилиты означал бы staging-копию PGDATA). Соединение:

- TCP `127.0.0.1:5432` → `SSLRequest` → TLS (`SslStream`, доверие серта
  источника — как у стримного подключения приёмника);
- `StartupMessage` с `replication=database`, user `backup_exec`; пароль —
  в памяти процесса (строка подключения), НЕ argv (child-процессов нет);
- аутентификация: SCRAM-SHA-256 (SASL) и cleartext-password; иная схема
  (MD5, SCRAM-SHA-256-PLUS, GSS) — fail-fast «unsupported auth» с
  диагностикой (несовместимость протокола не маскируется);
- команда simple-query `BASE_BACKUP (LABEL 'pgw-full-<id>', CHECKPOINT
  'fast', MANIFEST 'yes', MANIFEST_CHECKSUMS 'SHA256', TARGET 'client', WAL
  true)` — `TARGET` — строчное `client` (регистр значим у сервера), `WAL` в
  PG15+ булев (стриминг WAL клиенту при `TARGET 'client'`), не строковый
  метод доставки; манифест задаётся явно (по умолчанию `'no'`, а
  `MANIFEST_CHECKSUMS` без манифеста — отказ сервера);
- ответ — два обычных result set'а (стартовая позиция WAL; tablespace list —
  более одной строки = дополнительный tablespace, fail-fast «multiple
  tablespaces not supported», контур Spilo — один tablespace), затем ОДИН
  COPY OUT-поток с внутренним фреймингом CopyData: `n` — начало архива
  (имя `base.tar`/`pg_wal.tar`/`<oid>.tar` + каталог), `m` — манифест,
  `d` — данные, `p` — прогресс; после потока — финальный result set
  (конечная позиция WAL). При `WAL true` сервер дописывает сегменты WAL
  ВНУТРЬ `base.tar` (записи `pg_wal/…`), отдельного WAL-архива нет; манифест
  приходит отдельной секцией `m`/`d` и в единый tar кладётся ПОСЛЕДНЕЙ
  записью `backup_manifest` (verify читает его хвостом объекта). Архивы
  дополнительных tablespace (`<oid>.tar`) — fail-fast. Несовместимость
  версии протокола/сервера (SQLSTATE отказа, неизвестный формат сообщений) —
  fail-fast с однострочной диагностикой, набор НЕ создаётся.

Удержание WAL источником на время бэкапа — инвариант ядра PG
(`pg_backup_start` удерживает сегменты от start LSN до конца бэкапа);
слот стримящего приёмника продолжает удерживать хвост независимо — BASE_BACKUP
слот не использует и подтверждений слоту не шлёт.

## 3. Пайплайн

Фоновая Task процесса приёмника, параллельно стриму; резюмов нет — FAILED →
переснятие новым id:

1. резолв кредов/пула из etcd, REST-проба роли → write-список (фиксация на
   старте операции);
2. фаза `basebackup`: соединение BASE_BACKUP → потоковая перепаковка
   входных tar-потоков в ЕДИНЫЙ выходной tar (записи основного потока — как
   есть; записи WAL-потока — с префиксом `pg_wal/`; имена сегментов — как
   присланы сервером, ВЕРХНИЙ hex); перепаковщик — tar-writer/reader
   (ustar + GNU longname + PAX-записи длинных имён/размеров >8 ГиБ);
   `backup_label` (первая запись основного потока) парсится на лету —
   `wal_start_segment`; фиксируются смещения записей `pg_wal/` (для дубля)
   и сквозной sha256 объекта;
3. multipart-заливка ОДНИМ объектом `full/<id>.tar` параллельно чтению:
   `CreateMultipartUpload` при старте, части 16 МиБ (параллельная заливка
   до 4 частей в полёте; буфер памяти ≤ 5×part), каждая часть с
   Content-MD5, `CompleteMultipartUpload` по концу tar-потока (двухблочная
   нулевая добивка tar пишет завершающая часть); объект появляется в
   листинге только после Complete — существование = завершённая загрузка;
4. фаза `uploading`: дублирование закрытых сегментов набора в `wal/` —
   Range-GET из только что залитого tar-объекта (по зафиксированным
   смещениям) параллельно (те же 8 потоков, что у заливки файлов раньше),
   ключи — НОРМАЛИЗОВАННЫЕ (строчные), гвард чужой цепочки — как у стрима;
   закрытость — по источнику на момент заливки (IDENTIFY_SYSTEM отдельным
   коротким соединением: дублируются сегменты СТРОГО ниже активного
   wal-файла источника); последний живой сегмент набора в `wal/` НЕ
   дублируется — его финал доставит стрим при закрытии;
5. итог `succeeded` с `wal_start_segment`, `size_bytes` (размер объекта),
   `sha256` (сквозной хэш) и прогрессом (`bytes_done`, `parts_done`).

**Multipart-сессия на ОДНОМ endpoint пула** — перебор нод посреди сессии
недопустим: отказ endpoint'а → `AbortMultipartUpload` → ПОЛНЫЙ рестарт
попытки (новое соединение BASE_BACKUP + новая сессия) на следующей ноде
write-списка; каждая попытка целиком живёт на одном endpoint; исчерпание
списка → FAILED с маркером `s3-pool-exhausted` в `error` (алерт панели,
обычный бэкофф переснятия). Пул-обращения — per-попыточный таймаут,
circuit-breaker 45 с ([backups/06-s3-layout.md](../backups/06-s3-layout.md)
§3); внутренние ретраи S3-клиента цели ВЫКЛЮЧЕНЫ (политика повторов —
рестарт попытки/перебор). Лимиты: ≤10000 частей, часть ≤5 ГиБ (OwnS3) —
части 16 МиБ дают потолок объекта 160 ГиБ; большее — FAILED с диагностикой.

## 4. Отмена и зависание

Отмена (cancel API / бюджет воркера) — гасит внутренний CTS: закрывается
сокет BASE_BACKUP (сервер прерывает бэкап), несостоявшаяся multipart-сессия
получает `AbortMultipartUpload` (best-effort; недоступный endpoint оставит
сессию — её зачистит супервизор по возрасту), операция завершается `failed`
с причиной `cancelled`; гейт-команда на СТАРТЕ (503) идущую операцию не
рвёт. Рестарт приёмника/ноды посреди операции → GET 404 → воркер FAILED
`operation-vanished` → переснятие новым id (резюмов нет); оборванная
multipart-сессия (uploadId утерян) зачищается супервизором
([backups/processes/e-supervisor.md](../backups/processes/e-supervisor.md) §1).
Отдельного контейнера полного нет — cleanup только cancel API (воркер чужой
процесс убить не может); etcd пишет ТОЛЬКО воркер, приёмник etcd-контракта
полного не знает.

ENOSPC-риск операции отсутствует (на диск операция не пишет; диск ноды
занят только её PGDATA).
