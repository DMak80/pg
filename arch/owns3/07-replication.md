# 07. ownS3: межсерверная mesh-репликация

Межсерверная mesh-репликация ownS3: пул **2–5 серверов** на разных
docker-хостах (гео), full-mesh active-active. Клиент пишет в любой
доступный сервер; синхронизация — внутренняя механика ownS3, для
клиентов каждый сервер — полный S3 (в части закоммиченных объектов).
Входные требования —
[`docs/owns3-replication-requirements.md`](../../docs/owns3-replication-requirements.md)
(R1–R6); изыскания по платформам —
[`docs/s3-replication.md`](../../docs/s3-replication.md). Реализация:
`src/OwnS3.Replication` (ядро) + касания `src/OwnS3.Storage` (применение
реплики штатным xl-коммитом), `src/OwnS3.Protocol` (исходящая SigV4),
`src/OwnS3.App` (события в хендлерах, грани, hosted-сервисы) — состав и
границы зависимостей в главе [01-overview.md](01-overview.md) §3.
Модель xl-хранения, которую репликация не меняет, — глава
[04-storage.md](04-storage.md).

## 1. Модель доставки: уведомления + pull

Каждый сервер mesh несёт **обе роли**:

- **Источник** — клиентские операции после локального коммит-поинта
  пишут события в журнал доставки (§3–§4); фоновый notifier (§8)
  рассылает соседям **только уведомления** — лёгкие сообщения
  (сущность + метаданные, без данных). Per-target курсор источника
  двигается **подтверждением ПРИЁМА уведомления** — ответом
  `acceptedToSeqNo` на батч (§6), **НЕ фактом применения данных**.
  Ответственность источника заканчивается приёмом уведомления соседом;
  прогресс данных приёмника источник не отслеживает.
- **Приёмник** — сам фетчит данные с источников, когда ему удобно
  (свой темп, ограничения скорости) и при наличии свободного места
  (backpressure по диску), идемпотентно применяет с LWW-разрешением
  (§7); reconcile/backfill (§9) — гарантийный контур сходимости.

Принципы модели (канон; любое решение по репликации сверяется с ними):

1. **Запись превыше всего (R1/R3)**: путь клиентского запроса НЕ
   содержит ни одного синхронного взаимодействия с соседями — ни
   подтверждений, ни inline-проверок целей. Отказ/таймаут/изоляция
   любого числа соседей — событие фоновых процессов, никогда — пути
   записи. Append события в журнал + fsync (мс) — единственная
   синхронная стоимость записи (§3).
2. **Уведомление лёгкое, данные — pull**: из outbox передаются только
   уведомления; тело объекта приёмник забирает сам с replication-грани
   источника. Источник никогда не навязывает передачу данных; диск
   источника не масштабируется с объёмом данных, диск приёмника не
   занимается непрошеной передачей.
3. **Журнал — лог уведомлений, не копий данных**: запись журнала —
   сотни байт метаданных; bounded-бюджет журнала (§4) не зависит от
   объёма реплицируемых объектов.
4. **Идемпотентная обработка, LWW-сходимость (R4)**: повторные
   уведомления, повторные фетчи, повторное применение — безопасны;
   конкуренция разрешается по `(modTime, contentSha256)`, тай-брейк —
   детерминированный, без координации (§7).
5. **Анти-петля**: события в журнал ставят ТОЛЬКО клиентские операции
   (App-хендлеры 21 операции); приём реплики (уведомление/фетч)
   события не ставит. Каждый объект покидает каждый сервер не более
   одного раза на соседа (+reconcile) — штормов размножения нет.
6. **Доставляй актуальное состояние**: уведомление означает «ключ
   грязный для соседей»; фетчер читает актуальное состояние ключа
   источника на момент фетча (объект мог быть перезаписан/удалён
   позже события) и применяет именно его. Полностью обработанные
   приёмником уведомления делают его соответствующим источнику по
   всем упомянутым ключам.
7. **Курсор двигается ACK приёма** (см. выше): подтверждённое
   источником «сосед уведомлён» ≠ «данные у соседа»; прогресс данных —
   зона ответственности приёмника (его метрики + сверка листингов,
   §10). Дыры любых причин (крах приёмника, принудительный тримминг)
   закрывает reconcile.
8. **Bounded-журнал + reconcile как гарантийный контур (R6/R4)**:
   запись клиента никогда не отказывает из-за журнала; переполнение
   бюджета — алерт + принудительный тримминг (§4); потерянные
   уведомления НЕ теряют данных (объекты живут в томах источников) —
   дыры закрывает reconcile (§9).
9. **Самолечение без рестартов (R4)**: срастание сети → notifier
   продолжает с бэкоффом (at-least-once), приёмник до-фетчивает; любые
   дыры закрывает reconcile — автоматически, без рестартов процессов
   и ручного вмешательства. Бюджет полного догона тестового контура —
   ≤5 мин.
10. **Честная наблюдаемость (R5)**: лаг уведомлений (источник,
    watermark приёма) и лаг данных (приёмник, fetch-очередь) — РАЗНЫЕ
    величины, экспортируются обе; абсолютная истина — сверка листингов
    (sync-report, §10).

## 2. Состав mesh и его изменение (R6)

- **Сосед (target)** — запись
  `TargetRecord {name, endpoint, accessKey, secretKey}`:
  `endpoint` — `scheme://host:port`, advertised (multi-host/гео);
  креды — per-соседние, политика `replication` на соседе (§6, глава
  05 §3). Состав симметричен: сосед — и получатель наших уведомлений,
  и источник для наших фетчей.
- **Источник истины состава — файл тома**
  `.owns3.sys/replication/targets.json` — JSON camelCase,
  `[{name, endpoint, accessKey, secretKey}]`; персист атомарно
  (tmp + rename). Файл переживает рестарт; секрет на локальном томе
  допускается по прецеденту конфиг-контура (глава 05 §2).
- **Env — только seed первого старта**: переменные
  `OWNS3_REPLICATION_TARGETS__<i>__{NAME,ENDPOINT,ACCESSKEY,SECRETKEY}`
  (индексная нумерация — конвенция .NET, по образцу
  `OWNS3_ACCESS_KEYS__*`, глава 05 §4) переносятся в targets.json при
  первом старте, пока файла нет; повторные старты env НЕ перечитывают.
  Env пуст и файла нет → targets.json не создаётся, **репликация
  неактивна** — поведение системы байт-в-байт как single (события не
  ставятся, грань `/replication/*` отвечает 403/404 по §6, метрики
  репликации не экспортируются — Existing-регресс). Есть ≥1 сосед →
  репликация активна.
- **Изменение состава без даунтайма S3-грани — админ-грань** (глава
  05 §7; тем же конвейером SigV4, права admin/root):
  - `PUT /admin/replication/targets` — идемпотентная замена полного
    списка; тело `{targets:[{name, endpoint, accessKey, secretKey}]}`;
    валидация: имена и accessKey уникальны (accessKey — идентификатор
    источника на приёмнике, §6), endpoint `scheme://host:port`; ответ
    **202 Accepted**. Персист targets.json (tmp + rename), применяется
    на лету: **добавленный сосед** → наш notifier начинает слать ему
    уведомления с текущего конца журнала (курсор соседа −1, §8) + наш
    reconcile забирает с него его существующие данные (§9); **убранный**
    → notifier/фетчер по нему останавливаются, **курсор сохраняется**
    (возврат соседа — продолжение с сохранённой позиции).
  - `GET /admin/replication/status` — состав и стейт по каждому соседу,
    включая счётчики исходов (§10).
  - `POST /admin/replication/reconcile` — внеплановый reconcile-проход
    (§9): 202; идущий продолжается, параллельный не создаётся.
- Оркестратор трека s3 управляет составом живого пула именно через эту
  грань; ownS3 сам без etcd (глава 01).
- **Идентификация соседа-источника на приёмнике — по accessKey
  подписи** запроса к replication-грани (§6): креды пер-соседние, имя
  источника (`sourceName`) — запись `TargetRecord.Name` приёмника, чей
  accessKey совпал с подписью. Заголовок уведомлений `originHostId`
  (env `OWNS3_HOST_ID`, глава 05 §4) — **диагностика конфликтов**,
  НЕ ключ идентификации.

## 3. События репликации

Ставятся синхронно в App-хендлерах сразу после успешного коммит-поинта
клиентской операции, **до ответа клиенту** (append + fsync — милли-
секунды, бюджет R1 соблюдается; очередь переживает рестарт — R2).

| Событие | Коммит-поинт клиента | Запись |
|---|---|---|
| `object-put` | PutObject / CompleteMultipartUpload / CopyObject (замена `xl.meta`) | bucket, key, modTime фиксации (unix-мс из xl-записи), etag, size, contentSha256, originHostId |
| `object-delete` | DeleteObject / каждый ключ DeleteObjects | bucket, key, modTime фиксации удаления (текущее время сервера в момент delete-коммита — удаляемая xl-запись времени не несёт), originHostId |
| `bucket-create` | CreateBucket | bucket, CreationDate |
| `bucket-delete` | DeleteBucket | bucket, modTime |

- **Приём реплики события не ставит** (анти-петля, принцип 5).
- **Самодостаточность уведомлений**: `object-delete`, `bucket-create`,
  `bucket-delete` применяются приёмником ИЗ уведомления (данных не
  несут); `object-put` — приёмник сравнивает `(modTime, contentSha256)`
  уведомления со своей записью: локально не старше → событие закрыто
  без фетча (skip); старее/отсутствует → фетч данных. LWW-предфильтр
  не тянет тело зря — не тратятся ни канал, ни место приёмника.
- Окно «коммит есть, события нет» (крах между rename-коммитом и
  append) — микросекунды на одном диске; компенсация — сверка листингов
  (§10) и reconcile (§9). Специального 2PC-протокола нет.
- Multipart-состояния (активные загрузки) не реплицируются —
  транзитные состояния клиента; реплицируется только результат —
  закоммиченный объект (событие на коммит-поинт Complete).

## 4. Журнал доставки (outbox)

- **Расположение**: `.owns3.sys/replication/outbox/` — сегментный
  append-only журнал. Имена сегментов — `seg-<startSeqNo>.log`
  (startSeqNo — сквозной seqNo первого события сегмента, монотонная
  нумерация). Сегмент закрывается (открывается новый) по достижении
  **64 МиБ** размера или **5 мин** возраста.
- **Формат записи v1** (бинарный; события маленькие — сотни байт,
  журнал НЕ хранит тела объектов):

  ```
  [int32 totalLen][byte version=1][byte type][int64 seqNo]
  [int64 modTimeUnixMs][int64 size]
  [str bucket][str key][str etag][str contentSha256][str originHostId]
  (str = int32 len + utf8; type: object-put=1, object-delete=2,
   bucket-create=3, bucket-delete=4; для delete/бакетов etag/contentSha256="")
  ```

- **Запись**: append + fsync, до ответа клиенту (§3). seqNo —
  сквозной монотонный через сегменты; при открытии журнала — скан
  хвоста последнего сегмента; пусто → seqNo = 1. Журнал создаётся
  лениво — каталога нет до первого события (неактивная репликация не
  оставляет следов на томе).
- **Чтение** — батчами через границы сегментов
  (`от seqNo, максимум N событий`) — источник notifier'а (§8).
- **Тримминг (штатный)**: сегмент удаляется, когда конец сегмента
  (максимальный seqNo в нём) меньше `minAcceptedSeqNo` =
  min(watermark ПРИЁМА активных соседей). Соседей нет → журнал не
  ведётся (события не ставятся). **Владелец цикла обслуживания —
  ReplicationCoordinator (§8-а)**: тримминг, принудительный тримминг
  и retention-чистка tombstones выполняются фоновым циклом, НЕ путём
  записи.
- **Bounded-бюджет (R6)**: `OWNS3_REPLICATION_OUTBOX_BUDGET_BYTES`
  (дефолт **2 ГиБ** — миллионы уведомлений; per-install). Превышение:
  запись клиента продолжается ВСЕГДА («переполнение — алерт, не отказ
  записи»); поднимается алерт-метрика
  `ownS3_replication_outbox_budget_exceeded` + лог-событие и выполняется
  **принудительный тримминг** — удаляются старейшие ЗАКРЫТЫЕ сегменты,
  пока размер не уложится в бюджет (активный сегмент не трогается).
  Лог-событие фиксирует «потеряны уведомления для отстающих соседей».
  Тримминг теряет уведомления (НЕ данные) — дыры закрывает reconcile
  приёмника (§9, принцип 8).

## 5. Курсоры приёма (watermark) per-target

- **Расположение**: `.owns3.sys/replication/cursors/<name>.json` —
  `{"acceptedSeqNo": <long>, "mode": "tail"|"reconciling"}` — позиция,
  до которой сосед ПОДТВЕРДИЛ ПРИЁМ уведомлений (ответом на батч,
  §6), и режим notifier'а. Данные могут быть ещё не применены — их
  прогресс источник не отслеживает (зона ответственности приёмника,
  принцип 7).
- **Продвижение** — по `acceptedToSeqNo` ответа приёма, **только
  вперёд** (монотонность; попытка назад игнорируется). Файла нет →
  курсор = **−1**: источник решает «новый сосед» → первая отправка с
  текущего конца журнала (§8, §2).
- **Персист** — fsync-дебаунс ~1 с и при graceful-shutdown. Потеря
  хвоста курсора ведёт лишь к повторной рассылке уведомлений —
  идемпотентно (дедуп приёмника, §6).

## 6. Replication-грань (транспорт)

Служебная грань вне 21 операции S3, тем же Kestrel-портом и конвейером
SigV4 (заголовочная подпись, глава 03 §1; TLS — существующая опция
per-install, глава 03 §6). Пути `/replication/*` — отдельный класс
служебных путей рядом с `/admin/*` (изоляция в S3Middleware App).

- **Аутентификация/авторизация**: подпись проверяется штатным
  SigV4-конвейером; accessKey подписи ищется в targets приёмника —
  так резолвится `sourceName` (§2). Доступ к грани — **только** ключи
  с политикой `replication` (глава 05 §3), и только если этот accessKey
  числится соседом; валидный replication-ключ, не числящийся соседом →
  **403 `AccessDenied`**; ключи read-only/read-write/admin/root на
  грани → **403 `AccessDenied`** (A13-изоляция). Неизвестный
  replication-путь → **400 `InvalidArgument`**.
- **Отдельного эндпоинта ACK применения НЕТ** — ACK встроен в ответ на
  батч: приёмник НЕ рапортует источник о применении данных; прогресс
  данных — внутреннее дело приёмника (§10).

| Операция | Запрос/ответ | Контракт |
|---|---|---|
| приём уведомлений | `POST /replication/notifications` — JSON `{originHostId, events:[...]}` (батч событий с seqNo и метаданными целиком) | Дедуп по **(источник, seqNo)** — источник резолвится по accessKey подписи (§2), `originHostId` — диагностика: события с seqNo ≤ последнего принятого от этого источника — skip без повторного применения, повторный ACK. Самодостаточные события (§3) применяются сразу; `object-put` — LWW-предфильтр (§7): локально не старше → skip, старее/нет → fetch-очередь источника; очередь полна → **429** (приёмный буфер переполнен — источник бэкоффит). Ответ **200 `{"acceptedToSeqNo": N}`** — последний seqNo батча, поставленный в очередь/применённый, — **ACK приёма**, двигающий курсор источника (§5). Malformed JSON → **400** |
| фетч объекта | `GET /replication/object/{bucket}/{key+}` | Актуальное состояние ключа (принцип 6): **200** + поток тела (без S3-лимита 5 ГБ — грань служебная) + заголовки `x-owns3-repl-modtime` (unix-мс), `x-owns3-repl-sha256`, `x-owns3-repl-etag`, `x-owns3-repl-origin` (HostId источника), `Content-Type`, `x-amz-meta-*` \| **200** + заголовок `x-owns3-repl-tombstone: <deleteTimeUnixMs>` без тела (ключ удалён, tombstone-знание живо) \| **404** (ключа нет, tombstone-знание истекло — приёмник состояние не меняет). SHA-256 тела приёмник сверяет на лету с `x-owns3-repl-sha256` — расхождение = фетч-ошибка → повтор |
| листинг | `GET /replication/listing?bucket=&marker=&max-keys=` | Постраничный листинг ключей бакета — источник для reconcile/backfill (§9): **200** `{entries:[{key, modTimeUnixMs, contentSha256, size}], nextMarker}`; порядок — байтовый UTF-8 (Utf8ByteOrder), пагинация по маркеру; `max-keys` дефолт 1000, потолок 1000. **Без `bucket` (или пустой)** — `{buckets:[{name, creationDateUnixMs}]}` — состав бакетов для backfill (§9) |

## 7. Приёмник: fetch-очередь, LWW, tombstones, место на диске

Компоненты на каждом сервере для каждого **соседа-источника**
(`sourceName` — §2):

- **Fetch-очередь** — in-memory bounded (Channel, ёмкость
  `OWNS3_REPLICATION_FETCH_QUEUE_MAX`, дефолт **10000**): object-put
  ключи, ждущие фетча. Приём уведомления (ACK ушёл источнику)
  обязывает приёмника довести работу до конца самостоятельно — источник
  это событие больше не пришлёт (курсор двигается ACK'ом приёма,
  принцип 7). Рестарт с чистым завершением — очередь дорабатывается до
  остановки (drain); крах — очередь теряется, источник не пере-шлёт —
  дыры закрывает стартовый reconcile (§9). Durable-очередь не нужна:
  либо drain, либо reconcile — обе ветки автоматические.
- **Маркер чистого завершения**: `.owns3.sys/replication/state.json` —
  `{"shutdownClean": bool}`. При старте маркер сразу сбрасывается в
  false; после drain fetch-очередей и fsync-точки остановки —
  выставляется true. Отсутствующий/битый/false маркер на старте →
  **стартовый reconcile-проход по всем соседям** (§9); «пустой том» —
  тем же механизмом (нет state.json → маркер грязный).
- **Фетчер** — фоновый per-source: берёт ключ из очереди →
  (backpressure по месту, ниже) → `GET /replication/object/...`
  источника → применение. 200-объект — применение штатным xl-коммитом
  **с сохранением исходных modTime/etag/sha256/user-метаданных**
  (внутренний метод Storage — §11/глава 04 §4), sha-сверка тела на лету
  с `x-owns3-repl-sha256` (мисматч — фетч-ошибка → повтор, локально не
  применено); tombstone-ответ — применение удаления; 404 — пропуск без
  изменений. Ошибки — бэкофф экспоненциальный 1 с →
  `OWNS3_REPLICATION_BACKOFF_MAX_SEC` (дефолт 60), успех — сброс.
  `OWNS3_REPLICATION_PARALLELISM` (дефолт 1): при 1 — per-source FIFO;
  при >1 порядок между ключами не гарантируется — корректность от
  порядка не зависит (LWW идемпотентен). Скорость —
  `OWNS3_REPLICATION_MAX_RATE_BYTES` (0 — безлимит). Повторы фетчей —
  локальная инициатива приёмника (источник о них не знает).
- **Backpressure по месту**: перед фетчем проверяется свободное место
  тома; ниже `OWNS3_REPLICATION_DISK_FREE_MIN_BYTES` (дефолт **1 ГиБ**)
  — фетчи **ПАУЗА**: флаг `ownS3_replication_fetch_paused{source}`
  + лог-событие; место появилось — продолжение с того же места.
  Уведомления и бакетные/удалительные события продолжают приниматься и
  применяться (метаданные диск почти не тратят) — курсор источника
  идёт, данные не навязываются (принцип 2).
- **LWW-применение (R4)**: ключ сравнения `(modTime, contentSha256)` —
  больше modTime фиксации; равенство modTime — тай-брейк
  **лексикографически больший** contentSha256 (детерминирован на всех
  репликах без координации); равные modTime и разные sha256 —
  **журналируемый конфликт**: лог-событие (ключ, обе версии
  modTime/sha, origin) + счётчик `ownS3_replication_conflicts_total`;
  слияние фиксирует каждая сторона как приёмник своего события
  (R4 «факт слияния журналируется с обеих сторон»).
  - `object-put` (после фетча): входящее строго больше локального
    (записи или tombstone) → применить; иначе skip/conflict.
    Перезапись поверх tombstone: in.mod > tombstone.deleteTime →
    применить и снять tombstone; иначе skip (защита от воскрешения).
  - `object-delete` (tombstone-время из события): локальная запись с
    modTime ≤ deleteTime → удалить + записать tombstone; записи нет →
    записать tombstone (защита от воскрешения); локальная новее → skip.
  - Бакеты: `bucket-create` — идемпотентный create с CreationDate из
    события (существующий бакет — skip, первая дата сохраняется);
    `bucket-delete` — пустой бакет удалить; **непустой — отложить**:
    retry-очередь in-memory bounded (256), повтор по бэкоффу 1 с → 60 с
    (недоставленные объектные события опустошат бакет).
- **Tombstone-хранилище**:
  `.owns3.sys/replication/tombstones/<sha256hex(bucket)>/<sha256hex(key)>.json`
  — `{"bucket", "key", "deleteTimeUnixMs"}`; запись хранит **максимум**
  (новейшее) время удаления. Хранилище **едино** — пишется и локальным
  клиентским DELETE (тогда fetch-ответы отдают «ключ удалён», §6), и
  применением реплики object-delete, и как защита от воскрешения;
  локальный DELETE пишет tombstone ТОЛЬКО при активной репликации
  (без соседей каталог `replication/` не создаётся — §12; безопасно:
  tombstone нужен только mesh-обмену, а добавленный позже сосед
  захватывает состояние листингом — стартовый reconcile §9).
  Retention `OWNS3_REPLICATION_TOMBSTONE_RETENTION_HOURS` (дефолт
  **168** = 7 суток — с запасом больше любых ожидаемых окон
  раскола/доставки); чистка — фоновым циклом §8-а. После истечения
  retention опоздавший старый PUT применяется свободно — окно
  воскрешения ограничено retention (§12).
- Граница LWW — точность синхронизации часов серверов (NTP —
  эксплуатационное требование); проигравшая версия не хранится
  (versioning в ownS3 отсутствует, глава 02).

## 8. Источник: notifier per-target

Фоновый hosted-исполнитель **per-target** (§2 — состав меняется
админ-гранью без даунтайма):

1. читает события журнала от watermark ПРИЁМА соседа батчами
   (`ReadBatch(watermark+1, окно)`); пусто — ждать новых (сигнал
   Append'а / поллинг 500 мс);
2. шлёт `POST /replication/notifications` на replication-грань соседа.
   **Окно in-flight** `OWNS3_REPLICATION_INFLIGHT_WINDOW` (дефолт
   **64** события): шлёт события с seqNo < watermark + окно; за окном —
   ждёт ACK приёма. Окно — backpressure: приёмник, не принимающий
   уведомления (429/таймаут), останавливает рассылку, журнал копится
   на источнике (bounded-бюджет §4). Медленный ПРИЁМ ДАННЫХ приёмником
   окно НЕ блокирует — принимать уведомления легко (семантика курсора,
   принцип 7);
3. ответ 200 `{acceptedToSeqNo}` → watermark соседа = acceptedToSeqNo
   (персист дебаунсом §5); **429 или транспортная ошибка** → бэкофф
   экспоненциальный 1 с → `OWNS3_REPLICATION_BACKOFF_MAX_SEC`, повтор
   от watermark — **at-least-once**: неподтверждённые приёмом
   уведомления будут пере-сланы; дедуп (источник, seqNo) приёмника
   гасит повторы (пере-сланный батч получает тот же acceptedToSeqNo).
   Успех — сброс бэкоффа.

Новый сосед (курсор −1) → первая отправка от **LastSeqNo** (текущего
конца журнала) + reconcile-забор его данных (§2, §9). Notifier никогда
не в пути клиентского запроса; его зависание/бэкофф не влияет на
S3-грань. Состояние линка — метрика `ownS3_replication_link_online`
(§10).

## 8-а. Цикл обслуживания (ReplicationCoordinator)

Отдельный класс обслуживания (тестируем без хоста); hosted-координатор
App (§11 раскладка исполнения) зовёт проход **при старте и периодически
(60 с)**:

1. **Штатный тримминг журнала**: `Trim(min(watermark приёма АКТИВНЫХ
   соседей))` (§4);
2. **Бюджет**: журнал превысил бюджет (`BudgetExceeded`) →
   `ForceTrimToBudget()` + лог-событие «потеряны уведомления для
   отстающих соседей (принудительный тримминг)» (алерт-метрика — в
   самом журнале, §10);
3. **Retention-чистка tombstones**: `Cleanup(now, retentionHours)` +
   лог при удалённых > 0 (§7).

## 9. Reconcile / backfill (гарантийный контур сходимости, R4)

Приёмная операция: приёмник сверяет СВОЙ листинг с листингом соседа и
закрывает дыры фетчами. Один механизм для всех сценариев не-сходимости:
потеря fetch-очереди (крах приёмника), принудительный тримминг журнала,
добавление узла, любые неучтённые дыры.

**Триггеры — все пять:**

1. **добавление соседа** — событие замены состава (§2): reconcile по
   НОВОМУ соседу (backfill: новый узел забирает существующие данные
   всех соседей);
2. **старт на пустом томе при существующем составе** — реализуется
   стартовым reconcile: на пустом томе нет `state.json` → маркер
   грязный → стартовый проход по всем соседям (§7);
3. **грязная остановка процесса** — маркер `state.json` отсутствует/
   false (крах/kill без drain) → стартовый reconcile-проход по всем
   соседям;
4. **периодически** — `OWNS3_REPLICATION_RECONCILE_INTERVAL_SECONDS`
   (дефолт **60**: самозаживление приостановленных проходов — suspend
   при переполнении fetch-очереди подхватывается следующим проходом
   максимум через минуту — и общий страховой контур сходимости;
   нагрузка листинга на домашнем контуре пренебрежима);
5. **админ-команда** `POST /admin/replication/reconcile` (202; идущий
   продолжается, параллельный не создаётся).

**Механизм**: постраничный `GET /replication/listing` соседа (маркер
пагинации) → для каждого ключа LWW-сравнение `(modTime, sha256)` со
своей записью → старее/отсутствует → fetch-задача в очередь источника
(обычный фетч §7, идемпотентно); новее → ничего (наш вариант выиграет
при взаимной доставке). **Backfill состава бакетов**: листинг без
bucket (§6) — недостающие бакеты создаются с CreationDate соседа
(только в сторону «у соседа есть, у нас нет»). Прогресс-маркер —
`.owns3.sys/replication/reconcile/<sourceName>.marker`, персист после
каждой страницы; рестарт продолжает с маркера, отсутствие — с нуля,
идемпотентно. **Параллельный проход по одному соседу не создаётся**.
Приём записи не останавливается — фон с теми же ограничениями
скорости/места (§7). Наблюдаемость — позиция/остаток в статусе и
метрике `ownS3_replication_reconcile_position` (§10).

## 10. Наблюдаемость (R5)

**Метрики** (каркас `Shared.Metrics`, Meter `ownS3`; словарь главы
05 §5 расширяется; экспортируются при активной репликации — без соседей
серий нет, Existing-регресс). Роли: `{target}` = имя соседа-ПОЛУЧАТЕЛЯ
(исходящие), `{source}` = имя соседа-ИСТОЧНИКА (приёмные).

| Метрика | Тип | Смысл |
|---|---|---|
| `ownS3_replication_link_online{target}` | gauge | 1 — сосед онлайн по исходам notifier |
| `ownS3_replication_queue_depth{target}` | gauge | событий журнала после watermark ПРИЁМА соседа |
| `ownS3_replication_delivery_lag_seconds{target}` | gauge | возраст старейшего события, не подтверждённого ПРИЁМОМ уведомления (лаг уведомлений) |
| `ownS3_replication_notified_total{target,result}` | counter | исходы рассылки уведомлений (accepted/backoff/retry) |
| `ownS3_replication_fetch_queue_depth{source}` | gauge | ключей в fetch-очереди приёмника |
| `ownS3_replication_fetch_lag_seconds{source}` | gauge | возраст старейшего принятого-но-несохранённого ключа (лаг данных; 0 — очередь пуста) |
| `ownS3_replication_fetch_paused{source}` | gauge | 1 — фетчи на паузе (нет места) |
| `ownS3_replication_fetched_total{source}` | counter | успешные фетчи тел |
| `ownS3_replication_applied_total{source,result}` | counter | исходы применения: applied/skipped/conflict |
| `ownS3_replication_retries_total{target}` | counter | повторы рассылки уведомлений |
| `ownS3_replication_conflicts_total` | counter | зафиксированные LWW-конфликты (журналируются) |
| `ownS3_replication_reconcile_position{source}` | gauge | прогресс reconcile (обработано ключей) |
| `ownS3_replication_outbox_bytes` | gauge | текущий размер журнала |
| `ownS3_replication_outbox_budget_exceeded` | gauge | 1 — бюджет журнала превышен (алерт-состояние) |

**Счётчики исходов приёма** (внутренние per-source, видны в статусе и
питают серии `applied_total{source,result}`/`fetched_total`/
`conflicts_total`); **точки инкремента** — только точки применения,
каждая по результату СВОЕГО вызова и со своим sourceName:

- `applied` — применение самодостаточных событий приёмником уведомлений
  И применение фетча;
- `skipped` — LWW-предфильтр уведомлений (включая дедуп-повторы) И
  skip-ветка фетча;
- `conflict` — флаг конфликта LWW: компаратор предфильтра уведомлений
  И флаг применения фетчера;
- `fetched` — успешный фетч тела объекта (только фетчер).

Событие «конфликт детектед» компаратора применения (без sourceName) —
ТОЛЬКО лог: инкремент по нему дал бы мульти-счёт при ≥2 живых
источниках.

**Админ-сверка листингов** — `GET /admin/replication/sync-report?bucket=&prefix=&marker=`
(глава 05 §7): JSON-отчёт листинга ЭТОГО сервера от маркера
(до 1000 ключей, prefix-фильтр):

```json
{"bucket": "...", "prefix": "...", "marker": "...",
 "firstKey": "...", "firstModTime": 0, "lastKey": "...", "lastModTime": 0,
 "count": 0, "totalSize": 0, "aggregateHash": "<64-бит hex>"}
```

`aggregateHash` — порядко-независимая (XOR) 64-битная **FNV-1a**-свёртка
пар `(key, modTimeUnixMs)`: попарное сравнение отчётов двух серверов
даёт вердикт «синхронно/расходится» без передачи полных листингов;
внешний зонд синхронности трека s3 опирается на этот эндпоинт.

**Статус** — `GET /admin/replication/status` (глава 05 §7): `active`,
`outbox {bytes, budgetBytes, budgetExceeded, lastSeqNo}` и по каждому
соседу `{name, online, acceptedSeqNo, queueDepth, deliveryLagSeconds,
fetchQueueDepth, fetchLagSeconds, fetchPaused, reconcileRunning,
reconcilePosition, counters {notifiedAccepted, notifiedBackoff,
notifiedRetry, fetched, applied, skipped, conflict}}`.

**Лог-события**: LWW-конфликты (ключ, обе версии modTime/sha, origin);
пауза/резюм фетчей по месту; принудительный тримминг журнала (потери
уведомлений); отложенные бакетные удаления; budget-exceeded; грязная
остановка → стартовый reconcile; запуск/завершение reconcile.

**Сквозные измерения в E2E** (не рантайм-метрики узлов): end-to-end
латентность репликации и время восстановления связи после срастания
сети измеряются самой тестовой серией и публикуются фактическими
значениями в журнале прогона — канон и пороги — раздел 7 (A15/A4);
рантайм-метрики `delivery_lag`/`fetch_lag` при этом сверяются тестом
со своими измерениями (сквозная честность наблюдаемости).

## 11. Раскладка, конфигурация, исполнение

**Раскладка на томе** (владелец — эта глава; глава 04 §1 несёт
строку-ссылку):

```
.owns3.sys/replication/
├── targets.json                    ← состав mesh (§2)
├── state.json                      ← маркер чистого завершения (§7)
├── outbox/seg-<startSeqNo>.log     ← журнал доставки (§4)
├── cursors/<name>.json             ← watermark приёма per-target (§5)
├── tombstones/<sha256(bucket)>/<sha256(key)>.json   ← (§7)
└── reconcile/<source>.marker       ← прогресс reconcile (§9)
```

**EC-режим**: состояние репликации — на служебном контуре **первого
диска** (глава 06 §2), НЕ реплицируется на диски сета: состояние
репликации — состояние узла, не данных. Отказ диска = как отказ узла —
очередь/прогресс теряются → расхождение закрывает reconcile (§12).

**Env** (конвенция главы 05 §4; секция appsettings `OwnS3:Replication:*`):

| Env | Назначение | Дефолт |
|---|---|---|
| `OWNS3_REPLICATION_TARGETS__<i>__{NAME,ENDPOINT,ACCESSKEY,SECRETKEY}` | seed состава mesh первого старта (§2) | пусто = неактивна |
| `OWNS3_REPLICATION_OUTBOX_BUDGET_BYTES` | bounded-бюджет журнала (§4) | **2 ГиБ** |
| `OWNS3_REPLICATION_INFLIGHT_WINDOW` | окно in-flight notifier'а (§8) | **64** |
| `OWNS3_REPLICATION_PARALLELISM` | фетчеры: параллелизм на источник (§7) | **1** |
| `OWNS3_REPLICATION_MAX_RATE_BYTES` | троттлинг фетчей, байт/с; 0 — безлимит (§7) | **0** |
| `OWNS3_REPLICATION_BACKOFF_MAX_SEC` | потолок эксп-бэкоффа (§7/§8) | **60** |
| `OWNS3_REPLICATION_DISK_FREE_MIN_BYTES` | watermark свободного места фетчей (§7) | **1 ГиБ** |
| `OWNS3_REPLICATION_TOMBSTONE_RETENTION_HOURS` | retention tombstones (§7) | **168** |
| `OWNS3_REPLICATION_RECONCILE_INTERVAL_SECONDS` | период reconcile (§9) | **60** |
| `OWNS3_REPLICATION_FETCH_QUEUE_MAX` | ёмкость fetch-очереди на источник (§7) | **10000** |
| `OWNS3_HOST_ID` | originHostId уведомлений — диагностика (§2; глава 05 §4) | имя контейнера |

**Исполнение в App** (глава 01 §3 — App стыкует): события в 7 хендлерах
после коммит-поинта (§3); replication-грань и админ-грань в
S3Middleware; hosted-сервисы — координатор: notifier per-target, фетчер
per-source, цикл обслуживания §8-а, reconcile-триггеры §9, graceful
stop (drain → flush курсоров → маркер clean). Путь записи клиента не
содержит синхронных сетевых вызовов (принцип 1).

## 12. Границы надёжности

- **RPO второй копии = лаг доставки данных**: секунды штатно, минуты
  после отказов (бэкофф/очередь/место приёмника). Подтверждение
  клиенту — локальная фиксация (R1, осознанно). Курсор по ACK приёма:
  «сосед уведомлён» ≠ «данные у соседа» — прогресс данных наблюдается
  метриками приёмника и сверкой листингов (§10).
- **Крах приёмника с недрейненной fetch-очередью**: принятые, но не
  сохранённые ключи теряются из памяти, источник их не пере-шлёт
  (курсор ушёл) — компенсация автоматическая: стартовый reconcile
  (§9); RPO-окно потери ограничено временем до ближайшего reconcile.
- **Отказ машины целиком** (multi-host-правило системы, глава 01)
  теряет её журнал/курсоры/tombstones/маркеры — локальный том = кэш/
  очередь БЕЗ durability-гарантий; источники истины — сами
  реплицируемые данные на всех серверах mesh. Расхождение закрывается
  reconcile при возврате или замене сервера (оркестрация трека s3);
  данные отказавшей машины восстанавливаются остальными узлами mesh
  (mesh и есть источник).
- **LWW и часы**: точность разрешения — точность NTP хостов;
  тай-брейк sha256 детерминирован; проигравшая версия не хранится.
- **Зафиксированные компромиссы** (закрыты сверкой листингов/reconcile):
  окно commit→append (микро, §3); окно retention tombstones — окно
  воскрешения (§7); принудительный тримминг теряет уведомления (НЕ
  данные) — интервал reconcile — параметр эксплуатации.
- **Multipart-состояния** между серверами не согласованы — клиент
  завершает загрузку на сервере приёма (§3).
- **Доставка — логическая**: приёмник пишет своим режимом хранения
  (single/EC независимо от режима источника); реплицируются объект как
  данные+метаданные, не xl-раскладка.
- **Один trust-домен**: peer-креды per-install (targets.json — секрет
  на локальном томе — допускается по прецеденту главы 05 §2);
  enterprise-IAM/mTLS-pKI — вне (roadmap-паттерн).
- **Existing-регресс**: соседей нет → поведение байт-в-байт как
