# 06. ownS3: erasure coding (multi-drive)

Режим EC-хранения ownS3: коды Рида—Соломона на multi-drive томе, erasure-сеты,
кворумы, bitrot-контроль и heal. Реализует `src/OwnS3.Storage` поверх общей
xl-механики главы [04-storage.md](04-storage.md) (раскладка, `xl.meta`,
коммит rename, чистки — те же); эта глава описывает отличия и расширения
EC-режима. Контракты операций — глава [02-operations.md](02-operations.md);
конфиг/env и админ-грань — глава [05-access-config.md](05-access-config.md).

Референс при сверке механики (устройство, не перенос целиком):
[cmd/erasure-coding.go](../../../minio/cmd/erasure-coding.go) (инициализация
k/m/блока, кворумы), [cmd/erasure-encode.go](../../../minio/cmd/erasure-encode.go)
/ [cmd/erasure-decode.go](../../../minio/cmd/erasure-decode.go) (потоковое
кодирование/декодирование), [cmd/erasure-sets.go](../../../minio/cmd/erasure-sets.go)
(сеты, SIPMOD), [cmd/erasure-object.go](../../../minio/cmd/erasure-object.go)
(объектные операции через сеты, RenameData кворумом),
[cmd/format-erasure.go](../../../minio/cmd/format-erasure.go) (формат
multi-drive тома), [cmd/bitrot.go](../../../minio/cmd/bitrot.go)
(highwayhash256 bitrot), [cmd/erasure-healing.go](../../../minio/cmd/erasure-healing.go)
(heal). Отступления от референса оговорены явно.

## 1. Режимы и конфигурация

ownS3 поддерживает два режима хранения — выбор по числу путей в
`OWNS3_DATA_DIR` (глава [05-access-config.md](05-access-config.md)):

- **1 путь — `XL Single`**: single-drive главы 04, без EC. Текущие
  инсталляции ничего не меняют.
- **≥ 2 путей — `XL Erasure`**: multi-drive том с erasure-кодированием
  (эта глава). Порядок путей в env — канонический порядок дисков; дубликат
  пути или несуществующий и не-создаваемый — отказ старта.

Параметры топологии:

| Параметр | Env | Ограничение | Дефолт |
|---|---|---|---|
| число дисков N | `OWNS3_DATA_DIR` (список) | ≥ 2, N % setSize == 0 | — |
| размер сета (k+m) | `OWNS3_EC_SET_SIZE` | 4–16 | авто: наибольший делитель N из {4, 8, 16}; нет делителя — отказ старта с требованием задать явно |
| parity m | `OWNS3_EC_PARITY` | 1 ≤ m ≤ setSize/2 | 2 |

- data-блоков k = setSize − m; число сетов = N / setSize; сет s составляют
  диски на позициях `[s·setSize, (s+1)·setSize)` списка путей.
- **setSize фиксируется форматом тома** (п. 2): его изменение на живом томе —
  отказ старта. **parity — per-object** (в `xl.meta`, п. 5): значение env —
  default для новых объектов; смена parity конфига на живом томе разрешена
  (старые объекты читаются по своим полям, перекодирования нет).
- Отказ старта (fail-fast, диагностика в лог + ненулевой exit): N < 2;
  N % setSize ≠ 0; setSize вне 4–16; parity вне границ; несоздаваемый путь;
  несовместимость с форматом существующего тома (п. 2).
- **Переход single → EC без авто-миграции**: инсталляция с данными не
  «наращивается» дисками; EC-топология стартует на пустых дисках или на
  уже-EC-томе. Перенос данных — операция клиента (`mc mirror`, перезаливка);
  миграция MinIO→ownS3 — задача трека `t41`.

## 2. Формат multi-drive тома

`volume.json` в `.owns3.sys/` **каждого диска** (модель — п. 3 главы 04;
EC-расширение):

| Поле | Содержимое |
|---|---|
| magic | `OWNS3-VOL` |
| версия формата | **2** (single — 1) |
| deploymentId | UUID v4 — общий для всей инсталляции, генерируется при создании тома |
| diskId | UUID v4 — уникальный для диска |
| uuid тома | UUID v4 (как single) |
| режим | `XL Erasure` |
| setSize | размер сета формата |
| sets | 2D-массив diskId: `sets[s][j]` — diskId диска на позиции `s·setSize + j` |
| distribution | перестановка позиций 0..setSize−1 (детерминированно из deploymentId при создании) — база EcDist записей |
| distributionAlgo | `SIPMOD` |

Правила старта:

- **Свежая инсталляция** (все каталоги пусты): создание формата на каждом
  диске — общий deploymentId, свои diskId, sets по позициям путей, одинаковые
  distribution. Любой каталог с посторонним содержимым при отсутствии
  формата — отказ старта.
- **Существующий EC-том**: на каждой позиции путь либо несёт валидный
  `volume.json` с ожидаемым diskId (по sets из формата любого онлайн-диска),
  либо пуст (без `volume.json`) — **кандидат замены** (п. 9). Отсутствующий
  путь позиции на живом томе — диск **offline** (не кандидат замены):
  создание каталогов несуществующих путей выполняется только при создании
  нового тома; возврат пути с его `volume.json` возвращает диск в сет онлайн.
  Несовпадение setSize/deploymentId/distributionAlgo между дисками, чужой
  magic, версия новее поддерживаемой, diskId вне sets на своей позиции —
  **отказ старта всего сервиса** (подмена дисков местами и смешение
  топологий запрещены; критерий — fail-fast над тихой порчей).
- **Изменение числа путей** против sets формата (добавление/убирание дисков) —
  отказ старта: топология фиксирована, расширение тома — отдельная задача
  трека.
- Служебная структура `.owns3.sys` (tmp/multipart/.trash/buckets/config)
  создаётся на **каждом** диске; конфиг-секция (`config/`) реплицируется на
  все диски (источник — env, глава 05).

## 3. Распределение объектов по сетам

- Объект (bucket + ключ) закрепляется за одним сетом: **индекс сета =
  SipHash-2-4(deploymentId-ключ, «bucket/object») % число сетов** (алгоритм
  `SIPMOD`; SipHash-2-4 — собственная реализация
  `OwnS3.Storage.Erasure.SipHash24` с тест-векторами референса Aumasson/DJB —
  пакет `System.IO.Hashing` SipHash не содержит; ключ — 16 байт deploymentId).
  Детерминированность: тот же ключ всегда в тот же сет, пока жив формат тома.
- Multipart-загрузка закрепляется за сетом своего ключа при
  CreateMultipartUpload (uploadId не мигрирует между сетами).
- Бакеты и служебные метаданные бакета (`bucket.json`) создаются на **дисках
  всех сетов**: объекты одного бакета распределены по сетам, каталог бакета
  должен существовать на каждом диске.

## 4. Кодирование

- **Код Рида—Соломона над GF(2⁸)**, собственная реализация: систематическая
  матрица (Vandermonde/Cauchy-приведённая), кодирование k data-шардов →
  m parity-шардов, декодирование с восстановлением до m потерянных/битых
  шардов из любых k. Тест-векторы кодека — обязательные юнит-тесты
  (round-trip на случайных данных, восстановление каждой комбинации потерь
  до m, известные векторы матрицы).
- **Erasure-блок — 1 МиБ** исходных данных; блок режется на k шард-блоков по
  `ceil(1 МиБ / k)` байт; последний блок объекта может быть короче (шарды
  хвостового блока — по `ceil(tail/k)` с добивкой нулями в памяти кодека).
- Шард j блока попадает на диск сета на позиции `distribution[j]` (перестановка
  из формата; одна на инсталляцию). Шардовый поток диска d = конкатенация его
  шард-блоков всех erasure-блоков объекта — это и есть `part.N` на диске d
  (п. 5).
- Пустой объект (size 0): шардовые файлы нулевой длины, записи bitrot-блоков
  нет.
- Оптимизации малых объектов (inline-данные в `xl.meta`) — нет: маленький
  объект занимает по `ceil(size/k)` байт на каждом диске сета (поведение
  референса; критерий — простота формата).

## 5. Раскладка данных и EC-поля `xl.meta`

Раскладка каталогов на каждом диске — та же, что single (глава 04 §1: бакеты
— каталоги, объект — каталог с `xl.meta` + `<dataDir-uuid>/part.N`), отличия:

- `part.N` на диске — **шардовый поток этого диска** (закодированные блоки),
  не исходные данные.
- `xl.meta` пишется на **все диски сета** с одинаковым содержимым, кроме
  поля `EcIndex` (индекс позиции этого диска).
- `contentSha256` в записи — SHA-256 **исходного** содержимого объекта
  (считается кодером на лету); семантика сверки при полном чтении — глава 04
  §2 без изменений.

**Запись-версия v2** (`xl.meta`, формат-запись за RecordVersion 2; чтение
RecordVersion 1 — single-записи без EC-полей):

- все поля записи v1 (versionId, size, modTime, metadata, etag,
  contentSha256);
- EC-поля:

| Поле | Содержимое |
|---|---|
| EcAlgo | `reedsolomon` |
| EcM | число data-шардов k |
| EcN | k + m |
| EcBSize | размер erasure-блока (1 МиБ) |
| EcIndex | позиция этого диска в Distribution |
| EcDist | перестановка распределения шардов (distribution формата) |

- **bitrot-записи**: для каждого `part.N` — исходный размер части (uint64),
  число шард-блоков (uint32) и HighwayHash-256 (32 байта) каждого шард-блока
  каждого шарда — полный 2D-набор ecN × blockCount в каждой копии записи
  (п. 6: сверка чтения, реконструкция и heal адресуют произвольный шард);
- побайтовый хвост записи v2 после `ecDist`: `uint16 partCount`; на каждую
  часть по возрастанию `part.N`: `uint64 sourceSize` (исходный размер части —
  источник GetObjectAttributes без декодирования), `uint32 blockCount`, затем
  для каждого шард-индекса `j = 0..ecN−1` — `blockCount × 32` байта
  HighwayHash-256 его шард-блоков по порядку блоков; раскладка шард-мажор:
  `hashes[shardIndex][blockIndex]`; размер bitrot-секции части —
  `8 + 4 + ecN × blockCount × 32` байт; копия записи на любом диске сета
  несёт полный набор (одинаковое содержимое, кроме `EcIndex`);
- порядок записи файла (`xl.meta.bkp` → tmp+fsync → rename) — глава 04 §2
  без изменений, на каждом диске независимо.

## 6. Bitrot-контроль

- **HighwayHash-256** (порт референса `cmd/bitrot.go`, включая магический
  256-битный ключ) от каждого шард-блока каждого шарда; хэши — в bitrot-записях
  `xl.meta` (п. 5).
- Сверка — при каждом чтении шардового блока (в т.ч. heal-проходом):
  несовпадение = диск считается **битым для этого объекта**: шард
  реконструируется из k других, битый помечается для heal.
- Битый `xl.meta` на диске (обрыв структуры при кворумно-валидном объекте) —
  тот же исход: объект читается по кворуму остальных, диск лечится heal.
- Тест-векторы HighwayHash (включая магический ключ) — обязательные
  юнит-тесты порта (сверка с известными векторами Go-реализации).

## 7. Кворумы и деградация

| Кворум | Значение |
|---|---|
| чтение (read quorum) | k |
| запись (write quorum) | k; при k == m — k+1 |

- **Онлайн-диск** — каталог доступен и I/O не падает. Ошибка I/O переводит
  диск сета в offline до ближайшей успешной операции; ленивая перепроверка —
  фоновым тикером (30 с) и heal-проходом.
- **Деградация сета** — offline до m дисков: чтение (реконструкция
  недостающих из k), запись и листинги работают; heal (п. 9) восстанавливает
  при возврате дисков.
- **Недоступность сета** — онлайн-дисков < k: объекты сета недоступны.
  Операции с объектами сета → **503** `InsufficientReadQuorum` /
  `InsufficientWriteQuorum` (формат ошибок — глава 03; коды добавляются в
  общие семантики главы 02). **Не 404**: недоступность не выдаётся за
  отсутствие (клиент бэкапов не должен принять потерю связи с сетом за
  «объекта нет» и начать перезаливку).
- **Листинги объектов и бакетные мутации Create/Delete** требуют онлайн
  ≥ k **во всех сетах**: любой сет < k → 503 на весь запрос (критерий:
  неполный листинг для бэкапов опаснее недоступности — цепочки
  восстанавливаются клиентом по 503 с retry, а «пропавших» ключей листинг
  не показывает никогда); ListBuckets — консенсус по любому сету с
  read-кворумом (п. 8).
- Консенсус `xl.meta` при чтении: собираются записи онлайн-дисков сета,
  актуальная версия — мажоритарный versionId (порог ≥ k). ownS3 —
  одиночный процесс: конкурентных писателей между дисками нет, кворум
  защищает от отказов дисков, не от гонок записи.
- Потеря > m дисков сета **безвозвратно** — данные этого сета утрачены
  (durability-граница п. 10); сервис продолжает обслуживать остальные сеты
  (листинги объектов — 503 до возврата k дисков, п. выше).

## 8. Жизненный цикл записи/чтения

**Запись** (PUT/перезапись/Complete) — коммит-поинт **кворумный rename**
(механика staging/rename главы 04 §4 на каждом диске сета независимо):

1. стриминговое кодирование: тело режется erasure-блоками, шард-потоки
   пишутся в `tmp/<guid>/` **каждого онлайн-диска сета** (его позиции из
   EcDist), bitrot-хэши считаются на лету;
2. `xl.meta` (v2, с EcIndex диска) — tmp+rename на каждом онлайн-диске;
3. rename каталога объекта из staging в bucket-дерево на каждом онлайн-диске
   (порядок шагов перезаписи — глава 04 §4; на дисках независимо);
4. **кворум**: успехов ≥ writeQuorum → объект закоммичен, ответ клиенту;
   меньше — откат (staging → trash на всех дисках) и 503
   `InsufficientWriteQuorum`. Диски, упавшие между шагами, оставляют
   мусор tmp/orphan — удаляемый чистками по порогу (п. 10); недостающее
   на диске живое (в консенсусе) доливается heal (п. 9).
5. перезапись: старый dataDir → `.trash/` на каждом диске после кворума
   (глава 04 §4, по-дисково).

**Чтение** (GET/Head/Range/Copy-источник):

1. консенсус `xl.meta` (п. 7); Range вычисляет нужные erasure-блоки и
   смещения внутри шард-потоков;
2. чтение шард-блоков с k дисков (приоритет data-позиций), bitrot-сверка
   каждого блока; недостающие/битые — реконструкция декодером из k
   доступных;
3. декодирование в исходный поток; полное чтение сверяет `contentSha256`
   (несовпадение → 500 InternalError, глава 04 §2);
4. онлайн < k → 503 `InsufficientReadQuorum`.

**Delete** — rename в `.trash/` на каждом диске сета (кворум ≥ writeQuorum
успехов; недоступные при Delete диски выравниваются при возврате: живое-в-
консенсусе доливается heal (п. 9); контент, не актуальный в консенсусе
сета, удаляется чистками по порогу — фантом-записи (п. 10)); идемпотентность
204 — по-ключевая (глава 02).

**Multipart**: каталог загрузки и `parts.json`/`uploads.json` — на дисках
**сета ключа** (журналы пишутся на все онлайн-диски сета, читаются с любого
успешного; рассинхрон после отказов выравнивается heal). Части —
EC-закодированные (UploadPart = запись п. 8 для тела части). Complete —
по-дисковые rename частей в dataDir целевого объекта + кворумный коммит
`xl.meta`; идемпотентность повторного Complete — глава 04 §5 на каждом
диске.

**Бакеты**: Create/Delete — на всех дисках всех сетов (кворум ≥ writeQuorum
каждого сета; иначе 503/409 по главе 02); `bucket.json` — репликация на все
диски; ListBuckets — консенсус по любому кворумному сету.

**Доставка исходов**: кворумные отказы записи/чтения (503
`Insufficient*`) и исходы операций стора доставляются вызывающему слою
по Result-конвенции главы 01 §4 — без летящих исключений через границу
`IXlDrive`: отказ (включая кворумный) — `Result.Failed` с доменным
кодом, терминальное знание (в т.ч. «записи нет») — `Result.Success`.

## 9. Heal

- **Фоновый проход** (старт + периодическая задача): по каждому сету
  листинг бакетов и объектов (по консенсусу `xl.meta` онлайн-дисков), для
  каждого объекта сверка по-дисково:
  - отсутствует dataDir/`xl.meta` на диске сета;
  - bitrot-несовпадение шарда;
  - битый `xl.meta` (обрыв структуры);
  - отсутствующие части multipart-загрузок/журналы.
  Недостающее **реконструируется и пишется** на диск (шард — декодером,
  `xl.meta` — копией консенсусной записи с корректным EcIndex; часть
  multipart — аналогично). `.trash/` и orphan heal не сканирует: heal
  реконструирует только живое — объекты, актуальные в консенсусе сета
  (недостающее на диске живое доливается). Помеченное к удалению
  (`.trash/`) и не упомянутое живой записью (orphan) удаляется чистками по
  порогу (п. 10). Ответственность heal и чисток не дублируется.
- **Замена диска**: пустой каталог (без `volume.json`) на позиции сета при
  живых старых дисках сета ≥ k — занимает слот: новый diskId, обновление
  `sets` в формате всех онлайн-дисков (кворумно), heal доливает на него
  все объекты сета. Одновременно заменяемых дисков в сете ≥ k — отказ
  старта (реконструировать не из чего).
- **Админ-грань** (глава 05 §7): `GET /admin/storage` — статус сетов/дисков/
  деградации/хода heal; `POST /admin/heal` — запуск внепланового прохода.
  Запуск не создаёт параллельного прохода: идущий продолжается.
- Heal не меняет коммит-семантику: все дозаписи идут через tmp+rename
  (глава 04), объекты для клиентов атомарны всегда.

## 10. Чистки

Механизмы и пороги — глава 04 §6, применяются **на каждом диске независимо**
(tmp — только на старте процесса; `.trash/` и orphan-dataDir — порог 1 ч;
брошенные multipart-загрузки — 24 ч). Дополнения EC:

- orphan-dataDir на диске сверяется с `xl.meta` **этого же диска** (локальная
  сверка; кворум не нужен — каталог, не упомянутый локальной записью, на этом
  диске не нужен);
- фантом-записи: ключ с локально валидной `xl.meta`, не актуальный в
  консенсусе сета (кворумно удалён при offline-диске либо недозакоммичен
  крахом записи), удаляется локальной сверкой: чистка диска читает `xl.meta`
  того же ключа на других онлайн-дисках сета (внутрипроцессное чтение
  корней, без кворумных операций); запись отсутствует на ≥ k онлайн-дисках
  сета и локальная запись старше порога 1 ч (mtime `xl.meta`) → каталог
  ключа rename в `.trash/`; кворум отсутствия недостижим (онлайн-дисков без
  записи < k) → ключ консервативно сохраняется до ближайшей сверки
  с кворумом;
- чистки не конкурируют с heal: heal доливает только то, что живо в
  консенсусе сета и отсутствует на диске; чистка удаляет только
  незакоммиченное/устаревшее локально и не актуальное в консенсусе сета
  (фантом-записи — при кворуме отсутствия ≥ k).

## 11. Durability и отказы

- **Потеря до m дисков одного сета — безопасна**: данные читаются и пишутся
  (реконструкция), возврат дисков + heal восстанавливает полноту. Потеря
  дисков разных сетов до m в каждом — также безопасна.
- **Потеря > m дисков сета — потеря данных этого сета** (невосстановимо);
  источник восстановления — реплики PG-шардов и цепочки бэкапов вне
  отказавшей машины.
- ownS3 — single-node: все диски в одном docker-хосте; отказ **машины
  целиком** недоступен весь сервис (как и в single-режиме). EC защищает от
  отказов отдельных дисков/томов, не от отказа хоста; реплицированные
  источники истины — вне ownS3 (multi-host-правило системы).
- Метрики деградации и heal — глава [05-access-config.md](05-access-config.md)
  §5/§7.
