# 04. ownS3: xl-хранение single-drive

Модель хранения ownS3: single-drive xl-раскладка по механике MinIO
(единственное сознательное заимствование — принцип главы
[01-overview.md](01-overview.md)), имена служебных сущностей —
собственные. Реализует `src/OwnS3.Storage`. Контракты операций — глава
[02-operations.md](02-operations.md); конфиг тома (`OWNS3_DATA_DIR`) —
глава [05-access-config.md](05-access-config.md).

Референс при сверке механики:
[cmd/xl-storage.go](../../../minio/cmd/xl-storage.go) (раскладка,
кодирование имён, запись метаданных),
[cmd/xl-storage-format-v2.go](../../../minio/cmd/xl-storage-format-v2.go)
(устройство xl-meta-v2 — образец, не формат),
[cmd/erasure-object.go](../../../minio/cmd/erasure-object.go) (запись
через tmp + атомарный rename-коммит),
[cmd/format-erasure.go](../../../minio/cmd/format-erasure.go)
(format-тома xl-single — образец),
[cmd/erasure-multipart.go](../../../minio/cmd/erasure-multipart.go)
(multipart на диске).

## 1. Раскладка тома

```
<том>/
├── .owns3.sys/
│   ├── volume.json                ← формат/идентификация тома (см. п. 3)
│   ├── tmp/                       ← staging записи (tmp-префикс guid)
│   ├── multipart/<sha256(bucket/object)>/<uploadID>/   ← части multipart загрузки
│   │                              (журнал uploads.json — в каталоге
│   │                               <sha256(bucket/object)>/, см. п. 5)
│   ├── .trash/                    ← отложенное удаление (rename вместо rm)
│   ├── buckets/<bucket>/          ← служебные метаданные бакета
│   └── config/                    ← конфиг и ключи (глава 05)
├── <bucket>/                      ← бакеты — каталоги первого уровня
│   └── <путь объекта (кодированный)>/
│       ├── xl.meta                ← метаданные объекта
│       └── <dataDir-uuid>/part.1  ← данные (одна часть для простого PUT)
```

Имена:

- `dataDir` — UUID v4 (новый на каждую запись версии объекта);
- части — `part.N`, N с 1 (простой PUT — ровно `part.1`;
  multipart-сборка — `part.N` по номерам частей);
- **кодирование имени объекта в путь каталогов**: слэши ключа →
  вложенные каталоги; спецсимволы — percent-кодирование сегмента
  (каждый сегмент ключа кодируется по RFC 3986: всё вне unreserved
  ASCII → `%XX`; обратное преобразование однозначно). Ключ-маркер
  каталога (завершающий `/`) кодируется суффиксом `__XLDIR__` у
  последнего сегмента — по образцу `encodeDirObject` референса
  (`cmd/utils.go`: `prefix/` → `prefix__XLDIR__`). Отступление от
  референса: MinIO спецсимволы сегментов не кодирует; ownS3 кодирует —
  критерий: переносимость между файловыми системами (недопустимые на
  некоторых ФС символы) и однозначность декодирования.
- **ограничение длины пути**: длина одного кодированного сегмента ≤
  255 байт (лимит компонента пути ФС), суммарный кодированный путь —
  в пределах `PATH_MAX`; превышение → 400 `InvalidArgument`
  (Message «Key too long after encoding»). Ключ ≤ 1024 байт
  (глава 03) после кодирования раздувается максимум втрое — под
  лимиты укладывается.

## 2. Формат `xl.meta`

Собственный бинарный формат по образцу устройства MinIO xl-meta-v2
(`cmd/xl-storage-format-v2.go`): header + записи-версии. **НЕ msgp**,
побайтовая совместимость с MinIO не требуется.

**Header**: magic-байты — ASCII `OWS3` (4 байта) + uint8 версия
формата, стартовая версия **1**.

**Запись-версия** (одна на каждый записанный вариант объекта; в
unversioned-режиме — ровно одна, текущая):

| Поле | Содержимое |
|---|---|
| версия записи | uint16 — версия структуры записи (расширяемость без смены версии формата) |
| versionId | UUID v4 |
| размер объекта | int64, байты |
| modTime | UTC, точность **миллисекунды** (uint64, unix-мс) |
| metadata | contentType; user-metadata (словарь `x-amz-meta-*` без префикса); etag; прочие сохранённые заголовки (headers) |
| checksum данных | **SHA-256** от содержимого dataDir (hex) |

- **Checksum — SHA-256** (критерий: целостность бэкапов при чтении —
  сильная хэш-функция против случайных повреждений; сверка при
  **каждом чтении** данных: несовпадение → 500 `InternalError` с
  диагностикой в лог, клиенту данные не отдаются).
- **Расширяемость**: новые поля записи и EC-поля (Erasure-набор —
  EcAlgo/EcM/EcN/EcIndex/…) — через версию записи и версию формата
  (t40); старые записи читаются по своей версии записи.
- **Порядок записи**: текущий `xl.meta` копируется в `xl.meta.bkp` →
  новый `xl.meta` пишется во временный файл → атомарный rename на
  место (по образцу референса). `xl.meta.bkp` — страховочная копия:
  используется диагностикой (восстановление при повреждении
  основного), не клиентами. Отступление от референса: у MinIO
  бэкап-копия (`xl.meta.bkp`) пишется внутри старого dataDir при
  перезаписи — ownS3 держит её рядом с `xl.meta`.

## 3. `volume.json` тома

Файл формата/идентификации тома — `.owns3.sys/volume.json` (референс
MinIO — `format.json` в `cmd/format-erasure.go`). Поля:

| Поле | Содержимое |
|---|---|
| magic | ASCII-строка формата ownS3 |
| версия формата | uint, стартовая 1 |
| uuid тома | UUID v4 — генерируется при создании |
| режим | `XL Single` (один том без erasure-сета) |

- **Первый старт на пустом томе**: создание `.owns3.sys/` (подкаталоги
  `tmp/`, `multipart/`, `.trash/`, `buckets/`, `config/`) и запись
  `volume.json`.
- **Повторные старты**: валидация — отсутствие файла, чужой magic,
  несовместимая версия формата или режим не `XL Single` → **отказ
  старта**: диагностика в лог + ненулевой exit-code (fail-fast, по
  образцу референса).

## 4. Жизненный цикл записи

Запись объекта (PUT/перезапись) — единый **коммит-поинт: атомарная
замена `xl.meta`** (rename поверх, порядок записи — п. 2):

1. Данные пишутся в `.owns3.sys/tmp/<guid>/` — `part`-файлы +
   предварительный `xl.meta` (tmp-префикс — guid v4).
2. fsync файлов и каталога tmp.
3. **Новый ключ**: атомарный **rename** целевого каталога объекта
   целиком (данные + `xl.meta`) из staging в bucket-дерево
   (`<bucket>/<кодированный путь>/`) — для нового ключа один rename
   и есть коммит.
4. **Перезапись существующего объекта** — три шага в строгом порядке
   (по образцу референса `cmd/erasure-object.go` `RenameData`;
   rename непустого каталога объекта целиком невозможен — POSIX):
   1. rename нового каталога-данных (`<dataDir-uuid>/`) из staging в
      каталог объекта, рядом со старым; `xl.meta` ещё старый —
      читатели продолжают видеть старое содержимое;
   2. атомарная замена `xl.meta` (новый dataDir-UUID, новые
      метаданные) — **единственный коммит-поинт**: с этого мгновения
      все читатели видят новое содержимое;
   3. старый каталог-данных → `.trash/` — строго **после** коммита
      (сбой между шагами 1–2 оставляет новый dataDir рядом со старым
      как orphan-dataDir — не виден клиентам, чистится п. 6; сбой
      между 2 и 3 — то же для старого dataDir).
5. **Delete**: rename каталога объекта (целиком: `xl.meta` + dataDir)
   в `.trash/`.

- **Видимость**: объект появляется в Get/Head/List только после
  коммит-поинта; частично записанные объекты не видны никогда.
- **Сбой на любом шаге** оставляет мусор только в `tmp/`, `.trash/`
  и в виде orphan-dataDir внутри каталогов объектов (не виден
  клиентам: `xl.meta` указывает ровно на один dataDir) — всё это
  чистится стартом/фоном (п. 6).

## 5. Multipart на диске

- Каталог загрузки: `.owns3.sys/multipart/<sha256(bucket/object)>/<uploadID>/`
  — `part.N` загруженных частей + `xl.meta` загрузки (метаданные
  будущего объекта из CreateMultipartUpload: contentType,
  user-metadata, etag заголовков; дата инициации).
- **Журнал активных загрузок** — `uploads.json` в каталоге
  `<sha256(bucket/object)>/`: записи `{uploadId, initiation-время,
  access key создателя}` (создатель — для матрицы видимости глава 05);
  обновляется при Create/Complete/Abort.
- **Complete**: части rename'ами собираются из каталога загрузки в
  `<dataDir-uuid>/part.N` целевого объекта; **последним** атомарно
  ставится новый `xl.meta` с составным ETag
  (`<N>-<md5(concat ETag'ов)>`, глава 02) — это **коммит-поинт и
  точка видимости**: объект появляется для читателей только этим
  rename'ом (как при перезаписи, п. 4). После коммита — удаление
  записи из `uploads.json` и rename каталога загрузки в `.trash/`.
  **Сбой до коммит-поинта** оставляет загрузку живой (запись в
  `uploads.json` не тронута, частично собранный dataDir —
  orphan-dataDir, п. 6): дозагрузка недостающих частей и повторный
  Complete разрешены — повторная сборка идемпотентна (тот же
  манифест → тот же результат), состояние восстановимо клиентом без
  административного вмешательства.
- **Abort**: rename каталога загрузки в `.trash/` + удаление записи из
  `uploads.json`.
- **Чистка брошенных загрузок** по возрасту: порог **24 часа** от
  initiation-времени (критерий: референс MinIO — purge по умолчанию
  24 ч; потребности клиентов бэкапов — загрузки живут минуты);
  каталог загрузки → `.trash/`, запись → из `uploads.json`.

## 6. Восстановление и чистки

- **Старт**: валидация `volume.json` (п. 3); полное содержимое `tmp/`
  удаляется **безусловно** (это незакоммиченный staging — закоммиченных
  данных там не бывает по построению п. 4); чистка `.trash/` по порогу
  возраста — **1 час** от попадания (критерий: простота; содержимое
  `.trash/` никогда не читается клиентами); чистка orphan-dataDir —
  каталоги данных в каталогах объектов, не упомянутые текущим
  `xl.meta` (остатки прерванных перезаписей/Complete, п. 4–5), →
  `.trash/` (незакоммиченные: коммит-поинт уже прошёл или не наступил,
  текущее состояние объекта от них не зависит).
- **Фон** (периодическая задача): чистка `.trash/` тем же порогом 1
  час; чистка брошенных multipart-загрузок порогом 24 ч (п. 5);
  чистка orphan-dataDir — по возрасту файла каталога данных, порог
  **1 час** (механизм тот же, что у `.trash/`; критерий: простота).
- Мусор в `tmp/`/`.trash/` и orphan-dataDir не виден клиентам по
  построению раскладки (п. 4); чистки — вопрос места на диске, не
  корректности ответов.

## 7. Согласованность

- **Read-after-write коммита**: rename в одной ФС атомарен — после
  успешного ответа PUT/Complete объект доступен всем операциям чтения.
- **Листинги** читают те же каталоги bucket-дерева — согласованы с
  коммитами без отдельного механизма (нет отдельного индекса).
- **Без versioning**: перезапись атомарно заменяет видимые данные —
  коммит-поинт один (замена `xl.meta`, п. 4); читатель получает
  либо старое, либо новое содержимое целиком.
