# 10. Опция: 4-нодовый кластер

Базовый гайд (01–09) построен на **3 нодах**. Этот раздел — как перейти на **4 ноды**
PostgreSQL и поддерживать их. Большая часть конфигов **не меняется** — добавляется
одна нода и пара настроек.

> TL;DR: PostgreSQL можно держать сколь угодно много, а **etcd всегда нечётный (3 или 5)**.
> Для 4 БД-нод оптимально держать **3 узла etcd** (на pg1, pg2, pg3) и **4 БД-ноды**
> (pg1–pg4). pg4 не держит etcd.

---

## 1. Главное правило: etcd — только нечётный

etcd использует Raft, которому нужно **строгое большинство (quorum)**:

| Узлов etcd | Кворум | Переживает потерю |
|---|---|---|
| 1 | 1 | 0 (нет отказоустойчивости) |
| **3** | 2 | **1** ✅ |
| **4** | 3 | **1** ⚠️ столько же, сколько у 3, но +машина и +нагрузка |
| 5 | 3 | 2 |

**Вывод**: 4 узла etcd не имеют смысла. Поэтому при переходе на 4 БД-ноды **etcd
оставляем на 3**. Это и безопаснее, и дешевле.

---

## 2. Топология 4-нодового кластера

| Роль | Имя | IP (пример) | Что крутится | Диск |
|---|---|---|---|---|
| Нода 1 | `pg1` | `10.0.0.11` | **etcd1** + pg1 (Spilo) | `/data/pg`, `/data/etcd` |
| Нода 2 | `pg2` | `10.0.0.12` | **etcd2** + pg2 (Spilo) | `/data/pg`, `/data/etcd` |
| Нода 3 | `pg3` | `10.0.0.13` | **etcd3** + pg3 (Spilo) | `/data/pg`, `/data/etcd` |
| Нода 4 | `pg4` | `10.0.0.14` | pg4 (Spilo) — **БЕЗ etcd** | `/data/pg` |
| Балансировщик | `pg-lb` | `10.0.0.10` | HAProxy | — |

> pg4 — «чисто БД-нода»: на ней нет etcd, она только реплика PostgreSQL. Это правильно и
> экономит ресурсы.

### Что это даёт по сравнению с 3 нодами
- **Отказ до 2 БД-нод одновременно** (с 3 нодами — только 1).
- **3 реплики для балансировки чтения** (быстрее аналитика, меньше нагрузки на мастера).
- Возможность держать **2 синхронные реплики** (`ANY 2 (...)`) → при потере 2 нод всё
  равно нулевая потеря данных (на 3 нодах так нельзя).

### Сценарии отказа
| Что упало | etcd (3 узла) | PostgreSQL (4 ноды) | Результат |
|---|---|---|---|
| pg4 | не задет (0/3) | 1/4 | кластер работает, чтение балансируется на 3 ✅ |
| pg3 (где etcd3) | 1/3 → кворум 2/3 ✅ | 1/4 | кластер работает ✅ |
| pg3 + pg4 | 1/3 → кворум 2/3 ✅ | 2/4 | кластер работает (осталось 2 БД-ноды) ✅ |
| pg1 + pg2 (оба с etcd) | 2/3 → кворум **1/3** ✗ | 2/4 | etcd потерял кворум → Patroni замораживается. Редкий катастрофический случай. |

> Последняя строчка — почему «5 узлов etcd» имеет смысл для совсем параноидальных сценариев.
> Для 4 БД-нод это обычно избыточно: одновременная потеря двух **конкретных** (pg1+pg2)
> крайне маловероятна при правильной раскладке по стойкам/зонам.

## 3. Что меняется в конфигах (по шагам)

### Шаг 0. Подготовить pg4 как любую ноду
По `03-prerequisites.md`: docker, `/data/pg`, `chown 999:999`, `/etc/hosts` с именами всех нод.

### Шаг 1. etcd — БЕЗ ИЗМЕНЕНИЙ
Кластер etcd из 3 узлов (на pg1, pg2, pg3) **не трогаем**. На pg4 etcd **не ставим**.
Конфиги из `04-deploy-etcd.md` актуальны как есть.

### Шаг 2. PostgreSQL на pg4
Копируем конфигурацию pg3 и меняем только `hostname`:

```bash
# на pg4
sudo mkdir -p /opt/postgres && cd /opt/postgres
# docker-compose.yml — копия configs/postgres/docker-compose.yml, но:
#   hostname: pg4
# pg.env — копия configs/postgres/pg.env (или готовый configs/postgres/pg4.env.example)
docker compose up -d
docker compose logs -f postgres
# ждём: Patroni видит существующий кластер → pg_basebackup с лидера → "replica"/"streaming"
```

> Patroni **автоматически** добавит pg4 в DCS как нового member. `./scripts/patronictl.sh list`
> покажет 4 строки.

### Шаг 3. HAProxy — добавить pg4 в backend-ы
Используй готовый `configs/haproxy/haproxy-4nodes.cfg` (отличается от базового
только двумя строками `server pg4 ...` в каждом backend). Перезагружаем:
```bash
docker exec haproxy kill -HUP 1     # reload без обрыва соединений
```
Теперь порт 5433 (чтение) балансируется на **4** ноды.

### Шаг 4. (опционально, рекомендую) 2 синхронные реплики
В `SPILO_CONFIGURATION` (pg.env всех нод) или через hot-config:
```bash
./scripts/patronictl.sh edit-config
```
добавить в `postgresql.parameters`:
```yaml
postgresql:
  parameters:
    synchronous_standby_names: 'ANY 2 (pg2,pg3,pg4)'
```
Теперь лидер ждёт подтверждения от **2** реплик перед коммитом. Потеря 2 нод из 4 —
и всё ещё есть лидер + синхронная реплика = нулевая потеря данных.

> Это «настройка кластера» (живёт в DCS), применяется на лету без перезапуска.

### Шаг 5. topology.env — добавить NODE4
В `configs/topology.env.example` (и своём private-файле) добfвь:
```ini
NODE4_HOST=pg4
NODE4_IP=10.0.0.14
ALL_NODES="pg1 pg2 pg3 pg4"
```
Скрипты (`find-leader.sh`, `health.sh` и др.) читают `ALL_NODES` — они автоматически
начнут учитывать pg4.

## 4. Поддержание 4 нод (операционка)

Все процедуры из `08-operations.md` работают **идентично**, просто с 4 нодами:

| Операция | Особенности для 4 нод |
|---|---|
| **Switchover** | То же: `./scripts/switchover.sh pg3`. HAProxy переключит на нового лидера. |
| **Failover** | Автоматически. Выбирается самая свежая из 3 реплик. |
| **Rebuild ноды** | `./scripts/rebuild-node.sh pg4` — проверка «≥2 живых» теперь позволяет больше свободы. |
| **Бэкапы** | pg_basebackup/pgbackrest/wal-g — без изменений. Можно снимать с реплики pg4. |
| **Удаление ноды** | `./scripts/patronictl.sh remove pg4` + убрать из haproxy.cfg + `kill -HUP`. |

### Удаление ноды (масштабирование 4 → 3)
Если pg4 больше не нужна:
```bash
# 1) убедиться, что pg4 НЕ лидер (если лидер — сначала switchover)
./scripts/get-role.sh pg4

# 2) удалить из кластера Patroni
./scripts/patronictl.sh remove pg4

# 3) убрать из haproxy.cfg строки с pg4, reload
docker exec haproxy kill -HUP 1

# 4) остановить контейнер на pg4
ssh pg4 'cd /opt/postgres && docker compose down'
```

## 5. Когда стоит выбрать 4 ноды, а когда хватит 3

| Критерий | 3 ноды | 4 ноды |
|---|---|---|
| Базовая HA (пережить 1 отказ) | ✅ | ✅ |
| Пережить 2 одновременных отказа | ❌ | ✅ |
| Высокая read-нагрузка (нужно много реплик) | средняя | высокая |
| Требуется 0-loss при потере 2 нод | ❌ | ✅ (с ANY 2 sync) |
| Стоимость (железо/облако) | ×3 | ×4 |
| Сложность поддержки | ниже | чуть выше |

**Правило большого пальца**: 3 ноды достаточно для большинства production-нагрузок.
4+ ноды имеет смысл при (а) очень высокой read-нагрузке, (б) жёстких требованиях к
нулевым потерям при двойных отказах, (в) гео-распределении (по ноде в каждой зоне).

## 6. Чек-лист перехода 3 → 4

```text
[ ] pg4 подготовлена по 03-prerequisites.md (docker, /data/pg, /etc/hosts)
[ ] /opt/postgres/{docker-compose.yml (hostname: pg4), pg.env} на pg4
[ ] docker compose up -d на pg4 → "replica"/"streaming" в логах
[ ] ./scripts/patronictl.sh list → 4 member'а, 1 Leader + 3 Replica
[ ] haproxy.cfg заменён на haproxy-4nodes.cfg (или дописаны server pg4 ...)
[ ] docker exec haproxy kill -HUP 1
[ ] curl http://pg-lb:7000/ → pg4 видна в обоих backend'ах
[ ] (опц.) patronictl edit-config → synchronous_standby_names: 'ANY 2 (...)'
[ ] topology.env: добавлен NODE4, ALL_NODES="pg1 pg2 pg3 pg4"
[ ] ./scripts/find-leader.sh и health.sh работают (учитывают pg4)
```
