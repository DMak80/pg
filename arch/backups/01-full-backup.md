# Бэкапы: полные бэкапы

Уровень 3. Функция «полные бэкапы»: политика и планировщик rolling-съёма,
выбор источника, требования к инструменту, судьба WAL набора, идентификатор
и бэкофф. Механика исполнения на ноде — [pgnode/04-full-backup.md](../pgnode/04-full-backup.md);
состояния — [processes/enums.md](processes/enums.md); ключи —
[05-etcd-contract.md](05-etcd-contract.md).

## 1. Инструмент и требования

Собственный стриминговый клиент `BASE_BACKUP` протокола физической
репликации (репликация `TARGET=CLIENT`, tar-поток, `WAL STREAM` внутри,
`CHECKPOINT fast`, `MANIFEST_CHECKSUMS SHA256`) — утилита `pg_basebackup`
НЕ используется (не имеет режима stdout: `-D`/`-Ft` пишут в каталог —
staging-копия PGDATA на диске; пофайловая выгрузка порождает тысячи
S3-объектов). Поток tar перепаковывается на лету в ЕДИНЫЙ несжатый
tar-объект `full/<id>.tar` ([06-s3-layout.md](06-s3-layout.md) §1) и
заливается напрямую в S3 multipart — вторая копия PGDATA на диске не
возникает (пик диска ≈ PGDATA ноды), пик памяти — ограниченный буфер частей
(N×part). `fast`, а не `spread`: spread берёт давний checkpoint/restartpoint
источника — `wal_start_segment` из `backup_label` оказывается ниже первого
сегмента набора WAL, сегменты `[wal_start .. набор)` не дублируются в
`wal/` → цепочка от wal_start не сходится → бесконечные пересъёмы без
валидного полного; fast делает checkpoint на момент старта — wal_start-сегмент
входит в набор и дублируется, цепь сходится.

## 2. Исполнитель и команда

Исполнитель — агент PgNode выбранной ноды, тот же процесс, что стримит WAL:
программа `pgnode` supervisord'а образа `pgworker-node`
([pgnode/01-placement.md](../pgnode/01-placement.md)). PgWorker подаёт
команду `POST /api/backup/full` `{"id"}` на `http://<имя ноды>:8080`
(канал `alias:8080` по имени ноды в общей сети воркера и нод; порт наружу
хоста НЕ публикуется —
[pgworker/01-placement.md](../pgworker/01-placement.md) §1/§5), статус —
`GET /api/backup/full` (404 = операция исчезла — vanished), отмена —
`POST /api/backup/full/cancel` (best-effort). Детали операции —
[pgnode/04-full-backup.md](../pgnode/04-full-backup.md).

Статус операции — IMMUTABLE-снимок в памяти приёмника (фазы
`basebackup|uploading`, `wal_start_segment`, `size_bytes`, прогресс
`bytes_done`/`parts_done`, однострочный `error`); `wal_start_segment` — из
`backup_label` tar-потока, `size_bytes` — суммарный размер объекта. Воркер
поллит GET тиками, отражает фазы и прогресс в etcd-статусе и по итогу
фиксирует исход — **etcd пишет ТОЛЬКО воркер**.

**503 стоп-гейтов операции** — `STOPPED`, `/pgworker/backups-disabled`,
`Backups:Enabled=false`-семантика. **`WAL_CHAIN_ERROR` — НЕ гейт операции
полного**: POST отвечает 202, операция начинается (WAL_CHAIN_ERROR —
нарушение цепочки WAL в АРХИВЕ S3, НЕ состояние кластера и НЕ
свидетельство о данных нод; его единственное лечение — пересъём полного,
гейтом он блокироваться не может; выбор источника пересъёма — штатный:
sync-standby, fallback мастер; замирание стрима при WAL_CHAIN_ERROR
параллельному полному не мешает — стрим стоит backpressure'ом, слот держит
WAL, полный пишет в S3). Рестарт приёмника/ноды посреди операции → GET 404 →
воркер FAILED `operation-vanished` → переснятие новым id (резюмов нет).
Отдельного контейнера полного нет — cleanup только cancel API (воркер чужой
процесс убить не может).

## 3. Источник

Реплика шарда (sync-standby из Patroni `GET /cluster`: member с
`state=running`, `role=replica`, sync-статусом); реплика недоступна/отстала
→ fallback на мастер (резолв мастера — существующий `ShardEndpoints`,
[pgworker/processes/f-move.md](../pgworker/processes/f-move.md) §1). Источник
фиксируется в etcd-статусе (`node`, `role`).

Первое окно: до избрания sync-standby полный снимается с мастера
(fallback); ПОСЛЕ избрания sync-standby самый свежий COMPLETED с
`role=master` — due для пересъёма с реплики (канон «источник полного —
синхрон-реплика» исполним в любом порядке событий; пересъём с реплики гасит
force; sync не избран — force нет, обычный due, вечного цикла master-полных
нет).

## 4. Пайплайн операции

Фоновая Task процесса приёмника, параллельно стриму; резюмов нет — FAILED →
переснятие новым id: соединение `BASE_BACKUP` (127.0.0.1:5432, роль
`backup_exec`) → потоковая перепаковка tar-потоков в единый tar →
multipart-заливка в S3 ОДНИМ объектом `full/<id>.tar` → дубль закрытых
сегментов набора в `wal/`. Загрузка в пул S3 — write-список по СВОЕЙ
фактической роли (REST-проба Patroni: реплика → `write_replica`, мастер →
`write_master`); multipart-сессия живёт на ОДНОМ endpoint — перебор нод
посреди сессии недопустим; per-попыточный таймаут, circuit-breaker 45 с
([06-s3-layout.md](06-s3-layout.md) §2); исчерпание списка → FAILED с
маркером `s3-pool-exhausted` в `error` (алерт `backup-pool-unreachable`,
обычный бэкофф переснятия). Фазы — [pgnode/04-full-backup.md](../pgnode/04-full-backup.md).

**WAL набора (`WAL STREAM`)**: сегменты набора входят в tar-объект
(`pg_wal/…`); ЗАТЕМ закрытые сегменты этого набора дублируются в общий
WAL-префикс `wal/` шарда ПОД НОРМАЛИЗОВАННЫМ (СТРОЧНЫМ) именем (сервер
кладёт сегменты набора ВЕРХНИМ hex — имя дубля нормализуется при заливке):
канон ключей `wal/` — строчные (симметрия стриму приёмников и fetch-wal),
дубль сливается со стримом — дублирования объектов нет. Источник байтов
дубля — сам tar-объект (Range-GET по зафиксированным перепаковщиком
смещениям записей `pg_wal/`): на диске второй копии не возникает.

Дублирование осознанное — снимает конфликт «layout vs общий префикс»,
закрытый сегмент = один объект, перезапись идемпотентна ДЛЯ ТЕХ ЖЕ БАЙТОВ.
Закрытость — по источнику на момент заливки: сегмент набора, имя которого
СТРОГО ниже текущего активного wal-файла источника. Последний сегмент
набора (несёт end-of-backup запись, но в кластере ещё ЖИВ — PG допишет в
него же до ближайшего switch) в `wal/` НЕ дублируется: его байты остаются в
tar-объекте (самодостаточность полного — recovery дочитывает из
распакованного набора), финальную версию сегмента в `wal/` доставляет
стрим при закрытии: срез живого сегмента байт-в-байт не равен будущему
финалу (идемпотентность «тех же байтов» недостижима), а заняв ключ, срез
отсекает цепь от записей после снапшота.

Дубль чужой инкарнации (пересозданный кластер) не перезаписывает цепочку —
гвард «чужая цепочка» ([pgnode/03-wal-receiver.md](../pgnode/03-wal-receiver.md)
§2), полный завершается FAILED с причиной.

## 5. Идентификатор

`id = YYYYMMDDHHMMSSZ` (UTC старта, сортируемый); коллизия в пределах шарда
— суффикс `-2`, `-3`…; детерминизм имён — как у `pgw-<C>-<X>-<n>`
([pgworker/08-operability.md](../pgworker/08-operability.md) §2).

## 6. Планировщик (rolling)

Воркер тиками под клэймом `<C>` для каждого шарда Active-кластера с `dsn`
проверяет due (валидного COMPLETED нет; возраст > `full_max_age_sec`;
`WAL_CHAIN_ERROR` без покрывающего полного; живой `gap`) и создаёт
`full/<id>` (PLANNED → API-запуск → RUNNING), поддерживая максимум один
активный полный на шард. При создании записи воркер фиксирует в ней номер
жизни цепочки шарда (`chain_life` из счётчика `wal-life` — манифест
полного хранит номер своей жизни, источник для restore-заявок;
[05-etcd-contract.md](05-etcd-contract.md) §1). Бэкофф серии FAILED,
`CHECKPOINT` на мастере перед
пересъёмом при живой границе разрыва, takeover и `operation-vanished` —
[A. FullBackupScheduler](processes/a-full-scheduler.md).

## 7. Проверка полного (verify)

Verify — потоковая проверка целостности tar-объекта, итог — verify-статус
полного (`PENDING/OK/FAILED`):

1. **Потоковый верификатор** — операция PgNode ноды-источника полного (тот
   же единственный процесс ноды; отдельный ops-реестр операций приёмника —
   полная операция и ops-операция на одной ноде не блокируют друг друга):
   команда `POST /api/ops/verify` от воркера на `alias:8080` ноды
   (`candidate.Node`; S3-контекст read-списка — секреты только в POST) →
   фаза `downloading`: Range-чтение хвоста объекта `full/<id>.tar` и разбор
   `backup_manifest` (без перекачки всего объекта) → фаза `verifying`:
   единственный проход по объекту — tar-записи, sha256 каждого файла,
   сверка с manifest (перечень файлов/размеры/хэши; лишние/отсутствующие
   файлы — ошибка; WAL-сегменты `pg_wal/<segment>` манифестом не
   перечисляются и в сверке пропускаются —
   [pgnode/05-verify.md](../pgnode/05-verify.md) §2); сквозной sha256 объекта сверяется
   с полем `sha256` etcd-статуса полного. Распаковки на диск НЕТ; staging
   не используется. Статус `GET /api/ops/verify` (фазы
   `downloading|verifying`, `started_unix`); воркер супервизит поллингом до
   итога ([pgnode/05-verify.md](../pgnode/05-verify.md)). Транспортный
   сбой чтения (S3/сеть) — transient (статус операции `failed` с фазой
   `downloading`): PENDING остаётся, ретраи тиками (следующий тик повторяет
   POST — операция начнётся заново, резюмов нет); расхождение с manifest
   (фаза `verifying`) — permanent (данные плохие). Операторская отмена
   идущей проверки (`POST /api/ops/cancel` приёмника — внешний канал мимо
   воркера) — операция завершается снимком `state=cancelled` (НЕ failed):
   отмена — не суждение о данных; воркер-супервиз по GET `cancelled`
   возвращает кандидата в PENDING (`checked_unix=now` — перепроверка по
   расписанию политики `verify.interval_sec`, лив-лок немедленных
   перезапусков исключён), journal-факт `cancelled-by-operator` обязателен;
   перманентного FAILED отмена не порождает. GET 404 (операции нет — старт
   не дошёл/рестарт приёмника) — transient: следующий тик повторяет POST;
   идущий процесс приёмника жив под supervisord'ом ноды — «окна бута
   ephemeral-контейнера» нет (стартовавшее приложение уже слушает API).
2. **Сверка снимка по `id` и виду операции.** Ops-реестр приёмника ОДИН
   на процесс, и снимок `GET /api/ops/verify` может быть чужим/прошлым
   (напр., терминал restore/drill-операции ТОГО ЖЕ полного с её текстом
   `pg_ctl`: id verify- и restore-снимков одного полного совпадают).
   Чужим является снимок с чужим `id`, с чужим `kind` (не `verify`) или
   без `kind` ([pgnode/02-api.md](../pgnode/02-api.md) §3) — доказательства
   итога проверки НЕТ (ни OK, ни FAILED) — vanished-семантика (повторный
   POST идемпотентно поверх терминального снимка; чужой running ответит
   409 — ожидание освобождения реестра, следующий тик повторит),
   verify-статус кандидата не меняется.

Полнота WAL-набора отдельной проверкой воркера НЕ проверяется: состав
манифеста и правило пропуска `pg_wal/<segment>` — канон механики
([pgnode/05-verify.md](../pgnode/05-verify.md) §2); непрерывность дубля в
`wal/` — общий контроль цепочки от `chain_start_segment`
([02-wal-archive.md](02-wal-archive.md) §3): list только `wal/`, сегменты
самого набора листингом недоступны (внутри tar-объекта).

Зелёная → `verify.state=OK` + `checked_unix`; красная → `FAILED` + `error`;
verify идемпотентен — vanished-операция перезапускается (PENDING),
переснятие полного не требуется. Проверки по политике: `verify.on_create` —
сразу после COMPLETED, `verify.interval_sec` — периодическая перепроверка
каждого оставшегося COMPLETED-полного по возрасту `verify.checked_unix`
(тихая порча/утеря объектов S3).

## 8. Наблюдаемость итога verify

Итог проверки каждого полного — OK/FAILED + причина (`verify.error`) —
воркер фиксирует и строкой собственного журнала (host-лог), в дополнение к
verify-статусу etcd-ключа: исходы verify обязаны быть наблюдаемы из журнала
воркера — etcd-ключи префикса чистятся deprovisioning'ом (D2), журнал
остаётся летописью после факта. Порядок фиксации: сначала etcd-статус, затем
journal-фаза, затем строка host-лога — отказ journal-фазы строку НЕ отменяет:
итог уже зафиксирован в etcd-ключе, а повторного терминального исхода тот же
полный не порождает.
