# Бэкапы: хранилище S3 — layout и пул

Уровень 3. Функция «хранилище»: раскладка объектов, семантика пула
(запись/чтение/удаление), circuit-breaker, дублирование WAL, служебный
префикс и клиенты. Ретенционная чистка — [07-retention.md](07-retention.md);
ключи/креды — [05-etcd-contract.md](05-etcd-contract.md),
[08-secrets.md](08-secrets.md).

## 1. Layout

Bucket ОДИН на установку (`PgWorker:Backups:S3:Bucket`, env
`PGW_BACKUP_S3_BUCKET`); запись кластера — в ПУЛ S3 (per-cluster выбор
policy.s3 — пул = кластер `/s3/clusters/`, bucket единый на всех нодах пула;
разные пулы — раздельные экземпляры этого bucket, mesh-репликация — внутри
пула). Префиксы per-cluster/per-shard:

```
s3://<bucket>/<C>/<X>/
 full/<id>/          # файлы pg_basebackup 1:1
                     # (вкл. backup_manifest, pg_wal/)
 wal/<segment>       # 000000010000000000000001, …
 wal/00000002.history # timeline-истории (обязательны)
```

Ключ объекта = путь файла; `backup_manifest` в корне `full/<id>/` — база
`pg_verifybackup` (скачивание в staging → verify). Никаких tar-обёрток;
WAL-сегмент = один объект. Layout одинаков для MinIO и облака; адресация —
ноды пула.

## 2. Семантика пула

**Запись (put/delete)** — «первый доступный по списку роли»
(`write_master`/`write_replica`, перебор при отказе; исчерпание → маркер
`s3-pool-exhausted`). **Чтение** — все ноды пула без приоритетов, «где данные
есть» (страховка на лаг доставки mesh-репликации), три семантики: точечные
GET — перебор до найденного; инвентарь-листинги — первая доступная нода (лаг
mesh допускается — повторные проходы досматривают); исключение — проверки
непрерывности цепочки (контроль
[02-wal-archive.md](02-wal-archive.md) §3, verify, drill): union-листинг
`wal/` и `full/<id>/pg_wal/` по ВСЕМ нодам пула с дедупом по имени объекта
(соло-листинг отстающей ноды даёт ложную дыру и ложный WAL_CHAIN_ERROR, а
соло-лист набора полного на ноде, куда он не заливался, — ложное «пусто»);
контроль цепочки получает вместе с union и ФАКТ ПОЛНОТЫ обхода — перечень не
ответивших транспортом целей (включая исключённых breaker-окном): неполный
набор НЕ доказывает дыру (сегмент может лежать на недоступной ноде — см.
правила непрерывности [02-wal-archive.md](02-wal-archive.md) §3).

**Удаления ретенции** per-cluster — по `write_master`-списку (перебор при
отказе; недоступны все мастера при живой реплике — удаление откладывается до
ретрая следующего прохода; успешное удаление mesh разносит tombstone). 
**Глобальные сверки** (`used_bytes`, реестр сирот) — union по ВСЕМ
существующим пулам `/s3/clusters/` (первый доступный endpoint каждого; дедуп
ключей — по (пул, ключ)).

## 3. Исключение отказавшей цели (circuit-breaker)

Перебор любого списка всегда начинается с первой цели; цель с транспортным
отказом (таймаут, обрыв соединения; ответ NotFound — НЕ отказ: сервер жив и
отвечает) исключается из перебора на окно восстановления 45 с. Внутренние
ретраи S3-клиента цели ВЫКЛЮЧЕНЫ (`MaxErrorRetry=0`): политика повторов —
перебор целей + breaker; SDK-ретраи дублировали её и умножали
пер-попыточный таймаут на мёртвой ноде. Без окна кумулятивные
пер-попыточные таймауты недоступной первой ноды стоили бы каждому вызову
прохода (минуты на проход по всем операциям тика); с окном мёртвая цель
зондируется не чаще раза в 45 с. По истечении окна цель возвращается в
перебор, успешный ответ возвращает её сразу; отказ цели в окне несёт
исходную ошибку в маркере исчерпания (`s3-pool-exhausted`). Отмена/исчерпание
бюджета источника — НЕ транспортный отказ цели: попытка, прерванная отменой
токена источника (linked-CTS бюджета операции при истёкшем общем таймауте),
breaker цели не открывает — цель остаётся в переборе; окно открывает только
собственный отказ цели (таймаут/обрыв на её вызове).

## 4. Дублирование WAL и служебный префикс

**Дублирование WAL**: закрытые сегменты набора `-X stream` полного бэкапа
лежат и в `full/<id>/pg_wal/` (1:1 с manifest — база verify), и копией в
`wal/` (общий префикс — стартовая точка цепочки); перезапись одного и того
же сегмента идемпотентна ([01-full-backup.md](01-full-backup.md) §4).

**Служебный префикс `etcd/`**: выгрузка снапшотов etcd (контроль-плейн) —
`etcd/snapshot-<id>.db` 1:1 + `etcd/snapshot-<id>.meta.json`
(sha256/size/revision?/taken_unix/uploaded_unix/instance; `uploaded_unix` —
фактическое время put'а объекта, в отличие от «покрытия» в статус-ключе).
Экспортёр — EtcdWorker ([etcdworker/04-snapshots.md](../etcdworker/04-snapshots.md)):
цель — фиксированный etcd-слепковый bucket `etcd-backups` на нодах
etcd-backup кластера `/s3/clusters/` (признак `etcd_backup=true`;
bucket создаёт S3Worker; креды — ключ `backups` secrets-ключа кластера),
каденс — плановый интервал + детекция изменений; каждый снятый слепок
выгружается; статус-ключ покрытия `/etcdworker/snapshots` обновляется после
каждой выгрузки. Вне per-cluster layout: не форма `<C>/<X>/` → реестр сирот
его не группирует (ключи короче 3 сегментов); ретенция и wal-sweeper к
`etcd/` не прикасаются (их пути адресны: `full/<id>/`, `wal/`, `<C>/<X>/`).
Единственный удаляющий — ретенция самого экспорта (N последних пар, guard ≥1
полная пара). Слепковый bucket `etcd-backups` — отдельный от per-install
bucket'а бэкапов: объекты `etcd/` в `used_bytes` ключа
`/pgworker/backups/storage` не входят (list per-install bucket'а пула; объём
слепков — собственная ретенция N пар).

## 5. Панель и клиенты

**Панель читает bucket read-only**: live-инвентарь/health/сверка в грани
«Хранилище бэкапов» ([adminpanel/02-etcd-contract.md](../adminpanel/02-etcd-contract.md)
§2.5); пишущие/удаляющие операции S3 — ТОЛЬКО воркер (ретенция, супервизор).

**Клиент S3 воркера** (AWSSDK в процессе воркера; операции бэкапов
исполняют приёмники нод своими .NET-клиентами — не этот клиент):
пер-попыточный таймаут короче окна проверки watchdog
(`AmazonS3Config.Timeout` = полокна, 10 с при дефолтах — симметрия
таймаутов etcd/patroni/SQL,
[pgworker/08-operability.md](../pgworker/08-operability.md) §3) + пульс
активности на время каждого вызова (`S3Pulse`,
[pgworker/08-operability.md](../pgworker/08-operability.md) §3 «пульс
конечного внешнего вызова»). Недоступный endpoint → transient-фейл тика
(журнал/статус несут ошибку), повтор — следующим тиком/проходом/retry
выгрузки (`Retry.BaseSec`, `RetryIntervalSec`); списки/геты/put-ы снапшотов
и wal-history, ретенция и sweeper — один класс (никаких «вечных» вызовов
воркера к S3). **Кэш пул-клиентов**: фабрика создаёт клиент пула ОДИН РАЗ
на контекст пула (pool + endpoints + креды + bucket + CA; смена любого —
новый клиент, прежний живёт до конца процесса — клиентов по числу пулов,
единицы), вызывающие получают кэшированный инстанс и НЕ диспоузят его —
circuit-breaker-стейт отказных целей переживает тики: недоступная нода пула
оплачивает свой таймаут один раз за breaker-окно, а не в каждом тике каждой
врезки (иначе мёртвая цель растягивала бы КАЖДЫЙ тик воркера на полный
S3-таймаут — фактический тик 5 c превращался в ~35 c).
