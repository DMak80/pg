# F. RestoreProcess (восстановление шарда)

Уровень 4. Машина тика восстановления шарда под клэймом `<C>`: валидация,
демонтаж, подъём, восстановление, REJOINING, SQL-гейт, завершение/отмена.
Функция — [03-restore.md](../03-restore.md) §3; механика операции ноды —
[pgnode/06-restore-drill.md](../../pgnode/06-restore-drill.md); ключи —
[05-etcd-contract.md](../05-etcd-contract.md); состояния —
[enums.md](enums.md).

## 1. Параллелизм

Заявка несёт `chain_life` — номер жизни ВЫБРАННОГО полного (воркер
подставляет при создании заявки из `chain_life` full-статуса выбранного;
DR-кандидат без etcd-статуса — поля нет; fetch-wal фильтрует куски по
этому номеру — [../../pgnode/06-restore-drill.md](../../pgnode/06-restore-drill.md)
§2, формат — [05-etcd-contract.md](../05-etcd-contract.md) §1).

Заявки РАЗНЫХ шардов прогрессируют в одном тике независимо (один шаг на
шард за тик, каждый — ОТДЕЛЬНОЙ таской; тик ждёт все через Task.WhenAll):
шарды независимы (свои ноды/тома/S3-префиксы). Так же независимы НОДЫ
внутри шага: снос нод при демонтаже, ensure + bootstrap-доставка каждой
rejoin-реплики — параллельные таски одного шага; журнал фаз (WorkJournal)
сериализует свои read-modify-write записи. Обработка «только самого старого
активного» / последовательный обход сериализовали бы DR-восстановление
нескольких шардов.

## 2. Автомат

```
PLANNED → валидация (кластер Active, шард заявлен, шард без усыновлённых
  object-нод (чужой PGDATA-контур — permanent-отказ «ручной runbook»),
  бэкап существует — etcd-статусы ИЛИ list-S3 backup_manifest (DR: etcd
  пуст), WAL-цепочка от wal_start_segment полного непрерывна (WalChain) —
  дыра → permanent-отказ с границами, включая RPO-зазор tli-прыжка
  приёмника: восстановление от полных ниже зазора невозможно до
  переснятия — честное RPO-окно; verify полных вне диапазона зазора не
  затрагивается)
→ RUNNING (демонтаж: контейнеры/volumes ВСЕХ нод шарда снесены (приёмники
  WAL уходят с нодами), HA-scope /service/<C>-<X>/ вычищен
  (P2.2-Д3-образец: initialize/leader/sync/status/failover + префиксы
  optime//members/; failover обязателен — остаточный маркер с scheduled_at
  в прошлом для Patroni новой жизни «accelerated failover» на
  неинициализированную ноду-кандидат, лидерство недостижимо;
  request_* — декларации панели — НЕ трогаем), ноды state=REBUILDING,
  portalloc/dsn НЕ меняются; факт — фаза заявки phase="demolished";
  ПЕРВЫЙ переход в demolished инкрементирует счётчик `wal-life` шарда
  (причина `restore`: все ноды снесены — старая жизнь цепочки гарантированно
  закончилась до возможного старта стрима восстановленных нод; инкремент
  идемпотентен на заявку — повторный тик/takeover по той же фазе не
  считает; правила — [05-etcd-contract.md](../05-etcd-contract.md) §1);
  демонтаж идемпотентен — takeover-повтор безопасен)
→ подъём первой ноды (EnsureNode, новый пустой volume, щит; ПАРАЛЛЕЛЬНО
  восстановлению первички — оптимизация обязательная, ноды независимы:
  подъём/delivery-хендшейк остальных (rejoin) нод шарда — EnsureNode +
  bootstrap-ключи + команда доставки НЕ ждут завершения restore первички
  (их Patroni ждут initialize/лидера — фаза (б) SELECT 1 без бюджета
  легитимно держит initializing до REJOINING; после промоута первички
  реплики бутстрапаются pg_basebackup и сходятся к ready); шаги
  restore-операции по одной ноде доставкой других не блокируются;
  первичку параллельный путь не трогает — её доставка/хендшейк в
  собственном порядке (tool-доставка параметров для restore-команды →
  восстановление → REJOINING-старт Patroni: параметры её старта зависят
  от восстановленного состояния); PgNode ноды ПЕРЕД RESTORE-восстановлением
  ОСТАНАВЛИВАЕТ Patroni ноды (только restore: дрилл на живой ноде Patroni
  не трогает — stop spilo там гасит прод-постгрес) (supervisorctl stop
  spilo; supervisord-сокет контейнера — chmod=0770 root:postgres в
  supervisord.conf образа — приёмник работает под postgres) с
  ПОДТВЕРЖДЕНИЕМ останова: stop не удался — операция не начинается
  (честный failed-снимок, не тихая гонка) — и возвращает Patroni в finally
  ПОСЛЕ любого исхода — живой Patroni иначе вмешивается в заполняемую
  PGDATA (стартует постгрес «secondary» на полуданных, воссоздаёт
  standby.signal, убивает restore-постгрес «чужим» процессом)) + команда
  POST /api/ops/restore её PgNode (факты — фазы заявки: phase="demolished"
  → phase="launching" (команда принята) → фазы операции приёмника
  downloading/recovering; 409 при запуске — в общем ops-реестре приёмника
  (одна ops-операция на процесс) идёт ЧУЖАЯ операция (verify свежего
  полного): снимок 409 не различает свою/чужую — launching откладывается
  (transient, фаза остаётся demolished, повтор следующим тиком до
  освобождения реестра); принять 409 за «свою живую» нельзя — verify
  затирает снимки общего реестра, и воркер уходил бы в REJOINING от чужого
  succeeded без system_id (щит-заполнитель навсегда запир бы bootstrap))
→ REJOINING (щит initialize → system_id восстановленного PGDATA; рестарта
  ноды НЕТ: restore-операция сама вернула Patroni (start spilo) уже с
  валидным initialize и данными — Patroni поднимает восстановленный
  постгрес и продолжает recovery до промоута, bootstrap с непустым PGDATA
  при чистом DCS; ожидание идентифицирующей пробы P2.2-образцом; остальные
  ноды подняты/доставлены ПАРАЛЛЕЛЬНО восстановлению, реплики догоняются
  pg_basebackup с восстановленного лидера)
→ все ноды RUNNING → SQL-гейт мастера: проба фактического постгреса лидера
  восстановленного шарда pg_is_in_recovery = false по admin-DSN первой
  ноды; Patroni-пробы живы и в переходном окне рестарта postmaster, а
  COMPLETED обязан означать закрытое окно — после него планировщик полных
  немедленно стартует пересъём, тесты/панель читают. Бюджет —
  PatroniBootSec; исчерпан → permanent-FAILED «мастер не принял SQL»
→ COMPLETED (пост-обработка: ключ wal шарда УДАЛЯЕТСЯ — планировщик
  немедленно переснимает полный (инвариант цепочки; PITR-назад ломает
  сшиваемость TLI — новая цепочка начинается с нового полного), приёмники
  WAL новых нод включаются сами с новым слотом)
```

## 3. Гвард исключения

Пока у шарда есть активный (не COMPLETED/FAILED) restore-ключ, контуры
воркера шард не трогают — надзор не пересоздаёт снесённые ноды (иначе пустой
Patroni поверх restore), не ускоряет failover и не rebuild'ит ноды шарда,
эвакуатор не считает шард мёртвым, планировщик полных скипает шард,
wal-sweeper не исполняет ветку кусков чужих номеров жизни (куски жизни
заявки ещё читает fetch-wal наката — [D](d-wal-sweeper.md)),
усыновление/репарация переездов не касаются (restore сам владеет жизненным
циклом шарда; переезды бакетов получают обычный transient «мастер
недоступен»). Гвард проверяется СВЕЖИМ чтением restore-ключей из etcd НА
ШАГЕ мутации надзора (перед ускорением failover, пересозданием/сносом ноды,
пробами rebuild): снапшот тика отстаёт от записи заявки, и долгий тик
надзора без свежей сверки исполняет мутации посреди демонтажа/REJOINING —
ускорение failover кладёт residual `failover`-маркер в чистый HA-scope,
пересоздание — пустую ноду поверх восстанавливаемой.

## 4. Исходы и отмена

Transient-сбой фазы → ретраи тиками (демонтаж/запуск идемпотентны);
permanent (дыра WAL, бэкап исчез, recovery-бюджет исчерпан, target не
достигнут — конец цепочки раньше `target_time`) → `FAILED` + `error`;
повтор — НОВАЯ заявка оператора.

Операторская отмена идущей операции (`POST /api/ops/cancel` приёмника ноды —
внешний канал мимо воркера) → операция приёмника завершается снимком
`state=cancelled` (НЕ failed); воркер-супервиз по GET `cancelled` возвращает
всё к состоянию «как до старта операции»: первая нода сносится вместе с
data-volume (до-restore «пустое» состояние демонтажа), щит `initialize`
снимается (заполнитель «restore-in-progress» запер бы bootstrap пустых
нод), запись заявки `/<C>/<X>/restore/<id>` УДАЛЯЕТСЯ из etcd — операции
нет, записи нет; journal-факт `cancelled-by-operator` обязателен;
перманентного FAILED отмена не порождает — шард остаётся разобранным,
повтор — новая заявка оператора. Takeover: статус + детерминированные
имена — новый инстанс продолжает.

## 5. Стоп-семантика

Deprovisioning (D1) сносит ноды шарда вместе с приёмниками (restore-операция
уходит с нодой), D2 чистит префикс `/pgworker/backups/<C>/` (вкл.
restore-ключи); remove-shard с активным restore → заявка FAILED
`cancelled-by-remove`. S3-объекты restore не удаляет никогда (только читает).
