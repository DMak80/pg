# C. Retention (GFS-ретенция и чистка WAL)

Уровень 4. Rolling-проход ретенции полных: GFS-отбор, guard последнего
валидного, `DELETING`, гигиена FAILED, чистка WAL ниже cutoff. Функция —
[07-retention.md](../07-retention.md) §1–§2; ключи —
[05-etcd-contract.md](../05-etcd-contract.md); состояния —
[enums.md](enums.md).

Проход воркера под клэймом `<C>` по расписанию `Retention:IntervalSec`, для
каждого шарда Active-кластера.

## 1. GFS-отбор

1. **По календарю UTC**: дневные — все COMPLETED-полные последних
   `retention.days` календарных суток; недельные — ПОСЛЕДНИЙ COMPLETED
   каждой из `retention.weeks` предыдущих календарных недель (ISO-неделя);
   месячные — ПОСЛЕДНИЙ COMPLETED каждого из `retention.months` предыдущих
   календарных месяцев. Активные (PLANNED/RUNNING/UPLOADING) и DELETING в
   отборе не участвуют. Счётчики — policy-ключ кластера, дефолт —
   `PgWorker:Backups:Policy`. Полные ТЕКУЩЕЙ недели/месяца вне дневного
   окна недельными/месячными точками НЕ удерживаются: счётчики считают
   строго ПРЕДЫДУЩИЕ календарные недели/месяцы; текущий период удерживает
   только дневная гранула.
2. **Guard последнего валидного**: последний COMPLETED-полный шарда не
   удаляется НИКОГДА, даже просроченный по GFS. «Валидный» = COMPLETED
   (verify-статусы на guard НЕ влияют; полные с `verify.state=FAILED` —
   первые кандидаты на удаление, но guard «≥1 COMPLETED» держится и над
   ними: лучше старый невалидный, чем никакого).
3. **Удаление полного**: `DELETING` (journal-before-manipulations) → delete
   объекта `full/<id>.tar` (полный — один объект; вместе с ним abort
   висячих multipart-сессий ключа, если есть) → del etcd-ключа.
   Transient-отказ S3 → остаётся `DELETING`, следующий проход повторяет
   (идемпотентно). За один проход удаляется ОДИН полный (по старшинству;
   FAILED-verify — вперёд) — тик короткий, backlog выгребается
   последующими проходами. Зависший `DELETING` (возраст > порога панели) →
   warning-алерт `backup-deleting-stuck`.
4. **Гигиена истории**: FAILED-ключи шарда — держатся последние
   `Retention:KeepFailed` (по `started_unix`), старше — del. Бэкофф
   переснятия не ломается: n = FAILED с последнего COMPLETED ≤ KeepFailed, а
   `BaseSec·2^(n−1)` упирается в `MaxSec` задолго до границы (при дефолтах —
   с n≈5).

## 2. Чистка WAL ниже cutoff

Cutoff = `wal_start_segment` новейшего (по `started_unix`) COMPLETED-полного
с `verify.state=OK` ИЗ ОСТАВЛЯЕМЫХ — кандидат удаления текущего прохода
(Delete[0] GFS-отбора) точкой cutoff не якорит: в переходном окне, где
новейший OK-полный сам стал кандидатом удаления, привязка cutoff к нему
срезала бы WAL между предыдущим OK-полным и ним — RPO-дыра после доводки
DELETING. Срез только после создания полного И его успешного verify.

**Нижняя граница чистки — самый старый ОСТАВЛЯЕМЫЙ COMPLETED-полный**
(`oldest` = минимальный по (TLI, позиции) `wal_start_segment` среди
оставляемых): цепочка оставляемого полного идёт от его `wal_start` через
ВСЕ промежуточные TLI-переходы (failover/restore/promote), поэтому
удаляются только объекты вне цепочек оставляемых полных:

- сегменты и `.partial`-семейства строго ниже `oldest` (TLI ниже или тот
  же TLI с позицией `log·256+seg` ниже `oldest`) — их не может читать ни
  одно оставляемое восстановление;
- сегменты и куски в TLI `cutoff` строго ниже позиции `cutoff` — чистка
  хвоста перед новейшим полным;
- `.history` удаляется только для TLI ≤ `oldest.TLI`: переход в TLI самого
  старого оставляемого полного уже позади. `.history` выше `oldest.TLI` —
  часть цепочек оставляемых полных и живут.

Объекты в TLI между `oldest.TLI` и `cutoff.TLI` (сегменты, куски,
`.history`) НЕ удаляются, пока соответствующий оставляемый полный жив:
удаление промежуточного TLI режет его цепочку, и restore по `target_time`
упирается в «конец WAL» до цели, хотя полный формально хранится
(факт t92). Сам `cutoff`-сегмент и всё выше/новее — живут; объект TLI выше
`cutoff` позицией ниже `cutoff` по-прежнему консервативно не трогается.

**ГВАРД verify**: прунинг WAL ниже точки полного, НЕ прошедшего verify
(PENDING/FAILED — в т.ч. при перепроверке OK→FAILED), запрещён — cutoff
держится на предыдущем verify-OK полном; verify-OK-полного нет вовсе — WAL
не чистится (нет безопасной точки привязки).

Правило окна WAL: удерживается от `wal_start_segment` последнего
оставляемого verify-OK полного — полный переснимается по
`full_max_age_sec` (суточный цикл), фактический интервал варьируется
(форсированный пересъём по WAL_CHAIN_ERROR, бэкофф серии FAILED, guard
последнего валидного) — окно WAL ≈ «от последнего полного, приблизительно
раз в сутки, с временными сдвигами»; PITR-окно = от cutoff до хвоста
потока. Недельная/месячная GFS-точки на cutoff НЕ влияют.
`.partial`-кусочные объекты (базы/дельты/legacy-версии) чистятся двумя
путями: поглощение финалом (лежит `wal/<segment>` → всё кусочное семейство
сегмента — мусор этого же прохода) и общий порядок ниже cutoff; куски ниже
базы и куски ЧУЖИХ номеров жизни (сразу, не дожидаясь cutoff) чистит
wal-sweeper ([D](d-wal-sweeper.md)) — КРОМЕ кусков жизни последнего полного
шарда: пока номер жизни L — жизнь последнего `full/<id>` шарда, куски L
остаются (RPO-хвост повторного restore/drill в окне до пересъёма), гейт —
[D](d-wal-sweeper.md). `chain_start` пересчитывается автоматически при
следующем контроле (list S3 — истина; старт контроля — от той же точки из
оставляемых; в переходном окне контроль может якориться выше cutoff — по
кандидату удаления текущего прохода: безопасно, нижележащий cutoff режет
меньше): list-префикс укорачивается, старые дыры ниже cutoff исчезают.

`Backups:Enabled=false` → ретенция no-op (чистки нет, копится до включения;
зависшие DELETING видит панельный алерт).
