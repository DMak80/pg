# D. WalSweeper (фоновая чистка `wal/`)

Уровень 4. Фоновый цикл гигиены префикса `wal/`: куски чужих номеров жизни,
поглощённые финалом `.partial`, устаревшие версии живого сегмента, сегменты
ниже cutoff. Функция — [07-retention.md](../07-retention.md) §3; ключи —
[05-etcd-contract.md](../05-etcd-contract.md).

Приёмники пишут объекты префикса `wal/` (`.partial`-версии и финальные
сегменты) в S3 напрямую, мимо воркера — устаревший мусор префикса
отслеживает и чистит САМ PgWorker (тот же, кто инициирует бэкапы). Исполняет
ТОЛЬКО глобальный лидер `/pgworker/leader` (паттерн orphan-sweeper)
отдельным ФОНОВЫМ циклом вне тиков управления/контроля: чистка не тормозит
ни клэймы, ни контроль цепи, ни планировщик полных.

Цикл идёт ПО КАЖДОМУ ШАРДУ НЕЗАВИСИМО — отказ/пауза одного шарда (S3-цель
недоступна, шард снесён) не останавливает остальные. Вход кусочной гигиены —
текущий номер жизни цепочки шарда (счётчик `wal-life`,
[05-etcd-contract.md](../05-etcd-contract.md) §1) и номер жизни последнего
полного шарда. Опрос и оценка гигиены кусков (базы-компаки и дельты
`wal/<segment>.partial_*`, legacy `.partial`-версии): куски ЧУЖИХ номеров
жизни (`<life>` ≠ текущему) — мусор СРАЗУ, не дожидаясь cutoff (ветка смены
жизни; безномерные t14-версии сегмента, у которого появился кусок текущего
номера, — тот же класс мусора), КРОМЕ кусков жизни L, пока L — номер жизни
ПОСЛЕДНЕГО полного шарда (`full/<id>`, последний по id в etcd-статусах;
verify-OK не требуется — именно последний полный вообще): у полных без
`chain_life` (старые записи) гейта нет. Такие куски — RPO-хвост, который
читает повторный restore/drill выбранного полного B (`chain_life` = L,
[F](f-restore.md) §3) в окне до пересъёма; появился полный с более новой
жизнью (пересъём после restore) — ветка (д) для L открывается, каноническое
«чужие — сразу» действует для всех прочих жизней; поглощённые финалом
сегмента; куски НИЖЕ БАЗЫ (`end` ≤ end лучшей базы сегмента — инкременты под
кумулятивом); устаревшие базы живого сегмента — остаётся длиннейшая (max
end); кусочное семейство сегмента ниже cutoff — НЕ РЕЖЕ раза в минуту по
каждому шарду; срез финальных сегментов ниже cutoff — тем же проходом по
факту ретенционного отбора ([C](c-retention.md) §2). Дельты выше базы (живое
покрытие) sweeper НЕ трогает — их поглощает следующая компакция/финал.
Гвард исключения restore: у шарда с активным (не COMPLETED/FAILED)
restore-ключом ветка чужих номеров НЕ выполняется — куски жизни заявки
(`chain_life` выбранного полного) ещё читает fetch-wal накатываемого
restore ([F](f-restore.md) §3); гейт жизни последнего полного действует и
после терминала заявки (окно до пересъёма полного); прочая гигиена
(поглощение финалом) — как обычно.

Механика удаления: по шарду вычисляется полный список на удаление → ОДНИМ
batch-delete (повтор прохода идемпотентен). Наблюдаемость: живость цикла —
серия `worker_loop_last_success_timestamp_seconds{loop="wal-sweeper"}` плюс
per-shard свежесть последнего успешного прохода (алерт остановки цикла и
алерт просрочки отдельного шарда —
[metrics/README.md](../../metrics/02-dictionary.md) §2, паттерн OrphanSweepStalled);
`Backups:Enabled=false` → проход no-op, как ретенция.
