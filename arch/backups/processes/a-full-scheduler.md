# A. FullBackupScheduler (планировщик полных)

Уровень 4. Rolling-планировщик полных бэкапов шардов Active-кластера.
Функция — [01-full-backup.md](../01-full-backup.md) §6; ключи —
[05-etcd-contract.md](../05-etcd-contract.md); состояния —
[enums.md](enums.md).

Тик под клэймом `<C>`, для каждого шарда Active-кластера с `dsn`. Условия
due (любое):

- возраст последнего ВАЛИДНОГО COMPLETED-полного (`verify.state ≠ FAILED` —
  OK, PENDING «идёт» или verify отсутствует; полный с проваленным verify
  свежестью НЕ считается) > `full_max_age_sec`;
- валидного COMPLETED-полного нет вовсе (инвариант «поднятый шард всегда
  имеет валидную цепочку или свежий полный»: цепочку контроль заведёт от
  `wal_start_segment` свежего COMPLETED, когда приёмники донесут ПЕРВЫЙ
  ЗАКРЫТЫЙ сегмент — приёмник выгружает только закрытые сегменты, поэтому
  на шарде без нагрузки ключ `wal` появляется позже первого полного, и
  пересъём в этом окне бессмыслен: серия полных подряд ничего не добавляет;
  сброс цепочки restore'ом покрыт гвардом «полный не старее последней
  COMPLETED-restore», разрыв — WAL_CHAIN_ERROR-гвардом ниже);
- wal-ключ шарда в `WAL_CHAIN_ERROR` — разрыв цепочки, пересъём безусловно
  (инвариант «у живого шарда валидная цепочка или активный полный»;
  бэкофф серии FAILED работает как всегда — шторм пересъёмов исключён;
  исключение не работает для УСПЕШНЫХ пересъёмов — COMPLETED не включает
  бэкофф, и при живом WAL_CHAIN_ERROR-ключе полный планировался заново
  каждый тик; правило покрытия: WAL_CHAIN_ERROR-пересъём планируется только
  пока НЕТ COMPLETED-полного с `wal_start_segment` ≥ границы разрыва
  (`chain_start_segment` WAL_CHAIN_ERROR-записи) — такой полный уже покрывает
  разрыв, контроль заживит им очередным тиком; не покрывший полный (FAILED,
  либо старт ниже границы) — пересъём снова, по общим правилам);
- живой непокрытый `gap` в wal-ключе — tli-зазор приёмника, пересъём
  безусловно (симметрично WAL_CHAIN_ERROR-правилу покрытия: покрывший
  COMPLETED-полный ждёт снятия метки контролем; непокрывший — пересъём
  снова; инвариант одного активного и бэкофф FAILED работают как всегда).

Действие: создать `full/<id>` (PLANNED → API-запуск на приёмнике →
RUNNING); инвариант — максимум один активный (PLANNED/RUNNING/UPLOADING)
полный на шард одновременно.

Бэкофф `min(Retry.BaseSec·2^(n−1), Retry.MaxSec)`, где n — число попыток с
момента последнего валидного COMPLETED шарда: FAILED операции +
verify-FAILED + НЕпокрывшие COMPLETED (wal_start ниже живой границы разрыва
— антишторм: пока redo/restart-точка источника не перешла границу, повторный
полный снимается с той же позиции — без пользы — вычислимо из истории
ключей, дополнительных полей контракта не требуется).

Пересъём при живой непокрытой границе ПРЕДВАРЯЕТСЯ `CHECKPOINT` НА МАСТЕРЕ
шарда (пересъём — следующий тик, без гонки за replay): BASE_BACKUP-клиент
получает в `backup_label` START WAL с redo/restart-точки источника; restartpoint
реплики движется ТОЛЬКО по checkpoint-записям мастера, а idle-мастер их не
пишет — точка стоит в сегменте ДО границы зазора, и пересъём снимался бы с
той же позиции бесконечно (CHECKPOINT на самой реплике — restartpoint по
старой checkpoint-записи — точку НЕ двигает); checkpoint-запись мастера
реплика replay'ит, точка переносится в текущий сегмент — следующий полный
получает `wal_start ≥ границы` и покрывает зазор.

Лимита попыток нет: порог «долго без валидного» — суточный алерт панели.
Takeover: всё состояние в etcd, адрес приёмника детерминирован
(`alias:8080` по имени ноды) — новый инстанс продолжает супервизить;
RUNNING-статус при GET 404 → FAILED `operation-vanished` (рестарт
приёмника/ноды; переснятие по общему правилу).
