# G. RestoreDrillProcess (дрилл восстановимости)

Уровень 4. Машина тика дрилла: супервиз операции, отбор кандидата,
валидация, запуск, исходы. Функция — [04-drill.md](../04-drill.md) §2–§6;
механика операции — [pgnode/06-restore-drill.md](../../pgnode/06-restore-drill.md) §3;
ключи — [05-etcd-contract.md](../05-etcd-contract.md); состояния —
[enums.md](enums.md).

Тиковая машина под клэймом `<C>` (Op `backup-drill`; врезка ReconcileLoop
после backup-restore, до repair; вызов ВСЕГДА — стоп-семантика ниже):
супервиз активной drill-операции PgNode первой ноды шарда (фазы
`downloading|recovering` и итог — по API `GET /api/ops/restore`), затем
отбор кандидата, валидация, запуск (`POST /api/ops/restore` с id дрилла —
latest, БЕЗ target).

## 1. Супервиз и исходы

Бюджет активного дрилла — `Drill:TimeoutSec` от `started_unix` ключа →
FAILED `drill-timeout` (+ `POST /api/ops/cancel` best-effort); бюджет наката
WAL внутри операции — общий `Restore:RecoveryTimeoutSec` (REJOINING-фаз у
дрилла нет — после операции сразу терминальный исход). Takeover: всё
состояние — в etcd-ключе, адрес приёмника детерминирован (`alias:8080`
первой ноды) — новый инстанс продолжает супервиз до исхода; GET 404
(операция vanished — рестарт приёмника) при молодом ключе — повторный POST
(резюмов нет — скачается заново), при возрасте ≥ бюджета — FAILED
`drill-vanished`.

Операторская отмена идущего дрилла (`POST /api/ops/cancel` приёмника —
внешний канал мимо воркера) → операция приёмника завершается снимком
`state=cancelled` (НЕ failed); воркер-супервиз по GET `cancelled` УДАЛЯЕТ
ключ дрилла — операций нет, записи нет (scratch-каталог чистит приёмник при
отмене — следов на ноде не остаётся); journal-факт `cancelled-by-operator`
обязателен; перманентного FAILED отмена не порождает (следующий дрилл шарда
— по общим правилам отбора).

## 2. Отбор кандидата

Чистая функция: один шард за проход кластера — наименее свежий по последнему
терминальному дриллу (MIN `finished_unix`; «никогда» = 0 — обслуживается
первым; tie-break по имени — детерминизм). Гварды: `interval_days ≤ 0` —
дрилл кластера выключен; RUNNING-дрилл кластера блокирует новые — один
активный дрилл на кластер; активная restore-заявка владеет жизненным циклом
шарда — шард не кандидат; `ToRemove`-шард и шард без COMPLETED-полных — не
кандидаты. Готовность: `now − (finished_unix последнего терминального
дрилла шарда)` ≥ `interval_days×86400`; ключа дрилла нет вообще — готов
немедленно (первый дрилл). Интервал per-cluster:
`policy.drill.interval_days` ?? дефолт конфига `Drill:IntervalDays`.

## 3. Валидация и запуск

Валидация кандидата — та же, что у restore-заявки own-source (новейший
COMPLETED ⇒ объект `full/<id>.tar` существует (S3) ⇒
`wal_start_segment` (etcd-статус либо `backup_label`) ⇒ WalChain непрерывна
— RPO-зазор tli-прыжка приёмника тоже даёт permanent-отказ с границами:
дрилл периодически вскрывает незакрытый зазор оператору; verify полных вне
диапазона зазора не затрагивается); S3-отказ — transient (статус не трогаем,
тик повторит). Отказ валидации (манифеста нет / дыра цепочки) → FAILED-дрилл
БЕЗ запуска операции: `started_unix`/`finished_unix` поставлены, `error` —
причина (границы дыры от WalChain); контейнера/каталога не было — чистка не
нужна, ключ сразу чистый терминальный итог — честный исход «восстановимость
не доказана». Запуск — journal-before-manipulations: put ключа RUNNING до
команды ⇒ `POST /api/ops/restore` (id дрилла, `chain_life` выбранного
полного — fetch-wal дрилла фильтрует куски по номеру жизни,
[../../pgnode/06-restore-drill.md](../../pgnode/06-restore-drill.md) §2)
на приёмник первой ноды; отказ
команды — transient (ключ остаётся RUNNING — следующий тик повторит POST
идемпотентно; 409 — операция уже жива).

## 4. Стоп-семантика

`Backups:Enabled=false` (или интервал `0`) — новых запусков нет; идущий
дрилл доводится до терминального исхода (стоп-семантика супервиза
продолжается). Активная restore-заявка владеет жизненным циклом шарда —
ИДУЩИЙ дрилл уступает при появлении заявки: операция отменяется
(`POST /api/ops/cancel`, только если активная операция реестра — своя,
сверка `id` снимка), ключ дрилла УДАЛЯЕТСЯ (симметрия операторской отмене —
записи нет), journal-факт `yielded-to-restore`. Иначе дрилл держит
единственный ops-слот первой ноды, restore получает 409 и остаётся в фазе
`demolished` до конца дрилла.

Deprovisioning: D1 сносит ноды шарда вместе с приёмниками (drill-операция
уходит с нодой); D2 — ключ `drill` уходит с per-cluster префиксом
`/pgworker/backups/<C>/`. Идущий дрилл не ломается демонтажом шарда (дрилл
не создаёт нод — S3 + приёмник живой ноды); remove-shard при активной
restore — дрилл шарда не стартует (гвард отбора).
