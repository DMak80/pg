# B. WalChainControl (контроль WAL-цепочки)

Уровень 4. Контроль непрерывности WAL-цепочки в S3, диагностика
`WAL_CHAIN_ERROR`/`gap`/отставания, ensure и пересоздание слотов,
стоп-семантика. Функция — [02-wal-archive.md](../02-wal-archive.md) §3–§6;
ключи — [05-etcd-contract.md](../05-etcd-contract.md); состояния —
[enums.md](enums.md).

## 1. Истина прогресса и контроль

Приёмник пишет объекты в S3 (сегменты, `.history`) и свой статус-ключ — и
ничего больше; воркер с периодом `Wal:VerifyIntervalSec` выполняет контроль
цепочки — union-листинг префикса `wal/` по ВСЕМ нодам пула с дедупом по
имени объекта (ложная дыра на отстающей ноде исключена; успех — при ответе
хотя бы одной ноды, исчерпание — маркер) — и по факту объектов вычисляет
`last_uploaded`, непрерывность цепочки и пишет etcd-ключ `wal` (хвост
потока — максимальный валидный префикс: финальный объект сегмента либо
лучший `.partial` этого сегмента — версии в дедупе схлопываются по сегменту,
учитывается длиннейшая). Статус-ключи приёмников воркер только читает;
«последний загруженный» из статуса приёмника НЕ используется — один
источник истины, объекты.

**Правила непрерывности**: имя сегмента — 24 hex символа
`TLI(8)+log(8)+seg(8)`; следующий = `seg+1`, при `seg=0xFF` → `log+1,
seg=0`; переход timeline валиден при наличии загруженного
`<newTLI>.history` и первом сегменте нового TLI, равном последнему сегменту
старого TLI ИЛИ следующему за ним (точка переключения внутри сегмента —
PG перезаписывает сегмент с нового TLI); полный LSN-разбор history — verify
([pgnode/05-verify.md](../../pgnode/05-verify.md) §2): воркер скачивает
`.history`-объекты из `wal/` и валидирует TLI-переходы по точке переключения
из файла (`switchWALLSN` в границах сегмента первого сегмента нового TLI);
runtime-контроль потока остаётся на эвристике номеров.

Цепочка проверяется от `chain_start_segment`: стартовая точка =
`wal_start_segment` новейшего (по `started_unix`) COMPLETED-полного с
`verify.state=OK` из оставляемых — точка cutoff WAL-чистки ретенции. Ложный
WAL_CHAIN_ERROR даёт расщепление точек только В ОДНУ сторону — контроль НИЖЕ
cutoff (стартующий от срезанных сегментов видит дыру); обратное расщепление
переходного окна (контроль выше cutoff — якорится на кандидате удаления
текущего прохода, когда новейший оставляемый OK-полный ниже) безопасно:
нижележащий cutoff режет меньше. verify-OK-полного нет → первый сегмент
потока приёмников (закрепляется в статусе при первом upload). Ретенция чистит
сегменты ниже этой точки — `chain_start` поднимается автоматически при
следующем контроле (list S3 — истина), list-префикс укорачивается.

## 2. WAL_CHAIN_ERROR, gap, DEGRADED

Дыра (нет next-сегмента / TLI-переход без history) и исчезновение ИЛИ
инвалидация (`wal_status='lost'`) слотов ВСЕХ нод-источников при живой
цепочке (per-instance) → `WAL_CHAIN_ERROR`: permanent-деградация разрыва,
приёмники шарда замирают (стоп-семантика приёмника), лечение — НОВЫЙ полный
бэкап ([A](a-full-scheduler.md) реагирует на WAL_CHAIN_ERROR пересъёмом);
`error` несёт границы разрыва.

Дыра при НЕПОЛНОМ union-наблюдении (среди нод пула есть не ответившие
транспортом) — разрыв НЕ доказан: сегмент может лежать на недоступной ноде
(она была write-целью доставки), union её не видит. Такой случай —
transient-`DEGRADED` с маркером `s3-pool-exhausted` в `error` (алерт
`backup-pool-unreachable`): приёмники продолжают стрим (DEGRADED — не
стоп-гейт), контроль — каждый тик; возврат нод даёт полный обход: цепочка
цела → снятие деградации общим порядком, дыра подтвердилась →
WAL_CHAIN_ERROR-путь выше. Ложный WAL_CHAIN_ERROR от неполного наблюдения
глушит live-детекцию исчерпания write-списка (стоп-гейт замирает приёмники
до их первого неудачного put).

Сегменты между хвостом S3 и точкой старта прыжка tli-процедуры (58P01,
[pgnode/03-wal-receiver.md](../../pgnode/03-wal-receiver.md) §6) в S3 не
появятся — осознанный RPO-зазор. Зазор на TLI-границе — НЕ
WAL_CHAIN_ERROR (CheckWithRestart склеивает цепочку от максимального TLI):
он живёт полем `gap` ключа `wal` + форсированным пересъёмом полного
(приёмники архивации не замирают); зазор внутри одного TLI — обычная дыра →
существующий WAL_CHAIN_ERROR-путь. `DEGRADED` — только transient-деградации
(lag/тишина): приёмник жив, ретраи тиками, пересъём НЕ триггерит; `error`
DEGRADED несёт маркер `s3-pool-exhausted`, когда статус-ключ
мастер-приёмника несёт живой флаг `pool_exhausted` («lag/тишина» без
маркера — обычное отставание). Флаг держит приёмник: ставит при исчерпании
write-списка, снимает первым успешным put ЛИБО границей сессии стрима —
контроль читает как факт, позиционных эвристик нет; снятие флага — статус
пересчитывается общим порядком (цепочка/lag/тишина), `error` очищается.
Exhaustion-DEGRADED (DEGRADED с маркером в `error`) — контроль КАЖДЫЙ тик,
как WAL_CHAIN_ERROR (скорость заживления; union-листинг — один класс
вызовов).

## 3. Слоты

Слоты создаёт воркер (SQL ensure идемпотентно: `pg_replication_slots` →
`pg_create_physical_replication_slot(..., true)`) на КАЖДОЙ ноде-источнике
(мастер + sync-standby) — удержание WAL на случай переключения/потери
второй стороны. Зонд слота источника — существование И `wal_status`:
существующий lost-слот лечится recreate (drop+create immediate+reserved), а
не пропускается ensure-идемпотентностью — стрим через инвалидированный слот
PG отвергает, «слот есть» ≠ «слот работает».

Слот при WAL_CHAIN_ERROR: жив (не lost) — не трогаем (копит WAL в пределах
`max_slot_wal_keep_size`), исчез или lost — пересоздаётся
immediate+reserved СРАЗУ ЖЕ (drop+create; к старту пересъёма полного слот
держит позицию ≤ wal_start нового полного; механика первого старта).
Инвалидация (lost) ОДНОГО источника при живом слоте второго — НЕ
WAL_CHAIN_ERROR: lost-слот функционально отсутствует — воркер пересоздаёт
его автоматически (journal-факт); потерянный источник возвращается сам:
приёмник ретраит от хвоста S3, хвост достраивает второй приёмник двойной
архивации (префикс `wal/` один, put идемпотентен), старт успешен, когда
следующий за хвостом сегмент существует на его ноде (срез ниже не идёт,
горизонт удаления поднимается записью). lost на всех источниках →
WAL_CHAIN_ERROR-путь выше. Пустой префикс `wal/` + lost — тот же recreate:
свежий слот immediate+reserved держит текущую позицию, приёмник стартует от
неё.

**Инвариант записи при «слот исчез»**: `last_uploaded_unix` в живом
(ACTIVE/DEGRADED) ключе обязан существовать (гварды парсеров — первая
линия); при нарушении (ручная правка/будущий писатель при ослабленном
гварде) ветка не крашится тиком: defensive-фолбэк времени (clock-сейчас) —
только defensive-значение параметра расчёта, в WAL_CHAIN_ERROR-запись now не
попадает (запись строится из живого ключа), битый ключ маркируется
journal-заметкой `wal-key-invalid/<X>`; WAL_CHAIN_ERROR/пересоздание слота
работают как обычно.

**Ratchet `chain_start_segment`**: записанное значение НИКОГДА не
понижается; в WAL_CHAIN_ERROR-записи — граница разрыва (последний
непрерывный сегмент контроля; для «слот исчез» — `last_uploaded_segment` на
момент обнаружения). При контроле цепочки стартовая точка =
wal_start_segment новейшего (по started_unix) COMPLETED-полного с
`verify.state=OK` и wal_start ≥ записанного chain_start (ratchet не
понижается) — кандидаты ниже границы разрыва игнорируются для контроля
(их цепь до их точки может быть цела; дыра выше). Контроль при
WAL_CHAIN_ERROR — каждый тик (без VerifyIntervalSec-расчёта: скорость
заживления; list дырного префикса дёшев); появился COMPLETED-полный со
стартом ≥ границы и цепь от него непрерывна → `ACTIVE`, приёмники
возобновляют стрим этим же тиком. Restore COMPLETED удаляет wal-ключ
целиком — ratchet сбрасывается вместе с ключом, противоречий нет.
`wal/<segment>` после дыры до переснятия НЕ загружаются приёмником заново
(слот держит позицию; цепь восстанавливает новый полный + новый поток).

## 4. Отставание и стоп-семантика

`lag_segments` = сегмент текущей позиции записи мастера (SQL-зонд
`pg_current_wal_lsn` → имя сегмента; подключение — admin-DSN мастера,
существующие билдеры) − `last_uploaded`; `lag_segments > Wal:LagMaxSegments`
или возраст `last_uploaded_unix` > `Wal:StaleSec` при живом кластере →
`DEGRADED` + `error` (transient: ретраи тиками; постоянное отставание без
прогресса — алерт панели).

`Backups:Enabled=false` → воркер ставит глобальный ключ
`/pgworker/backups-disabled` — приёмники кластеров замирают; демонтаж шарда
(S-процессы) и deprovisioning кластера (D1) сносят контейнеры нод —
приёмники уходят вместе с нодами (отдельных сущностей нет, staging-томов
нет); etcd-ключи кластера чистит Deprovisioning D2 (`del --prefix
/pgworker/backups/<C>/`). `STOPPED` — воркер сознательно остановил WAL-поток
живого шарда записью wal-ключа (шард QUARANTINED/эвакуация — поток WAL
мёртвого шарда не нужен; приёмники замирают по стоп-семантике приёмника);
демонтаж ключи удаляет. Этими путями S3-объекты не удаляются (R4-симметрия;
осознанные удаляющие — ретенция, wal-sweeper, супервизор, `orphan-deletes`).
