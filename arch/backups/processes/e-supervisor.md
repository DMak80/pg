## 1. Гейты мусора живого шарда

Проход сверяет СВОЙ снапшот `/pgworker/backups/` с листингом S3 — снапшот
может отставать от планировщика того же тика (запланировал и запустил полный
ПОСЛЕ снятия снапшота), поэтому «unowned»-объект удаляется только после
двух гейтов:

1. свежее чтение etcd-ключа `full/<id>` — появился → живой полный, не мусор;
2. возрастной гейт `garbage_min_age_sec` политики кластера (дефолт 600 с):
   объект `full/<id>.tar` моложе порога → заливка in-flight, не мусор
   (объект появляется в листинге только после Complete — но снапшот сверялся
   раньше; кроме того объект мог быть залит источником, чей статус воркер
   ещё не зафиксировал).

Оба гейта — перед delete; неподошедший объект остаётся следующему проходу.

**Гигиена multipart-сессий**: `ListMultipartUploads` по префиксу шарда —
оборванные сессии (uploadId без Complete; источник: рестарт приёмника
посреди операции, потерянный abort) старше `garbage_min_age_sec` →
`AbortMultipartUpload` (части сессии место в bucket занимают, но объектами
не видны — чистятся только abort'ом). Живая заливка НЕ трогается никогда:
перед abort'ом конкретной сессии супервизор СВЕЖИМ чтением etcd-ключа
`full/<id>` (id — из ключа сессии) проверяет её владельца — активный полный
(`PLANNED`/`RUNNING`/`UPLOADING`) с возрастом операции в пределах
`Job:FullTimeoutSec` (бюджет §4) означает, что сессия может быть текущей
multipart-заливкой; сессия пропускается до следующего прохода (Abort живой
сессии = `NoSuchUpload` у следующей части и падение большого полного).
Ключ не прочитан (etcd недоступен) — сессия тоже не трогается (безопасность
важнее места: недоказанный владелец не абортится). Транспортный отказ
endpoint'а листинга/abort'а — warning и следующий проход.

## 2. Реестр сирот и DR-hold

Глобальный лидер-проход `/pgworker/leader` пишет `/pgworker/backups/orphans`
(формат — [05-etcd-contract.md](../05-etcd-contract.md) §2). Живость
лидер-прохода наблюдаема серией
`worker_loop_last_success_timestamp_seconds{loop="orphan-sweep"}` (тик цикла
по итогам прохода; алерт OrphanSweepStalled).

- `first_seen_unix` переносится из предыдущей записи (merge — TTL от первого
  наблюдения); `has_valid_full` пересчитывается каждым проходом из уже
  снятого list bucket (в префиксе есть объект `full/<id>.tar` — критерий
  валидного полного, тот же, что у DR-выбора; ненаблюдаемый сирота
  сохраняет прежнее значение — защита переживает transient list).
- Владелец воскрес (кластер/шард появился в `/clusters/`) → запись удаляется,
  идущая DELETING-доводка отменяется, hold-ключ гасится; воскресение
  проверяется и при merge (по снимку `/clusters/` прохода), и повторно перед
  удалением объектов (снимок мог устареть — тогда вместо объектов гасится
  запись/hold/заявка).
- **DR-hold**: TTL-кандидатом становится OBSERVED старше
  `Supervisor:OrphanTtlSec` ТОЛЬКО при `has_valid_full=false` И без живого
  hold-ключа — сирота с валидным полным автоматикой НЕ удаляется никогда
  (последний DR-источник; осознанное удаление — только заявкой
  `orphan-deletes`).
- Кандидат → DELETING (фаза orphan-journal) → batch-delete префикса →
  list-подтверждение → del записи; один префикс за проход (приоритет:
  доводка DELETING → заявка orphan-deletes → TTL-кандидат);
  `OrphanTtlSec=0` — авто-удаление выключено, только алерт панели (заявки
  orphan-deletes работают).

**Hold-флаги** `/pgworker/backups/orphan-holds/<C>/<X>`: ставит/снимает API
воркера — атомарные put/del одного ключа, без read-modify-write (нет гонок
ни между инстансами API, ни с лидер-проходом sweeper'а — реестр тот не
пишет); гварды API: префикс — OBSERVED-сирота реестра (нет → 404;
DELETING → 409 — доводку уже начатого удаления не спасти); повторный hold
идемпотентен (put поверх); снятие hold (unhold) → сирота возвращается под
общие правила (TTL уже истёк и защиты нет → удаление ближайшим проходом;
unhold — гварды реестра не применяются: идемпотентен, только 503). Sweeper
читает при TTL-отборе (hold → не кандидат), повторно перед удалением
TTL-кандидата (hold появился после отбора → удаление откладывается до
следующего прохода) и гасит ключи несирот (владелец воскрес / префикс исчез)
— санитар прохода; DELETING-записи hold не защищают.

**Заявки orphan-deletes** `/pgworker/backups/orphan-deletes/<C>/<X>`: пишет
API воркера по confirm-команде оператора (`POST
/api/backups/orphans/{C}/{X}/delete`, body `{"confirm":"<C>/<X>"}` — мисматч
→ 400; сироты в реестре нет → 404; уже DELETING → 409; повторная заявка
идемпотентна — put поверх); исполняет sweeper ближайшим проходом: DELETING
(фаза orphan-journal) → batch-delete → del записи реестра + del заявки;
заявка гасится и когда сирота к проходу исчезла/воскресла; заявка — осознанная
команда оператора: минует и hold, и автоправило «последнего полного»
(единственный путь удалить защищённый DR-источник).

**Журнал** `/pgworker/backups/orphan-journal`: пишет ТОЛЬКО глобальный лидер
(единственный писатель — гонок нет; plain put без read-modify-write);
«последняя фаза побеждает» — ключ перезаписывается каждым проходом, чистка
не нужна; панель ключ НЕ читает (состояние сирот наблюдаемо через реестр +
hold + delete-заявки).

## 3. Storage и квота

Ретенционный проход (расписание то же, per-instance) list-ит ВЕСЬ bucket
(пагинация; включая чужие/осиротевшие префиксы — занятость bucket, не только
свои) → `used_bytes` = сумма размеров объектов → ключ
`/pgworker/backups/storage` при изменении. Реакции автоматикой НЕТ
(emergency-чистки, запрета новых полных): WARN/CRIT → панельный алерт
`backup-storage-quota`, действует оператор (расширить квоту / ужать policy).

## 4. Бюджеты зависших операций

- **Полный**: активный (PLANNED/RUNNING/UPLOADING) с возрастом
  (`now − started_unix`) > `Job:FullTimeoutSec` (default 6 ч) →
  `POST /api/backup/full/cancel` best-effort (приёмник гасит дерево текущего
  child-процесса; промежуточный staging на диске не создаётся — чистить
  нечего; недостижимый приёмник — journal-пометка
  «cancel пропущен» в той же записи `job-timeout/<X>/<id>`) → `FAILED`
  `error="job-timeout: <age> с > FullTimeoutSec"` → переснятие по общему
  бэкоффу. Возрастной бюджет — ПЕРВЫЙ гвард супервизии активного: вердикт
  `FAILED` по возрасту — самостоятельный факт etcd (`started_unix` + часы
  воркера), docker/API-доступ не требуется; transient-пропуск источника
  (portalloc/engine/receiver) бюджет НЕ откладывает (операции с возрастом >
  6 ч нечем оправдаться); PLANNED без запуска — FAILED без cancel.
- **Verify**: операция running дольше `Job:VerifyTimeoutSec` (default 6 ч;
  возраст — `started_unix` из GET-снимка операции приёмника) →
  `POST /api/ops/cancel` best-effort, кандидат остаётся PENDING с
  `checked_unix = now` (попытка зачтена, лив-лок немедленных перезапусков
  исключён; вердикт FAILED по таймауту НЕ ставится — данные не виноваты).
- **Restore**: фаза RUNNING заявки старше `Job:RestoreTimeoutSec` (default
  24 ч) → снос первой ноды (restore-операция уходит с ней, volume — тем же
  путём) + `FAILED` `restore-job-timeout` с чисткой щита initialize;
  REJOINING не таймаутится (бюджеты Patroni-проб — свои). Бюджет наката WAL
  внутри restore/drill-операции — `Restore:RecoveryTimeoutSec` из команды.
- **Drill**: бюджет активного дрилла — `Drill:TimeoutSec` от `started_unix`
  ключа → FAILED `drill-timeout` (+ `POST /api/ops/cancel` best-effort).

`Backups:Enabled=false` → проходы, удаляющие объекты (ретенция, sweeper,
супервизор), no-op; зависшие DELETING видит панельный алерт.
