# PgWorker: аварийная эвакуация бакетов

Уровень 3. Функция «аварийная эвакуация»: при полной смерти шарда
аварийно перевести его бакеты на живые шарды (без логической репликации —
источник недоступен) и удержать вернувшийся шард в карантине. Полный
автомат — [D. BucketEvacuator](processes/d-bucket-evacuator.md);
состояния нод — [processes/enums.md](processes/enums.md).

## 1. Условия запуска

Guard'ы перед любым действием (journal-before-manipulations, P7):

- шард недоступен целиком ≥ `ShardDeadSec` (300 с, конфиг) — все ноды
  молчат, master-ключ протух; порог трекается в `/pgworker/work/<C>`
  (поле `unreachable`);
- ни один бакет шарда не в `SYNCING`/`FROZEN`/`ABORTING` (незавершённый
  переезд — блокируем, alert-журнал);
- живые шарды есть;
- снапшот P12 «до».

Кандидат эвакуации требует `dsn` и ≥1 бакета на шарде по routing
(эвакуация пустого/незарегистрированного шарда бессмысленна и блокировала
бы G6 карантином); шард с `TO_REMOVE`-маркером кандидатом МОЖЕТ быть —
эвакуация умирающего помеченного шарда освобождает бакеты, после чего G3
пропускает демонтаж (Д6).

## 2. Шаги E0–E4

```
E0 journal /pgworker/evacuations/<C>/<X> (план: bucket → целевой шард;
   цели — живые шарды, баланс round-robin; при живых=0 — ждать)
E1 на целевых шардах: CREATE SCHEMA IF NOT EXISTS bucket_<i> + GRANT'ы
   (пустые схемы — источник недоступен, копировать нечего: данные шарда
   остаются на его дисках и вернутся вместе с ним)
E2 по каждому бакету: txn (compare routing=<старый шард>) put routing=
   <новый> — владение переведено; статус-ключей нет → бакет сразу ACTIVE
E3 ноды шарда: state=QUARANTINED; контейнеры НЕ удаляются (данные на
   месте!), но при возврате REST-доступности — остановить (docker kill —
   spilo-нода: жёсткая смерть — штатный канал; exited-факт немедленный),
   чтобы «призраки» не писали в осиротевшие схемы (P1-логика)
E4 journal state=DONE; снапшот P12 «после»
```

## 3. Возврат шарда

PgWorker видит journal `DONE` + живой REST → останавливает ноды, держит
`QUARANTINED`, в journal — `state=QUARANTINED, returned_unix`. Слияние и
восстановление — только ручной runbook; автоматизация слияния отвергнута:
воркер не знает семантику схем `bucket_%`, конфликт двух живых ветвей
записей неразрешим автоматически, а данные до момента смерти доступны на
дисках карантина и в бэкапах ([backups/README.md](../backups/README.md)). PgWorker
ничего не удаляет и не запускает сам.

RPO эвакуации = момент смерти шарда (фиксируется в journal). Эвакуация
«пустыми схемами» теряет записи, сделанные умершим шардом с момента
смерти — осознанное аварийное поведение (R4,
[08-operability.md](08-operability.md) §6).
