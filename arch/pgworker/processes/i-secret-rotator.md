# I. ClusterSecretRotator (ротация per-cluster секретов, R0–R4)

Уровень 4. Смена ВСЕХ per-cluster кредов кластера — app
(`app_user`/`app_password`), bucket_mover (`mover_password`) и bucket_admin
(`bucket_admin_user`/`bucket_admin_password`) — по заявке
`/pgworker/rotations/<C>`. Функция — [04-security.md](../04-security.md) §6;
ключи — [../00-etcd-contract.md](../00-etcd-contract.md) §4; доставка
секретов и статус агента — [04-security.md](../04-security.md) §3–§4,
[F](../../pgnode/processes/f-node-agent.md); перечисления — [enums.md](enums.md).

Исполнитель — держатель клэйма `<C>`; цикл ReconcileLoop зовёт процесс в
Active-ветке после scale-прохода (короткая секундная операция — не ждёт
длинных переездов). Порядок фаз — **ETCD-FIRST** (решение пользователя):
etcd — источник истины, NEW-креды коммитятся в etcd В НАЧАЛЕ окна; PG
следует etcd финальным ALTER'ом в КОНЦЕ (принцип «etcd — источник, PG
следует» — как выравнивание ролей provisioning P1.5).

```
R0 заявка есть → journal op=rotate-app-password phase=started; клэйм-гвард
   (имя op сохранено — совместимость журналов, образец RotationRole.Phase
   [kafkaworker/processes/h-password-rotator.md](../../kafkaworker/processes/h-password-rotator.md))
R1 ensure per-cluster четвёрки (P1.5): {app_user, app_password},
   {mover_password}, {bucket_admin_user, bucket_admin_password},
   {rest_password} — OLD-значения (compare-база R2)
R2 NEW = сгенерировать ×4 (32 симв [A-Za-z0-9]) → ОДНА txn:
   [compare value==OLD для app_password, mover_password,
    bucket_admin_password, rest_password и КАЖДОГО dsn-ключа шардов]
   [put app_password=NEW_app; put mover_password=NEW_mover;
    put bucket_admin_password=NEW_admin; put rest_password=NEW_rest;
    перезапись dsn-ключей всех шардов (пароль bucket_admin заменён
    regex-ом по conninfo); del /pgworker/rotations/<C>; put work-ключа
    с rest_window_open=true — ФЛАГ ОКНА КЛАДЁТСЯ ТОЙ ЖЕ txn (отдельный
    put после txn мог потеряться при сбое/потере клэйма — заявки уже нет,
    флага нет, вечный дрейф NEW/OLD без следов)] — ОКНО ОТКРЫТО: etcd
    несёт NEW, роли PG — ещё OLD. Коммит, снятие заявки и флаг
    неразделимы; журнальная фаза rotate-etcd-committed пишется обычной
    записью ПОСЛЕ txn (сбой её записи не фатален — флаг уже в etcd);
    compare dsn закрывает гонку с внешней записью dsn (репарация P11).
    Compare проигран (внешняя запись etcdctl) → re-read, ретрай тиком со
    свежими OLD (генерация между тиками безопасна — NEW ещё не закоммичены).
   Takeover-продолжение: заявки уже нет — окно живёт в ПЕРЕНОСИМОМ флаге
   rest_window_open журнала работы (true — этой же txn-записью фазы
   rotate-etcd-committed, false — при done R4; флаг carry-forward всеми
   писателями журнала — надзор пишет supervise-записи каждый тик, и
   фазовый маркер last-write-wins затирался бы); пара NEW читается из etcd
R3 rolling применение НОД (rest_password, каналом агента БЕЗ пересоздания
   контейнеров — [04-security.md](../04-security.md) §3): NEW-пара — в
   перерендеренных bootstrap-ключах нод (spilo_configuration с NEW; put +
   команда применения каналом — [C](c-node-supervisor.md), только
   ready-нодам); агент применяет новую конфигурацию Patroni RELOAD'ом —
   SIGHUP процессу patroni ИЛИ REST POST /reload (эквивалентны, выбор за
   реализацией; факты эксперимента spilo-18:4.1-p2/patroni 4.1.0: reload
   перечитывает restapi-аутентификацию — OLD-пара 401, NEW-пара 200,
   POST /reload 202; postmaster PID/start_time неизменны — PG не
   останавливается).
   Рестарт Patroni-ПРОЦЕССА и рестарт контейнера для применения
   rest-ПАРОЛЯ ЗАПРЕЩЕНЫ: штатное завершение Patroni (TERM) гасит
   управляемый PG — рестарт процесса = остановка PG (постмастер
   демонизирован, PPID=1: механика — TERM-логика Patroni, не дерево
   процессов). Нюанс верификации: GET / REST-эндпоинта публичен (отвечает
   без аутентификации) — применённость пары проверяется ТОЛЬКО на
   мутирующих эндпоинтах (PATCH /config и др.): пробы живости GET'ом
   доказательством аутентификации НЕ являются. Права доставляемых файлов
   обеспечивает поставщик (tmpfs 0600 postgres): root-владелец —
   PermissionError Patroni на reload.
   TLS-материал REST при перегенерации: configure_spilo (child-процесс
   агента, user=postgres) получает env SSL_RESTAPI_CERTIFICATE_FILE/
   SSL_RESTAPI_PRIVATE_KEY_FILE = пути пер-инсталл рест-серт ноды
   /run/certs/* (спило-константы get_placeholders; серты материализованы
   bootstrap'ом из тех же env, что spilo-supervised.sh передаёт в launch).
   Без этих env-путей placeholders SSL_RESTAPI_*_FILE пусты (env сертов у
   агента нет — секреты не покидают память/tmpfs), шаблон restapi теряет
   certfile/keyfile (cafile остаётся) и первое же перечитывание конфига
   пересоздаёт REST-листенер В PLAIN HTTP — mTLS-канал агента (:8081 ↔
   :8008) умирает посреди окна ротации (факт t05probe2; POST /reload
   отвечает «202 reload scheduled» АСИНХРОННО — исполнение перечитывания
   в лупе Patroni, следующая команда канала может прийти ДО исполнения).
   POST /reload отправляется HttpClient.SendAsync по подготовленному
   запросу — заголовок Authorization (basic patroni:OLD|NEW, попытки
   покрывают состояния in-memory S1/S2) живёт в самом запросе;
   PostAsync(uri, content) заголовки подготовленного запроса НЕ несёт —
   reload уходил без авторизации (401 «no auth header received» на любой
   пароль; факт пробы t05probe3a). Зонд применённости пары — PATCH /config
   с телом {}: 400 = аутентификация пройдена, 401 = отвергнута.
   Порядок — реплики вперёд, лидер последним, ≤1 нода/тик (консервативный
   порядок: при сбое применения лидер остаётся на старой рабочей
   конфигурации; reload лёгкий — деградации обслуживания применением нет;
   restore/TO_REMOVE-шарды и усыновлённые ноды гейт пропускает).
   Прогресс по нодам — факт applied_revision статусного ключа ноды
   ([../00-etcd-contract.md](../00-etcd-contract.md) §4) против ревизии
   bootstrap-ключа — takeover-безопасен (обе ревизии в etcd); есть нода с
   отстающей ревизией → окно открыто, тик ЖДЁТ (фаза rotate-rest-rolling);
   все ноды применили → R3 завершён (канал агента режимно-симметричен:
   plain и swarm — одинаково)
   Дисциплина доставки R3 (повторы): команда применения — ОДИН пин ноде на
   ревизию bootstrap-ключа (delivered-факт per нода у доставщика —
   ротатора и шага конвергенции [C](c-node-supervisor.md)); повтор —
   ТОЛЬКО по транспорт-фейлу доставки (или по новой ревизии ключа — новый
   материал); per-тик re-пин при не-applied ЗАПРЕЩЁН («Delivered = команда
   принята, прогресс — проба тиками»). Применение неудавшегося материала
   агент ПОВТОРЯЕТ САМ: фон-задача применения после сбоя циклит ретрай с
   паузой анти-дребезг-коулдауна до успеха/смены материала/остановки
   процесса; коулдаун гейтится ОТ МАТЕРИАЛА (отпечаток YAML+серт+ключ), а
   не от ревизии — переписывание ключа тем же контентом (растущий
   mod_revision) коулдаун НЕ снимает и re-применение не триггерит
   (переписанный тем же контентом ключ догоняется фиксацией ревизии без
   рестартов); воркер re-пин после takeover безвреден — агент
   ok-пинок/материальный гейт/«материал уже применён» делают его no-op
   R3-ЛАЙВЛОК-гвард: нода, ВОШЕДШАЯ в initializing/старт ВО ВРЕМЯ окна
   (рестарт агента/ноды, start_failed-пересоздание, rebuild), читает
   app-креды из etcd (NEW) и пробует doorman против pg_authid (OLD до R4)
   — 28P01 без бюджета → ready недостижим → полный-схождением R4
   заблокирован навсегда. Разрешение: R4 запускается не только при полном
   схождении R3, но и при ОТСУТСТВИИ ПРОГРЕССА R3 N=3 тика подряд
   (счётчик тихих тиков — переносимая carry-фаза журнала; любой прогресс
   обнуляет) И все неприменившие ноды —
   initializing/not_initialized/unreachable (МЕНЬШИНСТВО, не отказывающиеся
   применять — их статусы не несут отказа): ALTER выполняется, окно
   ОСТАЁТСЯ открытым (флаг не гаснет, гварды окна действуют), R3-rolling
   продолжается до полного схождения → done. После ALTER пробы
   initializing-нод сходятся (etcd NEW == pg_authid NEW) — лайвлок
   невозможен
   R3-СЕРТ (ротация rest-СЕРТА ноды — смена per-install REST-CA, редкое
   событие, вне тикета четвёрки; оркестрацию ведёт воркер: перерендер
   bootstrap-ключей сертами нового CA → применение конвергенцией
   [C](c-node-supervisor.md) по applied_revision): reload SSL-материал НЕ
   применяет — свойство patroni 4.1.0 (факт эксперимента: restapi зависает
   на TLS-handshake, материал подхватывается только рестартом Patroni),
   механика материала: (i) все РЕПЛИКИ рестартуются ПО ОЧЕРЕДИ (rolling,
   по одной: рестарт Patroni-программы → PG реплики останавливается на
   секунды рестарта → Patroni стартует и усыновляет локальный PG по DCS;
   между шагами — ожидание возвращения реплики в кластер); (ii) затем
   МАСТЕР — ПЕРЕСОЗДАНИЕ контейнера (kill+remove+ensure; новый диск НЕ
   требуется — PGDATA сохраняется; НЕ рестарт: пересоздание гарантирует
   переезд лидерства failover'ом на уже обновлённую реплику; после
   failover старый лидер возвращается в кластер репликой уже с новым
   сертом). Порядок «реплики вперёд» обязателен: к моменту пересоздания
   мастера все реплики уже несут новый серт — failover идёт на
   обновлённую реплику. ГРАНИЦА ЗАПРЕТА: запрет рестарта
   Patroni-процесса/контейнера (R3-пароль выше) касается ТОЛЬКО применения
   rest-пароля; R3-серт (рестарт реплик, пересоздание мастера),
   restore-контур ([backups/03-restore.md](../../backups/03-restore.md) — stop/return
   Patroni ноды) и start_failed-пути [C](c-node-supervisor.md) — отдельные
   легитимные пути, запрет на них НЕ переносится
R4 (ПОСЛЕДНИЙ — закрытие окна; вход — полное схождение R3 ИЛИ
   R3-лайвлок-гвард выше) для каждого шарда с dsn (шард без dsn — домен
   AddShard: роли создадутся по свежим кредам): мастер (master-ключ →
   Patroni fallback) → admin-DSN → ALTER ROLE app / bucket_admin /
   bucket_mover PASSWORD '<NEW из etcd>' (реплики получают pg_authid
   физической репликацией; ALTER идемпотентен перезаписью). Любой сбой
   R3/R4 → transient: journal last_error, окно живёт (журнальная фаза),
   тик продолжает с записанной фазы. Все шарды ALTER-ены И R3 сошёлся
   полностью (лайвлок-ветка: ALTER раньше, ожидание схождения после) →
   снапшот P12 (точка изменения) + journal phase=done
   (rest_window_open=false) — ОКНО ЗАКРЫТО
```

## Открытое окно (R2-txn … R4-done)

etcd несёт NEW, роли PG — OLD до финального ALTER'а. В окне:

- SQL-подключения с NEW-кредами из etcd (приложения, перечитавшие etcd;
  mover-DSN свежего снапшота переездов; клиенты DSN-точки входа; пробы нод
  — doorman `SELECT 1` под app-ролью с `app_password` из etcd) получают
  SCRAM-отказ (28P01: pg_authid ещё OLD) — **ТРАНЗИЕНТ по определению
  окна, НЕ инцидент**: окно закрывается финальным ALTER'ом R4. За окном
  (journal done) несовпадение кред etcd↔PG — честный инцидент
  provisioning/ротации.
- Проба агента PgNode в окне НЕ мешает машине состояний и НЕ роняет
  готовность: отказ аутентификации app (28P01) — очередной цикл фазы
  (б) ([04-security.md](../04-security.md) §4: waiting-повтор), `ready`-нода
  остаётся `ready` (проба — наблюдение, не гейт статуса). Тем самым
  пост-apply состояние шарда («No standbys available», ноды initializing —
  следствие пробо-блокировки прежнего порядка) с ETCD-FIRST НЕ возникает:
  после R4 пробы сходятся, шард остаётся согласованным (готовые ноды
  готовы, инициализирующиеся доходят до ready).
- Rest-часть окна: ноды разных поколений несут разные пары (dual-auth у
  Patroni нет) → межнодовые REST-вызовы между поколениями получают 401 —
  HA-инициации Patroni (fetch_node_status/switchover) деградированы;
  запись/репликация/DCS-heartbeat/master-ключ НЕ затронуты (мимо REST).
  Гварды окна: ПОКА окно открыто (флаг `rest_window_open` журнала; маркер
  окна — ТОЛЬКО флаг: после открытия окна ротатор пишет фазы как есть,
  включая failure-фазы — на предикат окна они не влияют) воркер не
  инициирует через REST кластера ни switchover (RecreateMarked-soft,
  [C](c-node-supervisor.md)), ни PATCH `/config` (конвергенция DCS —
  транзиент-skip тика); подавленные мутации ретраются после done; ускорение
  failover мёртвого лидера — DCS-ключ etcd, работает.
- Рендер bootstrap-ключей в окне берёт пару из etcd (NEW с R2) — все
  EnsureNode-пути окна (rebuild, TO_RECREATE) не расширяют окно: рендер
  любым путём несёт NEW-пару.

Длительность окна — rolling + ALTER (2–3 ноды × reload Patroni без
остановки PG + идемпотентные ALTER'ы), записи не рвёт: приложения до R4 с
NEW из etcd получают плановый транзиент (перечитывание кредов — тихое окно,
предупреждение — в UI-модалке панели). Специфика ролей: **bucket_admin**
живёт внутри dsn-ключей — клиенты DSN-точки входа перечитывают dsn (тот же
паттерн перечитывания); **bucket_mover** — креды переездов: активный
переезд строит mover-DSN из свежего снапшота на тик, оборванная ротацией
фаза переезда возобновляется с journal-фазы с новыми кредами. Битая заявка
(не-JSON/без числового `requested_unix`) — мусор: процесс её удаляет с
journal-записью (панель до того получает 409 «уже запрошена»). Заявка
кластера в NOT_INITIALIZED/TO_REMOVE панелью не ставится (guard 409,
[adminpanel/02-etcd-contract.md](../../adminpanel/02-etcd-contract.md) §9.8);
Deprovisioning D2 удаляет ключи точечно.
