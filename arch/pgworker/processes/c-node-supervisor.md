# C. NodeSupervisor (надзор)

Уровень 4. Постоянный надзор нод Active-кластера: пересоздание снесённых
контейнеров, rebuild мёртвых нод, ускорение failover, конвергенция
DCS-конфига, HA-факты, сверка мастер-ключа, усыновлённые ноды, доставка
секретов. Функция — [02-cluster-lifecycle.md](../02-cluster-lifecycle.md)
§4; модель — [01-placement.md](../01-placement.md); секреты и статусная
машина агента — [04-security.md](../04-security.md) §3–§4,
[F](../../pgnode/processes/f-node-agent.md); принципы —
[synchronization/README.md](../../synchronization/README.md).

## 1. Сверка декларации с фактом

- Каждой плановой ноде — контейнер/сервис (по имени); снесённый руками
  пересоздаётся (декларативное самовосстановление),
  `state=PROVISIONING→RUNNING`; как и rebuild ниже — с тюнингом от
  АКТУАЛЬНЫХ `request_*` на момент пересоздания
  (PgtuneInputsFactory.Create: пересчёт на каждый EnsureNode-путь).
- Patroni-REST каждой ноды по HTTPS (`GET /cluster`, timeout 3 с;
  верификация цепочки к kfw-install-ca без hostname-проверки —
  [pg-clusters/13-network-security.md](../../pg-clusters/13-network-security.md) §4; адрес —
  `host:patroni-port` portalloc).

## 2. Rebuild мёртвой ноды

Нода недоступна дольше `NodeDeadSec` (90 с, конфиг) и **не лидер** и
кворум шарда жив (мертва максимум одна нода: живых ≥ max(1, nodes−1) —
обобщение «≥2» фазы исполнения для 2-нодовых шардов) и есть
**положительное свидетельство смерти процесса** — docker-инспекция
(`SupportsRunningInspection`): объект отсутствует ИЛИ не running
(симметрично ускорению failover ниже: недоступность REST при работающем
контейнере — деградация наблюдаемости — нагрузка хоста, транспорт, долгий
bootstrap пересозданной ноды; снос здорового контейнера недопустим — нода
остаётся `UNREACHABLE`, трек продолжается, rebuild исполняется, когда
контейнер действительно мёртв; драйверы без честной инспекции — Swarm-
заглушка InspectNodesAsync — rebuild по недоступности проб, инспекции у них
нет) → **rebuild**: удалить контейнер + volume, создать заново (Patroni
сделает pg_basebackup с лидера — эталон `rebuild-node.sh`),
`state=REBUILDING→RUNNING`; параметры PG пересозданной ноды — тюнинг от
актуальных `request_*` на момент пересоздания. Лидер недоступен →
ускорение failover (ниже) + ожидание: выборы делает Patroni; лидер-призрак
станет репликой и обработается общим путём.

## 3. Бюджет смены лидера (критическое требование ≤5 с)

Канал graceful (SIGTERM/stop) — Patroni-демоут + промоушен синхронной
реплики ≈ `loop_wait`-циклы, ≤3–5 с; канал жёсткой смерти — истечение
lease лидер-ключа ограничено полом Patroni 4.x `ttl≥20`
([01-placement.md](../01-placement.md) §2), т.е. 20+ с — НЕ укладывается в
бюджет, поэтому воркер АКСЕЛЕРИРУЕТ: при положительном свидетельстве
смерти лидера — docker-объект ОТсутствует (существовавший путь
EnsureDeclared) ИЛИ контейнер лидера есть, но **не running** (inspect-
ветка — только для драйверов с честной running-инспекцией, capability
`SupportsRunningInspection`: Plain — да; Swarm-драйвер InspectNodesAsync —
заглушка (пустой результат), для него ветка НЕ применяется: «отсутствует в
инспекте» не свидетельство смерти, промоушен живёт на lease/loop_wait
Patroni; проба REST при этом молчит — транспортный флап исключён:
не-running и есть свидетельство смерти процесса) — удалить
`/service/<scope>/leader` (lease всё равно протух бы через ttl) и
выставить `/service/<scope>/failover` с кандидатом (sync-standby, кандидат
— по `GET /cluster`), после чего промоушен происходит в пределах
`loop_wait`. Итоговый бюджет: тик надзора + проба + loop_wait (e2e-профиль:
≤5 с).

Ускорение идемпотентно, но `docker restart`/кратковременный флап лидера
может оставить маркер у уже вернувшейся ноды: Patroni тогда зацикливается
на неисполнимом switchover (обе ноды «following a different leader»,
`/primary` не резолвится — факт rtls). Надзор САНИТИРУЕТ: failover-маркер,
`leader` которого в текущем тике отвечает пробой (жив), снимается — выборы
идут штатно. Заявки про мёртвого лидера не трогаются. Нода, ускоренная в
текущем тике (leader-ключ уже снят), в том же тике rebuild не проходит:
снос volume лидера запрещён — rebuild исполнится следующим тиком по
обычному свидетельству смерти.

## 4. Конвергенция DCS-конфига (pg-параметры)

Раз в тик надзора по одному узлу шарда — `GET /config`; расхождение с
каноном ([01-placement.md](../01-placement.md) §2:
ttl/loop_wait/retry_timeout/synchronous_mode + `synchronous_mode_strict` с
per-cluster ожиданием из config кластера (не константа) +
`postgresql.parameters` = merge(PGTune ∪ канон) от актуальных заявок
`request_{cpu,mem}` и опций `PgWorker:Pgtune`, пересчёт на каждый тик
конвергенции, БЕЗ фиксации в etcd) → ОДИН `PATCH /config` (несёт
`Authorization: Basic` per-cluster — `rest_password`; GET-запросы заголовок
не несут): обновляет расходящиеся значения, добавляет отсутствующие и
удаляет лишние (null-патч — параметр исчез из PGTune-вывода при смене
заявок или добавлен в `ExcludeParams`; «старое не живёт параллельно
канону», включая вручную записанные оператором ключи — канал
переопределения один: опции `PgWorker:Pgtune` + `ExcludeParams`); порядок
ключей патча детерминированный: тайминги → strict → параметры. Динамические
параметры Patroni применяет сам (reload в пределах loop_wait);
postmaster-параметры (`max_connections`, `shared_buffers`, …) Patroni
помечает `pending_restart` (`GET /patroni`) — применяются при ближайшем
рестарте ноды (rebuild/эвакуация/оператор; воркер НИКОГДА не инициирует
рестарт PG — `POST /restart`/`POST /switchover` в контексте конвергенции не
используются; `pending_restart=true` — штатное состояние, не алерт). Заявка
`request_{cpu,mem}` отсутствует или неполна (любое из полей ресурсов null) —
pg-часть патча пропускается с warning-логом воркера (в конвергенции
мутация опциональна: пропуск = конфиг остаётся прежним, безопасно;
выдумывать размер ноды по остаточному ресурсу нельзя), тайминги
конвергируются как раньше. Нода, начавшая работу на чужом/дефолтном/
мусорном конфиге, приводится к канону без пересоздания; в т.ч.
свежеподнятая нода — bootstrap-параметры в живой конфиг не попадают
([01-placement.md](../01-placement.md) §2, Spilo 4.1-p2), первый тик
конвергенции приводит её к канону; патч недоступен (шард мёртв) — лечат
общие контуры (rebuild/эвакуация).

## 5. Эвакуация и HA-факты

- Весь шард недоступен (все ноды молчат, master-ключ протух) дольше
  `ShardDeadSec` (300 с, конфиг) → эвакуация
  ([D](d-bucket-evacuator.md)). Пороговое время трекается в
  `/pgworker/work/<C>` (поле `unreachable`).
- **HA-факты в work-ключе** (`last_failover`/`last_rebuild`,
  [../00-etcd-contract.md](../00-etcd-contract.md) §4): надзор фиксирует
  последний факт каждого вида. Failover: недоступность лидера (трек
  `unreachable`) с применённым ускорением
  (`AccelerateDeadLeaderFailoverAsync` — docker-объект отсутствует/не
  running) → `cause=accelerated`; без применения ускорения — нет
  `SupportsRunningInspection`, живых по пробам, либо живой кандидат не
  найден (промоушен ждёт Patroni) → `cause=elections`. Закрытие — тик, где
  leader-ключ scope указывает на ДРУГУЮ ноду (`resolved_unix` = тик,
  `duration_sec` = resolved − detected); транзиентный флап (нода ожила,
  лидерство сохранила) — открытая запись удаляется без фиксации; graceful
  switchover живого лидера (soft-path recreate) — не событие. Rebuild:
  rebuild-ветка надзора → `cause=auto-dead`; исполнение маркера
  `TO_RECREATE` → `cause=operator-recreate`; закрытие — первый тик, где
  пересозданная нода жива пробой (переход state → RUNNING). Границы:
  усыновлённые (`object`) ноды фактов не порождают; QUARANTINED/REMOVING —
  вне проб; шард без dsn и шард с TO_REMOVE — фактов нет
  (самовосстановление и ускорение для TO_REMOVE работают как раньше —
  гвард только на записи фактов). Открытое событие живёт в ключе (переживает
  takeover); запись — финальный put тика надзора, сбой записи — warning
  (наблюдаемость ≠ данные). Панель отображает факты только шардов живой
  декларации (ключ кластерный; чистки D2 достаточно).

## 6. MasterKeyReconciler (P11)

У каждого шарда сверить master-ключ с фактом (`GET /primary` по нодам):
расхождение или ключа нет при живом primary → lease-put коррекция
`host:<doorman-port>` (пишет только при рассинхроне — не второй регулярный
писатель). **Усыновлённые шарды** (записи portalloc с `object`) сверки НЕ
проходят: их master-ключ пишет внешний HA-контур (Patroni-callback/эмулятор)
в своём формате `node:port` — коррекция порождала бы войну писателей;
резолв мастера ([F](f-move.md) §1) понимает оба формата.

## 7. Усыновлённые ноды

Запись portalloc с `object`: живость — Patroni-REST, а при `patroni=0` —
SQL-проба мастера (`SELECT 1` по admin-DSN — положительное свидетельство
живости PG); сверка декларации к ним НЕ применяется вовсе — их контейнер
вне docker-домена `pgw-<C>-` (ListNodeObjectsAsync отдаёт только
канонические имена): живой object-контейнер — «нода на месте» (skip),
мёртвый не rebuild'ится. Матчинг по имени `pgw-<C>-<X>-<n>` остаётся только
для канонических нод. Self-healing (пересоздание/rebuild/TO_RECREATE) для
усыновлённых нод отключён: rebuild поднял бы канонический `pgw-`-контейнер
рядом с внешним orchestration-кругом (например, вторым «Patroni» на тот же
scope, R9) — мёртвая усыновлённая нода получает `UNREACHABLE` + journal
(реальная проблема, разбор оператором). Evacuation-кандидат — по общим
правилам (allDead + master-ключ протух).

## 8. Миграция app_params

Ленивый ensure: у нод шардов с dsn (любого state — мастером может стать
любая нода) без `nodes/<n>/app_params` (кластеры, созданные до ключа) —
put-if-absent значения по умолчанию (как P2.5'). Модель снапшота уже несёт
наличие ключа — прогон без etcd-запросов, put только для отсутствующих;
после первого обеспечения последующие тики — no-op.

## 9. Хендшейк и конвергенция доставки секретов

Надзор читает статусный ключ ноды
`/pgworker/nodes/<C>/<X>/<N>/status`
([../00-etcd-contract.md](../00-etcd-contract.md) §4) и реагирует по
состоянию:

- ключа нет (агент стартует/рестартует, lease истёк) — ничего не делать
  (transient: следующий тик увидит `not_initialized`);
- `not_initialized` — доставка (put bootstrap-ключа при устаревании +
  команда канала с per-install паролями PG);
- `initializing` — ждать (агент — конечный автомат: bounded-попытки
  приводят к `ready`/`start_failed`);
- `ready` с `applied_revision` != `mod_revision` bootstrap-ключа — команда
  применения (ротация: перечитывание etcd агентом, точечные замены).

Дисциплина повтора команды применения (канал, общая с R3 процесса I):
пин — ОДИН на ревизию bootstrap-ключа (delivered-факт per нода у
доставщика); повтор пина — ТОЛЬКО по транспорт-фейлу доставки либо по
НОВОЙ ревизии ключа (новый материал). Применение неудавшегося материала —
обязанность АГЕНТА: самоповтор применения с анти-дребезг-коулдауном,
гейтованным МАТЕРИАЛОМ, а не перетикивание воркером — ok-ответ команды
(«принята») ≠ прогресс: прогресс воркер читает тиками по статусному ключу;
долбёжка apply-пинами каждый тик при не-applied ЗАПРЕЩЕНА.

`start_failed` — пересоздание ноды С НОВЫМ ДИСКОМ c ДВУМЯ обязательными
правилами (снос лидера до failover уничтожал авторитетную копию, а чистка
scope-ключей живого кластера делала пару невосстановимой — «waiting for
leader to bootstrap» навсегда):

1. **failover-first для лидера**: `start_failed` на ТЕКУЩЕМ лидере
   (DCS leader-ключ scope) сносом НЕ обслуживается — сначала
   ГАРАНТИРОВАННЫЙ failover: start_failed-нода уже не поднимется
   (Patroni не стартует), лидерство уходит живой реплике по ttl; воркер
   ждёт ФАКТА перехода (leader-ключ сменил владельца в DCS) и только
   затем RemoveNode+новый диск (уже как бывший лидер); witness-гвард
   (живой свидетель по DCS-членству) — необходимое, но НЕ достаточное
   условие: дополняется фактом свершившегося failover. Failover невозможен
   (нет живых реплик/свидетеля) — реакции СНОСА НЕТ: тик ждёт (журнальная
   фаза `start-failed-waiting-quorum`), сигнализация оператору. Одноузловой
   шард: лидер = единственная копия — снос только через restore-контур
   (восстановление данными из бэкапа,
   [backups/03-restore.md](../../backups/03-restore.md)), не «в пустоту».
2. **scope живого кластера неприкосновенен**: RemoveNode старт-реакции НЕ
   чистит Patroni-scope-ключи (`/service/<scope>/initialize`, `leader` и
   смежные) — чистка scope допустима ТОЛЬКО при демонтаже
   кластера/шарда целиком (D2/S3); после сноса ноды пара восстановима
   живыми членами (новая нода бутстрапается по существующему scope —
   репликой к живому кластеру, не новым кластером).

Данные пересозданной ноды не сохраняются — шард восстанавливает их
репликацией/бэкапом; `object`-нод и restore/TO_REMOVE-шардов реакция не
касается (R9/владельцы процессов). Этим же шагом закрывается рестарт
контейнера: tmpfs-секреты утрачены, lease-ключ исчез, новый процесс
публикует `not_initialized` — тик доставляет, агент поднимает
spilo/pg_doorman. Недоступность канала — transient тика (journal-факт с
адресом), статус ноды не портится. Пересоздание контейнеров по СЕКРЕТАМ не
выполняется — замены применяются доставкой; единственная реакция
пересозданием — `start_failed`. RecreateMarked (operator `TO_RECREATE`) —
отдельный механизм, без изменений (в открытом окне ротации — гварды
[I](i-secret-rotator.md)).

## 10. Границы надзора

- Шард без `dsn` — домен AddShardProcess (пробы/самовосстановление/
  UNREACHABLE-переходы не трогаем — state нод входит в A1-гвард add).
- Шард с маркером `TO_REMOVE` — самовосстановление отключено (домен
  RemoveShardProcess — не пересоздавать демонтируемое), пробы остаются
  (шард жив и обслуживает бакеты до демонтажа).
- Ноды в `QUARANTINED`/`REMOVING` надзор не пробирует и их state не
  трогает — карантин держится эвакуатором до разбора runbook'ом
  (E3-инвариант; UNREACHABLE-перезапись ломала бы G6/Д6), демонтаж идёт
  своим процессом.
- Кандидат эвакуации требует `dsn` и ≥1 бакета на шарде по routing
  (эвакуация пустого/незарегистрированного шарда бессмысленна и
  блокировала бы G6 карантином); шард с `TO_REMOVE`-маркером кандидатом
  МОЖЕТ быть — эвакуация умирающего помеченного шарда освобождает бакеты,
  после чего G3 пропускает демонтаж (Д6).

Состояния и переходы — [enums.md](enums.md).
