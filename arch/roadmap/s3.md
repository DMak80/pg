# Roadmap: S3-хранилище бэкапов (кластеры MinIO, репликация, наблюдение)

Кластеры S3-хранилища бэкапов как управляемый объект системы: пул
S3-серверов с гео-распределением (привязка к docker/swarm-хостам) и
mesh-репликацией между ними. Целевая платформа пула — **ownS3**
(собственное хранилище, arch/22; межсерверная репликация — требования
[`docs/owns3-replication-requirements.md`](../../docs/owns3-replication-requirements.md),
задача `t35-owns3-replication` трека [owns3.md](owns3.md)); MinIO —
переходный вариант тех же сценариев (факты его механик — в изысканиях).
Для клиентов подсистемы
бэкапов (воркер, джобы, restore/verify/drill) контур остаётся обычным
S3; синхронизация между серверами — часть обслуживания кластера, не
клиентов. Управление (создание/изменение состава/диски) и наблюдение
(синхронность, связность) — декларативно в etcd, полностью отражено в
панели UI.

Исходные изыскания платформы — свойства MinIO bucket replication,
проверенные факты (fan-out, backfill, окно догона, поведение PUT на
изолированной ноде, split-brain, ограничения resync) и выводы для
архитектуры — [`docs/s3-replication.md`](../../docs/s3-replication.md);
задачи трека опираются на него. Паттерны оркестрации —
[../17-synchronization-principles.md](../17-synchronization-principles.md);
контекст потребителя хранилища — [../19-backups.md](../19-backups.md).

Порядок: канон (etcd-контракт, оркестратор, секреты) → provisioning
кластеров + replication-mesh → синхронность/связность → панель.

## Задачи

- **`t31-s3-clusters-canon`** — канон кластеров S3 (arch-first, новый
  документ arch/): etcd-контракт деклараций и статусов — кластер
  (кол-во нод, привязка нод к docker/swarm-хостам — гео-распределение
  по образцу multi-host arch/14, размер диска/квота ноды), состав и
  здоровье нод, состояние связности и синхронности; выбор
  оркестратора (идемпотентный воркер по образцу существующих либо
  расширение существующего — фиксируется спекой); секреты нод — env
  (направление arch/14 §4/arch/19 §7, per-install профили вне etcd);
  границы: клиентская грань пула записи/чтения для подсистемы бэкапов
  остаётся обычным S3, перебор серверов с per-попыточным таймаутом —
  по фактам docs/s3-replication.md.
- **`t32-s3-cluster-provisioning`** ← `t31-s3-clusters-canon` —
  создание и управление контуром по декларации: подъём MinIO-нод
  контейнерами (placement по хостам, volumes/квоты диска, образ из
  локального registry), изменение состава (добавление ноды — с
  bucket versioning, подключением в replication-mesh и backfill
  `existing-objects`; вывод ноды), снос; настройка/поддержание mesh
  (правила bucket replication с уникальными приоритетами, флаги
  `delete,delete-marker,existing-objects`), операции выравнивания
  после долгих отказов (платформенный resync недоступен на
  автосозданных правилах — путь выравнивания фиксируется спекой:
  пере-добавление правил/`mc mirror`); идемпотентность по факту,
  takeover, journal-before-manipulations — arch/17; чистка физических
  версий поверх versioning (согласование с ретенцией arch/19 §4/§5).
- **`t33-s3-sync-connectivity`** ← `t32-s3-cluster-provisioning` —
  контроль синхронности и связности кластера: зонд синхронности по
  команде (API оркестратора + панель) и периодический — сверка
  содержимого бакетов между нодами (list/хвосты; штатные метрики
  репликации лаг данных не отражают — docs/s3-replication.md);
  состояние связности нод между собой (линки репликации, PUT-пробы —
  health-проба недостаточна: изолированная от всех целей нода отвечает
  health, но не принимает запись); статусы и лаг в etcd, алерты панели
  (расхождение, отставание, нода вне контура).
- **`t34-s3-panel`** ← `t31-s3-clusters-canon`, `t33-s3-sync-connectivity`
  — панель UI: управление кластерами S3 (создание/изменение состава
  нод, гео-placement, диски — мутации через API оркестратора, панель —
  немой читатель etcd по канону adminpanel/02), наблюдение (состав,
  связность, синхронность/лаг, занятость нод), интеграция с гранью
  «Хранилище бэкапов» (adminpanel/02 §2.5 — read-only бакет остаётся).
- **`t36-s3-pool-integration`** ← `t31-s3-clusters-canon` —
  клиентская интеграция пула S3-серверов (ownS3) в подсистему бэкапов:
  **запись в любой доступный** — перебор серверов с per-попыточным
  таймаутом PUT (health-проба недоступность не доказывает —
  docs/s3-replication.md; быстрый отказ/успех, не молчание —
  R3 требований ownS3), **чтение/восстановление по приоритетам** —
  перебор «где данные есть» (страховка на лаг доставки); приоритеты
  per-cluster — в etcd (приём через API воркера, паттерн policy
  arch/19 §4), отдельная per-install пара для etcd-слепков — env
  воркера (arch/14 §6: источник правды о DR слепков не может жить в
  восстанавливаемом etcd), креды серверов — env-профили (arch/19 §7);
  arch-first правки: arch/19 §5 («один bucket», layout), §7 (наборы
  кредов), arch/14 §6/§8 (экспорт слепков, владелец кредов),
  adminpanel/02 (storage/приоритеты). Синхронизация между серверами —
  вне задачи (механика ownS3, `t35-owns3-replication`).
