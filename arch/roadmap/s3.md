# Roadmap: S3-хранилище бэкапов (кластеры ownS3, репликация, наблюдение)

Кластеры S3-хранилища бэкапов как управляемый объект системы: пул
S3-серверов с гео-распределением (привязка к docker/swarm-хостам) и
mesh-репликацией между ними. Платформа пула — **ownS3** (собственное
хранилище, arch/22; межсерверная mesh-репликация — канон
[`arch/owns3/07-replication.md`](../owns3/07-replication.md)).
Для клиентов подсистемы
бэкапов (воркер, джобы, restore/verify/drill) контур остаётся обычным
S3; синхронизация между серверами — часть обслуживания кластера, не
клиентов. Управление (создание/изменение состава/диски) и наблюдение
(синхронность, связность) — декларативно в etcd, полностью отражено в
панели UI.

Изыскания платформ репликации (MinIO bucket replication, Garage: штрафы
записи при отказах, split-brain, недостаточность штатных метрик) —
справочник [`docs/s3-replication.md`](../../docs/s3-replication.md);
требования к mesh ownS3 —
[`docs/owns3-replication-requirements.md`](../../docs/owns3-replication-requirements.md).
Паттерны оркестрации —
[../17-synchronization-principles.md](../17-synchronization-principles.md);
контекст потребителя хранилища — [../19-backups.md](../19-backups.md).

Канон домена — [../23-s3-clusters.md](../23-s3-clusters.md) (контракт etcd
`/s3/` + `/s3worker/`: декларации кластеров, статусы, дискавери) и
[../24-s3worker.md](../24-s3worker.md) (оркестратор S3Worker:
provisioning/надзор/изменение состава/зонд синхронности); задачи трека
исполняются по канону.

Порядок: provisioning кластеров → синхронность/связность → панель;
replication-mesh — механика ownS3
(канон [../owns3/07-replication.md](../owns3/07-replication.md)).

## Задачи

- **`t33-s3-sync-connectivity`** ← `t37-owns3-replication-ping` —
  контроль синхронности и связности кластера:
  (форматы ключей — [../23-s3-clusters.md](../23-s3-clusters.md) §3;
  процесс F канона [../24-s3worker.md](../24-s3worker.md) §5) зонд
  синхронности по команде (API оркестратора + панель) и периодический —
  сверка содержимого бакетов между нодами (list/хвосты; штатные метрики
  репликации лаг данных не отражают — docs/s3-replication.md);
  состояние связности нод между собой — активные репликационные
  ping-пробы (грань — `t37-owns3-replication-ping` трека owns3):
  зонд опрашивает `POST /admin/replication/probe` каждой ноды →
  симметричная матрица линков в обе стороны (PUT-пробы связность ownS3
  не детектируют: путь записи без синхронных взаимодействий с
  соседями — PUT всегда 0 с,
  [../owns3/07-replication.md](../owns3/07-replication.md) §1);
  ping-ок = «канал жив» — отдельно от доставки (лаг/очередь статуса) и
  сверки данных (sync-половина), в `connectivity` ложится только линк;
  статусы и лаг в etcd, алерты панели (расхождение, отставание, нода
  вне контура). Arch-first правки: arch/23 §3 (механизм пробы
  связности — ping-матрица вместо PUT-проб), arch/24 §5F (зонд
  пользуется гранью).
- **`t34-s3-panel`** ← `t33-s3-sync-connectivity`
  — панель UI: управление кластерами S3 (создание/изменение состава
  нод, гео-placement, диски — мутации через API оркестратора, панель —
  немой читатель etcd по канону adminpanel/02; проекция домена —
  [../23-s3-clusters.md](../23-s3-clusters.md) §8–§9 (глава домена S3 в
  adminpanel/02 — по образцу §10 kafka / §11 valkey)),
  наблюдение (состав,
  связность, синхронность/лаг, занятость нод), интеграция с гранью
  «Хранилище бэкапов» (adminpanel/02 §2.5 — read-only бакет остаётся).
- **`t36-s3-pool-integration`** —
  клиентская интеграция пула S3-серверов (ownS3) в подсистему бэкапов:
  (клиентская грань пула — канон
  [../23-s3-clusters.md](../23-s3-clusters.md) §7;)
  **запись в любой доступный** — перебор серверов с per-попыточным
  таймаутом PUT (health-проба недоступность не доказывает —
  docs/s3-replication.md; быстрый отказ/успех, не молчание —
  R3 требований ownS3), **чтение/восстановление по приоритетам** —
  перебор «где данные есть» (страховка на лаг доставки); приоритеты
  per-cluster — в etcd (приём через API воркера, паттерн policy
  arch/19 §4), отдельная per-install пара для etcd-слепков — env
  воркера (arch/14 §6: источник правды о DR слепков не может жить в
  восстанавливаемом etcd), креды серверов — env-профили (arch/19 §7);
  arch-first правки: arch/19 §5 («один bucket», layout), §7 (наборы
  кредов), arch/14 §6/§8 (экспорт слепков, владелец кредов),
  adminpanel/02 (storage/приоритеты). Синхронизация между серверами —
  вне задачи (механика ownS3,
  канон [`arch/owns3/07-replication.md`](../owns3/07-replication.md)).
