# Roadmap: S3-хранилище бэкапов (кластеры ownS3, репликация, наблюдение)

Кластеры S3-хранилища бэкапов как управляемый объект системы: пул
S3-серверов с гео-распределением (привязка к docker/swarm-хостам) и
mesh-репликацией между ними. Платформа пула — **ownS3** (собственное
хранилище, ../OwnS3/arch/01-owns3.md; межсерверная mesh-репликация — канон
[`../OwnS3/arch/owns3/07-replication.md`](../OwnS3/arch/owns3/07-replication.md)).
Для клиентов подсистемы
бэкапов (воркер, джобы, restore/verify/drill) контур остаётся обычным
S3; синхронизация между серверами — часть обслуживания кластера, не
клиентов. Управление (создание/изменение состава/диски) и наблюдение
(синхронность, связность) — декларативно в etcd, полностью отражено в
панели UI.

Изыскания платформ репликации (MinIO bucket replication, Garage: штрафы
записи при отказах, split-brain, недостаточность штатных метрик) —
справочник [`../OwnS3/docs/s3-replication.md`](../../../OwnS3/docs/s3-replication.md);
требования к mesh ownS3 —
[`../OwnS3/docs/owns3-replication-requirements.md`](../../../OwnS3/docs/owns3-replication-requirements.md).
Паттерны оркестрации —
[../17-synchronization-principles.md](../17-synchronization-principles.md);
контекст потребителя хранилища — [../19-backups.md](../19-backups.md).

Канон домена — [../23-s3-clusters.md](../23-s3-clusters.md) (контракт etcd
`/s3/` + `/s3worker/`: декларации кластеров, статусы, дискавери) и
[../24-s3worker.md](../24-s3worker.md) (оркестратор S3Worker:
provisioning/надзор/изменение состава/зонд синхронности); задачи трека
исполняются по канону.

Порядок: provisioning кластеров → синхронность/связность → панель;
replication-mesh — механика ownS3
(канон [../OwnS3/arch/owns3/07-replication.md](../OwnS3/arch/owns3/07-replication.md)).

## Задачи

- **`s3-external-targets`** —
  статические внешние S3-цели подсистемы бэкапов (облако/MinIO вне
  `/s3/clusters/`): точка расширения зафиксирована в arch/19 §7
  (env-цели `external` наряду с пулами policy; per-цельные Region/
  PathStyle/CA). Подключение — отдельной задачей.
- **`t31-s3-cluster-creds`** — per-cluster клиентские креды S3-кластеров
  в etcd (etcd — источник правды; отказ от per-install env-профилей):
  S3Worker генерирует root-пару и access keys (read-write бэкапам,
  read-only панели) при создании кластера и хранит их per-cluster в etcd —
  прецедент per-cluster секретов PgWorker (arch/14 §4); в config кластера
  (arch/23 §2) вводится признак «бэкапный кластер etcd»: единственный
  кластер с внешним ключом — разворачивается спец-ключом бэкапа etcd из
  etcd (его материализует etcdworker, `t32-etcdworker`), остальные
  кластеры — сгенерированными per-cluster кредами. Упраздняются per-install
  env-профили `S3W_NODE_SECRETS__*` и поле `config.secret_profile` с
  валидацией 422 (arch/23 §6, arch/24 §1.1/§4/P1–P3 пересматриваются);
  потребитель — пул бэкапов PgWorker: креды читаются из etcd вместо
  env-профилей `PGW_BACKUP_S3_PROFILES__*` (arch/19 §7). Панель: создание
  кластера без профиля, просмотр/ротация per-cluster кредов; стенд —
  демо-блок `S3W_NODE_SECRETS__BACKUPS-MAIN__*` уходит из `deploy/.env`.
- **`t32-panel-bucket-etcd`** (`← t31-s3-cluster-creds`) — перенос имени
  bucket'а панели бэкапов из env в etcd: per-install имя bucket, которым
  панель оперирует в разделе бэкапов, живёт в etcd — контракт
  [adminpanel/02 §12](../adminpanel/02-etcd-contract.md) — рядом с
  per-cluster кредами t31; env-параметр `AdminPanel__Backups__S3__Bucket`
  уходит из `deploy/.env` и шаблона `.env.example`.
