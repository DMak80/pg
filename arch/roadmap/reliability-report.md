# Живой отчёт надёжности: сводка по характеристикам, открытые задачи

Статус-документ трека [reliability.md](reliability.md).

**Правило актуальности** (симметрично мерж-гейту трека): закрытие задачи
тем же мерж-коммитом (1) снимает пункт из reliability.md и (2) правит
сводку по затронутой характеристике здесь. Отчёт не может
рассинхронизироваться с roadmap: правятся вместе. Появление новой задачи
трека — дописывается в «Осталось» тем же коммитом, что и пункт в
reliability.md.

## Целевые характеристики

| Метка | Характеристика | Суть |
|---|---|---|
| **D** | Отсутствие потери данных | RPO, восстановимость, защищённость копий |
| **R** | Быстрая самовосстанавливаемость | RTO, автоматика без оператора, устойчивость control-plane |
| **N** | Надёжность / наблюдаемость | Видимость деградаций, устойчивость мониторинга, безопасность контуров |

## Сводка по характеристикам (обновляется при закрытии задач)

### D — отсутствие потери данных

Ядро добротное: непрерывный WAL-стриминг с подтверждением по доставке
(собственный приёмник подтверждает слот только после фактического put
сегмента в S3) и двойной архивацией мастер+sync-standby в один префикс:
RPO = 0 подтверждённых транзакций при потере любой одной машины;
граница — незакоммиченный хвост после последнего sync-подтверждения
(вне RPO durable). Суточные полные + verify (манифест SHA256 + цепочка
WAL) + restore latest/PITR/DR + GFS-ретенция + самолечение
BROKEN-цепочки; failover мастера в sync-режиме Patroni с ускорением
воркером ≤5 с; восстанавливаемость через точку TLI-переключения
(смешанный сегмент failover, побайтово подтверждённый) доказана E2E
в обоих режимах цели — latest и target_time на одной WAL-цепочке.
Kafka вне подсистемы бэкапов по зафиксированному решению 2026-09-28:
данные невосстановимы из бэкапов, RPO держится RF×minISR (arch/16 §6,
arch/19 §1).
Режим «долговечность-vs-доступность» — per-cluster выбор:
`synchronous_mode_strict` в config кластера (отсутствие поля = true),
bootstrap несёт значение в bootstrap.dcs, живые кластеры приводит
конвергенция DCS; strict-кластер без sync-standby блокирует запись —
потеря «хвоста» при failover исключена явным выбором оператора.
DR-источник защищён от сиротского TTL: сирота с валидным полным
(`full/<id>/backup_manifest`) не удаляется автоматикой никогда —
автоправило sweeper'а; операторская защита — hold/unhold, осознанная
потеря — только заявка delete с confirm (API воркера + панель, алерт
различает 4+1 судьбу сироты); `OrphanTtlSec` чистит только незащищённых
(arch/19 §4).
Восстановимость доказывается автоматически — RestoreDrillProcess по расписанию
(`policy.drill.interval_days`) разворачивает бэкап во временный изолированный
контур и контролирует выход из recovery, снос контура — доводимая фазой
cleaning при любом исходе (arch/19 §3.6).
Контроль-плейн восстановим из S3: каждый etcd-слепок (плановый 6 ч +
внеочередные в точках изменений) выгружается в бэкап-бакет (префикс `etcd/`,
пары db+meta с sha256, ретенция 28 пар), восстановление — runbook-канон:
ручная sha256-сверка — барьер, `etcdutl snapshot restore` верифицирует.

Открытые разрывы: бэкапы не шифрованы и в единственном хранилище
(`t01`, `t03`).

### R — быстрая самовосстанавливаемость

Автоматика богатая: failover ≤5 с, rebuild реплики 90 с (кворум-гварды),
takeover воркера ≤15 с, идемпотентность «по факту» во всех процессах,
конвергенция DCS-конфига и лимитов, самолечение цепочек бэкапов,
эвакуация мёртвого шарда (осознанное RPO = момент смерти, слияние
отвергнуто — решение 2026-09-28, arch/14 R4); контроль-плейн переживает
потерю хоста с etcd — каждый слепок (плановый 6 ч + внеочередные)
выгружается в S3 с доводкой тиком `RetryIntervalSec` при транзиенте,
восстановление — runbook-канон.

Открытые разрывы: Swarm без ускоренного failover (`t11`); сценарии
отказа хоста/DC не отработаны (`t21`).

### N — надёжность / наблюдаемость

~50 правил алертов с Hint/Remedy (панель), HA/бэкапы/workers-панели,
healthz с секциями; метрики реальных Patroni-нод собираются Prometheus'ом
напрямую (file_sd из portalloc, единая сеть мониторинга), REST :8008 —
TLS per-install CA + basic-auth мутаций (пробы/скрейп по https). Слабое
место — «молчание»: без внешней нотификации и истории деградация невидима,
если никто не смотрит в панель.

Открытые разрывы: нотификации и истории нет (`t13`); expiry сертификатов
не мониторится (`t16`).

| `t32-etcdworker` | выделенный etcdworker: состав etcd-узлов + бэкапы etcd в S3 (перенос `Snapshots:Export` из PgWorker); единственный секрет вне etcd — ключ бэкапа etcd (env etcdworker → спец-ключ в etcd) | P2 | R, D |

Смежное вне трека: `t02-external-secret-manager` (pgworker-трек) —
секреты вне etcd; закрыт вместе с ним — строку сюда не переносим,
отмечаем в сводке характеристики N. Per-cluster креды S3-кластеров
и признак бэкапного кластера etcd уже живут в `/s3/clusters/`
(arch/23 §2/§6) — отдельной строки не требуется.
