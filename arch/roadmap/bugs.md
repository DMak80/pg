# Roadmap: баги (падения тестов / дефекты вне текущих задач)

Сюда складываем найденные баги: падения тестов и дефекты продукта, обнаруженные
вне области текущей задачи (мерж-гейты, серии, ревью) и не решаемые в ней по
канону AGENTS.md («фейл вне области — отдельная задача»).

## Правила ведения

- Нумерация NN — своя внутри трека, тег `tNN-slug`; порядок номеров = порядок
  исполнения по умолчанию (правила общие — [README.md](README.md)).
- **К каждому пункту — своя подпапка логов** `arch/roadmap/bugs/<tNN-slug>/`:
  журналы серий (относящиеся фрагменты или целиком, если небольшой),
  телеметрия/артефакты E2E (docker-логи/inspect, timing, `README-cleanup.txt`),
  тексты ассертов. Папка **вне git** (путь в `.gitignore`): логи в репозиторий
  не коммитятся, живут только локально. Суммарно по кейсу > 100 МБ — содержимое
  подпапки архивируется в tar.gz внутри неё же (указано в пункте).
- Состав сведений пункта: точное имя теста/фильтр; команда запуска с
  env-префиксами; серия/дата/коммит/ветка; пути к логам (подпапка); текст/суть
  ошибки; наблюдаемое vs ожидаемое; гипотезы, если есть.
- **Закрытие бага**: пункт удаляется из этого файла тем же коммитом, что
  закрывает баг, — **вместе со своей подпапкой логов**
  `arch/roadmap/bugs/<tNN-slug>/` (папка — локально, git её не хранит).
  Пункт удаляется только когда баг реально
  разобран и исправлен/закрыт, не раньше; история остаётся в git и
  `docs/superpowers/`.

## Задачи

- **t06-app-role-etcd-password-mismatch** — provisioning не выравнивает роль app в PG с etcd `app_password`: прямой логин `psql -h 127.0.0.1 -U app` с etcd-паролем к PG ЛЮБОЙ ноды свежего E2E-кластера даёт `28P01: password authentication failed for user "app"`, при этом `pg_authid.rolpassword` существует (SCRAM-строка, идентична на лидере и реплике — снято живьём из `/run/pgw/spilo-env` + `pg_authid`) и НЕ соответствует etcd-значению. Следствие: SCRAM-passthrough doorman на всех нодах кластера отклоняет app-креды (`pgnode`-проба doorman (arch/14 §4 фаза (б)) не проходит → машины реплик висят `initializing` (pg=ready, doorman=starting), rest-окно ротации не закрывается (R3 ждёт ready-нод); Handshake-тест E2E зелёный — SELECT идёт через doorman ЛИДЕРА по первому живому хосту dsn, роль/пароль на нём выровнены (флап по контурам). Вне t05: t05 не менял provisioning-ALTER/ensurer-механику; найдено при отладке E2E-ротации. Команда повтора: `DOTNET_CLI_UI_LANGUAGE=en dotnet test src/tests/PgWorker.E2eTests -c Release --no-build --nologo --filter "FullyQualifiedName~Rotate_TicketRotates"` (живой контур: `docker exec <нода> sh -c ". /run/pgw/spilo-env && PGPASSWORD=\"$PGPASSWORD_SUPERUSER\" psql -h 127.0.0.1 -U postgres -d postgres -tAc \"SELECT left(rolpassword,60) FROM pg_authid WHERE rolname='app'\""` против etcd `app_password`; etcd-контейнер `pgw-ee1-*` несёт etcdctl). Вет/комм: `feat-t05-node-secret-push`, `fe7e671c`+; логи: `arch/roadmap/bugs/t06-app-role-etcd-password-mismatch/` (диаг `[nsf-diag]`/etcd-снапшоты прогонов). Диагностика 2026-10-31 (вечер): гипотеза «P2.5-ALTER по другому значению» ОПРОВЕРГНУТА — добавлены SHA256-отпечатки (без секретов, коммит 3db89fb1): fingerprint ensure-put == fingerprint ALTER'а (совпадают, тик за тиком), т.е. provisioning исполняет ALTER ровно с etcd-значением, но итоговый pg_authid(app) ему не равен — расхождение возникает ПОСЛЕ ALTER-фазы (повторный писатель pg_authid не найден; кандидаты для проверки: порядок bootstrap-клонов до/после ALTER и рестарты spilo из apply). Юнит Tick_CreatesAppSecretKeysAndAlignsRole подтверждает связку ensure→SQL. Дополнительно: после R2-ALTER и apply-rest Patroni в шард остаётся расстроен («No standbys available», ноды initializing) — ротатор с гвардом «тихого окна» (3db89fb1) корректно ждёт (waiting-nodes-ready).
