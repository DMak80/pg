Стек: `OwnPostgres.ConfigureTlsAsync` (OwnPostgres.cs:143) ← `StartAsync` (:111) ← тест (WalReceiverIntegrationTests.cs:170); вызов — `ExecAsync` (:176/:179), `NpgsqlConnection.OpenAsync`. 388/389 зелёные, серия 1 м 33 с. Тот же тест был предметом t94 (гонка листинга — иная причина; здесь обрыв соединения при `ALTER SYSTEM`-настройке SSL). Команда повтора: `DOTNET_CLI_UI_LANGUAGE=en dotnet test src/tests/PgWorker.IntegrationTests -c Release --no-build --filter "FullyQualifiedName~WalReceiverIntegrationTests"`. Логи: `bugs/t100-walreceiver-tls-reset/pgw-run-PgWorker.IntegrationTests.log`. Ожидаемое: TLS-конфигурация проходит, тест доходит до ассертов; фактическое: обрыв соединения postgres'ом на этапе SSL-negotiation. Направление разбора: стабильность локального postgres при переконфигурации TLS (перезапуск ssl=on между ExecAsync), retry/переподключение в OwnPostgres; транзиент (однократный факт) — проверить воспроизводимость.
  Разбор/решение (ветка `fix-t100-t102-bugs`): корневая причина — гонка postgres-entrypoint: wait `pg_isready -U postgres` без `-h` проходит по UNIX-сокету ВРЕМЕННОГО сервера initdb (listen_addresses='') ещё до рестарта на настоящий; первый TCP-коннект фикстуры (ALTER SYSTEM в ConfigureTlsAsync) попадает в окно переключения → RST в SSL-negotiation. Дефект тестовой фикстуры, продукт не при чём. Фикс: wait `pg_isready -U postgres -h 127.0.0.1` (TCP-ready: wait завершён — настоящий postmaster слушает 5432). Верификация: WalReceiver-серия 3/3 зелёные (1м35с/1м33с/1м25с), полная серия 389/389 (1м44с).

Контекст из журнала: restore `target=latest` тем же backup_id — COMPLETED (restored_to_lsn 0/10000AB8); failover accelerated (9 с) и rebuild auto-dead (30 с) незадолго до запроса; цепь WAL: финалы до 00000002000000000000000f + .partial-куски 00000002…10, далее 00000004.history и 00000004…11 (TLI 3 пройдена транзитом). Команда повтора: `DOTNET_CLI_UI_LANGUAGE=en dotnet run --project src/tests/PgWorker.E2ePrepare -c Release` → `DOTNET_CLI_UI_LANGUAGE=en dotnet test src/tests/PgWorker.E2eTests -c Release --no-build --filter "FullyQualifiedName~Restore_TargetTimeThroughTliSwitch_StopsAtGoal"`. Логи: `bugs/t101-e2e-restore-targettime-tliswitch/pgw-run-PgWorker.E2eTests.log`; телеметрия контура `bugs/t101-e2e-restore-targettime-tliswitch/artifacts-658d63657b2e4b7f9addb7b13fadf648/` (docker-логи + host.log + snapshots). Ожидаемое: PITR-restore останавливается на цели времени через TLI-переход; фактическое: restore FAILED — расчётный switchWALLSN 0/10000B30 вне границ сегментов истории 00000004.history.   Разбор/решение (ветка `fix-t100-t102-bugs`): ПРОДУКТ КАНОНИЧЕН — отказ и есть поведение f-restore §2 «дыра → permanent-отказ, включая RPO-зазор tli-прыжка». Факты: после Fact 1 (latest-restore COMPLETED) надзор штатно rebuild'нул убитую на подготовке ноду (docker kill → auto-dead, 30 с) — восстановленная жизнь пережила два промоута (TLI 3 пустой + TLI 4); приёмник новой жизни стримит от wal_start нового полнго 00000004…11 — переходный сегмент 00000002…10 ниже wal_start недоставляем (осознанный зазор b-wal-control §2, остался кусками старой жизни). Заявка time:T_cut от старого полнго обязана permanent-отказать — честное RPO-окно; Fact 1 прошёл валидацию случайно (TLI4-объектов ещё не было в листе на момент его валидации). Дефект ТЕСТА: не распознан rebuild-исход как «проверяемое состояние не возникло». Фикс: перед заявкой — WalChain.Check(wal_start старого полнго, list): прерывистая цепь → штатный скип предусловия (тот же статус, что BoundarySwitchException: легитимный одиночный TLI-переход не возник). Верификация: E2eTliSwitchScenarios 2/2 зелёные (переход легитимен, PITR дошёл до цели).

  Разбор/решение (ветка `fix-t100-t102-bugs`): воркер РАБОТАЛ корректно — диагностика фактов показала `master slot wal_status=reserved` при мёртвом приёмнике: тик пересоздал lost-слот (drop+create immediate+reserved) и записал фазу. Дефект — НАБЛЮДЕНИЕ теста: work-ключ `{prefix}/work/<C>` один на все процессы, стационарная запись надзора `op=supervise` перезаписывает его каждый тик надзора — фаза slot-recreate живёт <1-2 c, поллинг 500 мс ловит её недетерминированно (лотерея; ранее проходил по везению). Эксперимент на postgres:18 подтвердил: lost-инвалидация устойчива (60 с + checkpoint без consumer'а — статус не проходит сам), т.е. оживший при мёртвом приёмнике слот = факт recreate тиком воркера. Фикс (двухчастный): (1) порядок Act 3 — воркер возвращается ДО приёмника мастера (слот гарантированно lost на первом тике; приёмник не успевает занять слот от хвоста S3); (2) Assert 1 — детерминированный: слот покинул lost при ещё мёртвом приёмнике (= recreate тика), fleeting-журнальная фаза поллингом не ассертится. Верификация: WalStream_SlotLostAutoRecreate_NoBroken PASSED (1м21с).
