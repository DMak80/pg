# Roadmap: подсистема бэкапов шардов

Отложенные задачи подсистемы бэкапов PG-шардов. **PgWorker — хозяин
бэкапов**: он сам создаёт, ретраит/пересоздаёт при неудаче, чистит лишнее,
обрабатывает пограничные случаи и сигнализирует в алертинг панели — что
сломалось и какие действия предприняты. Канон подсистемы —
[../19-backups.md](../19-backups.md); контекст сервиса —
[../14-pgworker.md](../14-pgworker.md).

Порядок: канон → полный бэкап → online-архивация WAL → проверки →
восстановление → ретенция → супервизор-цикл над всем → панель управления
хранилищем (S3).

## Задачи

- **`t23-backup-job-endpoint`** — эндпоинт хранилища для бэкап-джобов:
  mc в bridge-контейнере джобы периодически ломится на localhost-эндпоинт
  хранилища (`BackupJobSpec`) — полные бэкапы подвисают/падают и дотягиваются
  ретраями; зафиксировать и сверять адрес, достижимый из сети джобы
  (диагностика 2026-09-29 в E2E-прогоне t06 — код бэкапов не менялся,
  механизм существующий).
- **`t24-job-status-channel`** — перевод каналов «джоба/агент → воркер» с
  чтения docker-логов на etcd-журнал: фазы/result-JSON backup-джобов (full/
  verify/drill/restore — `BackupProcess`, `BackupVerifyProcess`,
  `RestoreProcess`, `RestoreDrillProcess`) и stdout-маркеры wal-агента
  (фазы/`tli_jump` — `WalStreamProcess`, `BackupAgentLogsAsync`) сейчас
  воркер получает через `GetContainerLogsAsync` — отклонение от
  [../25-component-communications.md](../25-component-communications.md)
  №21–22. Джобы и агент пишут фазы/результат/маркеры в etcd (по образцу
  WorkJournal `/pgworker/work/<C>` — KafkaWorker-джобы, arch/19 §2 маркеры
  остаются в stdout только диагностике); воркер читает статус из etcd,
  exit-код через inspect — как сейчас. tli-процедура (`gap`-поле wal-ключа)
  уже в etcd — переезд маркера `tli_jump` её не меняет.
- **`t25-wal-receiver-in-pgnode`** — WalReceiver исполняется ВНУТРИ PG-контейнера
  ноды, работает напрямую с etcd и несёт собственные метрики: отдельный
  long-running контейнер `pgw-backup-wal-<C>-<X>-<N>` (образ `pgworker-wal`)
  упраздняется — приёмник WAL живёт процессом внутри контейнера PG-ноды
  (механика запуска/надзора процесса внутри образа ноды — решение spec);
  при старте приёмник знает только своё имя ноды/шарда/кластера, а всё
  «куда бэкапиться» резолвит сам из etcd (S3-пул endpoints по роли источника,
  креды, bucket — per-cluster контракт arch/19 §7; фазы/tli-состояние — в
  etcd-журнал, образец WorkJournal arch/25 №15). Собственные метрики работы
  (arch/18): передано байт/сегментов, размер WAL-хвоста к отправке
  (отставание), ретраи/ошибки put и т.п. Следствия: закрывается отклонение
  arch/25 №21 (фазы — etcd, факты — метрики, docker-логи не читаются);
  уходят образы `pgworker-wal` (dev/e2e), имена `pgw-backup-wal-*` и
  инвариант «нода и её wal-агенты в одной сети» (агент внутри ноды);
  arch-first: правки arch/19 §2/§3, arch/14 §2.1, arch/18, arch/02 — в spec
  задачи, до кода.
- **`t26-backup-jobs-in-receiver`** ← `t25` — перенос backup-джобов внутрь
  WalReceiver: приёмник, уже отправляющий бэкап-данные онлайн (WAL) и
  живущий внутри PG-ноды (t25), исполняет и полный бэкап — pg_basebackup
  локально из своей ноды. Все операции запускаются по API WalReceiver:
  PgWorker подаёт через ВНЕШНЕЕ API (транспорт — HTTP) команду запуска —
  у каждой операции своя команда со своими параметрами, если они нужны —
  и опрашивает статус; PgWorker ↔ WalReceiver — только через API, никакого
  контейнерного взаимодействия (arch/25 §1/§2): docker-контейнеры
  backup-джобов (`pgw-backup-full-*`, образ `pgworker-backup`) упраздняются.
  Закрывает отклонение arch/25 №22 (джобовая часть t24 поглощается — при
  мерже t26 пункт t24 корректируется её мерж-коммитом).
  **Verify/drill/restore запускаются по API**: PgWorker запускает контейнер
  нового PG-инстанса (с WalReceiver внутри) — при запуске никаких команд,
  только старт; запуск самих операций verify/drill/restore — по API
  WalReceiver (команда восстановления с параметрами), статус операции —
  опросом по API; WalReceiver выполняет и контролирует процесс
  восстановления, статус отдаёт по требованию. API — единственный канал
  команд и статуса после старта контейнера (arch/25 §1/§2: запуск —
  единственная роль PgWorker в отношении контейнера). Arch-суть разделения
  ролей: **WalReceiver работает с данными; PgWorker управляет — создаёт
  новые инстансы PG c WalReceiver внутри и запускает операции через API
  WalReceiver**. Arch-first:
  правки arch/19 §2/§3.5, arch/25 №22 → канон, в spec до кода.
