# Roadmap: подсистема бэкапов шардов

Отложенные задачи подсистемы бэкапов PG-шардов. **PgWorker — хозяин
бэкапов**: он сам создаёт, ретраит/пересоздаёт при неудаче, чистит лишнее,
обрабатывает пограничные случаи и сигнализирует в алертинг панели — что
сломалось и какие действия предприняты. Канон подсистемы появится с
`t01-backup-canon` (будущий `../17-backups.md`); контекст сервиса —
[../14-pgworker.md](../14-pgworker.md).

Порядок: канон → полный бэкап → online-архивация WAL → проверки →
восстановление → ретенция → супервизор-цикл над всем.

## Задачи

- **`t01-backup-canon`** — арх-канон подсистемы бэкапов (новый
  `arch/17-backups.md`) + spec-скелет: механика (полные — `pg_basebackup`,
  online-WAL — `pg_receivewal`/`archive_command`, выбор в spec), layout
  хранилища бэкапов (том docker-хоста или объектное хранилище — открытый
  вопрос), контракт etcd-состояния (`/pgworker/backups/*`: полные бэкапы,
  WAL-цепочки, статусы/ошибки, политика ретенции per-cluster), с кого
  снимается бэкап (мастер/реплика), влияние на HA-контур и ресурсные
  лимиты. Зависимостей нет.
- **`t02-backup-full-daily`** — полные бэкапы БД каждого шарда раз в сутки
  (`pg_basebackup`): планировщик в PgWorker, фиксация бэкапа и его статуса
  в etcd, повтор/пересоздание при неудаче (сетевой сбой, нет места,
  мастер сменился посреди бэкапа), алерт в панель если к концу окна суток
  валидного полного бэкапа нет. ← `t01-backup-canon`.
- **`t03-backup-wal-stream`** — непрерывная online-архивация WAL-сегментов
  (инкремент к последнему полному бэкапу): доставка в хранилище бэкапов,
  контроль непрерывности цепочки от стартовой точки полного бэкапа (нет
  дыр — восстановление возможно), алерт при разрыве/отставании цепочки.
  ← `t01-backup-canon` (исполнима параллельно с t02: доставка WAL не
  требует готового полного, привязка «нужного» диапазона — задача t06).
- **`t04-backup-verify`** — проверки полных бэкапов: `pg_verifybackup`
  (checksum) + проверка полноты WAL-цепочки до точки бэкапа, статус
  проверки в etcd; по политике — периодическая проверка оставшихся
  бэкапов, алерт при невалидном. ← `t02-backup-full-daily`.
- **`t05-backup-restore`** — восстановление шарда из бэкапа: полный бэкап
  + накат WAL (PITR, в т.ч. на точку времени), операция по команде через
  PgWorker (пересоздание ноды/шарда из бэкапа), runbook-сценарии (полная
  потеря ноды, порча данных, восстановление в новый кластер). Критерий:
  на dev-станде кластер уничтожается и поднимается из бэкапов с
  проверкой данных. ← `t02-backup-full-daily`, `t03-backup-wal-stream`.
- **`t06-backup-retention`** — управление бэкапами и местом: схема
  оставления полных бэкапов 1д/7д/1мес (GFS), удаление устаревших
  полных; удаление ненужных WAL-сегментов — старше стартовой точки
  старейшего оставшегося полного бэкапа; защита от переполнения
  хранилища (квоты/пороги, алерт при нехватке места, запрет удалять
  последний валидный бэкап). ← `t02-backup-full-daily`,
  `t03-backup-wal-stream`.
- **`t07-backup-supervisor`** — супервизор-цикл PgWorker над всей
  подсистемой (reconcile желаемого состояния бэкапов из etcd):
  сам решает — что создать/пересоздать (неуспех по любой причине), что
  удалить (лишнее место не сжирает), сверяет фактическое содержимое
  хранилища с etcd-состоянием (зависшие/осиротевшие бэкапы и WAL);
  пограничные случаи — удаление/эвакуация шарда (судьба его бэкапов),
  смена мастера посреди операций, рестарт PgWorker посреди бэкапа
  (возобновление/пересоздание); каждый сбой и предпринятое действие —
  алерт в панель (какие действия предприняты). ← `t02-backup-full-daily`,
  `t03-backup-wal-stream`, `t04-backup-verify`, `t05-backup-restore`,
  `t06-backup-retention`.
