# Roadmap: подсистема бэкапов шардов

Отложенные задачи подсистемы бэкапов PG-шардов. **PgWorker — хозяин
бэкапов**: он сам создаёт, ретраит/пересоздаёт при неудаче, чистит лишнее,
обрабатывает пограничные случаи и сигнализирует в алертинг панели — что
сломалось и какие действия предприняты. Канон подсистемы —
[../19-backups.md](../19-backups.md); контекст сервиса —
[../14-pgworker.md](../14-pgworker.md).

Порядок: канон → полный бэкап → online-архивация WAL → проверки →
восстановление → ретенция → супервизор-цикл над всем → панель управления
хранилищем (S3).

## Задачи

- **t14-backup-wal-partial** — RPO-хвост WAL и фоновая чистка `wal/` по
  канону [../19-backups.md](../19-backups.md) (правки канона уже в
  дереве): (1) `.partial`-доотправка — приёмник WalReceiver каждые
  `Wal:PartialIntervalSec` (дефолт 3 с) и/или по порогу байт выгружает
  валидный префикс незакрытого сегмента объектом
  `wal/<segment>.<endLsn>.partial` (версия выкладывается только длиннее
  лежащей; финал при закрытии поглощает версии), гвард байт-сверки —
  только на финальных объектах (§3); (2) дубль `pg_wal` полного — в
  `wal/` только сегменты, закрытые в источнике на момент заливки
  (последний живой сегмент набора остаётся в `full/<id>/pg_wal/`) —
  устраняет гонку «срез дубля против финала стрима», которая валит E2E
  Restore_TargetTime_PitrRollback / Drill_Failed_OnCorruptedWal /
  Restore_Latest_RebuildsDestroyedShard (§2); (3) читатели `wal/`
  (контроль цепи, restore/fetch-wal, панель) — хвост потока =
  максимальный валидный префикс (финал или лучший `.partial`, §3/§3.5);
  (4) фоновая чистка `wal/` — wal-sweeper глобального лидера: per-shard
  независимо, оценка `.partial`-гигиены не реже раза в минуту на шард,
  срез финальных ниже cutoff, список → один batch-delete, метрики
  живости цикла и per-shard свежести + алерты (§4); (5) retention-гигиена
  `.partial` (поглощение финалом, ниже cutoff — §4 п.5).
