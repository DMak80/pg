# Roadmap: подсистема бэкапов шардов

Отложенные задачи подсистемы бэкапов PG-шардов. **PgWorker — хозяин
бэкапов**: он сам создаёт, ретраит/пересоздаёт при неудаче, чистит лишнее,
обрабатывает пограничные случаи и сигнализирует в алертинг панели — что
сломалось и какие действия предприняты. Канон подсистемы —
[../19-backups.md](../19-backups.md); контекст сервиса —
[../14-pgworker.md](../14-pgworker.md).

Порядок: канон → полный бэкап → online-архивация WAL → проверки →
восстановление → ретенция → супервизор-цикл над всем → панель управления
хранилищем (S3).

## Задачи

- **`t23-backup-job-endpoint`** — эндпоинт хранилища для бэкап-джобов:
  mc в bridge-контейнере джобы периодически ломится на localhost-эндпоинт
  хранилища (`BackupJobSpec`) — полные бэкапы подвисают/падают и дотягиваются
  ретраями; зафиксировать и сверять адрес, достижимый из сети джобы
  (диагностика 2026-09-29 в E2E-прогоне t06 — код бэкапов не менялся,
  механизм существующий).
- **`t24-walreceiver-tli-jump`** — переживание приёмником WAL перехода
  таймлайна при зазоре S3-хвоста: после фейловера (сервер на TLI+1) старт от
  хвоста S3 (`START_REPLICATION … PHYSICAL <lsn>` без TIMELINE) падает
  навсегда 58P01 «requested WAL segment … has already been removed», если
  хвост позади точки форка (сегменты между последним загруженным и форком
  не существуют под именем нового таймлайна): агент циклится
  starting/retry каждые 5 с, `.history` не загружается, WAL-бэкап шарда
  заморожен до следующего фейловера — само не восстанавливается. Сделать:
  распознавать 58P01 на старте стрима и переходить на текущий таймлайн
  сервера (IDENTIFY_SYSTEM → TIMELINE <текущий>), семантику зазора
  (сегменты между хвостом и форком в S3 не появятся — разрыв цепочки,
  RPO) сначала закрепить в [../19-backups.md](../19-backups.md) §3:
  маркер разрыва в статусе/журнале, видимость в verify/drill. Класс E2E
  `WalStream_Promote_TliHistory_ChainGlued` (трек reliability, t29 п.3)
  устраняется этой задачей.
