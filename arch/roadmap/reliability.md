# Roadmap: сквозная надёжность (восстановимость данных, самовосстанавливаемость, наблюдаемость)

Задачи из аудита надёжности 2026-09-28 (HA / бэкапы / control-plane /
наблюдаемость — полный разбор в сессии аудита; срез состояния —
[reliability-report.md](reliability-report.md)). Трек сквозной: задачи
касаются нескольких доменов (PgWorker/KafkaWorker/ValkeyWorker/панель/деплой)
и не принадлежат ни одному доменному треку целиком.

Целевые характеристики (влияние задачи помечается в отчёте):

- **D** — отсутствие потери данных;
- **R** — быстрая самовосстанавливаемость;
- **N** — надёжность/наблюдаемость (видимость деградаций, устойчивость
  контуров мониторинга).

Порядок номеров = порядок исполнения по умолчанию: P1 (t01–t06) — прямые
риски потери данных, P2 (t07–t12) — самовосстанавливаемость,
P3 (t13–t17) — наблюдаемость, P4 (t18–t22) — долговременные улучшения.

**Мерж-гейт трека** (расширение общего правила README): закрытие задачи
снимает пункт здесь И обновляет статус строки в
[reliability-report.md](reliability-report.md) **тем же мерж-коммитом** —
отчёт живой, рассинхрона «задача закрыта / отчёт нет» не бывает.

## Задачи

- **`t01-backup-encryption`** — шифрование бэкапов (SSE-S3/SSE-KMS или
  клиентское): сейчас компрометация S3-кредов/бакета = доступ ко всем данным
  всех кластеров установки; риск признан каноном (arch/19 §10), технически
  не закрыт. Частично пересекается с `t02-external-secret-manager`
  (pgworker-трек) — креды, но шифрование самих объектов — отдельная работа.
- **`t03-backup-second-copy`** — вторая копия бэкап-бакета (mirror /
  bucket replication в отдельный endpoint-хранилище): DR-сценарий опирается
  на выживание того же S3, что и основной (один bucket на установку,
  arch/19 §5).
- **`t10-rotation-ticket-timeouts`** — возрастные таймауты/самозачистка
  зависших ротационных заявок kafka/valkey (password/CA: исходы `waiting-*`
  висят неограниченно, снятие только ручное по runbook) + алерт на
  зависание.
- **`t11-swarm-running-inspection`** — реализовать `SupportsRunningInspection`
  Swarm-драйвером: сейчас заглушка отключает ускоренный failover мёртвого
  лидера (промоушен ждёт Patroni ttl=20 с) и сверку портов EnsureNode
  (S7/E6, arch/14 §5 C).
- **`t12-loop-watchdog`** — watchdog зависших циклов воркера: исключения
  циклов ловятся (TickSafelyAsync), но «завис без исключения» виден только в
  `loops-alive` healthz; самоперезапуска по staleness нет.
- **`t13-alert-notifications`** — внешняя нотификация алертов + история:
  алерты живут в памяти панели (при её падении невидимы, истории нет);
  Alertmanager стенда стоит с пустым `METRICS_ALERT_WEBHOOK_URL` (arch/18).
- **`t14-backup-metrics-export`** — экспорт бэкапных статусов в Prometheus:
  возраст последнего валидного полного, лаг WAL-сегментов (gauge уже есть),
  verify/restore-исходы; сейчас только панельные правила (словарь arch/18
  §2.2 не включает бэкапные серии).
- **`t15-prometheus-file-sd`** — file_sd из etcd-снапшота для скрейпа
  реальных нод: per-cluster сети недостижимы для Prometheus стенда
  (arch/18 §5.4) — метрики Patroni/Kafka/Valkey прод-нод не собираются.
- **`t16-cert-expiry-monitoring`** — мониторинг сроков сертификатов
  (API-серты воркеров/панели, серты нод): expiry нигде не проверяется.
- **`t17-rpo-rto-dashboard`** `← t14-backup-metrics-export` — RPO/RTO-числа
  оператору (не только пороговые алерты): возраст последнего валидного
  полного, лаг WAL, фактическое время последнего failover/rebuild.
- **`t18-incremental-backups`** — инкрементальные полные (PG17+
  `pg_incremental_backup`): суточные полные на больших базах — длинные
  окна, двойной расход staging, риск ENOSPC (arch/19 §10).
- **`t19-slot-auto-recreate`** — автозакрытие потерянных слотов
  (`slot-wal-lost` сейчас → OperatorRunbook «recreate ноды, слот почистите
  по runbook»): авто-recreate ноды вместо ручного разбора.
- **`t20-kfw-vwk-takeover-e2e`** — host-kill E2E для KafkaWorker /
  ValkeyWorker (по образцу PgWorker AC3/mid-add: kill инстанса посреди
  надзора, takeover без дублей): крэш-доигрывание у них покрыто на уровне
  процессов/фаз, но не «kill инстанса» интеграционно.
- **`t21-host-failure-scenarios`** — сценарии отказа docker-хоста/DC:
  анти-аффинити placement есть, мульти-хостовая эвакуация нод kafka/valkey
  и split-brain-пробы — только документация (arch/18, прод-мультихост).
- **`t22-patroni-rest-tls`** — TLS/аутентификация Patroni REST :8008:
  открытый HTTP во внутренней зоне кластера (arch/13); access-логи
  идентифицируют панель только User-Agent'ом.
- **`t24-e2e-suite-under-load`** — устойчивость полной E2E-серии к
  параллельной нагрузке: при тяжёлом соседнем прогоне на том же хосте
  серия одним фильтром подвисает на существующих сценариях (Restore-переход,
  AC2–AC7), последовательно по классам — зелёные; найти причину (бюджеты/
  таймауты фикстур vs CPU/IO-конкуренция) и устранить либо зафиксировать
  канон прогона.
- **`t27-wal-staging-loss`** — потеря WAL-сегментов при пересоздании
  wal-агента (влияние D — RPO WAL). Ошибочная ситуация: при пересоздании
  wal-агента закрывшиеся, но ещё не доставленные в S3 сегменты WAL
  теряются безвозвратно — цепочка в S3 получает дыру («ожидался сегмент
  N, найден N+k»), контроль переводит ключ wal в BROKEN, восстановление —
  только пересъёмом полного бэкапа. Причины (механизм): wal-агент (bash:
  `pg_receivewal --slot` в staging-том + `find → mc cp → rm`)
  подтверждает слот (feedback по fsync) по факту ЗАПИСИ в staging, а не
  доставки в S3 — staging-том единственная копия недоставленного; при
  пересоздании контейнера воркер удаляет staging-том вместе с контейнером
  («чистый том»), новый агент получает пустой том, `pg_receivewal`
  возобновляет со позиции слота — уже за потерянными сегментами
  (`restart_lsn` ушёл вместе с подтверждениями). Пересоздание — штатные
  операции супервиза: exited-агент, смена мастера (failover), устаревшие
  креды, стоп-семантика Enabled=false, QUARANTINED-шард; в multi-host
  после отключения docker-хоста агент пересоздаётся на ДРУГОЙ машине —
  staging-том исходного хоста недоступен в принципе (volume —
  непереносимое состояние). Способ решения (направление для исполнителя;
  канон — AGENTS.md «надёжность в расчёте на multi-host»: потеря машины
  вместе с volume — штатный сценарий) — две ортогональные оси, вместе
  дающие RPO=0 для подтверждённых транзакций при потере любой одной
  машины:
  (1) подтверждение по доставке, не по записи — позиция слота
  (`restart_lsn`) не должна уходить за последний фактически
  доставленный в S3 сегмент: подтверждение приёмника — успешный put
  в S3, а не запись в локальный staging; тогда любой рестарт
  (включая пересоздание на другом хосте после потери машины)
  возобновляет стрим от хвоста S3 и досыпает дыру из удерживаемого
  слотом WAL; вероятный путь исполнения — собственный WAL-приёмник
  (START_REPLICATION/COPY-протокол, feedback по факту S3-put) вместо
  `pg_receivewal`;
  (2) избыточность источника через sync-реплику — инвариант
  `synchronous_mode=true` (arch/05): WAL каждого ПОДТВЕРЖДЁННОГО
  изменения физически лежит в pg_wal обеих нод (мастер +
  sync-standby). Удержание — только слот, слоты per-instance (слот
  мастера реплике не виден), без слота pg_wal рекулейтится
  checkpoint'ами — поэтому реплика НЕ заменяет ось (1), а дополняет
  её. Варианты: (а) переключаемый источник — агент один, при
  дыре/потере staging/потере хоста переподключение к ДРУГОЙ ноде от
  хвоста S3 (имена сегментов одинаковы на обеих нодах, put в S3
  идемпотентен — дозасылка без дедупа); полноценно работает только
  поверх оси (1): слот оставшейся ноды обязан держать до
  доставленного; побочный эффект — смена мастера перестаёт требовать
  пересоздания агента (источник переключается, контейнер и staging
  живут); (б) двойная архивация — агенты на мастере и sync-реплике
  пишут в один префикс `wal/`: дедуп бесплатен (имена сегментов
  детерминированы, объект один), контроль склеивает union двух
  потоков без изменений; дыра возможна только при потере одного и
  того же сегмента ОБИМИ агентами — пересоздания независимы,
  вероятности перемножаются; защита вероятностная и без оси (1), с
  ней — детерминированная; цена: ×2 стрим-трафик, второй staging,
  оркестрация failover (реплика стала мастером — склейка цепочки
  через `.history` уже поддержана WalChain.CheckWithRestart;
  поведение физического слота реплики при её promote — проверить при
  проектировании). Симметрия канона: полный бэкап уже читает
  приоритетно с sync-standby (ResolveBackupSourceAsync) — wal-агент
  выравнивается под тот же принцип. Граница обеих осей: WAL после
  последнего sync-подтверждения физически есть только на мастере —
  это неподтверждённые (незакоммиченные) изменения, вне RPO
  durable-транзакций. Выбор комбинации осей и конкретика — за
  исполнителем по фронту работ. Переиспользование именованного
  staging-тома при пересоздании на том же хосте — допустимая
  митигация single-host (сокращает окно потери), каноном НЕ является
  и проблему не закрывает.
