# Valkey-кластеры: клиентский дискавери (приложения)

Уровень 3. Что и в каком порядке читает приложение, как строится TLS-доверие
и как ведёт себя библиотека дискавери. Ключи — [02-keys.md](02-keys.md) §1;
сбойные случаи — [05-fault-tolerance.md](05-fault-tolerance.md).

## 1. Что читает приложение

Приложение читает из etcd и только из него (аналогия pg dsn/`app_password`
и kafka endpoints):

1. `/valkey/clusters/<C>/endpoints` → адрес(а) подключения;
2. `/valkey/clusters/<C>/app_user` + `app_password` → ACL-креды
   (username+password, роль app);
3. `/valkey/clusters/<C>/config` → только `state` (raw-строка; отсутствие
   = Active — клиент видит заявочные переходы);
4. `/valkey/clusters/<C>/ca_pem` → TLS-доверие клиента (публичный CA
   per-cluster — аутентификация сервера). **Окно ротации CA**: значение —
   bundle OLD+NEW; клиент строит доверие по ВСЕМ блокам CERTIFICATE значения
   (двойное доверие), после коммита — снова один блок; читатель использует
   значение как есть, специальной ветки нет.

## 2. Библиотека дискавери

`GetClientConfig()` внешней библиотеки дискавери (образец HA.Kafka —
`docs/01.19-ha-kafka.md` в репозитории Puzzle) отдаёт `ssl=true` + CA для
StackExchange.Redis.

- **Правило**: `ssl=true ⟺ ca_pem` прочитан (снапшот без `ca_pem` —
  переходное/миграционное состояние: окно миграции `ssl=false→true`
  прозрачно — старые контуры не ломаются, актуализация подтянет).
- **Неполный набор кредов** (есть `app_user`, нет `app_password`, и
  наоборот) → `App = null` → `GetClientConfig() = null` (потребитель обязан
  проверить).
