# EtcdNode: DR-слепки и выгрузка в S3

Уровень 3. Функция «DR-слепки»: плановое и внеочередное снятие слепков
etcd (только по ВАЖНЫМ изменениям — пульсы сервисов не триггерят),
выгрузка в etcd-backup кластер, доводка отставания и обслуживание
контура. Форматы объектов и статус-ключа —
[00-etcdnode-contract.md](00-etcdnode-contract.md) §3,
[backups/06-s3-layout.md](../backups/06-s3-layout.md); полный автомат —
[processes/c-snapshot-export.md](processes/c-snapshot-export.md);
модель агента — [01-agent.md](01-agent.md).

## 1. Цель выгрузки

- **Единственный** S3-кластер с признаком `etcd_backup=true` в
  `/s3/clusters/` — живой резолв на каждом проходе (range config'ов →
  признак; единственность гарантирует гвард создания —
  [s3worker/07-api.md](../s3worker/07-api.md) §3).
- **Bucket — фиксированная константа `etcd-backups`**, одинаковое имя на
  всех установках: создаёт S3Worker на каждом инстансе кластера при
  provisioning дополнительно к per-install bucket
  ([s3worker/02-cluster-lifecycle.md](../s3worker/02-cluster-lifecycle.md) §5);
  имя не конфигурируется, per-install env-пар S3 у агента нет.
- **Креды/endpoints** — из `/s3/clusters/<C>/{endpoints,secrets}` (ключ
  `backups`, read-write; для etcd-backup кластера значение — спец-ключ из
  env S3Worker, [s3worker/04-security.md](../s3worker/04-security.md) §1).
- **Отказы цели** (кластера с признаком нет / `TO_REMOVE` / битые
  secrets) — статус `FAILED` с маркером `etcd-backup-missing` (панельный
  алерт; transient для цикла — ретраи тиком), НЕ краш агента. Слепки при
  этом продолжают сниматься локально и догоняются после появления
  кластера.

## 2. Снятие

Слепок снимается `/v3/snapshot/save` СО СВОЕГО УЗЛА
(`http://localhost:2379` — [01-agent.md](01-agent.md) §2) в локальный том
`/snapshots` (ретенция `RetentionFiles`). Том — **кэш доводки**: источник
истины для восстановления — выгруженные объекты S3, а не локальные файлы.
Каждый агент-узел ведёт СВОЙ том: смена лидера начинается с пустого кэша
(эталонной карты нет — первый тик нового лидера снимает слепок немедленно:
том пуст — срабатывает плановая ветка БЕЗ гейта; том непустой (повторное
лидерство узла) — важно + гейт `MinIntervalSec` от последней выгрузки;
RPO-консервативно).

Каждый слепок — ПОЛНЫЙ автономный дамп всего пространства ключей
(`/v3/snapshot/save` иных не делает): каждый хранимый бэкап самодостаточен —
восстановление из любого одного слепка, без цепочек; инкрементальных форм нет.

## 3. Расписание и фильтр важности изменений

- **Плановое** — раз в `IntervalMin=360` (страховка тишины).
- **Внеочередное** — ТОЛЬКО важные изменения. Механика:
  - после успешной выгрузки лидер хранит **эталонную карту** —
    `key → mod_revision` всех ключей пространства (полный range;
    контроль-плейн установки компактен); эталон — карта, прочитанная
    ДО снятия слепка этого тика (изменение в окне снятие–выгрузка
    остаётся «важным» на следующем тике);
  - тик читает revision кластера; не вырос относительно эталона —
    снятия нет; вырос — полный range и сравнение с эталоном:
    появился/исчез/изменился хотя бы один ключ ВНЕ списка пульсов (§3.1)
    → изменение важное → слепок снимается (если выгрузка старше
    `MinIntervalSec=5`); изменения только в пульсах — снятия НЕТ;
  - эталонной карты нет (первый тик после старта/смены лидера) —
    изменение считается важным (снимаем).
- **3.1. Канонический список пульсирующих ключей** (обновляется правкой
  канона и кода; новых пульсов без записи сюда не бывает):

  | Паттерн | Кто пишет | Ритм |
  |---|---|---|
  | префикс `/service/` | Patroni-DCS (leader, members, sync, initialize, config) | каждые loop_wait ≈ 1–2 с |
  | `/clusters/<C>/shards/<X>/master` | мастер-ключ HA: Patroni-callback, демон master-lease ноды, MasterKeyReconciler | lease-put каждые 1–2 с |
  | префикс `/etcdnode/` | сам агент EtcdNode (leader, instances, snapshots) | по событиям тика/выгрузки |

  Обоснование: это временные метки живости/указатели работающих сервисов;
  после восстановления из слепка они не актуальны (сервисы перепишут их
  первыми же тактами) — решение: DR-слепок ими не триггерится. Служебные
  ключи домена `/etcdnode/` — состояние самой выгрузки: при восстановлении
  лидерство/живость перепишутся первыми тактами нового контура, статус —
  первой выгрузкой. Мастер-ключ — пульс БЕЗУСЛОВНО (механика диффа видит
  рост mod_revision lease-put'а, смену значения она не различает; события
  failover видны по не-пульсовым ключам — routing и прочие). Появление
  НОВОГО ключа вне списка (и любые изменения не-пульсовых ключей) —
  важные изменения.
- **Отставание** (по статус-ключу: `FAILED`, ключа нет или новейший
  локальный слепок снят позже подтверждённого покрытия) — короткий сон
  `RetryIntervalSec=300` вместо планового интервала: окно транзиента
  закрывается минутами, а не следующим плановым слепком.

## 4. Выгрузка

Каждый снятый слепок уезжает **новой парой** объектов:
`etcd/snapshot-<id>.db` + `etcd/snapshot-<id>.meta.json`
(sha256/size/revision/taken/uploaded/instance — имя узла; layout
[backups/06-s3-layout.md](../backups/06-s3-layout.md) без изменений).

- **Порядок**: put `.db` (серверная SHA256-проверка транспорта) → put
  `.meta.json` → ретенция N=3 пар (guard ≥ 1) → статус-ключ.
- **Статус** пишется с семантикой покрытия —
  [00-etcdnode-contract.md](00-etcdnode-contract.md) §3.
- **Доводка (CatchUp)** — до снятия и повторным расчётом после: отстающая
  выгрузка догоняется новейшим ЛОКАЛЬНЫМ (своего узла) слепком тем же
  конвейером; успех продвигает покрытие и закрывает окно.
- **Бюджет** — единый `TimeoutSec=30` на всю попытку (put'ы + ретенция +
  статус суммарно); S3-шаги несут per-попыточный таймаут и «пульс
  конечного внешнего вызова». Любая неудача — `FAILED` + `error`, поля
  последнего успеха сохраняются, снятие не откатывается; все шаги
  идемпотентны (put поверх; коллизия имён в одну секунду — новее поверх).

## 5. Обслуживание контура

Compact + defrag каждого члена последовательно (client-грани из member
list, [01-agent.md](01-agent.md) §2), не чаще
`MaintenanceIntervalMin=60` — этот же лидерный цикл (второй исполнитель
исключён). Отказ обслуживания — warning, тик не фейлит.

## 6. S3-клиент

AWSSDK-клиент по образцу `BackupS3`: `PathStyle`, per-попыточный таймаут,
SHA256-проверка put (несовпадение — `BadDigest` от сервера), доверие CA
https-эндпоинта из `ETCDNODE_S3_CA_PEM` (агент материализует PEM во
временный файл на старте; переменную `AWS_CA_BUNDLE` AWSSDK не читает);
креды и endpoints — из резолва §1 на каждую попытку, клиент —
per-попытку.
