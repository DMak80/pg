# EtcdNode: восстановление etcd из S3-выгрузки

Уровень 3. Операторский runbook восстановления etcd-контура из DR-слепков.
Снапшоты etcd (контроль-плейн: декларации кластеров, маршрутизация,
секреты, клэймы, portalloc) снимают и выгружают агенты EtcdNode
([02-snapshots.md](02-snapshots.md)) в фиксированный bucket `etcd-backups`
на нодах etcd-backup S3-кластера (признак `etcd_backup=true` в
`/s3/clusters/`, [s3worker/README.md](../s3worker/README.md); bucket
создаёт S3Worker — [s3-clusters/README.md](../s3-clusters/README.md)):
префикс `etcd/`, пары `snapshot-<id>.db` + `snapshot-<id>.meta.json`
(sha256/размер/ревизия/instance — имя узла), каденс — плановый интервал +
детекция важных изменений. Потеря docker-хоста вместе с etcd —
восстановимая авария.

1. **Диагностика**: подтвердить наличие выгрузок —
   `mc ls --recursive <alias>/<bucket>/etcd/` — выбрать новейший
   `snapshot-<id>.db` и его `.meta.json`. Пусто → см. границы (п.6).
2. **Проверка целостности ДО восстановления** (обязательный шаг):
   скачать `.db`; сверить sha256 файла с `sha256` из `.meta.json` —
   ручная сверка и есть операторский барьер (ловит порчу до restore);
   затем `etcdctl snapshot status <file>` — информационный шаг
   (структура/размер/ревизия слепка; etcd 3.5.x печатает hash, но при
   status его НЕ сверяет — целостность им не доказывается); restore
   дополнительно верифицирует сам слепок (`etcdutl snapshot restore`
   проверяет sha256 при разворачивании, шаг 4). Расхождение sha256 или
   провал restore ⇒ взять предыдущий слепок (ретенция хранит N последних
   пар); файл с битым хешем не разворачивать НИКОГДА.
3. **Свежий etcd**: контейнер(ы) etcd с чистым data-dir
   (`INITIAL_CLUSTER_STATE=new`). Прод-3-ноды: сначала single-member,
   остальные — `etcdctl member add` после старта.
4. **Restore**: остановить etcd → `etcdutl snapshot restore <file>
   --data-dir=<data-dir>` (restore — офлайн-операция над слепком;
   верифицирует sha256 слепка при разворачивании — финальный барьер
   целостности) → стартовать etcd на восстановленном data-dir.
5. **Контроль**: `etcdctl endpoint health`; воркеры/панель
   переподключаются сами (poll-тик; клэймы переснимутся lease-механикой;
   journal мог откатиться к точке слепка — процессы идемпотентны и
   доводят фазы); панель видит кластеры, healthz воркеров зелёные.
   Статус-ключ `/etcdnode/snapshots` появится первым же слепком агентов
   пересобранного контура.
6. **Границы**: слепок = точка его снятия (RPO = окно от последнего
   ВАЖНОГО изменения до выгрузки — детекция важных изменений закрывает
   ≈5 мин при активности, транзиент S3 — доводкой тика
   `RetryIntervalSec`); пульсы сервисов (Patroni-DCS `/service/*`,
   мастер-ключи `/clusters/*/shards/*/master`) в слепок попадают «как
   снялось» и после восстановления НЕ актуальны — сервисы перепишут их
   первыми тактами, восстановление без них корректно; локальные тома
   слепков узлов (если пережили) — альтернативный источник того же
   формата; WAL-данные PG-шардов живут в S3 бэкапов независимо
   ([backups/README.md](../backups/README.md)) — восстановление etcd их
   не касается. Алерты панели: `etcd-snapshot-export-failed` (выгрузка
   провалилась — проверить etcd-backup S3-кластер: заявлен признаком,
   ноды живы, secrets читаются), `etcd-snapshot-export-stale` (выгрузка
   молчит — агенты узлов молчат или вечный transient),
   `etcd-backup-cluster-missing` (кластер с признаком не заявлен).
