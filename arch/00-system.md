# 00. Система: назначение, контуры и инварианты

Корневой документ (уровень 1). Общая картина системы и навигация по
документации: компоненты — [00-components.md](00-components.md), сквозные
технологии и общие технические правила — [00-technologies.md](00-technologies.md).

## 1. Назначение

Домашний (self-hosted) контур кластеров данных на нескольких docker-хостах:

- **шардированные HA-кластеры PostgreSQL** — Patroni + etcd DCS + Spilo;
  поверх шардов — фиксированное число бакетов-схем с онлайн-переездом
  между шардами;
- **Kafka-кластеры** — KRaft-брокеры с per-cluster SASL-кредами и CA;
- **Valkey-кластеры** — разделяемый кеш инстансов приложения (standalone,
  `nodes=1`);
- **S3-кластеры** — пул объектного хранилища бэкапов (ownS3) с
  mesh-репликацией.

Управление — декларативное: панель AdminPanel заявляет объект (кластер, шард,
переезд, ротацию) через HTTP API исполнителя; воркер валидирует заявку,
пишет декларацию в etcd, исполняет её через docker/swarm и публикует факт
обратно в etcd. Приложения-потребители читают адреса и креды из etcd
(клиентский дискавери), а не из конфигурации панели.

## 3. Модель развёртывания

- **Multi-host.** Docker-хостов несколько; у каждого свой локальный диск.
  Отключение любого хоста — штатный сценарий: вместе с ним теряются его
  контейнеры и docker-volume.
- **Docker plain или swarm.** Воркеры управляют контейнерами через Engine API;
  транспорт — `tcp://` + mTLS (канон), `ssh://`-туннель или `unix://` (стенд).
- **Гарантии — только от реплицированных источников истины** (etcd и S3).
  Локальные volume, staging и файлы — кэш/очередь без гарантий durability;
  RPO и непрерывность строятся от etcd/S3 и подтверждений записи в них.
- **Панель и воркеры всегда работают в контейнерах**, никогда хост-процессами:
  из docker-сети они резолвят ноды кластеров и Patroni напрямую.
- Внешние образы — из локального registry; ownS3 — внешний образ.
  Полный локальный стенд поднимается одним сценарием
  (`dev-stand/adminpanel/checks/00-up.sh`) и живёт на одном etcd-контуре.

## 4. Базовые инварианты

1. **Один etcd на установку.** Все участники работают с одним кластером,
   адрес передаётся явно при старте; «второй etcd» в контуре невозможен.
   ([17](17-synchronization-principles.md) S1)
2. **У каждого префикса etcd один писатель.** Домены (`/clusters/`, `/kafka/`,
   `/valkey/`, `/s3/`, `/etcd/`) пишут только их воркеры;
   панель в etcd пишет лишь серверные серты API воркеров
   (`/workers/api_tls/*`), все мутации идут через HTTP API исполнителей.
   ([25](25-component-communications.md), [adminpanel/README.md](adminpanel/README.md))
3. **Каналы — только стандартные протоколы.** HTTP(S), PostgreSQL, Kafka,
   RESP, S3, etcd; stdout/stderr контейнера — не канал связи. Оркестрация —
   только запуск/остановка/удаление и проверка факта (list/inspect).
   ([25](25-component-communications.md) §1–2)
4. **Предикаты — по первоисточнику.** «Кто мастер», «чей ключ» определяются
   прямыми пробами владельца истины, а не значением etcd-ключа; etcd-ключи —
   маршрутизация и кэш. ([17](17-synchronization-principles.md) S4)
5. **Мутации идемпотентны.** Фиксированный порядок записей, клэйм или
   периодический тик, journal-before-manipulations; транспортный флап не
   считается смертью. ([17](17-synchronization-principles.md) S5–S7)
6. **Несколько инстансов воркера — норма.** Они координируются lease-клэймами
   в etcd; смерть контролирующего инстанса не останавливает процессы —
   takeover укладывается в TTL. ([pgworker/00-etcd-contract.md](pgworker/00-etcd-contract.md) §4)
