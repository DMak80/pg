# 01. Архитектура кластера

Здесь — теория. Без неё дальше будет непонятно, **почему** конфиги именно такие и
**что происходит** при отказе ноды.

---

## 1. Компоненты и их роли

### 1.1 PostgreSQL — сама база
В кластере работает **3 экземпляра** PostgreSQL. Роли:

| Роль | Кол-во | Что делает |
|---|---|---|
| **Primary (leader/master)** | ровно **1** | Принимает **запись и чтение**. Единственный, кто это может. |
| **Replica (standby)** | **2** | Read-only. Получают изменения стриминговой репликацией от лидера в реальном времени. |

> PostgreSQL «из коробки» **не умеет** multi-master. Поэтому вся HA-надстройка сводится к
> одному: держать **ровно одного** writable-лидера и быстро переключаться на реплику при отказе.

### 1.2 Patroni — менеджер репликации и failover
Patroni ([docs](https://patroni.readthedocs.io/)) — это демон, который живёт **рядом с
PostgreSQL на каждой ноде** и делает:

1. **Начальную инициализацию** кластера (bootstrap): первая нода делает `initdb`, остальные
   подключаются и клонируют данные (`pg_basebackup`).
2. **Поддержку репликации**: создаёт replication-пользователя, выдаёт `primary_slot_name`,
   следит за `pg_stat_replication`.
3. **Выборы лидера** через DCS (etcd). Если лидер пропал — оставшиеся ноды выбирают нового.
4. **Продвижение реплики** (`pg_ctl promote`) до primary при необходимости.
5. **Health-check REST API** на порту `8008`: возвращает HTTP 200 для лидера и для
   пригодной реплики, плюс отдельный endpoint только-для-лидера. Это и использует HAProxy.

REST API Patroni (по умолчанию `:8008`):

| Endpoint | Возвращает 200, если |
|---|---|
| `/` | нода жива (и лидер, и реплика) |
| `/primary` | нода — **лидер** (для write-трафика) |
| `/replica` | нода — реплика |
| `/read-only` | лидер **или** реплика (для read-трафика) |
| `/read-write` | нода — лидер и принимает запись |

Именно эти endpoints мы будем дёргать, чтобы **узнать, кто мастер** (см. `07-identify-master.md`).

### 1.3 Spilo — готовый Docker-образ
Разворачивать PostgreSQL + Patroni + зависимости вручную в Docker — долго и чревато ошибками.
**Spilo** (Zalando) — это образ, где всё уже собрано:

```
один контейнер spilo = postgresql + patroni + pgq + postgis + wal-e/pgbackpack + консоль (adminapp) + скрипты
```

Мы передаём конфигурацию **через переменные окружения** (см. `configs/postgres/pg.env`),
а Spilo сам: монтирует PGDATA, инициализирует кластер, запускает Patroni, который в свою
очередь поднимает PostgreSQL.

> Альтернатива без Spilo (Patroni + чистый postgres image) показана в
> `configs/patroni/patroni.yml` — на случай, если нужно тонкое управление.

### 1.4 etcd — распределённое хранилище (DCS)
etcd — согласованное key-value хранилище. Patroni использует его как ** Distributed
Configuration Store (DCS)**. Там хранятся:

- `/service/<scope>/config` — глобальная конфигурация кластера (список членов, параметры).
- `/service/<scope>/leader` — **ключ лидера**: кто сейчас мастер. TTL ~30с, лидер его
  обновляет. Не обновил → ключ протух → выборы.
- `/service/<scope>/members/<name>` — каждая нода публикует свой conn_url и role.
- `/service/<scope>/initialize` — одноразовый флаг инициализации (защита от повторного bootstrap).
- `/service/<scope>/optime/leader` — позиция репликации лидера (для выбора «самой свежей»
  реплики при failover).

**Почему 3 узла etcd?** etcd требует **строгого большинства (quorum)** для записи:
`N=2k+1` узлов переживают потерю `k`. С 3 узлами мы теряемим потерю **1** и сохраняем
работоспособность. 1 узел — нет кворума при отказе; 2 узла — нет кворума при отказе одного.
Поэтому **минимум 3**. Мы размещаем по одному узлу etcd на каждой ноде БД — итого 3.

### 1.5 HAProxy — единая точка входа
Приложения **не должны** знать, кто сейчас лидер — этот статус меняется при failover.
HAProxy решает это:

- Запрашивает у Patroni REST API каждой ноды её статус.
- **Порт 5432** → направляет на ту ноду, у которой `/primary` = 200 (мастер). Writes идут сюда.
- **Порт 5433** → направляет на ноды, у которых `/read-only` = 200 (мастер + реплики).
  Reads можно балансировать по репликам.
- Когда лидер меняется — HAProxy сам перенаправляет трафик (через health-check), перенастройка
  приложения не нужна.

Статистика HAProxy доступна на `:7000` (см. `configs/haproxy/haproxy.cfg`).

## 2. Как идёт репликация

```
       ┌──────────────┐   streaming replication (WAL over TCP, 5432)
       │  pg1 PRIMARY │ ───────────────────────────────────────────┐
       └──────────────┘                                            │
                ▲                                                  ▼
                │                                  ┌──────────────┐  ┌──────────────┐
                │ Patroni watch DCS                │   pg2 REPLICA│  │   pg3 REPLICA│
                │                                  └──────────────┘  └──────────────┘
                ▼                                                          ▲
       ┌──────────────┐                                                    │
       │     etcd     │  pg2/pg3 тоже шлют в etcd heartbeat о себе ────────┘
       │  3 узла, KV  │
       └──────────────┘
```

- **WAL (Write-Ahead Log)** — встроенный механизм PostgreSQL: все изменения сначала пишутся
  в WAL, потом применяются к данным. Репликация = передача WAL-сегментов подписчикам.
- **Streaming replication** — реплики тянут WAL по TCP в реальном времени (не по расписанию).
- **Synchronous vs asynchronous**: Patroni поддерживает режим `synchronous_mode: true`,
  когда лидер ждёт подтверждения от хотя бы одной реплики перед коммитом. Это убирает потерю
  данных при failover ценой латентности. **Рекомендую включить для fail-safe** (см. `pg.env`).

## 3. Как происходит отказ лидера (failover)

Это **самая важная** часть. Сценарий: упала нода pg1, которая была лидером.

```
T=0   pg1 упал. Он перестал продлевать lease в etcd.
T=30s lease лидера в etcd истёк (по умолчанию TTL ~30с, см. loop_wait/loop_wait).
       └→ ключ /service/pgcluster/leader удалён.

T=30s pg2 и pg3 заметили (каждый опрашивает DCS каждые loop_wait, по умолч 10с).
       └→ оба пытаются стать лидером: etcdctl/POST в DCS "я кандидат".

T=31s etcd (кворум 2/3) атомарно отдаёт лидерство одной из нод — скажем, pg3.
       └→ pg3 видит: "я избран". Убеждается, что его данные свежие (проверяет
          optime/leader). Если он отставал — догоняет или отказывается.

T=31s pg3 выполняет pg_ctl promote → становится новым PRIMARY (writable).
       └→ пишет в DCS новый conn_url, обновляет /optime/leader.

T=32s HAProxy делает следующий health-check:
       └→ pg3 отвечает 200 на /primary → HAProxy перенаправляет writes на pg3.
       └→ pg1 не отвечает → HAProxy убирает его из пула.

T=~60s Приложения автоматически пошли писать в pg3 (через HAProxy 5432).
```

Ключевые свойства:
- **Автоматично.** Без ручного вмешательства (если не задан `pause`).
- **Защита от split-brain.** Если нода не может достучаться до DCS — она **обязана**
  перестать быть writable (Patroni уводит её в read-only или останавливает PG).
  Два мастера невозможны, пока жив кворум DCS.
- **Выбор самой свежей реплики.** Patroni сравнивает `pg_wal_lsn_diff` и повышает ту,
  что ближе всех к лидеру. При sync-репликации — это гарантированно синхронная реплика.

### Плановая смена — switchover (без отказа)
Когда нужно сменить мастера планово (обслуживание, обновление):
```bash
./scripts/switchover.sh pg3   # сделать pg3 лидером, pg1 станет репликой
```
Это делает `patronictl switchover`: лидер штатно дожидается выравнивания реплики,
передаёт роль, старый лидер становится репликой. **Без даунтайма для приложений**
(через HAProxy).

## 4. Что где живёт (data flow)

| Слой | Данные | Где |
|---|---|---|
| PostgreSQL | таблицы, индексы, WAL | **локальный диск каждой ноды** (PGDATA, обычно `/var/lib/postgresql/data` или отдельный mount) |
| etcd | метаданные кластера | **локальный диск каждой ноды etcd** (`/var/lib/etcd`) |
| Patroni | stateless — читает конфиг из env/yml + DCS | только конфиг, на диске ничего критичного не хранит |
| HAProxy | stateless | только конфиг |

> Т.о. **данных кластера нигде нет в DCS** — только метаданные. Реальные данные — на дисках
> нод PostgreSQL. Потеря всего etcd = кластер не сможет проводить выборы, но данные на месте;
> восстановить можно (см. `09-troubleshooting.md`).

## 5. Сводка портов

| Порт | Что | Кому открывать |
|---|---|---|
| 2379 | etcd client API | Patroni-нодам, HAProxy (для запросов) |
| 2380 | etcd peer-to-peer | **только между узлами etcd** |
| 5432 | PostgreSQL | HAProxy, приложения (лучше через HAProxy) |
| 8008 | Patroni REST API | HAProxy, мониторинг, админ-скрипты |
| 5432 (HAProxy) | точка входа для writes | приложениям |
| 5433 (HAProxy) | точка входа для reads | приложениям |
| 7000 (HAProxy) | HAProxy stats UI | админам |
