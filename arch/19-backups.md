# 19. Подсистема бэкапов шардов: PgWorker-оркестрация (канон) ★

**PgWorker — хозяин бэкапов шардов**: он сам создаёт, ретраит/пересоздаёт,
чистит, сигнализирует в панель. Ноды (Spilo) бэкапами не управляют. Механика —
базовые утилиты PostgreSQL (`pg_basebackup`, `pg_receivewal`) + оркестрация
воркером; WAL-G/pgBackRest НЕ встраиваются (параллельное использование
оператором не поддерживается и не смешивается). Хранилище — S3-совместимое
объектное (dev-стенд MinIO, прод — любое S3, вкл. облако). Реализация —
t02–t07 по разделам §8; t01 (этот документ) код не исполняет.

Ключевые свойства:

- **Единый оркестратор** — PgWorker: джобы/агенты бэкапов — его docker-
  контейнеры, их жизнь супервизируется воркером; ноды остаются сторонними
  серверами для клиентов `pg_basebackup`/`pg_receivewal` (§6).
- **Контракт в etcd** — состояния пишутся под `/pgworker/backups/*`; пишет
  префикс ТОЛЬКО PgWorker (держатель клэйма `<C>`), панель читает (§4).
- **Хранилище — объектное S3** — один bucket на установку, layout
  per-cluster/per-shard, файлы `pg_basebackup` 1:1 (§5); креды per-install —
  только env воркера (§7).
- **Паттерны arch/17** — идемпотентность каждого шага,
  journal-before-manipulations, transient vs permanent-отказы (§1, §4).

Границы (что НЕ входит): UI/алерты панели (t02+), управление нодами/HA-контуром
при СОЗДАНИИ бэкапов (полные/WAL — сторонние клиенты нод; restore (t05, §3.5) —
операция пересоздания шарда: демонтаж нод/чистка HA-scope/подъём — выполняется
держателем клэйма `<C>` по команде оператора), файловое том-хранилище
docker-хоста (решение — S3).

---

## 1. Роль и границы

- **Роль в системе**: защита данных шардированных кластеров (полные +
  WAL), восстановление (t05) — единый оркестратор PgWorker.
- **Схема взаимодействия**:

```
AdminPanel (UI)              PgWorker (оркестратор бэкапов)
───────────────              ──────────────────────────────
читает снапшот ──читает──►   /pgworker/backups/<C>/…   (etcd)
(алерты t02+)                ──создаёт/супервизирует──► docker-контейнеры:
                               джобы pg_basebackup (t02),
                               агенты pg_receivewal (t03),
                               restore-джобы PITR (t05, §3.5)
                                 │                       │
                                 ▼                       ▼
                               PG-ноды шарда           S3 (MinIO на
                               (реплика/мастер —       стенде): bucket
                               сторонние клиенты)      per-install
```

- **Принципы**: arch-first (этот документ — источник правды для t02–t07);
  единый etcd-контур и паттерны
  [17-synchronization-principles.md](17-synchronization-principles.md)
  (идемпотентность каждого шага, journal-before-manipulations, transient vs
  permanent); PgWorker — единственный писатель префикса `/pgworker/backups/*`;
  S3-креды per-install только env (§7).

## 2. Механика полных бэкапов (реализация — t02)

- **Инструмент**: `pg_basebackup` (plain-формат, `-X stream`,
  `--checkpoint=spread`, `--manifest-checksums=SHA256`).
- **Исполнитель**: ephemeral docker-контейнер джоба
  `pgw-backup-full-<C>-<X>-<id>`, запускает PgWorker; образ — лёгкий
  `pgworker-backup` (отдельный Dockerfile в `docker/` —
  `PgWorker.Backup.Dockerfile` + `docker/backup/entrypoint.sh`, сборка —
  t02). **Контракт образа** (общий для джобов t02, агентов t03 и
  restore-джобов t05): образ содержит ТОЛЬКО инструменты — postgres-клиентские
  утилиты (`pg_basebackup`, `pg_receivewal`, libpq), серверные бинари того же
  мажора PG (`pg_ctl`/`postgres`/`pg_controldata` — база образа `postgres:18`
  несёт их; нужны restore-джобу t05 для локального наката WAL без сети),
  `mc` (MinIO/S3-клиент; работает с любым S3) и `bash`; S3-шиппер НЕ
  встраивается в образ — механику запуска (bash-скрипт: pg_*-утилита + цикл
  доставки в S3 через `mc`) воркер версионирует кодом: джоб полного —
  ENTRYPOINT-скрипт образа с env-параметрами (t02), WAL-агент — inline-команда
  при создании контейнера (t03, §3), restore-джоб — inline-команда при
  создании контейнера (t05, §3.5 — recovery-механика меняется чаще образа). Джоб не публикует портов
  (клиент) и запускается на docker-хосте источника (адрес ноды достижим по
  advertised-правилу ниже; оттуда же достижим S3-endpoint — он per-install,
  см. §7).
- **Источник**: реплика шарда (sync-standby из Patroni `GET /cluster`:
  member с `state=running`, `role=replica`, sync-статусом);
  реплика недоступна/отстала → fallback на мастер (резолв мастера —
  существующий `ShardEndpoints`, [14-pgworker.md](14-pgworker.md) §5 F).
  Источник фиксируется в etcd-статусе (`node`, `role`).
- **Пайплайн джоба**: staging-каталог (ephemeral volume) →
  `pg_basebackup -D <staging>` → загрузка в S3 (`mc cp` файлами 1:1
  объектами, включая `backup_manifest` и `pg_wal/`) → результат в stdout.
  Прогресс и результат джоб публикует структурированными JSON-строками в
  stdout (`{"phase":"basebackup"}`, `{"phase":"uploading"}`, финальный
  result `{"ok":true,"wal_start_segment":…,"size_bytes":…}` или
  `{"ok":false,"error":…}`); воркер поллит логи контейнера тиками
  (`GET /containers/<id>/logs`), отражает фазы в etcd-статусе и по exit-коду
  + result-JSON фиксирует итог — **etcd пишет ТОЛЬКО воркер** (§4), джоб
  контракта etcd не знает. `wal_start_segment` — из `backup_label`
  (START WAL LOCATION). После фиксации итога воркер удаляет контейнер и
  staging-volume джоба. Конфигурация джоба — только env контейнера от
  воркера: подключение к источнику, S3-комплект (§7), префикс `<C>/<X>`,
  путь staging `PGW_BK_STAGING_DIR` (опция `Staging.Dir`, дефолт
  `/backup-staging` — точка монтирования staging-volume в джобе).
- **WAL набора `-X stream` (t02)**: файлы бэкапа грузятся строго 1:1 в
  `full/<id>/` ВКЛЮЧАЯ `pg_wal/` (база `pg_verifybackup`, t04 — manifest
  перечисляет и WAL-файлы); ЗАТЕМ закрытые сегменты этого набора
  дублируются в общий WAL-префикс `wal/` шарда (стартовая точка цепочки
  для t03; дублирование осознанное — снимает конфликт «layout vs общий
  префикс», закрытый сегмент = один объект, перезапись идемпотентна).
- **Идентификатор**: `id = YYYYMMDDHHMMSSZ` (UTC старта, сортируемый);
  коллизия в пределах шарда — суффикс `-2`, `-3`…; детерминизм имён — как у
  `pgw-<C>-<X>-<n>` ([14-pgworker.md](14-pgworker.md) §6).
- **Подключение**: адресация из portalloc (pg-порты нод) в том же namespace
  адресов, что панель (advertised-правило
  [14-pgworker.md](14-pgworker.md) §2.4 п.5); БД-роль — §7.
- **Планировщик (rolling, t02)**: воркер тиками под клэймом `<C>` для
  каждого шарда Active-кластера с `dsn`: возраст последнего ВАЛИДНОГО

## 3. Online-WAL: pg_receivewal-агент (реализация — t03)

- **Агент**: long-running контейнер `pgw-backup-wal-<C>-<X>` (образ —
  `pgworker-backup`, контракт §2), запускает и супервизирует PgWorker.
  Команда — inline bash-скрипт от воркера (§2): `pg_receivewal
  --slot=<slot> -D <staging>` + S3-шиппер: закрытый сегмент → upload
  `wal/<segment>` (ключ объекта = имя сегмента) → удаление из staging;
  `.partial` — по канону `pg_receivewal` (НЕ грузится, не входит в цепочку);
  `.history`-файлы ЗАГРУЖАЮТСЯ обязательно (PITR через смену timeline).
  Обрыв приёмника — ШТАТНОЕ событие, не гасит контейнер (t05-регресс
  2026-09-13: рестарт PG мастера при смене sync-standby убил `pg_receivewal`
  на незакрытом сегменте → сегмент остался `.partial` и НИКОГДА не попал в
  архив → невосстановимая дыра → restore шарда невозможен): скрипт
  переподключает приёмник циклически — слот продолжает с `restart_lsn`,
  текущий `.partial` доигрывается до закрытия и доставляется. Контейнер
  гасят только неисправимые состояния (квота staging переполнена — exit 4):
  супервиз пересоздаёт агента чистым томом.
  S3-креды и DSN — env контейнера (§7); restart-политика `unless-stopped`
  (docker поднимает агента после смерти/ребута — воркер тиком сверяет).
- **Слот**: один на шард, имя `pgw_bkp_<C>_<X>`; длиннее NAMEDATALEN(63) →
  `pgw_bkp_` + sha1(`<C>/<X>`)[:16]. Слот создаёт воркер (SQL ensure на
  мастере, идемпотентно: `pg_replication_slots` → `pg_create_physical_
  replication_slot(..., true)`), держит WAL на мастере до подтверждения
  приёма — защита непрерывности цепочки. Подключение — роль `backup_exec`
  (§7; ensure/ротация — t02): ключ `/clusters/<C>/backup_password`
  отсутствует (t02 не смержена/ensure не прошёл) → transient-ожидание
  тиками, агент не поднимается.
- **Подключение**: к мастеру шарда (резолв `ShardEndpoints`, arch/14 §5 F).
  Агент подключается к per-cluster docker-сети кластера (как ноды) —
  адрес мастера = имя ноды (alias) `:5432` внутри сети; для усыновлённых
  (`object`) нод — `host:pg-port` из portalloc. Смена мастера →
  пересоздание контейнера агента с нового мастера (воркер тиком сверяет
  фактического мастера с `master_node` статуса), догон цепочки, склейка
  timeline через `.history`. Рестарт-луп контейнера (устаревшие креды
  после ротации) → пересоздание со свежими env.
- **Истина прогресса — S3**: агент пишет ТОЛЬКО объекты в S3 (сегменты,
  `.history`) и ничего больше; воркер с периодом `Wal:VerifyIntervalSec`
  list-ит префикс `wal/` и по факту объектов вычисляет `last_uploaded`,
  непрерывность цепочки и пишет etcd-ключ `wal` (§4; префикс
  `/pgworker/backups/*` пишет ТОЛЬКО воркер — агент etcd не касается;
  «последний загруженный» из статуса-объекта агента НЕ используется —
  один источник истины, объекты).
- **Правила непрерывности** (инвариант §4, детали): имя сегмента — 24 hex
  символа `TLI(8)+log(8)+seg(8)`; следующий = `seg+1`, при `seg=0xFF` →
  `log+1, seg=0`; переход timeline валиден при наличии загруженного
  `<newTLI>.history` и первом сегменте нового TLI, равном последнему
  сегменту старого TLI ИЛИ следующему за ним (точка переключения внутри
  сегмента — PG перезаписывает сегмент с нового TLI); полный LSN-разбор
  history — verify t04 (§5): воркер скачивает `.history`-объекты из
  `wal/` и валидирует TLI-переходы по точке переключения из файла
  (`switchWALLSN` в границах сегмента первого сегмента нового TLI);
  runtime-контроль потока (этот §) остаётся на эвристике номеров. Цепочка проверяется от `chain_start_segment`: стартовая
  точка = `wal_start_segment` старейшего COMPLETED полного бэкапа; полных
  нет → первый сегмент потока агента (закрепляется в статусе при первом
  upload). Ретенция (t06) чистит сегменты ниже стартовой точки старейшего
  ОСТАВЛЯЕМОГО полного (§4) — `chain_start` поднимается автоматически при
  следующем контроле (list S3 — истина), list-префикс укорачивается.
  Дыра (нет next-сегмента / TLI-переход без history) → `DEGRADED` +
  `error` c границами дыры; лечение — переснятие полного (t07/t02),
  t03 сигнализирует. `wal/<segment>` после дыры до переснятия НЕ
  загружаются агентом заново (слот держит позицию; цепь восстанавливает
  новый полный + новый поток).
- **Отставание**: `lag_segments` = сегмент текущей позиции записи мастера
  (SQL-зонд `pg_current_wal_lsn()` → имя сегмента; подключение —
  admin-DSN мастера, существующие билдеры) − `last_uploaded`;
  `lag_segments > Wal:LagMaxSegments` или возраст `last_uploaded_unix`
  > `Wal:StaleSec` при живом кластере → `DEGRADED` + `error` (transient:
  ретраи тиками; постоянное отставание без прогресса — алерт панели).
- **Стоп-семантика**: `Backups:Enabled=false`, демонтаж шарда (S-процессы),
  deprovisioning кластера (D1) → воркер останавливает и удаляет контейнеры
  агентов (идемпотентно по имени `pgw-backup-wal-<C>-<X>`); etcd-ключи
  кластера чистит Deprovisioning D2 (`del --prefix /pgworker/backups/<C>/`,
  arch/14 §5 B). `STOPPED` — воркер сознательно остановил агент живого
  шарда (шард QUARANTINED/эвакуация — поток WAL мёртвого шарда не нужен);
  демонтаж ключи удаляет. Этими путями S3-объекты не удаляются
  (§4, R4-симметрия; единственный осознанный удаляющий объектов —
  ретенция t06).

## 3.5. Восстановление шарда из бэкапа: PITR (реализация — t05)

- **Операция**: восстановление ОДНОГО шарда `<X>` кластера `<C>` из
  `full/<id>` + накат WAL-цепочки до цели: `latest` (конец цепочки — полная
  потеря шарда/DR) или `target_time` (RFC3339 — порча данных, откат к
  моменту до порчи). Запуск — команда оператора через HTTP API воркера
  (`POST /api/clusters/<C>/shards/<X>/restore`,
  [14-pgworker.md](14-pgworker.md) §1.1): тело задаёт `backup_id` (нет —
  новейший COMPLETED/list-S3), цель, `source` (S3-префикс источника;
  default — собственный `<C>/<X>`; DR: префикс погибшего кластера —
  восстанавливаем в пересозданный кластер) и `confirm` = имя шарда
  (перезапись данных осознана, мисматч → 400). Воркер валидирует и сам
  пишет заявку-статус в etcd (§4); UI — t08. Одна активная заявка на шард
  (повтор при активной → 409). Потеря ОДНОЙ ноды живого шарда restore'ом НЕ
  чинится (Patroni rebuild быстрее — runbook отсылает к
  recreate-эндпоинту).
- **Restore-джоб**: ephemeral контейнер `pgw-backup-restore-<C>-<X>-<id>`
  (id заявки — как у полных, §2), образ `pgworker-backup` (§2, с серверными
  бинари PG того же мажора), inline-команда от воркера (env-параметры;
  секреты — env, §7). Джоб монтирует data-volume ПЕРВОЙ ноды шарда
  `pgw-<C>-<X>-<n1>-data` (volume создаёт воркер) и: (1) скачивает
  `full/<id>/` файлами 1:1 в PGDATA-каталог Spilo-layout
  (`pgdata/pgroot/data`; владелец — uid:gid `101:101` Spilo- postgres,
  численно), (2) кладёт скрипт `restore_command` (скачивает сегмент/`.history`
  из `wal/` префикса S3 прямо в запрошенный путь; объекта нет → ненулевой
  exit — конец WAL) и `postgresql.auto.conf` c `restore_command` +
  recovery-параметры (`recovery_target_time` при цели time,
  `recovery_target_action=promote`; цель latest — БЕЗ target: конец WAL =
  promote), (3) локально стартует postgres (`pg_ctl`, unix-socket,
  `listen_addresses=''` — сеть не слушает, кредов PG не нужно) и ждёт
  выхода из recovery (поллинг `pg_is_in_recovery()`; бюджет
  `Restore:RecoveryTimeoutSec`), (4) `pg_ctl stop -m fast`, убирает
  recovery-остатки из `auto.conf`. Прогресс — stdout-маркеры
  (`{"phase":"downloading"|"recovering"}`, result-JSON с
  `{"ok":true,"restored_to_lsn"?…}` / `{"ok":false,"error"…}`) — супервиз
  по образцу t02 (поллинг логов, exit-код — истина итога). Накат большого
  объёма — одним проходом, резюмов нет (осознанная плата plain-механики).
- **RestoreProcess** (машина тика под клэймом `<C>`, паттерны arch/17):
  `PLANNED` → валидация (кластер Active, шард заявлен, шард без
  усыновлённых object-нод (чужой PGDATA-контур — permanent-отказ «ручной
  runbook»), бэкап существует —
  etcd-статусы ИЛИ list-S3 `backup_manifest` (DR: etcd пуст),
  WAL-цепочка от `wal_start_segment` полного непрерывна (WalChain t03) —
  дыра → permanent-отказ с границами) → `RUNNING` (демонтаж:
  WAL-агент шарда стоп (§3), контейнеры/volumes ВСЕХ нод шарда снесены,
  HA-scope `/service/<C>-<X>/` вычищен (P2.2-Д3-образец: initialize/leader/
  members/…; request_* — декларации панели — НЕ трогаем), ноды
  `state=REBUILDING`, portalloc/dsn НЕ меняются) → запуск restore-джоба
  (фазы downloading/recovering — из логов) → `REJOINING` (EnsureNode первой
  ноды на восстановленном volume — Patroni поднимает существующие данные,
  bootstrap с непустым PGDATA при чистом DCS; ожидание идентифицирующей
  пробы P2.2-образцом; остальные ноды — чистые EnsureNode, реплики
  догоняются `pg_basebackup` с восстановленного лидера) → все ноды RUNNING →
  `COMPLETED` (пост-обработка: ключ `wal` шарда УДАЛЯЕТСЯ — планировщик §2
  немедленно переснимает полный (инвариант цепочки; PITR-назад ломает
  сшиваемость TLI — новая цепочка начинается с нового полного), агент t03
  поднимется сам с новым слотом). **Гвард исключения**: пока у шарда есть
  активный (не COMPLETED/FAILED) restore-ключ, контуры воркера шард не
  трогают — надзор не пересоздаёт снесённые ноды (иначе пустой Patroni
  поверх restore), эвакуатор не считает шард мёртвым, планировщик полных
  скипает шард, усыновление/репарация переездов не касаются (restore сам
  владеет жизненным циклом шарда; переезды бакетов получают обычный
  transient «мастер недоступен»).
  transient-сбой фазы → ретраи тиками
  (демонтаж/запуск идемпотентны); permanent (дыра WAL, бэкап исчез,
  recovery-бюджет исчерпан, target не достигнут — конец цепочки раньше
  `target_time`) → `FAILED` + `error`; повтор — НОВАЯ заявка оператора.
  Takeover: статус + детерминированные имена — новый инстанс продолжает.
- **Стоп-семантика**: deprovisioning (D1) убивает restore-джобы вместе с
  джобами полных (префикс `pgw-backup-*`), D2 чистит префикс
  `/pgworker/backups/<C>/` (вкл. restore-ключи); remove-shard с активным
  restore → заявка FAILED `cancelled-by-remove`. S3-объекты restore не
  удаляет никогда (только читает).
- **Runbook** (t05, `docs/backup-restore.md`): полная потеря ноды (живой
  шард → Patroni recreate; весь шард → restore latest), порча данных
  (target_time до порчи), восстановление в новый кластер (DR: пересоздание
  декларации + restore с source) — критерий приёмки: кластер уничтожается и
  поднимается из бэкапов с проверкой данных (E2E-гейт + ручной прогон
  dev-станда).

## 4. Контракт etcd `/pgworker/backups/*`

- Пишет ТОЛЬКО PgWorker под клэймом `<C>` (операции бэкапов — под тем же
  клэймом, что остальные процессы кластера); панель читает (контекст —
  [adminpanel/02-etcd-contract.md](adminpanel/02-etcd-contract.md) §2.3.1;
  UI/алерты — t02+).

| Ключ | Значение |
|---|---|
| `/pgworker/backups/<C>/policy` | per-cluster политика: `{"retention":{"days":7,"weeks":4,"months":6},"full_max_age_sec":86400,"verify":{"on_create":true,"interval_sec":604800}}`; пишет воркер (приём через API — t06; до того — ручная запись ключа); отсутствует → дефолт `PgWorker:Backups:Policy` |
| `/pgworker/backups/<C>/<X>/full/<id>` | статус полного: `{"state":"PLANNED\|RUNNING\|UPLOADING\|COMPLETED\|FAILED\|DELETING","node":"<n>","role":"replica\|master","started_unix","finished_unix"?,"wal_start_segment"?,"size_bytes"?,"error"?,"verify":{"state":"PENDING\|OK\|FAILED","checked_unix"?,"error"?}}`; `wal_start_segment` заполняется с фазы UPLOADING (из `backup_label` джоба; для рано упавших FAILED может отсутствовать — до этого неизвестен); `verify` — результат проверки t04 (§5): PENDING в т.ч. «идёт», `error` — причина невалидности (checksums/цепочка с границами) |
| `/pgworker/backups/<C>/<X>/wal` | состояние WAL-потока шарда: `{"state":"ACTIVE\|DEGRADED\|STOPPED","slot":"<slot>","master_node","chain_start_segment","last_received_segment","last_uploaded_segment","last_uploaded_unix","lag_segments"?,"error"?}` |
| `/pgworker/backups/storage` | занятость хранилища установки (t06): `{"used_bytes":…,"quota_bytes"?,"used_percent"?,"state":"OK\|WARN\|CRIT","updated_unix":…}`; ключ ГЛОБАЛЬНЫЙ (вне per-cluster префиксов, D2-чистки не касается); пишет ретенционный проход (см. «Ретенция» ниже) — любой живой клэйм пишет одно и то же свежее значение (идемпотентно); `quota_bytes` не задан (0) → пишется только `used_bytes`, `state=OK` |
| `/pgworker/backups/<C>/<X>/restore/<id>` | операция восстановления шарда (t05, §3.5): `{"state":"PLANNED\|RUNNING\|REJOINING\|COMPLETED\|FAILED","backup_id","source":"<srcC>/<srcX>","target":"latest"\|"time:<RFC3339>","node","requested_unix","requested_by","started_unix"?,"finished_unix"?,"phase"?,"restored_to_lsn"?,"error"?}`; `id` — как у полных (§2); максимум один активный (не COMPLETED/FAILED) restore на шард; `phase` — фаза джоба/процесса (`downloading\|recovering`); по COMPLETED ключ `wal` шарда удаляется (переснятие полного планировщиком §2) |

- **Правила**: transient-сбой → статус с `error` + ретраи тиками (t02/t03);
  permanent-отказ → фиксация причины + алерт. `DELETING` — транзитная фаза
  ретенции (t06; запрет удалять последний валидный полный — guard t06).

- **Ретенция (t06)**: rolling-проход воркера под клэймом `<C>` по расписанию
  `Retention:IntervalSec`, для каждого шарда Active-кластера:
  1. **GFS-отбор по календарю UTC**: дневные — все COMPLETED-полные последних
     `retention.days` календарных суток; недельные — ПОСЛЕДНИЙ COMPLETED
     каждой из `retention.weeks` предыдущих календарных недель (ISO-неделя);
     месячные — ПОСЛЕДНИЙ COMPLETED каждого из `retention.months`
     предыдущих календарных месяцев. Активные
     (PLANNED/RUNNING/UPLOADING) и DELETING в отборе не участвуют.
     Счётчики — policy-ключ кластера, дефолт — `PgWorker:Backups:Policy`.
  2. **Guard последнего валидного**: последний COMPLETED-полный шарда не
     удаляется НИКОГДА, даже просроченный по GFS. «Валидный» = COMPLETED
     (verify-статусы t04 на guard НЕ влияют — деградация без t04; после его
     мержа полные с `verify.state=FAILED` — первые кандидаты на удаление,
     но guard «≥1 COMPLETED» держится и над ними: лучше старый невалидный,
     чем никакого).
  3. **Удаление полного**: `DELETING` (journal-before-manipulations) →
     delete объектов префикса `full/<id>/` (§5) → del etcd-ключа.
     transient-отказ S3 → остаётся `DELETING`, следующий проход повторяет
     (идемпотентно). За один проход удаляется ОДИН полный (по старшинству;
     FAILED-verify — вперёд) — тик короткий, backlog выгребается
     последующими проходами. Зависший `DELETING` (возраст > порога панели)
     → warning-алерт `backup-deleting-stuck`.
  4. **Гигиена истории**: FAILED-ключи шарда — держатся последние
     `Retention:KeepFailed` (по `started_unix`), старше — del. Бэкофф
     переснятия t02 не ломается: n = FAILED с последнего COMPLETED ≤
     KeepFailed, а `BaseSec·2^(n−1)` упирается в `MaxSec` задолго до
     границы (при дефолтах — с n≈5).
  5. **Чистка WAL**: сегменты префикса `wal/` СТРОГО ниже стартовой точки
     (`wal_start_segment`) старейшего ОСТАВЛЯЕМОГО COMPLETED-полного
     удаляются — сравнение по позиции (`log·256+seg`) при равном TLI и
     весь TLI ниже стартового, включая `.history` тех TLI (§5). Сам
     стартовый сегмент и всё выше/новее — живут. Полных нет → WAL не
     чистится (нет точки привязки). `chain_start` t03 пересчитывается от
     оставшихся полных автоматически при следующем контроле (list S3 —
     истина): list-префикс укорачивается, старые дыры ниже cutoff
     исчезают.
  Ретенция — ЕДИНСТВЕННЫЙ осознанный удаляющий S3-объектов воркера:
  стоп-семантика/deprovisioning объекты не трогают (R4, §3/§4), reconcile
  сирот — t07. `Backups:Enabled=false` → ретенция no-op (чистки нет,
  копится до включения; зависшие DELETING видит панельный алерт).
- **Хранилище/квота (t06)**: ретенционный проход (расписание то же,
  per-instance) list-ит ВЕСЬ bucket (пагинация; включая чужие/осиротевшие
  префиксы — занятость bucket, не только свои) → `used_bytes` = сумма
  размеров объектов → ключ `/pgworker/backups/storage` (формат — таблица
  выше) при изменении. Реакции автоматикой НЕТ (emergency-чистки, запрета
  новых полных): WARN/CRIT → панельный алерт `backup-storage-quota`,
  действует оператор (расширить квоту / ужать policy).
- **Суточный алерт (t02)**: панель вычисляет по снапшоту префикса —
  правило `backup-full-stale` per-shard: возраст последнего ВАЛИДНОГО
  COMPLETED-полного шарда (t04: `verify.state ≠ FAILED` — OK/PENDING/
  отсутствует; проваленный verify свежестью не считается) >
  `full_max_age_sec` политики кластера (policy-ключ
  отсутствует → панельный дефолт 86400). Пустой префикс кластера (ни
  одного ключа бэкапов — подсистема не включена) — правило молчит, ложных
  алертов на выключенной подсистеме нет. Воркер алертов не пишет — только
  статусы (все алерты панели — вычисления над снапшотом, как остальные
  правила AlertEngine).
- **Алерт невалидного (t04)**: правило `backup-verify-failed` (critical)
  per-shard — в статусе любого COMPLETED-полного `verify.state=FAILED`
  (описание — `verify.error`: провал checksums / дыра цепочки с
  границами); воркер реагирует переснятием (планировщик §2 не считает
  проваленный verify свежестью), действие оператора — разбор по runbook
  (t05). Проверки по политике: `verify.on_create` — сразу после
  COMPLETED, `verify.interval_sec` — периодическая перепроверка каждого
  оставшегося COMPLETED-полного по возрасту `verify.checked_unix`
  (тихая порча/утеря объектов S3).
- **Deprovisioning кластера** (D2, [14-pgworker.md](14-pgworker.md) §5 B)
  чистит etcd-префикс `/pgworker/backups/<C>/` тем же `del --prefix` (и
  убивает бегущие джоб-контейнеры `pgw-backup-full-<C>-*`); объекты
  S3 этим путём НЕ удаляются (данные дороже места; осознанное удаление —
  только ретенция t06 по политике): префикс S3 без
  etcd-владельца = orphan, его видит супервизор (t07: алерт + политика
  возраста/ручной разбор); восстановление удалённого кластера из S3 —
  runbook t05 (симметрия R4 arch/14: воркер не уничтожает потенциально
  ценные данные автоматикой).

## 5. Хранилище S3: layout

Один bucket на установку (`PgWorker:Backups:S3:Bucket`); префиксы
per-cluster/per-shard:

```
s3://<bucket>/<C>/<X>/
  full/<id>/                 # файлы pg_basebackup 1:1
                             #   (вкл. backup_manifest, pg_wal/)
  wal/<segment>              # 000000010000000000000001, …
  wal/00000002.history       # timeline-истории (обязательны)
```

- Ключ объекта = путь файла; `backup_manifest` в корне `full/<id>/` — база
  `pg_verifybackup` (t04: скачивание в staging → verify). Никаких
  tar-обёрток; WAL-сегмент = один объект. Layout одинаков для MinIO и
  облака; регион/endpoint — конфиг.
- **Дублирование WAL (t02, §2)**: закрытые сегменты набора `-X stream`
  полного бэкапа лежат и в `full/<id>/pg_wal/` (1:1 с manifest — база
  verify t04), и копией в `wal/` (общий префикс — стартовая точка цепочки
  t03); перезапись одного и того же сегмента идемпотентна.
- **Ретенционная чистка (t06, §4)**: удаление полного = delete всего
  префикса `full/<id>/` (list + batch-delete, идемпотентно; 404/пустой
  префикс = уже удалён); чистка WAL = delete сегментов `wal/<segment>` со
  позицией (`log·256+seg`) строго ниже стартовой точки старейшего
  оставляемого полного при равном TLI, и всех объектов TLI ниже
  стартового — включая `.history` тех TLI (сегменты их диапазонов
  удалены); стартовый сегмент, `.history` стартового и более новых TLI,
  всё выше/новее — НЕ трогаются.
- **Verify полного (t04, §4)**: две независимые проверки, итог —
  verify-статус полного:
  1. **Checksums** — ephemeral джоб-контейнер
     `pgw-backup-verify-<C>-<X>-<id>` (образ `pgworker-backup`, контракт
     §2, inline-команда от воркера): `mc cp` `full/<id>/` 1:1 в staging →
     `pg_verifybackup` (manifest SHA256, вкл. `pg_wal/` набора) →
     результат stdout result-JSON + exit-код (протокол джоба t02); воркер
     супервизит по детерминированному имени, staging-volume удаляет после
     итога (как t02). Сбой скачивания (S3/сеть/staging) — transient:
     статус остаётся PENDING, ретраи тиками; `pg_verifybackup` ≠ 0 —
     permanent (данные плохие).
  2. **Полнота WAL-цепочки до точки бэкапа** — воркер без скачивания
     сегментов и до запуска джоба: list `wal/` + list `full/<id>/pg_wal/`
     (последний сегмент набора `-X stream` = точка бэкапа) →
     непрерывность от `wal_start_segment` до точки бэкапа (подмножество
     общего gap-детектора §3) + строгий LSN-разбор `.history` при
     TLI-переходах в диапазоне (§3; GET history-объектов — они
     крошечные). Дыра → permanent FAILED c границами, джоб checksums не
     запускается (вердикт уже определён).
  Обе зелёные → `verify.state=OK` + `checked_unix`; любая красная →
  `FAILED` + `error`; verify идемпотентен — vanished-джоб перезапускается
  (PENDING), переснятие полного не требуется.

## 6. Источник, HA-контур и ресурсные лимиты

- **Реплика-источник**: штатно полный бэкап не трогает мастер; fallback на
  мастер — журнал-факт (`role=master`) + I/O одной операции (не потоковой).
  Смерть источника посреди бэкапа → джоб убивается, статус FAILED,
  переснятие (окно/алерты — t02).
- **Слот на мастере**: WAL копится, пока агент не принял; потолок —
  `max_slot_wal_keep_size` (уже в каноне нод,
  [14-pgworker.md](14-pgworker.md) §2.1 P3/P4): смерть агента → WAL в
  пределах лимита → по исчерпании слот инвалидируется PG → цепочка рвётся →
  алерт t03 + переснятие полного (t07). Диск мастера переполнить нельзя.
- **Лимиты джоба/агента**: `PgWorker:Backups:Agent { Cpu, Mem }` →
  `HostConfig.NanoCPUs/Memory` (образец: request_* нод,
  [14-pgworker.md](14-pgworker.md) §2.4 п.4); staging volume — ephemeral с
  квотой `Staging:QuotaBytes` (guard «нет места» → FAILED + алерт, t02):
  квота задана → tmpfs `size=` (жёсткий предел от ядра, ENOSPC
  гарантирован; память хоста — осознанная плата, для больших баз квоту не
  задавать); не задана → named volume на диске docker-хоста (ENOSPC
  ловится реактивно по падению `pg_basebackup`/`mc` → FAILED).
- **Patroni/HA не затрагивается**: бэкапы — сторонние клиенты нод; изменений
  в конфиги нод/HA-контура подсистема не вносит.

## 7. Секреты

- **Per-install, env воркера** (не etcd, не git): `PGW_BACKUP_S3_ENDPOINT`,
  `PGW_BACKUP_S3_REGION` (опц., MinIO не требует), `PGW_BACKUP_S3_BUCKET`,
  `PGW_BACKUP_S3_ACCESS_KEY`, `PGW_BACKUP_S3_SECRET_KEY` — конфиг-биндинг
  `PgWorker:Backups:S3` (группа транспортных секретов
  [14-pgworker.md](14-pgworker.md) §4 п.3); передача агенту/джобу — env
  контейнера (t02/t03).
- **Per-cluster БД-роль** `backup_exec` (LOGIN + REPLICATION): пароль
  per-cluster `/clusters/<C>/backup_password` — по образцу t02-секретов
  (ensure put-if-absent, ротация в общем тикете §9.8, 32 симв
  `[A-Za-z0-9]`); реализация ensure/ротации — t02. Отдельная от
  bucket_mover (иная зона доверия/ротации).
- **pg_hba-гвард** (t02): дефолтный Spilo-pg_hba разрешает replication-соединения
  только роли `standby` — физический WAL-стриминг `pg_basebackup` под
  `backup_exec` отсекается. Гвард G2 (каждый тик) дополняет `pg_hba.conf`
  нод шарда идемпотентной строкой `hostssl replication backup_exec all
  scram-sha-256` (docker-exec; прецедент — patch_hba стенда) + `pg_reload_conf()`;
  строка живёт в PGDATA-volume и переживает рестарты нод.

  джобов t02 и WAL-агентов t03, §2), `Retry { BaseSec=300, MaxSec=3600 }`
  (бэкофф переснятия FAILED, t02), `S3 { AdvertisedEndpoint }` (t03: адрес
  S3 из контейнеров агентов), `Wal { VerifyIntervalSec=30,
  LagMaxSegments=1024, StaleSec=300 }` (t03: период list/контроля цепочки,
  порог отставания в сегментах, порог тишины загрузок), `Retention {
  IntervalSec=600, KeepFailed=20 }` (t06: период ретенционного прохода
  per-shard и число хранимых FAILED-записей на шард), `Quota { Bytes=0,
  WarnPercent=80, CritPercent=90 }` (t06: квота bucket установки для
  ключа/алертов хранилища; `Bytes=0` — квота не задана, пишется только
  `used_bytes`), `Restore { RecoveryTimeoutSec=1800 }` (t05: бюджет
  локального наката WAL restore-джобом — фаза recovering; исчерпание →
  FAILED «target не достигнут»). Валидация старта:
  `Enabled=true` при пустых S3-полях — fail-fast.

## 10. Риски

| Риск | Закрытие |
|---|---|
| Канон зафиксирует детали, которые t02–t07 вскроют иначе (S3-стриминг больших баз, partial-сегменты) | этот документ — живой: корректировки тем же dev-flow через правку канона; spec-скелет задаёт рамку, не микрошаги |
| MinIO — ещё один сервис стенда (порты/ресурсы/зачистка) | фиксированные порты только стенда (9000/9001, не тестов); testcontainers — в t02+ с динамическими портами |
| Компрометация S3-кредов per-install = доступ ко ВСЕМ бэкапам установки | env-секреты вне git/etcd (контур §4 arch/14); отдельный bucket/креды per-install; ротация — перегенерация пакета (как TLS) |
| Слот `pg_receivewal` при смерти агента копит WAL на мастере | потолок `max_slot_wal_keep_size` уже в каноне нод (§2.1 P3/P4) — диск не переполнится; инвалидация слота → алерт t03 → переснятие (t07) |
| Длинные имена `<C>-<X>` ломают имена слота/контейнера | слот — sha1-усечение (§3); имена контейнеров — те же ограничения, что у pgw-нод (существующая практика) |
| Превышение staging-квоты джоба («нет места» — частый сбой бэкапов) | `Staging:QuotaBytes` → tmpfs `size=` (жёсткая квота, ENOSPC от ядра); null → disk-volume с реактивным ENOSPC; оба пути → FAILED + суточный алерт (§6, t02) |
| Протокол джоба (stdout-маркеры фаз/result-JSON) — неявный контракт воркера и образа | маркеры зафиксированы §2 (фазы + result с wal_start_segment/size_bytes); воркер толерантен к незнакомым строкам лога (парсит только свои JSON); смена формата — правкой канона |
| Restore перезатирает данные живого шарда (ошибка оператора) | обязательный `confirm` = имя шарда в API (мисматч → 400); максимум один активный restore на шард; runbook проговаривает необратимость (RPO = точка бэкапа/WAL-цели) |
| PITR-назад (target_time) несшиваем с прежней WAL-цепочкой (новая TLI с меньшими номерами сегментов) | по COMPLETED restore ключ `wal` удаляется → планировщик §2 немедленно переснимает полный → новая цепочка от новой точки (§3.5); старые S3-объекты не трогаются |
| Долгий накат WAL (большая база/длинная цепочка) — restore-джоб часами | бюджет `Restore:RecoveryTimeoutSec` + маркеры фаз в статусе (оператор видит прогресс); резюмов нет — повтор заявки качает заново (осознанная плата plain-механики) |
| `target_time` вне досягаемости цепочки (раньше старта полного / позже конца WAL) | PG завершает recovery ошибкой «target not reached» / ждёт WAL — джоб ловит по бюджету/логу → FAILED с причиной; валидация непрерывности цепочки — заранее (WalChain) |
| S3-endpoint недостижим с docker-хоста источника (джоб грузит из `mc`) | endpoint per-install обязан быть достижим отовсюду (объектное хранилище); стенд — `host.docker.internal:9000` (extra_hosts host-gateway в джобе) |
| Ошибка ретенции удаляет нужный бэкап (баг отбора/чистки) | guard «последний COMPLETED не удаляется никогда»; удаление только через транзитную DELETING-фазу с идемпотентными повторами; отбор/чистка — чистые функции под полным юнит-покрытием; WAL-чистка — строго ниже стартовой точки оставляемых (§4/§5, t06) |
| list всего bucket для `used_bytes` дорог на больших установках | по расписанию `Retention:IntervalSec` per-instance (не каждый тик), list-v2 пагинация; квота 0 → ключ пишется без вердикта; degradation — только свежесть числа (t06) |
| Стоимость verify: скачивание полного из S3 (трафик + staging размером бэкапа) на каждый verify | `interval_sec` по умолчанию 7 дней (не каждый день все полные); staging-квота/лимиты — общие §6; verify-джоб ephemeral — ресурс занят на время проверки |
| Тихая порча/утеря объектов S3 после снятия бэкапа (bit rot, ручное удаление) | периодическая перепроверка `verify.interval_sec` (t04) + алерт `backup-verify-failed`; планировщик не считает проваленный verify свежестью → переснятие |
| Расхождение spec↔arch при будущих правках | arch-правки — всегда первой фазой; ревью plan↔spec по чек-листам dev-flow |
