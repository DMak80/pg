# 19. Подсистема бэкапов шардов: PgWorker-оркестрация (канон) ★

**PgWorker — хозяин бэкапов шардов**: он сам создаёт, ретраит/пересоздаёт,
чистит, сигнализирует в панель. Ноды (Spilo) бэкапами не управляют. Механика:
полные — `pg_basebackup`; online-WAL — СОБСТВЕННЫЙ приёмник воркера
(физическая репликация, COPY-протокол `START_REPLICATION`, подтверждение слота
по факту доставки в S3 — §3); WAL-G/pgBackRest НЕ встраиваются (параллельное
использование оператором не поддерживается и не смешивается). Хранилище —
S3-совместимое объектное (dev-стенд ownS3, прод — любое S3, вкл. облако).

Ключевые свойства:

- **Единый оркестратор** — PgWorker: ВСЕ операции бэкапов (полный, verify,
 restore/drill) исполняет ОДИН И ТОТ ЖЕ процесс WalReceiver ноды — тот же
 процесс стрима WAL: стрим, полный, verify, restore, drill живут В НЁМ
 (фоновые задачи одного Kestrel-приложения, §2/§3.5/§3.6/§5); отдельных
 процессов/контейнеров для операций нет; воркер
 общается с приёмником через etcd (§3) и его HTTP API (§2); ноды остаются
 сторонними серверами для клиентов `pg_basebackup` (§6).
- **Контракт в etcd** — состояния пишутся под `/pgworker/backups/*`; пишет
 префикс PgWorker (держатель клэйма `<C>`), приёмники — свои статус-ключи
 (§4), панель читает (§4).
- **Хранилище — объектное S3** — один bucket на установку, layout
 per-cluster/per-shard, файлы `pg_basebackup` 1:1 (§5); креды per-install —
 только env воркера (§7).
- **Паттерны arch/17** — идемпотентность каждого шага,
 journal-before-manipulations, transient vs permanent-отказы (§1, §4).

Границы (что НЕ входит): UI/алерты панели, управление нодами/HA-контуром
при СОЗДАНИИ бэкапов (полные/WAL — сторонние клиенты нод; restore (§3.5) —
операция пересоздания шарда: демонтаж нод/чистка HA-scope/подъём — выполняется
держателем клэйма `<C>` по команде оператора), файловое том-хранилище
docker-хоста (решение — S3).

## 1. Роль и границы

- **Роль в системе**: защита данных шардированных кластеров (полные +
 WAL), восстановление — единый оркестратор PgWorker.
- **Граница по данным **: подсистема покрывает только
 PG-шарды. Данные Kafka невосстановимы из бэкапов — RPO держится
 RF×minISR (arch/16 §6); экспорт/снапшоты топиков не заводятся.
- **Схема взаимодействия**:

 (§2/§3.5/§3.6/§5)

 ▼ ▼

- **Принципы**: arch-first (этот документ — источник правды подсистемы);

 (идемпотентность каждого шага, journal-before-manipulations, transient vs

 кроме статус-ключей приёмников (§4); S3-креды per-install только env (§7).

## 2. Механика полных бэкапов

- **Инструмент**: `pg_basebackup` (plain-формат, `-X stream`,
 `--checkpoint=fast`, `--manifest-checksums=SHA256`). `fast`, а не `spread`:
 spread берёт давний checkpoint/restartpoint источника — `wal_start_segment`
 из `backup_label` оказывается ниже первого сегмента набора `-X stream`,
 сегменты [wal_start .. набор) не дублируются в `wal/` → verify-полнота от
 wal_start — вечный FAILED → бесконечные пересъёмы без валидного полного;
 fast делает checkpoint на момент старта — wal_start-сегмент входит в набор
 и дублируется, verify-цепь сходится.
- **Исполнитель**: приёмник WalReceiver выбранной ноды — тот же процесс,
 что стримит WAL (§3; программа `walreceiver` supervisord'а образа
 `pgworker-node`, .NET-бинарь self-contained publish'а). PgWorker подаёт
 команду `POST /api/backup/full` `{"id"}` на `http://<имя ноды>:8080`
 (канал `alias:8080` по имени ноды в общей сети воркера и нод; порт
 наружу хоста НЕ публикуется — [14-pgworker.md](14-pgworker.md) §2.1/§2.4),
 статус — `GET /api/backup/full` (404 = операция исчезла — vanished),
 отмена — `POST /api/backup/full/cancel` (best-effort). `pg_basebackup`
 исполняется ЛОКАЛЬНО в контейнере ноды — подключение `127.0.0.1:5432`
 под ролью `backup_exec` (пароль — env `PGPASSWORD` child-процесса, в
 argv НЕ передаётся); серверные бинари PG (нужны restore/verify-операциям
 приёмника, §3.5/§5) несёт образ `pgworker-node`. Тем же процессом
 исполняются node-операции `/api/node/*`: обеспечение pg_hba (§7),
 pg_dump схемы (arch/14 §Move M1), проба данных ноды (arch/14 Д3).
 Статус операции — IMMUTABLE-снимок в памяти приёмника (фазы
 `basebackup|uploading`, `wal_start_segment`, `size_bytes`,
 однострочный `error`); `wal_start_segment` — из `backup_label`,
 `size_bytes` — сумма файлов набора. Staging — каталог
 `<Staging:Dir>/<id>/` в data-volume ноды (дефолт
 `/home/postgres/pgdata/backup-staging`; ENOSPC — реактивный FAILED;
 приёмник чистит staging после исхода и при старте новой операции).
 Upload — .NET `IBackupS3`/`PoolBackupS3` приёмника по write-списку
 СВОЕЙ фактической роли (REST-проба, симметрия стриму §3;
 write-список фиксируется на старте операции — смена роли посреди
 полного её не рвёт). Выбор ноды-источника и node/role-факты
 etcd-статуса — воркер (`ResolveBackupSourceAsync`: sync-standby
 fallback мастер, ниже). Секреты (пароль `backup_exec`, креды пула S3)
 приёмник резолвит сам из etcd — как для стрима (§7); команда несёт
 только `id`. 503 стоп-гейтов операции — `STOPPED`,
 `/pgworker/backups-disabled`, `Backups:Enabled=false`-семантика (§3);
 **`WAL_CHAIN_ERROR` — НЕ гейт операции полного**: POST отвечает 202,
 операция начинается (WAL_CHAIN_ERROR — нарушение цепочки WAL в АРХИВЕ S3,
 НЕ состояние кластера и НЕ свидетельство о данных нод; его единственное
 лечение — пересъём полного, гейтом он блокироваться не может; выбор
 источника пересъёма — штатный, как ниже: sync-standby, fallback мастер;
 замирание стрима при WAL_CHAIN_ERROR (§3) параллельному полному не
 мешает — стрим стоит backpressure'ом, слот держит WAL, полный пишет в
 S3); рестарт приёмника/ноды посреди операции → GET 404 →
 воркер FAILED `operation-vanished` → переснятие новым id (резюмов
 нет). Отдельного контейнера полного нет — cleanup только cancel API
 (воркер чужой процесс убить не может); **etcd пишет ТОЛЬКО воркер**
 (§4), приёмник etcd-контракта полного не знает.
- **Источник**: реплика шарда (sync-standby из Patroni `GET /cluster`:
 member с `state=running`, `role=replica`, sync-статусом);
 реплика недоступна/отстала → fallback на мастер (резолв мастера —
 существующий `ShardEndpoints`, [14-pgworker.md](14-pgworker.md) §5 F).
 Источник фиксируется в etcd-статусе (`node`, `role`).
- **Пайплайн операции** (фоновая Task процесса приёмника, параллельно
 стриму; резюмов нет — FAILED → переснятие новым id): чистка staging →
 `pg_basebackup -D <staging>/<id>/full` (подключение `127.0.0.1:5432`,
 `-X stream --checkpoint=fast --manifest-checksums=SHA256`) →
 `wal_start_segment` из `backup_label` → загрузка в S3 .NET-клиентом
 файлами 1:1 (включая `backup_manifest` и `pg_wal/`).
 **Загрузка в пул S3**: write-список endpoints приёмник резолвит по СВОЕЙ
 фактической роли (REST-проба Patroni loopback, §3: реплика →
 `write_replica`, мастер → `write_master`, §4); перебор списка —
 per-попыточный таймаут, circuit-breaker 45 с (§5); «быстрый отказ/успех,
 не молчание» — R3, arch/23 §7; переливка идемпотентна — имена объектов
 детерминированы; исчерпание списка → FAILED с маркером
 `s3-pool-exhausted` в `error` (алерт панели `backup-pool-unreachable`,
 обычный бэкофф переснятия). Фазы операции приёмник отдаёт GET-статусом
 (`running/basebackup` → `uploading/uploading` → `succeeded`/`failed` +
 однострочный `error`); воркер поллит GET тиками, отражает фазы в
 etcd-статусе и по итогу операции фиксирует исход — **etcd пишет
 ТОЛЬКО воркер** (§4). Отмена (cancel API) — приёмник гасит дерево
 текущего child-процесса, операция завершается `failed` с причиной
 `cancelled`, staging чистится; гейт-команда на СТАРТЕ (503) идущую
 операцию не рвёт — отменяют только cancel и бюджет воркера.
- **WAL набора `-X stream`**: файлы бэкапа грузятся строго 1:1 в
 `full/<id>/` ВКЛЮЧАЯ `pg_wal/` (база `pg_verifybackup`, manifest
 перечисляет и WAL-файлы); ЗАТЕМ закрытые сегменты этого набора
 дублируются в общий WAL-префикс `wal/` шарда ПОД НОРМАЛИЗОВАННЫМ
 (СТРОЧНЫМ) именем (pg_basebackup кладёт сегменты набора ВЕРХНИМ hex —
 имя дубля нормализуется при заливке): канон ключей `wal/` — строчные
 (симметрия стриму приёмников и fetch-wal §3.5), дубль сливается со
 стримом — дублирования объектов нет. Дублирование осознанное — снимает
 конфликт «layout vs общий префикс», закрытый сегмент = один объект,
 перезапись идемпотентна.
- **Идентификатор**: `id = YYYYMMDDHHMMSSZ` (UTC старта, сортируемый);
 коллизия в пределах шарда — суффикс `-2`, `-3`…; детерминизм имён — как у
 `pgw-<C>-<X>-<n>` ([14-pgworker.md](14-pgworker.md) §6).
- **Подключение**: `pg_basebackup` — всегда `127.0.0.1:5432` своей ноды
 (приёмник живёт в контейнере ноды — сеть источника не нужна; БД-роль —
 §7). Канал команды/статуса — `alias:8080` по имени ноды в общей сети
 воркера и нод (инвариант поставки: контейнеры воркера и нод всегда в
 одной сети — контур или per-cluster сеть развёртывания,
 [14-pgworker.md](14-pgworker.md) §2.4; недостижимость alias — transient
 тика воркера с journal-фактом адреса, НЕ краш тика); адресация S3
 приёмника — та же, что у стрима (§5/§7).
- **Планировщик (rolling)**: воркер тиками под клэймом `<C>` для
 каждого шарда Active-кластера с `dsn`: возраст последнего ВАЛИДНОГО
 COMPLETED-полного (`verify.state ≠ FAILED` — OK, PENDING «идёт»
 или verify отсутствует; полный с проваленным verify свежестью НЕ
 считается) > `full_max_age_sec` **или валидного COMPLETED-полного нет
 вовсе** (инвариант «поднятый шард всегда имеет валидную цепочку или
 свежий полный»: цепочку контроль (§3) заведёт от `wal_start_segment`
 свежего COMPLETED, когда приёмники донесут ПЕРВЫЙ ЗАКРЫТЫЙ сегмент —
 приёмник выгружает только закрытые сегменты, поэтому на шарде
 без нагрузки ключ `wal` появляется позже первого полного, и пересъём
 в этом окне бессмыслен: серия полных подряд ничего не добавляет;
 сброс цепочки restore'ом покрыт гвардом «полный не старее последней
 COMPLETED-restore», разрыв — WAL_CHAIN_ERROR-гвардом ниже)
 **или wal-ключ шарда в `WAL_CHAIN_ERROR`** (разрыв цепочки — пересъём
 безусловно, инвариант «у живого шарда валидная цепочка или активный
 полный»; бэкофф серии FAILED работает как всегда — шторм пересъёмов
 исключён; исключение не работает для УСПЕШНЫХ
 пересъёмов — COMPLETED не включает бэкофф, и при живом
 WAL_CHAIN_ERROR-ключе
 полный планировался заново каждый тик (12 пересъёмов за 2 мин), отодвигая
 заживление. Правило покрытия: WAL_CHAIN_ERROR-пересъём планируется только пока
 НЕТ COMPLETED-полного с `wal_start_segment` ≥ границы разрыва
 (`chain_start_segment` WAL_CHAIN_ERROR-записи) — такой полный уже покрывает разрыв,
 контроль (§3) заживит им очередным тиком; не покрывший полный
 (FAILED, либо старт ниже границы) — пересъём снова, по общим правилам)
 **или живой непокрытый `gap` в wal-ключе** (tli-зазор приёмника §3 —
 пересъём безусловно, симметрично WAL_CHAIN_ERROR-правилу покрытия: покрывший
 COMPLETED-полный ждёт снятия метки контролем; непокрывший — пересъём
 снова; инвариант одного активного и бэкофф FAILED работают как всегда) →
 создать `full/<id>` (PLANNED → API-запуск на приёмнике → RUNNING); инвариант —
 максимум один активный (PLANNED/RUNNING/UPLOADING) полный на шард
 одновременно. Бэкофф `min(Retry.BaseSec·2^(n−1), Retry.MaxSec)`, где n —
 число попыток с момента последнего валидного COMPLETED шарда: FAILED
 операции + verify-FAILED + НЕпокрывшие COMPLETED (wal_start ниже живой
 границы разрыва — антишторм: пока redo/restart-точка источника не перешла
 границу, повторный полный снимается с той же позиции — без пользы (без этого
 правила открытый планировщику gap давал полный каждые ~10 с) — вычислимо из истории ключей, дополнительных полей
 контракта не требуется. Пересъём при живой непокрытой границе
 ПРЕДВАРЯЕТСЯ `CHECKPOINT` НА МАСТЕРЕ шарда (пересъём — следующий тик,
 без гонки за replay): `pg_basebackup` пишет в `backup_label` START WAL с
 redo/restart-точки источника; restartpoint реплики движется ТОЛЬКО по
 checkpoint-записям мастера, а idle-мастер их не пишет — точка стоит в
 сегменте ДО границы зазора, и пересъём снимался бы с той же позиции
 бесконечно (CHECKPOINT на самой реплике — restartpoint по старой
 checkpoint-записи — точку НЕ двигает);
 checkpoint-запись мастера реплика replay'ит, точка переносится в текущий
 сегмент — следующий полный получает `wal_start ≥ границы` и покрывает
 зазор.
 Лимита попыток
 нет: порог «долго без валидного» — суточный алерт панели (§4). Takeover:
 всё состояние в etcd, адрес приёмника детерминирован (`alias:8080` по
 имени ноды) — новый инстанс продолжает супервизить; RUNNING-статус при
 GET 404 → FAILED `operation-vanished` (рестарт приёмника/ноды;
 переснятие по общему правилу).
- **Наблюдаемость итога verify**: итог проверки каждого полного — OK/FAILED +
 причина (`verify.error`, §4/§5) — воркер фиксирует и строкой собственного
 журнала (host-лог), в дополнение к verify-статусу etcd-ключа: исходы verify
 обязаны быть наблюдаемы из журнала воркера — etcd-ключи префикса чистятся
 deprovisioning'ом (D2), журнал остаётся летописью после факта. Порядок
 фиксации: сначала etcd-статус, затем journal-фаза, затем строка host-лога —
 отказ journal-фазы строку НЕ отменяет: итог уже зафиксирован в etcd-ключе,
 а повторного терминального исхода тот же полный не порождает.

## 3. Online-WAL: собственный приёмник — двойная архивация (мастер + sync-реплика)

- **Агент**: процесс-приёмник ВНУТРИ контейнера КАЖДОЙ ноды шарда
 (программа `walreceiver` supervisord'а образа `pgworker-node`,
 [14-pgworker.md](14-pgworker.md) §2.1; приёмник живёт во всех нодах,
 стримят — только ноды-источники). Внутри — собственный .NET-приёмник:
 физическая репликация (COPY-протокол `START_REPLICATION ... PHYSICAL` по
 слоту, источник — `127.0.0.1:5432` своей ноды), приём XLogData,
 сборка сегментов в памяти (буфер текущего незакрытого сегмента размером
 `wal_segment_size`), при закрытии сегмента — put объекта `wal/<segment>`
 (ключ = имя сегмента); `.history`-файлы ЗАГРУЖАЮТСЯ обязательно (PITR через
 смену timeline); `.partial`-семантики нет вовсе (незакрытый сегмент живёт
 только в памяти и не подтверждается). Staging-ТОМ ОТСУТСТВУЕТ: локальный
 буфер — кэш без гарантий durability; всё неподтверждённое перезаказывается
 у источника (инвариант ниже), терять нечего. **Идентичность**: при старте
 приёмник знает только своё имя кластера/шарда/ноды (env контейнера ноды
 `PGW_BACKUP_CLUSTER/SHARD/NODE`, пишет EnsureNode) и адреса etcd (`PGW_ETCD`);
 ВСЁ «куда бэкапиться» резолвит сам из etcd: роль источника → S3-список
 (`write_master`/`write_replica` policy §4 + адреса/креды пула §7 — тот же
 резолв, что у воркера), креды подключения (`/clusters/<C>/backup_password`,
 роль `backup_exec` §7), имя слота (детерминизм §3 ниже); bucket per-install —
 env ноды (`PGW_BACKUP_S3_BUCKET`; CA https — `PGW_BACKUP_S3_CA_PEM`, §7).
 **Роль источника**: приёмник опрашивает свой Patroni REST loopback
 (`https://127.0.0.1:8008/primary`, `/sync` — прецедент lease-скрипта
 pgwnodetool; CA — REST-CA ноды): primary → write-список `write_master`,
 sync-standby → `write_replica`; прочее (async-реплика, переходное окно) —
 приёмник НЕ стримит (ожидание, периодический опрос роли). Смена ролей
 (failover/promote) подхватывается самим приёмником — пересоздание
 контейнеров воркером не выполняется. Приёмник пишет на первую доступную
 ноду write-списка и перебирает при отказе текущей (per-попыточный таймаут
 уже в S3-клиенте приёмника); исчерпание списка — ретрай-цикл (стрим стоит,
 backpressure, слот держит — RPO-инвариант ниже не меняется) + флаг
 `pool_exhausted` в своём статус-ключе (контроль ставит маркер
 `s3-pool-exhausted` в `error` DEGRADED-статуса — алерт панели
 `backup-pool-unreachable`; успешная put после исчерпания флаг снимает).
 Флаг — факт СЕССИИ стрима, а не вечный ярлык: на границе сессии
 (новая итерация цикла приёмника — смена роли, reconnect) факт
 перепубликуется фактическим состоянием новой сессии — исчерпания нет;
 при живом исчерпании факт возвращается первым же неудачным put. Иначе
 на idle-источнике (промоут без записи — put'ов нет) «снятый первым
 успешным put» не наступает никогда, и здоровый пул держит шард в
 DEGRADED неограниченно.
 **Надзор**: процесс живёт под supervisord'ом ноды (autorestart при падении);
 приёмник НЕ завершается при отказах — permanent-условия (несовместимый
 `wal_segment_size`, разрыв LSN протокола, невалидный env) — СОСТОЯНИЕ
 статус-ключа (`state=failed_permanent`, причина в `error`), не exit-код:
 воркер не может перезапустить процесс чужого контейнера, перезапуск
 permanent-причины не лечит — лечение за воркером/оператором (см. ниже).
 Отсутствие слота/кредов/policy — ожидание (retry-цикл, слот ensure'ит
 воркер — см. ниже), НЕ permanent. **Стоп-семантика приёмника** (всё через
 etcd, воркер контейнер ноды не трогает): глобальный ключ
 `/pgworker/backups-disabled` (жив ⇒ `Backups:Enabled=false` — приёмник
 замирает; пишет/стирает воркер, §4), wal-ключ шарда `STOPPED` (карантин,
 стоп-семантика §4) или `WAL_CHAIN_ERROR` (разрыв — приёмник замирает,
 лечение пересъёмом §2) ⇒ пауза стрима; `ACTIVE/DEGRADED`/отсутствие
 ключа ⇒ работает. Резюме запуска: при старте стрима приёмник резолвит хвост S3
 read-списком (§3 «Возобновление») и слот на своей ноде.
- **Инвариант подтверждения-по-доставке (RPO)**: приёмник подтверждает слот
 (standby status update: write/flush = конец последнего ДОСТАВЛЕННОГО в S3
 закрытого сегмента) ТОЛЬКО после успешного put объекта — `restart_lsn`
 слота никогда не уходит за доставленный в S3 хвост. Пока S3 недоступен —
 приёмник останавливает чтение потока (сервер сам ждёт подтверждения),
 ничего не теряется: неподтверждённое удерживается слотом на источнике.
 Любой рестарт приёмника (падение процесса/supervisord-рестарт, смена роли
 источника, потеря docker-хоста в multi-host) возобновляет стрим ОТ ХВОСТА
 S3 и досыпает дыру из удерживаемого слотом WAL — staging-потеря
 невозможна по построению (тома нет, неподтверждённое не удалялось из
 источника).
- **Возобновление**: старт/переподключение приёмника — от хвоста S3:
 list `wal/` с первой доступной ноды read-списка (инвентарь-листинг —
 первая доступная нода; перечитка сегментов выше хвоста идемпотентна
 по имени) → последний сегмент цепочки → стартовая LSN = его конец
 (граница закрытого сегмента; позиция передаётся в START_REPLICATION
 явно). Пустой префикс (первый старт) — от `restart_lsn` слота
 (immediate+reserved держит текущую позицию; цепочка закрепится первым
 upload). `restart_lsn` для старта ПОСЛЕ первого сегмента не используется
 — слот выполняет только функцию удержания WAL.
- **58P01 tli-переход**: при отказе старта стрима 58P01 (хвост S3 ниже точки
 форка текущего таймлайна сервера — запрошенный сегмент под именем нового
 TLI никогда не существовал) приёмник выполняет tli-процедуру:
 `IDENTIFY_SYSTEM` → (T, xlogpos); при T > TLI хвоста: `.history` T грузится
 немедленно, ДО досыпки, затем досыпка — `START_REPLICATION … TIMELINE <TLI
 хвоста>` от хвоста до точки переключения на СВЕЖЕМ replication-соединении
 (отказ старта гасит прежнее — процедура открывает своё; CopyDone →
 переподключение от выросшего хвоста, зазора нет, RPO=0; повторный 58P01 на
 досыпке — сегменты срезаны) → прыжок-fallback: старт на текущем T от
 границы сегмента, содержащего xlogpos; сегменты (хвост .. старт] в S3 не
 появятся — осознанный RPO-зазор; факты tli-процедуры
 (`tli_backfill`/`tli_jump`) — в статус-ключе приёмника (§4; контроль
 воркера по факту `tli_jump` ставит поле `gap` ключа `wal`); инвариант
 подтверждения-по-доставке не меняется; гонки повторного промоута —
 конвергентны (каждая итерация с IDENTIFY_SYSTEM, счётчиков нет).
- **Двойная архивация (избыточность источника)**: инвариант нод
 `synchronous_mode=true` (arch/05): WAL подтверждённого изменения
 физически лежит в `pg_wal` ОБЕИХ нод (мастер + sync-standby). Стримят
 приёмники ДВУХ нод-источников — мастера и sync-standby (приёмник сам
 узнаёт роль REST-пробой своей ноды, §3 «Агент»); оба пишут в ОДИН
 префикс `wal/` шарда: имена сегментов детерминированы (одинаковый WAL
 обеих нод), put идемпотентен — дедупликация не нужна; контроль
 непрерывности (ниже) склеивает union без изменений (union-листинг `wal/`
 по всем нодам пула с дедупом — §3 «Истина прогресса», §5). Дыра возможна
 только при потере одного и того же сегмента ОБИМИ приёмниками —
 рестарты приёмников независимы, а с подтверждением-по-доставке
 рестарт сегменты не теряет вовсе (защита детерминированная).
 Нет sync-standby (переходное окно failover, single-нода) — стримит
 один приёмник (мастер); приёмник новой sync-реплики включается сам при
 появлении роли (REST-проба, симметрия §2 fallback). Цена: ×2
 стрим-трафик, ×2 буфер сегмента (память приёмников, §6). Граница RPO:
 WAL после последнего sync-подтверждения физически есть только на
 мастере — незакоммиченные транзакции, вне гарантий durable.
- **`.history` при TLI-переходе**: приёмник, наблюдая первый сегмент нового
 TLI, запрашивает history-файл у сервера (команда протокола
 `TIMELINE_HISTORY`) и выгружает объект `wal/<TLI>.history`. Если рантайм
 репликации не экспонирует запрос — приёмник читает файл
 `pg_wal/<TLI>.history` ФАЙЛОВОЙ СИСТЕМЫ своей ноды (приёмник живёт в
 контейнере ноды, доступ к PGDATA есть) и грузит его; недоступен и файл —
 факт `history_missing` в статус-ключе (диагностика; воркер ничего не
 докладывает). При tli-процедуре (58P01) `.history` нового TLI грузится
 приёмником немедленно при детекте перехода (до досыпки) тем же порядком.
 Переход, случившийся вне окна стрима приёмника (промоут, пока нода не
 стримила), приёмник не наблюдает — его закрывает РЕ-ДОКЛАД ИНВЕНТАРЯ
 history: при (ре)старте стрима и далее раз за цикл подключения приёмник
 перечисляет `.history`-файлы `pg_wal` своей ноды и кладёт в `wal/`
 отсутствующие (list read-списком, put идемпотентен — та же ФС ноды и тот
 же канал, что и стрим-доклад; выполняется вне hot-path, отказ put —
 diagnostic-log, следующий цикл повторяет). После промоута файл
 `000000NN.history` лежит в `pg_wal` нового мастера, после restore — в
 pgdata восстановленной ноды: переход вне окна стрима доезжает от любой
 ноды, физически содержащей файл; нода без файла — прежний факт
 `history_missing`. Новых etcd-ключей и docker-операций ре-доклад не
 вводит, контроль воркера не меняется. Склейка TLI-переходов в контроле
 уже поддержана (WalChain, LSN-разбор history — verify §5).
- **Слот**: per-instance, имя `pgw_bkp_<C>_<X>` ОДНО И ТО ЖЕ на каждой
 ноде-источнике (слоты разных PG-инстансов независимы — конфликтов нет);
 длиннее NAMEDATALEN(63) → `pgw_bkp_` + sha1(`<C>/<X>`)[:16]. Слоты
 создаёт воркер (SQL ensure идемпотентно: `pg_replication_slots` →
 `pg_create_physical_replication_slot(..., true)`) на КАЖДОЙ
 ноде-источнике (мастер + sync-standby) — удержание WAL на случай
 переключения/потери второй стороны. Зонд слота источника —
 существование И `wal_status`: существующий lost-слот лечится recreate
 (drop+create immediate+reserved), а не пропускается
 ensure-идемпотентностью — стрим через инвалидированный слот PG
 отвергает, «слот есть» ≠ «слот работает». Подключение — роль `backup_exec`
 (§7): ключ `/clusters/<C>/backup_password` отсутствует (ensure не прошёл)
 → приёмник в ожидании (`waiting_password`), стрима нет.
- **Подключение**: приёмник подключается к источнику через
 `127.0.0.1:5432` своей ноды (приёмник живёт в контейнере ноды —
 сеть для стрима не нужна; нода усыновлена без приёмника внутри —
 WAL-архивация с неё невозможна, ошибка конфигурации контура). Смена
 мастера/смена sync-standby подхватывается самими приёмниками
 (REST-проба роли, §3 «Агент»; write-список перечитывается по факту
 роли): догон цепочки от хвоста S3, склейка timeline через `.history`
 (контроль уже понимает — WalChain). Promote реплики: физический слот
 при promote сохраняется, приёмник продолжает от хвоста S3 уже новой TLI
 (риск-таблица §10). Креды/цели не «протухают» — приёмник резолвит их
 заново на каждом цикле подключения (ротация паролей/смена policy
 подхватываются без пересоздания чего-либо).
- **Истина прогресса — S3**: приёмник пишет объекты в S3 (сегменты,
 `.history`) и свой статус-ключ (§4) — и ничего больше; воркер с периодом
 `Wal:VerifyIntervalSec` выполняет контроль цепочки — union-листинг
 префикса `wal/` по ВСЕМ нодам пула с дедупом по имени объекта (ложная
 дыра на отстающей ноде исключена; успех — при ответе хотя бы одной
 ноды, исчерпание — маркер, §5) — и по факту объектов вычисляет
 `last_uploaded`, непрерывность цепочки и пишет etcd-ключ `wal` (§4;
 статус-ключи приёмников воркер только читает; «последний загруженный»
 из статуса приёмника НЕ используется — один источник истины, объекты).
- **Правила непрерывности** (инвариант §4, детали): имя сегмента — 24 hex
 символа `TLI(8)+log(8)+seg(8)`; следующий = `seg+1`, при `seg=0xFF` →
 `log+1, seg=0`; переход timeline валиден при наличии загруженного
 `<newTLI>.history` и первом сегменте нового TLI, равном последнему
 сегменту старого TLI ИЛИ следующему за ним (точка переключения внутри
 сегмента — PG перезаписывает сегмент с нового TLI); полный LSN-разбор
 history — verify (§5): воркер скачивает `.history`-объекты из
 `wal/` и валидирует TLI-переходы по точке переключения из файла
 (`switchWALLSN` в границах сегмента первого сегмента нового TLI);
 runtime-контроль потока (этот §) остаётся на эвристике номеров. Цепочка проверяется от `chain_start_segment`: стартовая
 точка = `wal_start_segment` новейшего (по `started_unix`) COMPLETED-
 полного с `verify.state=OK` из оставляемых — точка cutoff WAL-чистки
 ретенции (§4 п.5). Ложный WAL_CHAIN_ERROR даёт расщепление точек только В ОДНУ
 сторону — контроль НИЖЕ cutoff (стартующий от срезанных сегментов видит
 дыру); обратное расщепление переходного окна (контроль выше cutoff —
 якорится на кандидате удаления текущего прохода, когда новейший
 оставляемый OK-полный ниже) безопасно: нижележащий cutoff режет меньше.
 verify-OK-полного нет →
 первый сегмент потока приёмников (закрепляется в статусе при первом
 upload). Ретенция чистит сегменты ниже этой точки — `chain_start`
 поднимается автоматически при следующем контроле (list S3 — истина),
 list-префикс укорачивается.
 Дыра (нет next-сегмента / TLI-переход без history) и исчезновение ИЛИ
 инвалидация (`wal_status='lost'`) слотов ВСЕХ нод-источников при
 живой цепочке (per-instance, §3) → `WAL_CHAIN_ERROR`
 : permanent-деградация разрыва, приёмники шарда замирают (стоп-семантика
 приёмника — §3 «Агент»), лечение — НОВЫЙ полный бэкап (планировщик §2
 реагирует на WAL_CHAIN_ERROR пересъёмом); `error` несёт границы разрыва.
 Сегменты между хвостом S3 и точкой старта прыжка tli-процедуры (58P01,
 выше) в S3 не появятся — осознанный RPO-зазор. Зазор на TLI-границе —
 НЕ WAL_CHAIN_ERROR (CheckWithRestart склеивает цепочку от максимального TLI):
 он живёт полем `gap` ключа `wal` (§4) + форсированным пересъёмом полного
 (приёмники архивации не замирают); зазор внутри одного TLI — обычная
 дыра → существующий WAL_CHAIN_ERROR-путь. `DEGRADED` — только
 transient-деградации (lag/тишина): приёмник жив, ретраи тиками, пересъём НЕ
 триггерит; `error` DEGRADED несёт маркер `s3-pool-exhausted`, когда
 статус-ключ мастер-приёмника несёт живой флаг `pool_exhausted`
 (§3 — алерт `backup-pool-unreachable`; «lag/тишина» без маркера — обычное
 отставание). Флаг держит приёмник: ставит при исчерпании write-списка,
 снимает первым успешным put ЛИБО границей сессии стрима (новая сессия
 публикует флаг фактическим состоянием — без исчерпания; при живом
 исчерпании первый же неудачный put ставит его снова, §3 «Агент») —
 контроль читает как факт, позиционных
 эвристик нет; снятие флага — статус пересчитывается общим порядком
 (цепочка/lag/тишина), `error` очищается. Exhaustion-DEGRADED (DEGRADED с
 маркером в `error`) — контроль
 КАЖДЫЙ тик, как WAL_CHAIN_ERROR (скорость заживления; union-листинг — один класс
 вызовов). Слот при WAL_CHAIN_ERROR: жив (не lost) — не трогаем (копит WAL в
 пределах `max_slot_wal_keep_size`), исчез или lost — пересоздаётся
 immediate+reserved СРАЗУ ЖЕ (drop+create; к старту пересъёма полного
 слот держит позицию ≤ wal_start нового
 полного; механика первого старта). Инвалидация (lost) ОДНОГО
 источника при живом слоте второго — НЕ WAL_CHAIN_ERROR: lost-слот функционально
 отсутствует (стрим через него PG отвергает, нужные слоту сегменты
 срезаны) — воркер пересоздаёт его автоматически (journal-факт);
 потерянный источник возвращается сам: приёмник ретраит от хвоста S3,
 хвост достраивает второй приёмник двойной архивации (префикс `wal/` один,
 put идемпотентен), старт успешен, когда следующий за хвостом сегмент
 существует на его ноде (срез ниже не идёт, горизонт удаления
 поднимается записью). lost на всех источниках → WAL_CHAIN_ERROR-путь выше
 (пересъём полного; оба приёмника возвращаются от wal_start нового
 полного). Пустой префикс `wal/` + lost — тот же recreate: свежий слот
 immediate+reserved держит текущую позицию, приёмник стартует от неё. Инвариант записи при «слот исчез»
 : `last_uploaded_unix` в живом (ACTIVE/DEGRADED) ключе обязан
 существовать (гварды парсеров — первая линия); при нарушении (ручная
 правка/будущий писатель при ослабленном гварде — прецедент ed1561b)
 ветка не крашится тиком: defensive-фолбэк времени (clock-сейчас) —
 только defensive-значение параметра расчёта, в WAL_CHAIN_ERROR-запись now не
 попадает (запись строится из живого ключа), битый ключ маркируется
 journal-заметкой `wal-key-invalid/<X>`; WAL_CHAIN_ERROR/пересоздание слота
 работают как обычно. Ratchet `chain_start_segment`:
 записанное значение НИКОГДА не понижается; в WAL_CHAIN_ERROR-записи — граница
 разрыва (последний непрерывный сегмент контроля; для «слот исчез» —
 `last_uploaded_segment` на момент обнаружения). При контроле цепочки
 стартовая точка = wal_start_segment новейшего (по started_unix) COMPLETED-
 полного с `verify.state=OK` и wal_start ≥ записанного chain_start
 (ratchet не понижается) — кандидаты ниже границы разрыва игнорируются
 для контроля (их цепь до их точки может быть цела; дыра выше).
 Контроль при WAL_CHAIN_ERROR — каждый тик (без VerifyIntervalSec-расчёта:
 скорость заживления; list дырного префикса дёшев); появился COMPLETED-
 полный со стартом ≥ границы и цепь от него непрерывна → `ACTIVE`,
 приёмники возобновляют стрим этим же тиком (стоп-семантика приёмника).
 Restore COMPLETED удаляет wal-ключ целиком
 ratchet сбрасывается вместе с ключом, противоречий нет.
 `wal/<segment>` после дыры до переснятия НЕ
 загружаются приёмником заново (слот держит позицию; цепь восстанавливает
 новый полный + новый поток).
- **Отставание**: `lag_segments` = сегмент текущей позиции записи мастера
 (SQL-зонд `pg_current_wal_lsn` → имя сегмента; подключение —
 admin-DSN мастера, существующие билдеры) − `last_uploaded`;
 `lag_segments > Wal:LagMaxSegments` или возраст `last_uploaded_unix`
 > `Wal:StaleSec` при живом кластере → `DEGRADED` + `error` (transient:
 ретраи тиками; постоянное отставание без прогресса — алерт панели).
- **Стоп-семантика**: `Backups:Enabled=false` → воркер ставит глобальный
 ключ `/pgworker/backups-disabled` (§4) — приёмники кластеров замирают;
 демонтаж шарда (S-процессы) и deprovisioning кластера (D1) сносят
 контейнеры нод — приёмники уходят вместе с нодами (отдельных сущностей
 нет, staging-томов нет); etcd-ключи
 кластера чистит Deprovisioning D2 (`del --prefix /pgworker/backups/<C>/`,
 arch/14 §5 B). `STOPPED` — воркер сознательно остановил WAL-поток живого
 шарда записью wal-ключа (шард QUARANTINED/эвакуация — поток WAL мёртвого
 шарда не нужен; приёмники замирают по стоп-семантике приёмника);
 демонтаж ключи удаляет. Этими путями S3-объекты не удаляются
 (§4, R4-симметрия; единственный осознанный удаляющий объектов —
 ретенция).

## 3.5. Восстановление шарда из бэкапа: PITR

- **Операция**: восстановление ОДНОГО шарда `<X>` кластера `<C>` из
 `full/<id>` + накат WAL-цепочки до цели: `latest` (конец цепочки — полная
 потеря шарда/DR) или `target_time` (порча данных, откат к
 моменту до порчи). Запуск — команда оператора через HTTP API воркера
 (`POST /api/clusters/<C>/shards/<X>/restore`,
 [14-pgworker.md](14-pgworker.md) §1.1): тело задаёт `backup_id` (нет —
 новейший COMPLETED/list-S3), цель, `source` (S3-префикс источника;
 default — собственный `<C>/<X>`; DR: префикс погибшего кластера —
 восстанавливаем в пересозданный кластер) и `confirm` = имя шарда
 (перезапись данных осознана, мисматч → 400). Воркер валидирует и сам
 пишет заявку-статус в etcd (§4); отображение статуса restore
 (state/phase/error бейджем в деталях шарда) — грань панели
 ([adminpanel/03](adminpanel/03-panels.md) §3); ЗАПУСК restore — команда
 оператора в HTTP API воркера по runbook (runbook backup-restore.md),
 из UI панель restore не запускает. Одна активная заявка на шард
 (повтор при активной → 409). Потеря ОДНОЙ ноды живого шарда restore'ом НЕ
 чинится (Patroni rebuild быстрее — runbook отсылает к
 recreate-эндпоинту).
- **Restore-операция WalReceiver ноды**: операцию исполняет WalReceiver
 ПЕРВОЙ ноды шарда (`pgw-<C>-<X>-<n1>`) — тот же единственный процесс ноды,
 что стримит WAL и снимает полные (§2/§3); отдельных процессов для операций
 нет. Ход: демонтаж нод шарда (ниже) → воркер поднимает первую ноду штатным
 EnsureNode на НОВОМ пустом data-volume (щит `initialize="restore-in-progress"`
 удерживает Patroni от bootstrap пустого PGDATA — постгрес Patroni не
 поднимает, PGDATA ноды свободен; WalReceiver ноды не стримит — роли нет,
 live в `waiting_role`) → `POST /api/ops/restore` на `http://<нода>:8080`
 (тело: `backup_id`, `target_time`? — PG-совместимый формат
 `yyyy-MM-dd HH:mm:sszzz` (воркер разбирает RFC3339 заявки и нормализует —
 parser postgres не принимает «T»-сепаратор/суффикс «Z»; `target_time`
 отсутствует = latest), `recovery_timeout_sec`, S3-контекст) и
 `GET /api/ops/restore` (фазы `downloading|recovering`,
 `restored_to_lsn`?, `system_id`?, `started_unix`?, `error`?). PGDATA
 операции — PGDATA САМОЙ ноды (`/home/postgres/pgdata/pgroot/data`,
 Spilo-layout, uid:gid `101:101`); volume ноды в этот момент пуст. Механика
 восстановления — WalReceiver (.NET, child-процессы PG-утилит
 `Process.Start`; WalReceiver ноды работает под `postgres` (uid 101) —
 файлы скачиваются сразу нужным владельцем: chown недоступен и не нужен,
 `chmod 700` PGDATA делает владелец):
 (1) скачивание `full/<id>/` файлами 1:1 .NET S3-клиентом в PGDATA;
 (2) `restore_command = '/opt/pgw-wal/walreceiver fetch-wal %f %p'` —
 sub-режим того же бинаря (S3-контекст — env процесса postgres,
 секреты не в argv): скачивает сегмент/`.history` из `wal/` префикса S3
 прямо в запрошенный путь; объекта нет → ненулевой exit — конец WAL;
 транспортные попытки fetch-wal — БЫСТРЫЕ и под ЖЁСТКИМ общим дедлайном
 вызова: внутренние ретраи S3-клиента на транспорт выключены (ретраит
 сам fetch-wal, ограниченно), и вызов в любом исходе укладывается в
 секунды. Без этого мёртвая/недостижимая нода пула растягивает КАЖДЫЙ
 вызов restore_command на минуты, целевое восстановление не доходит до
 «исчерпание архива → promote» в бюджете операции (restore висит
 в recovering до сноса). Длительные моргания сети покрываются
 повторными вызовами restore_command самим postgres'ом — их не
 компенсируют долгие ретраи внутри одного вызова;
 имя из `%f` postgres передаёт ВЕРХНИМ hex, а объекты `wal/` строчные —
 fetch-wal нормализует регистр, иначе первый буквенный сегмент даёт
 ложный 404 и обрывает recovery до цели; + `postgresql.auto.conf`
 override-строки: `data_directory`/`hba_file`/`ident_file`,
 `wal_level=replica`, `summarize_wal=off`,
 `shared_preload_libraries=''`, `ssl=off`, `logging_collector=off`,
 recovery-параметры (`recovery_target_time` при цели time,
 `recovery_target_action=promote`; цель latest — БЕЗ target: конец WAL =
 promote); pristine `auto.conf` приберегается в `.orig` и возвращается
 после promote, из него вычищаются управляющие Patroni параметры
 архивации (`archive_mode`/`archive_command`): pristine снят
 `pg_basebackup`-ом с ноды-источника и несёт её `archive_mode`, а
 Patroni нового HA-scope навязывает свой → reload для `archive_mode`
 недостаточен → «Pending restart» → отложенный рестарт postmaster рвёт
 соединения клиентов сразу после restore; WAL-архивация системы —
 приёмник WAL внутри нод, `archive_mode` постгреса не используется;
 (3) инцидентные правки: `standby.signal` удаляется → создаётся пустой
 `recovery.signal` (pristine-набор снят `pg_basebackup`-ом со
 standby-источника — §2: приоритет sync-реплики — и несёт его
 `standby.signal`; не убрав, postgres стартует standby-режимом и
 бесконечно ждёт WAL из restore_command, не входя в recovery);
 `standby.signal` удаляется ПОВТОРНО НЕПОСРЕДСТВЕННО ПЕРЕД `pg_ctl start`
 — живой Patroni ноды (нода поднята воркером на время restore, §3.5)
 может воссоздать файл в окне между правками и стартом, и postgres
 уйдёт в standby-ожидание WAL вместо recovery (бесконечный цикл
 «ждать сегмент» вместо промоута),
 канонический набор каталогов initdb, trust-строка pg_hba на время
 поллинга, права `chmod 700` PGDATA после модификаций (владелец файлов —
 уже `postgres`), PG-процессы под uid/gid 101 (`pg_ctl` — процесс уже
 работает под `postgres`), `HOME=/tmp`; (4)
 локальный postgres (`pg_ctl` под setpriv, unix-socket,
 `listen_addresses=''` — сеть не слушает, кредов PG не нужно),
 стартовое ожидание готовности `pg_ctl start -w -t` = тот же бюджет
 `recovery_timeout_sec` из команды, не фиксированный литерал — до
 консистентной точки postgres скачивает сегменты `restore_command`-ом
 (fetch-wal), под нагрузкой/узкой полосой S3 это минуты, и короткий
 старт-таймаут рвал операцию до поллинга; затем поллинг
 `pg_is_in_recovery` с бюджетом `Restore:RecoveryTimeoutSec` из
 команды (promote-окно рестарта postmaster ретраится до бюджета),
 снятие `pg_current_wal_lsn`, `pg_ctl stop -m fast`, чистка
 recovery-остатков (возврат pristine `auto.conf`, снятие trust-строки),
 `system_id` из `pg_controldata`. Фазы/итог — статус API (GET): воркер
 поллит GET тиками; exit-кодов/docker-логов нет. Адрес API —
 `alias:8080` ноды (тот же канал команды/статуса, что у полного, §2).
 Накат большого объёма — одним проходом, резюмов
 нет (осознанная плата plain-механики). REJOINING: воркер перезаписывает
 щит `initialize` настоящим `system_id` восстановленного PGDATA (из
 статуса операции) и РЕСТАРТАНЕТ контейнер первой ноды — Patroni стартует
 на восстановленных данных (сверка system_id сходится, лидерится);
 контейнер жив и идемпотентен (EnsureNode — no-op).
- **RestoreProcess** (машина тика под клэймом `<C>`, паттерны arch/17):
 `PLANNED` → валидация (кластер Active, шард заявлен, шард без
 усыновлённых object-нод (чужой PGDATA-контур — permanent-отказ «ручной
 runbook»), бэкап существует —
 etcd-статусы ИЛИ list-S3 `backup_manifest` (DR: etcd пуст),
 WAL-цепочка от `wal_start_segment` полного непрерывна (WalChain) —
 дыра → permanent-отказ с границами, включая RPO-зазор tli-прыжка
 приёмника (§3): восстановление от полных ниже зазора невозможно до
 переснятия — честное RPO-окно; verify полных вне диапазона зазора
 не затрагивается) → `RUNNING` (демонтаж:
 контейнеры/volumes ВСЕХ нод шарда снесены (приёмники WAL уходят с нодами),
 HA-scope `/service/<C>-<X>/` вычищен (P2.2-Д3-образец: initialize/leader/
 sync/status/failover + префиксы optime//members/; `failover` обязателен —
 остаточный маркер с `scheduled_at` в прошлом для Patroni новой жизни
 «accelerated failover» на неинициализированную ноду-кандидат, лидерство
 недостижимо; request_* — декларации панели — НЕ трогаем), ноды
 `state=REBUILDING`, portalloc/dsn НЕ меняются; факт — фаза заявки
 `phase="demolished"`; демонтаж идемпотентен — takeover-повтор безопасен) →
 подъём первой ноды (EnsureNode, новый пустой volume, щит; WalReceiver
 ноды ПЕРЕД RESTORE-восстановлением ОСТАНАВЛИВАЕТ Patroni ноды
 (только restore: дрилл на живой ноде Patroni не трогает —
 `stop spilo` там гасит прод-постгрес)
 (`supervisorctl stop spilo`; supervisord-сокет контейнера —
 `chmod=0770 root:postgres` в supervisord.conf образа — приёмник работает
 под `postgres`) с ПОДТВЕРЖДЕНИЕМ останова: stop не удался — операция не
 начинается (честный failed-снимок, не тихая гонка) — и возвращает
 Patroni в finally ПОСЛЕ любого исхода — живой Patroni иначе вмешивается
 в заполняемую PGDATA (стартует постгрес «secondary» на полуданных,
 воссоздаёт `standby.signal`, убивает restore-постгрес «чужим»
 процессом)) + команда
 `POST /api/ops/restore` её WalReceiver (факты — фазы заявки:
 `phase="demolished"` → `phase="launching"` (команда принята) → фазы
 операции приёмника downloading/recovering; 409 при запуске — в общем
 ops-реестре приёмника (§5, одна ops-операция на процесс) идёт ЧУЖАЯ
 операция (verify свежего полного): снимок 409 не различает свою/чужую —
 launching откладывается (transient, фаза остаётся demolished, повтор
 следующим тиком до освобождения реестра); принять 409 за «свою живую»
 нельзя — verify затирает снимки общего реестра, и воркер уходил бы в
 REJOINING от чужого succeeded без system_id (щит-заполнитель навсегда
 запир бы bootstrap)) →
 `REJOINING` (щит `initialize` → `system_id` восстановленного PGDATA;
 рестарта ноды НЕТ: restore-операция сама вернула Patroni (`start spilo`)
 уже с валидным initialize и данными — Patroni поднимает восстановленный
 постгрес и продолжает recovery до промоута, bootstrap с непустым PGDATA
 при чистом DCS; ожидание идентифицирующей
 пробы P2.2-образцом; остальные ноды — чистые EnsureNode, реплики
 догоняются `pg_basebackup` с восстановленного лидера) → все ноды RUNNING →
 SQL-гейт мастера: проба фактического
 постгреса лидера восстановленного шарда `pg_is_in_recovery = false` по
 admin-DSN первой ноды; Patroni-пробы живы и в переходном окне рестарта
 postmaster, а `COMPLETED` обязан означать закрытое окно — после него
 планировщик полных немедленно стартует пересъём, тесты/панель читают.
 Бюджет — `PatroniBootSec`; исчерпан → permanent-FAILED «мастер не принял
 SQL» → `COMPLETED` (пост-обработка: ключ `wal` шарда УДАЛЯЕТСЯ — планировщик §2
 немедленно переснимает полный (инвариант цепочки; PITR-назад ломает
 сшиваемость TLI — новая цепочка начинается с нового полного), приёмники
 WAL новых нод включаются сами с новым слотом). **Гвард исключения**: пока у шарда есть
 активный (не COMPLETED/FAILED) restore-ключ, контуры воркера шард не
 трогают — надзор не пересоздаёт снесённые ноды (иначе пустой Patroni
 поверх restore), не ускоряет failover и не rebuild'ит ноды шарда,
 эвакуатор не считает шард мёртвым, планировщик полных
 скипает шард, усыновление/репарация переездов не касаются (restore сам
 владеет жизненным циклом шарда; переезды бакетов получают обычный
 transient «мастер недоступен»). Гвард проверяется СВЕЖИМ чтением
 restore-ключей из etcd НА ШАГЕ мутации надзора (перед ускорением
 failover, пересозданием/сносом ноды, пробами rebuild): снапшот тика
 отстаёт от записи заявки, и долгий тик надзора без свежей сверки
 исполняет мутации посреди демонтажа/REJOINING — ускорение failover
 кладёт residual `failover`-маркер в чистый HA-scope, пересоздание —
 пустую ноду поверх восстанавливаемой.
 transient-сбой фазы → ретраи тиками
 (демонтаж/запуск идемпотентны); permanent (дыра WAL, бэкап исчез,
 recovery-бюджет исчерпан, target не достигнут — конец цепочки раньше
 `target_time`) → `FAILED` + `error`; повтор — НОВАЯ заявка оператора.
 Операторская отмена идущей операции (`POST /api/ops/cancel` приёмника ноды
 — внешний канал мимо воркера) → операция приёмника завершается снимком
 `state=cancelled` (НЕ failed); воркер-супервиз по GET `cancelled` возвращает
 всё к состоянию «как до старта операции»: первая нода сносится вместе с
 data-volume (до-restore «пустое» состояние демонтажа), щит `initialize`
 снимается (заполнитель «restore-in-progress» запер бы bootstrap пустых
 нод), запись заявки `/<C>/<X>/restore/<id>` УДАЛЯЕТСЯ из etcd — операции
 нет, записи нет; journal-факт `cancelled-by-operator` обязателен;
 перманентного FAILED отмена не порождает — шард остаётся разобранным,
 повтор — новая заявка оператора.
 Takeover: статус + детерминированные имена — новый инстанс продолжает.
- **Стоп-семантика**: deprovisioning (D1) сносит ноды шарда вместе с
 приёмниками (restore-операция уходит с нодой), D2 чистит префикс
 `/pgworker/backups/<C>/` (вкл. restore-ключи); remove-shard с активным
 restore → заявка FAILED `cancelled-by-remove`. S3-объекты restore не
 удаляет никогда (только читает).
- **Runbook** (`docs/backup-restore.md`): полная потеря ноды (живой
 шард → Patroni recreate; весь шард → restore latest), порча данных
 (target_time до порчи), восстановление в новый кластер (DR: пересоздание
 декларации + restore с source) — критерий приёмки: кластер уничтожается и
 поднимается из бэкапов с проверкой данных (E2E-гейт + ручной прогон
 dev-станда).

## 3.6. Дрилл восстановимости

- **Роль**: плановое НЕдеструктивное доказательство восстановимости —
 периодический автоматический прогон DR-пути restore-заявки (§3.5) на
 бэкапе живого шарда: тот же кандидат (новейший COMPLETED-полный) и та же
 валидация (манифест существует, WalChain от `wal_start_segment`
 непрерывна), что у реального DR-restore — дрилл доказывает ровно тот
 путь, который сработает при аварии. Прод-шард не трогается вовсе
 (scratch-каталог дрилла — НЕ PGDATA ноды); S3 —
 только чтение (list + скачивание). Контроль — «старт + выход из
 recovery»: postgres drill-операции стартовал на восстановленном наборе
 и вышел из recovery (`pg_is_in_recovery = false`), `restored_to_lsn`
 фиксируется в статус; SQL-проверок данных НЕТ (целостность файлов —
 verify §5; сверка счётчиков с продом не имеет смысла — прод уходит
 вперёд точки бэкапа).
- **RestoreDrillProcess** — тиковая машина под клэймом `<C>` (Op
 `backup-drill`; врезка ReconcileLoop после backup-restore, до repair;
 вызов ВСЕГДА — стоп-семантика ниже): супервиз активной drill-операции
 WalReceiver первой ноды шарда (фазы downloading|recovering и итог —
 по API `GET /api/ops/restore`), затем отбор кандидата, валидация,
 запуск (`POST /api/ops/restore` с id дрилла — latest, БЕЗ target).
 Команда уходит в ЖИВОЙ приёмник ноды — «заявка → операция работает»
 занимает секунды (никаких create/boot контейнеров). Бюджет активного
 дрилла — `Drill:TimeoutSec` от `started_unix` ключа → FAILED
 `drill-timeout` (+ `POST /api/ops/cancel` best-effort); бюджет
 наката WAL внутри операции — общий `Restore:RecoveryTimeoutSec`
 (REJOINING-фаз у дрилла нет — после операции сразу терминальный исход).
 Takeover: всё состояние — в etcd-ключе (§4), адрес приёмника
 детерминирован (`alias:8080` первой ноды, §2) — новый инстанс продолжает
 супервиз до исхода; GET 404 (операция vanished — рестарт приёмника)
 при молодом ключе — повторный POST (резюмов нет — скачается заново),
 при возрасте ≥ бюджета — FAILED `drill-vanished`.
 Операторская отмена идущего дрилла (`POST /api/ops/cancel` приёмника —
 внешний канал мимо воркера) → операция приёмника завершается снимком
 `state=cancelled` (НЕ failed); воркер-супервиз по GET `cancelled`
 УДАЛЯЕТ ключ дрилла — операций нет, записи нет (scratch-каталог чистит
 приёмник при отмене — следов на ноде не остаётся); journal-факт
 `cancelled-by-operator` обязателен;
 перманентного FAILED отмена не порождает (следующий дрилл шарда — по общим
 правилам отбора).
- **Drill-операция WalReceiver ноды**: операцию исполняет WalReceiver
 ПЕРВОЙ ноды шарда — тот же единственный процесс ноды (стрим/полный/
 verify/restore/drill, §3.5). Команда — та же
 `POST /api/ops/restore` с полем `id` (id дрилла — как у полных, §2;
 отличает drill-запуск от restore): механика restore §3.5 ЦЕЛИКОМ
 (recovery latest — БЕЗ target: скачивание `full/<id>/` в
 scratch-каталог, fetch-wal, локальный postgres unix-socket
 `listen_addresses=''`, поллинг
 `pg_is_in_recovery`, снятие `pg_current_wal_lsn`, stop
 — инцидентные правки restore-механики автоматически достаются дриллу;
 лишнее дриллу поле `system_id` результата воркер дрилла игнорирует).
 Фазы — `downloading|recovering` (GET /api/ops/restore). Изоляция
 ПО ПОСТРОЕНИЮ: scratch-каталог
 `/home/postgres/pgdata/backup-drill/<id>/pgdata` на data-volume
 ПЕРВОЙ ноды (НЕ PGDATA ноды — прод-данные недостижимы для записи);
 приёмник чистит scratch при ЛЮБОМ исходе операции (вкл. отмену и
 failed) — терминальный ключ дрилла сразу чистый (фазы docker-сноса
 нет). Сеть не нужна сверх общей (`alias:8080` воркер↔нода; S3 приёмник
 адресует как стрим, §7). Нод в кластере дрилл НЕ создаёт,
 HA-scope и synchronous-режим мастера (Patroni) не затрагивает,
 per-cluster сети не входят.
- **Отбор кандидата** — чистая функция: один шард за проход кластера —
 наименее свежий по последнему терминальному дриллу (MIN
 `finished_unix`; «никогда» = 0 — обслуживается первым; tie-break по
 имени — детерминизм). Гварды: `interval_days ≤ 0` — дрилл кластера
 выключен; RUNNING-дрилл кластера блокирует новые —
 один активный дрилл на кластер;
 активная restore-заявка владеет жизненным циклом шарда (§3.5) — шард
 не кандидат; `ToRemove`-шард и шард без COMPLETED-полных — не
 кандидаты. Готовность: `now − (finished_unix последнего терминального
 дрилла шарда)` ≥ `interval_days×86400`; ключа дрилла нет вообще —
 готов немедленно (первый дрилл). Интервал per-cluster:
 `policy.drill.interval_days` (§4) ?? дефолт конфига
 `Drill:IntervalDays` (§9).
- **Валидация и запуск**: валидация кандидата — та же, что у
 restore-заявки §3.5 own-source (новейший COMPLETED ⇒ манифест
 `full/<id>/backup_manifest` существует (S3) ⇒ `wal_start_segment`
 (etcd-статус либо `backup_label`) ⇒ WalChain непрерывна — RPO-зазор
 tli-прыжка приёмника (§3) тоже даёт permanent-отказ с границами:
 дрилл периодически вскрывает незакрытый зазор оператору; verify полных
 вне диапазона зазора не затрагивается); S3-отказ —
 transient (статус не трогаем, тик повторит). Отказ валидации
 (манифеста нет / дыра цепочки) → FAILED-дрилл БЕЗ запуска операции:
 `started_unix`/`finished_unix` поставлены, `error` — причина (границы
 дыры от WalChain); контейнера/каталога не было — чистка не нужна, ключ
 сразу чистый терминальный итог — честный исход «восстановимость
 не доказана». Запуск — journal-before-manipulations: put ключа RUNNING
 до команды ⇒ `POST /api/ops/restore` (id дрилла) на приёмник первой
 ноды; отказ команды — transient (ключ остаётся RUNNING — следующий тик
 повторит POST идемпотентно; 409 — операция уже жива).
- **Стоп-семантика**: `Backups:Enabled=false` (или интервал `0`) — новых
 запусков нет; идущий дрилл доводится до терминального исхода (стоп-семантика
 супервиза продолжается).
- **Deprovisioning**: D1 сносит ноды шарда вместе с приёмниками
 (drill-операция уходит с нодой);
 D2 — ключ `drill` уходит с per-cluster префиксом
 `/pgworker/backups/<C>/`. Идущий дрилл не ломается демонтажом шарда
 (дрилл не создаёт нод — S3 + приёмник живой ноды); remove-shard при
 активной restore — дрилл шарда не стартует (гвард отбора).

 воркер статусы приёмников только читает); панель читает (контекст —
 [adminpanel/02-etcd-contract.md](adminpanel/02-etcd-contract.md) §2.3.1;

- **Секция `s3` policy**: `"s3":{"pool":"<C пула>","write_master":["<I>",…],"write_replica":["<I>",…]}` — выбор пула S3 кластера (архитектура пула — [23-s3-clusters.md](23-s3-clusters.md)); `pool` — имя кластера `/s3/clusters/`; `write_master`/`write_replica` — упорядоченные (по приоритету записи) имена инстансов пула — ССЫЛКИ, не адреса: резолв `имя → host:port` воркер выполняет чтением `endpoints`-ключа пула и `/s3worker/portalloc/<C>` (arch/23 §7); поля названы по роли ИСТОЧНИКА записи (мастер-потоки/репличные), не по роли ноды. Пересечение списков и неполный охват нод пула допустимы. Отсутствие секции — пул не выбран: подсистема бэкапов кластера НЕ пишет и НЕ читает (алерт `backup-pool-missing` панели); никаких env-дефолтов. Приём секции — замещение целиком (как drill); сброс — отправкой policy без `s3`.
- **Правила**: transient-сбой → статус с `error` + ретраи тиками;
 **Failed-резолв пула** — пул удалён/`TO_REMOVE`, имя списка не заявлено в пуле (`nodes/<I>/placement` нет), пул без читаемых secrets, нода без portalloc-адреса — transient для процессов: ретраи тиком + journal-фаза `waiting-backup-pool`, НЕ краш тика; в `Error` wal/full-статусов при этом ставится тот же маркер `s3-pool-exhausted` — алерт `backup-pool-unreachable` закрывает и случай «policy записана, но резолв не удался» (единая алертная грань записи в пул);
 permanent-отказ → фиксация причины + алерт. `DELETING` — транзитная фаза
 ретенции (запрет удалять последний валидный полный — guard).
 `WAL_CHAIN_ERROR` — разрыв цепочки в АРХИВЕ S3 (дыра WalChain /
 исчезновение слотов всех нод-источников при живой цепочке — per-instance
 §3): НЕ состояние кластера и НЕ свидетельство о данных нод; приёмники
 замирают (стоп-семантика приёмника — гейт СТРИМА; операцию полного
 НЕ гейтит, §2), лечение — пересъём полного (§2/§3).
 `chain_start_segment` в WAL_CHAIN_ERROR-записи — граница разрыва; ratchet —
 значение никогда не понижается (§3).
- **Backwards-compat дрилла**: панельный парсер
 толерантен к отсутствию drill-ключей (подсистема не включена / дрилов
 не было — правила дрилла молчат) и к policy без поля `drill`
 (парсится как «дефолт интервала»); JSON статусов без новых полей
 читается без ошибок.
- **DR-hold сирот**: автоматика TTL удаляет только
 НЕзащищённые сироты (`has_valid_full=false` и без hold-ключа) — потеря
 потенциального DR-источника автоматикой исключена (R4-симметрия:
 данные дороже места); накопление защищённых в bucket квитируется ключом
 `/pgworker/backups/storage` (квота/алерты) и чистится явной заявкой
 `orphan-deletes` с confirm; hold — расширяемая человеком защита
 (WAL-огрызки без полного и т.п.).

- **Ретенция**: rolling-проход воркера под клэймом `<C>` по расписанию
 `Retention:IntervalSec`, для каждого шарда Active-кластера:
 1. **GFS-отбор по календарю UTC**: дневные — все COMPLETED-полные последних
 `retention.days` календарных суток; недельные — ПОСЛЕДНИЙ COMPLETED
 каждой из `retention.weeks` предыдущих календарных недель (ISO-неделя);
 месячные — ПОСЛЕДНИЙ COMPLETED каждого из `retention.months`
 предыдущих календарных месяцев. Активные
 (PLANNED/RUNNING/UPLOADING) и DELETING в отборе не участвуют.
 Счётчики — policy-ключ кластера, дефолт — `PgWorker:Backups:Policy`.
 Полные ТЕКУЩЕЙ недели/месяца вне дневного окна недельными/месячными
 точками НЕ удерживаются: счётчики считают строго ПРЕДЫДУЩИЕ календарные
 недели/месяцы; текущий период удерживает только дневная гранула.
 2. **Guard последнего валидного**: последний COMPLETED-полный шарда не
 удаляется НИКОГДА, даже просроченный по GFS. «Валидный» = COMPLETED
 (verify-статусы на guard НЕ влияют;
 полные с `verify.state=FAILED` — первые кандидаты на удаление,
 но guard «≥1 COMPLETED» держится и над ними: лучше старый невалидный,
 чем никакого).
 3. **Удаление полного**: `DELETING` (journal-before-manipulations) →
 delete объектов префикса `full/<id>/` (§5) → del etcd-ключа.
 transient-отказ S3 → остаётся `DELETING`, следующий проход повторяет
 (идемпотентно). За один проход удаляется ОДИН полный (по старшинству;
 FAILED-verify — вперёд) — тик короткий, backlog выгребается
 последующими проходами. Зависший `DELETING` (возраст > порога панели)
 → warning-алерт `backup-deleting-stuck`.
 4. **Гигиена истории**: FAILED-ключи шарда — держатся последние
 `Retention:KeepFailed` (по `started_unix`), старше — del. Бэкофф
 переснятия не ломается: n = FAILED с последнего COMPLETED ≤
 KeepFailed, а `BaseSec·2^(n−1)` упирается в `MaxSec` задолго до
 границы (при дефолтах — с n≈5).
 5. **Чистка WAL**: cutoff = `wal_start_segment` новейшего (по
 `started_unix`) COMPLETED-полного с `verify.state=OK` ИЗ ОСТАВЛЯЕМЫХ —
 кандидат удаления текущего прохода (Delete[0] GFS-отбора) точкой cutoff
 не якорит: в переходном окне, где новейший OK-полный сам стал кандидатом
 удаления, привязка cutoff к нему срезала бы WAL между предыдущим
 OK-полным и ним — RPO-дыра после доводки DELETING. Срез только
 после создания полного И его успешного verify. Сегменты префикса
 `wal/` СТРОГО ниже cutoff удаляются — сравнение по позиции
 (`log·256+seg`) при равном TLI и весь TLI ниже стартового, включая
 `.history` тех TLI (§5). Сам cutoff-сегмент и всё выше/новее — живут.
 ГВАРД verify: прунинг WAL ниже точки полного, НЕ прошедшего verify
 (PENDING/FAILED — в т.ч. при перепроверке OK→FAILED), запрещён —
 cutoff держится на предыдущем verify-OK полном; verify-OK-полного
 нет вовсе → WAL не чистится (нет безопасной точки привязки).
 Недельная/месячная GFS-точки на cutoff НЕ влияют. `chain_start`
 пересчитывается автоматически при следующем контроле (list S3 —
 истина; старт контроля — от той же точки из оставляемых, §3; в
 переходном окне контроль может якориться выше cutoff — по кандидату
 удаления текущего прохода: безопасно, нижележащий cutoff режет
 меньше): list-префикс укорачивается, старые дыры ниже cutoff
 исчезают.
 Ретенция и супервизор — осознанные удаляющие S3-объектов воркера
 (ретенция — по политике GFS/cutoff; супервизор — только мусор `full/<id>/`
 живого шарда без etcd-ключа и сироты по TTL): стоп-семантика/deprovisioning
 объекты по-прежнему не трогают (R4, §3/§4). `Backups:Enabled=false` →
 ретенция no-op (чистки нет, копится до включения; зависшие DELETING видит
 панельный алерт).
- **Гейты мусора супервизора** (§4): проход сверяет СВОЙ снапшот
 `/pgworker/backups/` с листингом S3 — снапшот может отставать от
 планировщика того же тика (запланировал и запустил полный ПОСЛЕ
 снятия снапшота), поэтому «unowned»-префикс удаляется только после
 двух гейтов: (1) свежее чтение etcd-ключа `full/<id>` — появился →
 живой полный, не мусор; (2) возрастной гейт `garbage_min_age_sec`
 политики кластера (дефолт 600 с): самый старый объект префикса моложе
 порога → заливка in-flight, не мусор. Оба гейта — перед batch-delete;
 неподошедший префикс остаётся следующему проходу.
- **Хранилище/квота**: ретенционный проход (расписание то же,
 per-instance) list-ит ВЕСЬ bucket (пагинация; включая чужие/осиротевшие
 префиксы — занятость bucket, не только свои) → `used_bytes` = сумма
 размеров объектов → ключ `/pgworker/backups/storage` (формат — таблица
 выше) при изменении. Реакции автоматикой НЕТ (emergency-чистки, запрета
 новых полных): WARN/CRIT → панельный алерт `backup-storage-quota`,
 действует оператор (расширить квоту / ужать policy).
- **Суточный алерт**: панель вычисляет по снапшоту префикса —
 правило `backup-full-stale` per-shard: возраст последнего ВАЛИДНОГО
 COMPLETED-полного шарда (`verify.state ≠ FAILED` — OK/PENDING/
 отсутствует; проваленный verify свежестью не считается) >
 `full_max_age_sec` политики кластера (policy-ключ
 отсутствует → панельный дефолт 86400). Пустой префикс кластера (ни
 одного ключа бэкапов — подсистема не включена) — правило молчит, ложных
 алертов на выключенной подсистеме нет. Воркер алертов не пишет — только
 статусы (все алерты панели — вычисления над снапшотом, как остальные
 правила AlertEngine).
- **Алерт невалидного**: правило `backup-verify-failed` (critical)
 per-shard — в статусе любого COMPLETED-полного `verify.state=FAILED`
 (описание — `verify.error`: провал checksums / дыра цепочки с
 границами); воркер реагирует переснятием (планировщик §2 не считает
 проваленный verify свежестью), действие оператора — разбор по runbook
 . Проверки по политике: `verify.on_create` — сразу после
 COMPLETED, `verify.interval_sec` — периодическая перепроверка каждого
 оставшегося COMPLETED-полного по возрасту `verify.checked_unix`
 (тихая порча/утеря объектов S3).
- **Deprovisioning кластера** (D2, [14-pgworker.md](14-pgworker.md) §5 B)
 чистит etcd-префикс `/pgworker/backups/<C>/` тем же `del --prefix`
 (идущие операции бэкапов уходят вместе с нодами шарда — D1 сносит
 контейнеры нод с приёмниками; отдельных контейнеров/джобов бэкапов
 нет — §2/§3.5/§3.6/§5); объекты
 S3 этим путём НЕ удаляются (данные дороже места; осознанное удаление —
 только ретенция по политике): префикс S3 без
 etcd-владельца попадает в реестр сирот `/pgworker/backups/orphans`
 супервизора: алерт панели +
 удаление по `Supervisor:OrphanTtlSec` (гибрид: мусор живого шарда —
 `full/<id>/` без ключа — удаляется per-cluster-проходом после гейтов
 «Гейты мусора супервизора» выше;
 исчезнувшие владельцы — реестр+TTL; DR-hold : TTL чистит
 только незащищённых — валидный полный или hold держат префикс до явной
 заявки `orphan-deletes`); восстановление удалённого кластера
 из S3 — runbook backup-restore (симметрия R4 arch/14: воркер не уничтожает
 потенциально ценные данные автоматикой).

## 5. Хранилище S3: layout

Bucket ОДИН на установку (`PgWorker:Backups:S3:Bucket`, env
`PGW_BACKUP_S3_BUCKET`); запись кластера — в ПУЛ S3 (per-cluster выбор
policy.s3, §4 — пул = кластер `/s3/clusters/`, bucket единый на всех нодах
пула; разные пулы — раздельные экземпляры этого bucket, mesh-репликация —
внутри пула). Префиксы per-cluster/per-shard:

```
s3://<bucket>/<C>/<X>/
 full/<id>/ # файлы pg_basebackup 1:1
 # (вкл. backup_manifest, pg_wal/)
 wal/<segment> # 000000010000000000000001, …
 wal/00000002.history # timeline-истории (обязательны)
```

- Ключ объекта = путь файла; `backup_manifest` в корне `full/<id>/` — база
 `pg_verifybackup` (скачивание в staging → verify). Никаких
 tar-обёрток; WAL-сегмент = один объект. Layout одинаков для MinIO и
 облака; адресация — ноды пула (§7).
- **Семантика пула**: запись (put/delete) — «первый доступный по
 списку роли» (`write_master`/`write_replica`, перебор при отказе;
 исчерпание → маркер `s3-pool-exhausted`, §2/§3/§4); чтение — все ноды
 пула без приоритетов, «где данные есть» (страховка на лаг доставки
 mesh-репликации), три семантики: точечные GET — перебор до найденного;
 инвентарь-листинги — первая доступная нода (лаг mesh допускается —
 повторные проходы досматривают); исключение — проверки непрерывности
 цепочки (контроль §3, verify §5, drill §3.6): union-листинг `wal/` и
 `full/<id>/pg_wal/` по ВСЕМ нодам пула с дедупом по имени объекта
 (соло-листинг отстающей ноды даёт ложную дыру и ложный WAL_CHAIN_ERROR, а соло-лист
 набора полного на ноде, куда он не заливался, — ложное «пусто»);
 удаления ретенции per-cluster — по `write_master`-списку (перебор при
 отказе; недоступны все мастера при живой реплике — удаление
 откладывается до ретрая следующего прохода; успешное удаление mesh
 разносит tombstone — [owns3/07-replication.md](../OwnS3/arch/owns3/07-replication.md)
 §7); глобальные сверки (`used_bytes`, реестр сирот) — union по ВСЕМ
 существующим пулам `/s3/clusters/` (первый доступный endpoint каждого;
 дедуп ключей — по (пул, ключ)).
- **Исключение отказавшей цели (circuit-breaker)**: перебор любого списка
 всегда начинается с первой цели; цель с транспортным отказом (таймаут,
 обрыв соединения; ответ NotFound — НЕ отказ: сервер жив и отвечает)
 исключается из перебора на окно восстановления 45 с. Без окна кумулятивные
 пер-попыточные таймауты недоступной первой ноды стоили бы каждому вызову
 прохода (минуты на проход по всем операциям тика); с окном мёртвая цель
 зондируется не чаще раза в 45 с. По истечении окна цель возвращается в
перебор, успешный ответ возвращает её сразу; отказ цели в окне несёт
исходную ошибку в маркере исчерпания (`s3-pool-exhausted`).
Отмена/исчерпание бюджета источника — НЕ транспортный отказ цели:
попытка, прерванная отменой токена источника (linked-CTS бюджета
операции при истёкшем общем таймауте), breaker цели не открывает —
цель остаётся в переборе; окно открывает только собственный отказ
цели (таймаут/обрыв на её вызове).
- **Дублирование WAL (§2)**: закрытые сегменты набора `-X stream`
 полного бэкапа лежат и в `full/<id>/pg_wal/` (1:1 с manifest — база
 verify), и копией в `wal/` (общий префикс — стартовая точка цепочки);
 перезапись одного и того же сегмента идемпотентна.
- **Служебный префикс `etcd/`**: выгрузка снапшотов etcd
 (контроль-плейн) — `etcd/snapshot-<id>.db` 1:1 + `etcd/snapshot-<id>.meta.json`
 (sha256/size/revision?/taken_unix/uploaded_unix/instance; `uploaded_unix` —
 фактическое время put'а объекта, в отличие от «покрытия» в статус-ключе).
 Каждый снятый слепок выгружается; статус-ключ покрытия
 `/pgworker/etcd-snapshots` (arch/14 §3) обновляется после каждой выгрузки.
 Вне per-cluster layout: не форма `<C>/<X>/` → реестр сирот его не группирует (ключи короче
 3 сегментов); ретенция и sweeper к `etcd/` не прикасаются (их пути
 адресны: `full/<id>/`, `wal/`, `<C>/<X>/`). Единственный удаляющий — ретенция
 самого экспорта (N последних пар, guard ≥1 полная пара). Объекты `etcd/`
 входят в `used_bytes` ключа `/pgworker/backups/storage` (list всего bucket —
 занятость bucket, корректно).
- **Ретенционная чистка (§4)**: удаление полного = delete всего
 префикса `full/<id>/` (list + batch-delete, идемпотентно; 404/пустой
 префикс = уже удалён); чистка WAL = delete сегментов `wal/<segment>` со
 позицией (`log·256+seg`) строго ниже cutoff — `wal_start` новейшего
 verify-OK COMPLETED-полного (§4 п.5; нет OK-полного — чистка не
 выполняется) — при равном TLI, и всех объектов TLI ниже
 стартового — включая `.history` тех TLI (сегменты их диапазонов
 удалены); стартовый сегмент, `.history` стартового и более новых TLI,
 всё выше/новее — НЕ трогаются.
- **Verify полного (§4)**: две независимые проверки, итог —
 verify-статус полного:
 1. **Checksums** — операция WalReceiver ноды-источника
 полного (тот же единственный процесс ноды, §2/§3.5; отдельный
 ops-реестр операций приёмника — полная операция и ops-операция на
 одной ноде не блокируют друг друга): команда
 `POST /api/ops/verify` от воркера на `alias:8080` ноды
 (`candidate.Node`; S3-контекст read-списка —
 секреты только в POST, §7) → скачивание `full/<id>/` 1:1
 .NET S3-клиентом в staging ноды (`<Staging:Dir>/full/<id>/`) →
 `pg_verifybackup` (manifest SHA256, вкл. `pg_wal/` набора) →
 статус `GET /api/ops/verify` (фазы `downloading|verifying`,
 `started_unix`); воркер супервизит поллингом до итога; staging
 чистит приёмник при любом исходе. Сбой скачивания (S3/сеть/staging) —
 transient (статус операции `failed` с фазой `downloading`):
 PENDING остаётся, ретраи тиками (следующий тик повторяет POST —
 операция начнётся заново, резюмов нет); `pg_verifybackup` ≠ 0 (фаза
 `verifying`) — permanent (данные плохие). Операторская отмена идущей
 проверки (`POST /api/ops/cancel` приёмника — внешний канал мимо
 воркера) — операция завершается снимком `state=cancelled` (НЕ
 failed): отмена — не суждение о данных; воркер-супервиз по GET
 `cancelled` возвращает кандидата в PENDING (`checked_unix=now` —
 перепроверка по расписанию политики `verify.interval_sec`, лив-лок
 немедленных перезапусков исключён — симметрия таймаут-ветке §6),
 journal-факт `cancelled-by-operator` обязателен; перманентного
 FAILED отмена не порождает. GET 404 (операции нет — старт не дошёл/
 рестарт приёмника) — transient: следующий тик повторяет POST;
 идущий процесс приёмника жив под supervisord'ом ноды — «окна бута
 ephemeral-контейнера» нет (стартовавшее приложение уже слушает API).
 2. **Полнота WAL-цепочки до точки бэкапа** — воркер без скачивания
 сегментов и до запуска verify-операции: list `wal/` + list `full/<id>/pg_wal/`
 (последний сегмент набора `-X stream` = точка бэкапа) →
 непрерывность от `wal_start_segment` до точки бэкапа (подмножество
 общего gap-детектора §3) + строгий LSN-разбор `.history` при
 TLI-переходах в диапазоне (§3; GET history-объектов — они
 крошечные). Дыра → permanent FAILED c границами, checksums-операция не
 запускается (вердикт уже определён).
 Обе зелёные → `verify.state=OK` + `checked_unix`; любая красная →
 `FAILED` + `error`; verify идемпотентен — vanished-операция
 перезапускается
 (PENDING), переснятие полного не требуется.
- **Панель читает bucket read-only**: live-инвентарь/health/сверка в
 грани «Хранилище бэкапов»
 ([adminpanel/02](adminpanel/02-etcd-contract.md) §2.5); пишущие/удаляющие
 операции S3 — ТОЛЬКО воркер (ретенция §4, супервизор).
- **Клиент S3 воркера** (AWSSDK в процессе воркера; операции бэкапов
 исполняют приёмники нод своими .NET-клиентами — не этот
 клиент): пер-попыточный таймаут короче окна
 проверки watchdog (`AmazonS3Config.Timeout` = полокна, 10 с при
 дефолтах — симметрия таймаутов etcd/patroni/SQL, arch/14 §6) +
 пульс активности на время каждого вызова (`S3Pulse`, arch/14 §6
 «пульс конечного внешнего вызова»). Недоступный endpoint →
 transient-файл тика (журнал/статус несут ошибку), повтор — следующим
 тиком/проходом/retry выгрузки (`Retry.BaseSec`, `RetryIntervalSec`);
 списки/геты/put-ы снапшотов и wal-history, ретенция и sweeper — один
 класс (никаких «вечных» вызовов воркера к S3). **Кэш пул-клиентов**:
 фабрика создаёт клиент пула ОДИН РАЗ на контекст пула (pool +
 endpoints + креды + bucket + CA; смена любого — новый клиент, прежний
 живёт до конца процесса — клиентов по числу пулов, единицы),
 вызывающие получают кэшированный инстанс и НЕ диспоузят его —
 circuit-breaker-стейт отказных целей переживает тики: недоступная нода
 пула оплачивает свой таймаут один раз за breaker-окно, а не в каждом
 тике каждой врезки (иначе мёртвая цель растягивала бы КАЖДЫЙ тик
 воркера на полный S3-таймаут — фактический тик 5 c превращался в ~35 c).

## 6. Источник, HA-контур и ресурсные лимиты

- **Реплика-источник**: штатно полный бэкап не трогает мастер; fallback на
 мастер — журнал-факт (`role=master`) + I/O одной операции (не потоковой).
 Смерть источника посреди бэкапа → `pg_basebackup` теряет соединение,
 операция завершается FAILED (приёмник чистит staging), переснятие
 (бэкофф §2).
- **Слот на источнике**: WAL копится, пока приёмник не подтвердил доставку;
 потолок — `max_slot_wal_keep_size` (уже в каноне нод,
 [14-pgworker.md](14-pgworker.md) §2.1 P3/P4): смерть обоих приёмников → WAL в
 пределах лимита → по исчерпании слот инвалидируется PG → цепочка рвётся →
 алерт панели + переснятие полного. Диск источника переполнить нельзя.
 Слоты per-instance (§3): инвалидация одного не касается второго.
- **Ресурсный профиль операций**: отдельных контейнеров/лимитов для
 операций бэкапов НЕТ — verify/restore/drill исполняет процесс
 WalReceiver внутри контейнера ноды и делит его ресурсы с нодой
 (стрим/полный — и так делили, §2); память приёмника: буфер сегмента
 `wal_segment_size` — обычно 16 МиБ + рабочие множества фоновых
 операций; скачанные наборы лежат на data-volume ноды: staging
 полного/verify — каталог `Staging:Dir` (§2/§5; ENOSPC — реактивный
 FAILED), scratch дрилла — `backup-drill/<id>/` (§3.6); размеры —
 операционный риск §10.
- **Бюджеты зависших операций**: активный полный (PLANNED/RUNNING/
 UPLOADING) с возрастом (`now − started_unix`) > `Job:FullTimeoutSec`
 (default 6 ч) → `POST /api/backup/full/cancel` best-effort (приёмник
 гасит дерево текущего child-процесса и чистит staging; недостижимый
 приёмник — journal-пометка «cancel пропущен» в той же записи
 `job-timeout/<X>/<id>`) → `FAILED`
 `error="job-timeout: <age> с > FullTimeoutSec"` → переснятие по общему
 бэкоффу. Возрастной бюджет — ПЕРВЫЙ гвард супервизии активного:
 вердикт `FAILED` по возрасту — самостоятельный факт etcd (`started_unix` +
 часы воркера), docker/API-доступ не требуется; transient-пропуск источника
 (portalloc/engine/receiver) бюджет НЕ откладывает (операции с возрастом >
 6 ч нечем оправдаться); PLANNED без запуска — FAILED без cancel, как
 раньше. Verify-операция running дольше `Job:VerifyTimeoutSec` (default 6 ч;
 возраст — `started_unix` из GET-снимка операции приёмника) →
 `POST /api/ops/cancel` best-effort, кандидат остаётся PENDING с
 `checked_unix = now` (попытка зачтена, лив-лок немедленных перезапусков
 исключён; вердикт FAILED по таймауту НЕ ставится — данные не виноваты).
 Restore-фаза (RUNNING заявки) старше `Job:RestoreTimeoutSec`
 (default 24 ч — канон §10 допускает «часами», сутки — явный завис) →
 снос первой ноды (restore-операция уходит с ней, volume — тем же путём) +
 `FAILED` `restore-job-timeout` с чисткой щита initialize;
 REJOINING не таймаутится (бюджеты Patroni-проб — свои, arch/14).
 Бюджет наката WAL внутри restore/drill-операции —
 `Restore:RecoveryTimeoutSec` из команды (§3.5).
- **Patroni/HA не затрагивается**: бэкапы — сторонние клиенты нод; изменений
 в конфиги нод/HA-контура подсистема не вносит.

## 7. Секреты

- **Per-install, env воркера** (не etcd, не git): (а) **bucket
 per-install** — env `PGW_BACKUP_S3_BUCKET` (конфиг-биндинг
 `PgWorker:Backups:S3:Bucket`, группа транспортных секретов
 [14-pgworker.md](14-pgworker.md) §4 п.3; единый на всех нодах всех пулов
 установки, §5); (б) **креды пулов — per-cluster secrets в etcd**:
 `/s3/clusters/<C>/secrets` ([23-s3-clusters.md](23-s3-clusters.md) §6;
 ключ `name=backups`, read-write) — воркер читает их резолвером пула
 живым резолвом на каждом тике (отсутствие/битость secrets —
 transient-отказ резолва с маркером `s3-pool-exhausted` у процессов,
 ретраи тиком, НЕ краш тика — §4); единого
 `PGW_BACKUP_S3_ENDPOINT/REGION/ACCESS_KEY/SECRET_KEY/ADVERTISED_ENDPOINT`
больше нет — цели даёт пул per-cluster (§4); (в) **etcd-слепки —
ОТДЕЛЬНАЯ per-install env-пара** `PgWorker:Snapshots:Export:S3`
(env `PGW_SNAPSHOTS_S3_ENDPOINTS/BUCKET/ACCESS_KEY/SECRET_KEY`) —
обязательна при `Snapshots:Export:Enabled=true` (fail-fast старта,
[14-pgworker.md](14-pgworker.md) §8); цели — запятая-список URI,
перебор до первого доступного (§5); `PGW_BACKUP_S3_*` для слепков НЕ
 переиспользуется: источник правды о DR-слепках не живёт в
 восстанавливаемом etcd. Приёмник WAL целей/кредов в env НЕ получает —
 резолвит сам из etcd
 живым резолвом (§3 «Агент»: policy.s3 → пул → secrets; пароль
 `backup_exec` из `/clusters/<C>/backup_password`) — тем же резолвом
 пользуется операция полного (§2; команда `POST /api/backup/full` несёт
 только `id`). Tool-операции (verify/restore/drill) — полный
 S3-контекст read-списка в POST-команде запуска от воркера (endpoints/
 креды/bucket/префикс; секреты ТОЛЬКО в POST — не в GET-статусах, не в
 логах). env контейнера ноды
 несёт только per-install bucket (`PGW_BACKUP_S3_BUCKET`), путь staging
 полного (`PGW_BACKUP_STAGING_DIR`) и опциональный CA (ниже). Bucket в env ноды отсутствует (пустой `S3:Bucket` —
 инконсистентность инсталляции, валидация старта воркера §9 её
 исключает) ⇒ приёмник стоит в `waiting_policy` с диагностикой в
 `error` — старт-отказа живого процесса нет: приёмник восстановится
 сам при появлении env (рестарт ноды/EnsureNode).
 Стенд/контур-режим:
 адресация S3 всех потребителей контура — по имени сети (`http://owns3:9000`
 на стенде); хост-публикация хранилища — только для внешних потребителей
 (чеки с хоста, mc-миграция, оператор). Прод — endpoints нод пула
 (`endpoints`-ключ + portalloc, arch/23 §7). Точка расширения: статические
 внешние цели (`external`, вне `/s3/`) в env воркера — вне задачи (roadmap: s3-external-targets).
- **Доверие CA при https-endpoint** (TLS-режим ownS3,
 [owns3/03-protocol.md](../OwnS3/arch/owns3/03-protocol.md) §6): per-install CA
 (`ca.pem` TLS-пакета `deploy/tls/`). Воркер: env
 `PGW_BACKUP_S3_CA_BUNDLE_PATH` → конфиг
 `PgWorker:Backups:S3:CaBundlePath`; при заданном пути SDK-клиент воркера
 (BackupS3, снапшеты etcd) доверяет CA **программно — фабрика HttpClient
 с валидацией корня цепочки сервера по отпечатку CA** (env `AWS_CA_BUNDLE`
 линейкой AWSSDK.Core 3.7.x не читается — эмпирический факт) — единый
 per-install пакет на ВСЕ цели (ноды всех пулов и слепочная пара;
 per-пул CA не вводится); путь не
 задан (http-endpoint) — фабрика не ставится, поведение прежнее;
 нечитаемый/пустой файл CA — отказ с диагностикой. Приёмник
 (контейнер на любом docker-хосте — файл хоста воркера в нём недоступен):
 CA передаётся значением PEM в env ноды
 (`PGW_BACKUP_S3_CA_PEM` — его ставит EnsureNode из
 `CaBundlePath` воркера); приёмник материализует
 PEM во временный файл и передаёт его тем же `CaBundlePath` (та же
 фабрика доверия) — и стриму, и операции полного (§2). Ops-операции
 (verify/restore/drill):
 PEM в POST-команде (`ca_pem`), приёмник материализует тем же порядком.
 http-endpoint — переменные не заданы, поведение прежнее.
- **Per-cluster БД-роль** `backup_exec` (LOGIN + REPLICATION): пароль
 per-cluster `/clusters/<C>/backup_password` — по образцу прочих per-cluster секретов
 (ensure put-if-absent, ротация в общем тикете §9.8, 32 симв
 `[A-Za-z0-9]`). Отдельная от
 bucket_mover (иная зона доверия/ротации).
- **pg_hba-гвард**: дефолтный Spilo-pg_hba разрешает replication-соединения
 только роли `standby` — физический WAL-стриминг `pg_basebackup` под
 `backup_exec` отсекается. Гвард G2 (каждый тик) командует приёмнику КАЖДОЙ
 ноды шарда `POST /api/node/hba-ensure` (канал [25](25-component-communications.md)
 №22): приёмник в своём контейнере добавляет идемпотентную строку
 `hostssl replication backup_exec all scram-sha-256` в ИСТОЧНИК конфига
 Patroni `/run/postgres.yml` (секция `postgresql.pg_hba`) и будит Patroni
 SIGHUP'ом — тот сам перегенерирует `pg_hba.conf` при каждом старте postgres
 уже с этой строкой (правка самого `pg_hba.conf` бессмысленна: файл
 перегенерируется Patroni). Ожидание применения — поллинг `$PGDATA/pg_hba.conf`
 (нода без PG_VERSION ещё бутстрапится — ждать нечего, строка применится при
 первом старте). Отказ операции — transient: шард skip, следующий тик
 дообеспечит (запуск на непатченной ноде карался бы FAILED-циклом с бэкоффом).

| ×2 стрим-трафик двойной архивации + второй буфер сегмента | осознанная плата избыточности источника (§3); домашняя установка — 1–2 кластера |
| Npgsql не экспонирует TIMELINE_HISTORY протокола | рантайм-чтение — сырой приватный `ReadSingleRow` Npgsql 10.0.3 (public `TimelineHistory` сломан: сервер с PG ≥ 14 объявляет колонку content как `text`, парсер кастует к `byte[]` → InvalidCast на каждом запросе; апстрим npgsql#6709 не выпущен) с нормализацией text/bytea к байтам; сбой обхода (смена приватного API) → fallback канона §3: приёмник читает `pg_wal/<TLI>.history` файловой системой своей ноды (контейнер общий с PG) и грузит объект сам; недоступен и файл — факт `history_missing` в статус-ключе (диагностика). ПЛАН: при обновлении Npgsql до версии с выпущенным фиксом `TimelineHistory` (ориентир — 11) убрать обход, вернуться к публичному API |
| Смешанный сегмент точки failover-переключения (TLI1→TLI2 внутри одного 16-МиБ сегмента) | приёмник закрывает сегмент по границе LSN — объект содержит байты обоих таймлайнов; восстановимость через точку переключения опирается на replay-континуальность postgres (промоутнутая нода начинает новую TLI с END_OF_RECOVERY-записи, restore-накат читает её в том же сегменте); восстанавливаемость через точку переключения проверяется docker-E2E `E2eTliSwitchScenarios`: restore latest и target_time по одному исходному полному через смешанный сегмент (сегмент — единственный объект под именем TLI родителя; строгий факт + побайтовое подтверждение: switchWALLSN внутри сегмента, page-заголовки по обе стороны точки показывают TLI1/TLI2); склейка `.history` и непрерывность CheckWithRestart ПОСЛЕ промоута, restore ЧЕРЕЗ точку переключения |
| Длинные имена `<C>-<X>` ломают имена слота/контейнера | слот — sha1-усечение (§3); имена контейнеров — те же ограничения, что у pgw-нод (существующая практика) |
| Переполнение staging полного («нет места» — частый сбой бэкапов) | staging — каталог в data-volume ноды (`Staging:Dir`, §2), отдельной квоты нет; ENOSPC ловится реактивно (падение `pg_basebackup`/IOException put) → FAILED с однострочной причиной + суточный алерт (§6) |
| Restore перезатирает данные живого шарда (ошибка оператора) | обязательный `confirm` = имя шарда в API (мисматч → 400); максимум один активный restore на шард; runbook проговаривает необратимость (RPO = точка бэкапа/WAL-цели) |
| PITR-назад (target_time) несшиваем с прежней WAL-цепочкой (новая TLI с меньшими номерами сегментов) | по COMPLETED restore ключ `wal` удаляется → планировщик §2 немедленно переснимает полный → новая цепочка от новой точки (§3.5); старые S3-объекты не трогаются |
| Долгий накат WAL (большая база/длинная цепочка) — restore-операция часами | бюджет `Restore:RecoveryTimeoutSec` + фазы в GET-статусе операции (оператор видит прогресс); резюмов нет — повтор заявки качает заново (осознанная плата plain-механики) |
