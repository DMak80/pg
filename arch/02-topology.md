# 02. Топология стенда

Прежде чем деплоить — зафиксируем конкретные адреса, диски и порты. Этот файл —
**таблица подмен**: при развёртывании на реальном железе меняешь IP/имена/диски на свои,
остальное остаётся прежним.

---

## 1. Номинальная схема (пример для стенда)

| Роль | Имя хоста | IP (пример) | Что крутится | Диск под данные |
|---|---|---|---|---|
| Нода 1 | `pg1` | `10.0.0.11` | etcd1 + pg1 (Spilo) | `/dev/sdb1` → `/data/pg`<br>`/dev/sdc1` → `/data/etcd` |
| Нода 2 | `pg2` | `10.0.0.12` | etcd2 + pg2 (Spilo) | аналогично |
| Нода 3 | `pg3` | `10.0.0.13` | etcd3 + pg3 (Spilo) | аналогично |
| Балансировщик | `pg-lb` | `10.0.0.10` | HAProxy | — (stateless, можно без отдельного диска) |

> HAProxy можно ставить:
> - на **отдельную** ноду `pg-lb` (рекомендуется, чтобы отказ БД-ноды не задевал точку входа),
> - либо **на одну из БД-нод** (дешевле для маленького стенда; при отказе этой ноды точка
>   входа тоже упадёт — поднимайте HAProxy на нескольких нодах + VIP/DNS round-robin для
>   надёжности).

### Вариант «всё на 3 нодах» (HAProxy на каждой)
Для максимальной отказоустойчивости точки входа HAProxy запускают **на всех 3 нодах** +
выносят единый VIP (keepalived / metallb / cloud LB). Тогда отказ любой ноды не рвёт
соединения к LB. Это описано отдельно в `08-operations.md` → «HAProxy HA».

## 2. Сетевые требования

Между всеми нодами должны быть открыты:

| Порт (src→dst) | Назначение |
|---|---|
| `2379/tcp` | Patroni/HAProxy → etcd client API |
| `2380/tcp` | etcd ↔ etcd (peer gossip/raft) |
| `5432/tcp` | Patroni(leader) → Patroni(replica) streaming replication; HAProxy → PG |
| `8008/tcp` | HAProxy/мониторинг → Patroni REST API |
| `22/tcp` | ssh (админ) |

**Важно:** все эти адреса должны быть **стабильны** (статические IP или постоянные DNS).
При смене IP ноды ей нужно обновить `PATRONI_NAME`/`PATRONI_<NODE>` в конфиге и рестартовать
Patroni.

### DNS / /etc/hosts
На каждой ноде пропиши имена остальных, чтобы конфиги читались человеком и не зависели от DNS:
```bash
# /etc/hosts (одинаково на pg1, pg2, pg3, pg-lb)
10.0.0.10  pg-lb
10.0.0.11  pg1
10.0.0.12  pg2
10.0.0.13  pg3
```

## 3. Диски и файловые системы

Рекомендация для прод-ноды:

| Каталог | Назначение | FS | Размер (стартовый) | Примечание |
|---|---|---|---|---|
| `/data/pg` | PGDATA + WAL | **XFS** или ext4 | от 100 ГБ | отдельный блочный том; WAL можно вынести в `/data/pg/wal` |
| `/data/etcd` | данные etcd | ext4 | 10–20 ГБ | **быстрый диск** (etcd чувствителен к fsync latency) |
| `/var/lib/docker` | docker | ext4 | 50+ ГБ | образы/слои |

### Почему отдельный том под PGDATA
- Изолированный бюджет IOPS — postgres не «душит» систему и наоборот.
- Легко расширять (LVM/cloud volume) без переустановки.
- Проще бэкап/снапшот на уровне тома.

### Заметка про скорость etcd
etcd пишет на диск каждое согласование. Если диск медленный (>10мс fsync) — etcd становится
узким местом всего кластера (Patroni ждёт DCS). Для прод ставьте etcd на **SSD/NVMe**.

## 4. Шаблон: заполнить под свой стенд

Перед деплоем заполни и держи рядом (или закоммить в private-репо с секретами):

```ini
# topology.env — отредактируй под свой стенд

# === Имена и IP нод ===
NODE1_HOST=pg1
NODE1_IP=10.0.0.11

NODE2_HOST=pg2
NODE2_IP=10.0.0.12

NODE3_HOST=pg3
NODE3_IP=10.0.0.13

LB_HOST=pg-lb
LB_IP=10.0.0.10

# === Пути к данным ===
PG_DATA_DIR=/data/pg          # куда монтируется PGDATA внутри контейнера Spilo
ETCD_DATA_DIR=/data/etcd      # данные etcd

# === Сетевой диапазон кластера (для firewall) ===
CLUSTER_CIDR=10.0.0.0/24

# === Образы (см. 03-prerequisites.md) ===
SPILO_IMAGE=ghcr.io/zalando/spilo-16:3.3-p3
ETCD_IMAGE=quay.io/coreos/etcd:v3.5.21
HAPROXY_IMAGE=haproxy:2.8-alpine

# === Учётные данные (СЕКРЕТ — в vault/secret-manager, не в git) ===
PG_SU_USER=postgres
PG_SU_PASSWORD=<CHANGE_ME_strong>
PG_REPL_USER=standby
PG_REPL_PASSWORD=<CHANGE_ME_strong>

ETCD_CLIENT_TOKEN=pgcluster-etcd-token-2026

# === Имя кластера (scope) — одинаковое на всех нодах ===
SCOPE=pgcluster
```

> В примерах конфигов в `configs/` переменные берутся из такого файла через `env_file:`.
> Значения выше — примерные; **обязательно замени IP/пароли** на свои.

## 5. Проверка готовности сети

Перед деплоем прогони на каждой ноде:

```bash
# должно отвечать со всех трёх нод
for h in pg1 pg2 pg3; do
  echo "=== $h ==="
  ping -c2 $h || echo "FAIL: нет маршрута до $h"
done

# порты между нодами (после поднятия сервисов — для проверки)
# nc -zv pg2 2380   # etcd peer
# nc -zv pg2 8008   # patroni api
```

Если хоть один `ping` упал — чини сеть/firewall/DNS, дальше бесполезно.
