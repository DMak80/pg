# EtcdWorker: DR-слепки и выгрузка в S3

Уровень 3. Функция «DR-слепки»: плановое и внеочередное снятие слепков etcd,
выгрузка в etcd-backup кластер, доводка отставания и обслуживание контура.
Форматы объектов и статус-ключа —
[00-etcd-contract.md](00-etcd-contract.md) §3, [19-backups.md](../19-backups.md) §5;
полный автомат — [C. SnapshotExport](processes/c-snapshot-export.md).

## 1. Цель выгрузки

- **Единственный** S3-кластер с признаком `etcd_backup=true` в
  `/s3/clusters/` — живой резолв на каждом проходе (range config'ов →
  признак; единственность гарантирует гвард создания —
  [s3worker/07-api.md](../s3worker/07-api.md) §3).
- **Bucket — фиксированная константа `etcd-backups`**, одинаковое имя на всех
  установках: создаёт S3Worker на каждом инстансе кластера при provisioning
  дополнительно к per-install bucket
  ([s3worker/02-cluster-lifecycle.md](../s3worker/02-cluster-lifecycle.md) §5);
  имя не конфигурируется, per-install env-пар S3 у воркера нет.
- **Креды/endpoints** — из `/s3/clusters/<C>/{endpoints,secrets}` (ключ
  `backups`, read-write; для etcd-backup кластера значение — спец-ключ из env
  S3Worker, [s3worker/04-security.md](../s3worker/04-security.md) §1).
- **Отказы цели** (кластера с признаком нет / `TO_REMOVE` / битые secrets) —
  статус `FAILED` с маркером `etcd-backup-missing` (панельный алерт;
  transient для цикла — ретраи тиком), НЕ краш воркера. Слепки при этом
  продолжают сниматься локально и догоняются после появления кластера.

## 2. Снятие

`SnapshotJob` (Shared.Etcd) снимает весь контур через `/v3/snapshot/save`
(failover по endpoints) в локальный том `/snapshots` (ретенция
`RetentionFiles`). Том — **кэш доводки**: источник истины для восстановления
— выгруженные объекты S3, а не локальные файлы.

## 3. Расписание

- **Плановое** — раз в `IntervalMin=360`.
- **Внеочередное** — детекция изменений: тик цикла (сон `ScanIntervalSec`,
  пульсирующий) читает revision кластера; revision вырос, а последняя
  выгрузка старше `MinIntervalSec=300` → слепок снимается и выгружается
  немедленно. RPO контроль-плейна ≈ 5 мин при активности и без лишних
  слепков в тишине.
- **Отставание** (по статус-ключу: `FAILED`, ключа нет или новейший локальный
  слепок снят позже подтверждённого покрытия) — короткий сон
  `RetryIntervalSec=300` вместо планового интервала: окно транзиента
  закрывается минутами, а не следующим плановым слепком.

## 4. Выгрузка

Каждый снятый слепок уезжает **новой парой** объектов:
`etcd/snapshot-<id>.db` + `etcd/snapshot-<id>.meta.json`
(sha256/size/revision/taken/uploaded/instance; layout
[19-backups.md](../19-backups.md) §5 без изменений).

- **Порядок**: put `.db` (серверная SHA256-проверка транспорта) → put
  `.meta.json` → ретенция N=28 пар (guard ≥ 1) → статус-ключ.
- **Статус** пишется с семантикой покрытия: `last_uploaded_unix` — метка
  покрываемого слепка (время снятия, не заливки), `last_object` — объект,
  реально лежащий в S3 ([00-etcd-contract.md](00-etcd-contract.md) §3).
- **Доводка (CatchUp)** — до снятия и повторным расчётом после: отстающая
  выгрузка догоняется новейшим локальным слепком тем же конвейером
  (промежуточные невыгруженные слепки — нижние ревизии того же ряда, для
  восстановления важен последний), успех продвигает покрытие и закрывает
  окно. Первый транзиент мог перевести статус в `FAILED` уже после расчёта
  «до» — без пере-расчёта цикл ушёл бы в длинный сон с невыгруженным
  слепком.
- **Бюджет** — единый `TimeoutSec=30` на всю попытку (put'ы + ретенция +
  статус суммарно); S3-шаги несут per-попыточный таймаут и «пульс конечного
  внешнего вызова» ([06-operability.md](06-operability.md) §3). Любая
  неудача — `FAILED` + `error`, поля последнего успеха сохраняются, снятие не
  откатывается; все шаги идемпотентны (put поверх; коллизия имён в одну
  секунду — новее поверх).

## 5. Обслуживание контура

Compact + defrag каждой ноды последовательно, не чаще
`MaintenanceIntervalMin=60` — этот же лидерный цикл (второй исполнитель
исключён; зоны maintenance/экспорта у PgWorker демонтированы,
[14-pgworker.md](../14-pgworker.md) §6/§8). Отказ обслуживания — warning, тик
не фейлит.

## 6. S3-клиент

AWSSDK-клиент по образцу `BackupS3`: `PathStyle` (ownS3 обслуживается одним
клиентом), per-попыточный таймаут запроса, SHA256-проверка put (несовпадение
— `BadDigest` от сервера), программное доверие CA https-эндпоинта из
`Snapshots:S3:CaBundlePath` (переменную `AWS_CA_BUNDLE` AWSSDK не читает);
креды и endpoints — из резолва §1 на каждую попытку, клиент — per-попытку.
