## S10. Изменения из etcd применяются только при изменении: опрос + кэш + различия

**Правило.** Ни один процесс (воркеры, панель, диагностика) не
пере-применяет etcd-состояние на каждом тике/цикле: применение etcd на
каждом тике — безумно дорогая операция (владелец). Модель — ПРОСТАЯ,
watch/лог событий etcd НЕ используется (выбор владельца):
1. **Периодический опрос** — Range наблюдаемого префикса раз в N секунд
   (существующий цикл процесса: тик воркера, refresher панели);
2. **Локальный кэш** последнего прочитанного состояния
   (ключ → значение; при необходимости + mod_revision);
3. **Сравнение** прочитанного с кэшем: обработка и применение — ТОЛЬКО
   различия (изменённые/добавленные ключи; ключи кэша, отсутствующие в
   прочитанном — УДАЛЕНИЯ: сравнение с кэшем видит их без watch);
4. **Различий нет — не делается ничего**: ни применений, ни пересчётов,
   ни уведомлений потребителей;
5. **Применение** во внешние системы (PG, docker, панель-API) — только при
   фактическом изменении значения (сравнение с применённым; для
   необратимых verifier'ов — пересчёт от etcd-значения,
   [backups/08-secrets.md](../backups/08-secrets.md) §3).
Дорогая часть — применения и пересчёты, а не чтение: range малых
префиксов (≤ нескольких тысяч ключей) дёшев и остаётся циклом процесса;
интервалы опроса — существующие интервалы циклов (не сокращаются и не
растягиваются этой моделью).

**Почему критично.** Тик воркера применял etcd-состояние целиком на
каждом тике: ensurer'ы перечитывали по 7 ключей на кластер и выравнивали
без проверок, панель пересобирала снапшот и пересчитывала алерты каждые
3 с независимо от наличия изменений — постоянная работа растёт линейно с
числом кластеров и ключей и ложится на все компоненты контура
(в деградации, t08, каждая операция ещё и платила штрафы недоступности).

**Кейс.** Стенд 2026-11-02: панель каждые 3 с пересобирала снапшот и
пересчитывала правила при неизменном etcd; воркер каждые ~5 с
пере-применял секреты и конфиги без факта изменения. Владелец:
«ПРИМЕНЕНИЕ ETCD НА КАЖДОМ ТИКЕ — БЕЗУМНО ДОРОГАЯ ОПЕРАЦИЯ»; предложенная
владельцем модель «полить раз в N секунд и сравнить с кэшем, обрабатывать
только различия» принята; watch-вариант (лог событий etcd) отклонён как
избыточный.

**Проверка.** Юниты кэша-сравнения (нет различий → нет событий/применений;
add/change/delete обнаруживаются; удаление = ключ кэша отсутствует в
прочитанном); в процессах применения во внешние системы — только по факту
изменения (юнит «нет изменения → записи нет»).

**Нормативная формулировка владельца (дословно, определение модели):**
«полить раз в N секунд и сравнивать, что у нас есть в памяти (в кеше) и что
пришло из etcd, и если что-то различается — это и обрабатывать»; «если не
получили — то, когда получим, тогда и сравним». Никаких дополнительных
условий (исход тика, счётчики отказов, принудительные пересборки после
сбоев) в модель добавлять запрещено — это её искажение.
