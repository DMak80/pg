## S4. Ключи не вырождаться: предикаты — на первоисточнике

**Правило.** Идентичность/роли/принадлежность нельзя выводить из значения
etcd-ключа, которое может **выродиться** (стать одинаковым у разных
сущностей). Предикаты («кто мастер», «чей это») строятся на
первоисточнике — прямых пробах владельца истины (Patroni REST `/primary` и
т.п.); etcd-ключи — маршрутизация/кэш, не истина о роли.

**Почему критично.** Вырожденное значение (host:0, port:0, пустая строка)
матчится в ОБЕ стороны: резолв «мастера по значению ключа» возвращает
произвольную ноду — DDL уходит на реплику (read-only), детекция смены
мастера «по изменению значения» не срабатывает вовсе.

**Проверка.** При проектировании ключа — прогонять вопрос «какое значение
даёт режим/конфиг, при котором ключ перестаёт различать сущности?»;
юнит-тест на вырожденном значении.

## S5. Порядок мутаций: клэйм или время, фиксированный порядок, первый — истина

**Правило.** Изменения общего состояния идут **либо** под клэймом (lease,
txn `version==0` + put-with-lease, смерть держателя → TTL — клэйм-паттерн),
**либо** строго периодическими тиками — но последовательность записей
внутри мутации **всегда одинаковая**. При гонке источником истины является
**первый записавший** — остальные обязаны дочитать его состояние и
догнать, а не перезаписать своё поверх.

**Владение клэймом — на всём протяжении мутации, а не только на входе
тика** (тик — до единиц минут, lease TTL — 15 с; иначе takeover даёт двух
писателей в один префикс). Механика ClaimStore (`Shared.Etcd`):
1. **cancellation-гвард** — держатель клэйма/лидера несёт per-cluster
   cancel-токен; тик линкуется с ним после захвата, потеря lease (провал
   keepalive ≤5 с, release, dispose) отменяет токен — исполняющиеся операции
   тика (etcd/docker/SQL — все принимают токен) прерываются, журнал получает
   фазу `lease-lost`; docker-остатки прерванного шага добивает декларативная
   сверка следующим тиком/инстансом (self-healing);
2. **живая сверка владения (`EnsureClaimAlive`)** — перед критическими
   мутациями длинных процессов (пересоздания/сносы нод, старты джобов,
   cutover переездов, финалы restore) — чтение ключа клэйма: ключа нет,
   чужой или etcd недоступен — мутация не начинается (P9), журнал — фаза
   `claim-lost/<фаза>`.

**Почему критично.** Два вольных писателя в один префикс = потерянные
обновления и «мигающие» состояния; без фиксированного порядка нет
воспроизводимого расследования (логи двух тиков не сопоставимы).

**Кейс.** параллельное довыделение портов из разных инстансов →
глобальный portalloc-клэйм `/pgworker/locks/portalloc` (захват, «не взял» →
ожидание следующего тика без мутаций). Обратная сторона — чтение:
детерминизация E2E-тестов построена на наблюдении **первого элемента**
изменения (заявка `op=finalize` появляется ДО kill-фазы) — ожидание этого
маркера устранило гонку тест↔воркер.

**Проверка.** Каждый новый писатель общего префикса — обоснование в arch:
под чем пишем (клэйм/тик), порядок записей, кто истина при гонке.

## S6. Журналы: фазовые записи не затирают накопленные треки

**Правило.** Служебный журнал (`/pgworker/work/<C>` и аналоги) хранит
**накопленные во времени данные** (unreachable-трек нод — основа порогов
NodeDead/ShardDead/эвакуации). Фазовые записи процессов (adopt/rotate/
scale/move) обязаны **сохранять** эти поля: read-modify-write с сохранением
тека, полный rewrite — только владельцу трека (supervise).

**Почему критично.** Затирание трека фазовой записью сбрасывает пороги
**каждый тик**: часы смерти ноды «не насчитываются», эвакуация не стартует
вовсе — отказ выглядит как вечное «почти готово».

**Кейс.** Фазовые записи всех процессов затирали unreachable-трек
supervise → эвакуация AC6 не стартовала. Фикс: `WritePhaseAsync` сохраняет
тек (+ optional-параметр), adoption уважает трекнутые ноды.

**Проверка.** Unit: фазовая запись не меняет трек; смешение писателей
(фаза после supervise) — трек прежний.

**Следствие.** Журнал — «последняя фаза побеждает», НЕ лог-история:
считать события через тики по нему нельзя (каждая запись затирает
предыдущую). Наблюдаемость «происходит ли мутация» строится на
Version/ModRevision целевого ключа, а не на подсчёте записей журнала
(идемпотентность конвергенции DCS — по mod_revision
`/service/<scope>/config`).
