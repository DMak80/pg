# 17. Принципы синхронизации распределённого состояния ★

Канон «как надо» для любых компонентов, работающих с общим состоянием в
etcd/DCS: воркеры (PgWorker/KafkaWorker), панель, Patroni-сады, тестовые
фикстуры, диагностические инструменты. Каждый принцип: **правило → почему
критично → кейс → чем проверяется**. Выведено из вскрытых дефектов регрессии
E2E (задача t09, 2026-09-03, журнал —
`docs/superpowers/2026-09-03-t09-e2e-release-regression/spec.md` §8) и
предшествующих задач (t90 — portalloc-клэйм). Новые компоненты синхронизации
проектируются по этим принципам (arch-first); реестр пополняется по мере
вскрытия новых ошибок использования — тем же форматом.

## S1. Один контур истины: единый etcd

**Правило.** Все участники системы (воркеры, Patroni-ноды, панель,
эмуляторы, инструменты) обязаны работать с **одним** etcd-кластером; адрес
передаётся явно (env/конфиг при старте), никак не «по умолчанию/обнаружению».
В тестовых контурах etcd фикстуры слушает динамический порт — инструменты
находят его по фактическому mapped-порту контейнера, а не по литералу.

**Почему критично.** Два «живых» etcd в одном эксперименте = каждый
участник видит свою картину мира: записи исчезают, лидеры «не выбираются»,
диагностика молчит. Второй etcd появляется легко: на хосте живёт стенд
(порт 2379), тест поднял свой — инструмент, взявший «первый попавшийся
etcd», читает чужое пустое состояние.

**Кейс (t09).** Диагностический сэмплер брал «etcd с ->2379» из `docker ps`
— на хосте это стендовый as-etcd, где ключей тестового кластера нет:
наблюдение «master=<NULL> всё время» было **ложным** (чужой etcd) и чуть не
стало основой неверного диагноза. Переход на поиск по образу+mapped-порту
контейнера фикстуры дал корректные данные.

**Проверка.** Диагностика любого «странного» состояния начинается с
сверки фактических endpoints ВСЕХ участников (docker inspect env, логи
подключений) — см. S9.

## S2. Динамический конфиг DCS ≠ bootstrap: конвергенция обязательна

**Правило.** `bootstrap.dcs` (SPILO_CONFIGURATION и аналоги) применяется
**только при первой инициализации** кластера в DCS. Далее живёт
**динамический конфиг** (`/service/<scope>/config`, REST `GET/PATCH
/config`), который может быть дефолтным, чужим или мусором от прошлого
прогона — и он **приоритетнее** локального. Владелец кластера (воркер)
обязан в надзоре **конвергить динамический конфиг к канону**: сверять
каждый тик, патчить только расходящиеся поля, сбой сверки — транзиент
(повтор тиком), не авария. Полагаться на «ноды стартуют с env-оверрайдами»
нельзя — DCS побеждает локальный конфиг.

**Почему критично.** Нода, подтянувшаяся к кластеру с дефолтным DCS-конфигом,
работает на дефолтных таймингах: в Patroni это ttl=30/loop_wait=10 → failover
десятки секунд. Никакой env её не спасёт — параметры живут в DCS.

**Кейс (t09).** Обе ноды e2e-кластера работали с динамическим DCS-конфигом
ttl=20 при контрактном `bootstrap.dcs` ttl=5 — тайминги «уезжали» бесследно
для наблюдателя. Фикс: `NodeSupervisor` конвергит `/config` к канону
`PatroniTimings` (arch/14 §5 C; unit-паттерн «канон — не патчим,
расхождение — патчим»).

**Проверка.** Unit: конвергенция при чужом/дефолтном конфиге; отсутствие
мутаций при каноне. Live: `GET /config` обеих нод кластера — значения
совпадают с каноном.

## S3. Инварианты внешних систем и плавающие версии: канон в одном источнике

**Правило.** Заявляемые параметры внешней системы обязаны удовлетворять её
инвариантам (для Patroni 4.x: `ttl ≥ 2·retry_timeout + loop_wait`, пол
ttl=20). Канонические значения живут в **одном источнике** в коде
(`PatroniTimings`), отражаются в arch (§2.1) и эталонах (`pg.env`), —
дублирование значений по файлам запрещено (только ссылка). Базовые образы —
плавающие теги: новая версия может молча изменить полы/семантику.

**Почему критично.** Patroni **молча** поднимает невыполнимый ttl до пола и
**пишет изменённое значение обратно в DCS** — заявленное «5 секунд»
превращается в 20 без единого сообщения об ошибке. Плавающий тег образа
привозит новую версию Patroni пересборкой: регрессия приезжает «без нашего
коммита».

**Кейс (t09).** Регрессия E2E 29.08→02.09 приехала пересборкой слоя
`ghcr.io/zalando/spilo-18:4.1-p2` (Patroni 4.1 `_validate_and_adjust_timeouts`),
а не коммитами репозитория; «ttl=5» всегда был ложью на этой версии.
Фикс: канон ttl=20/loop_wait=1/retry_timeout=3 (инвариант 2·3+1=7≤20
выполнен), единый источник + конвергенция S2 + эталон `pg.env`
синхронизирован.

**Проверка.** Unit: инвариант значений канона; `PatroniTimings` ↔
SPILO_CONFIGURATION ↔ `pg.env` — один источник. Кандидат в roadmap: пин
базовых образов по digest.

## S4. Ключи не вырождаться: предикаты — на первоисточнике

**Правило.** Идентичность/роли/принадлежность нельзя выводить из значения
etcd-ключа, которое может **выродиться** (стать одинаковым у разных
сущностей). Предикаты («кто мастер», «чей это») строятся на
первоисточнике — прямых пробах владельца истины (Patroni REST `/primary` и
т.п.); etcd-ключи — маршрутизация/кэш, не истина о роли.

**Почему критично.** Вырожденное значение (host:0, port:0, пустая строка)
матчится в ОБЕ стороны: резолв «мастера по значению ключа» возвращает
произвольную ноду — DDL уходит на реплику (read-only), детекция смены
мастера «по изменению значения» не срабатывает вовсе.

**Кейс (t09).** При `EnableDoorman=false` мастер-ключ легитимно вырождается
в `host:0` (недискриминантен, arch/14 §2.4 п.5): тест детектировал failover
по изменению значения (не менялось) и матчил мастера по doorman-порту
(матчились обе ноды — seed на реплику 25006). Фикс: факт смены мастера — по
пробам `/primary`, ключ — маршрутизация.

**Проверка.** При проектировании ключа — прогонять вопрос «какое значение
даёт режим/конфиг, при котором ключ перестаёт различать сущности?»;
юнит-тест на вырожденном значении.

## S5. Порядок мутаций: клэйм или время, фиксированный порядок, первый — истина

**Правило.** Изменения общего состояния идут **либо** под клэймом (lease,
txn `version==0` + put-with-lease, смерть держателя → TTL, t90-паттерн),
**либо** строго периодическими тиками — но последовательность записей
внутри мутации **всегда одинаковая**. При гонке источником истины является
**первый записавший** — остальные обязаны дочитать его состояние и
догнать, а не перезаписать своё поверх.

**Почему критично.** Два вольных писателя в один префикс = потерянные
обновления и «мигающие» состояния; без фиксированного порядка нет
воспроизводимого расследования (логи двух тиков не сопоставимы).

**Кейс.** t90: параллельное довыделение портов из разных инстансов →
глобальный portalloc-клэйм `/pgworker/locks/portalloc` (захват, «не взял» →
ожидание следующего тика без мутаций). t09 (обратная сторона — чтение):
детерминизация E2E-тестов построена на наблюдении **первого элемента**
изменения (заявка `op=finalize` появляется ДО kill-фазы) — ожидание этого
маркера устранило гонку тест↔воркер.

**Проверка.** Каждый новый писатель общего префикса — обоснование в arch:
под чем пишем (клэйм/тик), порядок записей, кто истина при гонке.

## S6. Журналы: фазовые записи не затирают накопленные треки

**Правило.** Служебный журнал (`/pgworker/work/<C>` и аналоги) хранит
**накопленные во времени данные** (unreachable-трек нод — основа порогов
NodeDead/ShardDead/эвакуации). Фазовые записи процессов (adopt/rotate/
scale/move) обязаны **сохранять** эти поля: read-modify-write с сохранением
тека, полный rewrite — только владельцу трека (supervise).

**Почему критично.** Затирание трека фазовой записью сбрасывает пороги
**каждый тик**: часы смерти ноды «не насчитываются», эвакуация не стартует
вовсе — отказ выглядит как вечное «почти готово».

**Кейс (t09).** Фазовые записи всех процессов затирали unreachable-трек
supervise → эвакуация AC6 не стартовала. Фикс: `WritePhaseAsync` сохраняет
тек (+ optional-параметр), adoption уважает трекнутые ноды.

**Проверка.** Unit: фазовая запись не меняет трек; смешение писателей
(фаза после supervise) — трек прежний.

## S7. Транспортный флап ≠ смерть: деструктив — только по положительному свидетельству

**Правило.** «Не отвечает» — НЕ свидетельство смерти. Деструктивные
действия (снятие лидер-ключа Patroni, пересоздание ноды, эвакуация)
допускаются только по **положительному свидетельству**: docker-объект
отсутствует **или** контейнер не-running по инспекции. Причём инспекция
обязана быть **честной**: если драйвер не умеет running-инспекцию
(заглушка Swarm), свидетельство «узла нет в списке» **не считается** —
ветка гейтится capability (`SupportsRunningInspection`), промоушен
остаётся на lease/loop_wait Patroni.

**Почему критично.** Ложное «смерть» по флапу на живом лидере → снятие
leader-ключа → лишний failover продакшн-кластера: доступность роняется
средством её защиты.

**Кейс (t09-review).** Заглушка `SwarmClusterDriver.InspectNodesAsync`
возвращает пустой список: «пусто = не running» дало бы ложный failover в
Mode=Swarm по любому флапу пробы. Фикс: capability-гейт
(arch/14 §5 C) + unit-инверсия (no-inspection → ускорения нет).

**Проверка.** Unit-инверсия на каждом деструктивном пути: «источник
свидетельства врёт/пуст → действия НЕТ».

## S8. Свежесть инструментов: тестируется собранное из текущего кода

**Правило.** Тесты/диагностика запускают артефакт, собранный из текущего
дерева (автосборка в фикстуре до старта контура), отказ сборки и отсутствие
артефакта — fail-fast. Явный opt-out (env-лазейка) — только для
целенаправленных исторических прогонов (бисект), никогда по умолчанию.

**Почему критично.** Устаревший «зелёный» бинар скрывает регрессию:
фикстура молча запускает старый артефакт, тесты проходят, дефект растёт
неделями (маскировка t09: регрессия 29.08→02.09 была невидима именно так).

**Кейс (t09).** `E2eFixture.EnsureAppDllAsync`: автосборка Release до
docker-очистки; `PGW_TEST_E2E_NOBUILD=1` — лазейка бисекта; отсутствие dll
при NOBUILD — ApplicationException с командой сборки.

**Проверка.** Юнит на fail-fast-ветки; правило мерж-гейта в AGENTS.md
(docker-E2E на свежем Release для задач, трогающих код воркеров).

## S9. Порядок расследования: от стабильного к меняемому

**Правило.** Диагностика сбоев синхронизации идёт строго снизу вверх, каждый
уровень — с фиксацией фактов до выводов:

1. **Контур**: все смотрят в один etcd (S1) — сверка фактических endpoints.
2. **Регистрация**: сущности записаны корректно (порты/адреса/роли —
   динамические порты против фактических mapped, S4).
3. **Связность**: участники видят друг друга (репликация, REST-статусы
   членов, кворум).
4. **Детерминизм**: мутации по тикам — одинаковый порядок, опора на первый
   элемент изменения (S5); где разрыв — кто первый не увидел/не записал.

**Почему критично.** Расследование «сверху» (симптом теста) ловит
следствия, а не причину: flipped=False в тесте был следствием трёх
независимых причин на разных уровнях (контур-конфиг DCS, вырожденный
предикат, флап готовности). Каждая «починка следствия» стоила прогона и
маскировала следующую причину.

**Кейс (t09).** Чек-лист 1–4 вскрыл: динамический конфиг ttl=20 (уровень 1–2),
503 Patroni из неготовности (уровень 3), недетерминированные ожидания
тестов (уровень 4). Фиксы по уровням закрыли всё; финальный бюджет failover
≤5 с подтверждён замерами ~3,1–3,2 с.

**Проверка.** Журнал расследования фиксирует факты уровнями; вывод
«механизм словами» — до правки кода (гейт задачи).
