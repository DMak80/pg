# E. RemoveNodeProcess

Уровень 4. Вывод инстанса по маркеру `nodes/<I>/state=TO_REMOVE`. Функция —
[03-node-scaling.md](../03-node-scaling.md) §2; контракт ключей —
[s3-clusters/02-keys.md](../../s3-clusters/02-keys.md); доводка связей —
[05-mesh-governance.md](../05-mesh-governance.md).

За тик выводится ОДИН инстанс; маркер обрабатывается при любом состоянии
инстанса (кроме битой записи).

```
E0 заявка: первый инстанс с state=TO_REMOVE; заявок нет — no-op
E1 ГВАРДЫ ДО деструктива (journal-отказ rejected, без мутаций):
   - последний инстанс кластера — вывод запрещён (пул не может быть пуст,
     состав 1..9; путь к кластеру без инстансов — снос кластера целиком);
   - нет живой RUNNING-ноды кроме выводимой — вывод рвёт последнюю точку
     записи пула
E2 journal(op=remove-node, phase=started) + снапшот P12 «до»;
   state=REMOVING
E3 снос контейнера и volume инстанса (по порт-аллокации; при утрате записи
   объект сносится на всех хостах — 404 = ок, имена s3w-<C>-<I> глобально
   уникальны)
E4 del ключей инстанса (placement, resources, state, placed_on, usage, pki —
   имя освобождается)
E5 имя из denylist кластера (read → remove → put txn по mod_revision; иначе
   deny-доведение потеряет publicKeyPem отозванного инстанса) и запись из
   portalloc (RMW под locks/portalloc)
E6 завершающее окно: RMW endpoints + актуализация config.nodes до
   фактического состава; снапшот P12 «после»; journal done
```

Связи выводимого инстанса сносятся доводкой G: его имя исчезло из состава —
target-записи у соседей «лишние». Отказ данных осознан: volume сносится;
копия — только у инстансов, связанных с ним в `links`
([08-operability.md](../08-operability.md) §6 R1–R2).
