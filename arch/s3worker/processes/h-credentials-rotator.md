# H. SecretRotator (ротация клиентских кредов)

Уровень 4. Rolling-ротация клиентских кредов кластера (root-пара + access
keys). Функция — [04-security.md](../04-security.md) §4; контракт
secrets-ключа — [s3-clusters/06-secrets.md](../../s3-clusters/06-secrets.md); заявка —
[07-api.md](../07-api.md).

Заявка `/s3worker/rotations/<C>`; исполняется держателем клэйма `<C>`;
**эксклюзивная ветка тика** ([08-operability.md](../08-operability.md) §1) —
надзор/D/E в этом тике не идут (дисциплина «одно пересоздание за тик»).
Journal — `op=rotate-secrets`. Заявки нет — ветка не активна (no-op).

```
H0 заявка: нет — no-op; мутации — только под живым клэймом
H1 чтение per-cluster secrets: отсутствие/битость/неполнота → journal
   invalid-secrets (заявка жива; оператор чинит кластер; значения в
   диагностику не попадают)
H2 однократность перевыпуска — по journal-маркеру: фаза `reissued` или
   `rotated-*` значит, что перевыпуск уже состоялся (дальнейшие тики
   доводят инстансы к ТЕКУЩИМ значениям — повторный перевыпуск каждым
   тиком обнулял бы rolling; фазы ДО решения не пишутся, иначе затёрли бы
   маркер)
H3 нет маркера: генерация новых root+ключей и атомарная замена secrets-ключа
   целиком (txn по mod_revision; etcd-backup — спец-ключ пере-подставляется
   из env); проигрыш RMW → journal waiting-secrets, заявка жива, следующий
   тик; успех → journal reissued
H4 обход инстансов по Ordinal, по одному за тик:
   - env контейнера совпадает с НОВЫМ secrets-ключом по ПОЛНЫМ значениям
     (root-пара + каждый OWNS3_ACCESS_KEYS__<i>__{ACCESSKEY,SECRETKEY,POLICY}
     и отсутствие лишних индексов): инстанс уже на новом профиле —
     если state ≠ RUNNING, health-проба по advertised-адресу; не ожил →
     waiting-node (следующая нода не трогается), ожил → state=RUNNING;
     далее следующий инстанс
   - env расходится: снос контейнера БЕЗ volume (данные объектов живы) →
     EnsureClusterPki/EnsureNodePki (материал переиспользуется из etcd;
     отказ → waiting-pki) → env из НОВОГО secrets-ключа и PKI →
     контейнер с теми же лимитами и адресом → state=PROVISIONING →
     journal rotated-<node>; выход (одна нода за тик)
H5 все инстансы приведены: del заявки (одна txn) + journal done
```

Повтор тика доигрывает по journal-фазе и фактической env-сверке (рестарт
воркера посреди rolling безопасен); takeover — по тому же маркеру. Заявка не
снимается по возрасту: начатая ротация доводится тиками, снятие заявки —
только по завершении (H5); журнал-маркер однократности исключает повторный
перевыпуск значений. Повторная заявка при живой (ротация ещё идёт) —
идемпотентный 200 без перезаписи.
