# 11. Виртуальные шарды: бакеты поверх нескольких кластеров ★

**Бакет** = схема (schema) в PostgreSQL. Все бакеты имеют одинаковую структуру:
это «виртуальный шард» поверх физического. **Шард** = отдельный HA-кластер
из доков [01](01-architecture.md)–[10](10-four-nodes.md) (Spilo + Patroni + etcd +
HAProxy). На одном шарде живёт несколько бакетов; любой бакет можно **онлайн**
перевезти на другой шард — запись в бакет при этом доступна всё время, кроме
финального cutover (пауза записи на секунды, что согласовано и допустимо).

Зафиксированные вводные (подтверждены заказчиком):
- PostgreSQL — **18.x**, последний стабильный мажорный релиз (скрипты проверены на 18.4).
  Минимально допустимая версия — **15** (`FOR TABLES IN SCHEMA`); начиная с **17** логические
  слоты синхронизируются на реплики — на 18 это есть из коробки (важно для failover
  во время переезда, раздел 7);
- секундный запрет записи на cutover — допустим;
- DDL меняется редко, **во время переезда DDL в бакете гарантированно не будет** —
  мораторий обеспечивается технически (P5: `REVOKE CREATE` + двойная сверка схем);
- приложение пишет в бакеты **отдельной app-ролью, не владельцем схемы** (P1/P5:
  заморозка `REVOKE` действует на app-роль; DDL выполняет миграционная роль-владелец);
- JOIN между бакетами не нужны → бакеты на разных шардах друг про друга не знают.

> Решения P1–P8 из реестра рисков [12-bucket-pitfalls.md](12-bucket-pitfalls.md)
> внесены в этот runbook: заморозка `REVOKE` (§5, шаг 4), подписки через HAProxy
> (§4, §6), failover slots (§4, §7, §10), контроль WAL (§4, §5, §7, §9),
> технический DDL-мораторий (§5, §8), синхронизация sequence→sequence (§5, шаг 4,
> §8), отмена незавершённых переездов `abort-move.sh` (§5 «Автоматизация», §7; P7),
> `synchronous_commit=remote_apply` подписок + сверка строк перед flip (§4, §5
> шаги 2/4, §7; P8).

## 1. Общая картина

```
                        ┌────────────────────┐
                        │   Приложение(s)    │
                        │  роутер бакетов    │  ← код приложения: по bucket_id
                        └────────┬───────────┘    выбирает мастера шарда (etcd watch)
                                 │
                    ┌────────────┴────────────┐
                    │  etcd-контрол-плейн     │  ← где какой бакет лежит + состояние
                    │  /buckets/*, /shards/*  │    (watch; P9–P12 — риски etcd)
                    └────────────┬────────────┘
                                 │ DSN = мастер шарда-владельца, :6432 (pg_doorman)
          ┌──────────────────────┼──────────────────────┐
          ▼                      ▼                      ▼
   ┌─────────────┐        ┌─────────────┐        ┌─────────────┐
   │   Шард 1    │        │   Шард 2    │        │   Шард N    │
   │  bucket_41  │        │  bucket_43  │        │  bucket_…   │
   │  bucket_42  │──LR──→ │  bucket_44  │        │             │
   └─────────────┘переезд  └─────────────┘      └─────────────┘
```

Каждый шард — HA-кластер из [01-architecture.md](01-architecture.md)–[10](10-four-nodes.md):
failover делает Patroni. Отличие от базовой топологии: **приложение не ходит
через HAProxy шарда** — роутер берёт из etcd адрес мастер-ноды (`/shards/X/master`,
его пишет Patroni-callback) и подключается к её **pg_doorman :6432** (per-node
sidecar, бэкенд `127.0.0.1:5432`). HAProxy остаётся точкой входа только
репликационного трафика переездов (P2). Раскладка сервисов на ноде — §4.

> Почему не Citus / pgEdge: Citus 12+ умеет schema-based шардирование и онлайн-ребалансинг
> из коробки, но требует перейти на топологию «координатор + воркеры» вместо N независимых
> Patroni-кластеров. pgEdge (Spock) решает проблему DDL-репликации, которая нам не актуальна
> (DDL-мораторий на время переезда). Решение: остаёмся на своей топологии и нативной
> логической репликации PG ≥ 15 (`FOR TABLES IN SCHEMA`).

## 2. Контрол-плейн: etcd

Состояние бакетов живёт в etcd (рецепт кластера — [04](04-deploy-etcd.md); риски
P9–P12 — в [12](12-bucket-pitfalls.md)). **Доступность etcd = доступность
роутинга**: пропал кворум — новые маршруты не выдаются и переезды невозможны,
старые маршруты продолжают работать из кэша. Ключей два вида:

```
/buckets/routing/bucket_42 → "shard1"                   # владелец (авторитет)
/buckets/status/bucket_42  → {"state":"SYNCING", ...}   # только при переезде
```

`/buckets/routing/N` — единственный ответ на «где бакет»: значение = имя шарда из
конфига mover'а. Нет статус-ключа = бакет **ACTIVE**. Статус-ключ появляется только
на время переезда и удаляется атомарно с flip:

| state (status-ключ) | Запись | Чтение | Что означает |
|---|---|---|---|
| *(нет ключа)* ACTIVE | шард-владелец | шард-владелец | обычная жизнь |
| `SYNCING` | шард-владелец | шард-владелец | идёт фоновая догоняющая репликация, для клиентов незаметна |
| `FROZEN` | **отклоняется** (retryable-ошибка) | шард-владелец | cutover: секунды, ждём нулевой лаг |
| `ABORTING` | отклоняется | шард-владелец | идёт уборка прерванного переезда (P7) |

Переключение владельца — **одна атомарная etcd-транзакция** (compare routing =
старый владелец → put routing = новый + delete status): «flip применился, а
контрол-плейн об этом не знает» невозможно по построению.

Кроме бакетных ключей, в том же etcd живёт **топология кластеров**: адрес
мастера каждого шарда `/shards/X/master → "host:6432"` (lease/TTL, пишет
Patroni-callback `on_role_change` — никто больше). Потребитель — роутер
приложений (§3); полная схема ключей и раскладка ноды — референс топологии
в [12](12-bucket-pitfalls.md) и §4.

> ⚠️ Бэкапируется отдельно от шардов (P12, `etcdctl snapshot`); потеря карты —
> не потеря данных (список схем на шардах восстанавливает истину), но restore-процедуру
> описать заранее.

## 3. Роутер (в приложении)

Маршрутизация **по схеме** — обязанность кода приложения (pgbouncer/HAProxy
выбрать шард по schema_name не могут). На каждый запрос/транзакцию приложение
знает `bucket_id` (из контекста клиента) и строит DSN так:

1. **bootstrap**: в статическом конфиге приложения — только адреса etcd
   (`ETCD_ENDPOINTS` + TLS к etcd). Адресов БД в статическом конфиге нет вообще;
2. `bucket_id = hash(tenant_id) % N` (N — константа из `/buckets/config`);
3. шард-владелец — `/buckets/routing/bucket_id` (кэш с TTL секунды,
   инвалидация watch'ем префикса `/buckets/`);
4. адрес мастера — `/shards/<shard>/master` (формат `host:6432`; lease/TTL,
   пишет Patroni-callback `on_role_change`) — тоже из кэша/watch;
5. DSN конструируется на лету: `host=<из ключа> port=6432 dbname=<общая БД>
   user=app sslmode=...` — dbname один на все бакеты (бакет = схема);
   подключение — к pg_doorman мастер-ноды (§4). Пулы соединений держим
   **на каждый шард** (map `shard_id → pool`), не на бакет: переезд бакета
   не рвёт пулы — меняется только соответствие бакет→шард.

Отказы и переходы:
- `state = FROZEN` (статус-ключ) — write-запросы отклоняются **повторяемой**
  ошибкой («бакет переезжает, повторите через N сек»), read-запросы идут
  на владельца;
- failover мастера шарда — Patroni-callback обновляет `/shards/X/master`
  (секунды): новые соединения идут на нового мастера, оборванные
  реконнектятся по тому же ключу;
- переезд бакета — flip меняет `/buckets/routing/N`: коннекты перетекают
  на нового владельца после разморозки записи.

## 4. Требования к шардам

### Нода шарда: раскладка сервисов

На каждой ноде кластера-шарда живут:

| Сервис | Слушает | Роль |
|---|---|---|
| PostgreSQL | `:5432` (локально) | принимает только pg_doorman, подписки переездов (через HAProxy) и админку |
| **Patroni** (агент) | REST `:8008` | управляет **локальным** PG; кластер агентов выбирает лидера через etcd; callback `on_role_change` делает lease-put `/shards/X/master` — единственный авторитет «кто мастер». REST `/primary` потребляет health-check HAProxy |
| **pg_doorman** (sidecar) | `:6432` | пулер приложений, бэкенд **только** `127.0.0.1:5432` этой ноды; конфиг одинаков на всех нодах (N пулов `bucket_0..N-1 → localhost`), переезды бакетов его не трогают |
| **HAProxy** | `:5432` | **не клиентский**: вход репликационного трафика переездов (P2); health-check `GET /primary` у Patroni всех нод кластера → ведёт на текущего мастера. Per-node или пара выделенных LB на шард — HAProxy **любой** ноды кластера эквивалентен, подписке дают multi-host conninfo (плашка ниже) |
| **etcd** (член) | `:2379` | пока кластер ≤ 7 нод — etcd на нодах (локальные чтения/watch, паттерн [10](10-four-nodes.md)); при росте — отдельный etcd-кластер 3–5 нод по [04](04-deploy-etcd.md). Записи всегда через лидера (кворум), локальность ускоряет чтения/watch |

Пишет в etcd Patroni-callback; читают — роутеры приложений (watch), mover
и, при динамических адресах нод, HAProxy-синкеры (runtime API, паттерн
`hasync` со [стенда](stand/README.md) — с валидацией идентичности ноды).

### Параметры и роли

| Что | Где | Зачем |
|---|---|---|
| PG 18.x (минимально 15) | оба шарда | `CREATE PUBLICATION ... FOR TABLES IN SCHEMA` (15); синхронизация логических слотов на реплики (17+) — на PG18 из коробки |
| `wal_level = logical` | **все ноды обоих шардов** | логическое декодирование + failover slots (P3): слоты синхронизируются и на репликах. Требует рестарта: `patronictl edit-config` → `postgresql.parameters.wal_level` → rolling restart |
| `sync_replication_slots = on` + `hot_standby_feedback = on` | реплики обоих шардов | failover slots (P3): логические слоты переездов переживают failover/switchover источника. В Patroni/Spilo — через `postgresql.parameters` в DCS ([05](05-deploy-postgres.md)) |
| `max_slot_wal_keep_size` (меньше диска, хватает на штатный переезд) | все ноды шардов | изоляция взрыва WAL (P4): при переполнении инвалидируется слот (умирает переезд), а не диск всего шарда |
| `max_replication_slots` (запас ≥ числа одновременных переездов + HA-слоты) | источник | слот создаёт подписка |
| `max_wal_senders` с запасом | источник | walsender на каждую подписку |
| `max_logical_replication_workers`, `max_sync_workers_per_subscription` | шард-приёмник | apply-воркеры; по воркеру на активную подписку + на таблицу при initial copy |
| `synchronous_standby_names` + живая реплика у мастера | оба шарда | P8: подписки переездов с `synchronous_commit=remote_apply` — коммит применённой транзакции ждёт replay на standby ПРИЁМНИКА; без sync-standby защита тихо вырождается в асинхронную → preflight move проверяет и отказывает |
| Роль `bucket_mover` с атрибутом `REPLICATION` и `GRANT SELECT ON ALL TABLES IN SCHEMA` | источник | подключение подписки (через HAProxy :5432!) + initial COPY. НЕ трогаем при заморозке `REVOKE` (P1) — обратная репликация пишет через неё |
| App-роль приложения (≠ owner схемы): `GRANT INSERT, UPDATE, DELETE, TRUNCATE ON ALL TABLES`, `GRANT USAGE, UPDATE ON ALL SEQUENCES` | оба шарда | write-доступ, который срезается `REVOKE` при заморозке (P1); на sequences обе привилегии — `nextval` даёт И `USAGE`, И `UPDATE`, заморозка обязана отобрать обе (проверено на стенде). Различимость сессий бакета в `pg_stat_activity`. Owner пишет вопреки REVOKE — поэтому app ≠ owner |
| Миграционная роль-владелец схем бакетов | оба шарда | единственная, кто выполняет DDL (P5); в окне переезда — процедурный мораторий (правами владельца не остановить → страховка сверками) |
| Правило в `pg_hba.conf` для `bucket_mover` с IP HAProxy **своего** шарда (per-node HAProxy — со всех нод кластера) | источник | подписка подключается через HAProxy источника → источник видит IP этого HAProxy (не приёмника) |

> ⚠️ **Строка подключения подписки — всегда через write-эндпоинт HAProxy шарда-источника**
> (порт 5432), не в конкретную ноду. Иначе failover источника рвёт репликацию намертво.
> Отказоустойчивость самого входа — **multi-host conninfo** (`host=node1,node2,node3`):
> libpq перебирает адреса, а HAProxy любой ноды кластера ведёт к текущему мастеру —
> подписка переживает и failover источника, и смерть ноды, на чьём HAProxy сидела.
> Обратная подписка — через HAProxy **нового владельца** (§6). HAProxy именно поэтому
> остаётся в инфраструктуре каждого шарда: он выведен из data path приложений,
> но остаётся точкой входа репликационного трафика переездов (P2).

Создание нового бакета (когда переездов нет) — `create-bucket.sh <bucket> --shard <shard>`
(накатывает DDL шаблона, выдаёт гранты app-роли и регистрирует
`/buckets/routing/N → shard`); раскладка — по свободному месту / round-robin.

## 5. Процедура переезда (runbook) ★

Переезд `bucket_42`: шард1 → шард2. Все шаги идемпотентны — сбой на любом шаге
лечится повтором шага или откатом (раздел 6), источник не портится до самого конца.

### Шаг 0. Предполётные проверки
```sql
-- шард1 (источник):
SHOW wal_level;                                    -- = logical
SELECT count(*) FROM pg_replication_slots;         -- < max_replication_slots
-- шард2 (приёмник):
SELECT count(*) FROM pg_subscription;              -- +1 должна влезть
SELECT count(*) FROM pg_namespace                  -- схемы ещё нет
WHERE nspname = 'bucket_42';
```

Технический DDL-мораторий (P5) — на **обоих** шардах, до сверки:
```sql
REVOKE CREATE ON SCHEMA bucket_42 FROM app_role;   -- и на шард1, и на шард2
```
Новых таблиц не появится — публикация не подхватит то, чего нет на приёмнике.
`ALTER`/`DROP` существующих закрыты тем, что app-роль ≠ owner (P1); для миграционной
роли-владельца мораторий процедурный (правами владельца не остановить) — страховка
сверками ниже.

Пре-сверка схем (P5): фактические схемы источника и приёмника против эталона
(шаблон бакета + журнал миграций). Расхождение → отложить переезд и накатить
миграции: дрейф взорвётся на этом или следующем переезде.

Прогнозный префлайт места (P4) — не «место есть сейчас», а «хватит на переезд»:
удержанный WAL ≈ скорость генерации записи × оценка длительности SYNCING
(initial copy читает таблицы, WAL не генерируя; копится новая запись) × запас —
против свободного места **на всех нодах шарда** (synced-слоты P3 держат WAL
и на репликах).

```bash
# контрол-плейн: заявить переезд (после всех проверок выше)
etcdctl put /buckets/status/bucket_42 \
  '{"state":"SYNCING","target":"shard2","updated_unix":...}'
```
С этого момента действует DDL-мораторий (выше) — до finalize (шаг 5).

### Шаг 1. Перенести DDL (без данных) на шард2
```bash
pg_dump --schema-only --schema=bucket_42 --no-owner --no-privileges \
  "host=<haproxy_shard1> port=5432 dbname=app user=..." \
| psql "host=<haproxy_shard2> port=5432 dbname=app user=..."
```
Схемы, таблицы, индексы, последовательности, ограничения — всё кроме данных.

### Шаг 2. Публикация на источнике, подписка на приёмнике
```sql
-- шард1:
CREATE PUBLICATION pub_b42 FOR TABLES IN SCHEMA bucket_42;

-- шард2:
CREATE SUBSCRIPTION sub_b42
    -- multi-host: HAProxy любой ноды шарда1 ведёт к мастеру (§4), libpq
    -- перебирает адреса — подписка переживает и failover, и смерть ноды
    CONNECTION 'host=<hap1_node1>,<hap1_node2>,<hap1_node3> port=5432 dbname=app user=bucket_mover password=...'
    PUBLICATION pub_b42
    WITH (copy_data = true, failover = true,          -- failover=true: слот синхронизируется
          synchronous_commit = remote_apply);         -- на реплики источника (P3);
                                                      -- remote_apply: feedback не убегает
                                                      -- вперёд физрепликации приёмника (P8)
```
Подписка создаст слот на источнике и начнёт initial COPY всех таблиц, дальше —
стриминг изменений. **Бакет всё время доступен на запись.**

> ⚠️ `synchronous_commit = remote_apply` (P8): коммит применённой транзакции ждёт
> replay на standby приёмника — иначе feedback (`confirmed_flush_lsn`) убегает вперёд
> его физической репликации, и failover приёмника посреди SYNCING **молча пропускает**
> срез изменений (стрим при этом выглядит здоровым). Работает только при живом
> sync-standby у мастера приёмника — preflight это проверяет и отказывает без него.

> ⚠️ Окно досинка слота после initial copy (найдено на стенде PG 18.4). Слот с
> `failover = true` синхронизируется на реплики асинхронно; в момент initial copy
> (скачок `catalog_xmin`) в логах реплик возможны `could not synchronize slot ...`.
> Промо реплики в этом окне **теряет слот** → fallback re-copy (§7). Поэтому после
> завершения initial copy и до допуска переезда к cutover: слот на репликах
> источника `synced = true` (стало тихо в логах реплик), и этот факт — часть
> префлайта cutover. Нюансы рецепта failover slots — [05](05-deploy-postgres.md).

### Шаг 3. Ждать догоняния
```sql
-- шард2: состояние подписки
SELECT subname, received_lsn, latest_end_lsn, latest_end_time
FROM pg_stat_subscription WHERE subname = 'sub_b42';

-- шард1: отставание слота в байтах
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS lag
FROM pg_replication_slots WHERE slot_name LIKE 'sub_b42%';
```
Initial copy большого бакета = часы; lag после него — доли секунды. Пока подписка жива,
**слот держит WAL на источнике** — следить за диском (раздел 9, P4). Ожидание
толерантно к обрывам соединения с приёмником (у него может идти failover, P8):
mover переживает транзиентные сбои в пределах бюджета недоступности и продолжает
с того же места; failover посреди initial copy рестартует копирование таблицы новым
tablesync-слотом (осиротевшие доберёт finalize).

### Шаг 4. Cutover (секунды)
```bash
# 4.1 Заморозить запись в контрол-плейне (роутер отклоняет запись, чтение живёт):
etcdctl put /buckets/status/bucket_42 \
  '{"state":"FROZEN","owner":"shard1","target":"shard2",...}'
```
```sql
-- 4.2 Железная заморозка на источнике — ДО capture LSN (P1):
BEGIN;
SET lock_timeout = '5s';
REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON ALL TABLES IN SCHEMA bucket_42 FROM app_role;
REVOKE USAGE, UPDATE ON ALL SEQUENCES IN SCHEMA bucket_42 FROM app_role;
-- nextval даёт И USAGE, И UPDATE — отбираем ОБЕ привилегии (проверено на стенде).
-- mover-роль НЕ трогаем: обратная (rollback) репликация продолжает писать.
-- ⚠️ Сам REVOKE барьером НЕ является: берёт лишь AccessShareLock и при живом
-- писателе проходит мгновенно (проверено на стенде PG 18.4). Барьер — явный
-- LOCK TABLE в ACCESS EXCLUSIVE MODE в той же транзакции:
LOCK TABLE bucket_42.<t1>, bucket_42.<t2>, ... IN ACCESS EXCLUSIVE MODE;
COMMIT;
-- LOCK физически ждёт завершения всех транзакций, державших блокировки на
-- таблицах (включая долгие SELECT): после COMMIT писателей доказательно нет.
-- Зависший idle in transaction → таймаут по lock_timeout → terminate
-- по pg_stat_activity + ретрай. Порядок обязателен: REVOKE + барьер до
-- capture LSN, иначе поздний писатель закоммитится уже после захвата позиции.
-- Список таблиц для LOCK — генерировать из pg_class/pg_namespace (все relkind='r'
-- схемы), не хардкодить.

-- 4.3 Зафиксировать последний LSN записи (строго ПОСЛЕ REVOKE):
SELECT pg_current_wal_lsn();          -- запомнить, напр. '0/A000123'
-- ждать, пока confirmed_flush_lsn слота >= этого LSN.

-- 4.4 Контрольная сверка схем перед flip (P5): initial copy долгий, между
-- префлайтом и cutover мог уехать DDL. Расхождение → отказ cutover
-- (GRANT + разморозка, разбор).

-- 4.5 Синхронизация sequence→sequence (P6) — поимённо для ВСЕХ sequence схемы
-- (не только привязанных к колонкам), без привязки к max(id) из таблиц:
--   на источнике:  SELECT last_value, is_called FROM bucket_42.<seq>;  -- обычный SELECT
--   на приёмнике:  SELECT setval('bucket_42.<seq>', <last_value>, <is_called>);
-- ⚠️ is_called в конкатенации с текстом (last_value||' '||is_called) даёт
-- 'true'/'false' — короткое 't' бывает только на дисплее psql. Скриптам
-- считать issued/next на стороне SQL (CASE WHEN is_called ...), не парсить
-- boolean в bash (найдено на стенде, arch/stand/README №7).
-- Источник уже заморожен (REVOKE закрыл nextval — обе привилегии USAGE и UPDATE)
-- — margin не нужен: новых выдач на источнике нет.
-- Затем инвариант-проверка перед flip: следующее выдаваемое значение на приёмнике
-- СТРОГО > последнего выданного на источнике. Расхождение или отсутствие sequence
-- на приёмнике → отказ cutover с разморозкой: тихий будущий duplicate key
-- становится громким отказом.

-- 4.6 Сверка строк перед flip (P8): лаг 0 не гарантирует полноты копии — после
-- failover приёмника срез изменений может быть пропущен при нулевом лаге.
-- SELECT count(*) FROM bucket_42.<каждая таблица>; -- на источнике и приёмнике,
-- расхождение → отказ cutover с разморозкой + abort (P7) и повторный move:
-- свежий initial copy переприготовит копию.
```
```bash
# 4.7 Переключить владельца — ОДНА атомарная etcd-транзакция (compare→put+del):
#    «flip применился, а контрол-плейн не знает» невозможно по построению
etcdctl txn <<'EOF'
val("/buckets/routing/bucket_42") = "shard1"

put /buckets/routing/bucket_42 shard2
del /buckets/status/bucket_42


EOF
```
Роутер видит нового владельца (в пределах TTL кэша/watch) — запись и чтение
идут на шард2. Опоздавший к flip писатель («соединение-призрак», P1) получает
**громкую** `permission denied` вместо тихой потери: REVOKE на источнике держится
до финализации, ретрай уводит призрака на новый шард через роутер. Фриз длится
ровно столько, сколько ждать лаг 0 (обычно < 1–2 сек).

Отказ/таймаут на любом подшаге до flip — **разморозка** на источнике:
`GRANT INSERT, UPDATE, DELETE, TRUNCATE ON ALL TABLES IN SCHEMA bucket_42 TO app_role;`
(+ `GRANT UPDATE ON ALL SEQUENCES`), бакет возвращается в SYNCING, репликация
продолжает догонять, move можно повторить.

### Шаг 5. Уборка = finalize (не спешить)
Окно DDL-запрета длится до finalize, **не до flip** (P5): после flip схема источника
ещё нужна обратной подписке, `ALTER` на ней сломал бы apply. Сначала — **обратная
подписка для отката** (раздел 6), пожить часы/дни, и только потом:
```sql
-- шард2 (новый владелец): снять DDL-запрет — GRANT CREATE ON SCHEMA bucket_42
--   TO app_role (если app-роли он был нужен); миграционная роль снова может работать;
-- шард2: DROP SUBSCRIPTION sub_b42;      -- отпускает слот на источнике
-- шард1: DROP PUBLICATION pub_b42;
-- шард1: DROP SCHEMA bucket_42 CASCADE;  -- ★ последним, когда уверены; REVOKE
--                                       --   на источнике умирает вместе со схемой
```

### Автоматизация: скрипты ★

Весь runbook выше автоматизирован в `scripts/` (конфиг — `configs/buckets/buckets.env`,
образец в `buckets.env.example`; на машине запуска нужны `psql`/`pg_dump`):

```bash
./scripts/create-bucket.sh bucket_42 --shard shard1 [--ddl ddl.sql | --template bucket_41]
./scripts/move-bucket.sh move     bucket_42 --to shard2 [--yes] [--skip-reverse] [--resume]
./scripts/move-bucket.sh status   bucket_42
./scripts/move-bucket.sh rollback bucket_42 [--yes]
./scripts/move-bucket.sh finalize bucket_42 --old-shard shard1 [--yes]
./scripts/abort-move.sh list                       # etcd: незавершённые переезды (P7)
./scripts/abort-move.sh abort bucket_42 [--yes]    # etcd: отмена + уборка артефактов
```

Свойства: шаги идемпотентны — прерванный `move` перезапускается теми же аргументами
(`--resume` — только если на приёмнике пустая схема после сорванного pg_dump, скрипт
проверяет и отказывает на непустой); `move` сам ставит/срезает подписки (`failover=true`,
`synchronous_commit=remote_apply` — P3/P8), делает cutover с заморозкой, сверками
(инвентарь P5, строки P8), sequence→sequence (P6) и атомарным etcd-flip, ставит
обратную подписку; `rollback` — раздел 6; `finalize` — уборка (включая осиротевшие
tablesync-слоты после failover приёмника, P8). Pre-flight `move` проверяет слоты/
walsender'ы/место (P4) и живой sync-standby у приёмника (P8 — без него remote_apply
не защищает, переезд отказывает). Сквозной smoke-тест на PostgreSQL 18.4 пройден:
create → move → призрак-P1 → rollback → повторный move → finalize, артефактов
не осталось (`arch/stand/checks/65-move-e2e.sh`).

`abort-move.sh` — отмена незавершённого переезда (P7): состояние читает из
etcd-контрол-плейна (`/buckets/routing/N` — владелец, `/buckets/status/N` — статус;
нет ключа = ACTIVE). До любых манипуляций с БД записывает в тот же статус-ключ
журнал уборки (`state=ABORTING` + план + `phase`) — крах уборки оставляет в etcd
самодокументирующийся след, повторный запуск продолжает. Порядок уборки: подписки →
слоты → публикации → re-GRANT на владельце (снятие заморозки P1/P5) → `DROP SCHEMA`
на не-владельцах; успех = удаление статус-ключа (бакет снова ACTIVE у владельца).
Если routing уже указывает на приёмник (flip прошёл, статус-ключ завис) — abort
без `--force` отказывается, с `--force` **доводит перевод до конца**: уборка старого
шарда + доводка sequences владельца до последних выданных на старом (P6, только
вперёд). Подробнее — P7 в [12-bucket-pitfalls.md](12-bucket-pitfalls.md).

## 6. Откат

До удаления схемы на источнике откат — это тот же cutover в обратную сторону
(автоматизировано: `./scripts/move-bucket.sh rollback <bucket>`):

1. На шард2: `CREATE PUBLICATION pub_b42_back FOR TABLES IN SCHEMA bucket_42;`
2. На шард1: `CREATE SUBSCRIPTION sub_b42_back ... PUBLICATION pub_b42_back
   WITH (copy_data = false, failover = true, synchronous_commit = remote_apply)` —
   conninfo через HAProxy **шард2** (P2: write-эндпоинт :5432 нового владельца);
   (схема на источнике ещё на месте со своими данными — copy_data не нужен,
   изменения догонятся инкрементально);
3. Вернуть бакет — зеркальный cutover с механикой P1/P6/P8: FROZEN → `REVOKE` DML
   на шард2 → лаг 0 → контрольная сверка → sequences: `last_value` читается
   у нового владельца и `setval` на шард1 (инвариант — в обратную сторону) →
   сверка строк → атомарный etcd-flip на шард1 → симметричный `GRANT` на шард2
   (заморозка там держится до finalize).

Откат работает и после `DROP SUBSCRIPTION` на шард2 — но через полный re-copy данных.

| Что случилось | Что происходит | Что делать |
|---|---|---|
| Mover умер посреди переезда (SYNCING/FROZEN) | Артефакты pubs/subs/slots/схема в промежуточном состоянии; статус-ключ висит в etcd; следующий move откажет | `abort-move.sh list` → `abort-move.sh abort <bucket>` (P7): журнал ABORTING в etcd до манипуляций, идемпотентная уборка БД (подписки → слоты → публикации → re-GRANT на владельце → схемы не-владельцев), удаление статус-ключа = ACTIVE. Недоступный шард — `phase=blocked`, повторить после его возврата |
| Failover источника (шард1) во время SYNCING | Подписка ходит через HAProxy (P2) → переподключается к новому мастеру. Слот переживает failover: failover slots PG17+ (`sync_replication_slots` + `hot_standby_feedback`, P3) синхронизировали его на реплики | Обычно ничего. Слот на новом мастере отстаёт на лаг репликации → повторная доставка; replication origin подписчика пропускает уже применённое. Обязательные стенд-проверки — раздел 10, п. 7. Fallback: на шард2 `DROP SUBSCRIPTION`; `DROP SCHEMA bucket_42 CASCADE`; повторить с шага 1. Источник не пострадал |
| Failover приёмника (шард2) во время SYNCING | Подписка — объект каталога PG, физическая репликация перенесёт её на нового мастера; соединение переустановится (conninfo ведёт на HAProxy шард1). `synchronous_commit=remote_apply` (P8) держит feedback за физрепликацией приёмника → срез изменений **пересылается**, а не пропускается | Обычно ничего: mover транзиенто-толерантен (бюджет недоступности), initial copy рестартует новым tablesync-слотом (сирот добьёт finalize). Если защита не действовала (переезд запущен без sync-standby) — сверка строк перед flip поймает дефект: abort (P7) + повторный move |
| Слот инвалидирован: `wal_status = 'lost'` | Initial copy долгий, `max_slot_wal_keep_size` (P4) превышен — PG срезал слот: **умирает переезд, а не шард**; бакет на источнике ACTIVE и консистентен, теряется только время | Детекция до порога: алерт по `safe_wal_size` (§9). | Сбой приложения-роутера при FROZEN | Записи в бакет отбиваются retryable-ошибкой | Клиенты повторяют; фроз рассчитан на секунды |

## 8. Подводные камни и ограничения

- **DDL не реплицируется.** Публикация `FOR TABLES IN SCHEMA` подхватит и новые таблицы
  на источнике, но на приёмнике их нет → apply упадёт. Мораторий технический (P5):
  `REVOKE CREATE ON SCHEMA` на обоих шардах + app-роль ≠ owner + двойная сверка схем
  (префлайт и перед flip); окно запрета — шаг 0 → finalize. Смена DDL между переездами:
  миграция адресуется **бакету** и применяется на его текущем владельце (из etcd),
  журнал миграций обязателен — иначе дрейф схем взорвётся на следующем переезде.
- **Sequences не реплицируются** — синхронизация sequence→sequence на cutover
  (шаг 4.5): `setval(last_value источника)` поимённо для всех sequence схемы +
  инвариант-проверка перед flip. Единственный авторитет выданных значений — сам
  счётчик: эвристика `setval(max(id)+margin)` ломается на кастомных `nextval`,
  дырах и нескольких sequence на таблицу — не использовать (P6).
- **Large objects (`pg_largeobject`) не переносятся** логической репликацией. Если бакеты
  их используют — переносить отдельно (`pg_dump --blobs` до cutover).
- **`TRUNCATE` реплицируется** (входит в публикацию) — это ожидаемо и хорошо.
- **Кросс-бакетные JOIN** возможны только внутри одного шарда. Между шардами —
  только сборка в приложении (нам не нужно, зафиксировано).
- **Долгие транзакции на источнике** тормозят логическое декодирование → лаг растёт.
  Мониторить `pg_stat_activity` `xact_start` при переездах.
- **Число одновременных переездов** ограничено `max_replication_slots` (источник) и
  `max_logical_replication_workers` (приёмник). Переезжать параллельно можно, но по счёту.

## 9. Мониторинг (дополнить раздел «Мониторинг» из [08-operations.md](08-operations.md))

- На источнике при активных слотах: `pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)`
  и размер `$PGDATA/pg_wal` — алерт при лаге > N МБ/диске > 80%; `safe_wal_size` —
  алерт ДО порога инвалидации, `wal_status = 'lost'` — слот уже срезан (P4).
- Слоты на репликах: failover slots (P3) удерживают WAL и там — контроль места
  на всех нодах шарда, не только на мастере.
- На приёмнике: `pg_stat_subscription` — `latest_end_time` не старше минуты.
- Sync-standby у мастеров обоих шардов (`pg_stat_replication.sync_state`): живой
  sync-standby приёмника — предусловие переездов (P8: без него `remote_apply`
  вырождается в асинхронность); его пропажа — алерт, а не сюрприз на preflight.
- Контрол-плейн: бакеты со статус-ключом (`/buckets/status/*`) дольше X минут —
  деградация переезда; `state=ABORTING` — незавершённая уборка (P7).
- Роутер: доля запросов, получивших FROZEN-ошибку, и длительность фризов.
- Постфактум переезда: сверка `count(*)` / `sum(hashtext(t::text))` таблиц на обоих
  шардах (раздел 10) — ловит тихие потери.

## 10. Как тестировать на стенде

1. Поднять **два** кластера по существующим докам (это же репетиция «двух шардов»).
2. Создать на шард1 два бакета из одного шаблона (`create-bucket.sh`, регистрация
   в etcd-контрол-плейне).
3. Записать генератор нагрузки (вставки + обновления в оба бакета, напр. цикл `INSERT`).
4. Запустить переезд `bucket_42` → шард2 по разделу 5; убедиться, что запись шла всё
   время, кроме секундного FROZEN.
5. Сверка: по каждой таблице
   `SELECT count(*), sum(hashtext(t::text)) FROM bucket_42.<tab> t;` — на обоих шардах;
   инвариант sequences (P6): следующее выдаваемое значение на новом владельце
   СТРОГО > последнего выданного на старом.
6. Отрепетировать отказы из раздела 7 (минимум: `docker stop` мастера источника
   во время SYNCING) и откат из раздела 6.
7. Стенд-проверки failover slots (P3, PG 18.4): failover источника в фазе стриминга
   (повторная доставка не даёт duplicate-key, apply жив); failover во время
   initial copy (поведение мутное — fallback re-copy, §7); возврат ноды через
   `pg_rewind` (слоты пересоздаются через sync, не битые); плановый switchover.
8. «Призрак» (P1): открыть сессию к старому шарду, выполнить flip, попытаться
   записать — ожидание: `permission denied`, а не тихая потеря.
9. Failover приёмника посреди SYNCING (P8): RED — без `remote_apply` срез
   изменений пропускается молча при «здоровом» стриме; GREEN — с `remote_apply`
   срез пересылается, mover доезжает до атомарного flip (`arch/stand/checks/70-p8-receiver-failover.sh`).

> Пункты 6–9 и решения P1–P8 **прогнаны практически** на docker-стенде
> (PostgreSQL 18.4): два «шарда» — мастер+реплика с эмуляцией Patroni REST API
> и HAProxy, приёмник; скрипты-проверки и найденные нюансы — `arch/stand/`
> (карта «тест → риск → результат» в его README). Главное, что изменило доку:
> REVOKE — не барьер (барьер `LOCK TABLE ... ACCESS EXCLUSIVE`); на sequences
> отбираются USAGE и UPDATE; у подписки `failover = true` + окно досинка слота
> после initial copy; неактивный слот при плавной записи не инвалидируется —
> лимит ловит активного молчащего потребителя (P4); failover приёмника без
> `remote_apply` молча пропускает срез изменений при «здоровом» стриме (P8).

> Скрипты из раздела «Автоматизация» прогнаны по этому сценарию на PostgreSQL 18.4,
> включая отказы (чеки `arch/stand/checks/30-*`, `70-*`) и e2e-цикл
> create→move→rollback→move→finalize (`checks/65-move-e2e.sh`).
