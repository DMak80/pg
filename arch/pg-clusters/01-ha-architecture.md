# PG-кластер: HA-архитектура

Уровень 3. Устройство HA-кластера-шарда: роли компонентов, репликация,
выборы лидера, failover и switchover, защита от split-brain, поведение при
отказах. Размещение и порты — [02-topology.md](02-topology.md);
конфигурация PG/Patroni — [05-postgres-patroni.md](05-postgres-patroni.md);
процессы — [processes/b-failover.md](processes/b-failover.md),
[processes/c-switchover.md](processes/c-switchover.md).

## 1. Компоненты ноды и их роли

| Компонент | Роль |
|---|---|
| **PostgreSQL 18** | База `<C>`: таблицы бакетов, WAL. Ровно один primary принимает запись, реплики — read-only. |
| **Patroni** (в Spilo) | Управляет локальным PostgreSQL: bootstrap, репликация, выборы лидера через DCS, promote/demote, REST API `:8008`. |
| **Spilo** | Образ Zalando: PostgreSQL + Patroni + окружение. Конфигурация — `SPILO_CONFIGURATION` (генерирует PgWorker). |
| **pg_doorman** | Пул клиентских соединений `:6432` на каждой ноде; бэкенд — только `127.0.0.1:5432` этой ноды. |
| **PgNode** | Агент ноды: приём WAL бэкапов, операции ноды, доставка секретов; API `:8080`/`:8081`. |
| **etcd** (внешний) | DCS Patroni (`/service/<scope>/`) и контрол-плейн домена (`/clusters/`, `/pgworker/`). На нодах кластера не живёт. |

Ноды не знают друг про друга ничего, кроме DCS и адресов репликации:
взаимодействие Patroni-нод — через etcd и REST `:8008` (fetch_node_status,
switchover), PostgreSQL-репликация — напрямую по `:5432` внутри
per-cluster сети.

## 2. Репликация

```
        ┌──────────────┐   streaming replication (WAL по TCP, :5432)
        │  primary     │ ─────────────────────────────────────────┐
        └──────┬───────┘                                          ▼
               │                                    ┌──────────────┐
               │ DCS: лидер, конфиг, члены          │  replica(s)  │
               ▼                                    └──────────────┘
        ┌──────────────┐
        │     etcd     │  Patroni каждой ноды продлевает lease и
        │  (внешний)   │  публикует состояние членов
        └──────────────┘
```

- **WAL** — журнал предзаписи: изменения сначала попадают в WAL, затем
  применяются к данным; реплика получает WAL-поток в реальном времени
  (physical streaming replication).
- **Реплики** — read-only; Patroni выдаёт каждой `primary_conninfo` и
  физический слот (`primary_slot_name`) от мастера.
- **Синхронность**: `synchronous_mode=true` — коммит на мастере ждёт
  подтверждения хотя бы одной синхронной реплики; per-cluster
  `synchronous_mode_strict` определяет поведение без sync-standby
  (durability-first по умолчанию) — канон
  [05-postgres-patroni.md](05-postgres-patroni.md) §4.
  Канонические тайминги Patroni (`ttl=20`, `loop_wait=1`, `retry_timeout=3`)
  и обоснование полов Patroni 4.x —
  [pgworker/01-placement.md](../pgworker/01-placement.md) §2.
- **Timeline**: после promote реплика продолжает новую timeline; `.history`
  хранит переключения. Реплика со старой timeline лечится `pg_rewind` или
  пересозданием.

## 3. Patroni: выборы и DCS

Patroni каждой ноды конкурирует за лидерский lease в etcd. Ключи scope —
`/service/<scope>/`, где `scope = <C>-<X>` (глобально уникален в общем
etcd; совпадение scope двух шардов слило бы их в один виртуальный кластер).
Состав ключей — [04-etcd-dcs.md](04-etcd-dcs.md) §3.

Leader-lease продлевается каждые `loop_wait` секунд; TTL — `ttl`. Пока lease
жив, только его держатель является primary. Нода, потерявшая DCS дольше
TTL, обязана уйти в read-only или остановить PostgreSQL — это и есть защита
от split-brain: два мастера невозможны, пока жив кворум etcd.

**REST API Patroni** (`:8008`, TLS сертом ноды):

| Endpoint | 200, если | Назначение |
|---|---|---|
| `/` | нода жива | общий health |
| `/primary` | нода — лидер | канонический предикат «кто мастер» ([07](07-identify-master.md)) |
| `/replica` | нода — реплика | выбор кандидата |
| `/read-only` | лидер или реплика | health чтения |
| `/read-write` | лидер и принимает запись | health записи |
| `/cluster` | всегда (снимок DCS) | состояние всех членов |
| `/config`, `/patroni`, `/history` | — | диагностика и конвергенция конфига |
| `/switchover`, `/failover`, `/restart`, `PATCH /config` | мутации | basic-auth per-cluster (`rest_password`); GET-пробы заголовок не несут |

Мутационные эндпоинты защищены basic-auth per-cluster; чтение — по TLS в
доверенной сети. Подробности TLS — [13-network-security.md](13-network-security.md) §4.

## 4. Failover (неплановая смена лидера)

Сценарий: лидер перестал продлевать lease (смерть процесса/хоста, сеть).

1. Lease лидера истекает (`ttl`); ключ `/service/<scope>/leader` исчезает.
2. Оставшиеся ноды видят отсутствие лидера и участвуют в выборах.
3. Побеждает нода с самой свежей позицией WAL (при синхронной репликации —
   гарантированно sync-реплика); Patroni делает `pg_ctl promote`.
4. Новая нода публикует себя лидером и обновляет `/service/<scope>/optime/
   leader`; Patroni-callback обновляет мастер-ключ
   `/clusters/<C>/shards/<X>/master` (lease, значение `host:<doorman-port>`).
5. Клиенты: новые соединения получают мастера из etcd; соединения к
   старому мастеру рвутся (запись — ошибка, повтор через роутер).

**Бюджет смены лидера** зависит от характера отказа:

- **graceful** (SIGTERM/stop): Patroni демотирует лидера и повышает
  синхронную реплику в пределах `loop_wait`-циклов — единицы секунд;
- **жёсткая смерть**: истечение lease ограничено полом Patroni 4.x
  `ttl≥20` — 20+ секунд. PgWorker ускоряет failover по положительному
  свидетельству смерти (docker-объект отсутствует/не running): удаляет
  leader-ключ и выставляет `/service/<scope>/failover` с кандидатом —
  промоушен происходит в пределах `loop_wait`
  ([pgworker/processes/c-node-supervisor.md](../pgworker/processes/c-node-supervisor.md)
  §3).

Точный автомат состояний — [processes/b-failover.md](processes/b-failover.md).

## 5. Switchover (плановая смена лидера)

Плановое обслуживание (замена ноды, обновление образа, ротация серта):
лидер штатно передаёт роль выбранной реплике. Patroni проверяет, что
кандидат догнал лидера, останавливает запись на старом мастере, повышает
кандидата; старый мастер становится репликой. Клиенты переезжают на нового
мастера после обновления мастер-ключа; уже открытые сессии старого мастера
завершаются.

Запуск — `patronictl switchover` внутри контейнера ноды или
`POST /switchover` с basic-auth per-cluster. Точные шаги и состояния —
[processes/c-switchover.md](processes/c-switchover.md).

## 6. Возврат ноды и rebuild

Упавшая нода при возврате догоняется автоматически: Patroni выбирает способ
по состоянию PGDATA — пустой диск → `pg_basebackup` с лидера; небольшое
расхождение → WAL; большое → `pg_rewind`. Ключ
`/service/<scope>/initialize` уже существует, поэтому пустая нода не
делает `initdb`, а клонируется с лидера.

Если автоматика не справляется или диск повреждён, PgWorker пересоздаёт
ноду с чистого места (удаление контейнера и тома, новый пустой диск,
`pg_basebackup`), сохраняя закреплённые порты. Для лидера действует
правило failover-first: сначала гарантированный failover, затем снос
(иначе уничтожается авторитетная копия). Полный автомат —
[processes/d-node-recovery.md](processes/d-node-recovery.md),
оркестрация — [pgworker/processes/c-node-supervisor.md](../pgworker/processes/c-node-supervisor.md)
§9.

## 7. Поведение при отказах

| Отказ | Что происходит | Запись |
|---|---|---|
| 1 нода из 3 (реплика) | HA-кластер жив, реплика выпала; Patroni продолжает надзор | работает |
| 1 нода из 3 (лидер) | Выборы нового лидера из оставшихся; sync-реплика гарантирует отсутствие потери подтверждённых коммитов | краткий разрыв на время выборов |
| 2 ноды из 3 | Выжившая может получить лидерство (etcd-контур отдельный и жив), но при `synchronous_mode_strict` без sync-standby запись блокируется; при `strict=false` — деградация в асинхронность | обычно остановлена (strict), при `strict=false` — работает с риском потери |
| 1 узел etcd из 3 | Кворум 2/3 жив, Patroni работает | работает |
| 2 узла etcd из 3 | Контрол-плейн заморожен: выборы, переезды, ротации невозможны; живые ноды не зависят от etcd для уже открытых соединений | работает до истечения lease |
| Сетевой split | Меньшинство теряет DCS и уходит в read-only/остановку; лидер остаётся один в большинстве | возможен краткий разрыв |
| Смерть лидера при лежащем etcd | Новый лидер не выбирается (нет DCS); запись стоит до восстановления etcd | остановлена |

Потеря docker-хоста = потеря всех его нод и локальных томов; гарантии
строятся от реплик и бэкапов, не от локального диска
([backups/README.md](../backups/README.md)). Восстановление etcd —
[09-troubleshooting.md](09-troubleshooting.md) §5,
[etcdworker/04-snapshots.md](../etcdworker/04-snapshots.md).

## 8. Чего в топологии нет

**HAProxy в топологии нет.** В образе ноды он не поднимается: его
write-фронтенд `:5432` конфликтует с PostgreSQL в одном netns (одна нода —
один контейнер). Отдельным контейнером PgWorker его не строит.

- **Клиентский вход приложений** — `pg_doorman` `:6432` на каждой ноде;
  адрес мастера приложение берёт из etcd (`shards/X/master` →
  `host:6432`), а не из общего балансировщика.
- **Вход операций и подписок** — прямой pg-порт ноды из portalloc;
  multi-host DSN с `target_session_attrs=read-write` находит текущего
  писателя средствами libpq.

Единственная точка входа, которую видит приложение, — `pg_doorman`
мастер-ноды; отказ ноды переживается сменой адреса из etcd, а не
переконфигурацией балансировщика.
