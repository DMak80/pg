## 1. Переезды и репликация

### P1. Соединения-«призраки» после flip 🔴
**Сценарий.** После flip опоздавшее соединение пишет в старый шард — тихая
потеря данных.
**Решение.** Заморозка старого владельца техническая: `REVOKE INSERT,
UPDATE, DELETE, TRUNCATE` на таблицах и `REVOKE USAGE, UPDATE` на
sequences + барьер `LOCK TABLE … ACCESS EXCLUSIVE MODE` в одной транзакции
с `lock_timeout` (REVOKE сам барьером не является — берёт AccessShareLock и
проходит при живом писателе). Порядок: REVOKE + LOCK до capture LSN.
REVOKE держится до finalize; «призрак» получает громкую `permission denied`
и ретраит через роутер на нового владельца. app-роль ≠ owner — иначе
владелец писал бы вопреки REVOKE.

### P2. Подписка не следует за мастером источника 🔴
**Сценарий.** Статический host в conninfo — failover источника рвёт
репликацию намертво.
**Решение.** conninfo подписки — multi-host по всем нодам шарда-источника
(`host=n1,n2,… port=… target_session_attrs=read-write`); libpq находит
текущего писателя, apply-worker переподключается после failover. Обратная
подписка — multi-host по нодам нового владельца. Креды — `bucket_mover`,
`sslmode=require`.

### P3. Логический слот теряется при failover источника 🟠
**Сценарий.** Слот существует только на мастере — promote реплики теряет
его, переезд умирает.
**Решение.** Failover slots: `sync_replication_slots=on` +
`hot_standby_feedback=on`; подписка создаётся `WITH (failover=true)`; у
каждой реплики — физический слот (`primary_slot_name`), в
`primary_conninfo` обязателен `dbname`. После initial copy слот на репликах
досинхивается асинхронно — перед cutover проверять `synced=true`.

### P4. Слот держит WAL 🟠
**Сценарий.** Долгий initial copy + слот = переполнение диска шарда.
**Решение.** `max_slot_wal_keep_size` меньше диска: переполнение
инвалидирует слот (умирает переезд), а не диск шарда; прогнозный префлайт
места (скорость записи × оценка SYNCING × запас) по всем нодам, включая
реплики (synced-слоты держат WAL и там); алерт по `safe_wal_size` ДО
инвалидации; лечение — rollback/abort, затем повтор.

### P5. DDL не реплицируется 🟠
**Сценарий.** Новая таблица источника не появится на приёмнике — apply
падает; дрейф схем между шардами.
**Решение.** Технический мораторий: `REVOKE CREATE ON SCHEMA` на обоих
шардах + app ≠ owner; окно — от префлайта до finalize; двойная сверка схем
(префлайт и перед flip). Для миграционной роли мораторий процедурный —
страховка сверками. Журнал миграций обязателен: DDL адресуется бакету и
применяется на текущем владельце.

### P6. Sequences 🟡
**Сценарий.** Sequences не реплицируются; эвристика `setval(max(id)+margin)`
ломается на кастомных `nextval`, дырах и нескольких sequence на таблицу.
**Решение.** Синхронизация sequence→sequence поимённо для всех sequence
схемы: `last_value`/`is_called` источника → `setval` на приёмнике; источник
уже заморожен, margin не нужен. Инвариант перед flip: следующее выдаваемое
на приёмнике СТРОГО > последнего выданного на источнике. `is_called`
считать на стороне SQL, не парсить `'t'/'f'` в bash.

### P7. Артефакты незавершённых переездов 🟡
**Сценарий.** Умерший исполнитель оставляет pubs/subs/slots/схему и
зависший статус — следующий move отказывает.
**Решение.** `ABORTING`-журнал в статус-ключе **до** манипуляций с БД
(план + фаза), идемпотентная уборка: подписки → слоты → публикации →
re-GRANT на владельце → `DROP SCHEMA` не-владельцев; успех = удаление
статус-ключа (ACTIVE). Недоступный шард — `phase=blocked`, повтор после
возврата. Репарация брошенных статусов — PgWorker (K), пороги
`RepairStaleSec`/`RepairFrozenSec`.

### P8. Failover приёмника во время SYNCING 🔴
**Сценарий.** Feedback (`confirmed_flush_lsn`) убегает вперёд физической
репликации приёмника — failover пропускает срез изменений при «здоровом»
стриме.
**Решение.** Подписки с `synchronous_commit=remote_apply`: коммит ждёт
replay на standby приёмника; preflight требует живого sync-standby и
отказывает без него; перед flip — сверка `count(*)` всех таблиц
(лаг 0 не гарантирует полноты копии); failover посреди initial copy —
fallback re-copy, осиротевшие tablesync-слоты добивает finalize.

## 2. Контрол-плейн etcd

### P9. Недоступность etcd 🟠
**Сценарий.** Кворум потерян: watch стоят, новые маршруты не выдаются,
переезды и смена мастер-ключей невозможны; открытые соединения работают.
**Решение.** Политика роутера — **fail-open**: last-known-good кэш без
лимита времени. Пока etcd лежит, контрол-плейн заморожен (cutover и
failover невозможны), поэтому кэш не протухает; смерть мастера при лежащем
etcd всё равно кладёт запись — простой неизбежен при любой политике.
Ограничение: новый инстанс приложения не забутстрапится (статика — только
адреса etcd) — принято. Отклонены: fail-closed, TTL кэша, снапшот маршрутов
на диск.

### P10. Расходимость кэшей роутеров 🔴
**Сценарий.** Инстансы видят flip/FROZEN в разное время; запись после flip
старому владельцу = P1.
**Решение.** Расходимость не устраняем: гарантию даёт техническая
невозможность записи (REVOKE + LOCK, P1) и контракт приложения: любая
ошибка записи → сброс кэша маршрута → refetch → ретрай. Watch + TTL —
ускоритель конвергенции, не гарантия. Отклонён «барьер подтверждений».

### P11. Писатель `/clusters/<C>/shards/*/master` 🟠
**Сценарий.** Callback может упасть, пропустить событие, протухнуть;
между фактическим failover и обновлением ключа есть окно ошибок записи.
**Решение.** Основной писатель — Patroni-callback (`on_start` +
`on_role_change`), lease TTL 5 с с продлением каждые 1–2 с. Окно смены
лидера: graceful — единицы секунд; жёсткая смерть ограничена полом Patroni
4.x `ttl≥20` — PgWorker **ускоряет** failover (удаление leader-ключа +
`/service/<scope>/failover` с кандидатом), промоушен — в пределах
`loop_wait` ([pgworker/processes/c-node-supervisor.md](../pgworker/processes/c-node-supervisor.md)
§3). Двойной контроль — **MasterKeyReconciler** PgWorker: сверка
`/master` ↔ Patroni REST `/primary`, lease-put только при рассинхроне (не
второй регулярный писатель), продление TTL/2.5. Усыновлённые шарды
сверки не проходят (внешний формат `node:<pg-port>`). Отклонены: второй
регулярный писатель, REST-опрос из роутера, гарантия по значению ключа.

### P12. Потеря/restore etcd-контрол-плейна 🟡
**Сценарий.** Потеря etcd = потеря карты бакетов и мастер-ключей; restore
может быть устаревшим относительно последнего flip/failover; снапшот
покрывает все кластеры сразу.
**Решение.** Регулярные DR-слепки и выгрузка в S3 — EtcdWorker
([etcdworker/04-snapshots.md](../etcdworker/04-snapshots.md)); PgWorker
снимает локальные снапшоты в точках изменений (provisioning, переезды —
`move-<bucket>-start` обязателен и `flip-<bucket>-<to>` best-effort,
ротации) — маршрутизация, не DR. Restore: etcd из слепка → сверка карты с
фактом (routing × фактические схемы `bucket_*`) → починка **только
однозначных** расхождений с журналом; окна переездов разбираются штатными
move/abort/finalize. Мастер-ключи после restore пишут живые callback'и/
reconciler. Снапшот общий — сверка по каждому кластеру.

## 3. Пулер и подключения

### P13. Ограничения transaction pooling 🟠
**Сценарий.** Сессионное состояние между транзакциями не сохраняется.
**Решение.** `pool_mode="transaction"` в единственном пуле `<C>`:
работают prepared statements (именованные и анонимные), `COPY`, `SET LOCAL`,
LISTEN внутри транзакции; зачистка бэкенда по факту мутаций. Запрещены
`SET` вне транзакции, кросс-транзакционные advisory locks (→
`pg_advisory_xact_lock`), `WITH HOLD`, temp tables, кросс-транзакционный
`LISTEN`. Исключения — per-user override `"session"` малым пулом.
Replication passthrough в doorman нет: подписки идут напрямую в `:5432`.

### P14. Ключование пулов 🟠
**Сценарий.** Per-bucket пулы/алиасинг `dbname=bucket_N` → серверная БД.
**Решение.** План снят инвариантом единой БД: имя БД = имя кластера `<C>`,
бакеты — СХЕМЫ; один пул `<C>` → `127.0.0.1:5432` на ноду. Следствия:
`max_db_connections` — кап единственного пула; per-bucket изоляции и Pause
нет (шумный бакет ест общий бюджет — принято, FIFO doorman); адресация
бакета — `bucket_N.table` или `SET LOCAL search_path`.

### P15. Бюджет соединений 🟡
**Сценарий.** doorman + подписки + админка + физрепликация должны
укладываться в `max_connections`/`max_wal_senders`.
**Решение.** `max_connections` — вход PGTune
(`PgWorker:Pgtune:Connections`, дефолт 60); бюджет doorman → PG на ноду —
вычисляемый от него (формула и значения —
[06-client-access.md](06-client-access.md) §4): 5 соединений оставлены
админке/mover/reserved, клиентский вход `:6432` бюджетом PG не является
(схлопывается пулом). `max_wal_senders=max_replication_slots=10`:
1 на физрепликацию + до 3 переездов (main + 2 tablesync) с источника —
префлайт ограничивает счётчиком слотов.

### P16. Зрелость pg_doorman 🟡
**Сценарий.** Молодой проект: неизученные углы (таймауты аутентификации,
утечки памяти, Pool Coordinator).
**Решение.** Риск принят: pg_doorman эксплуатируется в проде (Ozon) на
существенно больших нагрузках; нагрузочные тесты до прода, откат на
pgbouncer и canary-бакеты сняты.

## 4. Сеть и безопасность

### P17. Порты нод наружу 🟡
**Сценарий.** Наружу открыты `:6432` (приложения) и `:5432` (подписки,
админка); компрометация ноды даёт доступ к PG.
**Решение.** etcd вынесен из нод (внешний infra-слой); `:2379` на нодах не
слушается. TLS на `:6432` — `sslmode=require` (шифрование, без
verify-full: адрес из etcd, доверие — аутентификация etcd-канала).
Аутентификация — per-pool `auth_query` из `pg_shadow` от superuser;
doorman→PG loopback — `scram-sha-256` (не trust). Per-bucket роли отклонены
(ломают P14/P15); радиус компрометации app-кредов — весь кластер, принято.
Firewall-матрица и модель угроз — [13-network-security.md](13-network-security.md).
Итог: приложениям — только `:6432`; `:5432` — межшард-подписки и админка.

## 5. Модель шардирования

### P18. N — навсегда 🟡
**Сценарий.** Смена N ломает хеш-маппинг всех тенантов; малое N
ограничивает число шардов гранулярностью `1/N`.
**Решение.** N задаётся при создании и не меняется: повторный init
отказывает, бакеты только `0..N−1`, сверка ловит схемы вне диапазона.
Выбор — с запасом от пикового числа шардов; внутри бакета не делим (P19).

### P19. Hash-skew и крупные тенанты 🟡
**Сценарий.** `hash(tenant)` неравномерна; гигантский тенант перетягивает
бакет и шард.
**Решение.** Распределение данных — ответственность приложения (ключ
шардирования); инфраструктура даёт пер-бакетные метрики и штатный переезд
перекошенного бакета на отдельный шард. Отклонены: карта исключений для
«тяжёлых» тенантов (роутер обязан читать карту), автоконсолидация по
метрикам.

### P20. Кросс-бакетные запросы 🟡
**Сценарий.** Между шардами запросов нет; внутри шарда JOIN схем — обычный
SQL.
**Решение.** Ответственность приложения: внутри шарда JOIN работает (P14),
между шардами — нет; инфраструктура не запрещает и не поощряет.

## 6. Эксплуатация

### P21. Наблюдаемость 🟡
**Сценарий.** «Куда сейчас пишет бакет N», лаги слотов, протухший lease,
зависшие не-ACTIVE статусы должны быть видны без раскопок.
**Решение.** Дашборд «бакеты × шарды × статусы × лаги слотов» + lease
мастеров; алерты — список [11](11-buckets.md) §9
(лаги/`safe_wal_size`/`wal_status`, sync-standby, не-ACTIVE статусы,
FROZEN-доля, `maxwait` doorman) + протухший lease (P11); runbook «где бакет
сейчас» — routing + status ключи.

### P22. Бэкапы ⚪
**Сценарий.** Шарды бэкапятся независимо; контрол-плейн — отдельно;
восстановление бакета = восстановление схемы на шарде + ключ в etcd.
**Решение.** Домен бэкапов — [backups/README.md](../backups/README.md):
полные, WAL, verify, restore/PITR, drill; DR-слепки etcd —
[etcdworker/04-snapshots.md](../etcdworker/04-snapshots.md). Порядок
восстановления системы: etcd из слепка → шарды из своих бэкапов → сверка
карты → приложение (watch подхватит). Отдельный бакет — восстановление
схемы + сверка routing.

### P23. Жизненный цикл шарда 🟡
**Сценарий.** Удаление непустого шарда, remove параллельно с move,
add на занятое имя, крах init посередине.
**Решение.** Guards в PgWorker: remove — только пустой шард (routing и
status/target), не последний, без карантина; add — только в Active-кластер
и на свободное имя; init — только в пустой префикс; бакеты — только
`0..N−1`. Провал guard'а = journal `last_error`, маркерное состояние
живёт, демонтаж продолжится сам после уезда бакетов. Каскадное удаление
«вместе с бакетами» и перенос бакетов внутри remove-shard отклонены
(молча теряет данные / смешение ответственностей).
