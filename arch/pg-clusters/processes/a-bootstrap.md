# A. Bootstrap кластера

Уровень 4. Первичная инициализация HA-кластера-шарда: как из N пустых нод
появляется один primary и реплики. Модель — [01-ha-architecture.md](../01-ha-architecture.md);
DCS-ключи — [04-etcd-dcs.md](../04-etcd-dcs.md) §3; оркестрация — provisioning
PgWorker ([pgworker/processes/a-provisioning.md](../../pgworker/processes/a-provisioning.md)).

## 1. Участники и предусловия

- Ноды шарда созданы, PGDATA пусты, Patroni запущен, etcd доступен.
- В `/service/<scope>/` нет ключа `initialize` (новый scope) — иначе
  bootstrap не выполняется: кластер считается инициализированным.
- Scope `<C>-<X>` уникален; `SPILO_CONFIGURATION` доставлен агентом
  (bootstrap.dcs: тайминги, sync-режим, параметры PG).

## 2. Состояния

| Состояние | Что означает | Условие выхода |
|---|---|---|
| `NO_SCOPE` | ключей scope нет; ноды стартуют | хотя бы одна нода готова участвовать в выборах |
| `RACE` | ноды конкурируют за право инициализации | одна записала `initialize` и стала лидером |
| `INITDB` | лидер выполняет `initdb` и поднимает PostgreSQL | PG принимает соединения |
| `CLONING` | остальные ноды видят лидера и клонируются (`pg_basebackup`) | клон завершён, реплика стримит |
| `CONVERGED` | один primary, реплики streaming, lag 0 | стабильное рабочее состояние |
| `FAILED` | bootstrap не завершился (нет кворума etcd, ошибка initdb/basebackup) | повтор с восстановлением причины |

Переходы: `NO_SCOPE → RACE → INITDB → CLONING → CONVERGED`; из `RACE`
проигравшие уходят в `CLONING` вслед за победителем; `FAILED` —
диагностическая ветка, возврат в `NO_SCOPE`/`RACE` после устранения
причины (ключ `initialize` не оставлен полузаписанным).

## 3. Ход процесса

1. **RACE**: ноды видят отсутствие `initialize` и одновременно пытаются
   его записать (txn/compare Patroni). Побеждает одна; остальные получают
   отказ и переходят в режим реплик.
2. **INITDB**: победитель делает `initdb`, поднимает PostgreSQL, пишет
   `initialize` и становится лидером (`/service/<scope>/leader`).
3. **CLONING**: остальные ноды видят лидера и делают `pg_basebackup` с
   него; после клона стартуют репликами, получают `primary_conninfo` и
   физический слот, начинают streaming.
4. **CONVERGED**: Patroni публикует членов; PgWorker фиксирует
   `state=RUNNING` по факту HA-контура (`initialize` + leader + REST
   отвечает и идентифицирует ноду); master-ключ пишет callback.

Порядок запуска нод не критичен; на практике первая стартовавшая чаще
становится лидером первого поколения.

## 4. Отказы и нюансы

- **Нет кворума etcd** — выборы не проводятся; bootstrap ждёт
  восстановления DCS, ничего не инициализируется.
- **Гонка с «висящим» `initialize`** — лидер не выбирается; лечение —
  удалить ключ только при доказанно неинициализированном кластере
  ([09-troubleshooting.md](../09-troubleshooting.md) §7).
- **Ошибка initdb/basebackup** — нода не становится членом; PgWorker
  видит незавершённый provisioning и повторяет/пересоздаёт ноду по общим
  правилам надзора.
- **Reinit существующего кластера** — `initialize` уже есть, поэтому
  пустая нода НЕ делает initdb, а клонируется с лидера
  ([d-node-recovery.md](d-node-recovery.md)).
- **Bootstrap-параметры ≠ живой конфиг**: `bootstrap.dcs` применяется
  только при первой инициализации; далее действует динамический
  `/service/<scope>/config`, который приводит к канону конвергенция
  PgWorker ([05-postgres-patroni.md](../05-postgres-patroni.md) §6).
