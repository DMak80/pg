# Кто мастер: предикаты и источники истины

Уровень 3. Как определить текущего мастера шарда и почему мастер-ключ в
etcd — не истина. Сверка и коррекция ключа — PgWorker
([pgworker/processes/c-node-supervisor.md](../pgworker/processes/c-node-supervisor.md)
§6); HA-механика — [01-ha-architecture.md](01-ha-architecture.md).

## 1. Инвариант: ключ — маршрутизация, не роль

Значение `/clusters/<C>/shards/<X>/master` может отставать от факта
(failover, упавший callback, гонка демоушена). Поэтому **предикаты «кто
мастер» строятся на первоисточнике — прямых пробах Patroni REST `/primary`
к каждой ноде шарда**, а не на сравнении значений etcd-ключа
([17-synchronization-principles.md](../17-synchronization-principles.md) S4).

Мастер-ключ нужен потребителям маршрутизации (роутер приложений) как
быстрый кэш адреса; его корректность обеспечивает отдельный контур сверки.

## 2. Способы определения мастера

| Способ | Что даёт | Когда применять |
|---|---|---|
| `GET https://<нода>:<patroni-port>/primary` по всем нодам | 200 только у лидера | **канон** для предиката и выбора SQL-цели |
| `GET /service/<scope>/leader` в etcd | имя лидера по DCS | быстрое чтение без обхода нод; при живом кворуме |
| `GET https://<нода>:<patroni-port>/cluster` | снимок всех членов, роли, лаг | диагностика, выбор кандидата |
| `SELECT pg_is_in_recovery()` | роль **этой** сессии: `f` — primary, `t` — реплика | проверка конкретного соединения |
| `shards/X/master` в etcd | `host:<doorman-port>` мастера | **только** маршрутизация приложений; не предикат |

Для операций PgWorker (SQL-цель переезда/ротации) резолв мастера —
цепочка `ShardEndpoints`: master-ключ → `/service/<scope>/leader` → Patroni
REST `/cluster`; это деградационные ветки, не отменяющие S4
([pgworker/06-bucket-moves.md](../pgworker/06-bucket-moves.md) §2).

## 3. Сверка и коррекция мастер-ключа (P11)

Patroni-callback (`on_start` + `on_role_change`) — основной писатель
мастер-ключа: lease TTL 5 с, значение `host:<doorman-port>`, продление
процессом на мастере каждые 1–2 с; смерть ноды гасит ключ сама.

Отказы callback закрывает **MasterKeyReconciler** PgWorker:

1. по нодам шарда `GET /primary` → фактический primary;
2. если ключ отсутствует или расходится — lease-put корректного значения
   (`host:<doorman-port>`);
3. если ключ корректен — мутаций нет (reconciler не второй регулярный
   писатель);
4. lease, выданный reconciler'ом, продлевается циклом с периодом `TTL/2.5`
   (2 с), чтобы ключ не мигал между тиками; при исчезновении primary
   продление снимается — ключ протухает ≤ TTL;
5. усыновлённые шарды сверки не проходят: их master-ключ пишет внешний
   HA-контур в формате `node:<pg-port>` — коррекция порождала бы войну
   писателей.

Два класса отказов закрыты: «callback упал при живом primary» (ключ
пересоздаётся) и «ключ указывает на реплику/мёртвую ноду» (перезаписывается
по факту). Ошибка конфигурации callback'а «ключ в чужом префиксе» этим
контуром не ловится — внешний мониторинг.

## 4. Формат ключа и различимость нод

- Каноническая нода: `host:<doorman-port>`. Порт doorman уникален на ноду
  (пулер обязателен на каждой ноде), поэтому ключ **дискриминатен по ноде
  всегда**; хост-часть информативна и может расходиться с portalloc
  (advertised-режим, старые контейнеры) — это не повод для войны писателей.
- Усыновлённая нода: `node:<pg-port>` (внешний HA-контур). Резолв мастера
  понимает оба формата ([pgworker/06-bucket-moves.md](../pgworker/06-bucket-moves.md)
  §2).

Потребители читают смену мастера из проб Patroni (`/primary` по
portalloc-портам) или `pg_is_in_recovery`, а не из сравнения значений
ключа.

## 5. Как проверить вручную

```bash
# канон: спросить каждую ноду (порты patroni — из portalloc)
for hp in <host1>:<patroni1> <host2>:<patroni2> <host3>:<patroni3>; do
  echo "$hp: $(curl -s -o /dev/null -w '%{http_code}' --cacert <ca.pem> https://$hp/primary)"
done
# 200 — лидер, 503 — не лидер

# DCS: имя лидера scope
etcdctl --endpoints=<...> get /service/<C>-<X>/leader

# снимок кластера
curl -s --cacert <ca.pem> https://<host>:<patroni>/cluster | jq
```

`patronictl list` внутри контейнера ноды — человекочитаемая альтернатива
для админ-зоны; в автоматике используется REST/проба.

## 6. Чего не делать

- **Не определять мастера по значению мастер-ключа** — вырожденное
  значение (`host:0`, пустая строка) матчится в обе стороны: DDL уйдёт на
  реплику, детекция смены мастера «по изменению значения» не сработает
  (S4).
- **Не искать HAProxy stats** — HAProxy в топологии нет; его «backend UP»
  не существует как источник.
- **Не повышать реплику вручную** (`pg_ctl promote`) при живом DCS: это
  обходит Patroni и создаёт split-brain ([09-troubleshooting.md](09-troubleshooting.md)
  §4).
