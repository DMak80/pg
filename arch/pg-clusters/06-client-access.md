# Клиентский вход: pg_doorman и дискавери

Уровень 3. Как приложение находит мастера и подключается: дискавери из
etcd, пулер `pg_doorman` на каждой ноде, пул и его ограничения, TLS и
аутентификация. Раскладка ноды — [02-topology.md](02-topology.md);
сетевая модель — [13-network-security.md](13-network-security.md).

## 1. Роль pg_doorman

**pg_doorman** — пулер на каждой ноде, слушает `:6432` и держит бэкенд
**только** `127.0.0.1:5432` этой ноды. Клиентский трафик приложений идёт
исключительно через пулер; прямых подключений приложений к `:5432` нет.

Пул один: пара `(database, user)` = `<C>` + app-роль. Бакеты — схемы этой
же базы, а не отдельные БД/пулы: переезд бакета пулер не трогает (меняется
только соответствие бакет → шард в etcd). Per-bucket роли отклонены: каждая
роль — отдельный пул со своим `pool_size` и `max_db_connections`, общего
капа «на ноду» нет — 256 пулов ломают бюджет соединений
([12-bucket-pitfalls.md](12-bucket-pitfalls.md) P14/P15). Радиус
компрометации app-кредов — все бакеты кластера (принято вместе с
инвариантом единой БД).

**HAProxy в топологии нет** ([01-ha-architecture.md](01-ha-architecture.md)
§8): приложение получает адрес `host:6432` из etcd и подключается к
doorman мастер-ноды; общего балансировщика и отдельной точки входа нет.

## 2. Дискавери и построение DSN

Маршрутизация по схеме — обязанность кода приложения (pgbouncer/HAProxy
выбрать шард по `schema_name` не могут). На каждый запрос/транзакцию
приложение знает `bucket_id` (из контекста клиента) и строит DSN:

1. **Bootstrap**: в статическом конфиге приложения — только адреса etcd
   (`ETCD_ENDPOINTS` + TLS) и имя кластера `<C>`. Адресов БД и имени базы
   в статике нет.
2. `buckets` (N) и `dbname` — из `/clusters/<C>/config` (константы init;
   `dbname = <C>`).
3. `bucket_id = hash(tenant_id) % N`, схема = `bucket_<id>`.
4. Шард-владелец — `/clusters/<C>/buckets/routing/bucket_<id>` (кэш с TTL
   секунды, инвалидация watch'ем префикса `buckets/`).
5. Адрес мастера — `/clusters/<C>/shards/<X>/master` (формат `host:6432`,
   lease TTL 5 с + продление; Patroni-callback).
6. DSN — `host=<master-host> port=<master-port> dbname=<C>
   user=<app_user> password=<app_password>` **конкатенируется** с
   `app_params` мастер-ноды (`sslmode=require` и прочие серверные параметры
   соединения). `master-host`/`master-port` — из значения master-ключа
   (опубликованный порт doorman, не литерал `6432`). Клиент не додумывает
   серверные настройки.
7. Сопоставление `host:port` из master-ключа → нода (чьи `app_params`
   брать): hosts/ports в dsn-ключе идут по возрастанию имён нод; индекс в
   dsn-списках даёт имя ноды.
8. Пулы — **на каждый шард** (map `shard_id → pool`), не на бакет:
   переезд бакета пулы не рвёт.

Клиентское поведение (таймауты, `application_name`) — настройка клиента;
`app_params` — только сервернозависимая часть.

## 3. Отказы и переходы

- `FROZEN` (статус-ключ бакета) — write-запросы отклоняются **повторяемой**
  ошибкой («бакет переезжает»), чтения идут на владельца.
- **Контракт приложения на любую ошибку записи** (FROZEN-retryable,
  `permission denied` «призрака», обрыв при failover): сброс кэша маршрута
  → refetch из etcd → ретрай.
- **Failover мастера**: Patroni-callback обновляет master-ключ (окно —
  единицы секунд; budget — [01-ha-architecture.md](01-ha-architecture.md)
  §4); новые соединения идут на нового мастера, оборванные
  переподключаются по обновлённому ключу.
- **Смерть ноды**: master-ключ гаснет по lease (≤5 с) — роутер отказывает
  в новых подключениях к шарду, не тыкая в мёртвый адрес.
- **Недоступность etcd**: роутер работает по last-known-good кэшу
  (fail-open, [12-bucket-pitfalls.md](12-bucket-pitfalls.md) P9) — маршруты
  не протухают, переезды и выборы заморожены.
- **Переезд бакета**: flip меняет `routing`; коннекты перетекают на нового
  владельца после разморозки записи.

## 4. Пул и бюджет соединений

Конфиг пулера рендерит загрузочный агент из шаблона
`DOORMAN_CONFIG_TEMPLATE` (пароль — плейсхолдер `${PGW_SU_PASSWORD}`,
подставляется агентом; секрет живёт только в tmpfs/памяти контейнера).

| Параметр | Значение | Смысл |
|---|---|---|
| `port` | `6432` | клиентский вход, TLS `require` |
| `server_host`/`server_port` | `127.0.0.1`/`5432` | бэкенд только своей ноды |
| `server_database` | `<C>` | единственная БД кластера |
| `pool_mode` | `transaction` | бэкенд держится на время транзакции; 55 серверных соединений обслуживают тысячи клиентов |
| `max_db_connections` | `max(10, max_connections − 5)` | бюджет doorman → PG на ноду (P15); остаток — админ/mover/reserved |
| `auth_query` | `SELECT passwd FROM pg_shadow WHERE usename = $1` | динамическая проверка кредов клиента от superuser `postgres` |

Режим `transaction` поддерживает prepared statements (включая анонимные),
`COPY`, `SET LOCAL`; **запрещены** сессионные практики: `SET` вне
транзакции, кросс-транзакционные advisory locks, `WITH HOLD`, temp tables,
`LISTEN`. Адресация бакета — схема: `bucket_N.table` или
`SET LOCAL search_path` (P13/P14).

## 5. TLS

- app → doorman `:6432` — **`sslmode=require`** (минимум TLS 1.2);
  `hostssl`-правила в `general.pg_hba` doorman; серт/ключ doorman
  материализуются агентом из per-install REST-CA в `/run/pgw/doorman/`
  (один серт ноды обслуживает REST `:8008`, doorman `:6432` и mTLS-канал
  агента `:8081`).
- Верификация серверного сертификата клиентом **не требуется**:
  адрес ноды приложение получает из etcd, доверие адресу обеспечивает
  аутентификация etcd-канала (TLS + префикс кластера) — канон P17.
- doorman → PG (loopback) — без TLS (`server_tls_sslmode=disable`):
  трафик не покидает ноду; включение — одна строка, если потребует
  политика.
- Аутентификация doorman → PG — `scram-sha-256` на loopback (не `trust`):
  `host <C> app 127.0.0.1/32 scram-sha-256`.

## 6. Админ-консоль и служебные входы

- **Админ-консоль doorman** (БД `pgdoorman` на `:6432`): `admin_username`/
  `admin_password` из конфига; `general.pg_hba` — только с ноды
  (`host pgdoorman admin 127.0.0.1/32 …`).
- **Прямой `:5432`** — только loopback (doorman), реплики своего шарда,
  подписки переездов (`bucket_mover`) и админ-зона; приложениям закрыт.
- **Миграционная роль-владелец схем** — DDL, напрямую из админ-зоны, не
  через doorman (P5).
