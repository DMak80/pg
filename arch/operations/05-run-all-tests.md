# Runbook: полный прогон всех тестовых серий (параллельная схема)

Уровень 3. Процесс полного прогона всех тестовых проектов монорепо одной
командой: `PgWorker.E2eTests` — параллельно всем остальным сериям, остальные —
последовательно между собой. Родитель — [README.md](README.md); команды
одиночных серий — [04-e2e-runs.md](04-e2e-runs.md); правила телеметрии,
поведения при падении и изоляции — [testing/01-e2e-launch.md](../testing/01-e2e-launch.md),
[testing/02-e2e-isolation.md](../testing/02-e2e-isolation.md).

## 1. Скрипт

```bash
scripts/run-all-tests.sh          # полный прогон (сборка + все серии)
scripts/run-all-tests.sh --dry-run  # показать план (проекты/порядок), ничего не запускать
```

Скрипт самодостаточен и НЕ правится под каждый запуск:

- **автодетект проектов** — `src/tests/*/*.csproj` (фантомные каталоги без
  csproj отсеиваются сами); `PgWorker.E2ePrepare` (утилита подготовки) и
  `Shared.TestInfra` (инфраструктура) в прогон не входят;
- классификация по суффиксу: `*UnitTests` → юниты, `*IntegrationTests` →
  интеграционные, `*E2eTests` → E2E;
- логи каждого проекта — целиком в `<run-dir>/<проект>.log`; сводка —
  `<run-dir>/summary.tsv` (проект / exit / длительность / итоговая строка
  Passed-Failed-Skipped) и таблица в stdout в конце;
- каталог прогона `<run-dir> = /tmp/pgw-testruns-<UTC-дата>-<HHMMSS>`
  печатается в первой строке — разбор падений ведётся по этим логам;
- итоговый exit-код: 0 только если все проекты зелёные.

## 2. Порядок (процесс)

```
0) dev-stand/images/pull-images.sh            — внешние образы (docker-серии)
1) dotnet build src/PgWorker.slnx -c Release  — ОТДЕЛЬНОЙ командой (канон 04)
2) dotnet run --project src/tests/PgWorker.E2ePrepare -c Release
3) [фон]  PgWorker.E2eTests                   — самая длинная серия (~20–28 мин)
4) [последовательно, параллельно фону из 3]:
     юниты (все, ~2 мин) → интеграционные (docker, ~12 мин) →
     E2E KafkaWorker → S3Worker → ValkeyWorker (~6 мин)
5) ожидание фона из 3, сводка по всем сериям
6) отчёт об остатках docker (строки ниже) — без удаления
```

Обоснование схемы — статистика полного прогона 2026-11-05 (Release,
последовательные серии): юниты 12 проектов ~2 мин; интеграционные ~12 мин
(KafkaWorker 4м32с — тяжёлый); E2E: PgWorker 19м48с–28м, Kafka 59 с,
S3 2м45с, Valkey 1м15с. PgWorker.E2eTests — 60–70 % времени полного прогона;
его вынос в параллельный поток сжимает стену прогона с ~40 до ~25 мин
(лимит — PgWorker.E2eTests + интеграционные).

## 3. Канонические следствия параллельности

- Изоляция контуров (guid-имена, динамические порты —
  [testing/02-e2e-isolation.md](../testing/02-e2e-isolation.md)) делает
  параллельность безопасной по именам/портам; остаточная нагрузка на
  docker-хост (CPU/диск) растёт — известное следствие:
  - бюджеты фаз PgWorker.E2eTests выставлены под параллельную нагрузку
    полной серии (provision 150 с, потолки окон/факта 5 мин — история в
    git, коммит 0da9fd4e); при добавлении тяжёлых серий пересчитывать
    по прецеденту ×1.2 от фактической потребности;
  - падение серии по бюджету сходимости при зелёных соседях — первый
    кандидат на «нагрузка», а не на дефект: разбирать по логам
    (`<run-dir>`), не перезапуском (правила — 01-e2e-launch.md).
- Полные серии поверх поднятого dev-стенда по-прежнему запрещены; скрипт
  перед стартом печатает `docker ps` — стенд обязан отсутствовать.
- Зачистка — own-only (каждая серия чистит своё в teardown);
  скрипт в конце печатает остатки (`docker ps -a` c префиксами `pgw-`/`kfw-`)
  как страховочный отчёт и НЕ удаляет ничего: чужие контейнеры/стенд
  не трогаются; ручная зачистка — по этому отчёту.

## 4. Мониторинг

Запустивший скрипт (агент/человек) ведёт наблюдение по канону базовых
правил: после старта — убедиться по логам, что фаза 1–3 пошли; далее
каждые ~2 минуты — прогресс: `[phase]`-строки скрипта в stdout и хвосты
`<run-dir>/*.log`; упавшая серия НЕ перезапускается до разбора логов.
