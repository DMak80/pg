## 1. Цель (часть А — cutover)

Устранить вечную заморозку бакета при переезде, если приложение создало в схеме
бакета таблицу или sequence с именем вне алфавита `^[a-z][a-z0-9_]*$`
(например `"Orders"` — квотированный DDL ORM, `"order items"`, имя с кавычкой
или одинарной кавычкой внутри — любые имена, валидные для PostgreSQL).

Сегодня cutover читает имена таблиц/sequences из каталога источника
(`pg_class.relname`, в агрегате LOCK-списка — через `format('%I.%I')`), после
чего гонит их через `MoveSql.Qualified` → `Ident`, который бросает
`ArgumentException` на всём вне `^[a-z][a-z0-9_]*$`
(`src/PgWorker.Moves/Sql/MoveSql.cs:5–10, 31–32, 242–243`). Исключение летит
синхронно при построении SQL (аргумент `MoveSql.RowCount(...)` вычисляется до
`ScalarAsync`) — мимо `Result`-механики и мимо `FailAsync`: разморозки не будет.
Поражённые точки: шаг 5 sequences (`SequenceIssued`/`SequenceNext`/
`SetvalForward`, `CutoverSequence.cs:161/164/173`) и шаг 6 сверки строк
(`RowCount`, `CutoverSequence.cs:188/191`); тот же дефект — в доведении
sequences при abort+force (`AbortSequence.cs:295–310`, те же билдеры).

### Сценарий отказа (закрывается фиксом)

Переезд бакета с таблицей `"Orders"`: M0–M3 проходят, cutover замораживает
источник (REVOKE×3 + LOCK — app-роль без DML), на шаге 5/6 — синхронный
`ArgumentException`; пер-кластерный catch-all ReconcileLoop гасит исключение,
но статус `FROZEN` и заявка живы. Следующий тик: заявка в фазе cutover →
повтор M4 → заморозка идемпотентна → снова `ArgumentException` — вечный цикл,
бакет заморожен на запись до ручного abort/unfreeze, каждый тик пишет `crashed`
в журнал.

### Решение (принято пользователем, перевыбору не подлежит)

Имена, пришедшие из каталога источника, НЕ гонять через `Ident`-валидатор:
строить SQL квотированием — `"имя"` с удвоением внутренних `"` (инъекция
исключена: имя уже из каталога PG, а закавыченный идентификатор не
интерпретирует ничего, кроме незакрытой `"`). В строковых SQL-литералах
(единственный случай — regclass-аргумент `setval`) одинарные кавычки имени
экранируются удвоением `'` → `''`.

Отклонённая альтернатива: «валидировать один раз в M0 и отвергать заявку
`CutoverPermanentException` до заморозки» — ОТКЛОНЕНА пользователем.
Обоснование отказа: имена вида `"Orders"` — легальные имена PostgreSQL,
созданные приложением штатно (ORM, квотированный DDL); валидация в M0 не
чинит ничего, а делает легальные бакеты вечно непереезжаемыми — оператору
нечего «исправить» в заявке, переезд обязан уметь такие имена. Квотирование
устраняет сам корень: законны имена, незаконной была потеря квотирования при
построении SQL.

## 2. Принципы (часть А)

1. **arch/-first соблюдён без правки `arch/`.** Канон предписывает работать со
   ВСЕМИ объектами схемы без ограничений алфавита имён: arch/14 §5 F — cutover
   «5) sequences P6 (issued источника → setval только вперёд на приёмнике);
   6) сверка строк P8 (count(*) всех таблиц)»; arch/11 §5 шаг 4 — «список
   таблиц для LOCK — генерировать из pg_class/pg_namespace (все relkind='r'
   схемы), не хардкодить», синхронизация «поимённо для ВСЕХ sequence схемы».
   Ограничение `^[a-z][a-z0-9_]*$` в каноне отсутствует; механизм построения
   SQL (квотирование vs валидация) каноном не описан — это деталь
   реализации. До фикса код РАСХОДИЛСЯ с каноном (падал на легальных именах);
   фикс приводит код в соответствие; контракт не меняется — каталог `arch/`
   не трогаем.
2. **Два класса имён — два механизма подстановки.** Заявочные/конвенционные
   имена (bucket-схема, publication/subscription/slot, app-роль) приходят из
   etcd/API и валидируются `Ident` — защита от SQL-инъекций остаётся
   без изменений. Каталоговые имена (таблицы/sequences из `pg_class`
   источника) уже пережили парсинг PostgreSQL — они подставляются
   квотированием, без валидатора.
3. **Минимальный дифф, ничего сверх приказа.** Меняются только поражённые
   пути: билдеры каталоговых имён в `MoveSql` и получение списка таблиц для
   сверки в `CutoverSequence`. Freeze-шаг (агрегат `format('%I.%I'`
   вставляется в `LOCK TABLE` целиком, без парсинга) багом не поражён — не
   трогаем. Обработка исходов cutover в `MoveProcess` (transient/permanent,
   `flip.IsSuccess == false`) не меняется: после фикса путь с экзотическими
   именами просто перестаёт бросать.
4. **Идемпотентность cutover сохраняется.** Повторный заход (resume из
   `FROZEN`/fail-фаз, `ReachedCutover`) идёт с начала блока: заморозка
   идемпотентна, sequences — setval только вперёд, сверка — чистые SELECT.
   Фикс не добавляет новых состояний/фаз.
5. **AbortSequence чинится автоматически.** Доведение sequences при
   abort+force (`AbortSequence.cs:295–310`) использует те же
   `SequenceNames`/`SequenceIssued`/`SequenceNext`/`SetvalForward` — правка
   билдеров в `MoveSql` закрывает оба процесса; отдельных правок
   `AbortSequence` не требуется.

## 3. Структура / компоненты (часть А)

### 3.1. `src/PgWorker.Moves/Sql/MoveSql.cs`

1. **Новый квотирующий хелпер** (для имён ИЗ КАТАЛОГА источника):

   ```csharp
   // Квотирование имени из каталога источника (pg_class.relname): любые
   // валидные для PG имена, БЕЗ Ident-валидации. Удвоение " внутри —
   // закавыченный идентификатор не интерпретирует ничего, кроме " —
   // инъекция исключена.
   private static string Quote(string name)
       => $"\"{name.Replace("\"", "\"\"")}\"";
   ```

2. **`Qualified(schema, name)`** (`MoveSql.cs:242–243`): схема остаётся через
   `Ident` (bucket валидирован в M0/rollback — заявочное имя), имя переходит
   на `Quote`:

   ```csharp
   private static string Qualified(string schema, string name)
       => $"{Ident(schema)}.{Quote(name)}";
   ```

   Все потребители `Qualified` — каталоговые имена (`SequenceIssued`,
   `SequenceNext`, `SetvalForward`, `RowCount`); их сигнатуры не меняются.

3. **`SetvalForward`** (`MoveSql.cs:233–234`): `Qualified`-строка лежит в
   SQL-литерале `'...'` (regclass-аргумент setval) — одинарные кавычки имени
   экранируются удвоением:

   ```csharp
   public static string SetvalForward(string schema, string seq, long issued)
       => $"SELECT setval('{Qualified(schema, seq).Replace("'", "''")}', {issued}, true)";
   ```

   `RowCount`/`SequenceIssued`/`SequenceNext` — идентификатор вне литерала,
   достаточно `Quote` внутри `Qualified`.

4. **Новый построчный список таблиц для сверки** (по образцу `SequenceNames`;
   тот же фильтр, что у агрегата `TableNames`, — `relkind IN ('r','p')`):

   ```csharp
   // Имена r/p-таблиц схемы построчно (verify_row_counts P8): каталог
   // источника несёт любые валидные для PG имена — квотирование на стороне
   // C# (Quote), без строкового roundtrip через агрегат (split/trim теряют
   // имена с ", " и " внутри).
   public static string TableRelnames(string schema)
       => $"SELECT c.relname FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace " +
          $"WHERE c.relkind IN ('r','p') AND n.nspname = '{Ident(schema)}' ORDER BY 1";
   ```

   `ORDER BY 1` — детерминизм списка (как у `SequenceNames`).

5. **`TableNames` (агрегат) остаётся** — единственный потребитель:
   freeze-шаг 1 (`CutoverSequence.cs:99–104`): агрегат
   `format('%I.%I', ...)` строит корректно квотированный список самим PG и
   вставляется в `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE` целиком, без
   обратного парсинга, — любые имена работают и сегодня.

6. **Docstring класса `MoveSql`** обновить: каталоговые имена
   (таблицы/sequences из `pg_class` источника) подставляются квотированием
   (`Quote`, удвоение `"`; в SQL-литералах — ещё и удвоение `'`); заявочные/
   конвенционные имена (схема-бакет/публикация/подписка/слот/роль) —
   валидируются `Ident` (защита от инъекций через API/etcd).

### 3.2. `src/PgWorker.Moves/Process/CutoverSequence.cs`

Шаг 6 (сверка строк P8, строки 183–199): уходим от парсинга агрегата —
построчный `ListAsync`:

- `sql.ScalarAsync(curDsn, MoveSql.TableNames(c.Bucket), ct)` →
  `sql.ListAsync(curDsn, MoveSql.TableRelnames(c.Bucket), ct)`;
- сбой листинга — тот же путь `FailAsync(..., CutoverPhases.VerifyFailed, ...,
  unfreeze: true, ...)` (поведение исходов не меняется);
- `foreach (var table in tables.Value)` — имена напрямую в
  `MoveSql.RowCount(c.Bucket, table)`, без деквотирования;
- пустой список → цикл не выполняется (сверка пустой схемы проходит).

**`ParseTables` (строки 293–305) удаляется** — становится мёртвым кодом.
Обоснование обязательности (квотирования одного недостаточно):
`ParseTables` делает `Split(", ")` + `Trim('"')` — имя с `, ` внутри
разрезается сплитом, имя с `"` внутри теряет roundtrip через `Trim`
(`"a""b"` → `a""b` ≠ исходное `a"b` → сверка ходила бы в несуществующую
таблицу — вечный transient-ретрай вместо ArgumentException). Построчный
`TableRelnames` устраняет сам класс ошибок «строковый roundtrip имён».

Шаги 1–5, 7 (freeze, FROZEN, LSN, слот, sequences, flip) — без изменений
потока: шаг 5 уже получает sequences построчно (`SequenceNames`), его
билдеры чинятся внутри `MoveSql` (§3.1); freeze остаётся на агрегате
`TableNames`.

### 3.3. `src/tests/PgWorker.IntegrationTests/E2e/E2eMoveScenarios.cs`

E2E-маркер регрессии на реальном PG (решение пользователя): в
`SeedBucketAsync` сида исходного бакета добавить объекты с именами вне
алфавита валидатора, покрывающие ОБА поражённых пути:

- таблицу `"Orders"` (заглавная — точный сценарий отказа из ревью #3:
  квотированный DDL ORM): `CREATE TABLE {bucket}."Orders"(id bigint
  GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, note text NOT NULL);` +
  вставка нескольких строк (`generate_series`) — сверка строк идёт и по ней;
- sequence `"Orders_seq"`: `CREATE SEQUENCE {bucket}."Orders_seq";` — шаг 5
  sequences идёт и по ней (существующие `items`/`items_id_seq` остаются).

Существующие GRANT-строки сида (`ALL TABLES`/`ALL SEQUENCES IN SCHEMA`)
покрывают новые объекты без правок. Порты/окружение не меняются (канон
динамических портов E2E untouched).

### 3.4. Автоматически чинящиеся потребители (без правок)

- `AbortSequence.cs:295–310` — доведение sequences при abort+force: те же
  билдеры; существующие тесты `AbortSequenceTests` обязаны остаться зелёными.
- `MoveProcess.cs` — диспетчер исходов cutover не меняется.

### 3.5. Тестовые фейки

`FakesMove.CutoverLayer` и `CutoverSequenceTests.CutoverSql`: матчинг
«таблицы схемы» обновляется под новый поток — freeze продолжает матчиться по
агрегату (`string_agg(format('%I.%I'` в `ScalarResolver`), verify — по
построчному запросу `TableRelnames` (ветка в `ListResolver` по образцу
существующей `s.relkind = 'S'` для `SequenceNames`). Матчинг `RowCount`
(`count(*) FROM bucket_42.`) остаётся рабочим для квоченных имён.

### 8.3. Фейл 1 — `Acceptance_Scenario_Ac2_To_Ac7` (ac6-quarantine)

**Диагноз** (уверенность ВЫСОКИЙ; детали — investigation §Фейл 1):
структурная гонка «клиентский таймаут < грейс стопа + журнал после стопа».
`docker stop?t=10` упирающегося spilo длится 7–10+ c; `HttpClient`
(`DockerEngineFactory.CallTimeout=7.5 c`) обрывает запрос → `StopNodeAsync`
Failed при фактически успешном исходе. `BucketEvacuator.HandleReturnedShardAsync`
писал журнал `QUARANTINED`+`returned_unix` только ПОСЛЕ успешных стопов всех
нод → записи нет; следующий тик: REST-проб нет → ранний выход «ещё мёртв» →
журнал навсегда `DONE`, ассерт теста (контракт arch/14 §5 E3) падает по
бюджету 120 с. Не единичный флейк (3 падения за день).

**Природа:** прод-баг двух слоёв — docker-стоп (несовместимость одиночного
`CallTimeout=7.5 c` с `stop?t=10`) и порядок журнала эвакуатора.

**Решение (исполнено, задачи 10–11; уточнено kill-дельтой):**
1. `StopContainerAsync` — поллинг до exited-факта (`750ae4af`, arch/14 §6):
   одиночный HTTP-запрос ≤7.5 c; при клиентском таймауте — идемпотентный
   повтор `POST /stop` и/или GET-инспект `State.Running` до факта
   `exited`/`304`/`404` в бюджете `t + одна итерация` (<30 с); бюджет без
   факта — Failed. Сохраняется для ВСЕХ потребителей, кроме spilo-путей
   (пункт 1a).
2. `HandleReturnedShardAsync` — журнал `QUARANTINED`+`returned_unix` в
   момент первого обнаружения живой ноды, ДО docker-стопов
   (`8b94a1fe`, P7 journal-before-manipulations, arch/14 §5 D); сбой стопа
   не отменяет факт возврата (Failed-тик, retry следующим тиком).
3. Тест AC6: ассерты exited валидны только после фактической остановки —
   фаза `ac6-returned-stopped` (WaitPhase exited ≤60 с ПОСЛЕ QUARANTINED),
   §6 п.22; существо сценария не меняется (exited требовался и раньше).

**1a. Kill-дельта (приказ пользователя, §6 п.21):** spilo-ноды (PG/Patroni)
останавливаются `docker kill` (SIGKILL) — семантика внезапной потери машины:
multi-host-модель (отказ docker-хоста целиком — штатный сценарий, arch/14
§6), жёсткая смерть ноды — штатный канал (arch/14 §5 C: бюджет смены лидера
явно различает каналы graceful/жёсткой смерти; Patroni реконвергирует).
SIGKILL даёт exited-факт немедленно — корень гонки `CallTimeout=7.5 c`
устраняется на spilo-путях вовсе, поллинг-стоп им больше не нужен (но остаётся
для всех прочих контейнеров, §5.9). Реализация — §8.3a.

### 8.3a. Компоненты kill-дельты (фаза 4a)

1. **`src/Shared.Docker/Engine/DockerEngine.cs`** — новый метод
   `KillContainerAsync(idOrName, ct)`: `POST /containers/{id}/kill`; сегодня
   метода в движке нет (есть только Stop/Remove). Идемпотентность: `404` =
   успех (контейнера нет); результат Failed — только по факту транспортного
   отказа/ошибки демона. Single HTTP-запрос в `CallTimeout=7.5 c` — kill
   не грейсный, ответ демона немедленен, поллинг не требуется.
2. **`src/PgWorker.Docker/Drivers/ClusterDriver.cs` — `StopNodeAsync`
   (~405–417):** остановка spilo-нод (PG/Patroni-контейнеры нод шардов)
   переводится на `KillContainerAsync` (вместо `StopContainerAsync(t=10)`);
   семантика вызова не меняется («остановить, данные/volume на месте» —
   карантин E3, restore-демонтаж, deprovision).
3. **`src/PgWorker.Provisioning/Processes/NodeSupervisor.cs` (~645)** —
   прямой вызов движка в ветке пересоздания (rest-tls: stop + rm force +
   EnsureNode): spilo-нода → `KillContainerAsync`.
4. Юнит-тесты — §7.13.5 (по образцу `DockerEngineStopTests`; тестовый фейк —
   синхронный, без задержек: kill — одиночный немедленный ответ демона,
   поллинга нет, отменять нечего — cancellation-aware-фейк не требуется, он
   был нужен поллинг-stop-тестам). Границы: kill ТОЛЬКО spilo-ноды PgWorker;
   NodeSupervisor-ы Kafka/S3/Valkey и их драйверы остаются на поллинг-стопе
   (их ноды — не spilo, §5.9).
