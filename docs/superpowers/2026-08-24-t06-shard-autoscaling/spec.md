## 1. Цель

Дать оператору панели AdminPanel управлять **числом шардов живого
инициализированного кластера** с оркестрацией PgWorker:

1. **Add-shard** — панель заявляет новый шард в уже инициализированном
   (Active) кластере по образцу создания кластера (02 §9): объявление
   `shards/<X>/replicas` + `nodes/<n>/state=NOT_INITIALIZED` + заявки
   ресурсов `/service/<C>-<X>/request_*`; PgWorker поднимает ноды
   (volume/контейнеры/сервисы, Patroni, роли, БД) и регистрирует шард
   (`dsn`). **Новый шард стартует пустым**: ни один routing-ключ не
   меняется, никаких схем бакетов на нём не создаётся.
2. **Remove-shard** — панель ставит на шард маркер демонтажа
   `shards/<X>/state=TO_REMOVE`; PgWorker проверяет guard'ы (шард без
   бакетов, нет незавершённых переездов, нет карантина), демонтирует
   контейнеры/volumes одного шарда, чистит его ключи (`/clusters/<C>/
   shards/<X>/`, `/service/<C>-<X>/`, записи portalloc, журнал эвакуации).
   **Кластер продолжает жить** — остальные шарды и запись в бакеты не
   затрагиваются.

Свойства наследуются от PgWorker: мульти-инстансность (пер-кластерный
lease-клэйм), takeover ≤ TTL 15 с + тик, идемпотентность всех шагов,
состояние в etcd + на нодах (смерть контроллера ничего не роняет).

## 2. Границы

### 2.1. КЛЮЧЕВАЯ ГРАНИЦА (уточнение пользователя — нарушать нельзя)

**Никакой автоматической перебалансировки бакетов в этой задаче нет:**

- add-shard **не двигает ни один бакет**: новый шард поднимается пустым
  (routing не меняется, схемы `bucket_<i>` на нём не создаются, status-ключи
  не трогаются);
- remove-shard шарда, на котором по routing есть бакеты, **блокируется**
  guard'ом с понятной оператору ошибкой — сначала явные переезды (заявки
  `/pgworker/moves/` из t01 — пока через etcdctl; панельные кнопки переездов
  будут отдельной задачей, см. §10.3), потом демонтаж. Маркер демонтажа
  «живёт»: после уезда последнего бакета следующий тик PgWorker демонтирует
  шард автоматически, повторная команда не нужна.

### In scope

- **pg**: контракт etcd (декларация add-shard — переиспользование ключей
  §9; новый ключ-маркер `shards/<X>/state=TO_REMOVE`); два новых процесса
  `AddShardProcess` (A0–A6) и `RemoveShardProcess` (S0–S4); классификация
  шардов в ReconcileLoop; правки NodeSupervisor (границы надзора), MoveProcess
  (guard'ы целей), DeprovisioningProcess (чистка журналов эвакуаций);
  парсер `ClusterSnapshotParser` (ключ `shards/<X>/state`); тесты unit/
  integration/e2e; правки arch/ (§10).
- **AdminPanel**: две новые мутации — `POST /api/clusters/{cluster}/shards`
  (add) и `DELETE /api/clusters/{cluster}/shards/{shard}` (remove);
  протоколы записи по образцу 02 §9.2/§9.4 (клэйм-txn имени шарда,
  компенсация, идемпотентность); парсер и DTO (`ShardDto.state`); UI —
  кнопки «Добавить шард»/«Убрать шард», бейдж «к удалению», форма добавления;
  тесты; правки arch/02 и arch/03 (§10.2).

### Out of scope (в roadmap, §10.3)

- **UI явных переездов бакетов** (кнопки «перевезти/откатить/finalize/abort»
  → заявки `/pgworker/moves/`) — новая задача `t07-move-bucket-ui`; в t06
  переезды инициируются только etcdctl'ом (существующий контракт t01).
- Любой автоподбор «куда переехать» (балансировка по метрикам, auto-rebalance
  после add-shard) — вне t06 и t07.
- Смена `replicas` у живого шарда (масштабирование реплик внутри Patroni —
  arch/11 §4.5 «Число реплик», ручной путь).
- Add-shard для кластеров `NOT_INITIALIZED` (структура кластера фиксируется
  при создании; дождаться provisioning) и любых кластеров вне PgWorker
  (`init-cluster.sh`-мир: скрипты `add-shard.sh`/`remove-shard.sh` остаются
  ручным путём для внешних кластеров).
- Per-cluster секреты (t02), метрики (t04), слияние карантинных данных (t05).
- Отмена add/remove из панели (кнопок отмены нет; см. §11.Д8).

## 3. Принципы

1. **Декларативность и симметрия с кластерным уровнем.** Add-shard —
   уменьшенная копия создания кластера (та же декларация, тот же подъём);
   remove-shard — уменьшенная копия TO_REMOVE (тот же паттерн маркера,
   те же guard'ы, тот же порядок «сначала docker, потом etcd»).
2. **Маркер — состояние, а не заявка.** `shards/<X>/state=TO_REMOVE` не
   удаляется по завершении операции (в отличие от заявок `/pgworker/moves/`):
   пока шард не демонтирован, маркер жив; сами ключи шарда исчезают вместе с
   маркером в финале. Идемпотентность повторных PUT — как у 02 §9.4.
3. **Guard'ы перед манипуляциями** (journal-before-manipulations, P7):
   демонтаж начинается только после полного прохождения guard'ов; провал
   guard'а = `work.last_error` с человекочитаемой причиной + повтор тиком
   (после явных переездов бакетов пройдёт сам).
4. **Пустой шард — конструктор** (arch/11 §4.5): число шардов — меняемая
   величина (в отличие от N). Add не пишет в routing/status вообще; remove
   требует routing-пустоты (инвариант P23 `remove-shard.sh`, воспроизведён
   guard'ом S1).
5. **Мутации — только под живым клэймом кластера** (инвариант spec бэкенда
   §4.3): оба процесса выполняются в ветке Active ReconcileLoop под тем же
   пер-кластерным клэймом; никаких новых клэймов.
6. **Идемпотентность и takeover**: каждый шаг перепроверяет факт (контейнер
   есть? dsn записан? Patroni поднялся? ключи удалены?); фазы — в
   `/pgworker/work/<C>`; смерть инстанса → следующий продолжает.
7. **Видимость панелью без расширения снапшота**: прогресс обоих процессов
   виден панели из её существующих префиксов (`nodes/<n>/state`:
   NOT_INITIALIZED→PROVISIONING→RUNNING / →REMOVING; появление `dsn`;
   исчезновение ключей шарда; маркер TO_REMOVE). Префикс `/pgworker/`
   остаётся невидимым панели (контракт 02 без расширения).

## 4. Контракт etcd

Транспорт и паттерны записи — существующие (HTTP JSON gateway `/v3/*`,
txn-compare, клэйм-txn; 02 §1/§9.2).

### 4.1. Add-shard: декларация нового шарда (переиспользование схемы §9)

Панель дописывает к живому (Active) кластеру `<C>` ключи нового шарда
`<X>` (R — реплики, T — unix-время):

```
/clusters/<C>/shards/<X>/replicas            "<R>"
/clusters/<C>/shards/<X>/nodes/<n>/state     "NOT_INITIALIZED"   (R ключей; n = <X>a, <X>b, …)
/service/<C>-<X>/request_cpu                 "<cores>"           (на каждую ноду)
/service/<C>-<X>/request_mem                 "<Gi>Gi"
/service/<C>-<X>/request_disk                "<Gi>Gi"
```

- Имя шарда `<X>` генерирует панель: `shard<k>`, k = max(числовых суффиксов
  существующих шардов) + 1, ≤ 128 (§6.1). Паттерн — как у существующих
  (`^[a-z][a-z0-9_]{0,30}$`, без дефиса: scope `<C>-<X>` однозначен,
  имена нод `<X><буква>` без дефисов — разбор сирот в D1 это предполагает).
- **НЕ пишется:** `dsn` (PgWorker запишет после подъёма), `master` (lease
  появится с Patroni), routing/status (шард пустой), `config` кластера
  (N/dbname — константы, P18).
- Семантика для PgWorker: **шард с declared-нодами и без `dsn`** — кандидат
  AddShardProcess (детекция — §5.1). Ноды в `NOT_INITIALIZED`/`PROVISIONING`
  без `dsn` — домен add-shard, не надзора.

Протокол записи панели (§6.1): клэйм-txn имени (compare `version(
/clusters/<C>/shards/<X>/replicas)==0` + put) → пакет PUT остальных ключей
→ компенсация при сбое (del prefix `shards/<X>/` + точечные `request_*`).
Частичная декларация безопасна: AddShardProcess ждёт полного набора
(guard A1, фаза `waiting-keys`).

### 4.2. Remove-shard: маркер демонтажа (НОВЫЙ ключ)

```
/clusters/<C>/shards/<X>/state    →  "TO_REMOVE"
```

- Пишет ТОЛЬКО панель (как `config.state=TO_REMOVE`, 02 §9.4); единственное
  значение — `"TO_REMOVE"`; отсутствие ключа = обычный шард. Обратного
  перехода нет (one-way door, §11.Д8).
- Читают: PgWorker (детекция RemoveShardProcess) и панель (бейдж «к
  удалению» в UI). Оба парсера расширяются (сегодня ключ попадает в
  unknown-счётчик).
- Идемпотентность PUT: значение уже `TO_REMOVE` → успех без записи.
- Имя шарда освобождается финалом демонтажа (ключи шарда удалены →
  клэйм-txn add-shard того же имени пройдёт).

### 4.3. Пишемые/удаляемые ключи PgWorker (дельта к arch/14 §3.2)

| Ключ | Когда | Действие |
|---|---|---|
| `/clusters/<C>/shards/<X>/nodes/<n>/state` | add-shard A3/A4 | `PROVISIONING` → `RUNNING` (те же значения) |
| `/clusters/<C>/shards/<X>/dsn` | add-shard A5 | put multi-host (порты из portalloc, без пароля) |
| `/clusters/<C>/shards/<X>/nodes/<n>/state` | remove-shard S2 | `REMOVING` |
| `/clusters/<C>/shards/<X>/` (весь префикс) | remove-shard S3, после удаления docker-объектов | del prefix (state/replicas/nodes/dsn/master — всё) |
| `/service/<C>-<X>/` (весь scope) | remove-shard S3, guard: docker-объектов нет | del prefix |
| `/service/<C>-<X>/request_{cpu,mem,disk}` | remove-shard S3 | точечные del (даже если scope ещё жив) |
| `/pgworker/portalloc/<C>` | remove-shard S3 | read-modify-write: из JSON удалить записи `"<X>/<n>"` (merge под клэймом) |
| `/pgworker/evacuations/<C>/<X>` | remove-shard S3 | del (журнал эвакуации не переживает демонтаж шарда) |

Контрактное **финальное состояние после add-shard**: у шарда есть `dsn`,
все ноды `RUNNING`, `nodes`-ключи = декларации, routing/status/schema-
мир кластера не изменён НИКАК. После remove-shard: префиксы `shards/<X>/`
и `/service/<C>-<X>/` пусты, записей шарда в portalloc нет, остальные
шарды кластера не затронуты.

### 4.4. Guard'ы PgWorker (авторитетная проверка перед демонтажом)

Все guard'ы — в S1, перед любым разрушающим действием; провал любого —
`work.last_error` с причиной (перевод причины — в текст ошибки) и повтор
тиком (маркер остаётся):

| # | Guard | Причина блокировки (текст оператору) |
|---|---|---|
| G1 | кластер Active (config без `state`) | «кластер в NOT_INITIALIZED/TO_REMOVE — демонтируется целиком отдельным процессом» |
| G2 | шард заявлен (`replicas` + `nodes` есть) | «шард не заявлен — нечего демонтировать» |
| G3 | **ни один routing не указывает на `<X>`** (P23) | «на шарде N бакетов (routing) — сначала явно перевезите их (заявки /pgworker/moves/, UI переездов — t07)» |
| G4 | ни один status-ключ не ссылается на `<X>` (owner ИЛИ target) | «незавершённый переезд бакета — завершите/отмените» |
| G5 | нет заявок `/pgworker/moves/<C>/` с `to=X` или `old_shard=X` | «есть заявки переездов, ссылающиеся на шард — дождитесь их разбора» |
| G6 | нет нод `QUARANTINED` | «шард в карантине после эвакуации — сначала разбор данных (t05 runbook)» |
| G7 | в кластере есть другой шард (`shards.Count > 1`) | «нельзя снять последний шард — для полного демонтажа удалите кластер» |

Примечания: G3 — данные guard'а из снапшота тика (routing — единственный
авторитет); G4 покрывает «flip прошёл, статус завис» (P7) — routing уже не
на X, но статус ещё жив; G5 — заявки, которые MoveProcess сам перманентно
отклонит из-за TO_REMOVE (§5.5) и удалит, т.е. guard саморазрешающийся;
G6 пропускает случай «эвакуирован и НЕ вернулся» (ноды UNREACHABLE, журнал
DONE) — демонтаж разрешён, данные на мёртвых дисках; G7 — защита от кластера
без шардов (routing в никуда, critical-алерты).

Guard'ы add-shard (A1): кластер Active; полное объявление (replicas>0,
nodes.Count == replicas, состояния NOT_INITIALIZED/PROVISIONING); `dsn` нет
(есть → уже поднят, ничего не делать); scope `/service/<C>-<X>/initialize`
отсутствует (живой чужой Patroni-кластер с тем же scope = коллизия имён —
перманентная ошибка в журнал).

## 5. Процессы PgWorker

### 5.1. Классификация в ReconcileLoop (ветка Active)

Ветка Active (default) сегодня: `SuperviseAsync` → эвакуации → `moves`.
Добавляется проход **`ScaleShardsAsync`** — после надзора, перед
эвакуациями/moves (порядок: remove-проход → add-проход — демонтаж
освобождает хосты/порты для подъёма):

- **кандидаты remove**: шарды с `state=TO_REMOVE` → `RemoveShardProcess`
  (по одному шард-за-тик, последовательно);
- **кандидаты add**: шарды с declared-нодами (nodes.Count > 0) и без `dsn`
  → `AddShardProcess` (по одному, последовательно).

Детекция — чистая функция над `ClusterSnapshot` (unit-тестируемая,
расширение `ClusterClassifier`/новый `ShardScaleClassifier`): кладётся в
`IClusterProcesses` как `ScaleShardsAsync(snap, ct)`. Кластеры в
`NOT_INITIALIZED`/`TO_REMOVE` процесс не выполняют (guard A1/S1; их
обрабатывают Provision/Deprovision — декларация добавленного шарда
подхватится provisioning'ом как обычный шард, маркер шарда игнорируется
deprovisioning'ом — кластер сносится целиком).

### 5.2. AddShardProcess (A0–A6)

Машина состояний одного тика, идемпотентная — переиспользует механику
ProvisioningProcess в scoped-to-shard виде (EnsureNodeAsync, WaitPatroni,
portalloc-merge, DatabaseProvisioner). Эталон смысла — `add-shard.sh`
(регистрируется пустым) + P2.1–P2.5 provisioning'а:

```
A0 journal(/pgworker/work/<C>, op=add-shard, phase=started)   [клэйм кластера уже у тика]
A1 guard'ы §4.4 (add): кластер Active; полное объявление шарда (иначе phase=waiting-keys,
   InProgress — ждём доустойчивости ключей панели); scope свободен; dsn нет (есть → Done);
   перечитать config (гонка R6: NOT_INITIALIZED/TO_REMOVE → phase=aborted, InProgress)
A2 план: placement (PlacementPlanner по живым хостам, анти-аффинити с учётом занятости
   живыми шардами) + порт-аллокация (PortAllocator) для нод шарда; merge в существующий
   /pgworker/portalloc/<C> (read-modify-write; мутации под клэймом — конкурентов нет);
   journal phase=planned
A3 для каждой ноды n: EnsureNodeAsync (volume pgw-<C>-<X>-<n>-data + контейнер/сервис,
   Spilo env SCOPE=<C>-<X>, ETCD3_HOSTS, wal_level=logical и пр. — тот же билдер конфигов),
   лимиты из /service/<C>-<X>/request_{cpu,mem} (заявка — не контракт, null = без лимита),
   env-секреты §4 arch/14; nodes/<n>/state=PROVISIONING (уже PROVISIONING — сверить и
   пропустить); существующий объект — сверить и пропустить (идемпотентность re-run)
A4 ждать Patroni: /service/<C>-<X>/initialize + leader + REST каждой ноды (бюджет
   PatroniBootSec, транзиент-толерантно; протух бюджет → last_error + ретраи тиками);
   nodes/<n>/state=RUNNING
A5 SQL на мастере нового шарда: создать БД <dbname> (если нет), роли app/bucket_admin/
   bucket_mover + GRANT'ы (если нет) — ТОЛЬКО это; СХЕМЫ БАКЕТОВ НЕ СОЗДАЮТСЯ (шард пустой,
   routing на него не указывает); put shards/<X>/dsn (multi-host по нодам, порты portalloc,
   без пароля)
A6 снапшот P12 (точка изменения); journal phase=done → шард переходит в надзор
   (dsn есть → supervisor видит)
```

Отказ шага: journal `last_error` + фаза; ретрай следующим тиком (бэкофф).
Перечитывание `config` перед фазами — та же защита R6, что у provisioning
(смена state кластера безопасно прекращает add; контейнеры подчистит
deprovisioning кластера).

Частные случаи: имя шарда не прошло валидацию / scope занят — перманентная
ошибка (journal, декларация остаётся — разбор оператором через etcdctl);
порт-диапазон исчерпан — last_error «расширьте PortRange» (декларация
остаётся, ретраи; панельной отмены нет — §11.Д8).

### 5.3. RemoveShardProcess (S0–S4)

Эталон смысла — `remove-shard.sh` (инвариант P23) + DeprovisioningProcess
в scoped-to-shard виде; порядок «сначала docker, потом etcd» сохранён
(мёртвые ключи при сбое безвредны — маркер стоит, повторный тик продолжает):

```
S0 journal(op=remove-shard, phase=started)
S1 guard'ы G1–G7 (§4.4) над свежим снапшотом; провал → journal last_error с причиной,
   InProgress (маркер остаётся; после уезда бакетов пройдёт сам)
S2 для каждой ноды: nodes/<n>/state=REMOVING → RemoveNodeAsync (остановить и удалить
   контейнер/сервис + volume; 404 = ок); сироты pgw-<C>-<X>-* (по ListNodeObjects с
   фильтром шарда) — тоже; перечитать config перед началом (кластер TO_REMOVE → abort:
   deprovisioning снесёт всё сам)
S3 guard: docker-объектов pgw-<C>-<X>-* нет → чистка etcd: del prefix /clusters/<C>/
   shards/<X>/ + del точечные /service/<C>-<X>/request_* + del prefix /service/<C>-<X>/
   + portalloc: удалить записи "<X>/<n>" из JSON + del /pgworker/evacuations/<C>/<X>
S4 снапшот P12 (точка изменения); journal phase=done. Успех = ключей шарда нет ни в
   /clusters/, ни в /service/, ни в portalloc; кластер продолжает жить
```

Master-ключ шарда исчезает сам (lease TTL 5 с после смерти callback), но
S3 удаляет префикс с ним и явно. Deprovisioning-хвост: если между S2 и S3
кластер перевели в TO_REMOVE — D1/D2 кластера подчищат остатки (del prefix
`/clusters/<C>/` заберёт и недоочищенный шард).

### 5.4. Правки NodeSupervisor и эвакуации (границы надзора)

Надзор управляет только «живыми» шардами:

- **EnsureDeclaredNodes (самовосстановление контейнеров) пропускает шарды
  без `dsn`** (домен AddShardProcess) **и с маркером TO_REMOVE** (домен
  RemoveShardProcess — не пересоздавать то, что демонтируется). Сегодня
  skip по QUARANTINED/REMOVING-нодам уже есть — расширяется до шард-уровня.
- **Кандидат эвакуации** (весь шард мёртв ≥ ShardDeadSec) требует `dsn`
  (незарегистрированный шард не эвакуируется — add ещё идёт) **и ≥ 1 бакета
  на шарде по routing** (эвакуация пустого шарда — бессмысленная операция,
  которая карантинила бы ноды и блокировала демонтаж по G6). Шард с
  TO_REMOVE-маркером кандидатом БЫТЬ МОЖЕТ: если он умер с бакетами,
  эвакуация — способ освободить их, после чего G3 пропустит демонтаж
  (снятие бакетов с умирающего шарда — не «перебалансировка», а аварийный
  контур, существующий до t06).
- MasterKeyReconciler без изменений (для поднимающегося шарда помогает:
  lease-put по факту — тот же ключ, что пишет callback).

### 5.5. Правки MoveProcess (t01)

Новые валидации M0 (перманентные отказы с подсказкой, del заявки):

- `op=move` с `to` = шард в TO_REMOVE → «шард помечен к удалению —
  выберите другую цель»;
- `to` без `dsn` (в т.ч. шард в процессе add-shard) → уточнённая причина
  существующего отказа «to зарегистрирован (dsn-ключ)»: «шард ещё не
  поднят (add-shard не завершён)»;
- `op=finalize` с `old_shard` = удалённый шард (нет dsn) → «шард удалён —
  убирать нечего» (артефакты исчезли вместе с volume).

Переезды ИЗ TO_REMOVE-шарда разрешены — это штатный способ его опустошить.

### 5.6. Правки DeprovisioningProcess (мини-фикс, найден при проектировании)

D2 сегодня не чистит `/pgworker/evacuations/<C>/` — журналы переживают
удаление кластера. Добавить `del prefix /pgworker/evacuations/<C>/` в
`CleanKeysAsync` (симметрия с remove-shard S3; тест DeprovisioningProcess
расширяется).

### 5.7. Модель и парсер (PgWorker.Core/Etcd)

- `ShardSpec` расширяется: `bool ToRemove` (из `shards/<X>/state`;
  отсутствие/иное значение = false — толерантность как у config.state).
- `ClusterSnapshotParser`: ветка `shards/<X>/state` (segments.Length == 6,
  leaf «state»); битое значение — не ошибка, ToRemove=false + parseError не
  пишем (значение одно).
- Новая чистая функция детекции кандидатов add/remove (§5.1) — в Core или
  App (рядом с `ClusterClassifier`), покрывается unit-тестами.

Новых NuGet-пакетов, секретов и секций конфигурации нет (бюджеты —
существующие `PatroniBootSec`/`Thresholds`).

## 6. AdminPanel

### 6.1. API (третья и четвёртая мутации панели)

**`POST /api/clusters/{cluster}/shards`** — добавить шард. Тело
`AddShardRequestDto`: `replicas` (целое 1..26, дефолт 2), `requestCpu`
(0.01..64), `requestMem`/`requestDisk` (целые GiB 1..65536) — правила те
же, что 02 §9.3. Ответ **201** `ShardAddedDto`: `cluster, name` (сгенерированное
`shard<k>`), `replicas, requestCpu, requestMem, requestDisk` (канонические
строки), `state:"NOT_INITIALIZED"`. Отказы: **404** кластер не найден
(config-ключа нет / имя неканоническое); **409** кластер не Active
(NOT_INITIALIZED — «дождитесь инициализации»; TO_REMOVE — «кластер
удаляется») или клэйм имени шарда не сошёлся (конкурентный POST занял имя);
**400** валидация полей; **503** etcd недоступен.

Протокол (образец 02 §9.2, адаптация): (1) config читается напрямую у etcd
— состояние проверяется до записи (Active only); (2) имя шарда —
`shard<max+1>` по фактическому снапшоту префикса `shards/` (range); (3)
клэйм-txn: compare `version(shards/<X>/replicas)==0` + put `replicas`;
проигрыш → 409; (4) пакет PUT: `nodes/<n>/state=NOT_INITIALIZED` × R +
`request_{cpu,mem,disk}`; (5) сбой посередине → компенсация: del prefix
`shards/<X>/` + точечные del `request_*` (best-effort; частичная декларация
безопасна — AddShardProcess ждёт полного набора). Без ретраев: повтор =
новый POST. Повтор вычислит ТО ЖЕ имя (max по префиксу не изменился):
компенсация успешна → повтор проходит под тем же именем; компенсация
провалилась (выжил `replicas`) → клэйм даёт 409 и остатки разбираются
вручную (etcdctl) — молча создать «другой» шард повтор не может.

**`DELETE /api/clusters/{cluster}/shards/{shard}`** — демонтаж шарда.
Протокол (образец 02 §9.4): (1) имена канонические, иначе 404; (2) config
напрямую: нет → 404; state кластера не Active → 409; (3) шард существует
(`replicas`-ключ есть) иначе 404; (4) **серверная пред-проверка guard'ов по
данным снапшота** (быстрая оператору ошибка, PgWorker перепроверит
авторитетно): routing на шард > 0 → 409 «на шарде N бакетов — сначала
явно перевезите (UI переездов — t07)»; любой status-ключ с owner/target =
шард → 409 «незавершённый переезд»; шард один в кластере → 409 «нельзя
снять последний шард»; ноды QUARANTINED → 409 «сначала разбор карантина»;
(5) PUT `shards/<X>/state="TO_REMOVE"` (уже TO_REMOVE → идемпотентный
204 без записи). Ответ **204**; отказы 404/409/503 как выше. Гонки между
проверкой (4) и flip'ом переезда ловит guard G3/G4 PgWorker'а — маркер
останется, демонтаж подождёт (панель покажет бейдж + счётчик бакетов).

## 7. Надёжность (сводка по сценариям)

- **Идемпотентность**: повтор тика на любой фазе безопасен (EnsureNode
  сверяет объект, RemoveNode 404=ок, чистка ключей повторяема, portalloc —
  merge/фильтрация под клэймом).
- **Takeover**: фазы в `/pgworker/work/<C>` + факт в docker/etcd; смерть
  инстанса гасит клэйм ≤ 15 с, следующий продолжает (готовые контейнеры
  подхвачены A3, наполовину снесённые — S2).
- **Гонки**: панель пишет маркер посреди add (шард без dsn) — S1→S2
  корректно демонтирует недоднятый шард (RemoveNode 404=ок, ключи чисты),
  add-процесс на следующем тике увидит отсутствие шарда; панель пишет
  add-декларацию посреди remove того же имени — клэйм-txn упрётся в живой
  `replicas`-ключ до финала S3, потом имя свободно; кластер в TO_REMOVE
  посреди любого процесса — перечитывание config (R6-паттерн) + полный
  deprovisioning подчищает всё.
- **Отказ etcd**: контрол-плейн заморожен (P9) — разрушительных операций
  без свежего клэйма нет; живые шард/кластер не зависят.
- **Снапшоты P12**: точки изменения — финал add (A6) и финал remove (S4);
  провал снапшота — как у существующих процессов (last_error, ретрай).

## 11. Открытые вопросы и принятые решения (автономный режим)

- **Д1. Маркер демонтажа — `shards/<X>/state="TO_REMOVE"` (новый leaf),
  а не флаг в `/pgworker/` и не значение в `replicas`.** Обоснование:
  симметрия с `config.state=TO_REMOVE` (02 §9.4 — тот же паттерн one-way
  маркера); видимость панелью из её снапшота (`/clusters/`) без чтения
  `/pgworker/` (контракт панели не расширяется префиксом оркестратора);
  альтернатива «заявка в /pgworker/ по образцу moves» отвергнута — заявка
  удаляется по завершении и невидима панели, а оператору нужен постоянный
  «шард помечен к удалению» до самого демонтажа. `replicas` не портим —
  это число, его читает планировщик.
- **Д2. Add-shard объявляется переиспользованием ключей §9 (replicas +
  nodes/NOT_INITIALIZED + request_*), без специального маркера.**
  Обоснование: «шард заявлен, но не поднят» уже выразимо существующей
  схемой — ноды NOT_INITIALIZED и нет dsn; отдельный маркер дублировал бы
  состояние. Детекция: declared-ноды + нет dsn (§5.1). У инициализированных
  внешних кластеров dsn есть всегда → ложных срабатываний нет.
- **Д3. Имя шарда генерирует панель (`shard<max+1>`), без свободного ввода.
  ** Обоснование: канон панельных кластеров `shard<k>` (02 §9.1); паттерн
  без дефиса уже нужен контракту (scope, имена нод, разбор сирот D1);
  свободные имена — лишняя валидация и операционный риск (коллизия scope)
  без потребности. Клэйм-txn на `replicas`-ключе гарантирует уникальность
  при гонках (конкурентные POST → 409 второму).
- **Д4. Блокировка remove шарда с бакетами — ДВУХУРОВНЕВАЯ: быстрая
  серверная (409 с числом бакетов, маркер НЕ пишется) + авторитетный guard
  PgWorker G3 (маркер жив, last_error, демонтаж сам продолжится после
  переездов).** Обоснование: панель считает routing из своего снапшота —
  мгновенная понятная ошибка без «полузаявки»; гонка «flip переезда между
  проверкой панели и тиком PgWorker» закрывается guard'ом (маркер —
  состояние, не заявка: ждать можно бесконечно, ничего не теряется).
- **Д5. Remove-shard подожрёт и «недоднятый» шард (declared, без dsn) —
  это единственный способ отменить зависший add.** Обоснование: guard'ы
  тривиально проходят (бакетов нет), S2 — RemoveNode 404=ок, S3 чистит
  декларацию; специальной кнопки «отменить add» не делаем (Д8).
- **Д6. Эвакуация (аварийная) НЕ отключается для TO_REMOVE-шарда с
  бакетами.** Обоснование: если помеченный шард умер с бакетами, демонтаж
  заблокирован G3 навсегда; эвакуация — существующий аварийный контур,
  который освобождает бакеты и разблокирует демонтаж. Это не
  «автоперебалансировка» из границы §2.1 (та — про плановые переезды
  живых шардов): аварийный контур существовал до t06 и его семантика не
  меняется. При этом эвакуация пустого/незарегистрированного шарда
  запрещена (§5.4) — бессмысленный карантин блокировал бы G6.
- **Д7. Guard G6 (нет QUARANTINED-нод) вместо чтения журнала эвакуаций.**
  Обоснование: состояние нод — уже в снапшоте; вернувшийся карантин
  (QUARANTINED, данные целы, ждут t05-разбора) блокируется; никогда не
  вернувшийся (UNREACHABLE, журнал DONE) — разрешён: данные на мёртвых
  дисках, оператор демонтирует осознанно. Журнал эвакуации удаляется в S3.
- **Д8. Отмена add/remove из панели отсутствует (one-way маркеры).**
  Обоснование: симметрия с TO_REMOVE кластера («обратного перехода нет»,
  02 §9.4); отмена посреди S2 — источник «полудемонтированных» состояний
  (nodes REMOVING без владельца). Отмена зависшего add — через remove (Д5);
  отмена remove до старта S2 теоретически возможна del'ом ключа через
  etcdctl (runbook-уровень, в UI не даём — гонка с тиком PgWorker не
  контролируема). Если практика потребует кнопку «отменить демонтаж» —
  отдельная задача.
- **Д9. Add-shard для кластера NOT_INITIALIZED запрещён (409).**
  Обоснование: структура такого кластера ещё исполняется
  ProvisioningProcess (P0–P5) — докладка шарда посреди provisioning'а
  гоняет два процесса по одним ключам; правильный путь — дождаться Active.
  Отдельный guard A1 на стороне PgWorker дублирует панель (гонка «панель
  пишет декларацию, а кластер ещё NOT_INITIALIZED» → ProvisioningProcess
  поднимет шард как обычный: для него это просто ещё один declared-шард —
  поведение корректное и ожидаемое).
- **Д10. portalloc при демонтаже чистится точечно (фильтрация JSON), не
  удалением ключа.** Обоснование: ключ содержит записи всех шардов кластера;
  read-modify-write безопасен под клэймом (единственный писатель);
  сохранённые порты остальных шардов переживают демонтаж (rebuild-инвариант
  arch/14 §2.4).
- **Д11. Панель НЕ читает `/pgworker/work/<C>` для отображения причин
  блокировки.** Обоснование: счётчик «бакетов на шарде» панель считает из
  routing сама; точные фазы/ошибки — etcdctl/логи (операторский уровень).
  Расширение снапшота панели префиксом оркестратора — контрактный сдвиг
  (arch/14 §3.3 «панель этот префикс не читает»), не нужный для t06-UX.
- **Д12. Мини-фикс DeprovisioningProcess (чистка `/pgworker/evacuations/
  <C>/`) включён в задачу.** Обоснование: пробел найден при проектировании
  S3 (журналы переживают удаление кластера); правка одной строкой в списке
  D2 + тест; отдельная задача на одну del-операцию — overhead.
- **Д13. Порядок scale-прохода: remove → add.** Обоснование: демонтаж
  освобождает слоты placement/порты до подъёма новых нод (существенно при
  тесных хостах); оба прохода идемпотентны, порядок не влияет на корректность.
