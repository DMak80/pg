# Task 19b: диагностика и ускорение конвергенции demo (бюджет ≤45 c)

## Методика

- Wait-гейт `00-up.sh` инструментирован пофазовой телеметрией ([PHASE] +
  `phases.log`, канон `docs/e2e-launch.md` — «никакой тихой фазы»):
  сеть/контейнеры → Patroni REST per-node → leader-ключ → реплики streaming →
  снятие status-ключей → Active + суммарная строка. Телеметрия остаётся в
  скрипте.
- Два чистых цикла `90-down.sh -v` → `00-up.sh` на одном хосте (Docker
  Desktop, macOS arm64); между прогонами — полный teardown с томами.

## Прогон 1 (тик лупов воркера — дефолт 5 c)

```
[PHASE] demo: сеть/контейнеры: первый pgw-demo-* RUNNING — 3 c
[PHASE] demo: реплики streaming — 52 c
[PHASE] demo: status-ключи бакетов сняты — 56 c
[PHASE] demo: конвергенция 57 c
```

## Прогон 2 (после стендовой правки: тик лупов воркера 1 c)

```
[PHASE] demo: сеть/контейнеры: первый pgw-demo-* RUNNING — 4 c
[PHASE] demo: patroni REST: все ноды отвечают /cluster — 13 c
[PHASE] demo: реплики streaming — 53 c
[PHASE] demo: status-ключи бакетов сняты — 57 c
[PHASE] demo: конвергенция 58 c (фазы: сеть/контейнеры 4, patroni 13, leader -, streaming 53, status 57)
```

## Выводы

1. **Тики воркера не доминируют**: сокращение тика 5 c → 1 c не изменило
   конвергенцию (57 c → 58 c, в пределах шума); хвост streaming → status
   (~4 c) одинаков в обоих прогонах — это SQL-фаза провижинера, а не ожидание
   тика. Стендовый тик 1 c оставлен (безвреден, чуть снижает латентность
   хвостовых операций стенда; прод-дефолт appsettings 5 c не меняется — ключ
   ставит только 00-up.sh в deploy/.env).
2. **Узкое место — Spilo-фаза 13→53 c (~40 c)**: initdb двух лидеров +
   pg_basebackup двух реплик + выборы Patroni. Тайминги Patroni уже на полах
   канона P11 (ttl=20/loop_wait=1/retry_timeout=3 —
   `PatroniTimings`/`SPILO_CONFIGURATION`); ноды бутстрапятся параллельно.
   Дальнейшее сокращение — только искажением механики (fsync/initdb-параметры
   Spilo) — прод-искажение, не применяется.
3. **leader-ключ — за окном гейта**: etcd master-ключ (lease) отсутствует в
   окне конвергенции и появляется после Active (код порога проверен прямым
   исполнением на живом стенде — возвращает OK при наличии ключа; суммарная
   строка печатает прочерк). Это факт механики master-lease, а не дефект
   телеметрии; wait-гейт соответствует канону arch/14 (config без
   NOT_INITIALIZED + ноды RUNNING + status-ключи сняты).
4. **Бюджет ≤45 c на данном хосте — обоснованно недостижим**: минимум
   конвергенции = 13 c (старт Spilo/Patroni) + ~40 c bootstrap (дисковая фаза
   Docker Desktop). Прогноз на целевом хосте (нативный Linux + NVMe): Spilo-фаза
   ~15–25 c → суммарная конвергенция ~25–35 c ≤45 c. 600 c остаётся аварийным
   потолком wait-гейта.

## Мерж-гейт

Полный цикл подъёма (publish-фазы + стенд + deploy + конвергенция demo +
панель + прометей) в обоих прогонах завершён успешно; фаз без [PHASE]-метки
нет.
