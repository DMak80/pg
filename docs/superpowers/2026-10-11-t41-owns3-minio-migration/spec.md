# Spec t41-owns3-minio-migration: перевод подсистемы бэкапов с MinIO на ownS3; канонический demo-контур

Дата: 2026-10-11 (v5 — развилки D1/D2 закрыты решением пользователя по
границе контура: контур = весь стенд, одна стендовая сеть; owns3 не
обязательно единственный — количество инстансов решается вне этой задачи).
Постановка — `arch/roadmap/owns3.md` (тег `t41-owns3-minio-migration`):
перевод подсистемы бэкапов с MinIO на ownS3 — выбор пути (перезаливка
цепочек бэкапов / `mc mirror` / новый цикл ретенции), гонка двух хранилищ
на переход, критерий готовности к отказу от MinIO; состав фиксируется этой
спекой. Расширение scope (решения пользователя): перестройка стендового
demo-кластера в каноническую модель движка и стендовые сетевые правки кода
PgWorker — в рамках t41.

**Базовый сетевой принцип (окончательный)**: в каждой сети — только свои
контейнеры; ВЕСЬ СТЕНД — ОДНА своя сеть, отличная от других стендов и
тестов; каждый e2e-тест-класс — в своей сети независимо от других; никаких
контейнеров в двух сетях; никаких хост-переходов ВНУТРИ контура (хост-порт
ownS3 — только наружу: чеки с хоста, mc-миграция, оператор).

Каноны: `arch/19-backups.md` (подсистема бэкапов), `arch/22-owns3.md` +
`arch/owns3/01…05` (ownS3), `arch/14-pgworker.md` (движок: провижининг,
сети, portalloc, seed/API), `arch/02`/`adminpanel/02` §9.1–9.3 (декларативное
создание кластера), `arch/adminpanel/01…04` (панель, вкл. §2.5 S3-грани и
канон dev-станда). Контекст реализованных слоёв ownS3 (t35–t39):
`docs/superpowers/2026-10-10-t39-owns3-e2e/spec.md`.

## 1. Цель

Подсистема бэкапов (воркер PgWorker, джобы полных бэкапов `pgworker-backup`,
WAL-агенты `pgworker-wal`, verify/restore/drill, экспорт etcd-снапшотов) и
панельная грань «Хранилище бэкапов» работают против **ownS3** вместо MinIO.
Составляющие:

1. **Перевод стендового контура на ownS3**: `deploy/.env.example`
   (комплект `PGW_BACKUP_S3_*` → адрес ownS3 по имени в стендовой сети +
   статические ключи), bucket-сид `00-up.sh`, чек `45-backups-storage.sh`.
   Панель и чек 45 видят реальные бэкапы demo — тот же инстанс ownS3.
2. **Путь миграции данных** — выбран и зафиксирован: `mc mirror` всего bucket
   `pgworker-backups` (включая служебный префикс `etcd/`) с гейтом сверки
   листингов (§4.1). Процедура — `docs/owns3-migration.md`.
3. **Гонка двух хранилищ на переход** = параллельная жизнь сервисов
   переходного периода: `as-minio` (full-профиль стенда) остаётся поднятым
   read-only-архивом, запись после переключения идёт только в ownS3 (§4.2).
4. **Критерий готовности к отказу от MinIO** зафиксирован (§4.4); физический
   снос `as-minio` — по достижении критерия, отдельным изменением (§2).
5. **Панель**: health-проба S3-грани панели получает фолбэк на ownS3-канон
   `/healthz` (`/minio/health/live` — MinIO-специфика; §4.5).
6. **Канонический demo-контур в ОДНОЙ стендовой сети**: стендовый
   demo-кластер — кластер, создаваемый движком (Spilo-ноды с настоящим
   Patroni, декларация через `POST /api/clusters`); все контейнеры стенда —
   воркеры, панель, etcd-контур, ноды demo, wal-агенты, джобы бэкапов,
   ownS3 — живут в одной стендовой сети; адресация S3 всех потребителей —
   по имени `owns3` в этой сети, единый endpoint. Сеть контура задаётся
   поставкой (стенд/E2E — внешняя сеть контура; прод — per-cluster сети по
   канону arch/14 без изменений) — сетевые правки кода PgWorker входят в
   scope (§4.7, §5.2). Число инстансов ownS3 — вопрос эксплуатации
   установки (может быть несколько или один), НЕ канон этой задачи; стендовая
   конфигурация — один инстанс `owns3` (`:9010` наружу).
7. **Образ wal-агентов** `pgworker-wal:dev` собирается подъёмом стенда
   (§4.7). Судьба усыновлённой модели demo — демонтаж (§4.7).

## 2. Не-цели (границы)

- **Физический снос `as-minio` из стендового compose и удаление тома
  `as-minio-data`** — по достижении критерия §4.4 отдельным изменением; в
  этой задаче сервис остаётся в full-профиле (гонка §4.2).
- **Трек `arch/roadmap/s3.md` (t31–t34)** — не трогается.
- **E2E-сценарии PgWorker** (`src/tests/PgWorker.IntegrationTests/E2e/*`,
  16 сценариев на testcontainers-MinIO) — остаются на MinIO и в прод-режиме
  сетей (сеть контура в тестах не задаётся → поведение движка/джобов —
  прод-канон, тесты остаются валидны без переработки). Перевод тестовых
  контуров на сеть контура — отдельная задача, если понадобится.
- **Количество инстансов ownS3 на установке** — не фиксируется этой задачей
  (не «единственный» как принцип, второй не заводится); стендовая
  конфигурация — один инстанс.
- **Второй набор S3-секретов не заводится** (arch/19 §7 — один env-комплект
  `PGW_BACKUP_S3_*` у воркера).
- **TLS ownS3** — t42; **erasure coding/репликация ownS3** — t40+.
- **Прод-режим сетей движка** — канон arch/14 без изменений (per-cluster
  `pgw-net-<C>`, default bridge + extra_hosts у ephemeral-джобов): правки
  кода добавляют РЕЖИМ «сеть контура задаётся поставкой», не меняя
  прод-поведение по умолчанию.
- **Глубокая переработка панельных сценариев** — вне scope: стендовые чеки
  адаптируются минимально (§5.3).

## 3. Контекст: как устроено сейчас

### 3.1. S3-контур (предмет перевода)

- **Хранилище стенда** — `as-minio` (сервис `minio` full-профиля
  `dev-stand/adminpanel/docker-compose.yml`, порты 9000/9001, креды
  `minioadmin/minioadmin`, том `as-minio-data`); bucket `pgworker-backups`
  создаёт `00-up.sh` (mc mb, идемпотентно).
- **Воркер** — `PGW_BACKUP_S3_*` в `deploy/.env` (endpoint
  `http://host.docker.internal:9000`, bucket `pgworker-backups`, креды
  minioadmin; `PGW_BACKUPS_ENABLED=true`; advertised — адрес из контейнеров
  джобов/агентов). Тот же комплект обслуживает экспорт etcd-снапшотов
  (префикс `etcd/`).
- **Панель** — env `AdminPanel__Backups__S3__*` стендового компоуза:
  `http://minio:9000` (compose-DNS), minioadmin; `PathStyle=true` — дефолт.
  Клиент `src/AdminPanel.Probes/S3/MinioS3Client.cs` (read-only;
  health: ApiOk=ListBuckets, LiveOk=`/minio/health/live`==200,
  ClusterOk=`/minio/health/cluster`==200/null).
- **owns3** — сервис `owns3` в `deploy/docker-compose.yml` (publish
  `${OWNS3_HOST_PORT:-9010}:9000`, том `owns3-data`, root-пара из
  `deploy/.env`); smoke-чек `46-owns3.sh`. Приёмочная грань клиентами
  (AWS SDK .NET, `mc`) пройдена (t39).
- **Истина подсистемы — list S3** (arch/19 §3/§4): etcd-статусы бэкапов
  endpoint-агностичны; это делает перенос данных «прозрачным».

### 3.2. Стендовый demo-кластер и сети подсистемных контейнеров

- **Модель demo** — усыновлённый кластер: PG-ноды `as-s1a/s1b/s2a/s2b`
  (postgres:18, стендовая сеть) + patroni-эмуляторы `hc1a/hc1b/hc2a/hc2b`
  (образ `dev-stand/adminpanel/sidecar/`). Декларация — сид
  `POST /api/seed/demo` (`PostgresDemoSeedPlan`): кластер `demo`, шарды
  `s1`/`s2` с `dsn host=s1a,s1b`, статичные master-ключи, routing, сид-аномалии.
  Панель: SQL-пробы `s1a:5432`, Patroni-пробы через HostMap
  (`adminpanel.appsettings.json`).
- **Подсистема бэкапов на усыновлённых нодах** расходится с каноном arch/19
  по трём механикам:
  1. wal-агент: каноническая нода даёт источнику alias `:5432` в сети
     кластера (`ResolveNodeRef`), усыновлённая — `host:pg-port` из
     portalloc (`local:15xxx`); спека агента не содержит extra_hosts —
     резолв `local` из сети контура невозможен;
  2. тик полных гвардится Spilo-специфичной правкой pg_hba (arch/19 §7) —
     на чистом postgres:18 гвард падает, шарды скипаются;
  3. образ `pgworker-wal:dev` не собирается подъёмом стенда — ensure
     агентов падает на отсутствии образа.
- **Каноническая альтернатива** (arch/14): движок провижинит кластер по
  декларации — Spilo-ноды `pgw-<C>-<X>-<n>` (образ
  `ghcr.io/zalando/spilo-18:4.1-p2` из локального registry) с настоящим
  Patroni, портами portalloc (pg `15xxx`, patroni `18xxx`, advertised
  `host.docker.internal`), инициализацией БД/ролей/схем, переводом в Active.
  Декларативное создание — `POST /api/clusters` (adminpanel/02 §9.1).
  Модель используется E2E-сценариями бэкапов (`E2eBackupJobsScenarios`).
- **Сети (факты кода)**: ноды кластера и wal-агенты — per-cluster
  `pgw-net-<C>` (драйвер: `NetworkName(cluster)`, создаётся идемпотентно,
  409 = успех); ephemeral-джобы (полный/verify/drill/restore) —
  `Network: null` (default bridge) с фиксированными кодом
  `ExtraHosts: ["host.docker.internal:host-gateway", "local:host-gateway"]`;
  воркер — контейнер deploy-проекта (default + `pgw-metrics`); панель и
  etcd-контур — стендовая сеть компоуза. S3-адреса из env: джоб полного —
  `opts.S3Endpoint`; wal-агент, verify, drill, restore — единый
  `opts.AgentS3Endpoint` = `AdvertisedEndpoint ?? Endpoint`.

## 4. Ключевые решения

### 4.1. Путь миграции данных — `mc mirror` (выбор из трёх вариантов roadmap)

Выбран **`mc mirror` всего bucket** `pgworker-backups` MinIO→ownS3 (тремя
проходами, §4.3). Отклонённые альтернативы:

- **«Новый цикл ретенции»** (переключить env, ничего не переносить):
  окно без валидных DR-точек до первого COMPLETED+verify-OK полного каждого
  шарда; потеря GFS-истории и истории etcd-снапшотов; при DR в этом окне —
  только ручная выгрузка из MinIO. Приемлемо для пустого стенда, но не
  максимально надёжно.
- **«Перезаливка цепочек бэкапов»** (форсированное переснятие полных всех
  шардов руками): та же потеря истории + ручное вмешательство в работу
  планировщика; пересъём — I/O всех баз без нужды.

Обоснование `mc mirror` (критерий — максимальная надёжность, AGENTS.base §9):

1. **DR-покрытие не прерывается**: после переключения ownS3 содержит все
   цепочки (полные, WAL, `.history`, etcd-снапшоты); restore/PITR доступны
   немедленно, GFS-история сохраняется.
2. **Бесшовность подсистемы**: list S3 — истина; совпавший листинг означает,
   что etcd-статусы корректны, планировщик не форсирует пересъёмов, агенты
   продолжают от хвоста ownS3, ретенция/супервизор/verify работают по
   перенесённым данным.
3. **Целостность переносимого**: (a) `mc mirror` копирует с контролем
   HTTP-результата каждого PUT; (b) гейт полноты переноса — сверка листингов
   (§4.3 п.6); (c) окончательная побайтовая уверенность — штатная
   verify-перепроверка (`verify.interval_sec`) и дрилл (§4.4). ETag/mtime
   после mirror меняются — подсистема от них не зависит.
4. **Инструмент в контуре**: `mc` работает с ownS3 (t39), mc-образ
   зеркалирован в локальном registry, новых внешних образов нет.

Граница: mirror переносит только bucket `pgworker-backups`; пользовательские
бакеты MinIO — ручной перевод вне scope.

### 4.2. Гонка двух хранилищ на переход

**Гонка = параллельная жизнь сервисов переходного периода**, без двойной
записи:

- До переключения: воркер пишет в `as-minio`; ownS3 живёт в стендовой сети
  параллельно (смок-чек 46).
- Переключение (§4.3, шаг 4) — единственная точка перехода: env-флип
  `deploy/.env` + рестарт инстансов PgWorker и панели.
- После переключения: запись только в ownS3; `as-minio` остаётся поднятым
  (full-профиль) как **read-only-архив** старых цепочек — источник ручного
  DR (`mc` с хоста через `:9000`), новых объектов не получает; его bucket
  более не чистится ретенцией воркера.
- Двойная запись не вводится (arch/19 §7).

**Откат** (деградация ownS3 в переходный период): env-флип назад на
`:9000` + рестарт. Дыра MinIO за окно работы с ownS3 самозаживляется:
WAL-агенты стартуют от хвоста MinIO и досылают дыру из удерживаемого слотом
WAL (в пределах `max_slot_wal_keep_size` — аварийный путь); полные
переснимет планировщик. Обратный mirror не нужен.

### 4.3. Процедура переключения (порядок; полный текст — `docs/owns3-migration.md`)

1. **Подготовка** (сделана задачей в репо): статические ключи ownS3 в
   `deploy/.env` (§4.6); bucket `pgworker-backups` в ownS3 создаёт
   обновлённый `00-up.sh` (mc mb root-кредами, идемпотентно).
2. **Mirror, проход 1 (базовый)**: `mc mirror` MinIO→ownS3 по живой
   подсистеме: ephemeral mc-контейнер с
   `--add-host host.docker.internal:host-gateway`;
   `mc alias set <src> http://host.docker.internal:9000 …; mc alias set
   <dst> http://host.docker.internal:9010 …; mc mirror --overwrite
   <src>/pgworker-backups <dst>/pgworker-backups` (миграция — снаружи
   контура, через хост-публикации; `--overwrite` идемпотентен к повторам).
3. **Mirror, проход 2 (дельта до переключения)**: повтор mirror до дельты,
   близкой к нулю.
4. **Переключение**: правка `deploy/.env` (`PGW_BACKUP_S3_ENDPOINT=
   http://owns3:9000` — имя в стендовой сети, единый endpoint §4.7; креды =
   writer-ключ) и стендового env панели (`http://owns3:9000`) → рестарт:
   `00-up.sh` + пересоздание панели.
5. **Mirror, проход 3 (хвостовая дельта после переключения)**: финальный
   повтор mirror — доносит объекты, записанные в MinIO в окне между
   проходом 2 и рестартом воркера (безопасен: PUT отсутствующих
   идемпотентен).
6. **Гейт полноты переноса** (обязателен до признания переключения
   завершённым): листинги `mc ls --recursive` обоих bucket (сравнение на
   хосте) — критерий: **каждый объект MinIO присутствует в ownS3 с тем же
   ключом и размером** (ownS3 — надмножество: новые объекты после
   переключения в гейте не учитываются). Промежуточные сверки 1→2 дают
   естественный дрейф живого источника — дельта обязана сходить к нулю.

Окно между проходом 2 и рестартом воркера **не требует остановки подсистемы**:
недостающие WAL-сегменты агент досылает из удерживаемого слотом WAL
(инвариант подтверждения-по-доставке, arch/19 §3); полный в полёте уходит в
FAILED (takeover) и переснимается штатно новым id.

### 4.4. Критерий готовности к отказу от MinIO

Отказ от MinIO (снос `as-minio` из full-профиля, удаление тома
`as-minio-data`, чистка env/чеков от переходных ссылок) допустим, когда
одновременно выполнено (чеклист в `docs/owns3-migration.md`):

1. **Цепочки всех Active-шардов валидны в ownS3**: у каждого шарда ≥1
   COMPLETED-полный с `verify.state=OK` и непрерывной WAL-цепочкой от его
   `wal_start_segment` (wal-ключи ACTIVE; нет BROKEN).
2. **DR-путь из ownS3 доказан**: ≥1 дрилл восстановимости завершился
   SUCCEEDED на бэкапе из ownS3 после переключения.
3. **Полный цикл без S3-деградаций**: прошло ≥ `full_max_age_sec`
   (дефолт — сутки) без алертов `backup-s3-unreachable`,
   `backup-verify-failed`, `backup-full-stale` и без CRIT/WARN ключа
   `/pgworker/backups/storage`.
4. **Источник исчерпан**: хвостовая дельта mirror пуста.

До выполнения критерия `as-minio` — источник ручного DR. Снос — отдельным
изменением.

### 4.5. Панель: health-грань S3

Панель — **read-only читатель** bucket (канон adminpanel/02 §2.5).
ListBuckets/ListObjectsV2 с ownS3 работают без правок (AWS SDK, path-style
— дефолт appsettings). Правится только health:

- **LiveOk**: проба `GET {endpoint}/minio/health/live` (MinIO-канон);
  ответ **404 или 403** → фолбэк `GET {endpoint}/healthz` (канон ownS3
  05 §5, без подписи). 200 → live, 503 → down, нет ответа/иное → down.
  Триггер 404/403 = «эндпоинт жив, health-путь не поддерживается — не
  MinIO-контур»: MinIO отвечает 404 на несуществующий путь, ownS3 на
  анонимный запрос вне `/healthz`/`/metrics` — **403 `AccessDenied`**
  (arch/owns3/03, таблица ошибок; arch/owns3/05 §5).
- **ClusterOk/Drives**: `GET /minio/health/cluster`; 404/403/нет ответа →
  null (фронт рисует «n/a», правок UI нет). Drives-парсинг сохраняется для
  MinIO-контура.
- Фолбэк по статусу (404/403), не по таймауту: мёртвый endpoint вторую
  пробу не крутит.

Проверка: `MinioS3Client.GetHealthAsync` + `ProbeHealthAsync`
(`src/AdminPanel.Probes/S3/MinioS3Client.cs`).

### 4.6. Ключи доступа ownS3 (канон owns3/05 §2–3)

Статические ключи — один комплект значений в env `deploy/.env`
(`OWNS3_ACCESS_KEYS__*`):

| Ключ | Policy | Потребитель |
|---|---|---|
| `pgw-backups-writer` | `read-write` | подсистема бэкапов: `PGW_BACKUP_S3_ACCESS_KEY/SECRET_KEY`; env пробрасывается джобам/WAL-агентам (arch/19 §2/§3/§7) |
| `panel-reader` | `read-only` | панель: `AdminPanel__Backups__S3__AccessKey/SecretKey` |

- Права по матрице канона 05 §3 (воркеру — объекты+multipart+delete =
  `read-write`; панели — листинги = `read-only`).
- Bucket создаёт `00-up.sh` root-кредами (CreateBucket — только `admin`);
  воркер bucket не создаёт.
- Один env-комплект у воркера (arch/19 §7 не нарушен).

### 4.7. Стенд = один контур = одна стендовая сеть; сетевые правки кода

**Принцип (решение пользователя)**: весь стенд — ОДНА своя сеть (в ней
живут ВСЕ контейнеры стенда: `as-etcd-1/2/3`, панель, воркеры deploy-проекта,
ноды demo, wal-агенты, джобы бэкапов, ownS3, прометей/мониторинг);
per-cluster сеть `pgw-net-<C>` на стенде контур НЕ разлучает — не
создаётся. Контейнеров в двух сетях нет; хост-переходов внутри контура
нет — адресация по именам стендовой сети; хост-порт ownS3 `:9010` — только
наружу (чеки с хоста, mc-миграция, оператор). Количество инстансов ownS3 —
вопрос эксплуатации, не этой задачи; стенд — один инстанс `owns3`.

- **Сеть контура задаётся поставкой (режим движка)**: новая настройка
  PgWorker — «внешняя сеть контура» (стенд/E2E задают её именем; пусто =
  прод-режим по канону arch/14: per-cluster `pgw-net-<C>` для нод и
  wal-агентов, ephemeral-джобы в default bridge с extra_hosts). В режиме
  сети контура: ноды кластера, wal-агенты И ephemeral-джобы (полный/
  verify/drill/restore) создаются в этой одной сети; `pgw-net-<C>` не
  создаётся; фиксированные `ExtraHosts`-хост-переходы из спек джобов
  уходят (внутри контура адресация по именам сети). Имя настройки —
  консервативно `PgWorker:Docker:ContourNetwork` (env `PGW_CONTOUR_NETWORK`;
  финальное имя — план, семантика фиксирована здесь).
- **Адресация S3 — единый endpoint по имени сети**: стендовый
  `PGW_BACKUP_S3_ENDPOINT` = `PGW_BACKUP_S3_ADVERTISED_ENDPOINT` =
  `http://owns3:9000` (рекомендуется advertised не задавать — равен
  endpoint). Все потребители (воркер — в стендовой сети; wal-агент;
  ephemeral-джобы — теперь в той же сети; панель) резолвят `owns3`
  compose-DNS. Сервис `owns3` deploy-compose на стенде подключается к
  стендовой сети (external, alias `owns3`); хост-публикация `:9010`
  сохраняется для внешних потребителей. Панель и чек 45 видят реальные
  бэкапы demo — тот же инстанс, без оговорок канона.
- **Адрес источника джоба полного** — имя ноды в сети контура `:5432`
  (симметрично `ResolveNodeRef` wal-агента для канонических нод); в
  прод-режиме — `host:pg-port` из portalloc, как сейчас.
- **Кластер `demo` — декларация через API**: `00-up.sh` после healthz
  воркера зовёт `POST /api/clusters` (mTLS healthcheck-парой; тело по
  контракту adminpanel/02 §9.1–9.3: имя `demo`, 16 бакетов, 2 шарда,
  2 реплики, `request_cpu=2`/`request_mem=2Gi` — прецедент E2E).
  Идемпотентность: живой `/clusters/demo/config` → 409; пересборка demo —
  полный цикл стенда (`90-down.sh -v` → `00-up.sh`). Движок провижинит
  Spilo-ноды с Patroni в стендовой сети, портами portalloc (host-публикации
  портов — наружу, для оператора/дебага), инициализацией БД/ролей/схем
  `bucket_%`, переводом в Active. Wait-гейт `00-up.sh`: Active, ноды
  RUNNING, status-ключи сняты — бюджет + `[PHASE]`-метки.
- **Мониторинг**: стенд задаёт `PGW_SCRAPE_NETWORK` = стендовая сеть
  (существующая параметризация t15): ноды Ensure-attach движком к ней —
  совпадает с контурной (no-op поверх); Prometheus скрейпит по именам
  стендовой сети (он в ней же); отдельная сеть `pgw-metrics` на стенде не
  создаётся. Прод — pgw-metrics-механика без изменений.
- **Образ wal-агентов**: `00-up.sh` publish'ит `PgWorker.WalReceiver` на
  хосте (`[PHASE]`-метки) и собирает `pgworker-wal:dev`; Dockerfile —
  publish-COPY (`ARG WAL_PUBLISH_DIR`, по образцу `docker/OwnS3.Dockerfile`;
  канон E2E-образов); build-сервис deploy-compose — тот же ARG.
- **Судьба усыновлённой модели**: сервисы `s1a/s1b/s2a/s2b` и
  `hc1a/hc1b/hc2a/hc2b` удаляются из стендового компоуза вместе со сборкой
  sidecar-образа и HostMap; из `00-up.sh` уходят блоки patch_hba/set_sync/
  инвентаря схем и wait-циклы as-нод (ноды demo поднимает движок — в
  стендовой сети). Панель пробирует канонические ноды по advertised-адресам
  portalloc напрямую.
- **Сид `POST /api/seed/demo`** (pg-ветка) стендом не наливается;
  `05-seed.sh` сохраняет kafka/valkey-ветки; эндпоинт остаётся в коде
  (no-op на живом кластере). Демо-аномалии UI чек 20-alerts насыпает сам.
- **E2E-режим**: механизм тот же — тест-класс задаёт свою сеть контура
  (изолированную от других); в существующих 16 сценариях сеть контура не
  задаётся → прод-режим → поведение и зелёность тестов сохраняются. Перевод
  E2E-контуров на сеть контура — вне t41.

   E2E-сценарии PgWorker (прод-режим сетей) зелёные на свежем Release.
9. **Процедура миграции** выполнена (стенд или тестовый прогон): гейт
   полноты переноса пройден; цепочки продолжились (wal-ключи ACTIVE, BROKEN
   нет, немотивированных пересъёмов нет).
10. **Каноны arch-first обновлены** (§5.1).
11. **Откат описан** в docs/owns3-migration.md.
