# t35-owns3-replication — межсерверная mesh-репликация ownS3 (spec)

Входные каноны: требования R1–R6 —
[`docs/owns3-replication-requirements.md`](../../../docs/owns3-replication-requirements.md);
изыскания и антиуроки платформ —
[`docs/s3-replication.md`](../../../docs/s3-replication.md);
канон ownS3 — [`arch/owns3/`](../../../arch/owns3/) (главы 01–06),
[`arch/22-owns3.md`](../../../arch/22-owns3.md); roadmap-запись задачи —
[`arch/roadmap/owns3.md`](../../../arch/roadmap/owns3.md).

Решения по ключевым развилкам согласованы с пользователем (брейнсторм
2026-10-11; доработки user-review): транспорт — отдельная
replication-грань; бакеты — реплицируются; состав mesh — админ-грань +
персист на томе; журнал — единый сегментный + per-target курсоры;
**модель доставки — уведомления + pull: источник передаёт соседям из
outbox ТОЛЬКО уведомления о новых сущностях; данные переедут позже сами
— их приёмник сам запросит и сохранит у себя**. **Курсор per-target в
outbox двигается подтверждением ПРИЁМА уведомления (ACK приёма), НЕ
фактом применения данных** — ответственность источника заканчивается
приёмом уведомления соседом, ответственность за доставку данных — на
приёмнике (fetch по своему темпу + reconcile как гарантийный контур).

---

## 1. Цель и границы

### 1.1. Цель

Межсерверная mesh-репликация ownS3: пул 2–5 серверов на разных
docker-хостах (гео), full-mesh active-active. Клиент (подсистема
бэкапов, `mc`) пишет в любой доступный сервер; синхронизация между
серверами — внутренняя механика ownS3, для клиентов каждый сервер —
полный S3 (в части закоммиченных объектов). Реализация — arch-first:
каноническая глава `arch/owns3/07-replication.md`, затем код.

Главная гарантия (R1): подтверждение PUT — после локальной фиксации
(существующий атомарный xl-коммит), латентность записи НЕ зависит от
числа и состояния удалённых целей: серия 10 PUT суммарно ≤1 с при любых
отказах целей, включая полный изолят.

### 1.2. Границы задачи (внутри)

- События репликации: PUT объектов (простой PUT, CompleteMultipart,
  CopyObject — все клиентские коммиты объектов), DELETE объектов
  (DeleteObject/DeleteObjects), CreateBucket, DeleteBucket. «Папок» как
  отдельной сущности нет — объект с ключом-префиксом покрывает
  «файл/папку»; бакет — отдельное событие.
- Доставка: источник рассылает из outbox уведомления (лёгкие сообщения
  с метаданными, без данных) и двигает per-target курсор
  подтверждением их ПРИЁМА; приёмник сам фетчит данные с источников,
  когда ему удобно и при наличии свободного места (backpressure по
  диску), идемпотентно применяет с LWW-разрешением конкурирующих записей
  и tombstone-удалениями; reconcile/backfill — гарантийный контур
  сходимости; метрики и админ-сверка листингов; изменение состава mesh
  без даунтайма S3-грани.

### 1.3. Вне задачи (соседние треки)

- **Клиентская часть пула** (перебор серверов с per-попыточным
  таймаутом, приоритеты чтения, per-cluster настройки) — `t36-s3-pool-integration`.
- **Управление пулом как объектом системы** (etcd-декларации,
  оркестратор подъёма/вывода нод, панель) — `t31–t34` трека
  [`arch/roadmap/s3.md`](../../../arch/roadmap/s3.md). ownS3 даёт им
  интерфейс (админ-грань), но сама без etcd (ownS3 — не воркер, глава 01).
- Внешний зонд синхронности (периодический) — `t33`; ownS3 предоставляет
  отчёт сверки листингов (раздел 3.8).
- **Multipart-состояния не реплицируются**: Create/UploadPart/Abort и
  списки активных загрузок — локальные транзитные состояния; клиент
  пишет и Complete-ит загрузку на одном сервере; реплицируется только
  результат — закоммиченный объект (событие на коммит-поинт Complete).
  `ListMultipartUploads`/`ListParts` между серверами расходуются — это
  не нарушение инварианта «полный S3» (инвариант — по закоммиченным
  объектам).
- Versioning не появляется (канон: бакеты без versioning); проигравшая
  LWW-версия не хранится (R4).
- Синхронный кворум записи — не делается (антипаттерн по измерениям:
  Garage consistent — висения 70–110 с при потере кворума).

## 2. Принципы

1. **Запись превыше всего (R1/R3)**: путь клиентского запроса НЕ
   содержит ни одного синхронного взаимодействия с целями. Отказ,
   таймаут или изоляция любой/всех целей — событие фоновых процессов
   (notifier/фетчер), никогда — пути записи. Сервер всегда отвечает
   быстро: health ≤1 с, S3-грань не «зависает» (урок MinIO: health жив,
   PUT виснет).
2. **Уведомление лёгкое, данные — pull (модель доставки)**: из outbox
   соседям передаются ТОЛЬКО уведомления (сущность + метаданные);
   тело объекта приёмник забирает сам с replication-грани источника —
   когда ему удобно (свой темп, свои ограничения) и при наличии
   свободного места. Источник никогда не навязывает передачу данных.
3. **Журнал — лог уведомлений, не копий данных**: запись журнала —
   маленькая ссылка (тип, bucket, key, modTime, метаданные); диск
   источника не масштабируется с объёмом данных, диск приёмника не
   занимается непрошеной передачей.
4. **Идемпотентная обработка, LWW-сходимость**: повторные уведомления,
   повторные фетчи, повторное применение — безопасны; приёмник
   разрешает конкуренцию по (modTime, contentSha256) — «время локальной
   фиксации» из требований R4; детерминированный тай-брейк без
   координации.
5. **Анти-петля**: события в журнал ставят ТОЛЬКО клиентские операции
   (App-хендлеры 21 операции); приём реплики (уведомление/фетч)
   события не ставит. Каждый объект покидает каждый сервер не более
   одного раза на соседа (+reconcile) — штормов размножения в mesh нет.
6. **Доставляй актуальное состояние**: уведомление означает «ключ грязный
   для соседей»; фетчер читает актуальное состояние ключа источника на
   момент фетча (объект мог быть перезаписан/удалён позже события) и
   применяет именно его. Инвариант: полностью обработанные приёмником
   уведомления делают его соответствующим источнику по всем
   упомянутым ключам.
7. **Курсор двигается ACK ПРИЁМА уведомления**: per-target курсор
   источника продвигается подтверждением приёма уведомления соседом —
   НЕ фактом применения данных. Ответственность источника заканчивается
   приёмом уведомления; данные переедут позже сами — их приёмник сам
   запросит и сохранит у себя. Отсюда: ответственность за применение и
   его прогресс — на приёмнике; дыры любых причин (crash приёмника,
   принудительный тримминг) закрывает reconcile (принцип 8).
8. **Bounded-журнал + reconcile как гарантийный контур (R6/R4)**: запись
   клиента никогда не отказывает из-за журнала; переполнение бюджета —
   алерт + принудительный тримминг; потерянные/недоставленные данные
   компенсирует reconcile приёмника (полный листинг источников по
   LWW-сравнению) — периодический, по событиям и по требованию.
9. **Самолечение без рестартов (R4)**: срастание сети → notifier
   продолжает с бэкоффом (at-least-once уведомлений), приёмник
   до-фетчивает; любые дыры закрывает reconcile — автоматически, без
   рестартов процессов и без ручного вмешательства (антиурок Garage);
   бюджет полного догона тестового контура ≤5 мин.
10. **Честная наблюдаемость (R5)**: лаг уведомлений (источник,
    watermark приёма) и лаг данных (приёмник, fetch-очередь) — РАЗНЫЕ
    величины и экспортируются обе; абсолютная истина — сверка листингов
    пары серверов. Штатные метрики не маскируют расхождение
    (антипример MinIO `Queued: 0` при живом отставании).
11. **Multi-host-правило системы**: всё состояние репликации (журнал,
    курсоры, targets, tombstones, маркеры reconcile) — на локальном томе
    = кэш/очередь без durability-гарантий против отказа машины целиком;
    источники истины — сами реплицируемые данные на всех серверах mesh и
    (для состава) оркестрация трека s3. Отказ машины X теряет её очередь
    и прогресс — расхождения закрываются reconcile после возврата или
    замены.

## 3. Структура и компоненты

### 3.1. Состав mesh и его изменение (R6)

- **Сосед (target)** — запись `{name, endpoint (scheme://host:port,
  advertised — multi-host/гео), accessKey, secretKey}`. Состав
  симметричен: сосед — это и получатель наших уведомлений, и источник
  для наших фетчей. Идентификация соседа в запросах — по его accessKey
  (креды пер-соседние → имя известно из targets) + `OWNS3_HOST_ID`
  источника в уведомлениях (диагностика конфликтов).
- **Источник истины состава — файл тома**
  `.owns3.sys/replication/targets.json` (персистентный, переживает
  рестарт). **Env — только seed первого старта**: переменные
  `OWNS3_REPLICATION_TARGETS__<i>__{NAME,ENDPOINT,ACCESSKEY,SECRETKEY}`
  (индексная нумерация, конвенция .NET — по образцу
  `OWNS3_ACCESS_KEYS__*`, глава 05 §2) переносятся в targets.json при
  первом старте, пока файла нет. Поведение: есть ≥1 сосед → репликация
  активна; соседей нет (env пуст, файла нет) → репликация неактивна,
  поведение системы не отличается от текущего (стенд single — без
  изменений).
- **Изменение состава без даунтайма — админ-грань** (тем же конвейером
  SigV4, права `admin`/root — глава 05 §7):
  - `PUT /admin/replication/targets` — идемпотентная замена полного
    списка соседей; 202 Accepted; персист targets.json (tmp+rename),
    применён на лету: добавленный сосед → наш notifier начнёт слать ему
    уведомления с текущего конца журнала + наш reconcile-процесс
    заберёт с него его существующие данные (3.7); убранный →
    notifier/фетчер по нему останавливаются (курсор сохраняется на
    случай возврата соседа);
  - `GET /admin/replication/status` — состав соседей и стейт по каждому
    (online/offline, watermark приёма, глубина очереди, лаг
    уведомлений, ход reconcile, счётчики исходов);
  - `POST /admin/replication/reconcile` — запуск внепланового
    reconcile-прохода (202; идущий продолжается, параллельный не
    создаётся — по образцу `POST /admin/heal`, глава 05 §7).
- Оркестратор трека s3 (t32) управляет составом живого пула именно
  через эту грань; добавление узла = его запись в targets всех
  существующих (они уведомляют его о новом и reconcile-ят с него своё) и
  запись всех существующих в его targets (он уведомляет их о своём и
  забирает их данные backfill-ом).

### 3.2. События репликации

Ставятся синхронно в App-хендлерах сразу после успешного коммит-поинта
клиентской операции (до ответа клиенту):

| Событие | Коммит-поинт клиента | Запись |
|---|---|---|
| `object-put` | PUT / CompleteMultipartUpload / CopyObject (замена `xl.meta`) | bucket, key, modTime фиксации (unix-мс из xl-записи), etag, size, contentSha256, originHostId |
| `object-delete` | DeleteObject / каждый ключ DeleteObjects | bucket, key, modTime фиксации удаления (текущее время сервера в момент delete-коммита — удаляемая xl-запись времени не несёт), originHostId |
| `bucket-create` | CreateBucket | bucket, CreationDate |
| `bucket-delete` | DeleteBucket | bucket, modTime |

- Приём реплики события НЕ ставит (анти-петля, принцип 5).
- Append в журнал + fsync — до ответа клиенту (R2: очередь переживает
  рестарт; локальная стоимость — миллисекунды, бюджет R1 соблюдён).
- **Самодостаточность уведомлений**: метаданные события позволяют
  приёмнику принять решение без фетча — `object-delete`, `bucket-create`,
  `bucket-delete` применяются ИЗ уведомления (данных не несут);
  `object-put` — приёмник сравнивает (modTime, contentSha256) уведомления
  со своей записью: локально не старше → событие закрыто без фетча
  (skip); старее/отсутствует → фетч данных. LWW-предфильтр не тянет
  тело зря — не тратится ни канал, ни место приёмника.
- Остаточное окно «коммит есть, события нет» (крах процесса между
  rename-коммитом и append) — микросекунды на одном диске; компенсация —
  сверка листингов (3.8) и reconcile (3.7). Специального 2PC-протокола
  не вводим.

### 3.3. Журнал доставки (outbox) — единый сегментный, per-target курсоры приёма

- **Расположение**: `.owns3.sys/replication/outbox/` — сегментный
  append-only журнал (сегмент закрывается по достижении размера
  сегмента или возраста; имена — монотонная нумерация). Запись события:
  seqNo (монотонный, сквозной через сегменты), тип, bucket, key,
  modTime/CreationDate, etag/size/contentSha256 (для `object-put`),
  originHostId. Формат записи — бинарный фиксированный заголовок +
  строки (детали — план); события маленькие (сотни байт), журнал не
  хранит тела.
- **Курсоры per-target = watermark ПРИНЯТЫХ уведомлений**:
  `.owns3.sys/replication/cursors/<name>.json` — позиция (seqNo, до
  которого сосед ПОДТВЕРДИЛ ПРИЁМ уведомлений — ответом на батч,
  принцип 7) + режим (`tail` | `reconciling`). Данные при этом могут
  быть ещё не применены — их прогресс источник не отслеживает (зона
  ответственности приёмника, 3.5). Продвижение курсора — по ответу
  приёмника; fsync по дебаунсу (~1 с) и при graceful-shutdown: потеря
  хвоста ведёт лишь к повторной рассылке уведомлений — идемпотентно.
- **Тримминг**: сегмент удаляется, когда min(watermark приёма всех
  активных соседей) за его концом. Соседей нет → журнал не ведётся
  (события не ставятся).
- **Bounded-бюджет (R6)**: параметр
  `OWNS3_REPLICATION_OUTBOX_BUDGET_BYTES` (дефолт 2 ГиБ — миллионы
  уведомлений; настраивается per-install). Превышение: запись клиента
  продолжается ВСЕГДА («переполнение — алерт, не отказ записи»);
  поднимается алерт (метрика `ownS3_replication_outbox_budget_exceeded`
  + лог-событие) и выполняется ПРИНУДИТЕЛЬНЫЙ тримминг (старейшие
  сегменты удаляются). Тримминг и ACK-приёма-семантика в совокупности
  означают: отстающий сосед мог НЕ получить часть уведомлений — данные
  при этом не теряются (объекты живут в томах источников своей
  ретенцией), дыры закрывает reconcile приёмника (3.7): уведомления —
  fast-path, reconcile — гарантийный контур сходимости.

### 3.4. Replication-грань (транспорт)

Служебная грань ownS3 вне 21 операции S3, тем же Kestrel-портом и
конвейером SigV4 (подпись заголовочная; TLS — существующая опция
per-install, глава 03 §6). Пути `/replication/*` — новый класс служебных
путей рядом с `/admin/*` (изоляция в S3Middleware, шаг 0). Доступ —
ключи с политикой `replication` (новая строка матрицы главы 05 §3:
доступна ТОЛЬКО replication-грань, все 21 операция — «—»; политика для
peer-кредей инсталляции, клиентам не выдаётся).

Каждый сервер mesh несёт обе роли; операции грани:

| Операция | Запрос | Смысл |
|---|---|---|
| приём уведомлений | `POST /replication/notifications` — батч событий от соседа-источника (seqNo + событие целиком с метаданными) | дедуп по (origin, seqNo); самодостаточные (`object-delete`, бакеты) применяются сразу; `object-put` — LWW-предфильтр (skip или fetch-очередь). Ответ `200 {acceptedToSeqNo}` — watermark ПРИНЯТЫХ уведомлений (последний seqNo батча, поставленный в очередь/применённый) — ЭТО и есть ACK приёма, двигающий курсор источника; `429` — приёмный буфер переполнен (аномальные повторы сверх окна) — источник бэкоффит |
| фетч объекта | `GET /replication/object/{bucket}/{key+}` | актуальное состояние ключа (принцип 6): `200` + тело + заголовки (`x-owns3-repl-modtime`, `x-owns3-repl-sha256`, `x-owns3-repl-etag`, `x-owns3-repl-origin`, `Content-Type`, `x-amz-meta-*`) \| `200` + заголовок `x-owns3-repl-tombstone: <deleteTime>` (нет данных — ключ удалён) \| `404` (ключа нет, tombstone-знание истекло — приёмник состояние не меняет). Тело — поток, без S3-лимита 5 ГБ (грань служебная) |
| листинг для reconcile | `GET /replication/listing?bucket=&marker=&max-keys=` — пагинация по маркеру | полный постраничный листинг ключей с (key, modTime, size, contentSha256) — источник для reconcile/backfill приёмника (3.7) |

- Отдельного эндпоинта ACK применения НЕТ — ACK встроен в ответ на
  батч уведомлений (приёмник НЕ рапортует источник о применении данных;
  прогресс данных — внутреннее дело приёмника, наблюдаемое его
  метриками и сверкой листингов).
- Приёмник сверяет SHA-256 тела на лету с `x-owns3-repl-sha256`:
  расхождение — фетч-ошибка → повтор.

### 3.5. Приёмник: fetch-очередь, LWW, tombstones, место на диске

Компоненты на каждом сервере для каждого СОСЕДА-источника:

- **Fetch-очередь** — in-memory (bounded, по масштабу окна источника):
  `object-put`-ключи, ждущие фетча. Приём уведомления (200
  acceptedToSeqNo) обязывает приёмника ДОВЕСТИ работу до конца
  самостоятельно — источник это событие больше не пришлёт (курсор
  ушёл). Рестарт с чистым graceful-shutdown — очередь дорабатывается
  до остановки (drain, она мала); крах (kill/падение/пауза по месту,
  не позволившая drain) — очередь теряется, и её содержимое источник
  НЕ пере-шлёт — дыры закрывает стартовый reconcile (триггеры 3.7,
  маркер чистого завершения ниже). Durable-очередь приёмнику не
  нужна: либо drain, либо reconcile — обе ветки автоматические.
- **Маркер чистого завершения**: файл
  `.owns3.sys/replication/state.json` — `shutdownClean: true|false`
  (ставится true после drain и fsync-точки остановки; при старте
  сбрасывается в false до полной готовности). Грязный/отсутствующий
  маркер на старте → стартовый reconcile-проход по всем соседям;
  чистый → без стартового reconcile (периодический — по расписанию).
- **Фетчер** — фоновый per-source: берёт из очереди → `GET
  /replication/object/...` источника → применение. Порядок: per-source
  FIFO при parallelism=1 (дефолт); при
  `OWNS3_REPLICATION_PARALLELISM > 1` порядок между ключами не
  гарантируется — корректность от порядка не зависит (LWW
  идемпотентен). Скорость: `OWNS3_REPLICATION_MAX_RATE_BYTES`
  (0 — безлимит). Ошибки фетча → бэкофф: экспоненциальный 1 с →
  `OWNS3_REPLICATION_BACKOFF_MAX_SEC` (дефолт 60), успех — сброс.
  Повторы фетчей — локальная инициатива приёмника (источник о них не
  знает и не должен).
- **Backpressure по месту (решение пользователя)**: перед фетчем
  проверяется свободное место тома; ниже
  `OWNS3_REPLICATION_DISK_FREE_MIN_BYTES` (дефолт 1 ГиБ) — фетчи
  ПАУЗА (флаг в метриках/статусе, лог-событие, алерт-метрика
  `ownS3_replication_fetch_paused{source}`); место появилось (чистки/
  ретенция освободили) — фетчи продолжаются с того же места. Уведомления
  и бакетные/удалительные события продолжают приниматься и применяться
  (метаданные диска почти не требуют) — курсор источника идёт, данные
  не навязываются: накопленные ключи ждут в fetch-очереди приёмника.
- **LWW-применение** (R4): ключ сравнения `(modTime, contentSha256)` —
  больше modTime фиксации; при равенстве modTime тай-брейк —
  лексикографически больший contentSha256 (детерминирован на всех
  репликах без координации). Равные modTime и разные sha256 —
  журналируемый конфликт (R4: «факт слияния журналируется с обеих
  сторон» — обе стороны фиксируют, каждая как приёмник своего события):
  лог-событие + счётчик `ownS3_replication_conflicts_total`.
  - `object-put` (после фетча): входящее строго больше локального
    (и локального tombstone) → применить — запись штатным xl-коммитом С
    сохранением исходных modTime/etag/sha256/user-метаданных (внутренний
    метод применения реплики в Storage, 3.9); иначе → skip/conflict.
  - `object-delete` (tombstone): локальный объект с modTime ≤
    tombstone-времени → удалить + записать tombstone; объекта нет →
    записать tombstone (защита от воскрешения); локальный новее → skip.
  - бакетные события: create — идемпотентный create (CreationDate из
    события); delete — удалить пустой бакет; непустой — отложить
    (повтор по бэкоффу: недоставленные объектные события догонят,
    бакет опустеет).
- **Tombstone-хранилище приёмника**:
  `.owns3.sys/replication/tombstones/` — негативные записи
  (bucket, key, deleteTime); retention
  `OWNS3_REPLICATION_TOMBSTONE_RETENTION_HOURS` (дефолт 168 = 7 суток —
  с запасом больше любых ожидаемых окон раскола/доставки), чистка фоном
  как остальные чистки (глава 04 §6 по духу). После истечения retention
  опоздавший старый PUT применяется свободно — окно воскрешения
  ограничено retention (граница — раздел 6).
- Граница LWW: точность зависит от синхронизации часов серверов
  (требования R4 осознанно принимают: проигравшая версия не хранится;
  для wal-сегментов байты идентичны от всех источников — конфликт
  безопасен; для полных бэкапов — разрешается верифицируемостью
  манифеста клиентом). Эксплуатационное требование — NTP на хостах.

### 3.6. Источник: notifier per-target

Фоновый hosted-сервис, по одному исполнителю на соседа:

1. читает события журнала от watermark ПРИЁМА соседа (батчем), шлёт
   `POST /replication/notifications` на replication-грань соседа;
2. **окно in-flight** `OWNS3_REPLICATION_INFLIGHT_WINDOW` (дефолт 64
   события): шлёт события, чей seqNo < watermark + окно; за окном ждёт
   ACK приёма. Окно — backpressure: приёмник, не принимающий
   уведомления (429/таймаут), останавливает рассылку, журнал копится
   на источнике (bounded-бюджет 3.3). Медленный ПРИЁМ данных приёмником
   окно НЕ блокирует (принимать уведомления легко — семантика курсора:
   данные переедут позже сами);
3. ответ `200 {acceptedToSeqNo}` → watermark соседа = acceptedToSeqNo
   (продвижение с дебаунс-персистом 3.3); `429` или транспортная
   ошибка → бэкофф (экспоненциальный 1 с →
   `OWNS3_REPLICATION_BACKOFF_MAX_SEC`), повтор от watermark —
   at-least-once: неподтверждённые приёмом уведомления пере-сланные
   будут, дедуп (origin, seqNo) на приёмнике гасит повторы
   (пере-сланный батч получает тот же acceptedToSeqNo).

Notifier никогда не в пути клиентского запроса; его зависание/бэкофф
не влияет на S3-грань.

### 3.7. Reconcile / backfill (гарантийный контур сходимости, R4)

Приёмная операция: приёмник сверяет СВОЙ листинг с листингом соседа и
закрывает дыры фетчами. Один механизм для всех сценариев не-сходимости:
потеря fetch-очереди (крах приёмника), принудительный тримминг
журнала, добавление узла, любые неучтённые дыры.

- **триггеры**:
  - добавление соседа (backfill нового узла: он забирает существующие
    данные всех соседей);
  - старт на пустом томе с существующим составом;
  - **грязная остановка процесса** (маркер 3.5: крах/kill без drain
    fetch-очереди) — стартовый reconcile-проход по всем соседям;
  - периодически `OWNS3_REPLICATION_RECONCILE_INTERVAL_SECONDS`
    (дефолт 60 — самозаживление приостановленных проходов и общий
    страховой контур сходимости; нагрузка листинга пренебрежима);
  - админ-команда `POST /admin/replication/reconcile` (по требованию/
    зондом t33);
- **механизм**: постраничный `GET /replication/listing` соседа (маркер
  пагинации) → для каждого ключа LWW-сравнение (modTime, sha256) со
  своей записью → старее/отсутствует → fetch-задача (обычный фетч 3.5,
  идемпотентно); новее → ничего (наш вариант выиграет при взаимной
  доставке — сосед получит наше уведомлением). Прогресс-маркер
  персистится на томе приёмника
  (`.owns3.sys/replication/reconcile/<source>.marker`; рестарт
  продолжает с маркера, отсутствие — с нуля, идемпотентно);
- **свойства**: приём записи не останавливается (фон с теми же
  ограничениями скорости/места); сходимость полная по LWW-сравнимым
  расхождениям; наблюдаемость — позиция/остаток в статусе и метриках.

### 3.8. Наблюдаемость (R5)

**Метрики** (каркас `Shared.Metrics`, словарь главы 05 §5 расширяется).
Роли: отправитель — `{target}` = имя соседа-получателя; приёмник —
`{source}` = имя соседа-источника. **Лаг уведомлений (источник) и лаг
данных (приёмник) — разные величины, экспортируются обе; фактическая
синхронность данных — совокупность приёмных метрик и сверки листингов**
(принцип 10).

| Метрика | Тип | Смысл |
|---|---|---|
| `ownS3_replication_link_online{target}` | gauge | 1 — сосед онлайн по исходам notifier |
| `ownS3_replication_queue_depth{target}` | gauge | событий журнала после watermark ПРИЁМА соседа |
| `ownS3_replication_delivery_lag_seconds{target}` | gauge | возраст старейшего события, не подтверждённого ПРИЁМОМ уведомления (лаг уведомлений) |
| `ownS3_replication_notified_total{target,result}` | counter | исходы рассылки уведомлений (accepted/backoff/retry) |
| `ownS3_replication_fetch_queue_depth{source}` | gauge | ключей в fetch-очереди приёмника |
| `ownS3_replication_fetch_lag_seconds{source}` | gauge | возраст старейшего принятого-но-несохранённого ключа (лаг данных по приёмнику; 0 — очередь пуста) |
| `ownS3_replication_fetch_paused{source}` | gauge | 1 — фетчи на паузе (нет места) |
| `ownS3_replication_fetched_total{source}` | counter | фетчи (байты/счёт) |
| `ownS3_replication_applied_total{source,result}` | counter | исходы применения: applied/skipped/conflict |
| `ownS3_replication_retries_total{target}` | counter | повторы рассылки уведомлений |
| `ownS3_replication_conflicts_total` | counter | зафиксированные LWW-конфликты (журналируются) |
| `ownS3_replication_reconcile_position{source}` | gauge | прогресс reconcile (обработано ключей) |
| `ownS3_replication_outbox_bytes` | gauge | текущий размер журнала |
| `ownS3_replication_outbox_budget_exceeded` | gauge | 1 — бюджет журнала превышен (алерт-состояние) |

Алерт-правила (цель офлайн >N с, лаг уведомлений >порога, лаг данных
>порога, очередь растёт/переполняется, фетч-пауза) — потребители метрик
(мониторинг/панель, вне ownS3).

**Админ-сверка листингов** — `GET /admin/replication/sync-report?bucket=&prefix=&marker=`
(SigV4, admin): JSON-отчёт листинга этого сервера от маркера:
`{bucket, prefix, marker, firstKey, firstModTime, lastKey, lastModTime,
count, totalSize, aggregateHash}` — `aggregateHash` — порядко-независимая
(XOR) 64-битная свёртка пар (key, modTime) — попарное сравнение отчётов
двух серверов даёт вердикт «синхронно/расходится» без передачи полных
листингов; внешний зонд синхронности трека s3 (t33) опирается на этот
эндпоинт. Формат канонизируется в arch-главе 07.

**Лог-события**: LWW-конфликты (ключ, обе версии modTime/sha, origin),
пауза/резюм фетчей по месту, принудительный тримминг журнала (потери
уведомлений), отложенные бакетные удаления, budget-exceeded,
грязная остановка → стартовый reconcile, запуск/завершение reconcile.

**Сквозные измерения в E2E** (не рантайм-метрики узлов): end-to-end
латентность репликации и время восстановления связи после срастания
сети измеряются самой тестовой серией и публикуются фактическими
значениями в журнале прогона — канон и пороги — раздел 7 (A15/A4);
рантайм-метрики `delivery_lag`/`fetch_lag` при этом сверяются тестом
со своими измерениями (сквозная честность наблюдаемости).

## 4. Потоки (сквозные сценарии)

1. **PUT клиента**: SigV4 → хендлер → staging → xl-коммит (rename) →
   append события в журнал + fsync → 200 клиенту. Время: локальный
   коммит + append (~мс). От соседей НЕ зависит ничего (notifier — фон).
2. **Доставка (уведомление с ACK приёма → фетч → применение)**: notifier
   источника шлёт батч уведомлений соседу (в окне in-flight) → приёмник
   возвращает `acceptedToSeqNo` (курсор источника двинулся — приём
   подтверждён) → приёмник: самодостаточные события применяет;
   `object-put` — LWW-предфильтр (skip или fetch-очередь) → фетчер
   (место есть) тянет данные с fetch-грани источника → применение LWW.
   Дальнейший прогресс — целиком забота приёмника (источник не знает и
   не влияет). Медленный приёмник (место/скорость) — источник не
   навязывает данные; окно блокируется только неприёмом уведомлений.
3. **Рестарт источника**: журнал/курсоры/targets с диска; notifier
   продолжает с watermark'ов приёма; неподтверждённые приёмом
   уведомления до-рассылаются (дедуп на приёмнике гасит повторы).
4. **Рестарт приёмника**: чистый (graceful) — drain fetch-очереди до
   остановки, маркер `shutdownClean`; старт чистым — без
   стартового reconcile. Грязный (крах/kill/пауза-без-drain) —
   принятые-но-несохранённые ключи fetch-очереди потеряны, источник их
   НЕ пере-шлёт (курсор ушёл) — старт с грязным маркером запускает
   reconcile-проход по соседям, дыры закрываются автоматически.
5. **Раскол/отказ соседа**: каждая сторона пишет локально (R1), у
   источника копится очередь (bounded-бюджет), приёмник не получает
   уведомлений; срастание → бэкофф истёк → at-least-once рассылка с
   watermark'а → фетчи → сходимость ≤5 мин на тестовом контуре;
   глубокие дыры (принудительный тримминг, потеря очереди) закрывает
   reconcile (периодический/по требованию) — лечение автоматическое,
   без рестартов и ручных действий (R4). Время от восстановления сети
   до первого успешного репликационного взаимодействия — измеряется
   (раздел 7, A4).
6. **Добавление сервера в mesh**: оркестратор (t32) обновляет targets
   на всех узлах (`PUT /admin/replication/targets`, без даунтайма) →
   новый узел: backfill-reconcile всех соседей (забирает существующее,
   когда и сколько может — место/скорость его), получает уведомления о
   новом; существующие: reconcile с нового не нужен (он пуст),
   уведомления его новых событий приходят им как обычно.
7. **Конкурирующий ключ (split-brain)**: PUT ключа в обеих половинах →
   по срастании взаимные уведомления → LWW-предфильтры/фетчи →
   (modTime, tie-break sha) → обе стороны сходятся к одному победителю,
   конфликт журналирован обеими.
8. **Удаления/чистки**: клиентский DELETE → tombstone-событие
   (самодостаточное) → применяется уведомлением → приёмник удаляет +
   хранит tombstone (retention). Служебные чистки `.trash/`/orphan
   (глава 04 §6) — локальные, на доставку не влияют (реплицируется
   логическое состояние, не файлы). Ретенция клиентов (DeleteObjects)
   расходится по mesh tombstone-ами — mesh сходится.
9. **Место приёмника кончилось**: фетчер на паузе (метрика fetch_paused,
   алерт) → данные не забираются и не навязываются; уведомления
   продолжают приниматься (курсор источника идёт), ключи копятся в
   fetch-очереди; чистки/ретенция освободили место → фетчи
   продолжаются, очередь разгоняется.

## 6. Ограничения и границы надёжности

- **RPO второй копии = лаг доставки данных**: секунды штатно, минуты
  после отказов (бэкофф/очередь; плюс место приёмника); подтверждение
  клиенту — локальная фиксация (осознанно, R1; contrast с кворумной
  RPO Garage consistent — выбрана доступность записи). Курсор по ACK
  приёма означает: подтверждённое источником «сосед уведомлён» ≠ «данные
  у соседа» — фактический прогресс данных наблюдается метриками
  приёмника и сверкой листингов (R5).
- **Крах приёмника с недрейненной fetch-очередью**: принятые, но не
  сохранённые ключи теряются из памяти, источник их не пере-шлёт
  (курсор ушёл за ACK приёма) — компенсация автоматическая: стартовый
  reconcile по грязному маркеру (+ периодический как страховка);
  RPO-окно такой потери ограничено временем до ближайшего reconcile.
- **Отказ машины целиком** теряет её журнал/курсоры/tombstones/маркеры
  (локальный том): расхождение закрывается reconcile при возврате или
  замене сервера (оркестрация t32); данные отказавшей машины
  восстанавливаются остальными узлами mesh (mesh и есть источник).
- **LWW и часы**: точность разрешения — точность синхронизации часов
  серверов (NTP — эксплуатационное требование); тай-брейк sha256
  детерминирован; проигравшая версия не хранится (канон: без
  versioning).
- **Окно commit→append** (микро, 3.2) и **окно retention tombstones**
  (3.5) — зафиксированные компромиссы, закрыты сверкой/reconcile.
  Расхождение сверх tombstone-retention (истёкшее знание об удалении) —
  видит сверка листингов; разрешается клиентской ретенцией/перезаписью;
  для wal-цепочек операционно безвредно (старье режется ретенцией).
- **Принудительный тримминг** при переполнении бюджета журнала теряет
  уведомления (НЕ данные) для отстающих соседей — сходимость
  гарантируется reconcile (периодическим/по требованию/стартовым);
  интервал reconcile — параметр эксплуатации.
- **Активные multipart-загрузки** между серверами не согласованы
  (1.3) — клиент завершает загрузку на сервере приёма.
- **Доставка — логическая**: приёмник пишет своим режимом хранения
  (single/EC независимо от режима источника); реплицируются объект как
  данные+метаданные, не xl-раскладка.
- **Один trust-домен**: peer-креды per-install (targets.json на томе —
  секрет на локальном томе допускается по прецеденту главы 05 §2);
  enterprise-IAM/mTLS-pKI — вне (roadmap-паттерн).
- **Тестовые каноны**: docker-E2E — изоляция/teardown/телеметрия по
  `docs/e2e-isolation.md`/`docs/e2e-launch.md`; динамические порты
  (`WithPortBinding(..., assignRandomHostPort: true)`); таймауты
  ожидания ≤30 с с промежуточными проверками (базовые правила);
  срастание-бюджет 5 мин проверяется поллингом с шагом ≤30 с.
- **Existing-регресс**: поведение системы без соседей байт-в-байт как
  текущее (события не ставятся, грань/метрики репликации не активны).

## 7. Критерии приёмки

Приёмочная матрица требований (методика — `docs/s3-replication.md`):
docker-E2E контур ownS3 2–5 серверов, сценарии stop/раскол/серии/
срастание. Все строки — автоматизированные тесты серии
`src/tests/OwnS3.IntegrationTests/E2e` (`PGW_TEST_DOCKER=1`, Release,
сборка E2eFixture-паттерном; изоляция guid, полный teardown, ассерт
чистоты).

| # | Сценарий | Критерий (требование) |
|---|---|---|
| A1 | серия 10 PUT при stop любого числа целей (2-, 3-, 5-нодовый контур) | суммарно ≤1 с, 0 блокировок, 0 отказов записи (R1) |
| A2 | серия 10 PUT при сетевом изоляте писателя (все соседи недоступны, TIMEOUT-природа отказа) | суммарно ≤1 с, 0 блокировок (R1 — антиурок MinIO: блок минутами) |
| A3 | health/GET/S3-грань изолированного сервера | ответы ≤1 с всегда; локальные запись+чтение работают (R3) |
| A4 | срастание после раскола/флапа (в т.ч. двусторонние записи в расколе) | доставка расхождений сама, без рестартов, полный догон тестового контура ≤5 мин (R4; путь: at-least-once уведомления → фетчи + reconcile при глубоких дырах). **Измерение времени восстановления связи**: от фактического восстановления сети (reconnect docker-сетей) до первого успешного репликационного взаимодействия (приём уведомления/фетч/применение — по журналам узлов/метрикам) — фактическое значение в журнал прогона `[METRIC] repl-recover-after-heal-ms=<v>`; ассерт ≤60 с (потолок бэкоффа `OWNS3_REPLICATION_BACKOFF_MAX_SEC` + запас); превышение — провал с разбором по логам, НЕ увеличением таймаута |
| A5 | backfill добавленного сервера (данные существовали до) | новый узел забирает существующее сам (reconcile соседей), полный, фоновый, приём записи на всех не останавливается (R4) |
| A6 | конкурирующий ключ, записанный в обеих половинах раскола | LWW-разрешение на всех серверах к одной версии, конфликт журналирован с обеих сторон (R4) |
| A7 | метрики при живом расхождении | лаг уведомлений (источник, watermark приёма) и лаг данных (приёмник, fetch-очередь) отражены раздельно и >0 при расхождении; sync-report пары серверов показывает расхождение, после догона — совпадение (R5) |
| A8 | удаления (DeleteObject/DeleteObjects, ретенционная чистка) на одном сервере | tombstone-уведомления применяются, mesh сходится к отсутствию ключа (R4) |
| A9 | добавление/вывод соседа через `PUT /admin/replication/targets` на живом контуре | состав применяется без рестарта и без даунтайма S3-грани; добавленный получает backfill (R6) |
| A10 | бюджет журнала: сосед offline долго, журнал растёт | запись не отказывает; алерт-метрика поднята; принудительный тримминг возвращает бюджет; возврат соседа — сходимость через reconcile (R6) |
| A11 | рестарт источника (повторная рассылка) и рестарт приёмника: чистый (drain) и грязный (крах с наполненной fetch-очередью) | источник: идемпотентная до-рассылка, дедуп гасит повторы (R2); приёмник чистый — без потерь; приёмник грязный — дыры закрыты стартовым reconcile автоматически (R2/R4) |
| A12 | доставка больших объектов (multipart-результат > 5 ГБ) | фетчится потоково без S3-лимита, sha-сверка на приёмнике (3.4) |
| A13 | изоляция peer-доступа: ключи read-only/read-write/admin на replication-грани | 403 AccessDenied; политика replication не проходит в 21 операцию (R6) |
| A14 | место приёмника: disk-free watermark поднят выше фактического свободного | фетчи на паузе (метрика fetch_paused, запись источника не деградирует — R1), уведомления/удаления применяются и ACK приёма идут; watermark опущен — фетчи продолжаются, сходимость достигается |
| A15 | штатная репликация (спокойный контур, без отказов): серия PUT на одном узле, измерение сквозной латентности каждого объекта — от фиксации на источнике (200 OK клиенту) до применения на приёмнике (HeadObject приёмника возвращает объект с тем же modTime/sha256; опрос с шагом ≤1 с) | фактические значения в журнал прогона `[METRIC] repl-e2e-latency-ms=<v>` (каждый объект + min/max/median серии); ассерт ≤5 с на объект спокойного контура (notify+fetch маленького объекта в локальной docker-сети — секунды с запасом); превышение — провал с разбором по логам, НЕ увеличением таймаута; измерение теста сверяется с рантайм-метриками `delivery_lag`/`fetch_lag` узлов (честность R5) |

Дополнительно:

- **Сквозные измерения E2E (телеметрия)**: обе величины запроса —
  скорость репликации (A15) и скорость восстановления связи после
  срастания сети (A4) — измеряются тестовой серией целенаправленно и
  публикуются фактическими значениями строками `[METRIC]` в журнале
  прогона (стиль/артефакты — канон `docs/e2e-launch.md`, по образцу
  `[PHASE]`-строк; попадают в артефакты телеметрии сценария).
  Ассерты-пороги — обоснованные (A4 ≤60 с — потолок бэкоффа; A15 ≤5 с —
  спокойный контур), их превышение лечится разбором причин, а не
  увеличением таймаутов.
- **Юниты**: LWW-компаратор (полная таблица исходов), журнал
  (append/чтение/тримминг/бюджет/принудительный тримминг), курсоры
  приёма (персист/дебаунс/acceptedToSeqNo), дедуп уведомлений, окно
  notifier (backpressure), drain/маркер чистого завершения,
  tombstone-retention, sync-report (порядко-независимость hash),
  подлинка исходящих SigV4.
- **Регресс**: существующие серии зелёные (OwnS3.UnitTests,
  OwnS3.IntegrationTests Release docker, мерж-гейт
  `Scale_AddEmptyShard` для затрагиваемого PgWorker-стека — код PgWorker
