# t40-owns3-erasure-coding — спецификация

Erasure coding для ownS3: multi-drive том с кодами Рида—Соломона,
erasure-сеты, кворумы записи/чтения, bitrot-контроль шардов и heal.
Канон — [arch/owns3/06-erasure.md](../../../arch/owns3/06-erasure.md)
(обновлён этой задачей arch-first, см. §2) + правки глав 01/02/04/05 и
[arch/22-owns3.md](../../../arch/22-owns3.md). Постановка —
[arch/roadmap/owns3.md](../../../arch/roadmap/owns3.md), пункт
`t40-owns3-erasure-coding`.

## 1. Цель

ownS3 получает второй режим хранения `XL Erasure`: потеря отдельных
дисков/томов (до parity дисков сета) перестаёт быть потерей данных —
чтение и запись продолжаются через реконструкцию, heal восстанавливает
полноту при возврате/замене диска. Режим `XL Single` (глава
[04](../../../arch/owns3/04-storage.md)) сохраняется без изменений —
существующие инсталляции, стенд и тесты не перенастраиваются.

Контракт 21 операции (глава
[02](../../../arch/owns3/02-operations.md)) не меняется: EC прозрачен
для клиентов; единственное протокольное дополнение — коды ошибок 503
`InsufficientReadQuorum` / `InsufficientWriteQuorum` при недоступности
сета (общие семантики главы 02, раздел «Недоступность кворума»).

Границы (канон 06 §1): N ≥ 2 путей в `OWNS3_DATA_DIR`; setSize 4–16
(дефолт — авто); parity 1 ≤ m ≤ setSize/2 (дефолт 2); без авто-миграции
single→EC; без расширения/уменьшения числа дисков живого тома; setSize
фиксирован форматом тома; parity per-object (смена конфига parity на
живом томе разрешена, перекодирования нет).

## 2. Принципы и ключевые решения

Зафиксированы совместно с пользователем при подготовке спеки:

| # | Решение | Обоснование |
|---|---|---|
| 1 | **Сеты фиксированного размера** (модель MinIO): диски бьются на сеты по позициям путей, объект закрепляется за сетом хэшем | масштабируемость топологии, референс-механика; не «один сет на всё» и не ручная конфигурация сетов |
| 2 | **setSize конфигурируемый**, 4–16, дефолт-авто (наибольший делитель N из {4,8,16}); тесты — минимальный сет 4 | разные масштабы инсталляций; минимальный сет дешёв в тест-контуре |
| 3 | **Режим по числу путей `OWNS3_DATA_DIR`**: 1 = `XL Single`, список ≥ 2 = `XL Erasure`; + `OWNS3_EC_SET_SIZE`, `OWNS3_EC_PARITY` | ноль перенастройки single-инсталляций, единый env-механизм |
| 4 | **Кодек Рида—Соломона — собственная реализация GF(2⁸)** (систематическая Vandermonde-матрица) | офлайн-контур без внешних зависимостей; полный контроль главного durability-механизма; корректность — тест-векторами |
| 5 | **Bitrot — HighwayHash-256** (порт MinIO, магический ключ) per-block per-shard, хэши в `xl.meta` | скорость на больших потоках; референс-механика |
| 6 | **Heal — автоматический фон** (старт + период) **+ админ-грань** `GET /admin/storage`, `POST /admin/heal` (SigV4, admin/root) | максимальная надёжность без вмешательства + наблюдаемость |
| 7 | **Оба режима рядом**: single-drive остаётся | обратная совместимость стенда/E2E t39 |
| 8 | **Без авто-миграции**: EC стартует на пустых дисках или уже-EC-томе; несовместимость — fail-fast | перенос данных — операция клиента (`mc mirror`); авто-миграция дублирует её с худшей надёжностью |
| 9 | **Архитектура встраивания — абстракция драйва**: одна логика `XlObjectStore` поверх интерфейса драйва; `SingleXlDrive` / `ErasureXlDrive` | никакого дублирования логики объектов/листингов/multipart; зелёные тесты t37–t39 как страховка рефакторинга |

Сверено с референсом MinIO (`cmd/erasure-{coding,encode,decode,sets,object}.go`,
`cmd/format-erasure.go`, `cmd/bitrot.go`, `cmd/erasure-healing.go`):
erasure-блок 1 МиБ; read-кворум k, write-кворум k (+1 при k == m);
`xl.meta` на все диски сета с полем индекса диска; `part.N` — шардовый
поток диска. Отступления от референса оговорены в каноне 06 (стратегия
листингов при недоступном сете — 503 всего листинга; консенсус метаданных
по мажоритарному versionId — ownS3 одиночный процесс).

## 4. Структура и компоненты

### 4.1. OwnS3.Storage — ядро EC

| Компонент | Ответственность |
|---|---|
| `GaloisField256` | GF(2⁸): таблицы exp/log, умножение/деление; полином 0x11D |
| `ReedSolomonCodec` | систематическая матрица (Vandermonde, приведение к identity сверху k×k); `Encode` (k data → +m parity), `Reconstruct` (восстановление ≤ m потерянных из любых k); потоковый интерфейс по erasure-блокам |
| `HighwayHash256` | порт `cmd/bitrot.go` + магический 256-битный ключ референса; API «хэш потока/буфера»; тест-векторы Go-реализации |
| `ErasureBlockWriter`/`ErasureBlockReader` | нарезка потока блоками 1 МиБ, стриминговое кодирование в k+m шард-потоков (запись) и сборка исходного потока из k шардовых (чтение, с реконструкцией и bitrot-сверкой блоков) |
| `XlDrive` (абстракция) | интерфейс размещения для `XlObjectStore`: staging записи части/объекта, коммит rename в объектный каталог, чтение записи `xl.meta` и данных, Range-чтение, trash, перечисление объектов бакета (листинги), бакетные mkdir/trash/метаданные, multipart-журналы, чистки. Контракт методов — по механике глав 04/06 |
| `SingleXlDrive` | сегодняшнее поведение `XlVolume`+`XlObjectStore`: один корень, данные как есть, `xl.meta` RecordVersion 1 |
| `ErasureXlDrive` | драйв поверх одного сета (k+m корней): шардированная запись через `ErasureBlockWriter`, по-дисковые tmp+rename-коммиты с кворумом write, чтение с консенсусом `xl.meta` (мажоритарный versionId, порог k) и реконструкцией, bitrot-сверка, `xl.meta` v2 с EcIndex диска, журналы multipart на все онлайн-диски сета |
| `ErasurePool` | набор сетов из N путей: формат тома v2 (создание/валидация/замена диска, п. 4.2), выбор сета — SIPMOD (`System.IO.Hashing.SipHash.HashData`, ключ deploymentId), трекинг online/offline дисков (перепроверка 30 с) |
| `ErasureHealService` | фоновый heal-проход (канон 06 §9): листинг сетов → сверка по-дисково → реконструкция дозаписей (tmp+rename), замена диска, статистика |
| `ErasureStatusProvider` | состояние сетов/дисков/деградации для админ-грани и метрик |

`XlObjectStore` (Objects/List/Buckets/Multipart/Copy) — рефакторинг на
`XlDrive`: логика (conditional, Range, ETag, листинги, журналы, идемпотентность
Complete) не меняется, меняется способ размещения. Существующие юнит/интеграционные
тесты single-режима остаются зелёными весь рефакторинг (страховка).

`XlMetaFile` — расширение до записи v2 (канон 06 §5, побайтово):
поля v1 + `ecAlgo`(string) + `ecM`/`ecN`(uint8) + `ecBSize`(uint32) +
`ecIndex`(uint8) + `distCount`×`ecDist`(uint8) + на часть: `blockCount`
× 32 байта HighwayHash-256 по порядку блоков. Формат файла (magic `OWS3`,
formatVersion 1) не меняется; читатель поддерживает обе версии записи;
single-том v2-записей не пишет.

### 4.2. Формат тома и старт

`volume.json` v2 на каждом диске (JSON camelCase): `magic`, `formatVersion: 2`,
`volumeId`, `mode: "XL Erasure"`, `deploymentId`, `diskId`, `setSize`,
`sets` (2D diskId по позициям путей), `distribution` (перестановка из
deploymentId), `distributionAlgo: "SIPMOD"`.

Старт `ErasurePool.Initialize()` (канон 06 §2): все пусты → создание;
несуществующий путь → создание каталога; смешанное/чужое содержимое без
формата → fail-fast. Живой том: позиция = валидный `volume.json` с
ожидаемым diskId, либо пустой каталог = кандидат замены (живых старых
дисков сета ≥ k, иначе отказ старта; новый diskId + кворумное обновление
`sets` на онлайн-дисках). Изменение N против `sets` → отказ старта.
Валидации одиночных дисков (битый JSON, чужой magic, версия новее) —
fail-fast всего сервиса.

Single-старт (`OWNS3_DATA_DIR` один путь) — код пути сегодняшний
(`XlVolume`, формат 1, режим `XL Single`) без изменений.

### 4.3. OwnS3.App

- env-парсинг: `OWNS3_DATA_DIR` — список путей (запятая; trim; дубликат/
  пустой элемент — отказ старта), `OWNS3_EC_SET_SIZE`, `OWNS3_EC_PARITY` →
  `OwnS3:Ec:*`; валидации канона 06 §1 — fail-fast до старта Kestrel.
- DI: по числу путей собирается `SingleXlDrive` или `ErasurePool`+`ErasureXlDrive`;
  `XlObjectStore` и хендлеры не различают режим.
- Админ-грань (канон 05 §7): `GET /admin/storage` (JSON-статус:
  режим/сеты/диски online/деградация/heal), `POST /admin/heal` (202,
  идущий проход продолжается) — конвейером S3Middleware (SigV4), права
  admin/root, прочим 403.
- Метрики канона 05 §5: `ownS3_ec_drive_online`, `ownS3_ec_set_readable`,
  `ownS3_ec_set_writable`, `ownS3_heal_passes_total`,
  `ownS3_heal_objects_total` (только EC-режим).
- `/healthz` — без изменений (том валиден + touch-проба записи; в EC —
  проба по каждому онлайн-диску; healthz отражает жизнеспособность
  сервиса, а не деградацию — деградация сетов наблюдается в
  `/admin/storage` и метриках).

## 5. Фазы реализации (ориентир для plan.md)

1. **Кодек**: `GaloisField256` + `ReedSolomonCodec` + юниты (round-trip
   случайных данных всех размеров; восстановление всех комбинаций потерь
   ≤ m; стабильность матрицы).
2. **HighwayHash-256**: порт + тест-векторы референса.
3. **Абстракция драйва**: выделение `XlDrive`, перенос single-пути в
   `SingleXlDrive`; все существующие тесты зелёные (поведение не меняется).
4. **Формат тома v2 + пул**: `volume.json` v2, `ErasurePool`
   (инициализация/валидация/замена диска/SIPMOD/online-трекинг), юниты.
5. **`xl.meta` v2**: расширение `XlMetaFile` (чтение/запись v1/v2), юниты.
6. **`ErasureXlDrive`**: шардированная запись (кворумный коммит), чтение
   (консенсус + реконструкция + bitrot + Range), trash, интеграции на
   N temp-каталогах (контрактовые тесты 21 операции в EC-топологии).
7. **Multipart/бакеты/чистки в EC**: журналы на дисках сета, бакетные
   операции на все сеты, per-disk чистки.
8. **Heal**: `ErasureHealService` (проход, дозаписи, замена диска) +
   статус-провайдер; интеграции (порча/удаление шарда → heal → чтение).
9. **App-интеграция**: env, DI, админ-грань, метрики, `/healthz` EC.
10. **Поставка и E2E**: compose-профиль, чек 47, docker-E2E EC-серия
    (§6.3), полный прогон всех серий + Release.

Фазы 1–2 независимы от 3–4 (параллелимы). Порядок 3→6 обязателен.

## 6. Тесты и критерии приёмки

### 6.1. Юниты (OwnS3.UnitTests)

- GF(256): таблицы, операции, обратимость.
- RS-кодек: round-trip (0 байт, хвост < блока, ровно блок, много блоков);
  восстановление каждой комбинации потерь до m (k+m ≤ 8 перебором);
  систематичность (data-шарды = вход).
- HighwayHash-256: векторы Go-референса (включая магический ключ), пустой
  ввод, длинные потоки.
- SIPMOD: стабильность (тот же ключ → тот же сет), равномерность на
  псевдослучайных ключах, зависимость от deploymentId.
- `xl.meta` v2: round-trip v1/v2, чтение v1-записи новым читателем,
  bitrot-секция.
- `volume.json` v2: создание/валидация/все отказы старта (чужой magic,
  версия новее, diskId вне sets, изменение N, замена при < k живых).
- Кворумы: границы read/write (k, k+1 при k==m) на моках дисков.

### 6.2. Интеграции (OwnS3.IntegrationTests, host-FS)

- EC-топология на N temp-каталогах: полный контракт 21 операции
  (переиспользование контрактовых кейсов single-серии, параметризация
  режима).
- Деградация host-FS: недоступный диск (каталог удалён/закрыт) → чтение
  реконструкцией; возврат каталога → heal; bitrot-порча шарда (правка
  байта part-файла) → чтение живо, heal чинит; потеря ≥ m+1 → 503
  `Insufficient*Quorum`, не 404.
- Single-режим: существующие 115 интеграций зелёные без правок.

### 6.3. Docker-E2E (OwnS3.IntegrationTests/E2e, гейты PGW_TEST_DOCKER=1)

Контур: контейнер `owns3:e2e`, 4 тома, setSize=4/parity=1 (3+1);
изоляция/telemetry/зачистка — каноны docs/e2e-isolation.md, e2e-launch.md
(guid-имена, own-only teardown, ассерт чистоты, [PHASE], MarkFailed).

- **базовый цикл**: AWS SDK PUT/GET/Head/Range/листинги/multipart/копия
  против EC-контура; ETag/conditional-семантики те же, что single.
- **деградация**: рестарт контейнера с 3 томами (один detached) → чтение
  и запись живы (реконструкция), статусы `ownS3_ec_set_*` это отражают.
- **недоступность**: рестарт с 2 томами (онлайн 2 < k=3) → GET/PUT/листинги
  503 `InsufficientReadQuorum`/`InsufficientWriteQuorum`.
- **возврат тома**: повторное включение 4-го тома (с данными) → heal
  восстанавливает полноту, чтение/метрики зелёные.
- **замена диска**: 4-й том подменён пустым → старт с заменой (sets
  обновлён), heal доливает объекты, все данные читаются.
- **админ-грань**: `/admin/storage` статус деградации корректен;
  `/admin/heal` 202; ключ read-write → 403 на админ-грани.
- Single-режим: E2E-серия t39 (18 Facts) зелёная без правок.

### 6.4. Критерии приёмки

1. Все серии зелёные на Release: юниты (существующие + новые), интеграции
   (single + EC), docker-E2E (t39 + EC-серия); 0 warnings
   (`TreatWarningsAsErrors`).
2. Деградация ≤ m дисков сета: чтение и запись работают без вмешательства;
   возврат/замена диска — heal восстанавливает полноту автоматически
   (подтверждено E2E-кейсами).
3. Недоступность сета: 503 `Insufficient*Quorum` на операциях с объектами
   сета и на листингах; никаких 404-подмен.
4. Single-режим: ни одно существующее поведение/тест/контур не изменился
   (стенд, E2E t39, интеграции).
5. Канон arch/owns3 соответствует реализации (расхождений проекта с
   главой 06 нет — код зеркалит канон; правки канона при находках —
   arch-first).
6. Стенд: `owns3-ec` поднимается профилем, чек `47-owns3-ec.sh` зелёный.

## 7. Ограничения и нерешаемое в задаче

- Без авто-миграции single→EC и без изменения N живого тома (расширение —
  задача трека); смена parity на живом томе разрешена (per-object).
- setSize фиксирован форматом тома; смена = новый том.
- ownS3 остаётся single-node: EC защищает от отказов дисков/томов, не от
  отказа docker-хоста; распределённые инстансы/репликация — вне задачи.
- Межсайтовая и бакетная репликация, versioning, TLS — прежние границы
  (глава 01).
- Вне набора: расширение S3-API (кроме админ-грани 05 §7), SSE-шифрование,
  оптимизация малых объектов inline-данными (канон 06 §4).
- Производительность кодека не оптимизируется специально (блок 1 МиБ,
  стримингово); фиксируется базовый ориентир throughput в юните на
  больших буферах (не жёсткий гейт).
