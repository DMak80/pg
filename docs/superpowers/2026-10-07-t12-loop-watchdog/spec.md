# t12-loop-watchdog — watchdog зависших циклов воркера

- **Roadmap**: [`arch/roadmap/reliability.md`](../../../arch/roadmap/reliability.md), трек сквозной надёжности, приоритет P2, целевая характеристика **R** (быстрая самовосстанавливаемость).
- **Формулировка**: «исключения циклов ловятся (TickSafelyAsync), но „завис без исключения“ виден только в `loops-alive` healthz; самоперезапуска по staleness нет».
- **Открытые решения** (вопросы пользователю заданы 2026-10-07, через AskUserQuestion):
  - **Q4 порог** — подтверждён пользователем (2026-10-07): конфигурируемый, дефолт = 2 × порог healthz loops-alive (60 с при дефолтных интервалах: 3×max(5,5)+15=30, ×2=60);
  - **heartbeat-семантика** — принята пользователем 2026-10-07 после разбора детерминированного ложного срабатывания AC3 (бутстрап-итерация reconcile ~41 с при пороге E2E 36 с: firing не по «нет тика», а по «нет активности»);
  - **heartbeat-точки moves** — подтверждены пользователем (2026-10-07, вопрос по итогам изучения кода): cutover-цепочка выполняется внутри одного тика и легитимно ждёт до `CutoverTimeoutSec=90 с` — больше порога 60 с;
  - **Q1 механизм** — выбран внутренний watchdog в воркере (альтернативы: внешний watchdog в панели; healthz 503 + docker HEALTHCHECK) — ожидает подтверждения при ревью;
  - **Q2 охват** — все три воркера (PgWorker, KafkaWorker, ValkeyWorker); панель — НЕ-цель — ожидает подтверждения при ревью;
  - **Q3 действие при staleness** — graceful `StopApplication` (путь RestartHandler), не `Environment.FailFast` — ожидает подтверждения при ревью;
  - **Q5 анти-луп рестартов** — без программного лимита (docker restart-backoff + метрика/журнал дают видимость) — ожидает подтверждения при ревью.

## 1. Контекст и цель

### 1.1. Проблема

Все фоновые циклы воркеров построены на `TickSafelyAsync`: исключение тика
превращается в ошибку тика (лог + `ErrorDelayMs`), цикл продолжает работать.
Но зависание «без исключения» — await внутри тика не возвращается (зависший
сетевой вызов без таймаута, deadlock, вечное ожидание внешней системы) —
этот контур защиты не ловит. Сегодня такое зависание:

1. **Видимо, но не лечится**: healthz `loops-alive` даёт `Degraded` — но это
   HTTP 200, docker HEALTHCHECK (`curl -sf /healthz`) считает успехом и
   контейнер не гасит; панельный алерт `worker-unhealthy` (warning) и
   Prometheus `WorkerLoopStalled` (critical, порог 60 с) — только сигналы
   оператору, нотификаций наружу нет (`t13`).
2. **Блокирует takeover**: keepalive-контур `ClaimStore` (продление lease,
   отдельный фоновый Task) продолжает жить при зависшем цикле — lease-клэймы
   и лидерство продлеваются бесконечно, второй инстанс (t07) клэймы НЕ
   забирает. Надзор (provisioning/rebuild/ротации/бэкапы) замерзает до
   ручного вмешательства оператора — нарушение характеристики R.
3. **Хуже одиночного инстанса**: при двух инстансах формально «всё живо»
   (оба lease горят, healthz у зависшего отвечает 200), но работающий цикл
   только у одного, а клэймы висят у зависшего.

Отдельный класс — **легитимно длинная итерация**: тик reconcile ставится
один раз в конце итерации, а её длительность определяется самой медленной
фазой (бутстрап кластера: pg_basebackup реплик ~41 с; cutover переезда:
ожидание догоняния слота до 90 с). Такая итерация жива, но тик «стареет» —
watchdog по «нет тика» расстреливал бы живой воркер (доказано двумя
побайтно одинаковыми AC3-прогонами Фазы 6: firing на 37-й секунде при
пороге 36 с). Поэтому семантика watchdog — «нет АКТИВНОСТИ», не «нет тика».

### 1.2. Цель

Зависший без исключения цикл воркера самолечется за ограниченное время:
внутренний watchdog замечает отсутствие активности цикла (нет ни тика, ни
прогресс-отметки) сверх порога, инициирует graceful self-stop процесса
(готовый путь `RestartHandler`: `IHostApplicationLifetime.StopApplication`),
docker-политика `restart: unless-stopped` поднимает контейнер; lease гаснут
≤15 с, клэймы мигрируют второму инстансу или возвращаются после подъёма.
RTO самовосстановления — порядка 1,5–2 минут (порог 60 с + shutdown ≤30 с +
старт контейнера). Долгая, но живая итерация (прогресс-отметки внутри порога)
рестарта не даёт.

### 1.3. НЕ-цели (границы)

- Не решаем «завис весь процесс» (threadpool starvation, вечная GC-пауза):
  healthz тогда тоже не отвечает — это зона docker HEALTHCHECK, не watchdog.
- Не трогаем `TickSafelyAsync`-механику и обработку исключений тиков —
  watchdog закрывает ровно дополнительный класс «завис без исключения».
- Не строим внешний watchdog в панели и не меняем семантику healthz
  (Degraded остаётся HTTP 200; причины деградации не разделяем на
  «рестартуемые/нерестартуемые»; loops-alive считается ПО ТИКАМ, как раньше)
  — если такое понадобится, отдельная задача roadmap.
- Не добавляем лимит частоты рестартов / «уставшие» состояния —
  идемпотентность процессов + takeover делают рестарт безопасным, сдерживание
  ресторма — docker restart-backoff (см. §3.5).
- Не распространяем watchdog на панель (`AdminPanel.*`): её фоновые циклы —
  другой паттерн (не TickSafelyAsync/loops-alive), вне формулировки t12.
- Не меняем etcd-контракт (ключи, payload, lease-семантика) — watchdog
  ничего не пишет в etcd (симметрия RestartHandler: lease сами погаснут).
- Не меняем пороги/формулы watchdog и healthz ради heartbeat-семантики —
  меняется только критерий firing (активность вместо тика).

- `BackupOrphanSweeperLoop` (`src/PgWorker.App/Loops/BackupOrphanSweeperLoop.cs`)
  не пишет тики в `HealthState` вообще («без health-обёртки») — невидим в
  `loops-alive` и выпадает из любого staleness-контроля;
- никакой компонент не преобразует staleness в действие.

## 3. Принципы

1. **Самодостаточность лечения**: воркер самовосстанавливается без внешних
   систем (панель/Prometheus могут быть мертвы) — канон multi-host
   надёжности (гарантии не строятся от соседних процессов).
2. **Единый источник живости**: `HealthState` — единственные отметки; тики —
   для healthz loops-alive, «последняя активность» — для watchdog (поле рядом
   с тиками, обновляется и тиком, и прогресс-отметками). Watchdog и healthz
   читают один `HealthState` и считают порог одной формулой (общий хелпер),
   различаются семантикой поля (healthz — тики, watchdog — активность) и
   множителем.
3. **Watchdog отличает зависание от долгой, но живой итерации**: firing — по
   отсутствию АКТИВНОСТИ (тик ИЛИ промежуточная прогресс-отметка), а не по
   отсутствию тика. Итерация reconcile легитимно длится десятки секунд
   (бутстрап нод, cutover переездов) — цикл обязан отмечать живость в начале
   итерации и на заведомо долгих фазах; порог и формулы при этом НЕ меняются.
4. **Готовый путь остановки**: никаких новых механизмов завершения — тот же
   graceful `StopApplication`, что у `POST /api/restart`; идемпотентность
   процессов и takeover делают рестарт безопасным (арх-канон «ошибка тика →
   продолжение со следующего тика» распространяется и на рестарт всего
   воркера).
5. **Watchdog проще наблюдаемого**: компонент — тривиальный цикл чтения
   отметок и сравнения возрастов (без сетевых вызовов, без etcd, без docker);
   всё, что может зависнуть в его собственной проверке, — отсутствует.
6. **Без анти-лупа**: систематический баг «после рестарта снова виснет»
   даёт рестарт-цикл — его сдерживает docker restart-backoff, а видимость
   дают метрика/журнал (новый InstanceId, счётчик рестартов). Программный
   лимит («после N рестартов — лечь») означал бы отказ от самовосстановления
   ровно тогда, когда оно нужнее всего — противоречит R.
7. **arch-first**: канон watchdog сначала в `arch/` (§14/§16/§21 — надёжность
   и наблюдаемость, §18 — метрика), затем код.
8. **Каноны проекта**: воркеры всегда в докере; тесты — динамические порты,
   полная самоочистка, короткие бюджеты; язык документации — русский.

## 4. Структура и компоненты

### 4.1. arch/ — контракт watchdog (первая фаза, только документация)

etcd-контракт и интерфейсы API не меняются. Дополняем:

- **`arch/14-pgworker.md`** §6 «Надёжность»: пункт «Watchdog зависших
  циклов» — внутренний компонент следит за возрастом активности всех фоновых
  циклов (reconcile/keepalive/snapshot/orphan-sweep) по `HealthState`;
  активность = тик или прогресс-отметка (долгие фазы итерации — создание
  контейнеров нод, ожидание готовности нод, поллинг-циклы переездов —
  отмечают живость); отсутствие активности (тик или прогресс-отметка) сверх
  порога → журнал + метрика + graceful `StopApplication` (путь
  `POST /api/restart`); контейнер поднимает docker-политика; lease гаснут
  ≤15 с → takeover вторым инстансом. Отдельно: «завис весь процесс» — зона
  docker HEALTHCHECK, watchdog закрывает только «цикл завис, процесс жив».
  §7 «Наблюдаемость»: counter рестартов watchdog в словаре метрик.
  §8 «Конфигурация»: секция `Loops:Watchdog` (ниже).
- **`arch/16-kafkaworker.md`** §6/§7/§8 — симметричное дополнение
  (циклы reconcile/keepalive/snapshot; формулировка активности «нет
  активности (тик или прогресс-отметка)» — без перечня долгих фаз: у
  KafkaWorker их нет, §4.6).
- **`arch/21-valkeyworker.md`** §6/§7/§8 — симметричное дополнение; в
  перечне долгих фаз — ожидание готовности нод (PING-цикл бутстрапа) и
  создание контейнеров нод.
- **`arch/18-metrics.md`** §2.2 — новая серия в словаре воркер-паттерна:
  `worker_watchdog_restarts_total` (counter, лейбл `loop`) — «инициированные
  watchdog-остановки по отсутствию активности»; источник — марк-метод
  `WorkerMetricsInstrumentation`.

Пороги, формулы и метрики heartbeat-семантикой НЕ меняются — в arch/ меняется
только критерий firing («нет активности» вместо «нет тика»).

### 4.2. LoopWatchdog — общий компонент (Shared.Core)

Новый `src/Shared.Core/Hosting/LoopWatchdog.cs` — `BackgroundService`:

- **Источник живости**: абстракция `ILoopsVitality` — снимок
  `IReadOnlyList<LoopHeartbeat>`, где `LoopHeartbeat = (string Name,
  DateTimeOffset? LastActivityAt, TimeSpan StaleAfter)`.
  `LastActivityAt` — момент последней активности цикла: тик ИЛИ
  прогресс-отметка (бывшее поле `LastTickAt` расширено до `LastActivityAt`;
  healthz — не консюмерер `LoopHeartbeat`, он читает `HealthSnapshot`
  напрямую, поэтому второго поля не требуется). Каждый воркер реализует
  `ILoopsVitality` поверх своего `HealthState` + `LoopsOptions` (перечень
  циклов и пороги — тем же общим хелпером формул, что в healthz, множитель
  watchdog-порога — §4.4). Существующий интерфейс
  `Shared.Core.HealthChecks.IHealthCheckService` (Inited/Working/StatusError)
  не расширяется.
- **Формулы порогов** (вынос из `*WorkerHealth` в общий хелпер
  `Shared.Core/HealthChecks/LoopStaleness.cs`; healthz переходит на хелпер
  без изменения поведения):
  - быстрые циклы (reconcile, keepalive, orphan-sweep):
    `3 × max(ScanIntervalSec, KeepaliveSec) + 15` — порог healthz;
    watchdog = `WatchdogMultiplier ×` этого порога;
  - snapshot-цикл: `3 × max(ScanIntervalSec, 60 × SnapshotIntervalMin) + 15`
    — порог healthz; watchdog = `WatchdogMultiplier ×` этого порога.
  - Пороги применяются к ВОЗРАСТУ АКТИВНОСТИ (`LastActivityAt`), значения
    формул не меняются.
- **Свой цикл**: проверка каждые `Loops:Watchdog.CheckIntervalSec`
  (дефолт 15 с) — чтение снимка (lock-free, миллисекунды), сравнение
  возрастов. Никаких сетевых вызовов.
- **Grace старта**: отметки `null` («цикл ещё не тикал и не отмечался») не
  firing, пока возраст самого watchdog (от его запуска, `clock`) меньше
  `2 × StaleAfter` цикла; если активность так и не пришла за grace —
  рестарт (цикл не стартовал или завис при старте).
- **Firing — превышение порога БЕЗ АКТИВНОСТИ** (одного наблюдения
  превышения достаточно — порог 60 с сам по себе защита от ложных
  срабатываний; гистерезис не вводим): возраст `LastActivityAt` цикла
  превысил `StaleAfter` — ни тика, ни прогресс-отметки за порог. Итерация с
  регулярными отметками (даже без тика) firing не даёт; «тиков нет, но
  активность свежая» — не firing; «нет ни тика, ни активности» — firing.
  Действия:
  1. `LogCritical` с именем цикла, возрастом активности и порогом;
  2. маркер метрики `worker_watchdog_restarts_total{loop}` (через колбэк,
     который app регистрирует при подключении — Shared.Core не зависит от
     Shared.Metrics);
  3. короткая пауза `StopDelaySec` (дефолт 1 с, чтобы лог/событие успели
     доехать в выхлоп контейнера);
  4. `IHostApplicationLifetime.StopApplication()`. Дальше — существующее:
     shutdown (зависший цикл не реагирует на токен → `ShutdownTimeout` 30 с
     закрывает ожидание) → exit → docker `restart: unless-stopped` →
     подъём → свежий InstanceId, lease старого погасли ≤15 с.
- **Не следит за собой** (принципиально: компонент без внешних вызовов;
  его собственное зависание означало бы деградацию всего процесса — зона
  docker HEALTHCHECK).

### 4.3. Дооснащение BackupOrphanSweeperLoop (PgWorker)

`BackupOrphanSweeperLoop` получает отметку тика в `HealthState`
(`MarkOrphanSweepTick`) и запись в `HealthSnapshot`/healthz `loops-alive`
симметично остальным циклам; порог — как у быстрых циклов. Долгих фаз у
sweeper'а нет (пауза между итерациями — `DelayTickingAsync`, сама итерация
короткая), отдельных прогресс-отметок не требует. Без этого зависание
sweeper'а невидимо (сейчас «без health-обёртки») — watchdog получает полный
перечень циклов воркера. У KafkaWorker/ValkeyWorker аналогичных «слепых»
циклов нет (их циклы уже пишут тики).

### 4.4. Конфигурация (appsettings всех трёх воркеров)

Секция `LoopsOptions` дополняется:

```
Loops:Watchdog { Enabled=true, Multiplier=2, CheckIntervalSec=15, StopDelaySec=1 }
```

- `Enabled=false` — компонент не регистрируется (поведение как до задачи);
- `Multiplier` — множитель порога healthz (дефолт 2 → быстрые циклы 60 с
  при дефолтных интервалах: 3×max(5,5)+15=30, ×2=60; snapshot — свой порог
  той же формулой ×2); окно между Degraded healthz (порог ×1, по тикам) и
  рестартом (порог ×2, по активности) — алертам оператора; легитимно-длинные
  итерации закрывает не окно, а heartbeat-семантика (§4.2);
- явного `StaleAfterSec`-оверрайда НЕ вводим — формула от интервалов циклов
  единственная (меняем интервалы → пороги следуют автоматически).

### 4.5. Метрика и журнал

- `WorkerMetricsInstrumentation` (Shared.Metrics): маркер-метод
  `WatchdogRestart(string loop)` → counter `worker_watchdog_restarts_total`
  (arch/18 §2.2, §4.1). Подключается колбэком из каждого app при
  регистрации watchdog.
- Журнал: `LogCritical("watchdog: цикл {Loop} не проявлял активности {Age} c
  (порог {Threshold} c) — инициирован self-restart", …)` — последняя запись
  контейнера перед остановкой; docker restart сохраняет логи контейнера,
  факт виден постфактум.
- healthz: в `data` добавляется секция `watchdog`
  (`armed; stale=<loop|нет>`), источник — состояние компонента; контракт
  статусов HTTP не меняется, loops-alive считается по тикам, как раньше.

### 4.6. Heartbeat-точки и подключение в воркерах

`Program.cs` каждого воркера (PgWorker, KafkaWorker, ValkeyWorker):
регистрация `ILoopsVitality` (поверх `HealthState` + `LoopsOptions`),
`AddHostedService<LoopWatchdog>` (после остальных hosted-сервисов) и
колбэк метрики. Состав наблюдаемых циклов:

| Воркер | Циклы под watchdog |
|---|---|
| PgWorker | reconcile, keepalive, snapshot, orphan-sweep (после §4.3) |
| KafkaWorker | reconcile, keepalive, snapshot |
| ValkeyWorker | reconcile, keepalive, snapshot |

**Механизм отметок**: `HealthState` каждого воркера получает поле «последняя
активность reconcile» (в `HealthSnapshot`; healthz loops-alive его НЕ читает);
`MarkReconcileTick` обновляет и тик, и активность; новый
`MarkReconcileActivity()` — только активность. Циклы, у которых долгих фаз
нет (keepalive, snapshot, orphan-sweep), отдельных активностей не заводят —
их активность = тик. Доставка отметок в глубину процессов (Provisioning /
Moves лежат ниже App и `HealthState` не видят): узкий интерфейс
`ILoopProgress { void Mark(); }` в `Shared.Core.Hosting`; app регистрирует
реализацию поверх `HealthState.MarkReconcileActivity`; процессы с долгими
фазами принимают её инжекцией. Сами циклы отмечают живость напрямую через
свой `HealthState`.

**Минимально достаточный набор точек** (отметка = `MarkReconcileActivity`;
принцип — начало итерации + каждая итерация опроса/создания в заведомо
долгой фазе):

| Воркер | Точка | Где |
|---|---|---|
| PgWorker | старт итерации reconcile | `ReconcileLoop.TickAsync`, первая отметка до чтения etcd |
| PgWorker | создание/старт контейнера каждой ноды | `EnsureNodesAsync` provisioning/add-shard → после каждого `EnsureNodeAsync` |
| PgWorker | каждая итерация опроса готовности ноды (пока не Running) | `WaitPatroniAsync` → после каждой пробы `IdentifyAsync` |
| PgWorker | каждая итерация поллинг-циклов переездов | `CutoverSequence` (заморозка: попытка; ожидание слота: проход), `AbortSequence`/`DropSlotAsync` (проход дезактивации) |
| KafkaWorker | старт итерации reconcile | `ReconcileLoop.TickAsync`, первая отметка до чтения etcd |
| ValkeyWorker | старт итерации reconcile | `ReconcileLoop.TickAsync`, первая отметка до чтения etcd |
| ValkeyWorker | создание/старт контейнера каждой ноды | фаза контейнеров provisioning → после каждого ensure-вызова драйвера |
| ValkeyWorker | каждая итерация PING-цикла готовности ноды (бюджет `NodeBootSec`, последовательно по нодам) | `AwaitBootAsync` → после каждой пробы `PingAsync` |

**KafkaWorker — глубоких точек не требуется** (зафиксировано по изучению
кода): ожидание готовности кластера расползается по тикам — `WaitReadyAsync`
делает ровно один `DescribeCluster` с `RequestTimeout=10 с` за тик
(бутстрап-бюджет `BrokerBootSec` считается между тиками); создание
контейнеров брокеров — короткие docker-вызовы; бэкап-процессы PgWorker
аналогично «запускают/поллят джобы, не ждут их» (non-blocking). Тик
KafkaWorker — единицы секунд, запас до порога 60 с кратный; точка старта
итерации достаточна.

Симметрично не требуют точек: keepalive/snapshot/orphan-sweep всех воркеров
(короткие тики; snapshot-порог к тому же на порядки больше интервалов),
`NodeSupervisor` PgWorker (пробы по 3 с × ноды одного шарда — секунды).

### 4.7. Тесты

- **Юнит** (новый `src/tests/Shared.Core.UnitTests/Hosting/LoopWatchdogTests.cs`):
  формулы порогов хелпера (быстрые/snapshot, симметрия healthz); grace
  старта (null-отметки в grace-окне → не firing, после grace → firing);
  heartbeat-семантика firing — три кейса: активность (прогресс-отметка)
  внутри порога → не firing; активность есть, тика нет → не firing;
  активности нет (возраст `LastActivityAt` превысил порог) → firing;
  firing → `StopApplication` вызван ровно once (fake
  `IHostApplicationLifetime`); живые циклы → не firing; `Enabled=false` →
  компонент не регистрируется. Комментарии тестов — по нотации AAA.
- **Юнит per-app** (PgWorker.UnitTests): `BackupOrphanSweeperLoop` пишет
  тик в `HealthState`; healthz `loops-alive` включает orphan-sweep;
  `ILoopsVitality` отдаёт полный перечень с корректными порогами;
  `HealthState`: `MarkReconcileActivity` обновляет активность без тика,
  `MarkReconcileTick` обновляет и тик, и активность.
- **Интеграционный** (PgWorker.IntegrationTests, не docker): поднимается
  хост воркера в тестовом окружении с уменьшенными интервалами `Loops`
  (пороги порядка десятков секунд) и подменённым `ILoopsVitality`, чей
  снимок показывает устаревшую активность → ассерт: хост инициировал
  остановку в бюджет (каждое отдельное ожидание поллинга ≤30 с на правило
  AGENTS.base.md §12). Симметричный негатив — долгая фаза с отметками:
  снимок отдаёт давний тик, но свежую активность (прогресс-отметки внутри
  «долгой итерации») → хост живёт без остановки (отмена через штатный
  token).
- **Мерж-гейт E2E** (правило AGENTS.md — задача трогает `src/PgWorker.App`):
  кейс-маркер `DOTNET_CLI_UI_LANGUAGE=en PGW_TEST_DOCKER=1 dotnet test
  src/PgWorker.slnx -c Release --filter FullyQualifiedName~Scale_AddEmptyShard`
  на свежем Release зелёный — доказывает, что watchdog не даёт ложных
  рестартов в живом docker-контуре (инстанс переживает полный provisioning,
  включая бутстрап нод с pg_basebackup, без остановки).

## 5. Фазы

1. **arch-first** (только документация): arch/14 §6/§7/§8, arch/16, arch/21
   (симметрично), arch/18 §2.2 — канон watchdog с heartbeat-семантикой
   («нет активности — тик или прогресс-отметка»), формулы, конфигурация,
   метрика (§4.1).
2. **Shared.Core + Shared.Metrics**: хелпер формул `LoopStaleness`,
   `LoopWatchdog` + `ILoopsVitality` (`LoopHeartbeat.LastActivityAt`,
   firing по отсутствию активности), интерфейс `ILoopProgress`, маркер
   `WatchdogRestart` (§4.2, §4.5, §4.6); юнит-тесты §4.7.
3. **Воркеры**: дооснащение `BackupOrphanSweeperLoop` (§4.3), переход
   healthz на общий хелпер формул (поведение без изменений), секция
   `data["watchdog"]`, `Loops:Watchdog`-опции, подключение в `Program.cs`
   трёх воркеров (§4.4–4.5); heartbeat-точки §4.6: `HealthState`-поле
   активности + `MarkReconcileActivity` у трёх воркеров, `ILoopProgress`
   в PgWorker-Provisioning/Moves и Valkey-Provisioning; юнит per-app.
4. **Интеграционные тесты** §4.7 (устаревшая активность → остановка;
   долгая фаза с отметками → хост живёт).
5. **Мерж-гейт**: E2E-маркер `Scale_AddEmptyShard` зелёный; runbook;
   roadmap-гейт (§4.8).

Фазы 2→3 жёстко последовательны (компонент → подключение); фаза 4 после 3;
фаза 5 последней.

## 6. Ограничения

- `TreatWarningsAsErrors=true`, `Nullable=enable`, `LangVersion=latest` —
  новый код без предупреждений.
- Тесты: никаких хардкодов хост-портов; таймауты ожидания ≤30 с (каждое
  ожидание — не правило, а проверка с повтором); интеграционные бюджеты —
  короткие.
- E2E (маркер): свежий Release, самоочистка контура фикстурой — каноны
  `docs/e2e-isolation.md`/`docs/e2e-launch.md`; зачистка контейнеров/сетей
  после серии.
- Watchdog не делает сетевых вызовов и не пишет в etcd — нарушение в ревью
  блокирует.
- Изменение HTTP-статусов healthz / формул порогов healthz / семантики
  loops-alive (Degraded по тикам) — вне scope (поведение healthz
  сохраняется бит-в-бит, кроме новой data-секции).
- Пороги/формулы watchdog не меняются ради heartbeat-семантики — меняется
  только критерий firing (активность вместо тика).
- Локально собираемые образы в registry `192.168.0.1:5000` не кладём.

## 7. Критерии приёмки

- **AC1 (юнит — механика)**: тесты §4.7 зелёные: формулы порогов
  (включая симметрию с healthz), grace старта, heartbeat-семантика firing
  (активность внутри порога → не firing; активность есть, тика нет → не
  firing; активности нет → firing), firing → ровно один `StopApplication`,
  свежие циклы → не firing, `Enabled=false` → компонент не поднят.
- **AC2 (интеграция — самолечение и терпимость)**: хост воркера с
  устаревшей активностью в `ILoopsVitality` инициирует остановку в бюджет
  при уменьшенных тестовых интервалах `Loops` (пороги порядка десятков
  секунд; каждое отдельное ожидание поллинга ≤30 с — AGENTS.base.md §12);
  с долгой фазой, отмечающей прогресс (давний тик, свежая активность),
  хост работает без остановки.
- **AC3 (ложных срабатываний нет)**: E2E-маркер `Scale_AddEmptyShard`
  зелёный на свежем Release; бутстрап кластера в E2E (итерации reconcile
  с pg_basebackup реплик) не даёт ни одного self-restart; за серию ни
  одного `worker_watchdog_restarts_total` и ни одной записи self-restart в
  журнале инстансов, участвующих в сценарии.
- **AC4 (наблюдаемость)**: `/metrics` инстанса содержит
  `worker_watchdog_restarts_total` (после триггера — с лейблом цикла);
  `/healthz` отдаёт секцию `watchdog`; журнал содержит критическое событие
  перед остановкой.
- **AC5 (полнота перечня)**: `loops-alive` healthz PgWorker включает
  orphan-sweep; зависание sweeper'а видно и лечится watchdog.
- **AC6 (симметрия)**: watchdog поднят у всех трёх воркеров с одним
  компонентом `Shared.Core` (без копий per-app), состав циклов — по §4.6;
  heartbeat-точки — по таблице §4.6 (KafkaWorker — только старт итерации,
  обоснование зафиксировано в спеке).
- **AC7 (канон и гейт)**: arch/14/16/18/21 дополнены (§4.1); runbook
  описывает watchdog; мерж-коммит закрытия снимает пункт t12 из
  `arch/roadmap/reliability.md` и обновляет строку в
  `arch/roadmap/reliability-report.md` (перенос в «Сделано», правка сводки
  R) — рассинхрона «задача закрыта / отчёт нет» нет.
