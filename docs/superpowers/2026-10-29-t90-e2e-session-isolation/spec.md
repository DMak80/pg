# t90: изоляция docker-E2E сессий + нулевые ложные скипы + параллельность классов — spec

## 1. Цель

Две рамки владельца, обе обязательны и не обсуждаются.

**Рамка A — изоляция сессий.** Каждый E2E-прогон/сессия корректен ПРИ наличии
любой фоновой нагрузки на docker-хосте (параллельные прогоны других
веток/worktree, соседние процессы, dev-стенд). Чужая нагрузка есть всегда, она
незначительна: на неё нельзя списывать падения, и её нельзя блокировать
глобальным локом:

- глобальный лок запуска серий — НЕ реализовывается;
- детект чужих живых `pgw-*`/`kfw-*`/`s3w-*` контуров перед стартом
  серии — НЕ реализовывается;
- **теги E2E-образов — PER-BRANCH: суффикс только из имени ветки; одна
  ветка работает с одним набором образов**;
- **контейнеры — PER-PROCESS**: изоляция экземпляров рантайма
  (контейнеры/сети/тома) по процессам/прогонам (guid в именах).

**Рамка B — нулевые ложные скипы + параллельность классов** (расширение scope,
дословно от владельца):

- «скипов быть не должно если тест реально должен быть запущен, а не скипнут
  всегда по какой-то причине»;
- «если нужно разделить — дели на проекты (интеграционные тесты, E2E-тесты),
  но запустив проект никаких ложных скипов быть не должно»;
- «параллельный запуск тестов организуется за счёт создания каждым тестовым
  КЛАССОМ своего окружения с новым гуидом (или его частью) и удалением после
  завершения»;
- «параллельность классов должна регулироваться либо настройками библиотеки
  тестирования, либо через семафор (но ДО создания окружения)».

Разделение ответственности: СТАТИКА (собираемые docker-образы) — едина в
пределах ветки и раздельна между ветками; РАНТАЙМ (контейнеры, сети, тома,
/tmp-телеметрия процесса) — уникален per-process/per-run. Git-гарантия: одна
ветка не может быть чекаутена в двух worktree одновременно — per-branch тег
всегда имеет ровно одного «владельца кода». Осознанное следствие per-branch
(фиксируется, не дефект): пересборка статики той же ветки обновляет образы
ветки «под ногами» живого прогона той же ветки — статику ветки контролирует
владелец ветки; «чужими» считаются только другие ветки/worktree/процессы.

## 2. Принципы

- **Запустил проект — ноль скипов**: запуск любого тестового проекта
  (`dotnet test <project>`) на docker-хосте разработчика даёт отчёт только из
  Passed/Failed. Любой Skip в штатном прогоне проекта — дефект. Единственный
  допускаемый скип — условное предусловие С4 (проверяемое состояние физически
  не возникло; не «всегда»).
- **Docker для docker-проектов обязателен, absence = fail, не skip**: нет
  docker-демона/образов — тест падает (testcontainers/файл-fast сам падает с
  диагнозом). Никаких env-переключателей «включи меня».
- **Класс = своё окружение**: единица окружения E2E — тестовый класс
  (класс-фикстура): подъём в `InitializeAsync`, полный teardown в
  `DisposeAsync` при любом исходе; имена всех объектов содержат новый guid
  прогона (или его hex-часть); факты внутри класса последовательны; классы
  параллельны. Мельчайшая единица (факт со своим окружением) допустима только
  как уже сложившаяся гранулярность Kafka/Valkey/S3 (§3.9), крупные общие
  контуры между классами запрещены.
- **Параллельность классов — настройками библиотеки и/или семафором ДО
  создания окружения**: `xunit.runner.json maxParallelThreads` и/или
  SemaphoreSlim-слот, захваченный до первого docker-объекта окружения
  (E2eParallelismGuard). Никакой параллельности «внутри» окружения класса.
- **Статика per-branch, рантайм per-process**: теги образов — только из имени
  ветки (`e2e-{ветка}`); всё, что процесс создаёт/пишет в рантайме —
  уникально для процесса либо read-only параллельным читателям.
- **Изоляция без блокировки соседей**: никакого глобального лока запуска,
  никакого детекта чужих контуров. Разрешён только лок ВЗАИМНОГО ИСКЛЮЧЕНИЯ
  записи в publish-каталоги статики одного worktree (файловый лок подготовки;
  разные worktree — разные ветки — независимы).
- **Arch-first для E2E-инфраструктуры**: каноны изоляции и запуска —
  `docs/e2e-isolation.md` и `docs/e2e-launch.md`; правки канонов — ПЕРВОЙ
  фазой, код зеркалит их. Правки канона запуска (`docs/runbook.md`) и строк
  запуска в `AGENTS.md` — тем же мерж-коммитом.
- **Бюджеты не меняются**: существующие таймауты (publish 10 мин, Kafka build
  120 с, retry 3 попытки) остаются. Новые ожидания — только там, где появится
  новое ожидание (лок подготовки), с явной фиксацией. Бюджеты упраздняемой
  механики (RunnerBudget 60 мин) уходят вместе с ней.
- **Чистка — own-only и по возрасту**: авто-уборка удаляет только теги
  e2e-образов своих репозиториев старше 24 ч; `docker rmi` сам отказывает на
  образах живых контейнеров — отказы игнорируются.
- Каноны проекта: .NET 10, `TreatWarningsAsErrors=true`, P/Invoke запрещён,
  комментарии русские / идентификаторы английские, образы в registry не
  кладутся, E2E-образы pg — publish на хосте (sdk-стадий в e2e-образах нет).

## 3. Целевая структура и компоненты

### 3.0. Терминология и суффикс тега

- **Ветка-суффикс тега образа** — `{ветка}`: `git rev-parse
  --abbrev-ref HEAD`, очищенная до `[a-z0-9._-]{1,32}` (существующая
  санитизация `TryGitBranch`), уникальная в пределах docker-хоста по
  git-инварианту «одна ветка — один checkout».
- **Fallback-суффикс** — если ветка не определена (git недоступен) ИЛИ HEAD
  detached: `{хэш8}` — первые 8 hex SHA256 абсолютного пути worktree.
- **Сессия подготовки (prepare-session)** — один запуск
  `dotnet run --project src/tests/PgWorker.E2ePrepare`; пишет штамп и
  обновляет per-branch теги pg-образов.
- **Процесс-сессия (test-process)** — один тестовый процесс
  (`dotnet test ...`); его рантайм-объекты (контейнеры/сети/тома по
  runId-guid, publish-каталог записи, /tmp-логи) уникальны.
- **Инвариант рантайма**: имена ВСЕХ контейнеров, сетей и томов содержат
  runId (guid окружения класса; guid ⊂ процесс — per-process уникальность
  гарантирована). Префиксы `pgw-en-/pgw-eeN-/pgw-eo-/pgw-ew-/pgw-em-`,
  `kfw-*`, `vwk-*`, `s3w-*` + `{runId}` во всех контурах.
- **E2E-проект** — тестовый проект категории E2E (`<Имя>.E2eTests`):
  долгие сценарии, каждый класс поднимает полный собственный контур.
  **Интеграционный проект** (`<Имя>.IntegrationTests`): быстрые
  контейнерные/контрактные тесты. Обе категории docker-обязательны.

### 3.1. PgWorker: per-branch теги образов + штамп свежести + лок

Файлы: `src/tests/PgWorker.E2eTests/E2e/E2eEnvironment.cs` (после переноса
§3.7), `src/tests/PgWorker.E2ePrepare/Program.cs`.

**Резолв суффикса** (`ComputeImageTagSuffix`): ветка-суффикс по §3.0
(детерминирован; хэш пути worktree из суффикса УДАЛЯЕТСЯ). Механизм передачи
тега раннеру (`PGW_E2E_TAG`/`PGW_E2E_INNER`) упраздняется вместе с раннером
(§3.8) — резолв всегда локальный.

Свойства `WorkerImage`/`NodeImage`/`SdImage` — формат
`{repo}:e2e-{ImageTagSuffix}`. **`RunnerImage` и образ `pgw-e2e-runner`
упраздняются** (§3.8): publish тестовой сборки в образ раннера, копирование
`xunit.runner.json` в publish, `docker/E2eRunner.Dockerfile` — удаляются.

**Штамп готовности** `artifacts/e2e/.prepared` — JSON `{"stampMs": <long>}`
(поле `suffix` отсутствует: тег вычислим из ветки без штампа):

- запись атомарно: временный файл `.prepared.tmp` + `File.Move(overwrite:
  true)`;
- проверка свежести (`VerifyStaticReadyOrThrowAsync`) — по `stampMs` против
  новейшего исходника + наличие ключевых per-branch образов (`pgworker`,
  `pgworker-node`; `sdgenerator` — лениво, как сегодня); иначе fail-fast с
  подсказкой подготовки (С7 — падение, не скип).

**Лок подготовки** `artifacts/e2e/.prepare.lock` (взаимное исключение ЗАПИСИ
в publish-каталоги статики одного worktree; НЕ глобальный лок запуска серий;
перезапись per-branch тега между ветками невозможна — теги различны):

- acquire: `FileStream(path, FileMode.OpenOrCreate, FileAccess.ReadWrite,
  FileShare.None)`; занят → поллинг `Task.Delay(5000)` (шаг 5 с), общий
  бюджет **10 минут**; истёк — `ApplicationException` с содержимым лок-файла;
  тест-процессы лок НЕ берут (не пишут в publish-каталоги);
- в открытый лок-файл пишется строка `pid=<PID> started=<UTC>`;
  освобождение — `finally`/`Dispose` владельца;
- держит: `PrepareStaticAssetsAsync` — от начала publish до записи штампа
  (успех) или первого фейла.

**Пересборка при живом прогоне той же ветки** — режим владельца ветки:
подготовка обновляет теги ветки; новые контейнеры живого прогона возьмут
обновлённый образ. Осознанное следствие per-branch (решение владельца).

**NOBUILD-бисект** (`PGW_TEST_E2E_NOBUILD=1`): publish-шаги пропускаются,
образы per-branch строятся из существующих `artifacts/e2e/*` (проверка штампа
не выполняется).

### 3.2. PgWorker: авто-уборка старых тегов (24 ч)

В конце УСПЕШНОЙ `PrepareStaticAssetsAsync` (после записи штампа) — уборка
тегов:

- источник: `docker images --format "{{.Repository}}:{{.Tag}}|{{.CreatedAt}}"`
  (парсинг `2006-01-02 15:04:05 -0700 MST` → UTC);
- отбор: репозиторий ∈ {`pgworker`, `pgworker-node`, `sdgenerator`} И тег
  начинается с `e2e-` И `CreatedAt` старше 24 ч от текущего UTC И тег ≠
  текущему per-branch тегу (страховка от перекоса часов);
- удаление: `docker rmi <tag>` по одному; любой неуспех (в т.ч. «image is
  being used by running container») — игнорировать;
- NEVER-список: `owns3:dev`, `minio/mc:*`, `quay.io/coreos/etcd:*`,
  `pgworker:dev`, `adminpanel:dev`, любые теги без префикса `e2e-`;
- чистая функция отбора выделена отдельно — юнит-тестируема без docker.

### 3.3. /tmp-логи статических фаз — имена per-process

Файлы: `E2eFixture.StaticPhase`, logFile-параметры статики.

- суффикс логов — `{ветка|-fallback}-{pid}` (per-process; связка с веткой —
  читаемость сортировки);
- журнал фаз: `/tmp/pgw-e2e-static-phase-{лог-суффикс}.log` (имя
  `/tmp/pgw-e2e-static-phase.log` упраздняется);
- процессы: `/tmp/pgw-e2e-static-process-{лог-суффикс}-{step}.log`, step ∈
  {`worker-e2e`, `node-wal-publish`, `node-tools-publish`, `node-e2e`,
  `sd-e2e-publish`, `sd-e2e-build`, `app-publish`} (шаг `tests-publish`
  упразднён вместе с раннер-образом);
- лог-суффикс вычисляется once-per-process; расположение `/tmp`
  сохраняется (канон e2e-launch.md).

### 3.4. Kafka/Valkey: per-branch тег, сборка once-per-process

Файлы: `src/tests/KafkaWorker.E2eTests/E2e/KafkaE2eEnvironment.cs`,
`src/tests/ValkeyWorker.E2eTests/E2e/ValkeyE2eEnvironment.cs` (после

- тег: `kafkaworker:e2e-{ветка-суффикс}` / `valkeyworker:e2e-{ветка-суффикс}`
  (резолв §3.0, корень — по маркеру `docker/KafkaWorker.Dockerfile` /
  `docker/ValkeyWorker.Dockerfile`); фиксированные теги `kafkaworker:e2e` /

- сборка once-per-process: `EnsureWorkerImageAsync` под
  `SemaphoreSlim`-гейтом + флаг готовности (образец — `StaticGate`
  PgWorker). СЕГОДНЯ билдят при КАЖДОМ StartAsync — заменить; параллельные
  классы ждут гейт;
- конкурентные тест-процессы ОДНОЙ ветки собирают один per-branch тег —
  безопасно (контент идентичен, docker build атомарно перевешивает `-t`;

- бисект `PGW_TEST_E2E_NOBUILD=1`: сборка скипается, используется

- авто-уборка §3.2 в once-точке ПОСЛЕ успешного build (репозитории
  `kafkaworker`/`valkeyworker`, теги `e2e-*`, 24 ч, текущий исключается);
- способ сборки (прод-Dockerfile, sdk-стадия в контейнере) НЕ меняется —
  фиксация в §7.

### 3.5. S3: per-branch тег, publish-каталог per-process

Файл: `src/tests/S3Worker.E2eTests/E2e/S3E2eEnvironment.cs` (после переноса).

- тег: `s3worker:e2e-{ветка-суффикс}` (per-run тег `e2e-{runId}`
  упраздняется);
- `S3WPublishDir` → АБСОЛЮТНЫЙ
  `{root}/artifacts/e2e/s3worker-{pid}-{s6}` (per-process; `s6` — 6 hex
  криптослучайных, защита от переиспользования pid);
- `dotnet publish` + `docker build` — once-per-process (гейт §3.4);

### 3.8. PgWorker E2E: хостовая модель «класс = своё окружение» (упразднение двухфазного контура)

Решение владельца (AskUserQuestion 2026-10-29, ответ дословно про «создание
каждым тестовым классом своего окружения»). Двухфазная механика с
раннер-контейнером и оркестраторным Skip (С3) упраздняется ЦЕЛИКОМ:

**Удаляются**: `E2eContour` (ClassRuns-оркестрация, `-class`-раннер,
`RunnerBudget` 60 мин, `SnapshotRunnerLogAsync`, fail-safe «Total: 0»),
образ `pgw-e2e-runner` + `docker/E2eRunner.Dockerfile` + publish тестовой
сборки (`tests-publish`, копирование `xunit.runner.json`), env
`PGW_E2E_INNER`/`PGW_E2E_TAG`/`PGW_E2E_NET`/`PGW_E2E_HOST_*`,
`AttachFromEnv`-ветки, `IsInnerRunner`, `SkipIfHostDelegated`/
`_hostDelegated`/`_hostError` (TliSwitch), скип Fact 2 при упавшем Fact 1
(С5).

**Целевая модель** (эталон — Kafka/Valkey/S3 E2E и канонизируется ими):

- **Единица окружения — тестовый класс**: класс-фикстура
  (`IAsyncLifetime`/общий хелпер окружения) в `InitializeAsync`:
  `E2eParallelismGuard.Acquire` (ДО первого docker-объекта, §3.9) → сеть
  `pgw-en-{guid}` → etcd (1|3 узла по параметрам класса) → ownS3-нода (если
  классу нужна) → per-run CA → окно портов 15100+. Факты класса
  последовательны и делят это окружение. Разным фактам нужны разные контуры —
  класс делится на два класса.
- Существующие сценарии с per-fact `await using var fx =
  E2eEnvironment.StartAsync(...)` мигрируют на класс-фикстуру механически
  (тела фактов сохраняются; параметры `slug/withS3Node/haEtcd` становятся
  параметрами класса). `E2eTliSwitchScenarios` — уже класс-фикстура, с неё
  снимается оркестрация (`OrchestrateClassAsync` → прямой подъём), `_prepareSkip`
  (С4) сохраняется.
- **Тест исполняется на хосте**: тело факта — обычный код хост-процесса;
  ассерты ходят по опубликованным динамическим хост-портам (docker
  выделяет свободные; фактическое значение — в assertions, литералов нет):
  - etcd: `WithPortBinding(..., assignRandomHostPort: true)` → тест ходит
    `http://localhost:{p}`; контейнеры (воркер, ноды) — на тот же etcd через
    `http://host.docker.internal:{p}` (env-endpoints; образец —
    `KafkaE2eEnvironment`);
  - ownS3: published динамический порт → тест `http://localhost:{p}`;
    ноды/воркер — `host.docker.internal`;
  - API воркера: published динамический порт → `https://localhost:{p}`
    (mTLS: SAN серверного серта покрывает адрес хоста; клиентские серты —
    из per-run CA, как сегодня);
  - ноды кластера (`pgw-<C>-*`): публикации троек pg/patroni/doorman из
    окна PortRange — уже канон; тест ходит `localhost:{port окна}`;
  - mc-инструмент: контейнер в сети окружения, вызовы `docker exec`
    (внутрисетевые имена) — без изменений.
  Внутрисетевые DNS-имена остаются для контейнерных потребителей (SAN
  сертов, advertise нод) — меняется только путь ТЕСТА.
- **Канон «ноль publish на хост» (e2e-isolation §2) переписывается**:
  тестовая инфраструктура публикует на хост ТОЛЬКО динамические маппинги
  (docker-выделенные свободные порты); фиксированных хост-портов нет;
  коллизий bind'ов нет (динамика + retry §3.6).
- **Сохраняются без изменений**: телеметрия teardown ДО удалений
  (`/tmp/pgw-e2e-artifacts-{guid}/`, docker-логи/inspect объединённо),
  `MarkFailed()` → стоп-режим упавшего (останавливать, не удалять;
  `README-cleanup.txt`), own-only чистка по runId/ClusterTag, АССЕРТ ЧИСТОТЫ
  после teardown, wait-стратегии готовности (поллинг, бюджет ≤ 100 с),
  `[PHASE]`/`[PHASE-TICK]`-хронометраж, `E2ePhase.WaitAsync`,
  fail-fast «provision-stuck».
- `E2eFixture`-хелперы (`RunProcessAsync` с бюджетом, `WaitForAsync`,
  `RunDockerLogsAsync`, секреты) — без изменений; `E2eProcessMergeTests`
  (механика объединённого съёма) переезжает в E2E-проект как есть.

### 3.9. Параллельность классов

- **Настройка библиотеки**: каждый E2E-проект — `xunit.runner.json`
  `maxParallelThreads: 5` (PgWorker/Kafka — уже есть; Valkey/S3 — добавить;
  сегодня у них дефолт xUnit «по числу ядер» — не канонизирован). E2E-классы
  БЕЗ `[Collection]`-атрибутов → collection-per-class → классы параллельны до
  потолка потоков. Факты внутри класса последовательны.
- **Семафор до создания окружения** (PgWorker): `E2eParallelismGuard`
  (дефолт 3 слота, env `PGW_E2E_MAX_CONTOURS`) — слот КЛАССА-окружения;
  `Acquire` в `InitializeAsync` класс-фикстуры ДО создания сети (двойная
  семантика: дроссель нагрузки и регулятор параллельности рамки B);
  `Release` в `DisposeAsync` при любом исходе. Guard per-process — по рамке
  A «чужую нагрузку не блокировать».
- Kafka/Valkey/S3 E2E — БЕЗ семафора: параллельность регулируется только
  `maxParallelThreads` (один из двух легитимных механизмов замечания
  владельца; контуры этих воркеров существенно легче PgWorker-PG-контуров).
  При выявленной перегрузке — отдельная задача, не самодеятельность.
- Не-E2E интеграционные (PgWorker): последовательная группа
  `NonE2eCollection` (`DisableParallelization=true`) — настройка библиотеки,
  сохраняется (фикстуры Etcd/PgApi/PgMetrics на коллекции). Юниты — дефолт.
- Пересечение с рамкой A: Guard и порт-окна (точки 7–8 §1.2) не меняются.

### 3.11. Раскип BackupS3Tests: скип устарел — OwnS3 уже валидирует чексумму

Проверенный факт (аудит кода OwnS3 main, `/Users/demakaev/ZCodeProject/OwnS3`):
сервер УЖЕ проверяет `x-amz-checksum-sha256` на PutObject и возвращает
**400 BadDigest** при несовпадении:

- `ParseChecksumHeader` (OwnS3/src/OwnS3.App/Handlers/OperationValidation.cs):
  алгоритмы crc32/crc32c/sha1/sha256, форматная валидация base64+длины →
  InvalidArgument; сверка значения против фактического дайджеста тела →
  BadDigest (400; HashingBodyStream.cs); чанковый режим с трейлерными
  чексуммами — тот же исход; покрыто тестами OwnS3 (юниты + сценарии через
  AWS SDK — тот же транспорт, что у pg);
- клиент pg шлёт ровно этот заголовок: `BackupS3.PutObjectAsync`
  (`src/PgWorker.Backups/BackupS3.cs`) выставляет `ChecksumSHA256`
  (канонический hex → base64 на границе). Тест
  `PutObjectBrokenShaRejectedByServer` с 64-hex-нулевым sha шлёт валидный
  base64 НЕВЕРНОГО значения → сервер 400 BadDigest → ассерт
  `put.IsSuccess == false` выполняется, тест зелёный. Оговорки канона
  OwnS3 (UploadPart не парсит заголовочные чексуммы, crc64nvme вне набора)
  на сценарий теста не влияют.

Правка в t90:

- `[Fact(Skip = "t91-owns3-checksum-verify …")]` → `[Fact]`; SKIP-блок
  комментариев над фактом удаляется; AAA-комментарий обновляется по
  текущему поведению (сервер отвергает put с неверной чексуммой — 400
  BadDigest);
- тест включается в штатный прогон `PgWorker.IntegrationTests` и ОБЯЗАН
  проходить (рамка B «ноль ложных скипов»);
- задача `t91-owns3-checksum-verify` НЕ заводится НИГДЕ — ни в
  `arch/roadmap/bugs.md` pg, ни в OwnS3: заводить нечего, валидация уже
  существует; скип был устаревшим (в `arch/roadmap` его никогда не было);
- оговорка по образу: тест поднимает контейнер `owns3:dev` (внешний образ,
  собирается `../OwnS3`). На docker-хосте нужен образ сборки OwnS3,

  вместе с раннером — не переносится.
- Fail-fast «статика не подготовлена» (С7) сохраняется: запуск E2E-проекта
  PgWorker без подготовки — пачка-фейл с подсказкой, НЕ скип и НЕ автосборка.
- Уборка образов не использует список живых контейнеров как условие;
  занятость образа разбирает сам `docker rmi` отказом.
- P/Invoke запрещён; `TreatWarningsAsErrors=true`; локально собираемые
  образы в registry не кладутся; тесты — AAA-комментарии; комментарии
  русские, идентификаторы английские.

## 6. Критерии приёмки

1. **Ноль скипов**: штатный запуск КАЖДОГО тестового проекта
   (`dotnet test <project> -c Release --no-build`) на docker-хосте —
   `Skipped: 0` (юниты, интеграционные, E2E всех четырёх воркеров).
   Единственный допускаемый скип в репозитории — условный `_prepareSkip`
   TLI (С4); `grep -rn "Assert.skip\|Skip = " src/tests` показывает только
   его.
2. **Гейтов нет**: `grep -rn "PGW_TEST_DOCKER" src/` пуст; `DockerTrait`
   отсутствует; env не упоминается в docs/ и AGENTS.md (команды — §3.7).
3. **Проекты**: `src/tests/{PgWorker,KafkaWorker,ValkeyWorker,S3Worker}.E2eTests`
   существуют в slnx; интеграционные проекты запускаются без env и без
   скипов; каждый E2E-проект имеет `xunit.runner.json` c
   `maxParallelThreads: 5`.
4. **Хостовая модель**: `E2eContour`, `pgw-e2e-runner`-образ,
   `docker/E2eRunner.Dockerfile`, `PGW_E2E_INNER`/`PGW_E2E_TAG` —
   отсутствуют; каждый PgWorker E2E-класс — класс-фикстура, поднимающая
   контур (Guard-слот → сеть → etcd → ownS3 → CA → окно портов) и полностью
   его удаляющую; тесты ходят по `localhost:{динамический порт}`;
   хост-портовых литералов в ассертах нет.
5. **Отчёт E2E**: серия E2E-проекта — `Failed: 0, Skipped: 0, Passed: N`
   (до разделения — «Skipped: N» у каждой серии); фейл сценария —
   `Failed` с хвостом телеметрии; стоп-режим и `README-cleanup.txt` — как
   раньше.
6. Подготовка PgWorker.E2ePrepare завершается успешно; в
   `artifacts/e2e/.prepared` — JSON с `stampMs`; образы `pgworker` /
   `pgworker-node` (и ленивый `sdgenerator`) несут per-branch тег
   `e2e-{ветка}` (без хэша пути, без раннер-образа).
7. Повторная подготовка той же ветки — тег ТОТ ЖЕ; подготовка другой ветки
   (другой worktree) — ДРУГОЙ тег (проверка `docker images`).
8. Конкурентные подготовки одного worktree сериализуются локом
   (интеграционный тест: держатель 3 с, второй ждёт и проходит).
9. Кейс-маркер `Scale_AddEmptyShard` зелёный на свежем Release (build →
   E2ePrepare → test `src/tests/PgWorker.E2eTests --no-build`).
10. Статические логи — `/tmp/pgw-e2e-static-phase-{ветка}-{pid}.log` и
    `/tmp/pgw-e2e-static-process-{ветка}-{pid}-*.log`; файл
    `/tmp/pgw-e2e-static-phase.log` не создаётся; параллельные процессы пишут
    в разные файлы.
11. Юнит-тесты: резолв ветка/fallback; атомарность штампа; чистая функция
    отбора уборки (24 ч, NEVER-список, исключение текущего); маска ретрая
    портов (`already allocated`, `address already in use` — в ретрай,
    прочие — нет).
12. После подготовки теги `e2e-*` старше 24 ч отсутствуют (либо rmi отказан
    живыми контейнерами); NEVER-список не тронут.
13. Серии E2E Kafka/Valkey/S3 зелёные: per-branch теги; фиксированные
    `kafkaworker:e2e`/`valkeyworker:e2e`/per-run `s3worker:e2e-{runId}` не
    используются; сборка once-per-process (один build на процесс в журнале);
    NOBUILD-прогон использует существующий per-branch тег.
14. **Параллельность**: PgWorker E2E-классы исполняются параллельно до
    `maxParallelThreads=5` при не более 3 живых контурах (Guard; слот
    захвачен до создания сети — видно по `[PHASE]`-порядку в журнале);
    интеграционные PgWorker — строго последовательно (NonE2eCollection).
15. **Раскип BackupS3Tests (С6)**: `PutObjectBrokenShaRejectedByServer`
    исполняется без скипа и ЗЕЛЁНЫЙ — сервер возвращает 400 BadDigest при
    несовпадении `x-amz-checksum-sha256` (ассерт `IsSuccess == false`);
    `grep -rn "t91-owns3-checksum-verify" arch/ src/ docs/` пуст — задача
    не заводилась, упоминаний скипа не осталось.
16. Инвариант рантайма: имена всех контейнеров/сетей/томов содержат runId;
    ассерты чистоты own-only работают; пост-серия `docker ps -a` пуст от
    своего guid.
17. Каноны docs/e2e-isolation.md, docs/e2e-launch.md, docs/runbook.md и
    строки запуска AGENTS.md отражают новое состояние (модель класса,
    проекты, команды без env); пункт `t90-e2e-session-isolation` удалён из
    `arch/roadmap/reliability.md` тем же мерж-коммитом (в
    `reliability-report.md` t90 не упоминается).

## 7. Принятые решения (закрытые развилки)

1. **Теги E2E-образов — PER-BRANCH** (решение владельца, user-review
   2026-10-29): суффикс только из имени ветки; одна ветка — один набор
   образов. Отменяет первоначальные per-запускные (PgWorker) и per-process
   (Kafka/Valkey/S3) суффиксы тегов ОБРАЗОВ.
2. **Контейнеры — PER-PROCESS** (решение владельца): guid во всех именах
   рантайма — обязательный инвариант (§3.0).
3. **Следствие per-branch принято осознанно**: пересборка статики той же
   ветки при живом прогоне обновляет образ «под ногами» — статику ветки
   контролирует владелец ветки.
4. **Fallback-суффикс**: git недоступен или HEAD detached — `{хэш8}` пути
   worktree.
5. **Конкурентные подготовки одного worktree** — файловый лок подготовки
   `artifacts/e2e/.prepare.lock` (5 с / 10 мин). ВЫБОР ПОЛЬЗОВАТЕЛЯ
   (AskUserQuestion, 2026-10-29).
6. **Конкурентные сборки одной ветки** (Kafka/Valkey/S3) — разрешены без
   лока: перезапись per-branch тега идентичным контентом безопасна; запись
   каждого процесса — в свой per-process publish-каталог (S3).
7. **Уборка тегов** — авто-уборка по возрасту 24 ч, отказы rmi
   игнорируются, текущий per-branch тег исключается. ВЫБОР ПОЛЬЗОВАТЕЛЯ
   (AskUserQuestion, 2026-10-29).
8. **Штамп .prepared** — `{"stampMs"}` без suffix; атомарная запись
   temp+move.
9. **/tmp-логи статики** — per-process имена `{ветка}-{pid}`; расположение
   `/tmp` сохраняется.
10. **Бисект-режимы** — NOBUILD везде использует существующий per-branch
    тег (отсутствие — fail-fast); фиксированные фоллбек-теги
    `kafkaworker:e2e`, `valkeyworker:e2e`, `s3worker:e2e` и per-run
    `s3worker:e2e-{runId}` упраздняются.
11. **Retry портов** — расширение маски ретрая старта окружения на
    `already allocated` / `address already in use`; FreePortWindow/зонд не
    меняются.
12. **Valkey в scope** — включён (механика идентична Kafka).
13. **Порт-окна PgWorker и E2eParallelismGuard — не меняются** (рамка A);
    Guard легитимен и как «семафор до создания окружения» рамки B.
14. **Способ сборки Kafka/Valkey-образов** (прод-Dockerfile) не
    переделывается — вне scope t90.
15. **Разделение: E2E в отдельные проекты ВСЕХ четырёх воркеров**;
    `PGW_TEST_DOCKER` упраздняется полностью; docker-обязательность
    проектов = падение без docker, не скип. ВЫБОР ПОЛЬЗОВАТЕЛЯ
    (AskUserQuestion, 2026-10-29).
16. **Двухфазный раннер-контур PgWorker упраздняется** — модель владельца:
    каждый тестовый класс сам создаёт своё окружение (guid в именах) и сам
    исполняется на хосте; раннер-образ/E2eContour/inner-env/оркестраторный
    Skip удаляются. Решение владельца (AskUserQuestion, 2026-10-29 — ответ
    владельца: «параллельный запуск тестов организуется за счёт создания
    каждым тестовым классом своего окружения»).
17. **Отчёт E2E-проекта**: Passed/Failed, `Skipped: 0` — норма; оркестраторных
    скипов больше не существует как класса (следствие 16).
18. **Гранулярность окружений**: PgWorker E2E — класс-фикстура (буква
    замечания «каждым тестовым классом»); Kafka/Valkey/S3 — существующая
    per-fact гранулярность сохраняется (мельче класса, изоляцию не
    нарушает; переделка — вне scope).
19. **Условный скип TLI `_prepareSkip` — легитимный** (не «всегда»:
    предусловие физически не наступило); скип Fact 2 при упавшем Fact 1
    упраздняется вместе с механикой раннера.
20. **Fail-fast статики (С7) — остаётся падением**: запуск E2E-проекта без
    подготовки — пачка-фейл с подсказкой; автосборка из тест-процесса не
    возвращается.
21. **Скип BackupS3Tests:493 (С6) — устаревший ЛОЖНЫЙ скип, раскип в t90**
    (коррекция 2026-10-29 по проверенному факту кода OwnS3 main: сервер уже
    валидирует `x-amz-checksum-sha256` на PutObject и возвращает 400
    BadDigest при несовпадении; прежняя посылка скипа «сервер не
    верифицирует чексумму» опровергнута — см. §3.11). Скип удаляется, тест
    включается в прогон и обязан проходить (зелёный). Задача
    `t91-owns3-checksum-verify` НЕ заводится нигде — заводить нечего.
    Прежнее решение этого пункта (завести t91 в `arch/roadmap/bugs.md` и
    раскипнуть тест в честно-красный; AskUserQuestion 2026-10-29) отменено
    проверкой: принималось на недостоверной посылке, а сам Skip ссылался на
    несуществующие пункт t91 и `arch/roadmap/owns3.md`.
22. **Параллельность**: все E2E-проекты — `maxParallelThreads: 5`
    (настройка библиотеки); PgWorker дополнительно — Guard-слот класса ДО
    создания окружения; Kafka/Valkey/S3 — без семафора (достаточно одного
    механизма по замечанию владельца); не-E2E PgWorker —
    NonE2eCollection.
23. **Общие тест-хелперы — новый общий проект инфраструктуры
    `src/tests/Shared.TestInfra`** (ВЫБОР ПОЛЬЗОВАТЕЛЯ, AskUserQuestion
    2026-10-29: «Новый общий проект инфраструктуры»): общие хелперы
    (`E2eFixture.cs`, `E2eTestPki.cs`, `FreePortWindow.cs` ×3 и т.п.),
    нужные и остающимся интеграционным проектам, и новым E2E-проектам,
    живут в ОДНОМ общем проекте; оба типа тестовых проектов используют его
    через ProjectReference (проект включается в `PgWorker.slnx`);
    namespaces переносимых файлов сохраняются.
