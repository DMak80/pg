## 1. Контекст и цель

### 1.1. Контекст

- **Трек ownS3** (`arch/roadmap/owns3.md`): собственное S3-совместимое
  объектное хранилище на C#/.NET 10 (проекты `src/OwnS3.*`). Начальный
  этап — API-грань и дисковое хранение: 22 операции, single-drive
  xl-раскладка без erasure coding, без репликации. Порядок трека: канон
  (t35) → протокол (t36) → хранение/операции (t37) → multipart (t38) →
  приёмка клиентами + dev-стенд (t39) → erasure coding (t40).
- **Документ канона заведён** — `arch/22-owns3.md`: заготовка с миссией и
  принципом «стандарт S3, а не копия MinIO»; наполнение выполняет эта
  задача.
- **Референс**: копия исходников MinIO (Go) — `../minio` рядом с репо
  (путь из `arch/roadmap/owns3.md`: `../../../minio` от файла, т.е.
  `/Users/demakaev/ZCodeProject/minio` относительно корня монорепо).
  Карта точечного референса (какие файлы MinIO отвечают за какую грань) —
  во введении трека; побайтовая совместимость форматов не требуется,
  полная копия механики не делается.
- **Целевые клиенты**: AWS SDK .NET подсистемы бэкапов (арх/19 — полные и
  WAL-бэкапы в S3, restore/verify/drill) и `mc`; оба работают path-style,
  настраиваются env-endpoint'ом и статическими ключами.
- **Соседний трек s3.md** (t31–t34) — управление MinIO-кластерами как
  объектом системы (provisioning/replication-mesh/панель); ownS3 — своя
  реализация S3-сервера, не зависит от t31–t34.
- **Прецедент структуры канона-домена**: `arch/adminpanel/` — подпапка с
  главами и короткой входной точкой в основном списке `arch/`.

### 1.2. Цель

Наполнить канон ownS3 до полноты, достаточной для реализации t36–t39 «по
канону, без досказок»:

1. `arch/22-owns3.md` — входная точка: миссия (целевая замена MinIO
   подсистемы бэкапов после t39), принципы, указатель глав.
2. `arch/owns3/01-overview.md` — обзор: место в системе, клиенты, границы
   этапа, состав проектов, durability-ограничения, таблица ключевых
   решений.
3. `arch/owns3/02-operations.md` — полный контракт 22 операций.
4. `arch/owns3/03-protocol.md` — протокол: SigV4 (заголовки/presigned/
   чанковая потоковая), XML-схемы, формат ошибок, ETag, conditional,
   Range.
5. `arch/owns3/04-storage.md` — модель xl-хранения single-drive:
   раскладка каталогов/файлов как в MinIO, собственный формат `xl.meta`,
   служебный контур `.owns3.sys`, атомарность записи, чистки.
6. `arch/owns3/05-access-config.md` — учётки (root + статические ключи,
   матрица прав), конфиг/env, порт, health/метрики, запуск в докере по
   правилам локального registry.
7. `arch/roadmap/owns3.md` — отражение: цель-замещение во введении трека;
   новые задачи «миграция данных MinIO→ownS3» и «TLS-опция S3-грани»;
   согласование формулировки t39 с правилом образов (§3.7).
8. Указатели: строка `22-owns3.md` в `arch/README.md` — ссылка на
   подпапку глав.

### 1.3. НЕ-цели (границы)

- **Не пишем код**: никаких `src/OwnS3.*`, Dockerfile, тестов, конфигов
  деплоя — только `arch/`, `arch/roadmap/`, указатели в `arch/README.md`.
  Скелеты и реализация — t36–t39.
- **Не трогаем `arch/19-backups.md`**: подсистема бэкапов остаётся
  клиенто-агностичной S3; переключение на ownS3 — после t39, не каноном
  t35. Влиять на формулировки arch/19 нельзя (расхождение проектов со
  `arch/` — блокер ревью).
- **Не каноним вне-наборные грани S3**: сабресурсы объекта
  (ACL/tagging/retention/legal-hold), конфигурации бакета
  (versioning/lifecycle/replication/encryption/…), S3-Express,
  notification, select. Канон фиксирует только поведение при обращении к
  ним (единый отказ — см. §3.4), не их семантику.
- **Не копируем MinIO**: раскладка хранения на диске — единственное, что
  берётся у MinIO сознательно (правило трека); формат `xl.meta` —
  собственный (побайтовая совместимость msgp не требуется); IAM MinIO,
  console, peer-механики, erasure sets — не берутся.
- **Не проектируем erasure coding и репликацию**: t40 и позже; глава
  хранения фиксирует расширяемость формата `xl.meta` под EC-поля, но не
  сам EC.
- **Не решаем миграцию данных** MinIO→ownS3: только задача в roadmap
  (решение пользователя 7).

## 2. Принципы

1. **arch-first**: канон — источник истины для t36–t39; каждое утверждение
   о поведении ownS3 фиксируется здесь, а не в коде или в голове
   реализатора.
2. **Критерий правильности — стандарт S3 API**: поведение, ожидаемое
   стандартными S3-клиентами (AWS SDK .NET бэкапов, `mc`). Канон
   фиксирует поведение собственными формулировками (полные контракты,
   XML-схемы, тест-векторы подписи), ссылаясь на S3 API Reference и
   референс MinIO только как на справку.
3. **MinIO — точечный референс, не образец**: для каждого решения глава
   указывает (если уместно) файл референса `../minio`, подтверждающий
   жизнеспособность подхода; перенос механики целиком не делается.
4. **Раскладка хранения — механика MinIO, имена — собственные**: бакеты —
   каталоги первого уровня; объект — каталог с `xl.meta` +
   `<dataDir-uuid>/part.N`; служебный контур — **`.owns3.sys`**
   (`format-тома`, `tmp/`, `multipart/`, `.trash/`, `buckets/`, `config/`).
   Иерархия и смысл раскладки — по референсу MinIO (обзор каталога тома
   глазами узнаваем), но имена служебных сущностей задаёт канон ownS3
   сам (решение пользователя 8): контур — `.owns3.sys`, файл формата
   тома — `volume.json` (референс MinIO — `format.json`);
   `xl.meta`, `part.N`, `uploads.json`,
   sha256-путь multipart — уже канонизированы треком. Содержимое
   `xl.meta` — собственный бинарный формат с версионированием.
5. **Надёжность = атомарный rename-коммит**: объект виден клиентам только
   целиком; запись — во временный каталог с последующим атомарным
   rename; сбои оставляют мусор только в `tmp/`/`.trash/`, который чистится
   стартом и фоново (правило multi-host: локальный диск — без гарантий
   durability, гарантии строятся выше — ограничение этапа фиксируется
   явно, см. §3.2 п. 6).
6. **Path-style only, HTTP-only** (решения пользователя 3, 6): роутинг и
   подписи не несут веток virtual-host; TLS — roadmap-задача.
7. **Язык и стиль**: документация по-русски, идентификаторы/имена
   операций/заголовков — английские; стиль и структура — как у соседних
   канонов `arch/` (таблицы решений, ASCII-схемы, §-нумерация).

### 3.2. `arch/owns3/01-overview.md` — обзор и структура решения

1. **Место в системе**: диаграмма «клиенты → ownS3 (докер-контейнер, том
   данных)»; клиенты — подсистема бэкапов (write: воркер/джобы, read:
   restore/verify/drill), `mc` (операции), связь с arch/19 (клиент
   остаётся S3-агностичным); отношение к MinIO (целевая замена после t39,
   трек s3.md — параллельный на переходный период; переключение клиентов —
   env-endpoint, без изменений кода клиентов).
2. **Границы начального этапа**: 22 операции; бакеты без versioning
   (ListObjectVersions — unversioned-семантика); single-drive без EC и
   репликации; перечень вне-наборных граний с единым поведением отказа
   (см. §3.4). Ссылка на трек для последующих этапов.
3. **Состав решения**: три проекта + тесты:
   - `src/OwnS3.Protocol` — чистые типы протокола: канонизация/проверка
     SigV4 (заголовочная, presigned, чанковая потоковая), XML-схемы
     запросов/ответов, формат S3-ошибок, ETag-семантика. Без ASP.NET и
     диска.
   - `src/OwnS3.Storage` — xl-модель хранения: раскладка каталогов,
     чтение/запись `xl.meta`, `.owns3.sys`, атомарный коммит, multipart
     на диске, чистки. Без HTTP.
   - `src/OwnS3.App` — хост Kestrel: роутинг 22 операций, хендлеры,
     конфиг/env (`OwnS3:*` / `OWNS3_*`), health/метрики (по канону
     [`arch/18-metrics.md`](../../18-metrics.md), каркас `Shared.Metrics`),
     стыковка Protocol×Storage.
   - `src/tests/OwnS3.UnitTests`, `src/tests/OwnS3.IntegrationTests` —
     юниты (тест-векторы подписи, XML) и контурные тесты.
   Зависимости: `Protocol` и `Storage` не зависят от `App`; `App` — от
   обоих; общие библиотеки (`Shared.*`) — по мере надобности.
4. **Таблица ключевых решений и почему**: path-style only; HTTP-only;
   собственный `xl.meta`; root + статические ключи; xl-раскладка MinIO;
   три проекта; каждая строка — критерий «стандарт S3 / простота /
   референс MinIO».
5. **Запуск**: всегда в докере (никогда хост-процессом — как PgWorker);
   том данных — единственный persistent-volume; env-секреты (root,
   ключи) из env-файла по образцу `deploy/.env.example` воркеров (сам
   env-шаблон ownS3 создаётся в t39);
   dev-стенд-сервис и E2E-образ — правила: сборка .NET на хосте, в образ
   упаковываются только артефакты publish (правило E2E-образов AGENTS.md),
   локально собираемый образ в registry не кладётся; базовый
   runtime-образ — из существующих `images.txt` (новых внешних образов
   нет). Детальная модель стенда — t39; здесь — только правила образа.
6. **Durability и отказы (вопрос «что теряется при отключении машины X»)**:
   single-drive том — отказ диска/машины = потеря всех данных ownS3 на
   нём (бэкапы MinIO-контура недоступны на время отказа, если ownS3 уже
   обслуживает бэкапы); осознанное ограничение начального этапа; путь
   митигации — t40 (erasure coding) и последующие задачи (репликация);
   локальный том — единственная копия, гарантий durability нет.

### 3.3. `arch/owns3/02-operations.md` — контракт 22 операций

Формат контракта каждой операции (единый шаблон):

- Назначение (1–2 предложения) и референс-хендлер MinIO (файл).
- HTTP: метод, URI path-style (`/{bucket}`, `/{bucket}/{key+}`),
  обязательные/опциональные query-параметры (вкл. `list-type=2`,
  `partNumber`, `uploadId`, `max-keys`, `continuation-token`, `marker`,
  `prefix`, `delimiter`, `encoding-type`).
- Заголовки запроса: специфичные (`Content-MD5`, `x-amz-*`,
  conditional-заголовки, `x-amz-copy-source`, `x-amz-metadata-directive`,
  `x-amz-storage-class` — игнорируется с фиксацией поведения).
- Тело запроса: есть/нет; XML-схема, если есть (DeleteObjects,
  CompleteMultipartUpload).
- Успех: код, заголовки ответа (`ETag`, `Last-Modified`,
  `x-amz-*`, `Content-Range`), тело/XML-схема ответа.
- Ошибки: специфичные коды S3 и условия их возникновения (по общему
  формату ошибок — глава 03).
- Семантика: атомарность/идемпотентность, ETag-правило, conditional
  поведение, видимость в листингах.

Состав (22, группами):

1. **Объекты**: PutObject, GetObject, HeadObject, DeleteObject,
   DeleteObjects (multi-delete XML), CopyObject (внутренняя копия;
   `x-amz-copy-source`; copy-условия), GetObjectAttributes
   (response-expires/ETag/и атрибуты `x-amz-object-attributes`).
2. **Листинги**: ListObjects (v1: marker), ListObjectsV2
   (continuation-token, start-after, owner), ListObjectVersions
   (unversioned: возвращает текущие версии, без delete markers и
   `VersionId`-полей). Общая семантика: лексикографический порядок ключей,
   `MaxKeys`, `IsTruncated`, common prefixes по `delimiter`,
   `EncodingType=url`.
3. **Бакеты**: CreateBucket (семантика существования/регион-игнор),
   DeleteBucket (только пустой), HeadBucket, ListBuckets,
   GetBucketLocation (фиксированное значение — фиксируется).
4. **Multipart**: CreateMultipartUpload (uploadId — формат фиксируется),
   UploadPart, UploadPartCopy, CompleteMultipartUpload (XML манифест,
   составной ETag `<N>-<md5-all-etag'ов>`, порядок частей, минимум 1
   часть), AbortMultipartUpload, ListParts, ListMultipartUploads.

Общие семантические разделы главы: ETag-правила (MD5 простого PUT;
составной multipart; отсутствие ETag у CopyObject-ответа — заголовок
возвращается, семантика по стандарту); conditional-запросы
(`If-Match`/`If-None-Match`/`If-Modified-Since`/
`If-Unmodified-Since`, комбинации, приоритет, 304/412); Range
(`bytes=`, суффиксный, множественный — поведение фиксируется,
`If-Range`, 206/416); поведение при обращении к вне-наборным сабресурсам
и конфигурациям бакета — единый канонизированный отказ: код и сообщение
фиксируются здесь, формат — глава 03 (база: S3-стандарт
`NotImplemented`/`501`, точное поведение — по референсу MinIO, сверка со
стандартом при написании главы); идемпотентность DeleteObject
(отсутствующий ключ = успех).

### 3.4. `arch/owns3/03-protocol.md` — протокол

1. **SigV4 (заголовочная подпись)**: canonical request (метод, path-style
   URI, canonical query, canonical headers, `x-amz-content-sha256`),
   string-to-sign, signing key (деривация `AWS4-HMAC-SHA256`), обязательные
   заголовки (`x-amz-date`, `Host`), допуск clock skew (15 мин — по
   стандарту), значения `x-amz-content-sha256`: hex-SHA256,
   `UNSIGNED-PAYLOAD`, `STREAMING-AWS4-HMAC-SHA256-PAYLOAD`;
   анонимный запрос → AccessDenied (public-доступа нет).
2. **Presigned URL**: `X-Amz-Algorithm/-Credential/-Date/-Expires/-
   Signature` в query, подпись без тела (UNSIGNED-PAYLOAD), максимальный
   срок (7 дней), какие операции разрешены через presigned (фиксируется:
   GET/PUT/DELETE и части multipart — ровно что нужно клиентам бэкапов).
3. **Чанковая потоковая подпись**
   (`STREAMING-AWS4-HMAC-SHA256-PAYLOAD`): фрейминг `aws-chunked`
   (hex-размер чанка, chunk-заголовки `;chunk-signature=`, финальный
   `0;chunk-signature=…`, trailers `x-amz-trailer`,
   `StreamBody-…`-вариант не поддерживается — фиксируется),
   `x-amz-decoded-content-length`, цепочка подписей (seed signature →
   chunk N), сверка и отказ на разрыв цепочки.
4. **XML-схемы**: namespace S3 (`xmlns="http://s3.amazonaws.com/doc/2006-03-01/"`),
   элементы всех XML-ответов (листинги v1/V2/versions, multipart
   listings, DeleteResult, CompleteMultipartUploadResult,
   LocationConstraint, ListAllMyBucketsResult), кодирование спецсимволов;
   запросные XML (Delete, Complete-манифест): валидация и ошибки
   MalformedXML.
5. **Формат ошибок**: канонический XML
   (`Error/Code/Message/Resource/RequestId/HostId`), маппинг внутренних
   сбоев на S3-коды (NoSuchBucket/NoSuchKey/BucketAlreadyExists/
   BucketNotEmpty/InvalidRange/PreconditionFailed/…
   EntityTooLarge/InvalidPart/InvalidPartOrder/MalformedXML/
   AuthorizationHeaderMalformed/SignatureDoesNotMatch/AccessDenied/
   NoSuchUpload/InternalError), `RequestId` — генерация и лог.
6. **Транспорт и стиль**: path-style only (virtual-host host-header →
   фиксируется: обработка как обычный host, бакет из пути; явная опора на
   path-style в подписи), HTTP/1.1 (+HTTP/2 при Kestrel — фиксируется
   поведение), лимиты (макс. размер ключа 1024 байта, бакет 3–63 символа —
   правила имён из стандарта), `Expect: 100-continue`.

### 3.5. `arch/owns3/04-storage.md` — xl-хранение single-drive

1. **Раскладка тома** (механика MinIO single-drive, имена служебного
   контура — собственные, решение пользователя 8):

   ```
   <том>/
   ├── .owns3.sys/
   │   ├── volume.json                ← формат/идентификация тома (см. п. 3)
   │   ├── tmp/                       ← staging записи (tmp-префикс guid)
   │   ├── multipart/<sha256(bucket/object)>/<uploadID>/   ← части multipart + uploads.json
   │   ├── .trash/                    ← отложенное удаление (rename вместо rm)
   │   ├── buckets/<bucket>/          ← служебные метаданные бакета
   │   └── config/                    ← конфиг и ключи (глава 05)
   ├── <bucket>/                      ← бакеты — каталоги первого уровня
   │   └── <путь объекта (кодированный)>/
   │       ├── xl.meta                ← метаданные объекта
   │       └── <dataDir-uuid>/part.1  ← данные (одна часть для простого PUT)
   ```

   Имена: `dataDir` — uuid; части — `part.N` с N с 1; кодирование имён
   объектов в имена каталогов (спецсимволы, слэши, ограничение длины
   пути — схема кодирования фиксируется по образцу MinIO
   `encodeDirObject`).
2. **Формат `xl.meta` — собственный бинарный формат по образцу MinIO
   xl-meta-v2**: header (magic + версия формата) + записи-версии
   (версионирование формата для будущих EC-полей); поля записи: version
   id (uuid), размер, modTime, metadata (content-type, user-metadata,
   etag и пр.), checksum данных (алгоритм фиксируется — CRC32C или
   SHA-256, сверка при чтении — фиксируется), зарезервированная
   расширяемость (Erasure-поля — версия формата t40). НЕ msgp, побайтовая
   совместимость с MinIO не требуется. Запись: `xl.meta` →
   `xl.meta.bkp` → новый файл + rename (по образцу MinIO).
3. **`volume.json` тома** (собственное имя формата тома; референс —
   `format.json` у MinIO): идентификация тома (uuid), версия формата,
   single-drive (XL Single) — момент проверки при старте: чужой/битый
   формат — отказ старта с диагностикой (по образцу MinIO
   `format-erasure.go`, xl-single).
4. **Жизненный цикл записи**: данные → `.owns3.sys/tmp/<guid>/…` →
   fsync → атомарный rename в целевой каталог объекта (коммит);
   перезапись существующего объекта — новый dataDir-uuid, старый
   каталог-данных в `.trash/`; delete — rename в `.trash/`; видимость:
   объект появляется в Get/List только после rename.
5. **Multipart на диске**: `.owns3.sys/multipart/<sha256(bucket/object)>/
   <uploadID>/xl.meta` + `part.N`; журнал активных загрузок
   `uploads.json` (список uploadID + initiation-время); Complete —
   сборка rename'ами частей в целевой объект + составной ETag; Abort и
   чистка брошенных загрузок по возрасту (порог фиксируется).
6. **Восстановление и чистки**: старт — проверка volume.json, подчистка
   остатков tmp (всё содержимое tmp можно удалять), чистка `.trash/`
   (порог возраста); листинг каталогов после сбоя (мусор в tmp/trash не
   виден клиентам по построению).
7. **Согласованность**: read-after-write коммита (rename на одной
   ФС атомарен); листинги читают каталоги — согласованы с коммитами;
   без versioning: перезапись атомарно заменяет видимые данные.

### 3.6. `arch/owns3/05-access-config.md` — учётки, конфиг, эксплуатация

1. **Root-учётка**: env `OWNS3_ROOT_USER`/`OWNS3_ROOT_PASSWORD` (мин.
   длина — фиксируется); полный доступ (admin).
2. **Статические access keys**: список в конфиге (env или файл —
   фиксируется): `accessKey`, `secretKey`, право — `read-only` /
   `read-write` / `admin`; хранение в `.owns3.sys/config/` (появляются при
   первом старте/изменении конфига); secret в файле тома — допускается
   (том локальный; фиксируется явно с комментарием о границах).
3. **Матрица прав**: read-only → Get/Head/List* (объекты, бакеты),
   GetBucketLocation, ListMultipartUploads/ListParts (чужие загрузки —
   нет); read-write → + Put/Delete/DeleteObjects/Copy/GetObjectAttributes
   и полный multipart-цикл; admin → + Create/Delete/Head/ListBuckets.
   Отказ — AccessDenied в формате ошибок главы 03.
4. **Конфиг/env**: `OWNS3_*` (`OWNS3_SERVER_PORT` — дефолт 9000,
   S3-конвенция; `OWNS3_DATA_DIR` — путь тома; `OWNS3_ROOT_*`;
   статические ключи), секция `OwnS3:*` appsettings; список полный —
   таблицей env → назначение → дефолт.
5. **Health/метрики**: `/healthz` (liveness: том смонтирован, volume.json
   валиден); Prometheus-метрики по канону arch/18 (базовые счётчики
   операций/ошибок — состав фиксируется минимальный).
6. **Запуск в докере**: образ — сборка .NET на хосте + runtime-слой с
   COPY publish-вывода (правило E2E-образов; прод-Dockerfile поставки —
   отдельный процесс, не канон t35); том данных — bind/volume на
   `OWNS3_DATA_DIR`; env-секреты через env-файл (шаблон `.env.example`
   по образцу deploy воркеров — файл создаётся в t39, канон фиксирует
   состав); локально собираемый образ в registry 192.168.0.1:5000 НЕ
   кладётся; базовый образ — из существующих images.txt.

## 5. Ограничения и риски

| Риск | Митигация |
|---|---|
| Канон устареет относительно стандарта (S3 API широк) | Критерий — не «весь стандарт», а 22 операции глазами двух целевых клиентов; остальные грани — единый канонизированный отказ; приёмка t39 реальными клиентами закрывает разрыв |
| Объём главы операций (22 полных контракта) — самый большой документ arch/ | Шаблон контракта един (§3.3); групповые общие семантики вынесены в разделы главы, не дублируются в каждой операции |
| Отступление от поведения MinIO там, где клиенты неявно полагаются на MinIO-специфику | Сверка каждой неочевидной семантики с референс-хендлером (карта трека) и стандартом S3; расхождение фиксируется в таблице решений главы 01 |
| Собственный xl.meta — риск несовместимости с будущим t40 (EC-поля) | Версионирование формата + зарезервированная расширяемость записи (§3.5 п. 2) |
| Мульти-хост-правила AGENTS.md vs single-drive без durability | Глава 01 фиксирует ограничение явно («что теряется при отказе машины») и путь митигации (t40+); спека не скрывает ограничение |
| Имена MinIO-происхождения просачиваются в контракт служебного контура | Принцип собственных имён (решение 8) в принципах и критериях приёмки; канонизированные треком имена (`xl.meta`, `part.N`, `uploads.json`) — осознанный список; ревью сверяет отсутствие прочих имён из MinIO |
| Новые roadmap-задачи (t41/t42) конфликтуют с нумерацией треков | Номера — следующие свободные после t40 в файле трека owns3.md; зависимость только от t39 |
| Пересечение с треком s3.md (MinIO-кластера) | Граница зафиксирована: s3-трек управляет MinIO-нодами, ownS3-трек — собственный сервис; введение трека и глава 01 проговаривают переходный период |
