# Спецификация: pgworker-adopt-repair — хозяин кластера: усыновление, резолв мастера, репарация брошенных переездов

Дата: 2026-08-31. Фаза dev-flow: spec. Источники: `arch/14-pgworker.md`
(канон — обновлён этой задачей: §2.4 `object`-поле portalloc, §5 C границы
усыновлённых нод, §5 F цепочка резолва мастера + advertised-правило,
§5 J AdoptionProcess, §5 K MoveRepairProcess, §8 пороги, §9 R8–R10),
`arch/adminpanel/03-panels.md` §4 (каталог алертов: `move-stale` 600 c /
`move-frozen-long` 60 c / `move-aborting`), `arch/11-bucket-sharding.md`
§2 (семантика статус-ключей), диагностика живого стенда (2026-08-31:
заявка `/pgworker/moves/demo/bucket_13` — 120 неудач/10 мин «мастер 's2'
не определён» при живом HA-контуре; сид-аномалии bucket_3/7/11 алертятся
вечно).

Архитектурная директива пользователя (неприкосновенна): **PgWorker отвечает
за кластер ЦЕЛИКОМ; «не наших» объектов не существует.** Статус-ключи
`/clusters/<C>/buckets/status/*` — домен воркера: даже нахераченное извне
состояние он обязан привести к согласованному — вся информация у него есть
(живой HA-контур `/service/<C>-<X>/…` + docker-сокет). Панель показывает
правду: алерт = реальная проблема, гашение = реальный ремонт.

---

## 1. Цель

Закрыть две дыры самодостаточности воркера и доказать их e2e на стенде:

- **A. Резолв мастера с усыновлением.** Сегодня `ShardEndpoints.ResolveMasterAsync`
  (`src/PgWorker.Provisioning/Endpoints/ShardEndpoints.cs:59`) резолвит мастера
  только среди нод из `/pgworker/portalloc/<C>`; portalloc пишут исключительно
  процессы собственного провижининга (`ProvisioningProcess`/`AddShardProcess`/
  `RemoveShardProcess`). Для Active-кластера с `dsn`-шардами без portalloc
  (потерян / кластер поднят извне — сид, стенд, restore etcd) ВСЕ SQL-пути
  (moves, эвакуация, ротация, инвентаризация) получают `null` и вечный
  transient. Решение: **усыновление** — восстановление адресов нод из
  HA-контура + docker-инспекции с **персистентной записью в portalloc**
  (решение пользователя: «воркер — хозяин, выбор — запись в portalloc»),
  плюс усиление цепочки резолва мастера (leader HA-контура как фоллбэк) и
  advertised-правило для подписок на внешних приёмниках.
- **B. Репарация брошенных статусов переездов.** Сегодня воркер видит только
  заявки `/pgworker/moves/*`; статус-ключ без заявки для него невидим —
  брошенные `SYNCING`/`ABORTING`/`FROZEN` (упавший инстанс, внешняя правка,
  протухший скриптовый след) алертятся панелью вечно. Решение: reconcile
  **MoveRepairProcess** — статус без живого владельца (нет заявки,
  `updated_unix` постарел) закрывается синтетической заявкой в существующий
  MoveProcess (механика доведения/журналов/идемпотентности переиспользуется
  1:1), с отдельным быстрым порогом для `FROZEN` (решение пользователя:
  заморозка режет запись — чиним быстрее).
- **C. E2e на стенде.** Чек сам «нахерачивает» аномальные ключи извне и
  доказывает: за N тиков воркер приводит кластер в согласованное состояние,
  алерты панели гаснут реальным ремонтом; полный move-цикл выполняется на
  усыновлённом кластере (решение пользователя: «полный move на стенде»).
  Стенд перестаёт иметь вечные сид-алерты: **сид чистый, чек нахерачивает
  сам** (решение пользователя).

Зачем: без этого воркер — не хозяин: живой кластер с потерянным portalloc
неремонтируем, брошенные статусы — вечные ложные алерты, а стенд системно
приучает оператора к «красному шуму».

## 2. Принципы

1. **«Не наших» объектов не существует** — воркер хозяин всего в `/clusters/`;
   адреса восстанавливаются и закрепляются (portalloc), декларация следует
   за фактом (`nodes/<n>/state=RUNNING` для найденных нод).
2. **Переиспользование машин состояний.** Репарация НЕ дублирует механику
   уборки/доведения: она диспатчит синтетические заявки (`requested_by=
   "pgworker-repair"`, put-if-absent `version==0`) в существующий
   MoveProcess/AbortSequence — журналы P7, идемпотентность, takeover,
   observe-способность оператора бесплатны.
3. **Пороги синхронизированы с панелью.** `RepairStaleSec=600` =
   `StaleMoveSeconds` панели: ремонт стартует, когда панель уже заалертила
   (алерт загорелся → ремонт пошёл → алерт погас). `RepairFrozenSec=120` =
   `AbortMinAgeSec`: живой cutover — непрерывный блок одного тика, межтиковое
   `FROZEN` аномалия по определению; 120 c — достаточная защита от тика,
   который сейчас пишет.
4. **Живой владелец неприкосновенен.** Статус со свежим `updated_unix` или с
   живой заявкой — домен MoveProcess; репаратор трогает только брошенное.
   Age считается от `updated_unix` (M3 тикает им каждый тик, Д12).
5. **Положительное docker-свидетельство для усыновления.** Adoption идёт
   только когда контейнеры нод реально найдены на docker-хостах воркера;
   ноль находок — тихий skip (кластер живёт вне нашего docker-домена).
6. **Arch-first.** Контракт `arch/14-pgworker.md` обновлён до кода (см. выше);
   код ниже — отражение контракта.
7. Язык: документация русская, идентификаторы английские (базовые правила).

## 3. Структура / компоненты

### 3.1. Docker-инспекция нод (механика восстановления адресов)

Расширение `IDockerEngine`/`PlainClusterDriver` (новый метод, образец —
существующий `ListContainersAsync` + `BusyPortsAsync`; `ContainerDto.Ports`
уже парсится в `src/PgWorker.Docker/Engine/DockerEngine.cs`):

- `InspectNodesAsync(hosts, nodeNames)`: по каждому хосту из `Docker:Hosts` —
  `GET /containers/json` → кандидаты → `GET /containers/<id>/json` для
  hostname/aliases/env. Контейнер опознаётся как **нода**, если его hostname
  ИЛИ сетевой алиас равен имени ноды; контейнер опознаётся как **Patroni-сайдкар
  ноды**, если `env NODE_NAME` равен имени ноды (паттерн стендовых
  эмуляторов `hc*`). Порты ноды = public-биндинги: `5432/tcp → pg`,
  `8008/tcp → patroni` (в контейнере ноды или сайдкаре), `6432/tcp → doorman`
  (отсутствует → `0`). Канонические контейнеры `pgw-<C>-<X>-<n>` матчатся той
  же механикой (их hostname = имя ноды).
- Неоднозначность (несколько контейнеров на одно имя ноды) → нода пропускается
  (безопасный отказ, journal-запись).

### 3.2. AdoptionProcess — усыновление (arch/14 §5 J, AD0–AD4)

Новый процесс `src/PgWorker.Provisioning/Processes/AdoptionProcess.cs`
(тиковый, как AddShardProcess; реиспользует `AppSecretEnsurer`,
`DatabaseProvisioner`-механику ролей, `IAppParamsEnsurer`):

- **AD0**: клэйм-гвард; journal `op=adopt`.
- **AD1**: кандидаты — шарды с `dsn`, чьи ноды (по HA-контуру
  `/service/<C>-<X>/members/*`) отсутствуют в portalloc. Имена нод — из
  members; адреса — docker-инспекция (§3.1). Найдено 0 контейнеров по всему
  кластеру → тихий skip (не наш docker-домен).
- **AD2**: portalloc merge — read-modify-write **под клэймом** (паттерн
  remove-shard S3), только отсутствующие записи `"<X>/<n>"`:
  `{"host":"<docker-хост находки>","pg":…,"patroni":…,"doorman":…,"object":
  "<имя контейнера>"}`. Существующие записи не перезаписываются. `object`
  отсутствует у канонических нод (обратная совместимость парсера
  `Portalloc.Parse`).
- **AD3**: `nodes/<n>/state=RUNNING` put-if-absent для найденных нод (шард с
  `dsn` уже зарегистрирован — надзорные границы t06 не задеты); ensure
  app-секрета (P1.5); ensure ролей БД на мастере каждого шарда
  (`app`/`bucket_admin`/`bucket_mover`, идемпотентный P2.3-паттерн —
  нужен для префлайтов M0 и грантов переезда); ensure `app_params` (P2.5').
- **AD4**: снапшот P12 (точка изменения); journal `phase=done`. Повторные
  тики — no-op.

Интеграция: `ReconcileLoop` Active-ветка — **после** `supervise`, **до**
`scale-shards`: `supervise → adopt → scale → rotate → repair → evacuate →
moves`. Первый тик надзора для не-усыновлённого кластера остаётся пустым
(topology пустая — «внешних нет» ещё не проверено); со следующего тика —
обычный надзор с границами §3.4.

### 3.3. Резолв мастера (ShardEndpoints) — цепочка + advertised-правило

- `ResolveMasterAsync` получает шаг (2): после промаха по master-ключу —
  `/service/<scope>/leader` → имя лидера → адрес ноды из portalloc (живое
  чтение etcd; работает при протухшем master-ключе в окне failover и для
  усыновлённых шардов без Patroni-REST). Порядок: master-ключ (byName →
  byHostPort) → **service/leader** → Patroni-REST `/cluster` (по нодам с
  `patroni≠0`).
- **Advertised-правило** (все вызовы `MoverConninfo`: M2 — подписка на
  приёмнике move, M5/rollback — `sub_rb` на бывшем источнике): подмена
  `AdvertisedPublisherHost` применяется только когда **контейнер-исполнитель
  подписки** — каноническая нода (запись portalloc этой ноды без `object`);
  внешний исполнитель (запись с `object`, например контейнер стендового
  кластера в compose-сети) получает адреса dsn-ключа как есть — подмена
  `host.docker.internal` сломала бы подключение (порт 5432 хоста никем не
  опубликован).
- `ExecNodeAsync` (docker-exec для `pg_dump`, M1): если канонический
  `pgw-<C>-<X>-<n>` не найден — exec в контейнер из `object`-поля portalloc
  (у стендовых `postgres:18` есть `pg_dump` и `su postgres`); вызовы M1
  передают адрес/объект мастера из portalloc.

### 3.4. Границы надзора для усыновлённых нод (arch/14 §5 C)

`NodeSupervisor`:

- **Живость**: Patroni-REST как сегодня; при `patroni=0` — SQL-проба
  (`SELECT 1` по admin-DSN ноды): положительное свидетельство живости PG
  ( Patroni-сайдкар мёртв ≠ PG мёртв — иначе чек 30-failover получал бы
  ложные rebuild-циклы).
- **Сверка декларации**: для усыновлённых нод (`Object != null`) не
  применяется вовсе — их контейнер вне docker-домена `pgw-<C>-`
  (ListNodeObjectsAsync отдаёт только канонические имена): живой
  object-контейнер = «нода на месте» (skip), мёртвый не rebuild'ится
  (второй Patroni на тот же scope, R9); матчинг по имени `pgw-<C>-<X>-<n>` —
  только для канонических нод.
- **Self-healing off**: recreate/rebuild/TO_RECREATE — только для канонических
  нод (`object` отсутствует): rebuild усыновлённой поднял бы второй Patroni
  на тот же scope (R9). Мёртвая усыновлённая → `UNREACHABLE` + journal
  (реальная проблема, разбор оператором); эвакуация — по общим правилам.
- **MasterKeyReconciler skip** для шардов, у которых хоть одна нода с
  `object` (R8): их master-ключ пишет внешний HA-контур (эмулятор/
  Patroni-callback) в своём формате `node:port`; резолв мастера понимает
  оба формата, reconciler не воюет с писателем.

### 3.5. MoveRepairProcess — репарация (arch/14 §5 K, MR0–MR3)

Новый процесс `src/PgWorker.Moves/Process/MoveRepairProcess.cs`
(тиковый; клэйм-гвард как у MoveProcess):

- **Модель**: `BucketRoute` (Core.Domain) расширяется полем
  `MoveUpdatedUnix` (парсер снапшота читает `updated_unix` статус-ключа) —
  возраст без дополнительных чтений etcd.
- **MR1-классификация** (только Active-кластеры; `NOT_INITIALIZED`-статусы —
  домен P3, не трогаем). Для каждого статуса `bucket_<i>` БЕЗ заявки
  `/pgworker/moves/<C>/bucket_<i>` (живое чтение префикса) и с возрастом
  `now − updated_unix` > порога состояния:

  | Состояние × routing | Возраст > | Синтетическая заявка |
  |---|---|---|
  | `ABORTING/*` | `RepairStaleSec` | `{"op":"abort"}` — resuming-доводка уборки |
  | `SYNCING/*`, routing==owner | `RepairStaleSec` | `{"op":"abort"}` — свежесть пройдёт сама (600 > AbortMinAgeSec=120) |
  | `SYNCING`, routing==target | `RepairStaleSec` | `{"op":"abort","force":true}` — flip прошёл, статус завис: доведение перевода (без force это permanent-отказ — цикл) |
  | `FROZEN`, routing==target | `RepairFrozenSec` | `{"op":"abort","force":true}` — то же для замороженного недоведения |
  | `FROZEN/*`, routing==owner | `RepairFrozenSec` | `{"op":"abort"}` — уборка артефактов + re-GRANT = разморозка владельца |
  | `phase=rollback-post-flip` | `RepairFrozenSec` | `{"op":"rollback"}` — доведение отката по живой `sub_<b>_rb` (§5 F rollback-исключение) |

  Все заявки: `requested_by="pgworker-repair"`, put-if-absent (txn
  `version==0` — операторская заявка не затирается).
- **MR2**: дальше работает MoveProcess (старейшая заявка тика) — существующая
  механика доведения, журналы, снапшоты, идемпотентность.
- **MR3**: journal `op=repair` (какие статусы диспатчены); повторный тик —
  no-op (заявка уже стоит).
- **Fail-state НЕ вводится** (нового состояния в формате статус-ключа нет —
  формат скриптов 1:1, Д6): недоступный шард честно висит в
  `ABORTING/blocked` (P7) — панель алертит реальную проблему. Это и есть
  «перевести в fail-state» из постановки: фаза/журнал уже несут семантику.

### 3.6. Стенд (dev-stand/adminpanel)

- **`seed.sh`**: убрать посев аномалий `bucket_3`/`bucket_7`/`bucket_11`
  (статусы) и заявки `bucket_13` — стенд поднимается согласованно; сид
  остаётся ответственным за «нормальный» контроль-плейн (config/shards/
  routing/HA-DCS/nodes-IP).
- **`checks/20-alerts.sh`** переписывается (существующие shard-no-master
  Assert/Act 2–5 сохраняются):
  1. *Act 1*: чек сам нахерачивает три статуса с протухшим `updated_unix`
     (`now−3600`): `bucket_3 SYNCING/copy`, `bucket_7 ABORTING/cleanup
     last_error="receiver went away"`, `bucket_11 FROZEN/cutover-wait`.
  2. *Assert 2*: алерты появились (`move-stale` ×3, `move-aborting`,
     `move-frozen-long` critical) ≤2 тиков панели.
  3. *Assert 3*: алерты погасли за ≤ N тиков воркера (бюджет чека ~120 c:
     пороги уже истекли в момент нахерачивания) — гашение = ключи статусов
     удалены (= ACTIVE), routing не изменился.
  4. *Act/Assert 4 (полный move на усыновленном кластере)*: заявка
     `move bucket_5 s2→s1` → ждём `routing=bucket_5:s1` + статус ACTIVE
     (auto-finalize дочистил) → заявка `move bucket_5 s1→s2` → ждём
     `routing:s2` (возврат раскладки — чек 40 рассчитывает на инвентарь 8+5).
  5. *Assert 5*: `etcdctl get /pgworker/portalloc/demo` — записи усыновления
     на месте (4 ноды, `object: as-*`); в конце — ни одного `move-*` алерта.
- Чеки 30-failover/40-live-probes не меняются: после 20-го раскладка и
  инвентарь исходные (два полных move возвращают состояние).

## 4. Фазы

1. **Контракт** (эта фаза): arch/14 обновлён; отражение в коде описано здесь.
2. **Docker-инспекция + AdoptionProcess**: `InspectNodesAsync`, portalloc
   merge с `object`, nodes-ключи, ensure секретов/ролей/app_params,
   интеграция в ReconcileLoop (Active: supervise → **adopt** → …).
3. **Резолв-цепочка + advertised + exec-fallback**: шаг `service/leader` в
   `ResolveMasterAsync`; advertised-правило в `MoverConninfo`-вызовах;
   `ExecNodeAsync` по `object`. Границы надзора §3.4 (живость SQL,
   object-матчинг, self-healing off, reconciler skip).
4. **MoveRepairProcess**: `MoveUpdatedUnix` в модели/парсере; MR1-таблица;
   синтетические заявки put-if-absent; интеграция (… → rotate → **repair** →
   evacuate → moves).
5. **Стенд**: чистка `seed.sh`; перепись `checks/20-alerts.sh` (сценарий §3.6).
6. **Тесты** (по фазам 2–5, см. §6).

Порядок 2→3 жёсткий (adoption пишет адреса, резолв их ест); 4 независимо от
3 частично (синтетические заявки не требуют адресов), но e2e-гашение требует
3 (уборке нужен admin-DSN) — держим порядок.

## 5. Ограничения

- **Out of scope** (одной строкой каждое, не расширять): sticky-StatusError
  KafkaWorker-циклов (`ReconcileLoop.cs` KafkaWorker — отдельная задача);
  DNS-флейд health-пробей KafkaWorker; любые правки панели (панель уже
  показывает правду — меняется только реальность под ней); автоперевод
  усыновлённых нод на канонические pgw-контейнеры (миграция под управление —
  roadmap); advertised per-cluster конфиг (правило §3.3 закрывает кейс без
  нового конфига); Kafka-домен.
- Ручной скриптовый переезд без обновления статуса дольше `RepairStaleSec`
  будет репарирован (R10) — осознанно: панель считает это аномалией уже
  сегодня; правило «не смешивать скрипты и заявки в одном окне» (arch/14 §1).
- Усыновление не находит контейнеры (кластер вне docker-хостов воркера) →
  тихий skip: резолв мастера ограничен шагом HA-leader, SQL-пути transient,
  панель алертит честную недоступность. Это граница, не дыра.
- Формат статус-ключа не меняется (скриптовая совместимость 1:1, Д6);
  `/pgworker/moves/*` по-прежнему не читается панелью — синтетические заявки
  в UI невидимы, виден только результат (гашение алерта).

## 6. Тесты

- **Unit** (PgWorker.UnitTests, AAA-комментарии):

    NOT_INITIALIZED);
  - portalloc-merge с `object` (отсутствующие добавляются, существующие не
    трогаются); матчинг контейнеров (hostname/alias/NODE_NAME, порты
    5432/8008/6432, неоднозначность → пропуск).
- **Integration** (PgWorker.IntegrationTests, Testcontainers-этcd,
  DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1):
  - adoption-контракт: сид «внешнего» кластера (dsn-шарды, HA-members) +
    стаб-драйвер с контейнерами → portalloc появляется с `object`,
    nodes-ключи RUNNING, повторный тик — no-op;
  - repair-контракт: сид брошенных статусов → синтетические заявки
    появляются put-if-absent; операторская заявка не затёрта; статус со
    свежим `updated_unix` не диспатчится.
- **E2e стенд** — главный полный прогон: `checks/20-alerts.sh` (§3.6) на
  full-стенде с живым PgWorker (00-up.sh): появление → гашение алертов,
  полный move-цикл bucket_5, portalloc усыновления, отсутствие `move-*`
  алертов в конце; затем 30/40 зелёные (состояние возвращено).
- AdminPanel-тесты не меняются (EtcdSeed-аномалии в тестах панели легитимны —
  панель обязана алертить аномалии; чистится только docker-стендовый сид).
- TreatWarningsAsErrors=true — весь новый код без ворнингов.

## 7. Критерии приёмки

1. **Усыновление**: на full-стенде после подъёма PgWorker в
   `/pgworker/portalloc/demo` появляются записи всех 4 нод с `object: as-*`
   (etcdctl-проверка чека 20), `nodes/*/state=RUNNING`; повторные тики —
   no-op (журнал без ошибок).
2. **Резолв**: заявка move на усыновлённом кластере проходит M0 без
   «мастер не определён»; `bucket_5` совершает полный цикл s2→s1→s2
   (routing возвращён, статус ACTIVE, инвентарь 8+5 — чек 40 зелёный).
3. **Репарация**: нахераченные чеком статусы bucket_3/7/11 гаснут за бюджет
   чека 120 c (пороги репарации истекли заранее — `now−3600`; практически —
   несколько тиков воркера): ключи удалены, routing не тронут, алерты
   `move-stale`/`move-aborting`/`move-frozen-long` исчезли из `/api/alerts`.
4. **Живое не трогается**: статус со свежим `updated_unix` и статус с живой
   заявкой не вызывают синтетических заявок (unit + integration).
5. **Границы надзора**: стоп патрони-эмуляторов (чек 30) не порождает
   rebuild-циклов усыновлённых нод (SQL-живость PG); чек 30 зелёный.
6. **Стенд честный**: после полного прогона 00→10→15→20→30→40 в панели нет
   вечных `move-*` алертов; сид больше не сеет аномалии (чистый подъём =
   согласованный кластер).
7. `dotnet build` и все тесты (unit + integration) зелёные;
   TreatWarningsAsErrors соблюдён.

## 8. Принятые решения (сводка, с обоснованиями)

| # | Решение | Обоснование |
|---|---|---|
| Д1 | Скоуп A включает полный move на стенде | выбор пользователя: воркер — хозяин и усыновлённого кластера; DDL через exec в `object`-контейнер (`postgres:18` несёт `pg_dump`) |
| Д2 | Адреса усыновления пишутся в portalloc (не runtime) | выбор пользователя: «не наших» объектов не существует; надзор/резолв получают полные данные, `object`-поле отличает внешний контейнер |
| Д3 | Репарация = синтетические заявки в MoveProcess, не новый движок | переиспользование проверенной механики (AbortSequence resuming/force-доведение, rollback-post-flip), журналы/идемпотентность/takeover бесплатны, формат статус-ключа неизменен |
| Д4 | `RepairStaleSec=600` (= панель), `RepairFrozenSec=120` (= AbortMinAgeSec) | выбор пользователя (отдельный порог FROZEN); синхронизация с алертами панели: ремонт гасит только уже заалерченное |
| Д5 | Сид чистый, чек нахерачивает сам | выбор пользователя; стенд между прогонами согласован, e2e-сценарий детерминирован |
| Д6 | Self-healing/реконструкция off для `object`-нод; reconciler skip | rebuild поднял бы второй Patroni на scope (R9); reconciler воевал бы с внешним писателем master-ключа (R8); резолв мастера понимает оба формата |
| Д7 | Живость усыновлённых при `patroni=0` — SQL-проба | Patroni-сайдкар мёртв ≠ PG мёртв; иначе чек 30 получал бы ложные rebuild-циклы |
| Д8 | Advertised только для канонических приёмников | внешний приёмник compose-сети видит адреса dsn напрямую; подмена `host.docker.internal` ломает подключение (порт 5432 хоста не опубликован) |

## 9. Риски и митигации (дополняют arch/14 §9 R8–R10)

- **Порты усыновления вне PortRange** (5433–5436 стендовые): допустимо —
  portalloc-записи фиксируют факт; аллокатор новых нод работает по диапазону
  конфига, `BusyPortsAsync` видит фактические биндинги — коллизий нет.
- **Гонка adoption vs заявка оператора**: merge под клэймом + только
  отсутствующие записи; операторские nodes-ключи не перезаписываются
  (put-if-absent).
- **Чек 20 timing**: нахераченные статусы протухли заранее (`now−3600`) —
  репарация стартует в первый же тик; бюджет чека 120 c покрывает
  RepairFrozenSec/RepairStaleSec с запасом (пороги уже истекли).
