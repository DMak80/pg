## 1. Проблема и контекст

Полная docker-E2E-серия PgWorker (26 фактов, все классы `E2e*` в
`src/tests/PgWorker.IntegrationTests/E2e/`, ~37–59 мин при параллелизме N=3)
обязана быть устойчивой к параллельной нагрузке на том же docker-хосте
(соседние прогоны серий, dev-стенд, соседние контуры самой серии). Сегодня
это не так — два зафиксированных симптома:

- **Симптом А (мерж-гейт t06, 2026-09-29).** При тяжёлом соседнем прогоне на
  том же хосте серия одним фильтром подвисает на существующих сценариях
  (Restore-переход, WalStream AC2–AC7); те же классы, прогнанные
  последовательно, — зелёные.
- **Симптом Б (мерж-гейт t27, 2026-10-05).** При 5 параллельных изолированных
  E2E-контурах (внутри одной серии) разрешение имён внутри docker-сетей
  деградирует: в логах PG-нод `getaddrinfo returns an empty list`, стрим-клиенты
  получают мгновенные (~0,3 с) фейлы коннекта в transient-цикле; зафиксирован
  упавший WalStream-сценарий promote. Ускорения от N=5 нет: 58 м 59 с / 26
  фактов (25/26 зелёные) против 37 м 37 с / 24 (24/24) при N=3.

Уже исключено расследованиями t27: conn-лимит PG (`too many connections` —
0 улик), пул адресов docker-сетей (пик 3 из ~30). Канон прогона «до
устранения причины» был **≤3 параллельных контура** — следствие деградации,
а не свойство системы; после внедрения целевого состояния (§1.3–§1.4) канон
ПЕРЕСМАТРИВАЕТСЯ приёмкой на N=3/5/6 (§6 фаза 4): выбор строго по
измерениям — максимально быстрое и стабильное.

### 1.1. Канон-основание сетевой изоляции (дословно, AGENTS.base.md §13)

«Единица изоляции — сценарный класс (минимальная граница — test class; если
методы внутри класса мешают друг другу — per-method). Каждая единица получает
ПОЛНОСТЬЮ СВОЁ окружение: своя docker-сеть (создавать и удалять самим), ВСЕ
контейнеры ТОЛЬКО СВОИ и смотрят ТОЛЬКО друг на друга там, где нужно.»

«Общими могут быть ТОЛЬКО статические ассеты (сертификаты, собранный образ) —
это не мутабельный рантайм-стейт.»

Терминология этого spec: **единица** — сценарный класс (per-method —
эскалация для классов, чьи методы мешают друг другу). Фактическая реализация
сегодня: окружение поднимается per-fact (`await using` в теле Fact; класс с
10 Facts поднимает 10 контуров) — это per-method-уровень для всех классов;
канону не противоречит (граница не грубее класса), для большинства классов
(1 Fact) совпадает с per-class. Смена фактической границы per-fact →
per-class — вне рамок t24 (на сетевую изоляцию не влияет: контур единицы уже
целиком свой).

### 1.2. Сетевой факт (разбор Фазы 6, 4f7b146)

- Per-unit сегодня только окружение инфраструктуры: etcd (1–3 узла) + MinIO в
  сети `pgw-en-{runId}` с guid-именами. Ноды кластеров и wal-агенты ВСЕХ
  параллельных тестов — в ОДНОЙ общесистемной сети
  (`src/PgWorker.Docker/Drivers/ClusterDriver.cs`:
  `public const string NodesNetwork = "pgw-net"`, `EnsureNetworkAsync(NodesNetwork)`
  на каждый create ноды/агента, спеки контейнеров `Network = NodesNetwork`):
  одна сеть ⇒ одна Docker-DNS-зона ⇒ перекрёстная видимость алиасов нод чужих
  контуров — сетевая изоляция контуров отсутствует, что нарушает канон §13
  п.1 («ВСЕ контейнеры ТОЛЬКО СВОИ и смотрят ТОЛЬКО друг на друга»).
- Прецедент правильной схемы в монорепо: KafkaWorker — per-cluster сети
  (`NodesNetworkPrefix = "kfw-net-"`, `NetworkName(cluster)`; arch/16 §2.1)
  — тем же фиксом лечилась ровно эта болезнь (единая сеть + общие короткие
  алиасы ломали Raft через docker-DNS round-robin).
- **Связанная находка (разбор 4f7b146):** advertise-client-urls etcd
  окружения содержит внутрисетевой алиас `e2e-etcdN:2379`, существующий
  только в сети окружения, — Patroni-ноды из сетей движка его ретраят ⇒
  NXDOMAIN-шторм; улика симптома Б «getaddrinfo returns an empty list» — это
  Patroni-клиент, НЕ docker-резолвер. При потере etcd-сессии (шторм ретраев
  по недостижимому URL) ноды остаются минуты без DCS ⇒ фейлы Restore/WalStream
  по бюджетам уже при N=3. Потребителей алиаса вне сети окружения нет.

### 1.3. Конфигурационный факт и целевая схема параллелизма (эмпирика Фазы 6, гейт Task 1)

- Атрибут
  `[assembly: CollectionBehavior(CollectionBehavior.CollectionPerAssembly, DisableTestParallelization = true)]`
  в `src/tests/PgWorker.IntegrationTests/AssemblyInfo.cs` — **РАБОЧИЙ**: задаёт
  всей сборке последовательный прогон (N=1) при любом способе `dotnet test`
  (проверено контрольными прогонами по проекту и по solnx — журнал задачи).
  Свойства csproj `XunitParallelizeTestCollections`/`XunitMaxParallelThreads` —
  **МЁРТВЫЕ**: xunit.v3 не поддерживает v2-механику MSBuild-свойств;
  конфигурация v3 — xunit.runner.json (обязан копироваться в output) +
  assembly-атрибуты.
- Следствия: «фактического N=3 в обычном запуске серии не существовало» —
  обычные прогоны библиотеки шли N=1 (атрибут — единственный живой источник);
  все наблюдавшиеся параллельные режимы (симптомы и замеры t06/t27, 3–5
  контуров) возникали при внешнем переопределении параллелизма запуском.
  Удаление атрибута — не чистка мёртвого кода, а СМЕНА режима прогона всей
  сборки: без доп. механики не-E2E-тесты стали бы параллельными (эмпирика:
  под конкуренцией получен фейл
  `WalReceiverIntegrationTests.Рестарт_дозасылает_от_хвоста` — приёмник не
  вышел из `starting` за бюджет 30 с), а E2E-серия впервые реально параллельна.
- **Целевое состояние параллелизма (решение пользователя, гейт Task 1,
  дословно: «не е2е должны быть последовательно, их в коллекцию надо
  закинуть»)**: атрибут удаляется; единственный источник истины параллелизма —
  **xunit.runner.json** (стартовое `maxParallelThreads=3`; финальное значение —
  по приёмке фазы 4 из {3,5,6}, AC10); мёртвые `Xunit*`-свойства убираются
  из csproj; не-E2E тесты объединяются в `[Collection]`-группу(-ы) с
  `CollectionDefinition(DisableParallelization=true)` — их
  последовательность сохраняется гарантированно; E2E-серия становится
  реально параллельной (впервые в каноническом запуске).

### 1.4. Целевое состояние сетевого слоя (требование пользователя «свой контур НЕ ПО СЕРВИСАМ А ПО ТЕСТАМ»)

- **Движок PgWorker: per-cluster сеть нод `pgw-net-<C>`** — по образцу
  `kfw-net-<cluster>` (arch/16 §2.1): константный префикс +
  `NetworkName(cluster)`, БЕЗ Options-параметризации — консистентность с
  kfw-прецедентом и с arch/04 §8 п.3, который уже говорил «per-cluster сети
  воркера» (правка arch/14 §2.1 устраняет рассинхрон между документами).
  Константа `pgw-net` уходит. Per-unit изоляция достигается по построению:
  имена кластеров в E2E уникальны per-unit (содержат guid-тег прогона) ⇒
  уникальна и DNS-зона контура; передавать воркеру отдельное имя сети не
  требуется.
- **Advertise-митигация:** из advertise-client-urls etcd окружения убирается
  внутрисетевой алиас, недостижимый для клиентов из сетей движка; остаются
  URL, реальные для всех потребителей (канон arch/04 §8 п.3).
- Контракты обновлены (arch-first): `arch/14` §2.1 (сеть нод per-cluster,
  ensure-инвариант «нода и её агенты в одной сети кластера», демонтаж чистит
  сеть), `arch/04` §8 п.3 (в список advertise — только URL, резолвимые для
  потребителей), `docs/e2e-isolation.md` (таблица объектов, teardown, §8).
- Сетевые митигации входят в решение независимо от исхода гейта (изоляция
  контуров — требование канона §13), а причина болей N=3 — В ГРАНИЦАХ нашей
  инфраструктуры (ветка «устраняем», фаза 3).

### 1.5. Портовый факт и целевое состояние (решение пользователя, 2026-10-06, «решаем сразу в текущей задаче»)

Решение пользователя (дословно): «надо чинить. крайне ошибочное решение: на
каждую ноду резервируется база + смещения: patroni +3000, doorman +1500. на
каждый тест класс резервируется свои 200 портов динамически и для всех
контейнеров они выделяются последовательно (никаких + 3000 и + 1500).
резервирование происходит запуском на первом порту из диапазона контейнера
etcd (etcd используется везде, потому его поднятие будет сразу и полезным);
если порт занят — пытаемся следующие 200 портов зарезервировать. решаем
сразу в текущей задаче.»

Факт (текущая схема, уходит):

- `PortRangeOptions` — «Диапазон базовых портов нод [From, To): pg=base,
  patroni=+3000, doorman=+1500» (`src/PgWorker.App/Options.cs:210-216`,
  дефолт 15000–16000); выделение — `AddShardProcess` (~200-236): лок
  portalloc в СВОЁМ etcd контура + занятость `docker ∪ portalloc` —
  межконтурных коллизий НЕ видит (два контура выбирают порт одновременно до
  чужого bind).
- E2E передаёт воркеру ЛИТЕРАЛЬНЫЙ диапазон `15100–15200`
  (`E2eEnvironment.cs:475-476`) — ОДИН И ТОТ ЖЕ всем параллельным контурам:
  межконтурная гонка гарантирована конструкцией. Улика: прогон №8 —
  `Bind 0.0.0.0:15102 failed: port is already allocated`, нода остаётся
  «created» (класс = фейл №3 прогона №1) — единственный фейл серии после
  сетевых митигаций.

Целевое состояние:

- **Единица (тест-класс/контур) резервирует ДИНАМИЧЕСКИ окно из 200 портов**
  на docker-хосте. Резервирование — физическое, реальным bind: первым портом
  окна публикуется контейнер etcd контура (etcd поднимается окружением всегда
  — его подъём одновременно «запирает» окно). Bind не удался (порт занят кем
  угодно на хосте) → окно сдвигается на следующие 200 портов → повтор до
  успеха (бюджет попыток ограничен).
- **Все контейнеры контура** (etcd-узлы, MinIO, ноды кластеров, wal-агенты,
  джобы) получают host-порты ПОСЛЕДОВАТЕЛЬНО из окна — никаких смещений
  +3000/+1500.
- **Движок:** схема смещений из `PortRangeOptions` уходит; portalloc выделяет
  последовательные слоты из переданного диапазона; `PortRange`
  параметризуется per-contour средой — E2eEnvironment передаёт воркеру окно
  ЗА ВЫЧЕТОМ уже занятых инфраструктурой контура портов; advertised-адреса —
  от фактических портов (канон §13 п.4). Внутриконтурные защиты (занятость
  docker ∪ portalloc, глобальный portalloc-клэйм) сохраняются.
- Контракт обновлён (arch-first): `arch/14` §2.4 п.2 (последовательные слоты,
  диапазон параметризуется средой: прод — per-install, E2E — per-contour
  окно), `docs/e2e-isolation.md` §5 (резервирование окна bind'ом, запрет
  литеральных диапазонов в конфиге воркера).
- Это ЧЕТВЁРТАЯ обязательная сетевая/портовая митигация (вместе с per-cluster
  сетями и advertise-фиксом — вне гейта Task 7); гейт остаётся для «прочих
  митигаций».

Прочее: **канон прогона серии нигде не описан целиком** — потолок N=3 только
в комментариях; в `docs/e2e-launch.md` (канон запуска) раздела про
параллелизм/соседнюю нагрузку нет.

Факты об окружении, на которые опирается расследование:

- Хост — macOS (darwin), docker-хост один на серию: Docker Desktop; имена
  внутри сетей резолвит embedded DNS (127.0.0.11), `host.docker.internal` —
  спец-резолвер; Patroni-ноды, wal-агенты, бэкап-джобы и воркеры ходят друг
  на друга ПО ИМЕНАМ (алиасы etcd/MinIO в сети окружения, имена нод
  `pgw-<C>-*`, `host.docker.internal:<published-port>`).
- Один контур серии — это сеть `pgw-en-{guid}` + etcd + MinIO + per-cluster
  сети движка + PG-ноды с Patroni + бэкап/wal-джобы + хост-процессы воркеров.

## 2. Цель

Предмет задачи (ревизия 7, решение пользователя): устойчивость ПАРАЛЛЕЛЬНОГО
запуска тестов — полная E2E-серия стабильно зелёная при N контурах,
работающих одновременно (N=3/5/6), в границах зафиксированного канона
прогона. Поведение тестов под внешней нагрузкой/шумовым соседом — ВНЕ
предмета задачи. Причина деградации устраняется: сетевые митигации (§1.4)
выполняются обязательно, прочие — по гейту фазы 2; выбор канона
параллелизма — НЕ по прежней цифре ≤3, а приёмкой на N=3/5/6
(раздел 6, фаза 4): **максимально быстрое и стабильное** из измеренных,
зафиксированное в runner.json, docs и рельсе E2eParallelismGuard. Решения —
НЕ молчаливые: гейт фазы 2 и выбор канона фазы 4 фиксируются в журнале
задачи по измеримым критериям; при неоднозначности — вопрос пользователю
через `AskUserQuestion`.

Сетевая и портовая изоляция (требования пользователя, §1.4–§1.5) выполняется
независимо от исхода гейта: контур каждой единицы (сценарного класса)
сетево изолирован — собственная Docker-DNS-зона (per-cluster сеть нод),
advertise только с URL, достижимыми для потребителей, и собственное
НЕПЕРЕСЕКАЮЩЕЕСЯ окно host-портов (bind-резервирование, последовательное
выделение).

Вторичные цели:

- **Воспроизводимость:** параллельные прогоны — управляемые и повторяемые
  (потолок N задаётся конфигурацией раннера и фиксируется в журнале, условия
  прогона детерминированы), а не ручная импровизация.
- **Порядок в конфигурации:** единственный источник истины параллелизма —
  xunit.runner.json; `Xunit*`-свойств в csproj и `CollectionBehavior`-атрибута
  нет; последовательность не-E2E гарантирована `[Collection]`-группой с
  `DisableParallelization`.
- **Канонизация:** `docs/e2e-launch.md` получает раздел «Параллелизм и
  нагрузка» (потолок N, границы одновременных контуров на хосте, признаки
  деградации, действия при фейле) — согласован с runner.json и
  `docs/e2e-isolation.md`.

Задача меняет `arch/**` только в части сетевого слоя движка и
advertised-правил (§1.4 — обновлены по arch-first до кода); roadmap-гейт
закрывается по общему правилу трека (раздел 8, AC8).

## 3. Принципы

1. Буква канонов E2E: `AGENTS.base.md` §13 (цитаты — §1.1), изоляция
   guid-контурами с own-only teardown и ассертом чистоты
   (`docs/e2e-isolation.md`), телеметрия «что произошло — по логам, без
   перезапуска» (`docs/e2e-launch.md`), динамические порты, никакой
   мутабельной shared-инфраструктуры между контурами. t24 работает В ГРАНИЦАХ
   этого канона — не ослабляя его.
2. Гипотеза — ДО эксперимента, с проверяемыми следствиями; эксперимент обязан
   РАЗЛИЧАТЬ гипотезы (меняет одну переменную). Прогон без сформулированной
   гипотезы — нарушение (в т.ч. духа e2e-launch §4: перезапуск «авось
   зелёное» запрещён; эксперименты фаз 1–2 — новые прогоны с гипотезой, не
   перезапуски упавших).
3. Никаких «увеличим таймаут/бюджет — авось проедет»: каждый обнаруженный
   подвис/фейл получает объяснение по телеметрии до любого изменения бюджета.
4. Изменения прод-кода (воркер, приёмник WAL, движок) — только по
   локализованной причине и каноничному фиксy (production-ready). Сетевая
   митигация движка (§1.4) — контрактное изменение по arch-first, выполняется
   независимо от исхода гейта; прочие изменения прод-кода — по общему правилу.
5. Результаты расследования живут в журнале задачи
   (`docs/superpowers/2026-10-06-t24-e2e-suite-under-load/` — рядом с этим
   spec): каждый прогон — гипотеза, условия, измерения, вердикт.
6. Язык — русский для документации/журнала; идентификаторы — английские.

## 4. Стартовый набор гипотез (уточняется в фазе 1; не взаимоисключающие)

- **H1 — DNS-резолвер Docker Desktop деградирует.** Embedded DNS / vpnkit
  медленнее или ошибается при росте параллельных сетей/контейнеров/запросов.
  Согласуется с уликой `getaddrinfo returns an empty list` (с учётом находки
  4f7b146 — часть наблюдений объясняется NXDOMAIN-штормом Patroni по
  advertise-алиасу, НЕ docker-резолвером; остаток — предмет проверки).
  Проверяемые следствия: латентность/ошибки резолва растут с числом сетей
  (видно синтетическим DNS-зондом без PG вообще); фейлы приходят на этапе
  разрешения имени, а не TCP-коннекта/хендшейка, и НЕ объясняются
  advertise-алиасом (после митигации §1.4). Статус по решению пользователя
  (ревизия 5): ЗАКРЫТ имеющимися уликами без отдельного прогона — причина
  симптома Б была в пересекающихся сетях/advertise-алиасе, что исправлено
  сетевыми митигациями; факт-подтверждение: прогоны №6-до-фикса (N=5) и №8
  (N=3) — после advertise-фикса Patroni resolve-фейлов 0; вердикт по H1
  формулируется по этим уликам и разбору 4f7b146 (фаза 2), DNS-кривая
  (отдельный замер резолва от числа сетей) исключена.
- **H2 — CPU/IO-конкуренция на хосте МЕЖДУ контурами серии.** N контуров ×
  (PG-ноды+Patroni, etcd, MinIO, джобы, воркеры) перегружают хост: сессии
  Patroni↔etcd таймаутятся → failover-каскады, акцепты медленные → коннекты
  падают в transient-циклах. Конкуренция между контурами САМОЙ серии — в
  предмете (параллельный запуск). Следствия: корреляция фейлов с загрузкой
  CPU хоста и load average по данным параллельных прогонов при варьировании
  N (без синтетического шума — исключён ревизией 7).
- **H3 — «подвисание» = транзиент-циклы против бюджетов фикстур.** Прогон не
  висит, а честно ретраится (полл 500 мс, ErrorDelayMs=500), но при
  деградировавшем коннекте упирается в бюджеты (ожидания сценариев 120–360 с,
  PatroniBootSec=300 у движка) — снаружи выглядит висяком. Следствия: фейл по
  бюджету сопровождается журналом прогресса (`[PHASE] … elapsed=…`), между
  ретраями есть движение; на снятой телеметрии виден прогресс до обрыва.
  Находка 4f7b146 — подтверждённый экземпляр: NXDOMAIN-шторм → потеря DCS →
  съеденные бюджеты Restore/WalStream при N=3.
- **H4 — соседний прогон как множитель.** Деградация определяется СУММАРНОЙ
  нагрузкой docker-демона (контейнеры/сети/IO всех процессов хоста), а не
  только контурами самой серии. Следствия: порог воспроизведения зависит от
  K соседних контуров, а не от N самой серии; генератор соседней нагрузки
  воспроизводит симптомы при N≤3. Статус: ИСКЛЮЧЕНА решением пользователя
  (ревизия 7) — предмет задачи «параллельный запуск тестов, а не под
  нагрузкой запуск тестов»: внешняя нагрузка/шумовой сосед вне предмета;
  до-митигационные улики с соседями (прогоны №1, №5-прерванный) — история,
  не план измерений.

## 5. Структура / компоненты (что строится)

1. **Диагностический нагрузочный генератор — инструмент исследования, в
  целевом состоянии НЕ используется (ревизия 7)**: был реализован для
  шумовых прогонов с соседом (Task 2, факт — в журнале); прогоны с K>0
  исключены ревизией 7 («проверять параллельный запуск тестов, а не под
  нагрузкой запуск тестов»), генератор (включая dns-профиль и dns_probe.py)
  не используется ни в одном прогоне и демонтируется с веткой (Task 10
  плана). Описание инструмента (для журнала/истории): поднимает K «шумовых»
  изолированных контуров с профилями `dns`/`cpu`/`io`/`full`; управление —
  аргументы запуска (K, профиль, время).
2. **Синтетический DNS-зонд — ИСКЛЮЧЁН из целевого состояния (ревизия 6,
   решение пользователя)**: зонд (python-alpine контейнер `pgw-dns-{runId}` в
   каждом тестовом контуре, опция `PGW_TEST_E2E_DNS_PROBE`, CSV в
   docker-логи) был реализован в Task 2 (факт разработки остаётся в журнале)
   и подлежит ДЕМОНТАЖУ отдельной задачей плана: врезка `E2eDnsProbe.cs`,
   крюки в `StartOnceAsync`/catch/`DisposeAsync`, env-опция — удаляются.
   Обоснование: причина DNS-симптоматики устранена сетевыми митигациями
   (per-cluster сети + advertise-фикс; прогоны №8/№9 — Patroni resolve-фейлов
   0), отдельная DNS-телеметрия контура не нужна; контроль DNS-здоровья в
   оставшихся прогонах — по Patroni-логам/docker-логам кластеров («failed to
   resolve»/«getaddrinfo» считаются по ним — главный источник и так).
   DNS-профиль ГЕНЕРАТОРА (п. 5.1, шумовые профили E2eLoadGen) — НЕ трогать
   (решение ревизии 6: инструмент нагрузки, не телеметрия); ревизия 7
   выводит генератор из использования ЦЕЛИКОМ — демонтаж вместе с веткой
   (Task 10 плана), приведёншее обоснование сохраняется как история.
3. **Матрица экспериментальных прогонов серии** — полная E2E-серия на Release
   при ПАРАЛЛЕЛЬНОМ варьировании N (число контуров одной серии
   одновременно; без внешнего соседа — ревизия 7) с фиксацией: время серии,
   зелёность, `[PHASE]`-тайминги, телеметрия teardown (артефакты
   `/tmp/pgw-e2e-artifacts-*`). Состав матрицы — раздел 6.
4. **Приведение конфигурации параллелизма к одному источнику истины** —
   целевая схема по решению гейта Task 1 (§1.3): удалить `CollectionBehavior`-
   атрибут из `AssemblyInfo.cs`; `xunit.runner.json` (стартовое
   `maxParallelThreads=3`; финальное значение выбирает приёмка фазы 4 — AC10;
   копирование в output) — единственный источник потолка параллелизма;
   мёртвые `Xunit*`-свойства удалить из csproj; не-E2E-классы — в
   `[Collection]`-группу(-ы) с `CollectionDefinition(DisableParallelization=true)`
   (последовательность не-E2E гарантирована, параллельная конкуренция для них
   не норма — эмпирика Task 1); комментарий-обоснование канона — в
   runner.json/docs.
5. **Раздел «Параллелизм и нагрузка» в `docs/e2e-launch.md`** — канон
   прогона: потолок N (выбранный приёмкой фазы 4), границы одновременных
   контуров на docker-хосте (включая dev-стенд), признаки деградации (что
   смотреть в логах: getaddrinfo empty, рост `[PHASE]` elapsed), действия
   при фейле. Согласование с runner.json и `docs/e2e-isolation.md`.
6. **Рельса E2eParallelismGuard** — предупреждение при запуске серии с
   фактически большим числом потоков, чем выбранный канон (сверка
   фактического потолка потоков раннера при старте серии, предупреждение в
   журнал прогона; жёсткий запрет НЕ вводим — диагностические прогоны
   легальны, но обязаны быть громкими). Порог = N, выбранный приёмкой
   фазы 4.
7. **Сетевые митигации (реализация контрактов §1.4; причина локализована
   разбором 4f7b146)**:
   - движок PgWorker: per-cluster сеть нод `pgw-net-<C>` (kfw-паттерн:
     константный префикс + `NetworkName(cluster)`), константа `pgw-net`
     уходит; ensure-инвариант «нода и её wal-агенты в одной сети кластера»
     (сверка сети при усыновлении/идемпотентном create, лечение по канону
     идемпотентности — arch/14 §2.1); демонтаж кластера удаляет свою сеть;
   - E2eEnvironment: advertise-client-urls etcd без внутрисетевого алиаса
     (только URL, достижимые из сетей потребителей — arch/04 §8 п.3);
     teardown — без шага «снести общесистемную pgw-net», per-cluster сети
     подбираются own-only чисткой (имя содержит имя кластера) и входят в
     ассерт чистоты;
   - (только ветвь «устранено» гейта) прочие кандидаты митигаций — состав
     определяется фазой 2 (снижение DNS-зависимости горячего тракта,
     настройки резолвера/количества сетей, ограничение одновременных
     контуров per-класса); каждый кандидат — через свой мини-эксперимент.
8. **Портовые митигации (реализация контракта §1.5; решение пользователя
   «решаем сразу в текущей задаче»)**:
   - E2eEnvironment: динамическое резервирование окна (200 портов) bind'ом —
     первым портом окна публикуется etcd-контейнер контура; занят → сдвиг
     окна на следующий блок → повтор (бюджет попыток ограничен); все
     контейнеры контура получают host-порты последовательно из окна;
     воркеру передаётся `PortRange` = окно за вычетом занятых
     инфраструктурой контура;
   - движок: упразднение схемы смещений (+3000/+1500) из `PortRangeOptions`
     и аллокатора — последовательные слоты диапазона (arch/14 §2.4 п.2);
     advertised — от фактических портов; внутриконтурные защиты portalloc
     (занятость docker ∪ portalloc, глобальный клэйм) сохраняются.

- Матрица прогонов — ПАРАЛЛЕЛЬНОЕ варьирование N, БЕЗ внешнего соседа

  1. (N=3) — контроль;
  2. (N=5) — воспроизведение симптома Б (контроль известных измерений;

- Выход: симптом Б устойчиво воспроизведён (или опровергнут) с измерениями;
  данные, различающие оставшиеся гипотезы (H2, H3).

### Фаза 2 — различение гипотез

- Анализ по данным параллельных прогонов фазы 1, без синтетического шума

- Выход: карта «симптом → причина → измерение → подтверждено/исключено» для

  наших границах — 4f7b146), а какая требует иных мер или является

  t27; на целевой конфигурации скорость и стабильность меряются заново
  приёмкой фазы 4).

### ГЕЙТ РЕШЕНИЯ (после фазы 2)

Решение «прочие митигации СВЕРХ сетевых и портовых» фиксируется в журнале
задачи с опорой на критерии (сетевые §1.4 и портовые §1.5 митигации
выполняются в любом случае — изоляция контуров есть требование канона §13 и
прямые решения пользователя, а не опции; межконтурная portalloc-гонка
прогона №8 закрывается именно портовой митигацией §1.5). Предмет — только
параллельный запуск серии: митигации «под внешнюю нагрузку/шумового соседа»
вне предмета и гейтом не рассматриваются (ревизия 7):

- **Реализуем прочие митигации** — если фаза 2 показала остаточные причины
  В НАШИХ ГРАНИЦАХ (код тестов / конфигурация контуров / имена вместо DNS) с
  дешёвым каноничным фиксом.
- **Не реализуем** — если остаточное — ограничение Docker Desktop/хоста
  (vpnkit/резолвер), или митигация дороже выгоды: канон параллелизма тогда
  просто выбирается приёмкой фазы 4 в реально доступном диапазоне.
- Критерии не дают однозначного ответа → вопрос пользователю через
  `AskUserQuestion`, ответ — в журнал.

### Фаза 3 — реализация решения

Конфигурация параллелизма уже приведена в фазе 0 (§5.4); здесь — митигации.

- **Сетевые митигации (обязательные, контракты §1.4):** реализация
  per-cluster сети нод движка (arch/14 §2.1 → код: префикс + NetworkName,
  ensure-инвариант, демонтаж сети; константа `pgw-net` удаляется), правки
  E2eEnvironment (advertise без внутрисетевого алиаса; teardown per-cluster
  сетей, шаг «снести общесистемную pgw-net» уходит); контрольный прогон
  фиксирует эффект (DNS-зона контура своя; NXDOMAIN-шторм Patroni
  устранён).
- **Портовые митигации (обязательные, контракт §1.5):** реализация
  динамических окон контура (bind-резервирование через публикацию etcd,
  последовательное выделение всем контейнерам, PortRange воркеру = окно за
  вычетом инфраструктуры) и упразднение смещений +3000/+1500 в движке
  (arch/14 §2.4 п.2); контрольный прогон фиксирует: окна параллельных
  контуров не пересекаются, «port is already allocated» между контурами
  отсутствует.
- **Прочие митигации (по гейту фазы 2):** реализуются кандидаты по карте
  фазы 2, каждый — через свой мини-эксперимент.
- Если подтверждён вклад H3 — точечные уточнения бюджетов/телеметрии
  медленных фаз, каждое с объяснением по телеметрии (запрет «просто
  увеличить таймаут» не снимается).

### Фаза 4 — приёмка канона параллелизма и канонизация

- **Три точки приёмки на ЦЕЛЕВОЙ конфигурации** (сетевые митигации и всё
  решённое гейтом внедрены): полные серии при N=3, N=5 И N=6 — не
  «диагностические переопределения», а полноправные канонические прогоны
  (N переключается правкой runner.json с возвратом до фиксации выбора).
  Каждый прогон — с гейтом тишины/чистоты по операционной модели: хост чист
  до/после, контроль остатков, полная телеметрия.
- **Критерий выбора канона: МАКСИМАЛЬНО БЫСТРОЕ И СТАБИЛЬНОЕ** — сравнение
  времени полной серии и стабильности: зелёность всех сценариев, отсутствие
  NXDOMAIN-бурь/DNS-деградации в телеметрии (Patroni-логи/docker-логи
  кластеров: «failed to resolve»/«getaddrinfo» считаются по ним), отсутствие
  флейков сверх бюджета повторов §9.
- **Фиксация победителя:** runner.json `maxParallelThreads=<N>`;
  раздел `docs/e2e-launch.md`; порог рельсы E2eParallelismGuard = выбранное N.
- **Подтверждение выбранного канона:** вторая последовательная зелёная серия
  на выбранном N (устойчивость, а не удача).
- Мерж-гейт трека: пункт `t24` снят из `arch/roadmap/reliability.md`, строка
  в `arch/roadmap/reliability-report.md` перенесена в «Сделано» — тем же
  коммитом.

## 7. Ограничения

- Канон изоляции E2E нерушим (AGENTS.base.md §13, цитаты §1.1): guid-контуры,
  own-only чистка, ассерты чистоты, динамические порты. Сетевой слой —
  per-unit/per-cluster (арх-контракт arch/14 §2.1): общесистемная сеть нод
  не возвращается; общими остаются только статические ассеты (§13 п.5).
- Таймауты ожиданий агента ≤30 с с проверкой (AGENTS.base §12); полл в тестах
  500 мс — канон репо.
- Перезапуск упавших прогонов для выяснения «что было» запрещён; каждый
  новый прогон фаз 0–3 — с гипотезой, согласованной с журналом.
- Прод-код — сетевые митигации движка по контракту arch/14 §2.1 (arch-first);
  прочие изменения прод-кода — только при локализованной в нём причине
  (принцип 4).
- Не-E2E тесты той же сборки сохраняют последовательность ГАРАНТИРОВАННО —
  `[Collection]`-группой с `CollectionDefinition(DisableParallelization=true)`;
  параллельная конкуренция для них не норма (фейл WalReceiver в Фазе 6
  относится к прежней беззащитной конфигурации). Проверка — прогон не-E2E
  серии до/после смены конфигурации в эквивалентном (последовательном)
  режиме: зелёность и длительность сопоставимы.
- Локально собираемые образы в registry не кладутся; новые ВНЕШНИЕ образы не
  вводятся (генератор — из уже зеркалированных base-образов локального
  registry; если нужен новый внешний образ — строки в `images.txt` по ранбуку,
  что в рамках задачи не предполагается).
- Суммарное число живых user-сетей в экспериментах не подбирается к пулу
  (~30) и не пересекается с dev-стендом (per-cluster сети добавляют по сети
  на кластер — короткоживущие, удаляются демонтажем; контроль `docker
  network ls` после каждой серии, зачистка остатков по канону).
- Генератор шума E2eLoadGen не используется ни в одном прогоне целевого
  состояния и удаляется из ветки (ревизия 7; демонтаж — Task 10 плана);
  встроенный DNS-зонд демонтируется отдельной задачей плана (ревизия 6,
  §5.2).

## 8. Критерии приёмки

- **AC1 (воспроизведение — параллельный запуск).** Симптом Б (DNS-деградация
  при N≥5, до-митигационные улики) либо устойчиво воспроизведён параллельным
  прогоном серии (без внешнего соседа — ревизия 7), либо опровергнут — с
  измерениями; итог — в журнале задачи. Симптом А (подвисание при тяжёлом
  соседнем прогоне) — вне предмета (ревизия 7), остаётся историей (§1).
- **AC2 (причина).** Для проверяемых гипотез H1–H3 (H4 исключена ревизией 7)
  есть строки «следствие → измерение → подтверждено/исключено» со ссылками
  на артефакты прогонов (docker-логи кластеров/Patroni-логи, `[PHASE]`-тайминги,
  артефакты `/tmp/pgw-e2e-artifacts-*`); доля, закрываемая сетевыми
  митигациями, выделена.
- **AC3 (гейт решения).** Выбор ветки зафиксирован в журнале с критериями и
  измерениями; при неоднозначности — задокументированный вопрос/ответ
  пользователя.
- **AC4 (конфигурация).** Единственный источник истины параллелизма —
  xunit.runner.json (`maxParallelThreads=<N выбранного канона, AC10>`,
  копируется в output); `Xunit*`-свойств в csproj нет;
  `CollectionBehavior`-атрибута нет; не-E2E — `[Collection]`-группа с
  `DisableParallelization`. Фактическое поведение подтверждено НАБЛЮДЕНИЕМ
  прогонов, не только чтением конфигурации: E2E-серия параллельна (не больше
  выбранного N контуров одновременно), не-E2E последовательны.
- **AC5 (канон прогона).** `docs/e2e-launch.md` содержит раздел
  «Параллелизм и нагрузка»: потолок N (выбранный приёмкой), границы
  одновременных контуров на docker-хосте, признаки деградации, действия при
  фейле; runner.json и `docs/e2e-isolation.md` согласованы с docs.
- **AC6 (стабильность).** Полные серии приёмки (фаза 4) на выбранном каноне
  — зелёные; полная чистота хоста после каждой (ни контуров, ни сетей, ни
  томов своих guid, ни per-cluster сетей своих кластеров); выбранное N
  подтверждено второй последовательной зелёной серией (устойчивость, а не
  удача).
- **AC7 (рельса).** E2eParallelismGuard: запуск серии с фактически большим
  числом потоков, чем выбранный канон (порог рельсы = выбранное N), даёт
  громкое предупреждение в журнале прогона (проверено прогоном с
  переопределённым потолком параллелизма).
- **AC8 (мерж-гейт трека).** Пункт `t24` снят из `arch/roadmap/reliability.md`
  и `reliability-report.md` тем же мерж-коммитом; в отчёте — строка
  «Сделано» с сутью решения и влиянием на характеристику N (устойчивость
  приёмки).
- **AC9 (сетевая изоляция и advertise).** После сетевых митигаций:
  (а) в коде движка нет константы `pgw-net`; сети нод — `pgw-net-<C>`,
  создаются движком при provisioning, удаляются демонтажем, попадают в
  own-only teardown и ассерт чистоты E2E (имя содержит имя кластера);
  (б) DNS-зоны контуров изолированы — проверяемый ассерт: из сети своего
  контура имя ноды/алиас чужого контура НЕ резолвится (прямая проба
  резолва в контрольном прогоне с ≥2 контурами);
  (в) advertise-client-urls etcd окружения не содержат URL, недостижимые
  для потребителей: каждый URL списка резолвится из сети Patroni-нод
  (прямая проба в контрольном прогоне);
  (г) NXDOMAIN-бурь нет — «resolve-фейлов 0» по Patroni-логам/docker-логам
  кластеров контрольных прогонов матрицы: серийные `failed to resolve` /
  `getaddrinfo … empty` отсутствуют;
  (д) зелёный базлайн: контрольная матрица после митигаций зелёная при N=3
  (включая сценарии Restore/WalStream, падавшие до митигаций).
- **AC10 (выбор канона параллелизма).** Три прогона приёмки фазы 4 (N=3,
  N=5, N=6) на целевой конфигурации выполнены и зафиксированы в журнале с
  измерениями (время полной серии, зелёность, DNS-телеметрия, чистота
  хоста); канон = МАКСИМАЛЬНО БЫСТРОЕ И СТАБИЛЬНОЕ N из {3,5,6} по критериям
  §6 (фаза 4); выбранное значение зафиксировано в runner.json
  (`maxParallelThreads`), разделе `docs/e2e-launch.md` и пороге рельсы
  E2eParallelismGuard (AC4/AC5/AC7 согласованы с ним).
- **AC11 (портовая изоляция контуров).** Межконтурные портовые коллизии
  исключены конструкцией: (а) в движке нет схемы смещений +3000/+1500 —
  порты нод выделяются последовательными слотами диапазона (arch/14 §2.4
  п.2); (б) E2eEnvironment не содержит литерального PortRange — окно
  контура резервируется динамически bind'ом (первым портом публикуется
  etcd), занятость → сдвиг окна, бюджет попыток конечен (быстрый фейл с
  диагностикой, не вечный ретрай); (в) окна параллельных контуров не
  пересекаются (проверяемо в контрольном прогоне с ≥2 контурами: фактические
  published-порты контуров дискретны); (г) все контейнеры контура получают
  host-порты последовательно из своего окна; (д) прогоны приёмки фазы 4
  (N=3/5/6) — без «port is already allocated» между контурами (телеметрия
  docker-логов серий).

## 9. Риски

- **Невоспроизводимость симптома А** (сосед mergе-гейта t06 не повторён
  генератором) — риск снят ревизией 7: симптом А (внешний сосед) вне
  предмета, до-митигационные улики остаются историей (§1); проверка
  опирается на параллельные прогоны серии (симптом Б, N=3/5/6).
- **Флейк-природа измерений** (серия 37–59 мин): матрица держится
  минимальной, каждый прогон имеет единственную изменяемую переменную;
  спорный результат повторяется один раз с той же гипотезой.
- **Docker Desktop обновления меняют поведение резолвера** — канон
  формулируется через наблюдаемые признаки деградации (что смотреть), а не
  только через число N.
- **Смена режима прогона всей сборки** (атрибут удалён, N=3 стал реальным):
  не-E2E защищены коллекцией (ограничение §7), но любые тесты, тихо
  полагавшиеся на последовательность ВСЕЙ сборки (порядок между
  коллекциями), требуют внимания при появлении флейков — фиксируется в
  журнале, а не расширяет рамки t24.
- **Миграция усыновлённых контейнеров из `pgw-net`**: ensure обязан ловить
  расхождение сети (контракт arch/14 §2.1 — нода и агенты в одной сети
  кластера); пропущенный случай = агент, не видящий мастера, — ловится
  юнит/интеграционными проверками ensure и E2E-базлайном.
- **Рост числа сетей** (per-cluster на каждый кластер): короткоживущие,
  демонтаж чистит; в экспериментах не подбираемся к пулу ~30 (ограничение
  §7); сиротские сети ловит ассерт чистоты и контроль `docker network ls`.
- **Портовые окна**: (а) исчерпание окна ВНУТРИ контура — тест с несколькими
  кластерами × ноды × публикации: размер окна (200) и его достаточность
  проверяются контрольным прогоном самого порогового сценария; не хватает —
  ширина окна параметр окружения, а не причина раздувать смещениями;
  (б) сдвиг окна при занятости — бюджет попыток конечен (быстрый фейл с
  диагностикой: какие порты и кем заняты); (в) эфемеральные исходящие
  соединения хоста могут попадать в выбранное окно после резервирования —
  etcd-bind запирает первый порт, остальные слоты заняты контейнерами
  последовательно; остаточный риск ловится внутриконтурной проверкой
  занятости движка (docker ∪ portalloc) и ретраем create.
