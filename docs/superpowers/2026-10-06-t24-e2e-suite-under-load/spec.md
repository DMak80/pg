# Spec: t24-e2e-suite-under-load — устойчивость полной E2E-серии к параллельной нагрузке

Тег roadmap: `t24-e2e-suite-under-load` (трек reliability, P3, влияние N).
Канон требований: `arch/roadmap/reliability.md`, пункт `t24` (первоисточник; ниже —
развёрнуто в spec). Рабочие каноны: `AGENTS.base.md` §13 (E2E), `AGENTS.md`,
`docs/e2e-isolation.md`, `docs/e2e-launch.md`.

## 1. Проблема и контекст

Полная docker-E2E-серия PgWorker (26 фактов, все классы `E2e*` в
`src/tests/PgWorker.IntegrationTests/E2e/`, ~37–59 мин при параллелизме N=3)
обязана быть устойчивой к параллельной нагрузке на том же docker-хосте
(соседние прогоны серий, dev-стенд, соседние контуры самой серии). Сегодня
это не так — два зафиксированных симптома:

- **Симптом А (мерж-гейт t06, 2026-09-29).** При тяжёлом соседнем прогоне на
  том же хосте серия одним фильтром подвисает на существующих сценариях
  (Restore-переход, WalStream AC2–AC7); те же классы, прогнанные
  последовательно, — зелёные.
- **Симптом Б (мерж-гейт t27, 2026-10-05).** При 5 параллельных изолированных
  E2E-контурах (внутри одной серии) разрешение имён внутри docker-сетей
  деградирует: в логах PG-нод `getaddrinfo returns an empty list`, стрим-клиенты
  получают мгновенные (~0,3 с) фейлы коннекта в transient-цикле; зафиксирован
  упавший WalStream-сценарий promote. Ускорения от N=5 нет: 58 м 59 с / 26
  фактов (25/26 зелёные) против 37 м 37 с / 24 (24/24) при N=3.

Уже исключено расследованиями t27: conn-лимит PG (`too many connections` —
0 улик), пул адресов docker-сетей (пик 3 из ~30). Канон прогона до устранения
причины: **≤3 параллельных контура** (`XunitMaxParallelThreads=3` в csproj).

Факты об окружении, на которые опирается расследование:

- Хост — macOS (darwin), docker-хост один на серию: Docker Desktop; имена
  внутри сетей резолвит embedded DNS (127.0.0.11), `host.docker.internal` —
  спец-резолвер; Patroni-ноды, wal-агенты, бэкап-джобы и воркеры ходят друг
  на друга ПО ИМЕНАМ (алиасы etcd/MinIO в сети окружения, имена нод
  `pgw-<C>-*`, `host.docker.internal:<published-port>`).
- Один контур серии — это сеть `pgw-en-{guid}` + etcd + MinIO + per-cluster
  сети движка + PG-ноды с Patroni + бэкап/wal-джобы + хост-процессы воркеров.

Конфигурационный долг (закрывается задачей):

- **Источник истины параллелизма в двух местах.** В
  `src/tests/PgWorker.IntegrationTests/AssemblyInfo.cs` стоит
  `[assembly: CollectionBehavior(CollectionBehavior.CollectionPerAssembly, DisableTestParallelization = true)]`
  с комментарием «e2e tests share etcd/docker state and must run sequentially» —
  атрибут введён 2026-08-26 и УСТАРЕЛ после введения канона изоляции
  (guid-контуры), фактически перекрыт настройками csproj от 2026-10-05
  (`XunitParallelizeTestCollections=true`, `XunitMaxParallelThreads=3`,
  `XunitParallelizeAssembly=false` — фактическое поведение подтверждено
  реальными параллельными прогонами 3–5 контуров). Мёртвый атрибут с ложным
  комментарием — ловушка для следующего читателя.
- **Канон прогона серии нигде не описан целиком:** потолок N=3 — только в
  комментарии csproj; в `docs/e2e-launch.md` (канон запуска) раздела про
  параллелизм/соседнюю нагрузку нет.

## 2. Цель

Полная E2E-серия устойчива к параллельной нагрузке на том же docker-хосте в
границах зафиксированного канона прогона. Причина деградации найдена и ЛИБО
устранена (потолок параллелизма поднят и доказан прогонами), ЛИБО осознанно
принята как ограничение docker-хоста и закрыта каноном N=3 с рельсами.
Выбор между ветками — НЕ молчаливый: он делается на гейте фазы 2 по
измеримым критериям (раздел 6) и фиксируется в журнале задачи; при
неоднозначности — вопрос пользователю через `AskUserQuestion`.

Вторичные цели:

- **Воспроизводимость:** нагрузочные диагностические прогоны — управляемые и
  повторяемые (генератор соседней нагрузки с профилями), а не ручная
  импровизация «погоняю рядом что-нибудь тяжёлое».
- **Порядок в конфигурации:** один источник истины параллелизма; устаревший
  атрибут и комментарий убраны.
- **Канонизация:** `docs/e2e-launch.md` получает раздел «Параллелизм и
  нагрузка» (потолок N, правило соседних прогонов, признаки деградации,
  действия при фейле) — согласован с csproj.

Задача НЕ меняет контракты `arch/**` (тестовая инфраструктура и канон
прогона — не продуктовый контракт); roadmap-гейт закрывается по общему
правилу трека (раздел 8, AC8).

## 3. Принципы

1. Буква канонов E2E: изоляция guid-контурами с own-only teardown и ассертом
   чистоты (`docs/e2e-isolation.md`), телеметрия «что произошло — по логам,
   без перезапуска» (`docs/e2e-launch.md`), динамические порты, никакой
   мутабельной shared-инфраструктуры между контурами. t24 работает В ГРАНИЦАХ
   этого канона — не ослабляя его.
2. Гипотеза — ДО эксперимента, с проверяемыми следствиями; эксперимент обязан
   РАЗЛИЧАТЬ гипотезы (меняет одну переменную). Прогон без сформулированной
   гипотезы — нарушение (в т.ч. духа e2e-launch §4: перезапуск «авось
   зелёное» запрещён; эксперименты фаз 1–2 — новые прогоны с гипотезой, не
   перезапуски упавших).
3. Никаких «увеличим таймаут/бюджет — авось проедет»: каждый обнаруженный
   подвис/фейл получает объяснение по телеметрии до любого изменения бюджета.
4. Изменения прод-кода (воркер, приёмник WAL, движок) — только если причина
   локализована в нём и фикс каноничен (production-ready); основное поле
   задачи — тестовая инфраструктура и канон прогона.
5. Результаты расследования живут в журнале задачи
   (`docs/superpowers/2026-10-06-t24-e2e-suite-under-load/` — рядом с этим
   spec): каждый прогон — гипотеза, условия, измерения, вердикт.
6. Язык — русский для документации/журнала; идентификаторы — английские.

## 4. Стартовый набор гипотез (уточняется в фазе 1; не взаимоисключающие)

- **H1 — DNS-резолвер Docker Desktop деградирует.** Embedded DNS / vpnkit
  медленнее или ошибается при росте параллельных сетей/контейнеров/запросов.
  Прямо согласуется с уликой `getaddrinfo returns an empty list` при N=5 и
  мгновенными ~0,3-с фейлами коннекта стрим-клиентов. Проверяемые следствия:
  латентность/ошибки резолва растут с числом сетей (видно синтетическим
  DNS-зондом без PG вообще); фейлы приходят именно на этапе разрешения имени
  (алиас сети / `host.docker.internal`), а не TCP-коннекта/хендшейка.
- **H2 — CPU/IO-конкуренция на хосте.** N контуров × (PG-ноды+Patroni, etcd,
  MinIO, джобы, воркеры) перегружают хост: сессии Patroni↔etcd таймаутятся →
  failover-каскады (упомянуты при откате 5→3), акцепты медленные → коннекты
  падают в transient-циклах. Следствия: корреляция фейлов с загрузкой CPU
  хоста и load average; синтетическая CPU/IO-нагрузка (без DNS-шума)
  воспроизводит фейлы коннекта.
- **H3 — «подвисание» = транзиент-циклы против бюджетов фикстур.** Прогон не
  висит, а честно ретраится (полл 500 мс, ErrorDelayMs=500), но при
  деградировавшем коннекте упирается в бюджеты (ожидания сценариев 120–360 с,
  PatroniBootSec=300 у движка) — снаружи выглядит висяком. Следствия: фейл по
  бюджету сопровождается журналом прогресса (`[PHASE] … elapsed=…`), между
  ретраями есть движение; на снятой телеметрии виден прогресс до обрыва.
- **H4 — соседний прогон как множитель.** Деградация определяется СУММАРНОЙ
  нагрузкой docker-демона (контейнеры/сети/IO всех процессов хоста), а не
  только контурами самой серии — тогда «серия одним фильтром при тяжёлом
  соседе» падает там, где одиночный класс (меньше совокупной нагрузки)
  выживает. Следствия: порог воспроизведения зависит от K соседних контуров,
  а не от N самой серии; симметрия — генератор соседней нагрузки воспроизводит
  симптомы при N≤3.

## 5. Структура / компоненты (что строится)

1. **Диагностический нагрузочный генератор** — временный инструмент ветки
   задачи (не постоянный тест): поднимает K «шумовых» изолированных контуров
   (по канону изоляции: guid-имена, своя сеть, собственный teardown) с
   профилями: `dns` (шторм резолвов внутрисетевых имён и
   `host.docker.internal`), `cpu`, `io`, `full` (комбинация, паттерн
   реального контура). Управление — аргументы запуска (K, профиль, время).
   Реализация минимальная (YAGNI): один класс/скрипт поверх testcontainers
   или docker-CLI; локальные образы, ничего в registry.
2. **Синтетический DNS-зонд** — циклический резолв набора имён (алиас сети,
   `host.docker.internal`, внешнее имя) с логированием исхода и латентности.
   Встраивается в шумовые контуры и (опционально, env-флаг
   `PGW_TEST_E2E_DNS_PROBE=1`) в тестовые окружения — доказательная база
   «резолв умер, а не PG». Малый образ/скрипт из локального base.
3. **Матрица экспериментальных прогонов серии** — полная E2E-серия на Release
   при варьируемых (N; профиль и K соседней нагрузки) с фиксацией: время
   серии, зелёность, `[PHASE]`-тайминги, телеметрия teardown (артефакты
   `/tmp/pgw-e2e-artifacts-*`), логи DNS-зонда. Состав матрицы — раздел 6.
4. **Приведение конфигурации параллелизма к одному источнику истины** —
   убрать устаревший `CollectionBehavior`-атрибут из `AssemblyInfo.cs`
   (фактическое поведение задаёт csproj), комментарий-обоснование канона —
   в csproj и docs. Проверить и зафиксировать, что интеграционные не-E2E
   классы той же сборки после этого НЕ меняют поведение (атрибут и так
   перекрыт) — их параллелизм вне рамок t24.
5. **Раздел «Параллелизм и нагрузка» в `docs/e2e-launch.md`** — канон
   прогона: потолок N (по исходу гейта), правило соседних прогонов (сколько
   контуров суммарно допустимо на хосте, включая dev-стенд), признаки
   деградации (что смотреть в логах: getaddrinfo empty, рост `[PHASE]`
   elapsed), действия при фейле. Согласование с комментарием csproj.
6. **(Только ветвь «устранено» гейта)** — митигации по найденной причине;
   состав определяется фазой 2. Кандидаты-примеры (НЕ обязательны заранее):
   снижение DNS-зависимости горячего тракта (джобы/приёмник на
   published-портах и IP вместо имён, где канон это допускает), настройки
   резолвера/количества сетей, ограничение одновременных контуров
   per-класса. Каждый кандидат проходит через свой мини-эксперимент.

## 6. Фазы

### Фаза 0 — базлайны (без новых инструментов)

- Контрольные прогоны: полная серия при N=3 без соседней нагрузки (эталон
  времени/зелёности) и N=1 (последовательный). Хост чист между прогонами
  (контроль остатков по канону AGENTS.md).
- Выход: базлайн-тайминги фаз в журнале задачи; подтверждение, что «тихое»
  состояние серии зелёное.

### Фаза 1 — воспроизведение и инструменты

- Реализуются генератор и DNS-зонд (п. 5.1–5.2).
- Матрица прогонов (минимально достаточная, каждый — с гипотезой в журнале):
  1. (N=3, K=0) — контроль;
  2. (N=3, K=тяжёлый сосед `full`) — воспроизведение симптома А;
  3. (N=5, K=0) — воспроизведение симптома Б (контроль известных измерений);
  4. (N≤2, K=тяжёлый сосед) — проверка H4 (порог от суммарной нагрузки);
  5. синтетический DNS-зонд при 0/1/3/5/7 живых сетях — кривая резолва без
     PG вообще (H1 в чистом виде).
- Выход: симптомы устойчиво воспроизведены (или опровергнуты) с измерениями;
  данные, различающие гипотезы.

### Фаза 2 — различение гипотез

- Изолирующие эксперименты: DNS-латентность от числа сетей без PG (H1);
  CPU/IO-нагрузка без DNS-шума → фейлы коннекта? (H2); разбор фейлов упавших
  прогонов фазы 1 по телеметрии — где именно умирает соединение (резолв /
  TCP-коннект / хендшейк), какие бюджеты съедены, был ли прогресс (H3).
- Выход: карта «симптом → причина → измерение → подтверждено/исключено» для
  H1–H4; вердикт «устранимо в наших границах или это ограничение
  Docker Desktop/хоста»; оценка стоимости митигации против выгоды
  (ускорения от N=5 нет — уже измерено; выгода возможна только в
  устойчивости, не в скорости).

### ГЕЙТ РЕШЕНИЯ (после фазы 2)

Решение «устранить vs канон N=3» фиксируется в журнале задачи с опорой на
критерии:

- **Устраняем и поднимаем N** — если причина локализована в наших границах
  (код тестов / конфигурация контуров / имена вместо DNS) И митигация дёшева
  И контрольная матрица (п. 6.3 без соседей + с соседями) показывает
  устойчивость при N>3 без DNS-деградации.
- **Канон N=3 + рельсы** — если причина — ограничение Docker Desktop/хоста
  (vpnkit/резолвер), или митигация дороже выгоды, или N>3 не даёт
  измеримого выигрыша.
- Критерии не дают однозначного ответа → вопрос пользователю через
  `AskUserQuestion`, ответ — в журнал.

### Фаза 3 — реализация решения

- **Ветвь А (канон):** N=3 закреплён как канон (csproj уже так); рельса —
  предупреждение при запуске серии с фактически большим числом потоков, чем
  канон (E2eEnvironment при старте серии сверяет фактический
  `MaxParallelThreads`/конфиг раннера и пишет предупреждение в журнал
  прогона; жёсткий запрет НЕ вводим — диагностические прогоны с N>3
  легальны, но обязаны быть громкими); раздел в `docs/e2e-launch.md`;
  чистка `AssemblyInfo.cs`.
- **Ветвь Б (устранение):** реализуются митигации по карте фазы 2; повторная
  матрица прогонов доказывает устойчивость при новом N; канон в docs и
  csproj обновлён на новое N; чистка `AssemblyInfo.cs`.
- В обеих ветвях: если подтверждён вклад H3 — точечные уточнения
  бюджетов/телеметрии медленных фаз, каждое с объяснением по телеметрии
  (запрет «просто увеличить таймаут» не снимается).

### Фаза 4 — приёмка и канонизация

- Финальный контрольный прогон: полная серия на свежем Release по канону —
  зелёная, чистый teardown всех контуров, хост чист.
- Мерж-гейт трека: пункт `t24` снят из `arch/roadmap/reliability.md`, строка
  в `arch/roadmap/reliability-report.md` перенесена в «Сделано» — тем же
  коммитом.

## 7. Ограничения

- Канон изоляции E2E нерушим: guid-контуры, own-only чистка, ассерты чистоты,
  динамические порты. Никаких «общего etcd, чтобы сэкономить сети».
- Таймауты ожиданий агента ≤30 с с проверкой (AGENTS.base §12); полл в тестах
  500 мс — канон репо.
- Перезапуск упавших прогонов для выяснения «что было» запрещён; каждый
  новый прогон фаз 0–3 — с гипотезой, согласованной с журналом.
- Прод-код — только при локализованной в нём причине (принцип 4).
- Локально собираемые образы в registry не кладутся; новые ВНЕШНИЕ образы не
  вводятся (генератор/зонд — из уже зеркалированных base-образов локального
  registry; если нужен новый внешний образ — строки в `images.txt` по ранбуку,
  что в рамках задачи не предполагается).
- Суммарное число живых user-сетей в экспериментах не подбирается к пулу
  (~30) и не пересекается с dev-стендом; после каждой серии — контрольный
  `docker network ls` / зачистка остатков по канону.
- Генератор нагрузки — инструмент диагностики: постоянным тестом в main не
  остаётся (исход — по гейту: DNS-зонд как опциональная телеметрия E2E может
  остаться).
- Интеграционные не-E2E тесты той же сборки: их параллелизм/устойчивость —
  вне рамок t24 (фиксируется только отсутствие ИЗМЕНЕНИЯ их поведения из-за
  чистки AssemblyInfo).

## 8. Критерии приёмки

- **AC1 (воспроизведение).** Каждый заявленный симптом (А: подвисание серии
  при тяжёлом соседе; Б: DNS-деградация при N≥5) либо устойчиво воспроизведён
  управляемым генератором, либо опровергнут — с измерениями; итог — в журнале
  задачи.
- **AC2 (причина).** Для H1–H4 есть строки «следствие → измерение →
  подтверждено/исключено» со ссылками на артефакты прогонов (docker-логи,
  логи DNS-зонда, `[PHASE]`-тайминги, артефакты `/tmp/pgw-e2e-artifacts-*`).
- **AC3 (гейт решения).** Выбор ветки зафиксирован в журнале с критериями и
  измерениями; при неоднозначности — задокументированный вопрос/ответ
  пользователя.
- **AC4 (конфигурация).** Источник истины параллелизма один — csproj;
  устаревший `CollectionBehavior`-атрибут и комментарий из `AssemblyInfo.cs`
  удалены; фактическое поведение раннера (N=3 по канону или новое N по
  ветке Б) подтверждено НАБЛЮДЕНИЕМ прогона, не только чтением конфига.
- **AC5 (канон прогона).** `docs/e2e-launch.md` содержит раздел
  «Параллелизм и нагрузка»: потолок N, правило соседних прогонов, признаки
  деградации, действия при фейле; комментарий csproj согласован с docs.
- **AC6 (стабильность).** Финальный прогон полной серии на свежем Release по
  канону — зелёный; полная чистота хоста после (ни контуров, ни сетей, ни
  томов своих guid). Для ветки А (канон N=3) — две последовательные зелёные
  серии (устойчивость, а не удача); для ветки Б — матрица (без соседа и с
  соседом) зелёная при новом N.
- **AC7 (рельсы, ветвь А).** Запуск серии с фактическим N выше канона даёт
  громкое предупреждение в журнале прогона (проверено прогоном с
  переопределённым N).
- **AC8 (мерж-гейт трека).** Пункт `t24` снят из `arch/roadmap/reliability.md`
  и `reliability-report.md` тем же мерж-коммитом; в отчёте — строка
  «Сделано» с сутью решения и влиянием на характеристику N (устойчивость
  приёмки).

## 9. Риски

- **Невоспроизводимость симптома А** (сосед mergе-гейта t06 не повторён
  генератором) — сама по себе результат: фиксируется в журнале с профилями,
  которые НЕ воспроизводят; канон тогда опирается на симптом Б и
  профилактические рельсы.
- **Флейк-природа измерений** (серия 37–59 мин): матрица держится
  минимальной, каждый прогон имеет единственную изменяемую переменную;
  спорный результат повторяется один раз с той же гипотезой.
- **Docker Desktop обновления меняют поведение резолвера** — канон
  формулируется через наблюдаемые признаки деградации (что смотреть), а не
  только через число N.
