| Гипотеза | Проверяемое следствие | Измерение | Вердикт (подтверждено/исключено) | Артефакт |
|----------|-----------------------|-----------|----------------------------------|----------|
| H1 — DNS-резолвер Docker Desktop деградирует (латентность/ошибки растут с числом сетей; фейлы на этапе резолва, не TCP) | | | | |
| H2 — CPU/IO-конкуренция на хосте (корреляция фейлов с загрузкой; синтетическая CPU/IO без DNS-шума воспроизводит фейлы коннекта) | | | | |
| H3 — «подвисание» = транзиент-циклы против бюджетов фикстур (журнал прогресса `[PHASE] … elapsed` до обрыва; движение между ретраями) | | | | |
| H4 — соседний прогон как множитель (порог от суммарной нагрузки K соседей, не от N серии) | | | | |

## Наблюдения вне прогонов

- ФОКУС-РАЗБОР «failed to resolve host e2e-etcd1» (распоряжение пользователя 2026-10-06; по телеметрии №3/№3п/№4, без перезапусков упавших). ИСТОЧНИК: процесс Patroni (python, `pgworker-node:e2e`) в Patroni-нодах кластеров; DCS-подключение etcd3. МЕХАНИКА (улики — артефакт 9852f46b, нода shard1-shard1a): ноды сидят ТОЛЬКО в сети `pgw-net` (инспект: NetworkSettings=[pgw-net]); etcd-узел окружения — ТОЛЬКО в сети окружения `pgw-en-{runId}` с алиасом `e2e-etcd1`; сети НЕ пересекаются → имя `e2e-etcd1` в DNS-зоне pgw-net НЕ СУЩЕСТВУЕТ. При этом etcd запущен с `--advertise-client-urls=http://e2e-etcd1:2379,http://host.docker.internal:<порт>` (E2eEnvironment) — etcd ОТДАЁТ Patroni оба URL при member-discovery, и Patroni ретраит ПО ВСЕМ: `INFO: Selected new etcd server http://e2e-etcd1:2379` → `WARNING: failed to resolve host e2e-etcd1: [Errno -2] Name or service not known` → `ERROR: … getaddrinfo returns an empty list` (НЬЮАНС: именно эта строка — известная улика «симптома Б» из t27 — принадлежит Patroni-клиенту etcd, а НЕ docker-резолверу!) → `Selected new etcd server http://host.docker.internal:<порт>` — рабочий. РЕШОЛВЕР: embedded docker DNS 127.0.0.11 контейнера (NXDOMAIN для имени из чужой сети — КОРРЕКТНОЕ поведение, не деградация). КОГДА: (а) старт ноды — единичный мгновенный фейл (9 мс) и переключение — безвредно; (б) потеря etcd-сессии под нагрузкой — БУРЯ десятков resolve-ретраев минутами (shard2a rs-time: 41 WARN в 2 минуты БЕЗ DCS) → HA-контур кластера деградирует → бюджеты Restore/WalStream съедаются. ЧАСТОТА N-ЗАВИСИМА: N=3 — буры у большинства кластеров (фейлы Restore 2/2 прогонов); N=1 — 2714 WARN в 25 из 32 артефактов №4, но серия зелёная (конкуренции нет — ретраи быстрые, бюджеты вывозят): ошибка необходима, но фатальна только с N=3-конкуренцией. ОТЛИЧИЕ ТРАКТА ЗОНДА: зонд живёт в сети окружения, где алиас `e2e-etcd1` ЕСТЬ → 0 фейлов; его латентность-выбросы до ~1 с — отдельный слабый сигнал, НЕ тот же феномен. ВЫВОД: «симптом Б»-улика getaddrinfo в логах PG-нод = конфигурационная дыра тестового контура (advertise-client-urls содержит внутрисетевой URL, недостижимый из pgw-net),放大енная N=3-конкуренцией до фейлов. КАНДИДАТ МИТИГАЦИИ (для гейта Task 7): убрать `e2e-etcd{i}:2379` из advertise-client-urls (оставить только host.docker.internal:<порт>) — Patroni потеряет мёртвый endpoint; правка ОДНОЙ строки E2eEnvironment, находится в наших границах.
