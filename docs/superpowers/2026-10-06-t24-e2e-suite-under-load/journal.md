## Гейт решения (AC3)

- Критерии: spec §6 «ГЕЙТ РЕШЕНИЯ» (устраняем и поднимаем N — причина в наших границах + митигация дёшева + матрица зелёная при N>3; канон N=3 + рельсы — ограничение Docker Desktop/хоста, или митигация дороже выгоды, или N>3 без выигрыша).
- Измерения к гейту: (заполняет Task 7 из карты гипотез и сводки прогонов)
- РЕШЕНИЕ: (заполняет Task 7: ветка А или Б, обоснование по критериям; при неоднозначности — вопрос/ответ пользователя)
- Судьба инструментов: генератор E2eLoadGen — удалить перед мержем (Task 10); DNS-зонд в E2E — (решение гейта: остаётся как опциональная телеметрия / удаляется)

Анализ паттерна завершения тестов (interleaving классов): ДО — 40 смен класса на 41 класс (строгие блоки = последовательное исполнение всей сборки), ПОСЛЕ — 225 смен (параллельное); сумма длительностей тестов: ДО 172 с при стене ~220 с тестовой фазы, ПОСЛЕ 184 с при ~90–100 с (отдельные тесты замедлились конкуренцией — сумма выше при стене ниже). ВЫВОД: атрибут CollectionBehavior(DisableTestParallelization=true) в запуске `dotnet test <проект>` был РАБОЧИМ, не мёртвым — трактовка spec §1 для этого способа запуска эмпирически неверна. Файл возвращён (`git checkout HEAD --`), не закоммичен.
- Отладка в рамках шага (гипотеза ДО запуска): контрольные пары плана шли по ПУТИ `dotnet test src/tests/PgWorker.IntegrationTests` (проект), а канонический запуск серии — `dotnet test src/PgWorker.slnx`. Гипотеза: solnx-путь доставляет csproj-свойства (XunitParallelizeTestCollections/MaxParallelThreads) в конфигурацию раннера и перекрывает атрибут — тогда (ДО-атрибут, solnx) параллелен, атрибут мёртв для КАНОНИЧЕСКОГО запуска серии, а расхождение моих контрольных пар — артефакт способа запуска (проект), не удаления атрибута. Проверка: не-E2E прогон через solnx с живым атрибутом, той же детализацией; interleaving классов параллелен → гипотеза подтверждена; последователен → атрибут жив и для канона (тогда NEEDS_CONTEXT по Step 5).
- Отладка, РЕЗУЛЬТАТ — гипотеза solnx ОПРОВЕРГНУТА (`/tmp/pgw-t24-none2e-slnx-attr.log`): с живым атрибутом через `dotnet test src/PgWorker.slnx` IntegrationTests идут ПОСЛЕДОВАТЕЛЬНО (interleaving: 308 строк, 41 класс, 40 смен, макс. блок 31 — строгие блоки классов). Итоговая эмпирика атрибута:
  - (атрибут жив, запуск по проекту) = последовательно;
  - (атрибут жив, запуск по solnx) = последовательно;
  - (атрибут удалён, запуск по проекту) = параллельно (225 смен классов), 1 фейл WalReceiver (`starting`-цикл за бюджет 30 с), время 272→110 с.
  ВЫВОД: `CollectionBehavior(DisableTestParallelization=true)` — РАБОЧИЙ при любом `dotnet test`; csproj-свойства (`XunitParallelizeTestCollections=true`, `XunitMaxParallelThreads=3`) его НЕ перекрывают — предпосылка spec §1 «атрибут мёртв, перекрыт csproj» инвертирована: мёртввы именно csproj-свойства в обычном запуске, источник истины был атрибут, и он задаёт N=1. Следствие для канона: «фактический N=3» в обычном запуске серии никогда не существовал — обычные прогоны шли последовательно (N=1), а наблюдавшиеся t27 «3–5 контуров» возникали при внешнем переопределении параллелизма (MSBuild `-p:XunitMaxParallelThreads=N` при запуске). Удаление атрибута — не чистка мёртвого кода, а СМЕНА режима прогона всей сборки: E2E-серия реально станет N=3 (впервые в каноническом запуске), не-E2E — параллельными (radical изменение их поведения: spec §7 «фиксируется отсутствие изменения» становится невыполнимым без доп. механики).
  Побочно (вне рамок t24, зафиксировано как условие): в этом же slnx-прогоне упали 2 теста KafkaWorker.IntegrationTests (CaRotationTests.CaRotate_RollingWindow_FinalsOnNewCa, ReassignmentTests.Reassign_Повторная_Подача_Безопасна, оба ~22 с) — другая сборка, не разбирается в t24; хост после прогона чист (pgw-контейнеров 0, сетей 0).
