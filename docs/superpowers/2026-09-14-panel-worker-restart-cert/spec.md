# Спецификация: управление сертификатами API воркеров и их перезапуск из AdminPanel

Дата: 2026-09-14. Домены: AdminPanel (backend+frontend), PgWorker.App,
KafkaWorker.App, контракт etcd.

## 1. Цель

Дать оператору из панели две способности для обоих воркеров установки
(PgWorker — «бд», KafkaWorker — «кафки»):

1. **Перезапустить воркеров** — чтобы они перечитали конфигурацию (в первую
   очередь серверный сертификат своей входящей mTLS-грани).
2. **Поставить воркерам нужный серверный сертификат** — сертификат хранится
   в etcd, панель может его создать (сгенерировать) и поменять; воркеры
   сертификат только читают и используют для входящего HTTPS (свои
   mTLS-эндпоинты API, включая `/healthz`, `/metrics`, `/api`).

Критическое требование безопасности операции: **если сертификат влияет на
дальнейшие коммуникации воркеров с их подчинёнными сервисами — сертификат
НЕ обновлять, но явно сообщить об этом пользователю**. Панель при создании/
замене оценивает, затрагивает ли сертификат исходящие коммуникации воркеров
(PgWorker → PG-шарды/Patroni/docker-хосты/etcd/S3; KafkaWorker →
kafka-брокеры/docker-хосты/etcd), и при любом пересечении отказывает в
записи с явным сообщением (см. §4.3).

Контракт обновлён в `arch/` ДО этой спеки (arch-first): arch/14 §1.1/§3.3/§4,
arch/16 §1.1/§3.1/§4, arch/adminpanel/02 §2.3.1/§2.3.2/§9.9,
arch/adminpanel/03 §1/§3/§3.7, arch/adminpanel/01 (потоки панели),
arch/adminpanel/README.

## 2. Принципы

1. **Источник истины — etcd, писатель — панель**. Серверные серты API
   живут в ключах `/workers/api_tls/<worker>` (JSON `cert_pem`+`key_pem`+
   аудит). Панель — единственный писатель; воркеры только читают ключ при
   старте. Запись идёт напрямую в etcd (не через API воркера): воркер не
   может «принять» серт без перезапуска, а панель должна уметь положить
   серт до первого запуска воркера. Это вторая (после §9 provisioning)
   категория прямой записи панели в etcd.
2. **Применение — только перезапуском**. Серты живут всё время жизни
   процесса (Kestrel); замены на живой грани нет. Панель всегда показывает
   статус применения (applied / pending restart) — оператор видит, что
   перезапуск ещё требуется.
3. **Рестарт — самостоятельный graceful-stop воркера**. Панель НЕ получает
   docker-доступ (канон: панель никогда не трогает контейнеры). Команда
   `POST /api/restart` воркеру → 202 → `IHostApplicationLifetime.
   StopApplication` → контейнер перезапускается docker-политикой
   `restart: unless-stopped` (deploy-канон). Клэймы/джорнал/заявки — в
   etcd, lease гаснет ≤15 с: операции продолжает этот же или другой
   инстанс — рестарт безопасен для кластеров.
4. **Env-секреты — бутстрап-фоллбек**. `PGW_API_TLS_{CERT,KEY}` /
   `KFW_API_TLS_{CERT,KEY}` остаются рабочими: если etcd-ключа нет, воркер
   стартует на env/volume-серте (обратная совместимость установок без
   управляемого серта; статус в панели — `unmanaged`). Приоритет:
   etcd-ключ > env. `*_CLIENT_CA` (валидатор клиентских сертов) — только
   env, панелью не меняется.
5. **Серт входящей грани ≠ материалы исходящих**. Исходящие коммуникации
   воркеров используют другие материалы: docker Engine API — unix-socket
   или docker-TLS-CA (env воркера); PG — per-cluster креды/DSN (etcd
   `/clusters/`); kafka-брокеры — per-cluster CA (`/kafka/clusters/<C>/
   ca_pem`); etcd — HTTP JSON gateway без клиентского серта. Управляемый
   серт проектируется так, чтобы физически не мог использоваться в
   исходящих, — это проверяется при записи (§4.3).
6. **Явность для пользователя**. Любой отказ «влияет на исходящие» —
   422 с причиной, в UI — баннер с текстом «сертификат влияет на
   коммуникации воркеров с их подчинёнными сервисами — обновление
   отклонено» и расшифровкой (CA / clientAuth / совпадение fingerprint).
7. **Приватный материал не покидает backend**. `key_pem` (и `cert_pem`)
   не отдаются в API/UI — только метаданные серта (subject, issuer, SAN,
   сроки, sha256-thumbprint, кем/когда записан) — прецедент kafka-паролей
   (02 §10.1).
8. **Домашняя установка, без enterprise**. Приватный ключ в etcd —
   осознанно допустим (etcd установки — закрытый контур; базовые правила:
   enterprise-защиты не нужны).

## 3. Структура и компоненты

### 3.1. Контракт etcd

Ключи (обычные, без lease; панель пишет, воркеры читают):

```
/workers/api_tls/pgworker     {"cert_pem":"<PEM>","key_pem":"<PEM>",
                               "updated_unix":<unix>,"updated_by":"<username>"}
/workers/api_tls/kafkaworker  (симметрично)
```

Дискавери-ключи воркеров получают опциональное поле `cert_thumbprint`
(sha256-hex серта, фактически применённого на грани):

```
/pgworker/api/<id>     {"url":…,"instance":…,"since_unix":…,"cert_thumbprint"?}
/kafkaworker/api/<id>  (симметрично)
```

Модель панели:

- `EtcdSnapshot` + `KafkaSnapshot`: новое поле `WorkerApiCert` — метаданные
  целевого серта своего воркера (парсинг ключа `/workers/api_tls/<worker>`;
  битый JSON — parseError-запись по канону, key_pem в модель не попадает —
  хранится только thumbprint и метаданные).
- `WorkerEndpoint` (AdminPanel.Core) — опциональный `CertThumbprint`
  (старые инстансы не пишут → null → статус `unknown`).

### 3.2. Воркеры (PgWorker.App, KafkaWorker.App — симметрично)

1. **Чтение серта при старте** — до поднятия Kestrel (в `Program.cs` до
   `ConfigureMtls`): одиночный HTTP-запрос `/v3/kv/range` к первому
   endpoint'у `Etcd:Endpoints` (формат gateway — base64, как EtcdGateway).
   Правила:
   - ключ есть и PEM валиден → серверный серт из ключа (источник — в логе
     старта; env-серт игнорируется);
   - ключ есть, но JSON/PEM битые → **fail-fast** с понятной ошибкой (ключ —
     явное намерение оператора, тихий fallback на env маскирует проблему);
   - ключа нет → env/volume-серт (как сейчас); env-серта тоже нет →
     fail-fast (действующее поведение);
   - etcd недоступен: env-серт есть → старт на env + warning; env-серта
     нет → fail-fast.
   Один общий ридер для обоих воркеров (копирование минимального кода —
   осознанное, по существующему паттерну TlsEndpoints у обоих воркеров).
2. **`POST /api/restart`** (новый эндпоинт обоих воркеров): без тела;
   заголовок `X-Requested-By` (оператор) — в лог. Ответ 202
   `{"restarting":true}`, затем отложенный на ~1 с graceful stop
   (`StopApplication`), чтобы ответ успел уйти. Хендлер — синглтон-класс
   по образцу Operations/*; в etcd ничего не пишет.
3. **`cert_thumbprint` в lease-ключе**: keepalive-контур (ClaimStore у
   PgWorker, аналог у KafkaWorker) пишет в value дискавери-ключа
   sha256-thumbprint серта, поднятого на грани (вычисляется при старте и
   передаётся в keepalive). Поле опционально для читателей.

### 3.3. Backend панели

1. **`AdminPanel.Etcd/Workers/WorkerCertService`** — ядро грани:
   - парсинг/валидация PEM-пары (пункты §4.3);
   - генерация self-signed листа (`CertificateRequest`, прецедент —
     `KafkaWorker.Core/Templates/ClusterPki.cs`): RSA-2048,
     CN=`<worker>-api`, SAN — DNS/IP-хосты живых advertise-URL инстансов
     этого воркера + `localhost`,`127.0.0.1`; EKU только serverAuth;
     `BasicConstraints CA=false`; срок 825 дней; NotBefore = now−5 мин;
   - чтение известного набора fingerprint'ов для проверки изоляции
     (per-cluster `ca_pem` всех kafka-кластеров из снапшота; ClientCa/
     ServerCa панели из конфига `AdminPanel:Workers:WorkerTls`);
   - запись ключа: создание — txn `compare version==0` + put (конкурентный
     POST → 409), замена — безусловный put; аудит `updated_by` — username
     сессии, `updated_unix` — now.
2. **`WorkerApiGateway`**: новый метод `SendAllAsync(worker, method, path,
   …)` — обходит ВСЕ живые endpoints (для рестарта), возвращает per-instance
   результаты; существующий `SendAsync` (failover на первый удачный) не
   меняется.
3. **`WorkerTlsHandler`**: расширение валидатора серверного серта — цепочка
   к ServerCa ИЛИ совпадение sha256-thumbprint с целевым сертом любого
   воркера (живые значения из снапшотов, панель доверяет сертам, которые
   сама записала). Без этого self-signed генерация рвала бы панели доступ
   к перезапущенному воркеру.
4. **`AdminPanel.Api/Operations/WorkersModule`** (query + команды, CQRS по
   канону):
   - `GET /api/workers` — сводка: по каждому воркеру инстансы (instance,
     url, since, health, applied-thumbprint) + целевой серт (метаданные)
     + вычисленный статус применения per-instance:
     - `applied` — thumbprint инстанса == thumbprint целевого;
     - `pending restart` — ключ есть, thumbprint инстанса другой;
     - `unmanaged` — ключа нет (инстанс на env-серте);
     - `unknown` — инстанс не сообщает thumbprint (старая версия).
   - `POST /api/workers/{worker}/api-cert/generate` — генерация + запись
     (валидация §4.3 к сгенерированному применяется всегда — самоконтроль);
   - `PUT /api/workers/{worker}/api-cert` — upload `{cert_pem, key_pem}`;
   - `DELETE /api/workers/{worker}/api-cert` — отказ от управляемого серта
     (откат к env; 404 если ключа нет);
   - `POST /api/workers/{worker}/restart` — `SendAllAsync` прокси
     `POST /api/restart`; живых инстансов нет → 503.
   Коды ответов — по 03 §1 (см. таблицу там); `worker` ∈
   {pgworker, kafkaworker} иначе 404.

### 3.4. Frontend (React/Mantine)

Страница `/workers` (`pages/WorkersPage.tsx`, пункт навигации «Воркеры»),
карточки PgWorker и KafkaWorker: инстансы (id, url, uptime, health-бейдж),
блок целевого серта (subject, issuer, SAN, сроки, thumbprint, кем/когда),
статус применения; действия: «Сгенерировать сертификат», «Загрузить
сертификат» (модал: два textarea/файла PEM), «Перезапустить воркера»
(красная, подтверждение с предупреждением о кратком окне недоступности API
и продолжении идущих операций после подъёма), «Убрать управляемый
сертификат» (красная, только при живом ключе). Отказ 422 — баннер с
формулировкой о влиянии на коммуникации с подчинёнными сервисами + причина.
Клиентская валидация форм — зеркало серверной (UX), сервер — источник
истины. Опрос — существующий polling (TanStack Query).

## 4. Протоколы

### 4.1. Создание (generate)

1. Панель генерирует лист §3.3 п.1 (SAN по живым URL; живых инстансов нет →
   SAN только localhost/127.0.0.1, в ответе warning).
2. Запись: txn `version==0` + put (первое создание); ключ уже есть → 409
   «сертификат уже управляется — замените (PUT) или удалите».
3. Ответ 201 `{worker, thumbprint, updatedUnix, updatedBy,
   restartRequired: true}`.

### 4.2. Замена (upload) и удаление

- PUT: полная валидация §4.3 → безусловный put (замена; панель —
  единственный писатель, перезапись чужого значения невозможна);
  ответ 201 как выше.
- DELETE: del ключа → 204; 404 если ключа нет. После удаления целевой серт
  отсутствует — воркер при следующем старте вернётся к env-серту (статус
  инстансов станет `unmanaged`).

### 4.3. Валидация «сертификат не затрагивает исходящие коммуникации»

Сервер панели проверяет ДО записи; нарушение → запись НЕ выполняется,
ответ **422** с заголовком ProblemDetails: title «Сертификат влияет на
коммуникации воркеров с их подчинёнными сервисами», detail — конкретная
причина. Правила:

| # | Правило | Код |
|---|---|---|
| 1 | Серт — лист: BasicConstraints CA=FALSE (CA=TRUE → это потенциальный trust anchor исходящих — отказ) | 422 |
| 2 | EKU (если задан) содержит serverAuth и НЕ содержит clientAuth (клиентский серт пригоден в исходящих — отказ) | 422 |
| 3 | sha256-thumbprint серта не совпадает ни с одним известным материалом исходящих/доверия установки: per-cluster `ca_pem` всех kafka-кластеров, ClientCaPem и ServerCaPem панели | 422 |
| 4 | PEM-пара синтаксически валидна, приватный ключ соответствует сертификату | 400 |
| 5 | Срок действия: NotBefore ≤ now < NotAfter | 400 |
| 6 | Есть хотя бы один SAN (DNS или IP) | 400 |

Правила 4–6 — «не годен как серверный» (обычная валидация, 400); правила
1–3 — именно «влияет на коммуникации с подчинёнными сервисами» (422,
явное сообщение пользователю). Сгенерированный панелью серт проходит все
правила по построению (проверка всё равно выполняется).

### 4.4. Перезапуск

1. Панель резолвит живые endpoints воркера из снапшота; пусто → 503
   (+ существующий алерт `worker-api-unreachable` остаётся движителем).
2. На каждый endpoint — `POST /api/restart` (mTLS, `X-Requested-By`).
3. Ответ 202 `{results: [{instance, accepted: true} | {instance, error}]}`.
4. Воркер: 202 → пауза ~1 с → StopApplication → выход процесса → docker
   поднимает контейнер → при старте перечитывается etcd-серверный ключ →
   lease-ключ переподставится с новым `since_unix` и `cert_thumbprint`.
5. Панель тиками видит новый thumbprint → статус `applied`.

### 4.5. Ошибки и надёжность

- Сбой etcd при записи серта → 503, частичных состояний нет (одна txn/put).
- Рестарт при упавшем etcd: воркер стартует, ключа не прочитать → правила
  §3.2.1 (env-фоллбек или fail-fast).
- Воркер поднялся, но серт отвергнут панелью (не совпал ни ServerCa, ни
  thumbprint — теоретически при ручной порче ключа в etcd): панель
  показывает `pending restart`/ошибку соединения; лечение — повторная
  запись серта (PUT) или DELETE (откат на env) + рестарт.
- Идемпотентность: generate идемпотентен через 409 на живом ключе; PUT/DELETE
  идемпотентны по значению; рестарт повторяем (202 каждый раз).

  окружении с полным teardown.

## 6. Ограничения и сознательные НЕ-делания (YAGNI)

- Замена серта на живой грани без рестарта — не делается (серты живут
  процесс; усложнение SslStream-ротации не оправдано домашней установкой).
- `CLIENT_CA` воркеров (валидатор клиентских сертов) — не управляется
  панелью (смена сломала бы доступ панели/сида/prometheus к воркеру).
- Автопереключение серта по расписанию/ротация — вне задачи (roadmap при
  необходимости).
- Алерты «серт истекает» — вне задачи (метаданные в UI уже показывают
  сроки).
- Панель не проверяет hostname при подключении к воркеру (действующее
  поведение `WorkerTlsHandler`) — не меняется.
- Рестарт «всех воркеров одной кнопкой» — не делается: per-worker
  (`pgworker`/`kafkaworker`) достаточно.
- Запуск воркеров вне docker без restart-политики: рестарт оставит процесс
  остановленным (документировано в runbook; deploy-канон —
  `restart: unless-stopped`).

## 7. Критерии приёмки

1. **Создание**: на чистой установке (ключа нет) `generate` для обоих
   воркеров создаёт ключи; статус инстансов — `pending restart`; UI
   показывает бейдж «требуется перезапуск».
2. **Перезапуск применяет**: `POST /api/workers/{worker}/restart` → 202;
   после подъёма контейнера (`restart: unless-stopped`) инстанс жив,
   `cert_thumbprint` совпадает с целевым → статус `applied`; панель всё
   это время способна звать API воркера (self-signed серт принят
   thumbprint-доверием).
3. **Загрузка чужого серта**: валидный серверный лист (подписан install-CA
   или другой CA) принимается (PUT 201) и применяется рестартом; невалидная
   пара/просроченный/без SAN — 400 с причиной, ключ в etcd не меняется.
4. **Защита исходящих**: CA-серт, серт с EKU clientAuth, серт с
   fingerprint'ом равным per-cluster `ca_pem` kafka-кластера или ClientCa/
   ServerCa панели — все дают 422 «сертификат влияет на коммуникации
   воркеров с их подчинёнными сервисами — обновление отклонено» (с
   причиной), ключ в etcd НЕ записан, в UI — явный баннер.
5. **Исходящие воркеров не затронуты**: после замены серта и рестарта
   PgWorker продолжает provisioning/переезды (клэймы, docker, SQL),
   KafkaWorker — управление брокерами (SASL_SSL per-cluster CA не тронут).
6. **Откат**: `DELETE api-cert` → 204 → рестарт → воркер на env-серте
   (статус `unmanaged`), панель сохраняет доступ.
7. **Обратная совместимость**: воркер при отсутствии ключа стартует как
   раньше (env/volume); старые инстансы без `cert_thumbprint` не ломают
   `GET /api/workers` (статус `unknown`); деплой без изменений работает.
8. **Секретность**: `GET /api/workers` и UI не отдают PEM-материалы
   (только метаданные).
9. **Тесты**: юниты (валидатор/генератор/ридер/парсеры) и интеграция
   (команды, рестарт-эндпоинт) зелёные; E2E-мерж-гейт — кейс полного цикла
   на свежем Release с полным teardown (изоляция по канону docs/e2e-
   isolation.md).
