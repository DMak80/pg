## 2. Контракт, который проверяет тест AC10 (не меняется)

`arch/16-kafkaworker.md` §5 «Возрастная самозачистка (t10)» и §5 H
(PasswordRotator), а именно:

1. Живая, но НЕ начатая ca-заявка НЕ гейтит H (приоритет H перед K):
   при обеих живых заявках H доигрывает свою (del заявки в фазе B), затем
   K исполняет свою — взаимное ожидание (дедлок) невозможно. Гейтит H
   только ОТКРЫТОЕ окно CA-ротации (staging `ca_next_{key,pem}`).
2. Обе заявки доигрываются БЕЗ экспирации: фазы H (A rolling OLD+NEW →
   B txn-коммит NEW + del заявки → C rolling только NEW → done) и K
   (P/D/R/C) завершаются; ни одна journal-фаза не `expired`; исходы
   `done` в `ticket_outcomes/<C>` (`kind=password-app`, затем `kind=ca`);
   `app_password` и `ca_pem` фактически изменены.
3. `waiting-cluster` при ЖИВОЙ заявке — каноническая передержка H (§5 H:
   «кластер не поднят (нет endpoints/кредов) или не отвечает
   DescribeCluster → journal waiting-cluster»): тик при этом Success,
   заявка жива, экспирация — только под тройным гвардом «не начато» (t10).

Кейс AC10 проверяет п.1–2; буква ассертов (порядок фаз H→K, ключи, исходы,
отсутствие `expired`, смена пароля/CA) сохраняется. Механика ожидания и
диагностика изменены (влито, §5.2) — как это было сделано для AC12 фиксом
2026-10-17.

Прод-дополение к контракту, вводимое этой задачей (§5.5): afterCommit-хвост
(заявка снята фазой B, до done) не перезаписывает журнал waiting-фазами —
маркер мутации (`rotated-commit`/`phase-c`) — единственный носитель
возобновляемости фазы C. Waiting-фазы с живой заявкой (п.3) и вся механика
экспираций/гвардов t10 — НЕ меняются.

## 3. Диагноз: УСТАНОВЛЕН (D2 — прод-дефект PasswordRotator)

### 3.1. Механизм дефекта (подтверждён телеметрией приёмочной серии и кодом)

Приёмочная серия (шаг A5 исходного плана) воспроизвела AC10 за 4 м 53 с;
влитая телеметрия §5.1 дала полный контекст падения (journal.md «Красный
приёмочной серии»):

```
phase ticks: rotate:phase-a=1, rotate:waiting-cluster=195, rotate:rotated-commit=1
rotations=<none>; outcome=<none>; snapshot-ключи все True;
describe probe=ok: brokers=1; createdClients=5
```

По коду `PasswordRotator.cs`:

1. Ротация H прошла фазы A и B: `phase-a=1`, маркер `rotated-commit=1`
   (ставится в НАЧАЛЕ фазы C, `:217`), заявка удалена txn-коммитом B
   (`rotations=<none>`), исход ещё не записан (`outcome=<none>`).
2. В afterCommit-хвосте фазы C (rolling-пересоздание брокера) случился
   одиночный транзиент describe — преф-чек `WaitForBrokersAsync` не прошёл
   (`:159–162`) → `WaitOrExpireAsync(ticket: null, "waiting-cluster", …)`.
3. **Дефект**: `WaitOrExpireAsync` (`:306`) ПЕРЕЗАПИСЫВАЕТ журнал на
   `waiting-cluster`, затирая `rotated-commit`. Детектор afterCommit
   (`:117–119`) признаёт ТОЛЬКО `rotated-commit`/`phase-c` → следующий тик:
   `ticket is null && !afterCommit` → ранний выход `Success(false)`
   (`:121–122`) — вечный no-op. Фаза C невосстановима: финал (исход done,
   journal done) недостижим никогда, OLD-пароль не снимается — ротация
   «зомби».
4. Телеметрия сходится полностью: РОВНО одна запись waiting-cluster
   (`updated_unix` застыл — джоб больше не пишет журнал), 195 тиков —
   чтения тестом неизменного журнала, `describe probe=ok: brokers=1`
   (брокер жив; джоб в no-op до describe не доходит), `createdClients=5`
   (один транзиент → пара Unhealthy-пересозданий; шторма нет —
   амплификация фабрики НЕ подтверждена).

Вторая дыра той же формы: ca-window-гвард (`:131–139`) при живом staging
`ca_next_*` вызывает ту же `WaitOrExpireAsync("waiting-ca-window")` и при
`ticket=null` точно так же затирает маркер хвоста (условий для неё в
приёмочной серии не возникло — staging не открывался, но кодовая форма
идентична). Третья точка — слепой снапшот (`:141–149`) — уже закрыта в
текущем коде: при `ticket=null` тихий no-op без записи журнала
(паттерн-образец фикса, §5.5).

Оба зелёных прогона AC10 до приёмочной серии (изолят, серия A2) — прогоны,
в которых транзиент describe в хвосте C не выпадал (в изоляте нагрузка
минимальна); дефект присутствовал в коде всегда — воспроизводимость
определялась выпадением одиночного транзиента в окне rolling C.

## 4. Принципы решения (наследуют §4 фикса 2026-10-17 и каноны проекта)

1. **Сначала телеметрия, потом прогоны, потом фикс.** — ИСПОЛНЕНО:
   телеметрия §5.1 влита до приёмки; красный прогон серии нёс причину в
   своём выводе; корень сформулирован без повторов.
2. **Падение — по расчётному backstop, не по литеральным часам.** —
   ИСПОЛНЕНО для механики теста (§5.2). Запрещено увеличивать таймауты
   «вслепую» — каждое числовое изменение обосновано механикой или уликами.
3. **Диагностика в сообщениях падения.** — ИСПОЛНЕНО (§5.1): любой красный
   исход фаз H/K несёт журнал, счётчик тиков по фазам, живость заявок,
   исход, ключи снапшота, прямую describe-пробу, `CreatedClients`.
4. **Буква AC10 не ослабляется.** Все ассерты сохраняются (§2); вырожденных
   путей у AC10 нет — обе заявки обязаны доиграться.
5. **Прод и arch/ — по подтверждённому диагнозу, arch-first.** Диагноз D2
   подтверждён телеметрией и кодом → ПЕРВОЙ правкой `arch/16` §5 H (правило
   afterCommit-хвоста), затем прод-фикс, юнит-тесты, полный гейт (§6
   A4-D2/A5-D2). Нарушение порядка = сломанный контракт.
6. **Зомби-состояние невозможно по построению.** Правило «хвост не
   перезаписывается» гарантирует: маркер afterCommit (`rotated-commit`/
   `phase-c`) не стирается waiting-фазой никогда → детектор `:117–119`
   всегда видит хвост → финал достижим. «Тихий пропуск тика» — уже
   существующий паттерн кода (слепой снапшот `:143–146`, «кластер ещё
   сходится — следующий тик продолжит» `:200/:229`); наблюдаемость стагнации
   хвоста — по застывшей фазе (`updated_unix` не растёт) + панельный алерт
   `kafka-rotation-stale`.
7. **Изоляция и зачистка — по канонам AGENTS/AGENTS.base**: per-class
   окружение; после КАЖДОЙ серии — зачистка `kfw-*`/`pgw-*`; полные логи
   прогонов — в файлы (`/tmp/pgw-kfw-…log`), не в обрезанном stdout.

### 5.5. Прод-фикс PasswordRotator: правило afterCommit-хвоста (ветка D2)

**Правило (вводится в канон arch-first, затем в код):** ПОСЛЕ фазы B
(afterCommit-хвост: заявка снята txn-коммитом B, журнал в
`rotated-commit`/`phase-c`, финал done не достигнут) джоб НЕ пишет в журнал
waiting-фазы ВООБЩЕ. Ожидания хвоста — «тихий пропуск тика» без перезаписи
журнала. Waiting-фазы (`waiting-cluster`, `waiting-ca-window`) пишутся
ТОЛЬКО при живой заявке.

**Точки покрытия в `PasswordRotator.RunRoleAsync`** (после раннего выхода
`:121–122` инвариант `ticket=null ⇔ afterCommit-хвост` уже выполняется —
достаточно проверять `ticket.Value is null`):

1. **Ca-window-гвард (`:131–139`)** — вторая дыра: при живом staging
   `ca_next_*` и `ticket=null` — тихий пропуск (сейчас: `WaitOrExpireAsync(
   "waiting-ca-window")` затирает маркер). При живой заявке — как сейчас
   (waiting + гвард экспирации, канон §5 H без изменений).
2. **Слепой снапшот (`:141–149`)** — уже закрыт текущим кодом
   (`ticket=null → Success(false)` без записи журнала): паттерн-образец,
   не трогается.
3. **Слепой преф-чек describe (`:159–162`)** — подтверждённая дыра: при
   неудачном `WaitForBrokersAsync` и `ticket=null` — тихий пропуск (сейчас:
   `WaitOrExpireAsync("waiting-cluster")` затирает маркер — корень §3.1).
   При живой заявке — как сейчас (waiting + тройной гвард t10).

**Форма тихого пропуска**: `return Result<bool>.Success(false);` — по
образцу ветки слепого снапшота (`:145–146`): тик Success, роль «не
обработана» (цикл ролей `RunAsync` продолжает перебор — семантика уже
существующая), журнал не тронут. Перепись СВОЕЙ фазы с `last_error`
(альтернатива) — НЕ выбирается: причина describe в точке теряется ещё в
`WaitForBrokersAsync` (наружу bool), обогащение тянуло бы расширение
сигнатур; тихий пропуск сохраняет `updated_unix` застывшим — стагнация
хвоста наблюдаема панельным алертом `kafka-rotation-stale`; меньше
etcd-записей — меньше гонок waiting-writes.

**Обоснование надёжности**: маркер afterCommit (`rotated-commit`/`phase-c`)
после фикса не стирается ни одной веткой (переписывается только `:217` —
тем же `rotated-commit` в начале C, и `Fail(..., "phase-c")` с last_error —
обе формы детектор `:117–119` признаёт) → зомби невозможен по построению:
любой транзиент хвоста (describe, ca-window, слепота снапшота) оставляет
хвост доигрываемым, финал (исход done + journal done + снятие OLD) достижим
всегда. Дедлоков не добавляется: staging `ca_next_*` открывается только
исполняющейся K-ротацией; если окно уже открыто, K его доигрывает и хвост
H продолжает; K-гвард «живая пароль-ротация» (`PasswordMutationLive`:
журнал H в `rotated-commit` — живой) не даёт K открыть НОВОЕ окно поверх
живого хвоста H.

**Правка канона `arch/16-kafkaworker.md` §5 H** (ПЕРВОЙ, до кода): в абзац
Guard'ов после описания `waiting-cluster`/`waiting-ca-window` вводится
правило: waiting-фазы журнала пишутся только при живой заявке;
afterCommit-хвост (заявка снята фазой B, журнал `rotated-commit`/`phase-c`,
финал не достигнут) в точках ожидания (окно CA, слепой снапшот, слепой
преф-чек) журнал не перезаписывает — тихая передержка тика: маркер мутации
— единственный носитель возобновляемости фазы C, его затирание делало бы
финал недостижимым; стагнация хвоста наблюдаема по застывшей фазе — зона
панельного алерта `kafka-rotation-stale`. (Букву формулировки исполняет
план; суть — эта.)

**Юнит-тесты** (`src/tests/KafkaWorker.UnitTests/Provisioning/
PasswordRotatorTests.cs`, AAA, комментарии по-русски, существующий риг
