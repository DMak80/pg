# t31-s3-clusters-canon — канон кластеров S3-хранилища бэкапов (arch-first)

- **Roadmap**: [`arch/roadmap/s3.md`](../../../arch/roadmap/s3.md), пункт
  `t31-s3-clusters-canon` (трек s3: t31 канон → t32 provisioning → t33
  синхронность/связность → t34 панель; смежно t36 — клиентская интеграция,
  owns3-трек t35 — mesh-репликация ownS3).
- **Формулировка**: «канон кластеров S3 (arch-first, новый документ arch/):
  etcd-контракт деклараций и статусов — кластер (кол-во нод, привязка нод к
  docker/swarm-хостам — гео-распределение по образцу multi-host arch/14,
  размер диска/квота ноды), состав и здоровье нод, состояние связности и
  синхронности; выбор оркестратора (идемпотентный воркер по образцу
  существующих либо расширение существующего — фиксируется спекой); секреты
  нод — env (направление arch/14 §4/arch/19 §7, per-install профили вне
  etcd); границы: клиентская грань пула записи/чтения для подсистемы
  бэкапов остаётся обычным S3, перебор серверов с per-попыточным таймаутом —
  по фактам docs/s3-replication.md».
- **Тип задачи**: arch-only — код не пишется; артефакт — два новых документа
  канона `arch/23-s3-clusters.md` + `arch/24-s3worker.md`, правки трека
  `arch/roadmap/s3.md` и указателей. Реализация — t32 (provisioning/mesh),
  t33 (зонды), t34 (панель), t36 (клиентская интеграция), t35-owns3-трек
  (механика репликации ownS3).

**Решения пользователя (2026-10-11):**

1. **Оркестратор — новый отдельный воркер S3Worker** (не расширение
   PgWorker): симметрия доменов монорепо (kafka→KafkaWorker,
   valkey→ValkeyWorker, s3→S3Worker). Пара документов: `arch/23-s3-clusters.md`
   (контракт etcd) + `arch/24-s3worker.md` (воркер:
   provisioning/надзор/изменение состава по образцу arch/14/16/21), корневые
   префиксы `/s3/` (контроль-плейн кластеров) + `/s3worker/` (координация
   воркера), собственный mTLS-API и docker-сервис в поставке. S3-контур живёт
   на своих docker-хостах и не связан с PG-нодами; PgWorker остаётся
   клиентом пула (участником контракта не становится).
2. **Привязка нод к хостам — явная, хранится в etcd и идёт по атрибутам
   хоста**: для docker это может быть имя хоста, для swarm — другие
   атрибуты (метки/констрейнты площадки). Модель: «хост = набор атрибутов,
   привязка ноды = предикат по атрибутам» — фиксируется в схеме ключей
   декларации (`nodes/node<k>/placement` — JSON-селектор, не жёсткое имя).

## 1. Контекст и цель

### 1.1. Контекст

- **Трек s3** (`arch/roadmap/s3.md`): кластеры S3-хранилища бэкапов как
  управляемый объект системы — пул S3-серверов с гео-распределением
  (привязка к docker/swarm-хостам) и mesh-репликацией между ними. Целевая
  платформа пула — **ownS3** (arch/22, трек owns3); MinIO — переходный
  вариант тех же сценариев. Порядок: канон (t31) → provisioning + mesh
  (t32) → синхронность/связность (t33) → панель (t34); клиентская
  интеграция пула — t36.
- **Факты платформ** — [`docs/s3-replication.md`](../../s3-replication.md)
  (проверенные свойства MinIO bucket replication: fan-out, backfill
  `existing-objects`, уникальные приоритеты правил, поведение PUT при
  отказах целей, split-brain, нерепрезентативность штатных метрик лага,
  ограничение «кластер бэкапов 2–3 ноды; 4+ непригодны» — факт 12) и
  [`docs/owns3-replication-requirements.md`](../../owns3-replication-requirements.md)
  (требования R1–R6 к mesh-репликации ownS3; канон механики — будущая глава
  `arch/owns3/07-replication.md`, задача t35).
- **Потребитель пула** — подсистема бэкапов (arch/19): один bucket на
  установку (§5), S3-креды per-install — env воркера (§7); клиентский код
  S3-агностичен. Клиентская интеграция пула (перебор серверов, приоритеты
  чтения) — задача t36 (правки arch/19 §5/§7, arch/14 §6/§8).
- **Прецеденты домена**: контракт кластера + воркер — pg (arch/11 + arch/14,
  префиксы `/clusters/` + `/pgworker/`), kafka (arch/15 + arch/16,
  `/kafka/` + `/kafkaworker/`), valkey (arch/20 + arch/21, `/valkey/` +
  `/valkeyworker/`). Панель — декларатор и наблюдатель: etcd только читает,
  мутации — через HTTP API воркера (adminpanel/02 §2.3.x, §9); дискавери API
  — lease-ключи `<worker>/api/<id>`.
- **Модель multi-host** — arch/14 §2 (docker plain/swarm-хосты, transport
  TLS/SSH, portalloc, advertised-адреса); правила надёжности —
  «локальный docker-volume — кэш без гарантий durability, гарантии строятся
  от реплицированных источников» (AGENTS.md, arch/14 преамбула); паттерны
  оркестрации — arch/17 (идемпотентность, клэймы, takeover,
  journal-before-manipulations, флап≠смерть).

### 1.2. Цель

Создать канон кластеров S3-хранилища бэкапов, достаточный для реализации
t32–t34/t36 «по канону, без досказок»:

1. `arch/23-s3-clusters.md` — контракт etcd домена S3: декларации кластеров
   `/s3/clusters/<C>/` (состав нод, привязка к хостам по атрибутам,
   ресурсы/диск, платформа, профиль секретов), статусные ключи наблюдения
   (состав/здоровье нод, связность, синхронность), клиентский дискавери
   (`endpoints`), координация воркера `/s3worker/`, модель размещения
   «хост = атрибуты, привязка = предикат», платформенные границы
   (minio/owns3), клиентская грань пула.
2. `arch/24-s3worker.md` — воркер S3Worker: роль и HTTP API (приём мутаций
   панели, mTLS, дискавери), модель размещения и портов, секреты (per-install
   env-профили, передача нодам), процессы (provisioning/deprovisioning/
   надзор/add-remove ноды/зонд синхронности), надёжность, наблюдаемость,
   конфигурация, риски.
3. `arch/roadmap/s3.md` — отражение: ссылки трека на канон (arch/23/arch/24),
   синхронизация формулировок t32–t34/t36 со схемой контракта (детали — §3.3).
4. Указатели: `arch/README.md` — строки 23/24; `arch/22-owns3.md` — строка
   о месте ownS3 как платформы пула (управление пулом — трек s3, arch/23/24).

### 1.3. НЕ-цели (границы)

- **Не пишем код**: никаких `src/S3Worker.*`, Dockerfile, compose, тестов —
  только `arch/**`, `arch/roadmap/**`, указатели. Реализация — t32+.
- **Не правим `arch/19-backups.md`** (§5 layout, §7 секреты) и
  **`arch/14-pgworker.md`** (§6/§8 экспорт слепков, владелец кредов):
  клиентская интеграция пула — задача t36; канон t31 ссылается на arch/19
  как на потребителя, не меняя его. Аналогично `arch/22` правится только
  указателем (одна строка), главы `arch/owns3/*` не трогаются — механика
  репликации ownS3 канонизируется задачей t35.
- **Не правим `arch/adminpanel/02-etcd-contract.md`**: панель начнёт читать
  `/s3/` и звать API S3Worker задачей t34 — тогда в adminpanel/02 появится
  глава домена S3 (по образцу §10 kafka / §11 valkey). Канон t31 обязан лишь
  спроектировать ключи совместимо с механикой панели (unknownKeys-толерантность,
  битый JSON — parseError без падения тика, мутации только через API воркера).
- **Не каноним механику межсерверной репликации**: mesh — внутренность
  платформы нод (MinIO bucket replication / журнальная доставка ownS3 по
  требованиям R1–R6). Канон t31 фиксирует: оркестратор управляет СОСТАВОМ
  нод и настраивает mesh средствами платформы (детали настройки/выравнивания
  — t32; механика ownS3 — t35), клиенты о репликации не знают.
- **Не проектируем клиентскую интеграцию** (перебор endpoints, per-попыточный
  таймаут, приоритеты чтения per-cluster, отдельная пара для etcd-слепков) —
  это t36; канон фиксирует только границу: клиентская грань пула остаётся
  обычным S3, факт-обоснование — docs/s3-replication.md.
- **Не решаем E2E/стенд-механику S3Worker** (профиль compose, чеки): состав
  поставки фиксируется каноном (§3.2 п. 9), реализация стенда — t32.

## 2. Принципы

1. **arch-first**: arch/23 + arch/24 — источник истины для t32–t34/t36;
   каждое утверждение о контракте и поведении фиксируется здесь, не в коде.
2. **Симметрия доменов монорепо** (решение пользователя 1): управляемый
   объект = корневой префикс контроль-плейна + свой воркер + координационный
   префикс воркера; панель — декларатор/наблюдатель, исполнитель — воркер;
   мутации — только через HTTP API воркера (mTLS, дискавери по lease-ключу);
   панель в etcd домена S3 не пишет ничего.
3. **Гео-распределение — явная декларация** (решение пользователя 2):
   привязка ноды к docker/swarm-хосту — предикат по атрибутам хоста в etcd;
   автоматический placement (least-loaded, как у pg) не применяется —
   гео-схема («дом + 2 ДЦ») — часть инварианта надёжности, а не оптимизация
   нагрузки.
4. **Идемпотентность и паттерны arch/17**: каждый шаг процесса перепроверяет
   факт; мутации — под клэймом кластера; journal-before-manipulations;
   takeover ≤ TTL клэйма; «флап ≠ смерть» — деструктив только по
   положительному свидетельству (S7).
5. **Клиентская грань — обычный S3**: для подсистемы бэкапов пул — набор
   независимых S3-endpoint'ов (`endpoints`-ключ); запись — в любой
   доступный (перебор с per-попыточным таймаутом: health-проба
   недоступность не доказывает — docs/s3-replication.md факт 8),
   чтение/восстановление — по приоритетам (t36); синхронизация между
   серверами — обслуживание контура, не клиентов.
6. **Секреты — per-install env, вне etcd**: креды нод (root-пара, access
   keys) живут в env-профилях воркера (направление arch/14 §4 / arch/19 §7);
   в etcd — только имя профиля. Передача нодам — env контейнера при
   создании.
7. **Платформенная нейтральность контракта**: декларация/статусы/диски не
   зависят от платформы нод; платформа (`minio`|`owns3`) — поле декларации,
   платформенные различия (versioning/mesh-настройка/health-грани/пределы
   состава) — отдельный раздел канона.
8. **Язык и стиль**: документация по-русски, идентификаторы — английские;
   структура и тон — как у соседних канонов (таблицы ключей, канонические
   примеры значений, §-нумерация, риски-таблица).

## 3. Артефакты: что и где каноним

### 3.1. `arch/23-s3-clusters.md` — контракт etcd домена S3

Структура по образцу arch/15/arch/20 (контракт кластеров + координация +
дискавери). Содержание глав:

**§1. Вводная.** Назначение домена: кластеры S3-хранилища бэкапов как
управляемый объект — пул S3-серверов с гео-распределением и mesh-репликацией;
декларатор — панель (через API воркера), исполнитель — S3Worker (arch/24);
потребитель — подсистема бэкапов (arch/19), для клиентов — обычный S3.
Имена: кластер `<C>` — `^[a-z][a-z0-9_]{0,62}$` (как pg/kafka/valkey, без
дефиса); ноды `node1..nodeN` (имя генерирует панель, `node<max+1>`, ≤ 9).
Транспорт — HTTP JSON gateway `/v3/*`, poll без watch (тик воркера 5 с /
панели 3 с). Два корневых префикса: `/s3/` и `/s3worker/`.

**§2. Ключи кластера `/s3/clusters/<C>/`** (таблица: ключ / формат /
пишет / примечание):

| Ключ | Формат | Пишет | Суть |
|---|---|---|---|
| `config` | `{"platform":"minio"\|"owns3","nodes":N,"secret_profile":"<имя>","created_unix":T,"state"?:"NOT_INITIALIZED"\|"TO_REMOVE"}` | панель через API воркера (создание, TO_REMOVE); воркер снимает `state` после инициализации (txn по `mod_revision`) | `state` — только у невыполненных заявок: отсутствие = Active (семантика pg/kafka/valkey); `platform` фиксируется при создании навсегда; `nodes` — плановое число нод; `secret_profile` — имя per-install env-профиля кредов нод (§6 канона, секреты вне etcd); валидация состава: `minio` — 1..3 (факт 12 docs/s3-replication.md: 4+ ноды непригодны для кластера бэкапов), `owns3` — 1..9 (структурный предел, операционная рекомендация 2–3 — гео-минимум и бюджет R1) |
| `nodes/node<k>/placement` | JSON-селектор атрибутов хоста: `{"docker_host":"h1"}` (plain) \| `{"swarm_node":"n1"}` \| `{"swarm_labels":{"geo":"dc1",...}}` \| комбинация атрибутов | панель через API воркера | явная привязка ноды (решение пользователя 2): модель «хост = набор атрибутов» (plain — имя из `S3Worker:Docker:Hosts[]`; swarm — hostname ноды и `node.labels.*`), привязка = предикат равенства по всем указанным атрибутам; изменение привязки живой ноды — только выводом/перевозом ноды (перепривязка на месте не допускается — данные тома привязаны к хосту) |
| `nodes/node<k>/resources` | `{"cpu":"2","mem":"4Gi","disk":"200Gi"}` | панель через API воркера (мутация ресурсов) | форматы как pg §9.3; cpu/mem — лимиты контейнера; `disk` — целевой объём volume данных ноды (декларация: создание volume и операционная квота-наблюдение; жёсткого enforcement-примитива у docker-volume нет — занятость наблюдается статусом `usage` и алертами панели t34) |
| `nodes/node<k>/state` | `NOT_INITIALIZED\|PROVISIONING\|RUNNING\|UNREACHABLE\|REMOVING\|TO_REMOVE` | `NOT_INITIALIZED`/`TO_REMOVE` — только панель (заявка/one-way маркер демонтажа ноды); остальные — воркер | жизненный цикл ноды (семантика kafka/valkey); `UNREACHABLE` ставит надзор по health-пробам (§5) |
| `nodes/node<k>/placed_on` | строка — имя docker-хоста `"h1"` | воркер (при резолвции placement) | фактическое размещение после резолвции селектора (§4); переживает rebuild (том ноды живёт на этом хосте) |
| `nodes/node<k>/usage` | `{"used_bytes":N,"total_bytes":N,"updated_unix":T}` | воркер (надзор, периодически) | занятость диска ноды из платформенной админ-грани/метрик; кормит квота-наблюдение `resources.disk` и панельные алерты (t34) |
| `endpoints` | строка `"h1:p1,h2:p2,..."` | воркер (после подъёма; RMW при изменении состава) | клиентские адреса пула (advertised host + S3-порт из `/s3worker/portalloc/<C>`) — точка дискавери клиентов (t36) |

Канонические примеры значений (критерий приёмки парсеров t34): `config`
при создании / Active / с `TO_REMOVE`; `placement` для plain и swarm;
`endpoints`; `usage`. Неизвестные ключи внутри `/s3/` — не ошибка: лог +
счётчик `unknownKeys` читателя (как pg/kafka/valkey).

**§3. Статусы наблюдения (связность и синхронность)** — контракт ключей
фиксируется t31, запись реализуется задачами трека:

| Ключ | Формат | Кто пишет |
|---|---|---|
| `/s3/clusters/<C>/connectivity` | `{"state":"OK"\|"DEGRADED"\|"DOWN","checked_unix":T,"links":{"node1":{"node2":"ok"\|"offline",...},...},"probe_error"?}` | зонд t33 (периодически + по команде API): связность нод между собой — PUT-пробы межнодовых линков (health-проба недоступность записи не доказывает: изолированная от всех целей нода отвечает health, но не принимает запись — docs/s3-replication.md факт 8) |
| `/s3/clusters/<C>/sync` | `{"state":"SYNCED"\|"LAGGING"\|"DIVERGED","checked_unix":T,"pairs":[{"from":"node1","to":"node2","missing":N,"extra":N,"lag_bytes"?,"lag_objects"?}...],"last_error"?}` | зонд t33: сверка содержимого bucket между нодами (list/хвосты; штатные метрики репликации лаг данных не отражают — факт 7; админ-грань ownS3 стартовая позиция/хвост per-target — R5 требований) |

`state`-агрегаты: connectivity DOWN — нет ни одного живого линка записи;
DEGRADED — часть линков offline; sync LAGGING — догон известен и мал/растёт,
DIVERGED — устойчивое расхождение/дыра (алерты панели — t34). Форматы
толерантны к расширению полей (парсеры панели читают известные поля).
Состав/здоровье нод наблюдается `nodes/*/state` + `usage` (отдельного
health-ключа нет — состояние живости несёт `state`, детальная телеметрия —
метрики arch/18).

**§4. Модель размещения (атрибуты хостов, предикат привязки).**
Формализация решения пользователя 2:

- **Хост — набор атрибутов**: plain-режим — атрибут `docker_host` (имя из
  таблицы `S3Worker:Docker:Hosts[]` воркера, arch/24 §2); swarm — атрибуты
  `swarm_node` (hostname ноды swarm) и `swarm_labels` (`node.labels.*` —
  произвольные пары ключ-значение, в т.ч. гео-метки площадок).
- **Привязка ноды = предикат**: `placement`-селектор ноды — конъюнкция
  равенств по атрибутам; нода кластера обязана иметь селектор (валидация
  API: пустой/невалидный — 400).
- **Резолюция** (воркер, фаза provisioning): по селектору — список
  кандидатов-хостов. Ноль кандидатов — transient-фейл фазы (journal,
  ретрай тиком: хост может появиться в конфигурации). Несколько кандидатов —
  детерминированный выбор (least-loaded по числу занятых портов/тасков,
  tie-break — по имени; journal-запись с перечнем кандидатов). Результат —
  `placed_on`; повторные проходы идемпотентны (тот же хост, пока селектор
  не изменён выводом ноды).
- Анти-аффинити по отношению к другим нодам того же кластера НЕ вводится
  автоматикой: раснос по площадкам — обязанность оператора (гео-схема —
  явные селекторы); канон фиксирует рекомендацию «ноды одного кластера — на
  разных хостах/площадках» и панельную индикацию совпадений (t34).

**§5. Платформы нод** (раздел границ платформ; настройка механик — t32):

- **minio** (переходная): образ — фиксированный RELEASE из локального
  registry (`192.168.0.1:5000`, строки `images.txt`; CE — end-of-life,
  обновлений нет — известно из docs/s3-replication.md); нода — контейнер
  `minio server` с volume данных; bucket per-install (arch/19 §5) создаётся
  на каждой ноде с **versioning** (replication без него не работает);
  mesh — правила bucket replication fan-out с уникальными приоритетами,
  флаги `delete,delete-marker,existing-objects` (backfill подключаемой
  ноды); предел состава 1..3 ноды (факт 12). Health-грани —
  `/minio/health/live|cluster` (200/503).
- **owns3** (целевая): образ `owns3:dev` (правила E2E-образов: сборка .NET
  на хосте, publish-COPY, в registry не кладётся); нода — ownS3 single-drive
  (`OWNS3_DATA_DIR=/data`); bucket per-install на каждой ноде (CreateBucket
  admin-кредом, идемпотентно); mesh — конфиг ownS3 per-install
  (адреса/креды целей — требования R6) — реализация и глава канона
  `arch/owns3/07-replication.md` — задача t35; до неё кластеры
  `platform=owns3` с N≥2 декларативно валидны, но mesh-синхронизация
  отсутствует (статусы sync это отразят). Health — `/healthz` (owns3/05 §5).
- Общее: S3-порт контейнера 9000 → host-порт из portalloc; bucket
  per-install — единое имя на всех нодах кластера (клиент с одним
  комплектом кредов работает с любой нодой); создание/поддержание bucket —
  обязанность оркестратора (идемпотентно).

**§6. Секреты (контрактная часть).** Креды нод — per-install env-профили
воркера, вне etcd и git (направление arch/14 §4 / arch/19 §7): профиль =
имя + root-пара + опциональные статические access keys (read-write для
записи бэкапов, read-only для панели — симметрия действующего стенда
owns3/05 §6). Кластер ссылается на профиль полем `config.secret_profile`;
профиль един на все ноды кластера (клиент пишет в любую ноду одним ключом;
mesh-настройка — один комплект). Формат env — `S3W_NODE_SECRETS__<PROFILE>__*`
(по прецеденту `OWNS3_ACCESS_KEYS__<i>__*`); в ноды передаётся env
контейнера: minio — `MINIO_ROOT_USER/MINIO_ROOT_PASSWORD`, owns3 —
`OWNS3_ROOT_USER/OWNS3_ROOT_PASSWORD` + `OWNS3_ACCESS_KEYS__<i>__*`.
Отсутствие/неполнота профиля — отказ фазы provisioning с диагностикой
(валидация API — 422 по факту env воркера). Ротация — заявка
`/s3worker/rotations/<C>` (rolling-пересоздание нод с новым env профиля;
поддержка рестарт-семантики платформ: ownS3 — переконфигурация env + рестарт,
owns3/05 §2).

**§7. Клиентская грань пула (границы для t36).** Пул для клиентов —
`endpoints`-набор обычных S3-серверов: запись — перебор «любой доступный» с
per-попыточным таймаутом PUT (health-проба недоступность не доказывает —
docs/s3-replication.md факт 8; быстрый отказ/успех, не молчание — R3
требований ownS3); чтение/восстановление — по приоритетам per-cluster
(страховка на лаг доставки); синхронизация между серверами — не забота
клиентов. Layout объектов — arch/19 §5 без изменений. Канон фиксирует
границу; реализация и правки arch/19/arch/14 — t36.

**§8. Координация воркера `/s3worker/`** (порт схемы `/kafkaworker/`
arch/15 §4 / `/valkeyworker/` arch/20 §3 один в один, свой префикс):
`leader` (lease TTL 15 с, singleton-процессы), `claims/<C>` (пер-кластерный
клэйм), `work/<C>` (журнал фаз `{"op","phase","updated_unix","instance",
"last_error"?}` — сохранение накопленных треков S6 arch/17), `portalloc/<C>`
(`{"node<k>":{"host":"h","s3":18001}}` — закрепление S3-портов, переживает
rebuild), `locks/portalloc` (глобальный portalloc-клэйм, t90-паттерн),
`instances/<id>`, `api/<id>` (дискавери API: lease TTL 15 с,
`{"url","instance","since_unix","cert_thumbprint"?}` — читает панель),
`rotations/<C>` (заявка ротации секретов профиля кластера). Панель читает
из `/s3worker/` только `api/` и `rotations/` (t34); остальные ключи —
координационные, вне панельного контракта.

**§9. Панель (проекция — т34).** Фиксируется: панель читает `/s3/` и
`/s3worker/{api,rotations}/`, мутирует только через API S3Worker;
проекция в adminpanel/02 (глава домена S3 по образцу §10/§11) — задача t34.
Совместимость с механикой панели: unknownKeys-толерантность, битый JSON —
parseError-запись без падения тика, `state`-семантика «отсутствие = Active».

### 3.2. `arch/24-s3worker.md` — воркер S3Worker

Структура по образцу arch/14/16/21 (роль → API → размещение → контракт →
секреты → процессы → надёжность → наблюдаемость → конфигурация → риски).
Содержание глав:

**§1. Роль и разделение ответственности.** S3Worker — фоновый сервис
(.NET 10), исполнительная сторона декларативного контракта `/s3/`: панель
заявляет кластер через HTTP API воркера → воркер записывает декларацию
(`state=NOT_INITIALIZED`) → поднимает ноды (volume + контейнер платформы на
хосте из placement-селектора), создаёт bucket per-install, настраивает mesh
(платформенным средством), пишет `endpoints` и снимает `state`; перевод в
`TO_REMOVE` — демонтаж. Ответственность изменений: префиксы `/s3/` и
`/s3worker/` пишет ТОЛЬКО S3Worker (панель и сиды — через его API). ASCII-
схема (панель → API → etcd → воркер → docker-хосты → ноды S3; PgWorker —
клиент пула, читатель `endpoints` в будущем t36, участник контракта НЕ
является). Несколько инстансов одновременно, координация — клэймы etcd;
свойства — как у PgWorker (идемпотентность, takeover ≤ TTL 15 с, состояние
переживает смерть инстанса).

**§1.1. HTTP API воркера** (mTLS, общий паттерн воркеров arch/14 §1.1:
единая per-install API-CA `kfw-install-ca`, клиентские серты панели;
серверный серт — ключ `/workers/api_tls/s3worker`, env-фоллбек
`S3W_API_TLS_*`; `/healthz`, `/metrics` — та же грань; дискавери —
`/s3worker/api/<id>`). Эндпоинты (сигнатуры/гварды — канон поведения
исполнителя, панель — прокси; протоколы записи — по образцу adminpanel/02
§9.2/§9.4/§9.5/§9.6):

| Метод+путь | Назначение |
|---|---|
| `POST /api/s3/clusters` | создание кластера: клэйм-txn `version(config)==0` + пакет PUT (config + nodes × {placement,resources,state=NOT_INITIALIZED}); сбой — компенсация `del --prefix /s3/clusters/<C>/` |
| `DELETE /api/s3/clusters/{c}` | перевод `config.state=TO_REMOVE` (RMW; already → 204 без записи) |
| `POST /api/s3/clusters/{c}/nodes` | добавление ноды (`node<max+1>`): клэйм-txn + put `placement`/`resources`/`state=NOT_INITIALIZED` |
| `DELETE /api/s3/clusters/{c}/nodes/{n}` | маркер демонтажа ноды `nodes/<n>/state=TO_REMOVE` (one-way; гварды: не последняя нода кластера) |
| `PUT /api/s3/clusters/{c}/nodes/{n}/resources` | мутация ресурсов ноды (cpu/mem — rolling-пересоздание контейнера надзором; disk — декларация/наблюдение) — образец kafka-мутации №15 |
| `POST /api/s3/clusters/{c}/rotations` | заявка ротации секретов профиля кластера (`/s3worker/rotations/<C>`, клэйм-txn — §9.8-паттерн) |
| `POST /api/s3/clusters/{c}/sync-probe` | внеплановый зонд синхронности/связности (202; результат — ключи §3 arch/23) — реализация t33, эндпоинт канонизируется сейчас |

Валидация (сервер — источник истины): `name` — паттерн; `platform` ∈
{minio,owns3}; `nodes` — 1..3 (minio) / 1..9 (owns3), рекомендуемый состав
3 (гео-минимум); `placement` — обязательный валидный селектор для каждой
ноды (400); `resources` — cpu 0.01..64, mem/disk 1..65536 GiB; `secret_profile`
— непустое имя, существующее в env воркера (422 с перечнем доступных имён,
без значений секретов).

**§2. Модель размещения.** Docker plain/swarm через `Shared.Docker`
(транспорт unix/tcp+TLS/SSH — как arch/14 §2.2.1, env `S3W_DOCKER_TLS_*`,
`S3W_DOCKER_SSH_*`); конфиг `S3Worker:Docker { Mode, Hosts[{Name,Endpoint}],
SwarmManager, PortRange{From,To}, Images{Minio,OwnS3}, Tls, Ssh,
ContourNetwork }`. Атрибуты хостов для placement-селекторов: plain — имя из
`Hosts[]`; swarm — hostname нод и `node.labels.*` (`GET /nodes`).
Portalloc: S3-порт (контейнерный 9000) → последовательные host-слоты
диапазона, закрепление `/s3worker/portalloc/<C>`, глобальный клэйм
`/s3worker/locks/portalloc` на довыделение (занятость = docker-публикации ∪
portalloc всех кластеров — t90-паттерн). Advertised-адреса — только от
фактических публикаций (`S3Worker:Docker:AdvertisedHost` по образцу
arch/14 §2.4 п.5 — single-host/стенд; multi-host — фактические имена
хостов). Сеть: per-cluster сеть НЕ создаётся (межнодовая коммуникация
mesh и клиенты — по advertised `host:port`, единый namespace адресов;
отказ от аналога `pgw-net-<C>` осознанный — Patroni-подобного внутреннего
кластерного протокола у нод S3 нет); опция `ContourNetwork` (стенд/E2E) —
ноды создаются в сети контура поставки, адресация по именам сети, сеть
воркером не создаётся/не удаляется (как arch/14 §2.1).

**§3. Контракт etcd.** Читаемые/пишемые ключи — ссылками на arch/23
(источник истины — не пересказ); здесь — только координационное поведение:
инвариант «мутации `/s3/` — только держателем клэйма `<C>`», txn с compare
по `mod_revision` config.

**§4. Секреты.** Per-install env-профили `S3W_NODE_SECRETS__<PROFILE>__*`
(формат arch/23 §6): root-пара + статические access keys; профиль един на
кластер; передача в ноды — env контейнера при создании (значения никогда
не попадают в etcd/журнал); ротация — заявка `rotations/<C>` →
rolling-пересоздание нод (по одной за тик, данные volume не трогаются) →
del заявки; транспортные секреты API/docker — env `S3W_*` (§1.1/§2).
Серверный серт API — ключ `/workers/api_tls/s3worker` (панель пишет — t34;
до того env-фоллбек).

**§5. Процессы (машины состояний)** — все шаги идемпотентны
(перепроверка факта), journal-before-manipulations (`/s3worker/work/<C>`),
клэйм `<C>` обязателен:

- **A. ProvisioningProcess** (P0 claim+journal → P1 резолв placement
  всех нод + portalloc → P2 создание нод: volume данных + контейнер
  платформы (env: креды профиля, адреса mesh-соседей — для minio это
  advertised-эндпоинты целей правил, для ownS3 — конфиг mesh t35), порты,
  health-ожидание (бюджет, transient-толерантно; поллинг-инвариант t19 —
  без одиночных блокирующих вызовов) → P3 bucket per-install на каждой ноде
  (идемпотентно; minio — с versioning) → P4 mesh-настройка платформенным
  средством (minio: `mc replicate add` fan-out, уникальные приоритеты,
  `delete,delete-marker,existing-objects`; owns3: конфиг поставки t35) →
  P5 `endpoints` + снятие `config.state` txn по `mod_revision`).
- **B. DeprovisioningProcess** (X0 claim → X1 маркеры `REMOVING` нодам →
  X2 снос контейнеров/volumes/portalloc → X3 `del --prefix /s3/clusters/<C>/`
  + чистка `/s3worker/{work,portalloc}/<C>`). Снос кластера уничтожает
  данные бэкапов его нод — осознанное действие оператора (панель t34 —
  confirm); фиксируется в рисках.
- **C. NodeSupervisor** (надзор, тик): health-проба каждой ноды
  (платформенная health-грань по host:port из portalloc; проба — не
  доказательство доступности записи, только живость контейнера/грани);
  снесённый контейнер (положительное свидетельство docker-инспекции, S7) →
  пересоздание на том же хосте (volume сохраняется); недоступная нода →
  `UNREACHABLE` + ретраи; периодический сбор `usage` (платформенная
  админ-грань/метрики) — квота-наблюдение `resources.disk`.
- **D. AddNodeProcess**: подъём новой ноды (по A) + включение в mesh +
  backfill существующих объектов (minio — `existing-objects`; ownS3 — R4)
  + RMW `endpoints`.
- **E. RemoveNodeProcess**: гварды (не последняя нода; вывод не рвёт
  единственную копию — при живых остальных) → исключение из mesh →
  остановка/снос контейнера и volume → чистка ключей/portalloc → RMW
  `endpoints`.
- **F. SyncProbeProcess** (контракт — t33, каркас канонизируется):
  периодический и по-командный зонд: PUT-пробы межнодовых линков
  (connectivity) и сверка листингов bucket между нодами (sync) — ключи
  arch/23 §3; источник истины о синхронности — собственный зонд (штатные
  метрики репликации лаг не отражают — факт 7).

**§6. Надёжность.** Идемпотентность каждого шага; takeover ≤ TTL 15 с;
отказ docker-хоста — ноды на нём `UNREACHABLE`, размещение не меняется
(`placed_on` фиксирован), новые ноды — только на резолвируемые хосты;
**«что теряется при отключении машины X»**: volume ноды — локальное
хранение без гарантий durability, доступность её доли теряется до возврата
машины; данные бэкапов переживают отказ машины благодаря mesh-репликации
на остальные ноды с точностью до лага доставки (RPO = лаг репликации:
секунды штатно, минуты после отказов — факты 6/12); полная гибель диска
ноды — потеря её доли, восстановление полноты — backfill из живых нод (D);
гарантии строятся от реплицированных источников (etcd + mesh), не от
локальных volume. Отказ etcd — контрол-плейн заморожен, живые ноды S3 от
него не зависят. Watchdog зависших циклов — общий каркас `LoopWatchdog`
(Shared.Core, arch/14 §6): инвариенты живости/поллинга обязательны и для
циклов S3Worker; «пульс конечного внешнего вызова» (S3-операции зонда —
пер-попыточный таймаут + пульс) — тот же канон.

**§7. Наблюдаемость.** `/healthz`: `etcd-reachable`, `docker-hosts`
(per-host ping), `loops-alive`, `claims`; Prometheus-метрики — каркас
arch/18 (`/metrics` на порту API): циклы/клэймы/фазы процессов/операции
воркера; телеметрия самих нод — метрики платформ (ownS3 — owns3/05 §5;
minio — собственные метрики; scrape-механика — вне канона t31).

**§8. Конфигурация (appsettings + env).** `S3Worker:Etcd { Endpoints[] }`;
`S3Worker:Docker { Mode, Hosts[], SwarmManager, PortRange, Images{Minio,
OwnS3}, Tls, Ssh, ContourNetwork, AdvertisedHost }`; `S3Worker:Loops {
ScanIntervalSec=5, KeepaliveSec=5, Watchdog{...} }`; `S3Worker:Thresholds
{ NodeBootSec=100, NodeDeadSec=90, HealthIntervalSec=15 }`; `S3Worker:Parallelism
{ MaxClusters=4 }`; секреты — env `S3W_*` (API TLS, docker TLS/SSH,
node-secrets-профили). Fail-fast валидации старта — по образцу pg
(неполные секретные пары, EnableSeedEndpoint-флаг — при необходимости
стендового сида, default false).

**§9. Риски.** Таблица: EOL MinIO (переходная платформа — образ закреплён
в registry, миграция на owns3 — t41-путь); 4+ нод minio непригодны
(валидация состава); потеря единственной ноды кластера N=1 = потеря данных
бэкапов (рекомендация N≥2/3, алерт панели t34); снос кластера уничтожает
данные (confirm, риск-строка); собственный зонд как единственный честный
источник синхронности (штатные метрики врут — факт 7); отсутствие
per-cluster сети — зависимость межнодовой связности от advertised-адресов
(ограничение фиксируется явно); зависимость mesh-owns3 от t35.

**§10. Дальше.** Указатели: arch/23 (контракт), arch/19 (потребитель),
arch/14/16/21 (образцы воркеров), arch/17 (принципы), roadmap/s3.md,
docs/s3-replication.md (факты), docs/owns3-replication-requirements.md.

## 6. Ограничения и риски

| Риск | Митигация |
|---|---|
| Расхождение формулировок roadmap-задач t32–t36 с каноном (roadmap — canonical source) | фаза 3 синхронизирует формулировки трека со схемой ключей/§ канона; границы задач не меняются |
| Канон фиксирует контракт статусов t33 до реализации зонда (формат может «не понравиться» реализации) | форматы толерантны к расширению полей (правило панельных парсеров); state-агрегаты — минимальный зафиксированный набор; t33 в праве дополнять поля, не меняя схему ключей |
| `platform=owns3` с N≥2 без t35: mesh не работает, статусы sync покажут DIVERGED | канон фиксирует это явно (arch/23 §5): платформенная готовность — t35; до того owns3-кластера гео-схем не поднимаются (операционное ограничение, не контрактное) |
| Минимизация квоты диска: docker не имеет enforcement-примитива для volume | `disk` — декларация + наблюдение (`usage`, алерты t34); фиксируется честно в arch/23 §2 и рисках arch/24 §9 |
| Отказ от per-cluster сети — межнодовые линки зависят от advertised host:port и открытых межхостовых портов | фиксируется в arch/24 §2 явно (ограничение модели); firewall/матрица — вопрос эксплуатации (arch/13 — pg-контур, для S3-пула — при необходимости t32+) |
| Номера документов (23/24) конфликтуют с параллельными задачами | следующий свободный номер после 22-owns3 проверен на момент спеки; при коллизии в мерж-окне — перенумерация в фазе 1 (спека допускает, канон — финальный арбитр) |
| Объём: два новых документа сразу | структура — порт проверенных образцов (arch/15/16/20/21); канон не пересказывает arch/19/22, только ссылается |
| Секреты: имя профиля в etcd раскрывает факт существования профилей | осознанно (направление задачи: per-install профили вне etcd — имя без значений; класс экспозиции не расширяется, arch/14 §4) |

## 7. Критерии приёмки

1. **arch/23-s3-clusters.md**: префиксы `/s3/` + `/s3worker/`; полная
   таблица ключей декларации (config/nodes:placement|resources|state|
   placed_on|usage/endpoints) с форматами, писателями и каноническими
   примерами значений (создание/Active/TO_REMOVE; plain- и swarm-селекторы);
   статусные ключи connectivity/sync с форматами; модель размещения
   «хост = набор атрибутов, привязка = предикат» с резолюцией и
   детерминизмом; платформенный раздел (minio/owns3: образы, bucket,
   versioning, mesh-границы, health-грани, пределы состава 1..3/1..9);
   секреты — env-профили вне etcd (профиль per-cluster, имя в
   `secret_profile`); клиентская грань (обычный S3, перебор с
   per-попыточным таймаутом — отсылка к фактам, реализация t36); координация
   `/s3worker/` (полный перечень ключей по образцу arch/15 §4); проекция
   панели (совместимость с механикой adminpanel/02, глава — t34).
2. **arch/24-s3worker.md**: роль/ответственность (единственный писатель
   `/s3/`+`/s3worker/`, PgWorker — не участник контракта); mTLS-API с
   таблицей эндпоинтов и протоколами записи (клэйм-txn/RMW/one-way — образцы
   adminpanel/02 §9); модель размещения (атрибуты, portalloc + глобальный
   клэйм, advertised, отказ от per-cluster сети — осознанный, ContourNetwork
   для стенда); секреты (профили env, ротация rolling); процессы A–F
   (идемпотентные, journal-before-manipulations, клэймы); надёжность с
   разделом «что теряется при отказе машины X» (RPO = лаг mesh, backfill);
   наблюдаемость (healthz/метрики arch/18); конфигурация `S3Worker:*` +
   env `S3W_*`; таблица рисков.
3. **Трек и указатели**: `arch/roadmap/s3.md` — ссылки на arch/23/24 и
   синхронизированные формулировки t32–t36 (границы задач не изменены);
   `arch/README.md` — строки 23/24; `arch/22-owns3.md` — строка-указатель
   на трек s3 как владельца управления пулом.
4. **Границы соблюдены**: `git status` — изменения только в `arch/**` и
   `docs/superpowers/**`; arch/19, arch/14, adminpanel/02, arch/owns3/*,
   docs/s3-replication.md, docs/owns3-replication-requirements.md —
   нетронуты.
5. **Согласованность**: ни одного расхождения нового канона с arch/14 §2/§6
