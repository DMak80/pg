# t19-slot-auto-recreate — автозакрытие потерянных слотов (wal_status='lost')

Спецификация фазы 1 (dev-flow). Канон домена — [arch/19-backups.md](../../../arch/19-backups.md)
§3 (обновлён этой задачей: пункт «Слот», «Правила непрерывности», риск-таблица §10);
задача — [arch/roadmap/reliability.md](../../../arch/roadmap/reliability.md) `t19-slot-auto-recreate`
(влияние D, R). Roadmap-тег снимается мерж-коммитом (main-агент, вне этой фазы).

## 1. Цель

Замена ручного операторского разбора потерянного слота автоматикой воркера.

Сегодня при `wal_status='lost'` слота `pgw_bkp_<C>_<X>` (PG срезал WAL под слотом
по `max_slot_wal_keep_size` после длительного неподтверждения — S3 недоступен →
приёмник в backpressure):

- приёмник (`WalReceiverCore`) бесконечно ретраит старт каждые 5 с — контейнер
  running, воркер проблемы НЕ ВИДИТ (зонд шага 3 `WalStreamProcess` проверяет
  только существование слота);
- панель видит lost только на мастере шарда (SQL-проба read-write multi-host) →
  critical-алерт `slot-wal-lost` с ручным remedy «запустите recreate ноды …
  потерянный слот почистите по runbook»; lost-слот sync-standby панели невидим
  вовсе;
- runbook-раздела чистки слота в `docs/runbook.md` НЕТ — remedy ссылается на
  несуществующую инструкцию.

После t19: воркер на каждом тике контроля зондирует `wal_status` на КАЖДОМ
источнике (мастер + sync-standby — закрывает и невидимую панели sync-сторону) и
лечит автоматически:

- **lost одного источника при живом втором** → recreate слота (drop + create
  immediate+reserved): живой агент продолжает доставку, потерянный возвращается
  сам от общего хвоста S3 (механика ниже); BROKEN не ставится;
- **lost/отсутствие слотов ВСЕХ источников при живой цепочке** → существующий
  BROKEN-путь t07 (BreakAsync с recreateSlot): пересъём полного, оба агента
  возвращаются от `wal_start` нового полного.

Решение пользователя (фаза 1): путь «слот + при дыре полный» — авто-recreate
НОДЫ отвергнут (данные нод целы, срезан только WAL-хвост; rebuild с basebackup
и switchover лидера избыточны); «всегда BROKEN при любом lost» отвергнуто
(лишние полные бэкапы, когда дыру закрывает живая вторая сторона).

## 2. Принципы

1. **Симметрия с каноном t27/t07**: lost-слот ≈ «слот исчез» своего источника —
   через него стрим невозможен (PG отвергает START_REPLICATION по
   инвалидированному слоту), нужные слоту сегменты срезаны. Правило «живой слот
   на любой ноде держит цепочку» (arch/19 §3.3 п.3) расширяется с
   «существует» до «существует и не lost» (alive).
2. **Живой источник продолжает** (решение пользователя): оба агента пишут в
   ОДИН префикс `<C>/<X>/wal/`, put идемпотентен — потерявшему не нужно
   «досылать с места остановки»: он продолжает от общего хвоста S3. Хвост
   достраивает живой агент; горизонт удаления на потерянной ноде стоит ниже
   среза и поднимается записью — как только следующий за хвостом сегмент
   существует на его ноде, START_REPLICATION приёмника проходит (вечный ретрай
   5 с — и есть механизм возврата). Приёмник НЕ дорабатывается.
3. **Recreate нод не делаем**: `RecreateNodeHandler`/`NodeSupervisor`
   не трогаем.
4. **Автоматика — дефолт без опций**: конфиг-переключателя не вводим (канон
   проекта — надёжность не опциональна, образец t07 second-instance).
5. **MULTI-HOST / идемпотентность**: решение принимается по факту зонда в
   каждом тике; всё состояние — существующие etcd-ключи; лечение идемпотентно,
   переживает рестарт/takeover воркера.
6. **Факт над записью**: в etcd не пишется ничего нового (журнал-фазы +
   существующее поле `error` BROKEN-ключа); «слот лечился» — journal-факт, не
   персистентный статус.
7. **arch-first**: контракт обновлён до кода (сделано в этой фазе, см. §7).

Семантическое обоснование (физическая репликация): `restart_lsn` слота — нижняя
граница УДЕРЖАНИЯ WAL, не запрет чтения; physical walsender стартует от
запрошенной приёмником позиции (хвост S3). Если нужные сегменты уже удалены —
ошибка «requested WAL segment has already been removed» → ретрай. Поэтому
после drop+create свежий `restart_lsn = current` НЕ мешает старту от более
старого хвоста S3, пока сегменты физически существуют на ноде.

## 3. Структура / компоненты

### 3.1 SQL-слой — `src/PgWorker.Backups/Sql/`

`IWalSqlExecutor` / `NpgsqlWalSqlExecutor`:

- `SlotExistsAsync` → заменяется на `SlotProbeAsync(adminDsn, slot)` →
  `(bool Exists, string? WalStatus)`: `SELECT wal_status FROM
  pg_replication_slots WHERE slot_name = $1`. `WalStatus == null` (строки нет)
  трактуется вызывающим; для существующего слота `null`-статус (старые PG /
  edge) — как «живой» (толерантность: лечим только явный `'lost'`).
- Новый `RecreateSlotAsync(adminDsn, slot)`: drop (`SELECT
  pg_drop_replication_slot($1)`, `undefined_object` — норм) + create
  (`pg_create_physical_replication_slot($1, true)` — immediate+reserved, тот же
  вызов, что ensure). Идемпотентен; ошибка — `Result.Failed` (transient, тик
  повторит). Реализация — до-переиспользование ensure после drop.

`EnsureSlotAsync` заменяется на `EnsureSlotAliveAsync(adminDsn, slot)`:
отсутствует → create (как сегодня); существует и `wal_status='lost'` →
drop+create; существует и жив → не трогать. Зонд внутри метода (self-contained:
вызывающие не обязаны сначала пробить). Все сегодняшние вызовы ensure в
`WalStreamProcess` (шаг 3 и BreakAsync) переходят на него без изменения логики
вызовов.

### 3.2 Правило в `WalStreamProcess` — шаг (3)

`slotProbes` собирает `(Src, Dsn, Exists, WalStatus)` вместо `(Src, Dsn,
Exists)`:

- `alive = Exists && WalStatus != "lost"`.
- **BROKEN-условие** (существующая ветка «слот исчез»): `All(!p.Exists)` →
  `All(!p.Alive)` при живой цепочке (ключ wal ACTIVE/DEGRADED) → тот же
  `BreakAsync(recreateSlot: true)`; error-текст различает «исчез» /
  «потерян (wal_status=lost)» по факту зонда. Механика t07 не меняется:
  BROKEN → планировщик немедленно переснимает полный → COMPLETED → контроль
  заживляет одним тиком.
- **Lost при живом втором источнике** (не BROKEN): для потерянного источника —
  `RecreateSlotAsync` + journal-фаза `slot-recreate/<X>` (op `backup-wal`,
  текст: нода, слот, «wal_status=lost — слот пересоздан, агент вернётся от
  хвоста S3»). Не BROKEN, агенты не трогаются, супервиз не блокируется.
- **Ensure-ветка** (первый старт / BROKEN-ключ, `chainKnown=false`):
  отсутствующие → create (как сегодня), lost → recreate (см. EnsureSlotAliveAsync) —
  пустой префикс `wal/` + lost лечится recreate без BROKEN: свежий слот держит
  текущую позицию, приёмник стартует от неё.

Журнал-факт пишется ДО мутации слота (journal-before-manipulations, канон
arch/17) —可见ность действия при падении между drop и create (тик повторит).

### 3.3 Наблюдаемость

- **Панель** `SlotWalLostRule`: `Remedy` → `AlertRemedy.WorkerAuto`, текст —
  «воркер пересоздаёт lost-слот автоматически (t19); алерт висит — воркер не
  лечит: журнал backup-wal / healthz»; Hint — без ручного разбора. Алерт
  остаётся страховкой и гаснет сам после лечения (слот перестаёт lost).
  Словарь таблицы arch/adminpanel/03-panels.md не меняется (источник/суть
  прежние).
- **`docs/adminpanel/03-probes-alerts.md`** — синхронно с remedy.
- **`docs/runbook.md`** — новый раздел «Потеря wal-слота (автоматика t19)»:
  что происходит (max_slot_wal_keep_size, backpressure), что делает воркер
  (recreate слота; потеря всех источников → BROKEN + пересъём полного), границы
  (RPO: неподтверждённый хвост теряется в момент среза PG — свойство аварии;
  потерянный источник возвращается от хвоста S3 когда сегменты достижимы),
  ручная чистка слота больше не требуется.

### 3.4 Приёмник — без правок

`WalReceiverCore`/образ `pgworker-wal` не меняются: вечный ретрай 5 с —
механизм возврата потерянного источника после recreate. Коды выхода не трогаем.

## 4. Фазы реализации

- **Ф1 — SQL-слой** (3.1): `SlotProbeAsync`, `RecreateSlotAsync`,
  `EnsureSlotAliveAsync`; юнит-тесты SQL-текстов/идемпотентности +
  интеграция на реальном PG (`OwnPostgres`-фикстура, postgres:18-alpine —
  образец `WalSqlTests`): create/probe/recreate; фактический lost-рецепт —
  `max_slot_wal_keep_size` малый (например `16MB`), слот создан, WAL нагенерён
  (``SELECT pg_switch_wal()`` циклом), checkpoint → зонд видит `'lost'`.
- **Ф2 — правило** (3.2): кейсы WalStreamProcessTests (FakeSql расширить
  `WalStatus`): lost одного при живом втором → не BROKEN + recreate-вызов +
  журнал; lost всех при живой цепочке → BROKEN + recreateSlot (error содержит
  lost) — регресс «слот исчез» не ломается; lost + пустой префикс → recreate
  без BROKEN; повторный тик на здоровом слоте — нулевые мутации.
- **Ф3 — панель/runbook** (3.3): remedy/hint, раздел runbook,
  docs/adminpanel, тесты AlertHintRemedyTests/HaAlertRulesTests обновить.
- **Ф4 — E2E** (docker, Release): сценарий в `E2eWalStreamScenarios` по
  образцу AC2 «слот исчез»: живой кластер с двойной архивацией → агент мастера
  снесён (демонтаж контейнера), `max_slot_wal_keep_size` малый, WAL нагенерён
  (pgbench) → SQL-зонд подтверждает lost → агент возвращён/тик воркера:
  assert — ключ wal НЕ BROKEN, журнал содержит `slot-recreate`, слот не lost,
  `last_uploaded_segment` растёт без дыры (цепочка WalChain непрерывна).
  Мерж-гейт по AGENTS.md: docker-E2E на свежем Release (кейс-маркер
  Scale_AddEmptyShard + wal-кейс t19).

## 5. Ограничения

- `RecreateNodeHandler` / `NodeSupervisor` / HA-надзор — не трогаем.
- Приёмник (`src/PgWorker.WalReceiver`, образ `pgworker-wal`) — не трогаем.
- Новых etcd-ключей и полей ключа `wal` нет; конфиг-опций нет.
- Панель остаётся читателем; SQL-проба панели не меняется.
- RPO-граница не двигается: неподтверждённый хвост WAL теряется в момент
  среза PG (свойство аварии до любой автоматики); t19 ускоряет RTO
  восстановления архивации и убирает ручной разбор.

## 6. Критерии приёмки

1. Юнит: lost на одном источнике при живом втором → тик НЕ пишет BROKEN,
   слот потерянного источника пересоздан (FakeSql фиксирует drop+create),
   journal-фаза `slot-recreate` записана.
2. Юнит: lost на ВСЕХ источниках при живом (ACTIVE/DEGRADED) ключе → BROKEN
   (BreakAsync, recreateSlot=true), error содержит «lost»; существующие кейсы
   «слот исчез» (WalStreamProcessTests AC2/AC6-семейство) зелёные — регресса
   нет.
3. Юнит: ensure-ветка (chainKnown=false / BROKEN-ключ) + слот есть, но lost →
   recreate (не duplicate-пропуск ensure).
4. Интеграция на реальном PG: слот фактически доведён до `wal_status='lost'`
   → `SlotProbeAsync` видит lost; `EnsureSlotAliveAsync`/`RecreateSlotAsync`
   возвращают живой слот (зонд не lost), повторный вызов идемпотентен.
5. E2E (docker, Release): кейс 4.Ф4 зелёный — автолечение без дыры цепочки и
   без BROKEN; мерж-гейт — свежий Release (AGENTS.md).
6. Панель/runbook: remedy `slot-wal-lost` = WorkerAuto; раздел runbook
   «Потеря wal-слота» существует и описывает автоматику; тесты панели зелёные.
7. Идемпотентность: тик на уже здоровом (не lost) слоте не делает мутаций и
   не пишет журнал-фаз.
8. arch/19 обновлён (правка этой фазы): пункт «Слот» (зонд существование+
   wal_status), «Правила непрерывности» (lost одного источника ≠ BROKEN;
   lost/исчезновение всех → BROKEN), риск-таблица §10.

## 8. Отвергнутые альтернативы

- **Авто-recreate ноды** (буква roadmap-ремеди): rebuild с basebackup / для
  мастера — switchover; данные ноды целы — избыточно и медленно. Отвергнуто
  пользователем.
- **Всегда BROKEN при любом lost**: зря останавливает живой источник и
  запускает полный пересъём, когда дыра уже закрыта второй стороной.
- **Проверка достижимости сегментов (хвост S3 vs горизонт ноды)** перед
  решением: не нужна — физическая семантика (§2) делает разделение избыточным:
  живой слот второго источника гарантирует бесшовность от хвоста S3 (его
  restart_lsn ≥ хвост), потерянный возвращается ретраем, когда сегменты
  появляются; потеря обоих — видна зонду напрямую (All lost/absent).
- **Доработка приёмника** (permanent-код при «segment removed»): вечный ретрай
  — уже нужное поведение возврата; воркер-зонд видит lost раньше и точнее.
