# t36-s3-pool-integration — спека

Клиентская интеграция пула S3-серверов (ownS3) в подсистему бэкапов:
выбор «какой кластер куда бэкапится» и приоритеты нод записи per-cluster
(отдельные списки мастера и реплики), приём через API воркера, управление
и наблюдение — на странице «Хранилище бэкапов» панели. Дополнительно (по
канону roadmap/s3.md): выгрузка etcd-слепков на отдельную per-install
env-пару и креды серверов как env-профили воркера.

Канон домена: `arch/23-s3-clusters.md` (пул, `endpoints`,
`secret_profile`), `arch/24-s3worker.md` (оркестратор пула),
`arch/19-backups.md` (подсистема бэкапов), `arch/14-pgworker.md` §1.1/§6/§8
(API, слепки), `arch/adminpanel/02-etcd-contract.md` +
`arch/adminpanel/03-panels.md` (панель).

## 1. Цель

1. **Куда бэкапится кластер — явный выбор оператора.** PG-кластер
   ссылается на пул S3 (кластер ownS3 из `/s3/clusters/`) через
   per-cluster policy бэкапов; без выбора бэкапы кластера не пишутся
   (алерт). Никакого env-дефолта и legacy-пути записи данных шардов —
   единственный путь записи: пул из policy.
2. **Приоритеты нод записи per-cluster, отдельные списки мастера и
   реплики.** Мастер-потоки (WAL-агент мастера, полный бэкап при
   fallback-источнике «мастер») пишут на первую доступную ноду
   master-списка; репличные (WAL-агент sync-standby, полный бэкап с
   реплики) — replica-списка. Списки независимы: оператор разводит
   мастера и реплику на разные ноды пула (надёжность — отказ ноды с
   диском не убивает оба потока); одна нода в пуле/списке — оба пишут на
   неё. Запись — «первый доступный по списку»: недоступна текущая нода →
   перебор к следующей по списку; исчерпан весь список → алерт (и
   ретрай-цикл для WAL-агента).
3. **Смена ролей учитывается автоматически.** Слейв стал мастером
   (failover) — его агент пересоздаётся воркером уже с master-списком
   (механика пересоздания агентов при смене мастера/sync-standby уже в
   каноне arch/19 §3; меняется только комплект списка).
4. **Чтение — все ноды пула без приоритетов**: verify, restore, drill,
   резолв хвоста WAL, ретенционные сверки — перебор нод пула в порядке
   `endpoints`-ключа, «где данные есть» (страховка на лаг доставки
   mesh-репликации).
5. **Etcd-слепки — отдельная per-install env-пара** воркера: источник
   правды о DR-слепках не может жить в восстанавливаемом etcd
   (arch/14 §6), поэтому слепки выгружаются на фиксированный
   endpoint/bucket/креды из env, независимо от пула.
6. **Креды серверов — env-профили воркера**: пул ссылается на профиль
   (`config.secret_profile`), PgWorker резолвит креды per-профиль из
   env (по образцу `S3W_NODE_SECRETS__*` у S3Worker). Секреты — вне etcd
   и git (arch/19 §7).
7. **Страница «Хранилище бэкапов»**: per-кластер выбор пула и
   редактирование списков мастера/реплики (мутация — через API воркера,
   панель по-прежнему в etcd домена бэкапов ничего не пишет).

### Решения пользователя (фиксированы)

| Вопрос | Решение |
|---|---|
| Объём | полный канон t36: пул + приоритеты + страница + слепки на отдельную пару + креды-профили |
| Policy без секции s3 | только явный выбор: бэкапы кластера не пишутся, алерт |
| Внешние S3 (облако/MinIO вне `/s3/`) | за рамками задачи; в arch — точка расширения («статические цели external»), подключение — отдельной задачей roadmap |
| Формат элементов списков | ссылки `pool + имя ноды` (не сырые адреса): воркер резолвит в host:port, переживает смену портов portalloc |
| Порядок чтения | все ноды пула без приоритетов (порядок `endpoints`-ключа), перебор «где данные есть» |

## 2. Принципы

- **Arch-first**: контракт меняется сначала в `arch/` (раздел 3), затем
  код. Код зеркалит канон.
- **PgWorker — читатель `/s3/`, участником контракта не становится**
  (arch/23 преамбула): дискавери пула — чтение `endpoints`/`config`/
  `nodes/<I>/state`; никаких записей в `/s3/`.
- **Паттерны arch/17**: идемпотентность каждого шага,
  journal-before-manipulations, transient vs permanent. Недоступность
  ноды пула — transient (перебор), недоступность всего пула — transient
  (алерт + ретраи), некорректная policy (пул/нода не существует) —
  валидация на приёме (400) + для уже записанной — алерт и отказ
  записи без краша тика.
- **Health-проба недоступность не доказывает** (факт 8
  `docs/s3-replication.md`): участие ноды в списках не фильтруется по
  `nodes/<I>/state` — перебор решает по факту операции; быстрый
  отказ/успех, не молчание (R3 `docs/owns3-replication-requirements.md`,
  per-попыточный таймаут уже в `BackupS3`).
- **Пишут/удаляют только процессы воркера** (арх-канон arch/19 §4/§5);
  панель по-прежнему немой читатель etcd + прокси мутаций в API воркера.
- **Один bucket per-install на всех пулах** (arch/23 §5): имя —
  `PgWorker:Backups:S3:Bucket`; layout `<C>/<X>/…` без изменений
  (arch/19 §5). Разные пулы — раздельные экземпляры этого bucket;
  синхронизация между пулами НЕ предполагается (mesh — внутри пула).
- **Ровно один пул на PG-кластер**: списки мастера/реплики — ноды одного
  пула. Мульти-пул в одной policy — точка расширения (вместе с
  external), в этой задаче не вводится.

## 4. Структура и компоненты (код)

### 4.1. PgWorker: домен /s3/ и резолвер пула

- **`S3PoolStore`** (`src/PgWorker.Etcd`): чтение
  `/s3/clusters/<C>/{config, nodes/<I>/state, endpoints}` тем же
  etcd-клиентом воркера (poll тиком, unknownKeys-толерантность). Модель:
  `S3Pool(string Name, string? SecretProfile, IReadOnlyList<S3PoolNode>
  Nodes, string[] Endpoints)`, `S3PoolNode(string Name, string? State,
  string? PlacedOn)`; `endpoints`-строка парсится в пары host:port,
  порядок сохраняется (порядок чтения).
- **`BackupPoolResolver`** (`src/PgWorker.Backups`): per-cluster
  policy.s3 → пул → списки: `WriteMaster`/`WriteReplica` (резолв ссылок
  в host:port через `endpoints`+portalloc-порядок пула) и `ReadAll`
  (все ноды пула в порядке `endpoints`). Креды: профиль пула →
  env-профиль `PGW_BACKUP_S3_PROFILES__*`. Исходы: пул не найден /
  профиль без кредов / списки пусты — диагностическая ошибка для
  вызывающего процесса (transient-путь: ретраи тиком + алертная
  проекция), не краш тика.
- **`IBackupS3` остаётся интерфейсом операций**, реализация
  **`PoolBackupS3`**: конструируется фабрикой per-цели (endpoint+креды
  одного адреса — существующий `BackupS3` как внутренний клиент),
  семантика перебора:
  - запись (put/delete): список `Write*` — операция на текущей ноде,
    отказ → следующая по списку; исчерпание → `Failed` c error-маркером
    `s3-pool-exhausted`;
  - точечное чтение (get/list полных): список `ReadAll` — NotFound/
    транспортный отказ → следующая нода; нашли — оттуда;
  - листинги (list-v2 префиксов): первая доступная нода `ReadAll`
    (лаг mesh допускается; повторные проходы досматривают — контроль
    цепочки уже толерантен к переходным окнам);
  - `BucketExistsAsync` — любая доступная нода.

### 4.2. Процессы: списки по ролям

- **WAL-агент (`WalStreamProcess` + `WalReceiverCore`)**: env агента
  вместо одного `S3_ENDPOINT` несёт `S3_ENDPOINTS` (запятая, порядок
  списка роли источника) + креды профиля пула; приёмник держит текущий
  endpoint (первый доступный), при отказе — следующий по списку, при
  исчерпании — ретрай-цикл (стрим стоит, backpressure, слот держит —
  инвариант RPO arch/19 §3 не меняется) + маркер
  `s3-pool-exhausted` в статусе (`DEGRADED`). Резолв хвоста (list
  `wal/`) — перебор `ReadAll`. Смена роли источника — пересоздание
  агента воркером со списком новой роли (существующая механика §3).
- **Полный бэкап (`BackupJobSpec` + `docker/backup/entrypoint.sh`)**:
  env `PGW_BK_S3_ENDPOINTS` (список роли источника: реплика →
  `write_replica`, fallback-мастер → `write_master`) вместо одиночного
  `PGW_BK_S3_ENDPOINT`; entrypoint: до загрузки — выбор первого
  доступного (короткая mc-проба `mc ls` с таймаутом per-попытки),
  загрузка на него; падение загрузки → следующий endpoint списка
  (переливка идемпотентна: имена объектов детерминированы). Результат
  `s3-pool-exhausted` — FAILED с маркером (обычный бэкофф переснятия).
- **Verify/restore/drill-джобы**: списки `ReadAll` для скачивания
  (entrypoint/inline: перебор до найденного); листинги verify
  (полнота цепочки) — первая доступная нода.
- **Ретенция и супервизор**: удаления — первая доступная нода пула
  кластера (tombstone разносит mesh — owns3/07 §7); глобальные проходы
  (`/pgworker/backups/storage`, реестр сирот) — union по всем
  существующим пулам `/s3/clusters/`: по первому доступному endpoint
  каждого пула отдельный list; дедуп ключей — по (пул, ключ).
- **Restore-заявка**: поле `source_pool` (опц.) — пул чтения
  DR-источника; свой пул — дефолт.
- **Слепки etcd (`EtcdSnapshotSink`)**: клиент из
  `PgWorker:Snapshots:Export:S3` (отдельная пара); префикс `etcd/` — в
  её bucket; ретенция слепков — там же.

### 4.3. API воркера (PgWorker)

- `POST /api/clusters/{c}/backups/policy`: тело дополнительно принимает
  `"s3":{"pool":string,"write_master":[string],"write_replica":[string]}`
  (замещение целиком — как drill). Валидация (400 по полям):
  - `pool` существует в `/s3/clusters/` (чтение живое, не из кэша
    снапшота) и не `TO_REMOVE`;
  - имена списков — инстансы пула (`nodes/<I>/placement` существует),
    без дублей внутри списка;
  - списки непустые (у кластера всегда есть мастер-источник; пустой
    список = «не выбрано» — это отсутствие секции целиком);
  - пересечение списков допустимо (одна нода — оба пишут на неё);
  - неполный охват допустим (в списках — только перечисленные ноды,
    порядок = приоритет; новые ноды пула подключает оператор).
- Отсутствие секции `s3` в теле — её удаление из policy (бэкапы
  кластера выключаются — «только явный выбор»).
- `POST /api/clusters/{c}/shards/{x}/restore`: опциональное
  `source_pool` (валидация как у policy-пула).

### 4.4. Env/конфиг PgWorker (deploy)

- Убирается: `PGW_BACKUP_S3_ENDPOINT`, `PGW_BACKUP_S3_REGION`,
  `PGW_BACKUP_S3_ACCESS_KEY`, `PGW_BACKUP_S3_SECRET_KEY`,
  `PGW_BACKUP_S3_ADVERTISED_ENDPOINT` (в части данных шардов; см.
  миграцию §7).
- Добавляется: `PGW_BACKUP_S3_PROFILES__<PROFILE>__ACCESS_KEY`,
  `PGW_BACKUP_S3_PROFILES__<PROFILE>__SECRET_KEY` (read-write ключи
  профилей пулов; имя профиля = `config.secret_profile` пула);
  `PGW_BACKUP_S3_BUCKET` остаётся (bucket per-install);
  `PGW_BACKUP_S3_CA_BUNDLE_PATH` остаётся (per-install CA на все цели).
- Добавляется: `PGW_SNAPSHOTS_S3_ENDPOINT`,
  `PGW_SNAPSHOTS_S3_BUCKET`, `PGW_SNAPSHOTS_S3_ACCESS_KEY`,
  `PGW_SNAPSHOTS_S3_SECRET_KEY` (+ опц. `__REGION`, `__CA_BUNDLE_PATH`)
  — обязательны при `PGW_SNAPSHOTS_EXPORT_ENABLED=true` (fail-fast).
- Валидация старта: `Backups:Enabled=true` требует непустой Bucket и
  хотя бы один профиль кредов; `Snapshots:Export:Enabled=true` требует
  полную слепочную пару.

### 4.5. AdminPanel

- **Read-минимум домена S3** (`AdminPanel.Etcd`): чтение
  `/s3/clusters/*/` (config/nodes/state/endpoints) в
  domain-снапшот `S3PoolInfo` — только для страницы бэкапов; битый
  JSON — parseError-запись, толерантность unknownKeys (как прочие
  домены).
- **Страница «Хранилище бэкапов»** (`BackupsStoragePage.tsx`):
  - в таблице «Кластеры → шарды»: колонка «Пул» — бейдж имени пула либо
    красный «пул не выбран»;
  - кнопка «Пул бэкапов» per-кластер → модал:
    - Select пула (Active-кластеры `/s3/`: имя + подсказка числа нод);
      «Не выбрано» — допустимый сохраняемый вариант (выключение);
    - два упорядоченных списка: «Запись мастера» / «Запись реплики» —
      чекбоксами нод выбранного пула + порядок кнопками
      вверх/вниз (Mantine, без DnD-библиотек); подпись-пояснение про
      разные ноды мастера/реплики и одну ноду как общий случай;
    - сохранение — полный policy (retention + full_max_age + verify +
      drill + s3) через `PUT /api/clusters/{c}/backups/policy`;
      ошибки ProblemDetails в теле модала (400 — по полям, 503 —
      воркер/etcd); двойной клик — блокировка кнопки.
- **Алерты AlertEngine**: `backup-pool-missing` (critical, per-cluster:
  Active-кластер со включённой подсистемой, policy без s3); 
  `backup-pool-unreachable` (critical, per-cluster: в статусах
  воркера маркер `s3-pool-exhausted` — wal `DEGRADED`/full `FAILED`).
- **Live-инвентарь §2.5**: env `AdminPanel:Backups:S3:Endpoints`
  (запятая; одиночный `Endpoint` — валидный частный случай), list с
  первого доступного; DTO несёт список endpoints (без ключей).

### 4.6. Стенд (dev-stand)

- `deploy/.env.example`: новые переменные (§4.4), убрать ушедшие;
  профиль пула стенда `backups-main` — креды создаются при подъёме
  ownS3-контура (sync с OWNS3_ACCESS_KEYS стенда).
- Стендовый ownS3-контур (`deploy/docker-compose.yml`, сервис `owns3`)
  остаётся «пулом из одной ноды» до заведения S3-кластера через
  S3Worker: сид/cheкка заводит кластер `/s3/` (S3Worker поднимет
  ownS3-ноды) ИЛИ стенд использует существующий `owns3` как внешнюю
  цель — НЕ вводим: пул только через `/s3/` (см. «ограничения» §6 —
  переходный период описан в миграции §7).

## 5. Формат policy (каноническое значение)

`/pgworker/backups/<C>/policy`:

```json
{"retention":{"days":1,"weeks":1,"months":1},
 "full_max_age_sec":86400,
 "verify":{"on_create":true,"interval_sec":604800},
 "drill":{"interval_days":1},
 "s3":{"pool":"backups",
       "write_master":["east1","east2"],
       "write_replica":["east2","east1"]}}
```

- Секция `s3` опциональна (отсутствие = пул не выбран, запись
  выключена, алерт).
- Списки — имена инстансов пула (`<I>`), упорядочены по приоритету
  записи; допускаются пересечения и неполный охват.
- Резолв ссылки → адрес: нода `<I>` пула → порт из
  `/s3worker/portalloc/<C пула>` (тот же источник, из которого
  S3Worker собирает `endpoints`); воркер читает готовый
  `endpoints`-ключ и сопоставляет имена нод по portalloc-записи.
- Толерантность парсеров: policy без `s3` читается без ошибок
  (backwards-compat, как drill).

## 6. Ограничения (осознанные)

- Внешние S3 (облако/MinIO вне `/s3/`) — НЕ поддержаны как цели записи
  этой задачей; контракт policy проектируется под расширение
  (статические цели `external` в env воркера), подключение — отдельная
  задачей roadmap (отметить в `arch/roadmap/s3.md` при мерж-гейте).
- Один пул на PG-кластер; мульти-пул — точка расширения.
- CA https — один per-install `CaBundlePath` на все цели; per-пул CA —
  за рамками (все пулы одной установки — один TLS-пакет `deploy/tls/`).
- `Region`/`PathStyle` per-цель не вводятся (MinIO/ownS3-контур;
  ForcePathStyle=true остаётся общим); прод-облако появится вместе с
  external-целями.
- Чтение листингов — с одной (первой доступной) ноды пула: лаг mesh
  допускается, сверка цепочки уже переживает переходные окна
  (list — истина, повторные проходы); точечные GET — перебор до
  найденного.
- Глобальные сверки (storage/orphans) — по одному list'у на пул
  (первый доступный endpoint), не по всем нодам: занятость/сироты —
  агрегат сходимости mesh.

## 7. Миграция и переходный период

- Существующие установки: после обновления у кластеров нет секции `s3`
  → бэкапы не пишутся, `backup-pool-missing` зажигается сразу —
  осознанное следствие решения «только явный выбор». Действие оператора:
  поднять пул (S3Worker) → задать policy с секцией `s3` со страницы.
- Старые env `PGW_BACKUP_S3_*` (endpoint/креды) игнорируются воркером
  (кроме Bucket/CA); в `deploy/.env.example` заменяются новыми.
- Dev-стенд: пул данных — S3-кластер из одной ноды, который заводит
  сид чеков стенда через S3Worker (S3Worker поднимает ownS3-ноду на
  хосте стенда, профиль кредов `backups-main`); существующий сервис
  `owns3` из `deploy/docker-compose.yml` остаётся целью СЛЕПКОВ (для
  них — отдельная пара: свой bucket `pgworker-etcd-snapshots`,
  отдельные креды; адрес того же сервиса допустим — контур per-install
  env, не пул). Чек `00-up.sh` дополняется сидом пула.

## 8. Фазы реализации

1. **arch-first**: правки §3 (все документы/разделы таблицы) — первая
   фаза, ревью подряд.
2. **Домен PgWorker**: `S3PoolStore` (чтение `/s3/`), env-профили,
   `BackupPoolResolver`, `PoolBackupS3` (+ юниты: резолв ссылок,
   переборы записи/чтения, исчерпание, толерантность парсинга).
3. **Процессы**: env-контракты агента/джоба (`S3_ENDPOINTS`,
   `PGW_BK_S3_ENDPOINTS`), entrypoint-перебор, verify/restore/drill/
   retention/supervisor на пул-клиенте, restore `source_pool`,
   маркер `s3-pool-exhausted` в статусах (+ юниты/интеграции).
4. **Слепки**: отдельная env-пара, вынос префикса `etcd/` (+ юниты).
5. **API**: расширение policy + валидация (+ API-интеграции).
6. **Панель**: read-минимум `/s3/`, модал «Пул бэкапов», алерты,
   инвентарь `Endpoints` (+ юниты API, e2e-чеки панели).
7. **Стенд/E2E**: deploy env, сид пула стенда; docker-E2E на свежем
   Release (обязателен — код воркеров меняется): сценарии §9.

## 9. Критерии приёмки (E2E и проверки)

1. **AC1 — выбор пула**: кластер без секции `s3` → полный не
   планируется, `backup-pool-missing` горит; задание policy со страницы
   (или API) → полный бэкап снимается в пул, объекты на нодах пула.
2. **AC2 — разведение мастера/реплики**: пул из 2 нод, списки
   `write_master=[n1]`, `write_replica=[n2]`: WAL-объекты
   мастер-агента наблюдаются на n1, sync-агента — на n2 (инспекция
   объектов нод); полный с реплики — объекты `full/<id>/` на n2.
3. **AC3 — одна нода**: списки `[n1]`/`[n1]` (или пул из одной ноды) —
   оба агента пишут на n1, цепочка валидна, restore проходит.
4. **AC4 — перебор и алерт**: списки `[n1,n2]`/`[n2,n1]`; стоп n1 →
   мастер-агент доезжает до n2 (стрим продолжается, RPO-инвариант
   удержан: подтверждение слота только после успешного put); списки
   `[n1]`/`[n2]`, стоп n1 → мастер-агент в ретрай-цикле,
   `s3-pool-exhausted` в статусе, `backup-pool-unreachable` горит;
   подъём n1 → поток сам заживляется.
5. **AC5 — смена ролей**: failover (слейв → мастер) → агент пересоздан
   с master-списком (объекты его потока наблюдаются на ноде
   master-списка), цепочка непрерывна через `.history`.
6. **AC6 — чтение без приоритетов**: verify/restore/drill читают с
   первой доступной ноды пула; стоп ноды, где лежали данные → чтение
   доезжает до другой (mesh доставил/лаг допущен), restore COMPLETED.
7. **AC7 — слепки**: при включённом экспорте и заданной отдельной паре
   слепки выгружаются в её bucket (префикс `etcd/`), статус-ключ
   обновляется; незаданная пара при Enabled → fail-fast старта.
8. **AC8 — API/валидация**: policy с несуществующим пулом/нодой,
   дублями, пустыми списками → 400 с полями; restore с `source_pool`
   DR-кластера → COMPLETED из чужого префикса.
9. **AC9 — панель**: модал сохраняет полный policy; бейдж пула в
   таблице; оба алерта зажигаются/гасятся по своим условиям;
   `Endpoints`-инвентарь переживает недоступность первого адреса.
10. **AC10 — регрессии**: полный прогон существующих бэкап-E2E серий
    зелёный (существующие фикстуры переведены на пул-режим: контур
    ownS3-цели фикстуры заводится как пул `/s3/` сидом).
