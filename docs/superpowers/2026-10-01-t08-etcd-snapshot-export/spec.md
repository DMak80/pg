## 1. Цель

Снапшоты etcd (контроль-плейн: декларации кластеров, маршрутизация, секреты,
клэймы, portalloc) сегодня не покидают docker-хост: `SnapshotJob` пишет
`snapshot-<ts>.db` в локальный volume `pgw-snapshots` (ретеншн 10 файлов),
снимает их лидер снапшотов PgWorker раз в 6 ч + процессы в точках изменений
(arch/14 §6 P12). Потеря хоста вместе с etcd = потеря контроль-плейна
целиком: декларации и маршрутизация восстанавливались бы только вручную,
per-cluster секреты (`/clusters/<C>/*_password`), portalloc и WAL-цепочки
бэкапов — невосстановимо. Roadmap-строка t08 фиксирует разрыв: снапшоты
есть, но «в локальном volume лидера» — защита умирает вместе с хостом.

Задача закрывает разрыв выгрузкой в S3 и каноном восстановления:

1. **Экспорт в точке снятия**: каждый снятый слепок etcd (плановый и
   внеочередной) уходит в S3 — объектное хранилище установки (тот же bucket
   бэкапов, MinIO/облако) — служебным префиксом `etcd/`, с sha256-метаданными.
   RPO контроль-плейна = точка последнего изменения минус окно transient-отказа
   S3 (доводка тиком, §3.5).
2. **Ретенция S3**: последние N пар `.db`+`.meta.json` (дефолт 28 ≈ неделя при
   интервале 6 ч); удаление — только ретенцией экспорта, guard «≥1 остаётся».
3. **Статус/наблюдаемость**: глобальный ключ `/pgworker/etcd-snapshots`
   (последняя выгрузка, sha256, ошибка) + панельные алерты
   `etcd-snapshot-export-failed` (critical) / `etcd-snapshot-export-stale`
   (warning): молчаливая деградация выгрузки видна оператору до аварии.
4. **Канон восстановления из выгрузки**: arch/09 §4 + раздел runbook
   (`docs/runbook.md`) — полный операторский путь «погиб etcd/хост → свежий
   etcd → restore из S3 → контроль-плейн жив», включая обязательную проверку
   целостности (`etcdctl snapshot status`) и R7-оговорку arch/14 (клэймы —
   lease, journal может откатиться — процессы идемпотентны).
5. **Доказательство разворачиваемости**: интеграционные тесты и E2E качают
   выгрузку из S3 и прогоняют `etcdctl snapshot status` на реальном
   etcd-контейнере — выгрузка гарантируемо разворачиваема, не просто
   «файл скопирован».

Функциональные результаты: опциональный sink-интерфейс снапшотов
(`Shared.Etcd`), S3-реализация sink + ретенция + статус (`PgWorker.Backups`),
доводка выгрузки в `SnapshotLoop`, опции+валидация+compose, панельные
парсер/алерты/карточка, runbook+arch-правки, юниты/интеграции/E2E.

## 2. Принципы

1. **Arch-first**: контракт (arch/14 §3/§6/§8, arch/19 §5/§7, arch/09 §4,
   adminpanel/02 §2.3.1, adminpanel/03 §4) обновляется ДО кода (Фаза 6
   dev-flow по плану); код зеркалит канон.
2. **Экспорт в точке снятия, а не по расписанию**: sink вызывается из
   `SnapshotJob.TakeAsync` сразу после записи локального файла — внеочередные
   слепки точек изменений (provisioning/deprovisioning/эвакуация, «до» и
   «после») уходят в S3 тем же вызовом. Отдельный «экспортный цикл по
   расписанию» отвергнут: точки изменений не повторяются — их слепок либо
   уехал сейчас, либо окно RPO держится до планового тика.
3. **Локальный слепок — истина снятия, экспорт её не роняет**: сбой выгрузки
   (S3-транзиент) НЕ делает `TakeAsync` неудачным — локальный файл записан,
   процессы кластеров не замедляются и не падают из-за S3; экспорт-ошибка
   фиксируется в статус-ключе и догоняется доводкой (§3.5). Транзиент
   удлиняет RPO окна, но никогда не блокирует снятие.
4. **Один экспортёр на установку**: слепок цел (снимает любой воркер —
   получаем весь etcd); выгружает PgWorker — единственный владелец
   S3-кредов per-install. KafkaWorker/ValkeyWorker продолжают писать только
   локальные тома (их контракты не меняются; их слепки — дубль того же
   содержимого, выгрузка не дублируется). Отказ воркеров PgWorker (оба
   инстанса) замораживает экспорт — панельный алерт `etcd-snapshot-export-stale`
   это видит.
5. **Bucket per-install, служебный префикс**: `etcd/` — тот же единственный
   bucket (arch/19 §5), те же креды (§7). Префикс служебный: он НЕ форма
   `<C>/<X>/` и по построению не попадает в реестр сирот t07
   (`GroupPrefixes`: ключи короче 3 сегментов мимо группировки) —
   фиксируется гвард-тестом. В `used_bytes` ключа `/pgworker/backups/storage`
   объекты `etcd/` входят (list всего bucket — занятость bucket, это корректно).
6. **Паттерны arch/17**: идемпотентность (повторный put того же объекта
   безопасен; перезапись при коллизии имён в одну секунду — новее поверх
   старее); journal-семантики не требуется — состояние вырождено в один
   статус-ключ (put поверх, без read-modify-write — паттерн `orphan-holds`);
   transient vs permanent (S3-транспорт — всегда transient: догоняет доводка;
   permanent-ошибок экспорта нет — даже «bucket исчез» остаётся transient,
   алерт панели сигнализирует оператору).
7. **Каждый слепок уезжает — без дедупа**: каждый снятый слепок (плановый и
   внеочередной) выгружается в S3 целиком; дедуп по sha256 целого слепка
   отвергнут как самореферентно недостижимый — статус-ключ живёт в том же
   etcd, из которого снимается слепок: запись статуса после каждой выгрузки
   меняет содержимое следующего слепка (байты и MVCC-ревизия), поэтому
   sha256 следующего слепка всегда ≠ `last_sha256` после первого цикла
   (ревью к.4; живой etcd и так мутирует между тиками — клэймы/journal
   воркеров). Рентабельность без дедупа: 4 пары/сутки при интервале 6 ч
   (слепки контроль-плейна маленькие), ретенция N последних пар (§3.2)
   ограничивает рост. sha256 остаётся в `.meta.json` — целостность и
   verify при восстановлении (§3.8); `last_sha256` в статус-ключе —
   наблюдаемость (последний подтверждённый sha), НЕ участник решения о put.
8. **Takeover наследуется**: экспорт выполняет держатель глобального клэйма
   снапшотов `/pgworker/leader` (leader-failover ≤ TTL 15 с уже работает);
   состояние экспорта — в статус-ключе etcd + объекты S3 (детерминированные
   имена) — новый лидер продолжает без дополнительной координации.
9. **Восстановление — зона оператора**: при погибшем etcd воркер сам
   восстановиться не может (живёт на нём) — путь восстановления:
   runbook-рецепт оператора + arch-канон; автоматизация восстановления
   вне скоупа.
10. **Нулевое влияние при выключенной опции**: `Snapshots:Export:Enabled=false`
    (дефолт) — поведение воркера байт-в-байт прежнее (sink не подключён);
    включение — fail-fast-валидация S3-комплекта.

## 3. Структура и компоненты

### 3.1. Контракт etcd: ключ `/pgworker/etcd-snapshots` (канон arch/14 §3)

Глобальный ключ (вне per-cluster префиксов; D2-deprovisioning не касается;
`del --prefix` чисток нет — ключ перезаписывается на месте). Пишет ТОЛЬКО
инстанс PgWorker, выполнивший экспорт-операцию (обычно лидер снапшотов;
точки изменений пишут из процессов под per-cluster клэймом — тоже корректно:
put одним ключом без RMW, значение — факт последней выгрузки, гонок между
писателями по смыслу нет). Панель читает (§3.7).

| Ключ | Значение |
|---|---|
| `/pgworker/etcd-snapshots` | `{"enabled":true,"state":"OK"\|"FAILED","last_uploaded_unix":N,"last_object":"etcd/snapshot-20261001-120000.db","last_sha256":"<hex>","size_bytes":N,"interval_min":360,"error"?:"…"}`; `enabled` — факт включённой опции (панель отличает «выключено» от «ключа ещё нет»); `interval_min` — плановый интервал снапшотов (`Loops:SnapshotIntervalMin`) для панельного расчёта stale без конфига воркера; `error` присутствует у FAILED (текст последней ошибки выгрузки) |

Правила: успешная выгрузка/доводка ⇒ `state=OK` + поля факта; неудача ⇒
`state=FAILED` + `error` (поля последнего успеха сохраняются — оператор видит,
насколько отстал). **Семантика `last_uploaded_unix` — «покрытие», а не время
последнего put-запроса**: метка снятия последнего слепка, чьё содержимое
подтверждённо доставлено в S3 фактическим upload'ом (§3.6). Поле двигается
каждым успешным проходом sink'а; на нём держатся детект отставания (§3.5) и
порог stale-алерта (§3.7) — замирание поля на живом контуре означало бы
ложное «отставание». `last_object` — объект последней выгрузки, реально
лежащий в S3; `last_sha256` — sha256 этой выгрузки (наблюдаемость; в решении
о put не участвует — дедупа нет, §2.7). Ключ не является источником для
восстановления (etcd мёртв — ключа нет); его роль — наблюдаемость.

### 3.2. Хранилище S3: layout и ретенция (канон arch/19 §5 — дополнение)

Тот же bucket per-install (`PgWorker:Backups:S3:Bucket`); служебный префикс
(вне per-cluster/per-shard формы):

```
s3://<bucket>/etcd/
  snapshot-<id>.db              # слепок etcd 1:1 (snapshot-<yyyyMMdd-HHmmss>.db)
  snapshot-<id>.meta.json       # метаданные выгрузки
```

- `<id>` — таймстемп имени локального слепка (`yyyyMMdd-HHmmss`, как
  `SnapshotJob`); коллизия двух слепков в одну секунду ⇒ перезапись объекта
  идемпотентна (в bucket остаётся новее содержимое той же секунды).
- **`snapshot-<id>.meta.json`**: `{"sha256":"<hex>","size_bytes":N,"revision":<n>?,"taken_unix":N,"uploaded_unix":N,"instance":"<InstanceId>"}`; `revision` — ревизия etcd на момент снятия (best-effort: `StatusAsync` первого живого endpoint, паттерн `MaintainAsync`; недоступна — поле опускается, слепок не виноват); `uploaded_unix` — фактическое время put'а объекта (в отличие от «покрытия» в статус-ключе, §3.1); `instance` — какой инстанс воркера выгрузил (диагностика takeover).
- **Ретенция S3**: после каждой успешной выгрузки — list префикса `etcd/`,
  пары `.db`+`.meta.json` сортируются по имени (таймстемп лексикографически =
  хронологически), старше `RetentionObjects` последних — batch-delete
  (`.meta.json` сносится вместе со своим `.db`; одиночный `.meta.json` без
  `.db` — тоже мусор ретенции, сносится). Guard по построению: удаляется
  только то, что старше оставляемых — ≥1 полная пара остаётся всегда.
  Единственный удаляющий объектов `etcd/*` — эта ретенция (R4-симметрия:
  стоп-семантика/deprovisioning префикс не трогают; ретенция бэкапов t06 и
  sweeper t07 к `etcd/` не прикасаются — их пути адресны: `full/<id>/`,
  `wal/`, префиксы сирот `<C>/<X>/`).
- **Реестр сирот t07**: `etcd/` не форма `<C>/<X>/` — `GroupPrefixes` его
  не группирует (ключи `etcd/…` короче 3 сегментов); фиксируется юнит-гвардом
  на `GroupPrefixes` с объектами `etcd/*` (реестр пуст).

### 3.3. Конфигурация (канон arch/14 §8)

Новая подсекция `PgWorker:Snapshots:Export` (в `SnapshotOptions`):

| Опция | Дефолт | Смысл |
|---|---|---|
| `Enabled` | `false` | выгрузка включена; `false` — sink не подключается, поведение прежнее |
| `RetentionObjects` | `28` | сколько последних пар держать в S3 (≈ неделя при интервале 6 ч); `≥1` |
| `RetryIntervalSec` | `300` | сон лидера-тика при отстающей выгрузке (вместо полного `SnapshotIntervalMin`; §3.5) |
| `TimeoutSec` | `30` | бюджет одного S3-put-шага внутри `TakeAsync` — транзиент не тормозит фазы процессов кластеров |

S3-комплект (endpoint/region/bucket/credы/path-style) — **переиспользуется из
`PgWorker:Backups:S3`** (per-install, env `PGW_BACKUP_S3_*`; второй набор
секретов не заводится). `PgWorker:Backups:Enabled` для экспорта НЕ требуется:
etcd-контроль-плейн не зависит от подсистемы бэкапов PG (допустимо
`Backups:Enabled=false` + `Snapshots:Export:Enabled=true` при заполненных
S3-полях).

Валидация старта (fail-fast): `Export:Enabled=true` при пустых
`Backups:S3 { Endpoint, Bucket, AccessKey, SecretKey }` — ошибка старта;
`RetentionObjects < 1`, `RetryIntervalSec ≤ 0`, `TimeoutSec ≤ 0` — ошибка
старта.

Развёртывание: `deploy/docker-compose.yml` (x-pgworker-env — ОБА инстанса)
+ `deploy/.env.example`: `PgWorker__Snapshots__Export__Enabled: ${PGW_SNAPSHOTS_EXPORT_ENABLED:-false}`
(креды уже есть в env). Dev-стенд: включается профилем с MinIO
(env в `dev-stand/adminpanel/` — по месту сборки стенда, без новых секретов).

### 3.4. Shared.Etcd: sink-интерфейс + SnapshotJob (обратная совместимость)

- **`ISnapshotSink`** (`src/Shared.Etcd/Maintenance/ISnapshotSink.cs`):
  `Task<Result> ExportAsync(string snapshotFileName, byte[] data, long? revision, CancellationToken ct)`.
  Контракт: попытка доставить слепок во внешнее хранилище; `Result` —
  успех/транзиент-отказ (детали/ретеншн/статус — внутри реализации);
  таймаут — забота реализации (§3.3 `TimeoutSec`).
- **`SnapshotJob`**: новый необязательный параметр конструктора
  `ISnapshotSink? sink = null`. `TakeAsync`: после записи локального файла и
  локальной ретенции — при `sink != null` вычислить sha256, снять ревизию
  (best-effort, существующий `StatusAsync`-паттерн failover по endpoints) и
  вызвать `sink.ExportAsync(...)`. Возврат `TakeAsync` прежний
  (`Result<string>` — путь локального файла): сбой sink НЕ роняет снятие
  (принцип 3); ошибка протоколируется вызывающему? — нет: sink сам пишет
  статус-ключ (§3.6), `SnapshotJob` остаётся чистым; SnapshotLoop-доводка
  (§3.5) подхватит.
- KafkaWorker/ValkeyWorker: `sink` не передаётся (`null`) — их код и тома не
  меняются вовсе (проверка: их `Program.cs`-фабрики сигнатурно совместимы —
  параметр опциональный).

### 3.5. PgWorker.App: SnapshotLoop — доводка выгрузки

`SnapshotLoop` (лидер снапшотов) расширяется, шаги тика лидера:

1. **Доводка перед снятием**: если sink подключён и выгрузка отстаёт
   (статус-ключ `state=FAILED`, либо ключа нет вовсе при включённой опции,
   либо новейший локальный файл тома снят позже `last_uploaded_unix` —
   возможный невыгруженный слепок) —
   re-export **новейшего локального** файла тома `snapshot-*.db`
   (перечитать байты; выгрузка тем же конвейером §3.6 — успешный проход
   продвинет `last_uploaded_unix` и закроет отставание).
   Достаточно новейшего: промежуточные невыгруженные слепки — нижние ревизии
   того же ряда, восстановление интересует только последний (осознанное
   упрощение; локальная ретеншн 10 файлов уже хранит глубже).
   Инвариант детекта: каждый успешный проход sink'а (upload — плановый,
   внеочередной или доводкой, §3.6) продвигает `last_uploaded_unix` к метке
   обработанного слепка, поэтому «отстаёт» всегда означает «есть слепок
   новее подтверждённого покрытия», а не «давно не было put-запроса».
2. **Снятие** — прежний `TakeAsync` (экспорт — внутри, §3.4).
3. **Сон**: выгрузка здорова (`state=OK`, не отстаёт) — `SnapshotIntervalMin`
   как раньше; отстаёт/FAILED — `RetryIntervalSec` (тики дёшевы: чтение
   ключа + возможный put; RPO-окно транзиента закрывается минутами, а не
   6 часами). Деградация на `RetryIntervalSec` — следствие реального
   отставания: исправный контур выгружает каждый плановый слепок и продвигает
   покрытие — каденс остаётся `SnapshotIntervalMin` (AC2).

Takeover: без изменений — клэйм/статус/объекты уже переживают смену лидера.

### 3.6. PgWorker.Backups: `EtcdSnapshotSink` + расширение `IBackupS3`

- **`IBackupS3`** — один новый метод: `Task<Result> PutObjectAsync(string key, byte[] data, string? sha256, CancellationToken ct)` — put с SHA256-проверкой целостности транспорта (AWSSDK `ChecksumSHA256`); list/delete уже есть (`ListPrefixAsync`/`DeleteKeysAsync`).
- **`EtcdSnapshotSink`** (`src/PgWorker.Backups/EtcdExport/EtcdSnapshotSink.cs`, реализует `ISnapshotSink`) — путь ОДИН, без сравнения с прошлым состоянием: put `etcd/<name>.db` (серверная SHA256-проверка транспортом) → put `etcd/<name>.meta.json` → ретенция (§3.2, чистая функция отбора) → put статус-ключа `OK` с семантикой покрытия: `last_uploaded_unix` = метка ПОКРЫВАЕМОГО СЛЕПКА (`taken` из имени файла; нераспознанное имя — now), не now — фактическое время заливки фиксируется только в `meta.uploaded_unix`. Любая неудача — put статус-ключа `FAILED` + `error` (поля последнего успеха сохраняются) и `Result.Failed` (транзиент — доводка §3.5). Все шаги идемпотентны (put поверх; повтор после обрыва безопасен). Внутренний таймаут шага — `TimeoutSec`.
  **Дедуп по sha256 целого слепка НЕ применяется** (§2.7): сравнение
  `sha == last_sha256` до put отвергнуто ревью к.4 — статус-ключ пишется в
  том же etcd, из которого снят слепок, и его запись делает следующий слепок
  байт-иным всегда (самореферентность: дедуп-условие недостижимо после
  первого цикла); `last_sha256` в статус-ключе остаётся для наблюдаемости и
  в решении о put не участвует. Реализация не должна содержать
  дедуп-ветви — каждый снятый слепок уезжает новой парой (AC2).
- **Ретенционный отбор** — чистая функция `EtcdExportRetention.Select stale(list of S3ObjectInfo, retentionObjects)` (юниты: пары+одиночные meta, сортировка, guard ≥1).
- **Статус-JSON** — чистые функции сериализации/парсера (юниты; парсер панели толерантен к отсутствующим полям).

### 3.7. Панель (канон adminpanel/02 §2.3.1 + 03 §4)

- **Парсер**: чтение `/pgworker/etcd-snapshots` → `EtcdSnapshotExportInfo`
  (state/enabled/last_uploaded_unix/last_object/last_sha256/size/interval_min/error)
  в модель снапшота панели; битый JSON — parseError-запись, правила молчат
  (паттерн толерантного читателя); ключа нет — «выгрузка не включена».
- **Алерт `etcd-snapshot-export-failed`** (critical): `enabled=true` и
  `state=FAILED` — текст `error`; Hint «выгрузка снапшотов etcd в S3
  провалилась — контроль-плейн не защищён от потери хоста», Remedy —
  runbook-раздел (docs/runbook.md §t08: проверка S3-доступности/кредов).
- **Алерт `etcd-snapshot-export-stale`** (warning): `enabled=true`,
  `last_uploaded_unix` отсутствует или старше `2×interval_min` (поле из
  ключа; дефолт панели 360 при отсутствии поля) — «выгрузка молчит»
  (обе инстанции воркера лежат / вечный транзиент / etcd-лидерство снапшотов
  не исполняется). Порог честен благодаря семантике «покрытия» (§3.1):
  поле двигается каждым выгруженным слепком — живой контур с работающей
  выгрузкой под порог не попадает. `enabled=false`/ключа нет — оба правила
  молчат (образец `backup-full-stale`: выключенная подсистема не алертит).
- **UI**: карточка «etcd-снапшоты» в грани «Хранилище бэкапов» (последняя
  выгрузка: время/возраст, sha256-префикс, размер, статус OK/FAILED, ошибка);
  read-only, мутаций из панели нет (конфиг — env воркера).

### 3.8. Канон восстановления из выгрузки (runbook + arch/09 §4)

Раздел `docs/runbook.md` «Восстановление etcd из S3-выгрузки (t08)» —
операторский путь потери etcd/хоста:

1. **Диагностика**: подтвердить, что выгрузки есть — list `s3://<bucket>/etcd/`
   (mc/AWSSDK), выбрать новейший `snapshot-<id>.db` + его `.meta.json`.
2. **Проверка целостности ДО восстановления** (обязательный шаг): сверить
   sha256 скачанного файла с `.meta.json`; `etcdctl snapshot status <file>`
   (проверяет hash и структуру слепка) — не прошёл ⇒ взять предыдущий
   (ретенция хранит N последних), файл с битым хешем не разворачивать.
3. **Свежий etcd**: поднять контейнер(ы) etcd с чистым data-dir
   (`INITIAL_CLUSTER_STATE=new` — arch/04 §5; прод-3-ноды: сначала
   single-member, остальные — `member add` после старта, arch/04).
4. **Restore**: остановить etcd, `etcdctl snapshot restore <file> --data-dir=<data-dir>`
   (restore — офлайн-операция над слепком), стартовать etcd на
   восстановленном data-dir.
5. **Контроль**: `etcdctl endpoint health`; воркеры/панель переподключаются
   сами (poll-тик; клэймы переснимутся lease-механикой — R7 arch/14: journal
   мог откатиться к точке слепка, процессы идемпотентны и доводят фазы);
   панель видит кластеры, healthz воркеров зелёные.
6. **Границы**: слепок = точка его снятия (RPO = точка последнего изменения
   минус транзиент-окно); локальные тома снапшотов (если пережили) —
   альтернативный источник того же формата; WAL-данные PG-шардов живут в S3
   бэкапов независимо (arch/19) — восстановление etcd их не касается.

arch/09 §4 дополняется: источник восстановления — S3-выгрузка t08 (ссылка на
runbook-раздел и layout `etcd/`), локальный файл тома — fallback.

## 6. Критерии приёмки

- **AC1 (экспорт каждого слепка)**: включённая опция: плановый слепок и
  внеочередной (точка изменения процесса) появляются в S3 парой
  `etcd/snapshot-<id>.db` + `.meta.json` с верным sha256/размером/ревизией;
  `taken_unix` ≤ `uploaded_unix` (интеграция + E2E).
- **AC2 (каждый слепок уезжает, каденс не срывается)**: повторный TakeAsync
  (в т.ч. когда операторских изменений в etcd не было) выгружается как
  НОВАЯ пара db+meta — дедупа нет (интеграция: объектов +2, локальные файлы
  растут; на живом etcd байты слепков различны — статус-ключ и MVCC-ревизии),
  статус-ключ остаётся `state=OK` и `last_uploaded_unix` продвигается к метке
  нового слепка, отставания (IsBehind) нет — сон лидера остаётся
  `SnapshotIntervalMin` (не деградирует на `RetryIntervalSec`), панельный
  stale-алерт на живом контуре молчит (интеграция + панельный юнит); рост
  объёма S3 ограничен ретенцией (AC4).
- **AC3 (транзиент S3 не роняет снятие и догоняется)**: S3 недоступен в
  момент TakeAsync — локальный файл записан, `TakeAsync` успешен, ключ
  `FAILED`+`error`; S3 ожил — доводка тика выгружает новейший локальный
  слепок, ключ `OK`; сон лидера при отставании — `RetryIntervalSec`
  (интеграции).
- **AC4 (ретенция S3 + guard)**: после выгрузок сверх `RetentionObjects`
  старейшие пары удалены, остаётся ровно N пар, ≥1 полная пара — всегда;
  одиночный `.meta.json` без `.db` сносится (юниты + интеграция).
- **AC5 (разворачиваемость выгрузки)**: скачанный из S3 `.db` проходит
  `etcdctl snapshot status` на реальном etcd-контейнере (hash/integrity OK);
  битый (порченный байт) — статус-проверка провалена (интеграция + E2E) —
  runbook-шаг «проверка до восстановления» доказан.
- **AC6 (статус-ключ + takeover)**: формат ключа §3.1 (enabled/state/факты/
  interval_min/error; `last_uploaded_unix` — семантика «покрытия»); смена
  лидера снапшотов (второй инстанс) продолжает выгрузку без потери объектов;
  статус пишет инстанс-исполнитель (интеграция).
- **AC7 (панель)**: `state=FAILED` ⇒ critical-алерт с `error`; успешная
  выгрузка старше `2×interval_min` при `enabled=true` ⇒ warning-алерт;
  `enabled=false`/ключа нет ⇒ оба молчат; карточка «etcd-снапшоты» в грани
  «Хранилище бэкапов» показывает последнюю выгрузку (панельные юниты).
- **AC8 (изоляция префикса)**: объекты `etcd/*` не попадают в реестр сирот
  (`GroupPrefixes`-гвард, юнит) и не удаляются ретенцией t06/sweeper t07
  (пути адресны); входят в `used_bytes` ключа storage (юнит/интеграция).
- **AC9 (канон восстановления)**: runbook-раздел docs/runbook.md — полный
  путь (list → sha256+snapshot status → свежий etcd → restore → health →
  R7-оговорка), arch/09 §4 ссылается на него; arch-правки §3.9 (формулировки
  без дедупа, семантика «покрытия» в arch/14/arch/19-редакциях) смержены до
  кода (arch-first, ревью plan↔spec).
- **AC10 (нулевое влияние при выключенной опции + fail-fast)**:
  `Enabled=false` — поведение воркера неизменно (sink null, ключ не пишется,
  панель молчит); `Enabled=true` с пустыми S3-полями / `RetentionObjects<1` /
