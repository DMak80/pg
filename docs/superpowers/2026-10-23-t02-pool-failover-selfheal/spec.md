# t02-pool-failover-selfheal — spec

Пункт роадмапа: `arch/roadmap/bugs.md`, тег `t02-pool-failover-selfheal`.
Worktree: `feat-t02-pool-failover-selfheal`.

## 1. Цель

E2E-сценарий `PgWorker.IntegrationTests.E2e.PoolFailoverExhaustionScenarios.Pool_FailoverList_And_Exhaustion_SelfHeal`
(AC4: перебор списка записи + исчерпание с маркером + самозаживление) стабильно
сходится: после исчерпания write-списка пула (DEGRADED + маркер
`s3-pool-exhausted`) и подъёма ноды воркер возвращает wal-статус шарда в ACTIVE
в бюджете гейта теста. Одновременно устраняются две найденные в артефактах того
же прогона патологии: вечный цикл пересъёмов полных бэкапов и медленная реакция
контроля на исцеление.

## 2. Диагноз (по артефактам прогона run 98792608d19c4b2896411e73bcc5c8a0)

Артефакты: `$TMPDIR/pgw-e2e-artifacts-6adb2309774347f699932468c20e45c8/`
(63 МБ; docker-логи 13 контейнеров, timing, snapshots).

### 2.1 Дефект A — блокер теста: залипающий exhaustion-маркер

Хронология прогона (логи воркера `pgw-ew-pac4b` и мастер-агента
`pgw-backup-wal-…-shard1-shard1a`):

- 06:13:32 — Act B: стоп node1 (write-список мастера после смены policy —
  только node1);
- 06:14:17–18 — воркер пересоздал агентов по policy-drift (механика t36
  работает);
- 06:14:53 — мастер-агент стартовал стрим, put падает: приёмник печатает
  `{"pool_exhausted":true}` раз в 5 c (24 строки, 06:14:53–06:16:48);
- 06:16:37 — контроль: `Active→Degraded; error=s3-pool-exhausted…` — тестовый
  гейт DEGRADED+маркер прошёл;
- 06:16:37 — `docker start` node1; **06:16:53 — приёмник ВОССТАНОВИЛСЯ**
  (heartbeat `0/8000000`, доставка сегментов 8..24, к 06:21:37 — heartbeat
  `0/25000000`); sync-агент (shard1b) доставлял сегменты на node2 весь прогон —
  union-хвост рос непрерывно;
- 06:16:40–06:21:38 — контроль shard1 так и не вернул Active: последний
  переход — `Degraded→Degraded` (06:16:40), далее запись не менялась; тест
  упал по 300-с бюджету гейта `healed`.

Причина — код `WalStreamProcess.ControlDueAsync`
(`src/PgWorker.Backups/WalStreamProcess.cs`, t36-блоки):
детект исчерпания — подстрочный поиск `"pool_exhausted"` в хвосте
(`AgentLogTail = 200` строк) docker-лога мастер-агента — БЕЗ учёта
актуальности. Маркер живёт в docker-логе контейнера неограниченно долго;
после восстановления приёмника старые строки остаются в хвосте, и каждый
контрольный проход, где цепочка/lag/тишина дают Active, снова переписывает
его в DEGRADED с маркером (блок «state == Active → искать pool_exhausted →
Degraded»), а блок «переход в Degraded → добавить префикс-маркер» усиливает
эффект. Self-heal невозможен, пока 200+ СВЕЖИХ строк не вымоют последний
маркер из хвоста (в прогоне всего 124 строки за 7 минут — никогда). Это
нарушение канона arch/19 §3: «DEGRADED — только transient-деградации …
ретраи тиками» — transient-деградация обязана заживать.

### 2.2 Дефект B — вечный цикл пересъёмов полных

С 06:16:40 до конца прогона (логи воркера: `full … started` каждые 10–20 c,
последний — 06:21:31) воркер бесконечно переснимает полные бэкапы шарда:

- `docker/backup/entrypoint.sh`: `pg_basebackup … --checkpoint=spread`.
  Spread берёт последний завершённый checkpoint/restartpoint источника
  (реплики): `wal_start_segment` из `backup_label` = сегмент 2 (позиция
  provisioning'а), при том что фактическая позиция кластера — сегмент 24;
- набор `-X stream` начинается с фактического старта бэкапа (в прогоне —
  сегмент B у последнего полного, 3–7 у первого), сегменты
  [wal_start .. первый сегмент набора) в полном НЕТ; дублирование в `wal/`
  (entrypoint, строки 76–83) кладёт только сегменты набора — wal_start-сегмент
  в `wal/` не появляется;
- verify полного (arch/19 §5 п.2, канон: «непрерывность от wal_start_segment до
  точки бэкапа») честно даёт `WAL chain gap: expected …0002, found …0003`
  (виден и в drill: 06:16:38) → `verify.state=FAILED` → валидного полного нет
  → `BackupPlanner.IsDue` → пересъём → новый полный с тем же старым
  checkpoint → та же дыра → ∞.
  Шторм `pg_basebackup` каждые 10–20 c + отсутствие валидного полного
  (restore/PITR такого полного невозможен: backup_label требует старта с
  сегмента 2, которого нигде нет) — патология и для тестового контура, и для
  прода.

### 2.3 Дефект C — медленная реакция контроля на исцеление

Реакция на exhaustion заняла ~1м44с (маркер с 06:14:53, переход 06:16:37):
контроль ходит по расписанию `Wal:VerifyIntervalSec` ВНУТРИ тиков клэйм-цикла,
а тик при мёртвой ноде пула длится минуты (S3-вызовы перебирают недоступную
ноду, breaker-окно 45 c, agent-create поллинг). Для BROKEN канон уже требует
контроль КАЖДЫЙ тик («скорость заживления», arch/19 §3) — exhaustion-DEGRADED
того же класса (заживление подъёмом ноды), но остаётся на общем расписании:
первый контрольный проход после подъёма ноды может отстоять от него на
минуты, съедая бюджет self-heal.

## 3. Принципы

- Arch-first: правки канона `arch/19-backups.md` — ДО кода; код зеркалит
  канон (источник истины один).
- Инвариант RPO не трогаем: подтверждение слота только после успешного put;
  семантика приёмника (маркеры stdout) не меняется.
- Контракт etcd `/pgworker/backups/<C>/<X>/wal` не меняется (поле `error`
  как было; панель/алерты — без правок).
- Максимальная надёжность: маркер снимается ФАКТОМ успешной доставки, а не
  таймером/порогом — нет ручек, нет рассинхрона часов, нет «залипания от
  нагрузки логов».
- Решения production ready; без enterprise-излишеств.

## 4. Структура/компоненты (что меняем)

### 4.1 arch/19 §3 (Online-WAL) — уточнение канона (ПЕРВОЙ)

В абзац про исчерпание write-списка (маркер `s3-pool-exhausted`) добавить
механику актуальности маркера и скорость заживления, в терминах канона:

- маркер актуален, пока в хвосте лога мастер-агента последняя строка
  `pool_exhausted` НОВЕЕ последнего `heartbeat` (heartbeat — единственный
  знак успешной доставки: подтверждение слота после успешного put);
- успешная доставка после исчерпания (heartbeat позже последнего маркера)
  снимает маркер: статус пересчитывается общим порядком (цепочка/lag/тишина),
  `error` очищается;
- exhaustion-DEGRADED (DEGRADED с маркером в `error`) — контроль КАЖДЫЙ тик,
  как BROKEN (скорость заживления; union-листинг — один класс вызовов).

### 4.2 arch/19 §2 (полные) — правка канона (ПЕРВОЙ)

Строка «Инструмент»: `--checkpoint=spread` → `--checkpoint=fast` с кратким
обоснованием: spread берёт давний checkpoint источника, `wal_start_segment`
оказывается ниже первого сегмента набора `-X stream`, сегменты
[wal_start .. набор) не дублируются в `wal/` → verify-полнота от wal_start —
вечный FAILED → бесконечные пересъёмы без валидного полного; fast делает
checkpoint на момент старта — wal_start-сегмент входит в набор и дублируется,
verify-цепь сходится.

### 4.3 Код: `src/PgWorker.Backups/WalStreamProcess.cs`

1. Новый `internal static bool`-детектор (чистая функция, имя
   `IsPoolExhaustionActive(string logTail)`, рядом с `ParseTliJumpMarker`):
   построчный разбор хвоста лога; true ⇔ найдена строка `pool_exhausted` и
   ПОСЛЕДНЯЯ такая строка стоит ПОСЛЕДНЕЙ строки `heartbeat`. Нет маркера →
   false. Посторонние строки (stderr, фазы starting/streaming/delivering,
   result-JSON) не матчатся; delivering успехом НЕ считается (heartbeat —
   единственное подтверждение).
2. Оба t36-блока `ControlDueAsync`: подстрочный `Contains("pool_exhausted")`
   заменить на детектор (блок `state == Active` → Degraded с маркером; блок
   префикс-маркера на переходе в Degraded). Чтение лога агента — ОДИН
   docker-вызов за контрольный проход (не два): прочитать при первом
   необходимости, переиспользовать во втором блоке.
3. Расписание контроля: условие пропуска «не время» действует только для
   НЕ-BROKEN и НЕ-exhaustion-DEGRADED (exhaustion-DEGRADED — DEGRADED-ключ,
   чей `error` содержит `S3PoolMarkers.Exhausted`) — симметрично существующему
   правилу BROKEN.

### 4.4 Код: `docker/backup/entrypoint.sh`

`--checkpoint=spread` → `--checkpoint=fast` (строка 24). Оба Dockerfile
(`PgWorker.Backup.Dockerfile`, `PgWorker.Backup.E2E.Dockerfile`) используют
этот один скрипт — больше нигде не менять.

### 4.5 Тесты

- Юнит (файл `src/tests/PgWorker.IntegrationTests/Backups/WalStreamProcessTests.cs`,
  паттерн фейкового драйвера; комментарии AAA):
  - детектор: `pool_exhausted` без heartbeat после → активен; heartbeat
    после последнего `pool_exhausted` → снят; маркера нет → не активен;
    `delivering` между маркером и heartbeat не снимает; посторонние строки
    игнорируются;
  - контроль: exhausted-агент (фейковый лог с маркером) → DEGRADED с маркером;
    после появления heartbeat в логе того же агента → контроль возвращает
    ACTIVE с очищенным `error` (self-heal в один контрольный проход);
  - расписание: exhaustion-DEGRADED-ключ + `VerifyIntervalSec=3600` →
    контроль выполняется тем же тиком (образец
    `VerifyAtBrokenEveryTickHealsInOneTick`);
  - checkpoint-флаг entrypoint — не юнитится (скрипт); покрытие — E2E.
- E2E: существующий `Pool_FailoverList_And_Exhaustion_SelfHeal` — без правок
  сценария; гейт `healed` и есть критерий. Остальные AC-серии пула
  (AC1–AC8) — регресс.

## 6. Ограничения

- НЕ менять: формат stdout-маркеров приёмника (`WalReceiverMarkers`),
  контракт wal-ключа etcd, механику breaker/перебора `PoolBackupS3`,
  инвариант подтверждения-по-доставке, тестовый сценарий AC4.
- `AgentLogTail = 200` остаётся (окно видимости для tli_jump-маркера не
  трогаем); позиционный детектор от размера хвоста не зависит корректностью —
  лишь чувствительностью к «маркер новее heartbeat».
- Никаких таймеров/порогов свежести маркера (рассинхрон часов, ручки) —
  только позиционное сравнение строк.
- Правила E2E: сборка и запуск — двумя ОТДЕЛЬНЫМИ командами; тесты — с
  `--no-build` и env-префиксом при команде; перед сериями —
  `dotnet run --project src/tests/PgWorker.E2ePrepare -c Release`;
  динамические порты; зачистка после КАЖДОЙ серии.
