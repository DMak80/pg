# t28-tli-switch-restore-e2e — E2E восстанавливаемости через точку TLI-переключения

Спецификация фазы 1 (dev-flow). Канон — [`arch/19-backups.md`](../../../arch/19-backups.md)
(§3 online-WAL, §3.5 restore/PITR, §10 риск смешанного сегмента); промис задачи —
та же строка риска §10 и пункт `t28-tli-switch-restore-e2e` в
[`arch/roadmap/reliability.md`](../../../arch/roadmap/reliability.md)
(зависимость ← t27 слита: собственный WAL-приёмник с двойной архивацией,
restore-механика pristine-наборов). Задача чисто тестовая: новых продуктовых
компонентов НЕТ — один docker-E2E контур с двумя restore-заявками + правки
канона/roadmap мерж-гейтом.

## 1. Контекст и цель

### 1.1 Что обещано и чего не хватает

Канон arch/19 §10 (риск «смешанный сегмент точки failover-переключения»):
failover открывает новую timeline ВНУТРИ текущего 16 МиБ-сегмента —
sync-реплика, промоутнутая на позиции replay, уже приняла от мастера хвост
сегмента S (байты TLI1), дописывает в него END_OF_RECOVERY-запись и новые
записи TLI2. Приёмник (t27), стримя с хвоста S3 (конец сегмента S−1), получает
от нового мастера сегмент S ЦЕЛИКОМ — объект wal/ с сегментом S несёт в
префиксе байты TLI1, а в хвосте — TLI2; TLI части имени объекта приёмник берёт
из long page header на границе сегмента (`SegmentAssembler.Close`) — границу
S открывал мастер, поэтому смешанный объект архивируется под именем TLI
родителя. Восстанавливаемость через такую точку опирается на
replay-континуальность postgres (restore-накат читает END_OF_RECOVERY в том
же сегменте) — и до сих пор НЕ доказана end-to-end: закрытые тесты покрывают
соседние, но не этот путь:

- `WalStream_Promote_TliHistory_ChainGlued` (t27 AC5) — склейка `.history` и
  непрерывность `WalChain.CheckWithRestart` ПОСЛЕ промоута; restore НЕ делается;
- `Restore_TargetTime_PitrRollback` (t05) — PITR на цель, но БЕЗ смены
  таймлайна: вся цепочка восстановления живёт на TLI1;
- `Restore_Latest_RebuildsDestroyedShard` (t05) — restore до конца цепочки,
  тоже без TLI-границы в диапазоне восстановления.

### 1.2 Цель

E2E-контур, доказывающий ЗАМКНУТЫЙ цикл восстановимости через точку
TLI-переключения (буква roadmap) в ОБЕИХ режимах цели restore (решение
user-review): provisioned-кластер → контрольные данные → полный бэкап на
TLI1 → WAL-нагрузка → `docker stop` мастера (Patroni failover, promote
sync-реплики → TLI ≥ 2) → контрольные данные на новом TLI → **две
restore-заявки на ОДНОЙ исходной WAL-цепочке и ОДНОМ контуре**:

- **(a) latest** — полный хвост через точку переключения: восстановлены ВСЕ
  строки, включая записанные после цели PITR (after-cut);
- **(b) PITR `target_time=T_cut`** — остановка в целевой точке ПОСЛЕ
  переключения: строки до T_cut (обеих таймлайнов) восстановлены, after-cut
  отсутствуют.

Обе заявки ссылаются на ОДИН исходный полный (`backup_id` задан явно) —
разные итоги на одной цепочке и есть демонстрация PITR через TLI-границу.

Уникальное доказательство контура (чего нет в закрытых тестах):

1. **Факт смешанности** — точка переключения (switchWALLSN из `.history`)
   лежит ВНУТРИ сегмента (не на границе 16 МиБ), сегмент доставлен в wal/
   ровно ОДНИМ объектом под именем TLI родителя, и побайтово: page-заголовки
   объекта по разные стороны switchWALLSN показывают TLI1/TLI2 (строгий
   ассерт + побайтовое подтверждение — решения user-review);
2. **Накат через точку** в обоих режимах — и хвост TLI1 (данные мастера
   после полного бэкапа до failover), и данные TLI2 (после promote) живут в
   восстановимом диапазоне через END_OF_RECOVERY смешанного сегмента.

## 2. Принципы

- **arch-first**: arch/19 — источник истины; правка формулировки риска §10
  (сценарий теперь существует) — частью мерж-коммита задачи (§7). Код меняет
  только тестовое дерево `src/tests/PgWorker.IntegrationTests`.
- **Каноны E2E обязательны**: [`docs/e2e-isolation.md`](../../e2e-isolation.md)
  (guid-окружение, own-only чистка, teardown при любом исходе + ассерт
  чистоты, динамические порты) и [`docs/e2e-launch.md`](../../e2e-launch.md)
  (телеметрия: `[PHASE]`-строки, сбор docker-логов при фазе > 60 с, `MarkFailed`
  → teardown останавливает не удаляя, без перезапусков упавших).
- **Граница изоляции — сценарный класс, окружение ОДНО на класс** (канон
  e2e-isolation §1: класс — минимальная граница; методы класса
  кооперируются на общем контуре): подготовка (окружение, failover, данные,
  гейт смешанности) выполняется ОДИН раз в класс-фикстуре, оба Fact'а
  ставят restore-заявки на готовый контур — без второго docker-контура и
  второго failover (решение user-review: экономия контура при покрытии обоих
  режимов).
- **Порядок заявок детерминирован: latest → target_time** (инвариант §3.3):
  после target_time-restore новый TLI-поток пишет с позиций T_cut (ниже
  after-cut сегментов TLI2) и делает latest-валидацию по исходной цепочке
  невозможной; обратный порядок валиден.
- **Строгость + побайтовость доказательства смешанности** (решение
  user-review): единственный объект сегмента S в архиве — под именем TLI
  родителя (приёмник именует по long page header границы сегмента);
  page-заголовки объекта по обе стороны switchWALLSN показывают TLI
  родителя / TLI нового. Точка промоута удерживается в открытом сегменте
  гейтом replica-sync до docker stop (§3.2, шаг 3).
- **Истина доставки — S3**: все гейты доставки (TLI2-хвост, `.history`,
  after-cut сегменты) — поллингом `ListWalAsync` host-клиента, не по etcd-ключу
  и не по состоянию агентов (канон §3 «истина прогресса — S3»).
- **Паттерн репо — независимые файлы сценариев**: новый файл
  `E2eTliSwitchScenarios.cs`; хелперы копируются из образцов
  (`E2eRestoreScenarios`, `E2eBackupScenarios`), не выносятся в общие утилиты.
- **Продуктовый код НЕ трогается**: нужные функции существуют и используются
  как есть (`BackupS3.GetObjectAsync`, `WalHistory.Parse`,
  `WalFileName.FromLsn`, `RestoreOperationState.BackupId`).
- **Бюджеты короткие, падение быстрое**: суммарный контур ~15–20 мин
  (подготовка ~10 мин + две заявки по ~3–5 мин); каждое ожидание — конечным
  бюджетом через `WaitPhaseAsync` с `[PHASE]`-телеметрией.

### 3.1 Файл сценария — `src/tests/PgWorker.IntegrationTests/E2e/E2eTliSwitchScenarios.cs`

- **`E2eTliSwitchScenarios : IClassFixture<TliSwitchContext>`** — два

  target_time вторым — инвариант §3.3): каждый ставит свою restore-заявку и
  ассертит исход; падение — `MarkFailed` + перевыброс.

Воркер контура поднимается `StartHostAsync` с ОБЪЕДИНЁННЫМ бэкап-комплектом
env (сегодня комплект разнесён по образцам: `StartRestoreHostAsync` не задаёт
`Wal:AgentImage`, `StartWalHostAsync` не задаёт `Restore:RecoveryTimeoutSec`
— t28 нужен и полный, и WAL-агент, и restore одновременно):

PgWorker__Backups__S3__Endpoint            = Fx.S3Endpoint
PgWorker__Backups__S3__AdvertisedEndpoint  = Fx.S3Endpoint
PgWorker__Backups__S3__Bucket / AccessKey / SecretKey     (MinIO окружения)
PgWorker__Backups__Job__Image              = E2eEnvironment.JobImage
PgWorker__Backups__Wal__AgentImage         = E2eEnvironment.WalImage
PgWorker__Backups__Retry__BaseSec=2, MaxSec=4
PgWorker__Backups__Wal__VerifyIntervalSec=2, StaleSec=600, LagMaxSegments=100000
PgWorker__Backups__Restore__RecoveryTimeoutSec=600
PgWorker__Thresholds__PatroniBootSec=120   (как restore-хост: выборы+rejoin)

Оба S3-поля — ОДНО значение `Fx.S3Endpoint` (`http://host.docker.internal:<порт>`,

`localhost:` внутри контейнера джоба указывает на сам контейнер (MinIO
недостижим → full падает бесконечным ретраем). `AdvertisedEndpoint` тем же
значением достаётся WAL/restore-агентам (`AgentS3Endpoint`); замена
`host.docker.internal:` → `localhost:` — ТОЛЬКО в host-клиентах сценария
(`HostS3Client`): воркер-процесс на хосте резолвит host.docker.internal.

Хелперы-копии из образцов: `WaitPhaseAsync` ([PHASE] + сбор логов > 60 с),
`SeedClusterAsync`, `ProvisionedAsync`, `MasterPgAsync` (резолв primary

тем же host-клиентом и проход page-заголовков — шаг страницы 8192: `xlp_tli`

### 3.2 Шаги контура (TliSwitchContext.InitializeAsync — Arrange/Act-подготовка)

**Шаг 1 — контур.** Окружение (сеть/etcd/MinIO по guid, динамические порты),
сид кластера `tlsw{tag}` (2 шарда, по 2 реплики — как образцы), воркер с
объединённым комплектом §3.1. Ожидание provisioning DONE (≤ 360 с).

**Шаг 2 — полный на TLI1.** На мастере shard1: контрольная таблица
`tli_switch_probe(id int, note text)`; строки `pre` (5 шт. — уйдут в полный);
`SwitchWalsAsync(4)`; ожидание COMPLETED-полного (≤ 300 с) с фиксацией
`OldBackupId`, `WalStartSegment`. Строки `pre-wal` (5 шт. — после точки
полного, должны накатиться TLI1-хвостом через смешанный сегмент); сегменты
закрываются по одному до непрерывности `WalChain.Check` от `wal_start_segment`
и доставки позиции `pre-wal` (паттерн rs-latest против дыры на валидации).
После этого гейта НИ ОДНОГО `pg_switch_wal` до failover — запись мастера
живёт в открытом сегменте S (точка переключения окажется внутри него).

**Шаг 3 — failover.** Резолв текущего мастера (`MasterPgAsync`); гейт
replica-sync (обязателен, бюджет ≤ 60 с): снимок `pg_current_wal_lsn()`
мастера и поллинг `pg_last_wal_replay_lsn()` выжившей sync-реплики до ≥
снятой позиции — отставшая реплика промоутится на позиции закрытого сегмента,
и точка переключения выходит из открытого S (профиль не смешанный). По
готовности → `docker stop pgw-{C}-shard1-{master}` (жёсткая потеря, БЕЗ
switchover — Patroni сам промоутит выжившую sync-реплику; образец AC4 t27).
Ожидание: новый primary (`MasterPgAsync`, узел ≠ остановленному) + его TLI ≥ 2
(`PrimaryTimelineAsync`, ≤ 120 с). Фиксация `Tli2`.

**Шаг 4 — данные на новом TLI.** На новом мастере: строки `post-switch`
(5 шт.); `SwitchWalsAsync(3)`; ожидание доставки по list-S3: объект
`wal/{tli:x8}.history` + ≥ 1 закрытый TLI2-именованный сегмент начиная с
Next(S) (≤ 300 с — агент реплики продолжает от хвоста S3, супервиз пересоздаёт
агентов на новых ролях; repair-контур остановленной ноды НЕ ждём — гвардом
restore владеет заявкой). Фиксация цели: `T_cut = UtcNow` (+ пауза 2 с —
разделение коммитов, rs-time-паттерн).

**Шаг 5 — данные после цели.** Строки `after-cut` (3 шт.);
`SwitchWalsAsync(3)`; ожидание доставки сегмента с after-cut данными
(`WalArchivedAsync` от вычисленной позиции). После-цельные записи ОБЯЗАНЫ
лежать в архиве — иначе их отсутствие в restore тривиально (их нет вовсе).

**Шаг 6 — строгий гейт смешанности.** См. §3.3. По завершении контур готов
к заявкам; упавший шаг — инициализация фикстуры падает (оба Fact'а красные
с ошибкой фикстуры, телеметрия собрана).

### 3.3 Строгий гейт смешанности и порядок заявок (инварианты корректности)

**Гейт смешанности (до заявок, шаг 6):** сценарий скачивает
`wal/{tli2:x8}.history` (host-клиент `GetObjectAsync`) и разбирает
`WalHistory.Parse`; последняя запись файла — сам TLI2: `ParentTli=1`,
`SwitchLsn` (строка «X/Y» → ulong для позиционных сравнений). Имя объекта
сегмента S предопределено приёмником: TLI части имени закрываемого сегмента
берётся из long page header на границе сегмента (`SegmentAssembler.Close`:
pageaddr границы → TLI заголовка), а границу S открывал мастер TLI1 —
смешанный объект архивируется под именем РОДИТЕЛЯ `00000001…S`. Ассерты:

1. `SwitchLsn % WalFileName.SegmentBytes != 0` — точка переключения
   ВНУТРИ сегмента S (случай «на границе» НЕ считается покрытием t28 —
   тогда накат идёт по стыку сегментов, а не через смешанный объект);
2. сегмент S доставлен в wal/ РОВНО ОДИН РАЗ, под именем TLI родителя:
   объект `wal/00000001…S` присутствует в list-S3 и единственен для своего
   log/seg (никаких иных имён сегмента S, в частности `wal/00000002…S`,
   в архиве нет);
3. ПОБАЙТОВОЕ подтверждение смешанности (`SegmentPageTlisAsync`): в объекте
   `00000001…S` страницы с `xlp_pageaddr` СТРОГО ниже SwitchLsn показывают
   `xlp_tli`=1 (включая страницу 0 — источник имени объекта), страницы
   СТРОГО выше — `xlp_tli`=2; страница, содержащая SwitchLsn, — переходная
   (её заголовок создан до переключения), жёстко не ассертится;
4. TLI2-поток продолжается со следующего сегмента: первый TLI2-именованный
   объект = Next(S) (`WalFileName.Next`), объект `.history` доставлен (уже
   скачан); TLI1-именованных объектов выше S нет — профиль S (имя TLI1) →
   Next(S) (имя TLI2) + history-объект — в точности эвристика TLI-перехода
   валидатора restore;
5. `WalChain.Check(wal_start, list)` непрерывен — тем самым валидатором,
   которым restore-заявка пройдёт валидацию.

Провал любого пункта — диагностическое исключение (дамп: history-содержимое,
list wal/, карта pageaddr→tli объекта S, ключи full/wal, Patroni /cluster),
НЕ ретрай: профиль прогона зафиксирован и либо смешанный (доказываем дальше),
либо контур честно красный с точной причиной.

**Порядок заявок: latest → target_time (обязателен, обе с явным
`backup_id=OldBackupId`):**

- **latest первым**: валидация идёт по чистому list-S3 (исходная цепочка
  TLI1+TLI2 без пост-restore артефактов). После COMPLETED шард восстановлен
  к концу TLI2 (replay до границы последнего сегмента — restore_command
  отдаёт только целые закрытые сегменты), promote открывает TLI3 с границы:
  первый TLI3-сегмент = Next(last TLI2) — эвристика `WalChain.Check` для
  перехода TLI2→TLI3 (при наличии `wal/00000003.history`, который грузит
  приёмник нового потока) валидна. Планировщик переснимает полный (wal-ключ
  удалён по COMPLETED), приёмник пишет TLI3-хвост ВЫШЕ конца TLI2 —
  исходная цепочка не искажается.
- **target_time вторым**: валидация от `wal_start` СТАРОГО полного по list
  с TLI3-хвостом выше конца TLI2 проходит (переход легитимен, см. выше);
  recovery останавливается на T_cut задолго до TLI3-хвоста. Явный
  `backup_id` обязателен — иначе валидация возьмёт НОВЕЙШИЙ COMPLETED
  (TLI3-полный после первой заявки), и восстановление не пересечёт точку
  переключения.
- Обратный порядок НЕвыполним: после target_time-restore TLI3-поток пишет с
  позиций T_cut (НИЖЕ after-cut сегментов TLI2) — первый TLI3-сегмент не
  совпадает с Next(last TLI2), эвристика даёт ложную дыру, latest-заявка
  валидацию не проходит.

### 3.4 Fact 1 — `Restore_LatestThroughTliSwitch_PicksUpWholeTail` (режим a)

Заявка `RestoreWithRetryAsync(target: "latest", backup_id: OldBackupId)`
(прямой PUT PLANNED-ключа — принятое отступление образцов: API-путь покрыт
`RestoreApiTests`; демонтаж/джоб/rejoin выполняет RestoreProcess воркера).
Ассерты:

1. **Статус**: COMPLETED, `restored_to_lsn` непуст.
2. **Полный хвост через точку** (гейт мастера t10 `SELECT 1` + ретраи чтения —
   переходное окно рестарта postmaster, rs-паттерны):
   `tli_switch_probe`: **18 строк** = 5 `pre` (полный) + 5 `pre-wal`
   (TLI1-хвост в смешанном сегменте) + 5 `post-switch` (TLI2 после
   END_OF_RECOVERY) + **3 `after-cut`** (конец цепочки) — восстановлено ВСЁ,
   включая хвост за целью PITR.
3. **Контур**: ноды шарда RUNNING, dsn-ключ не изменился.
4. **Инвариант §3.5 после restore**: wal-ключ сброшен и заведён заново
   (ACTIVE), появился новый COMPLETED-полный ≠ OldBackupId, wal-агент
   running (≤ 300 с — rs-latest-паттерн AC4).
5. Фиксация исхода в контексте: успех/падение (гейт Fact 2, §3.6).

### 3.5 Fact 2 — `Restore_TargetTimeThroughTliSwitch_StopsAtGoal` (режим b)

Гейт: Fact 1 упал → `Assert.skip` с отсылкой к телеметрии Fact 1 (повторная
заявка на сломанном контуре — каскадный красный без новой информации;
диагностику даёт телеметрия первой заявки).

Заявка `RestoreWithRetryAsync(target: "time:{TCut:yyyy-MM-ddTHH:mm:ssZ}",
backup_id: OldBackupId)` — по СТАРОМУ полному через ту же точку переключения.
Ассерты:

1. **Статус**: COMPLETED, `restored_to_lsn` непуст (LSN ≤ конца after-cut:
   цель раньше конца цепочки).
2. **Остановка в цели**: `tli_switch_probe`: **15 строк** = 5 `pre` +
   5 `pre-wal` + 5 `post-switch`; **`after-cut` = 0** — коммиты после T_cut
   не накатились. Вместе с Fact 1 (18 строк на той же цепочке) — прямая
   демонстрация PITR: разные цели на одном WAL-архиве через TLI-границу.
3. **Контур**: ноды RUNNING, dsn жив (rejoin после второй заявки — тот же
   RestoreProcess).

### 3.6 Телеметрия и падение

Все ожидания (в фикстуре и Fact'ах) — через `WaitPhaseAsync` (`[PHASE] …:
ok=…, elapsed=…s`; > 60 с — немедленный `CollectDiagnosticsAsync`). Любое
исключение — `MarkFailed()` до teardown: контейнеры останавливаются, не
удаляются, разбор по артефактам `/tmp/pgw-e2e-artifacts-<guid>/` (+
`README-cleanup.txt`); перезапуск упавшего сценария без полного анализа
логов запрещён (канон e2e-launch §4). Падение Fact 1 → Fact 2 skip (§3.5);
падение подготовки → оба Fact'а падают ошибкой фикстуры (контур не поднялся).

## 5. Ограничения и границы

- НЕ меняется: продуктовый код (src/PgWorker.*), контракт etcd, S3-layout,
  restore-механика, WalChain/WalHistory/WalFileName; конфигурация воркера
  вне тестового env.
- Ровно два Fact'а на одном контуре класса: третья вариация (независимые
  контуры per-Fact, DR-source-вариация и т.п.) НЕ заводится — закрытые
  тесты t05 покрывают соседние пути restore.
- Окружение на класс (не per-Fact) — прямое прочтение канона изоляции
  («минимальная граница — сценарный класс»); оба Fact'а кооперируются на
  общем контуре, порядок детерминирован orderer'ом.
- Побайтовый разбор смешанного объекта ограничен page-заголовками
  (`xlp_tli`/`xlp_pageaddr`, шаг 8192): полный декодер XLOG-записей
  (record-заголовки, END_OF_RECOVERY-запись) НЕ пишется — заголовков страниц
  достаточно для доказательства байт обеих таймлайнов в одном объекте,
  декодер записей хрупок к деталям формата.
- Repair-контур остановленной мастер-ноды не ждём и не ассертим: поведение
  надзора при failover покрыто AC4 t27; контур заявками restore забирает
  владение шардом (гвард §3.5).
- Контур не запускается параллельно сам с собой на одном docker-хосте сверх
  канона ≤ 3 контуров (`XunitMaxParallelThreads=3`, t24).

## 6. Критерии приёмки

- **AC1 (факт смешанности — строгий + побайтовый)**: до restore-заявок в
  wal/-префиксе шарда: switchWALLSN из `.history` удовлетворяет
  `0 < SwitchLsn mod 16 МиБ` (строго внутри S); сегмент S доставлен РОВНО
  один раз — под именем TLI родителя `wal/00000001…S`, объекта
  `wal/00000002…S` в архиве нет; побайтово: page-заголовки объекта S с
  pageaddr < SwitchLsn показывают TLI=1, с pageaddr > SwitchLsn — TLI=2;
  объект `wal/{tli2:x8}.history` доставлен; первый TLI2-именованный объект =
  Next(S); `WalChain.Check`-цепочка от `wal_start_segment` непрерывна
  (TLI1-именованные до S включительно). Профиль закреплён гейтом replica-sync
  подготовки (replay_lsn реплики ≥ pg_current_wal_lsn мастера до docker
  stop) — точка промоута в открытом сегменте.
- **AC2 (latest — полный хвост через точку)**: restore `latest` c
  `backup_id` = исходный полный → COMPLETED с `restored_to_lsn`;
  восстановленная таблица: 18 строк = 5 pre + 5 pre-wal + 5 post-switch +
  3 after-cut — накат прошёл TLI1-хвост, END_OF_RECOVERY смешанного сегмента
  и весь TLI2-хвост за целью PITR. Ноды RUNNING, dsn не изменился.
  Инвариант §3.5: wal-ключ заведён заново (ACTIVE), новый COMPLETED-полный
  ≠ исходного, wal-агент running.
- **AC3 (PITR — остановка в цели)**: restore `time:T_cut` (T_cut после
  post-switch и до after-cut) с тем же `backup_id` на той же цепочке →
  COMPLETED; таблица: 15 строк (pre + pre-wal + post-switch), `after-cut`
  0 — цель ПОСЛЕ точки переключения соблюдена. Порядок AC2 → AC3
  детерминирован.
- **AC4 (изоляция и телеметрия)**: ОДНО guid-окружение на класс (сеть/etcd/
  MinIO/кластер по тегу), полный teardown при любом исходе с ассертом
  чистоты; все ожидания через `WaitPhaseAsync` с `[PHASE]`-строками; фазы
  > 60 с — сбор логов в артефакты; падение — `MarkFailed` +
  `README-cleanup.txt`; падение Fact 1 → Fact 2 skip; порты только
  динамические, хардкодов-литералов нет.
- **AC5 (мерж-гейт)**: контур зелёный на свежем Release (E2eFixture-сборка);
  кейс-маркер `Scale_AddEmptyShard` зелёный; зачистка серий без остатков
  (контейнеры/сети/тома/ключи — 0 остатков своего guid); тег t28 удалён из
  `arch/roadmap/reliability.md`, строка обновлена в
  `arch/roadmap/reliability-report.md`, формулировка риска §10 в
  `arch/19-backups.md` переписана на «проверяется E2E через точку
  переключения» — всё тем же мерж-коммитом.
