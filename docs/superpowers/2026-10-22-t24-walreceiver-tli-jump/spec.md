# t24-walreceiver-tli-jump — переживание приёмником WAL перехода таймлайна при зазоре S3-хвоста

Спецификация фазы 1 (dev-flow). Канон — [`arch/19-backups.md`](../../../arch/19-backups.md)
§2/§3/§4/§10 (правки канона — часть задачи, arch-first, см. §8); контракт панели —
[`arch/adminpanel/02-etcd-contract.md`](../../../arch/adminpanel/02-etcd-contract.md),
правила — [`arch/adminpanel/03-panels.md`](../../../arch/adminpanel/03-panels.md).
Исходная формулировка — [`arch/roadmap/backup.md`](../../../arch/roadmap/backup.md),
пункт `t24-walreceiver-tli-jump`; эпизодический фейл E2E
`WalStream_Promote_TliHistory_ChainGlued` устраняется этой задачей
(`arch/roadmap/reliability.md`, t29 п.3).

## 1. Контекст и цель

### 1.1 Ошибочная ситуация (сегодня)

После фейловера PG (промоут реплики, сервер на TLI+1) приёмник WAL стартует от
хвоста S3: `START_REPLICATION SLOT <slot> PHYSICAL <lsn>` без TIMELINE.
PostgreSQL-walsender ищет стартовый сегмент под именем ТЕКУЩЕГО таймлайна
сервера: если позиция хвоста ниже точки форка нового таймлайна, сегмент
`<новыйTLI><log><seg>` никогда не существовал (новый таймлайн начинается с
точки форка) — сервер отвечает 58P01 «requested WAL segment … has already
been removed» на КАЖДОЙ попытке. Приёмник циклится starting/retry каждые 5 с
бесконечно: `.history` нового TLI не загружается, WAL-архивация шарда
заморожена до следующего фейловера, само не восстанавливается. Контроль воркера
этого не видит (объектов нет, цепь непрерывна; растёт только lag → DEGRADED
«lag» без причины).

Ключевой факт протокола (проверен по документации PG и API Npgsql 10.0.3,
пакет в решении): сегменты СТАРОГО таймлайна при этом физически лежат в
`pg_wal` оставшейся ноды — их удерживает слот `pgw_bkp_<C>_<X>`
(`restart_lsn` ≤ хвоста S3, потолок `max_slot_wal_keep_size`=16GB). Команда
`START_REPLICATION … PHYSICAL <lsn> TIMELINE <старый>` обязывает сервер отдать
WAL старого таймлайна от `<lsn>` до точки переключения (механика
timeline-following утилиты `pg_receivewal`) — зазор в большинстве случаев
закрывается БЕЗ потери данных. Байты доступны на обеих нодах (двойная
архивация + sync-репликация: WAL подтверждённого изменения физически в
`pg_wal` обеих нод, arch/19 §3).

### 1.2 Цель

1. **Механика переживания 58P01** (двухшаговая, закрывает RPO):
   - **Досыпка**: 58P01 на старте → IDENTIFY_SYSTEM → при TLI сервера выше
     TLI хвоста — стрим старого таймлайна от хвоста до точки переключения
     (CopyDone) → штатное переподключение от выросшего хвоста: зазора нет,
     RPO=0.
   - **Прыжок-fallback**: досыпка невозможна (58P01 и на старом таймлайне —
     сегменты срезаны: слот потерял удержание) → старт от текущей позиции
     сервера на текущем таймлайне; сегменты между хвостом и точкой старта в
     S3 не появятся никогда — осознанный RPO-зазор.
2. **Семантика зазора закреплена в каноне arch/19 §3**: маркер разрыва в
   статусе/журнале, форсированный пересъём полного бэкапа (агенты архивации
   НЕ останавливаются), видимость в verify/drill/restore.
3. **Наблюдаемость RPO-события**: панельный алерт `backup-wal-tli-gap`
   (critical) на время незакрытого зазора.
4. E2E `WalStream_Promote_TliHistory_ChainGlued` — зелёный (устраняется
   этой задачей); детерминированные E2E: t24a (досыпка) и t24b
   (сходимость после индуцированного среза сегментов); ассерты обоих
   кейсов — финальная сходимость системы; ветки механики — юнит-покрытие
   (§3.7, §6 п.15).

### 1.3 Инвариант хранения (проверен и подтверждён пользователем)

S3 — единственный источник истины: сегмент кладётся в S3 немедленно при
закрытии; локально на нодах-источниках удерживается ТОЛЬКО недоставленный
хвост (слот запрещает удаление выше `restart_lsn`, потолок
`max_slot_wal_keep_size`=16GB). Механика досыпки — дострелка недоставленного
хвоста, а не новое хранение. Этот принцип уже канон (arch/19 §3, t27); spec
его фиксирует как основание дизайна.

## 2. Принципы

- **Arch-first**: arch/19 + arch/adminpanel — источник истины; правки канона
  выполняются ДО кода (§8). Код зеркалит канон.
- **Durability только от S3** (AGENTS.md «multi-host»): локальное — кэш;
  инвариант подтверждения-по-доставке (t27) НЕ меняется: подтверждение слота
  по-прежнему ТОЛЬКО после успешного put.
- **Максимально надёжное решение** (AGENTS.base п.9): досыпка устраняет
  потерю в основном сценарии; прыжок — осознанный fallback с фиксацией
  потери; цикл BROKEN↔58P01 исключён дизайном (агенты при зазоре не
  останавливаются).
- **Идемпотентность каждого шага** (arch/17): put по имени детерминирован
  (двойная доставка двух агентов не конфликтует); повтор tli-процедуры
  корректен; маркер gap в etcd — WriteIfChanged.
- **Протокол агента — env + stdout-JSON-маркеры**: агент etcd не знает;
  новые маркеры `tli_backfill`/`tli_jump` — по образцу существующих
  (`pool_exhausted`, `history_missing`); воркер парсирует только свои строки.
- **E2E проверяет сходимость, а не воспроизведение ошибки**: ассерты —
  консистентный итог (доставка завершилась, цепь цела, каталог здоров,
  кластер Active); промежуточные события не ассертируются (§6 п.15).
- transient vs permanent: 58P01 — НЕ permanent (агент продолжает работу);
  выход с кодами 3/4/5/6 — без изменений.

## 3. Структура и компоненты

### 3.1 Приёмник `src/PgWorker.WalReceiver` — tli-процедура при 58P01

**Распознавание 58P01** (сейчас теряется в `ApplicationException`):
`NpgsqlXLogSource.StartReplicationAsync` ловит `PostgresException` с
`SqlState == "58P01"` и возвращает наружу типизированную ошибку-маркер
`WalStartRefused` (новый тип в проекте WalReceiver; текст исходной ошибки
сохраняется для stderr). Матч по SqlState, НЕ по тексту сообщения.

**Расширение контракта `IXLogReplicationSource`** (фейки юнитов — вместе):

```csharp
// Новый метод: идентификация сервера (репликация-протокол IDENTIFY_SYSTEM).
Task<Result<ServerIdentity>> IdentifySystemAsync(CancellationToken ct);
public sealed record ServerIdentity(uint Tli, ulong XLogPos);

// Расширение существующего: явный TIMELINE в START_REPLICATION.
Task<Result> StartReplicationAsync(string slot, ulong startLsn, uint? timeline, CancellationToken ct);
```

Реализация Npgsql: `PhysicalReplicationConnection.IdentifySystem(ct)` →
`ReplicationSystemIdentification { Timeline, XLogPos }` (подтверждено по
XML-докам пакета Npgsql 10.0.3); `StartReplication(slot, lsn, ct, timeline)`
— перегрузка с параметром `timeline` («Streaming starts on timeline tli»).
`IdentifySystemAsync` — по короткоживущему replication-соединению (образец
`ReadTimelineHistoryAsync`: replication-команды обслуживаются сервером до
START_REPLICATION, соединение после failed-старта уже погашено).

**Tli-процедура ядра (`WalReceiverCore.RunAsync`)** — вызывается вместо
обычного retry, когда старт упал с `WalStartRefused`; вход: `tail` (уже
резолвлен), `tailSegment` (имя хвостового сегмента, TLI из его имени):

1. `IDENTIFY_SYSTEM` → `(T, xlogpos)`. Сбой — transient: обычный retry-цикл.
2. `.history` нового TLI: при `T > tli_tail` — `ReadTimelineHistoryAsync(T)`
   → put `wal/<T:x8>.history` (механика put'а истории уже существует; файл
   есть на сервере — T ≥ 2 создан промоутом; провал запроса — маркер
   `history_missing`, fallback-контроль воркера, как сегодня).
3. **Досыпка** (только при `T > tli_tail`): маркер
   `{"phase":"tli_backfill","from_segment":"<хвост>","to_tli":T}` в stdout →
   `StartReplicationAsync(slot, tail, timeline: tli_tail)`. Сервер отдаёт WAL
   старого таймлайна от хвоста до точки переключения; приём идёт штатным
   контуром (assembler → put → confirm — подтверждение слота по доставке
   сохраняется). Поток завершится CopyDone → существующая ветка «поток
   кончился» → переподключение → повторный резолв хвоста (вырос до ≥ точки
   форка) → штатный старт без TIMELINE — успех, зазора НЕТ, склейка
   TLI-перехода по эвристике непрерывности (first ∈ {last, Next(last)}).
   Повторный 58P01 на досыпке (сегментов старого TLI нет — удержание
   потеряно) → шаг 4.
4. **Прыжок** (fallback; также единственный путь при `T == tli_tail` — зазор
   внутри одного таймлайна): стартовая позиция = ГРАНИЦА (начало) сегмента,
   содержащего `xlogpos` (текущий записываемый сегмент сервера существует
   всегда; сборщик доставит его целиком — произвольный старт уже поддержан
   `SegmentAssembler`, головной отброс не срабатывает: старт ровно на
   границе). Маркер
   `{"phase":"tli_jump","from_segment":"<хвост>","from_tli":<tli_tail>,"to_tli":T,"to_segment":"<имя стартового>"}` →
   `StartReplicationAsync(slot, segmentStart(xlogpos), timeline: T)` →
   стрим продолжается штатно.
5. Гонки «сервер промоутнулся снова между IDENTIFY_SYSTEM и START»:
   старт с TIMELINE ниже текущего безопасен (сервер отдаёт исторический
   таймлайн до его конца → цикл повторит процедуру); старт с TIMELINE T на
   сервере T+1 → снова 58P01 → процедура повторяется с новым IDENTIFY_SYSTEM.
   Конвергенция без счётчиков попыток; каждая итерация корректна.

Диагностика — stderr (`tli_procedure: backfill|jump ...`), stdout остаётся
протоколом воркера (образец `open_failed`/`start_failed`).

### 3.2 Контроль воркера `WalStreamProcess` — фиксация зазора

- **Чтение маркера**: на каждом верификационном проходе `ControlDueAsync`
  читает хвост лога мастер-агента (`BackupAgentLogsAsync`; хвост увеличить с
  50 до 200 строк — вымывание однократного маркера `tli_jump`
  streaming-маркерами 1/5 с замедляется) и ищет `"phase":"tli_jump"`.
- **Только TLI-граничный прыжок** (`from_tli != to_tli`): персистентная
  фиксация в ключ `wal`: state `DEGRADED`, `error` =
  `tli-gap: сегменты (from_segment, to_segment] не будут доставлены — приёмник пережил 58P01 tli-переход <from_tli>→<to_tli>; воркер переснимает полный`,
  новое опциональное JSON-поле
  `"gap":{"from":"<seg>","to":"<seg>","tli":<T>}`; journal-фаза
  `wal-tli-gap/<X>`. WriteIfChanged — идемпотентно; маркер в etcd переживает
  рестарты воркера/агентов (не зависит от лога контейнера).
- **Внутри-TLI прыжок** (`from_tli == to_tli`): tli-gap НЕ ставится — это
  обычная дыра цепочки: контроль увидит её сам (`WalChain.Check` → BROKEN →
  существующее лечение пересъёмом, arch/19 §3).
- **Снятие**: при живом `gap`-поле контроль проверяет покрытие — есть
  COMPLETED-полный с `wal_start_segment ≥ gap.to` (CompareOrdinal, как
  breakCovered у BROKEN) → `gap` убирается, `error` пересчитывается штатно
  (lag/тишина), состояние ACTIVE/DEGRADED по общим правилам. Снятие также
  происходит при исчезновении профиля зазора из листинга (ретенция срезала
  нижележащие TLI) — поле `gap` не переживает заживление дольше покрытия.
- **Контроль цепочки не меняется**: `CheckWithRestart` уже считает цепь от
  первого сегмента максимального TLI непрерывной (t05 AC4) — зазор на
  TLI-границе НЕ даёт BROKEN; `chain_start`/ratchet — без изменений.

**Известное ограничение канала (принято)**. Маркер `tli_jump` живёт в логе
контейнера агента, а после фейловера надзор воркера пересоздаёт агентов в
первые секунды: смена ролей источников (мастер/sync) → env-дрейф → recreate,
плюс REBUILD стопнутой ноды завершается пересозданием агентов по его
окончании. Лог контейнера, выполнившего прыжок, стирается пересозданием —
контроль успевает прочитать маркер не всегда (гонка «прыжок → контроль»).
Канал stdout-маркер → контроль НЕ меняется: прод-механика опирается на
периодические перечитывания хвоста и ретраи — метка ставится, если чтение
успело; пропущенная метка — грань наблюдаемости, НЕ корректности:
архивация восстанавливается приёмником независимо от метки (досыпка/прыжок —
внутри агента), а незакрытый RPO-зазор дополнительно вскрывается
валидациями drill/restore (`WalChain` даёт permanent-отказ с границами).
E2E от этого ограничения не зависит и требований на наблюдение метки не
выставляет: кейсы §3.7 ассертируют финальную сходимость, а не маркер
(§6 п.15).

### 3.3 Планировщик полных `BackupProcess` — форсированный пересъём

- Сигнал: `ShardBackups.Wal.Gap != null` И не покрыт (нет COMPLETED-полного
  с `wal_start_segment ≥ gap.to`) → `IsDue(..., force: true)` — по образцу
  `walChainBroken` (расширить параметр; инвариант одного активного
  `HasActive` и бэкофф серии FAILED работают как всегда — шторм исключён).
- Правило покрытия симметрично BROKEN-правилу arch/19 §2: покрывший полный
  ждёт снятия метки контролем; непокрывший (FAILED/ниже границы) — пересъём
  снова.

### 3.4 Модель и контракт etcd

- `WalStreamState` (PgWorker.Etcd/Parsing) += опциональное поле
  `WalGapState? Gap` (`record WalGapState(string From, string To, uint Tli)`).
- `WalStatusWriter` payload += `"gap":{...}` (null → не пишется;
  backwards-compat: парсеры панели читают известные поля, старые ключи без
  `gap` читаются без ошибок — правило канона §4).
- Ключ `wal` — расширенная строка таблицы канона arch/19 §4 (правка §8).

### 3.5 Панель

- Парсер `BackupsParser`: толерантное чтение `gap` (отсутствует/битое —
  null, parseError не пишется); `WalStreamInfo` += `Gap`.
- Новое правило алерта `backup-wal-tli-gap` (critical, образец
  `BackupChainBrokenRule`): поле `gap` живое в wal-ключе шарда живого
  Active-кластера; текст: границы зазора, «данные между from и to
  невосстановимы из бэкапов (RPO-событие), воркер переснимает полный
  бэкап»; Remedy WorkerAuto + указание оператору проверить окно потери;
  снимается снятием поля (заживление полным). DEGRADED без `gap` правилом
  не трогается (lag/тишина — существующие правила).

### 3.6 Verify / drill / restore — семантика зазора (код без изменений)

- **restore** (§3.5): валидация `WalChain.Check` от `wal_start` полного —
  TLI-переход со зазором даёт permanent-отказ с границами дыры: restore от
  полных ниже зазора невозможен до переснятия — честная видимость RPO-окна.
- **drill** (§3.6): та же валидация → FAILED «восстановимость не доказана»
  с границами — дрилл регулярно вскрывает незакрытый зазор оператору.
- **verify** (§5): `CheckRange` по диапазону [wal_start..end] полного —
  зазор вне диапазонов полных ниже него; новый полный (после точки старта)
  проходит зелёным.
- Закрепить формулировки в каноне (§8); код не меняется.

### 3.7 E2E — детерминированные сценарии сходимости

Новый класс в `src/tests/PgWorker.IntegrationTests/E2e/` (по образцу
`E2eWalStreamPromoteScenarios`: E2eEnvironment со своей сетью/etcd/ownS3,
guid-изоляция, полный teardown, ассерт чистоты, телеметрия по
docs/e2e-launch.md). **Ассерты обоих кейсов — ТОЛЬКО финальная сходимость
системы; промежуточные события (факт 58P01, факт прыжка, stdout-маркеры
`tli_jump`/`tli_backfill`, метка `gap` в моменте, timing «прыжок →
контроль») НЕ ассертируются** — они гоночные из-за пересоздания контейнеров
агентов надзором воркера после фейловера (§3.2); stdout-маркеры остаются в
телеметрии прогона как диагностика. Тест проверяет, что система сходится к
консистентному итогу при любом пути (прыжок с зазором + пересъём, досыпка
без зазора, зазор не возник вовсе) — ошибка PG была или нет, не важно.
Несходимость в бюджет — сигнал к новому расследованию (штатный процесс по
канону телеметрии, без перезапуска до анализа).

- **`WalStream_TliBackfill_ClosesGap_NoRpoLoss`** (t24a, главный путь):
  пауза S3 (остановка ownS3-ноды контура) → генерация WAL (`pg_switch_wal`
  ×N — сегменты закрыты, доставки нет, слот держит) → `docker stop` мастера
  → promote реплики (TLI ≥ 2, точка форка выше хвоста) → `pg_switch_wal` на
  новом мастере → возврат S3. Ассерты сходимости: цепочка непрерывна
  (`CheckWithRestart` от chain_start ключа), `.history` нового TLI в S3,
  ключ `ACTIVE`, `gap`-поля нет, BROKEN нет.
- **`WalStream_TliJump_GapMarked_FullRetaken`** (t24b, сходимость после
  индуцированного среза): пауза S3 → записная генерация WAL (INSERT +
  `pg_switch_wal`) → `docker stop` мастера → promote реплики → на новом
  мастере drop слота + записные `pg_switch_wal` суммарно за
  `wal_keep_size`=2048MB (сегменты старого TLI перекручиваются; ensure
  воркера пересоздаст слот уже на высокой позиции) → возврат S3 →
  контрольная INSERT-вставка. Ассерты сходимости (итог, любой путь):
  (1) кластер Active; (2) ключ `wal`: state `ACTIVE` (не BROKEN), без
  живого `gap`-поля (не возник или снят покрытием — незакрытый gap =
  несходимость); (3) цепочка `wal/` в S3 цела/склеена через TLI-границу
  (`CheckWithRestart` непрерывна); (4) каталог бэкапов здоров: существует
  COMPLETED-полный, снятый после индуцирования, с `verify ≠ FAILED`;
  (5) доставка догнала: хвост S3 (конец последнего сегмента цепи) ≥
  сегмента `pg_current_wal_lsn()` контрольной вставки.
- `WalStream_Promote_TliHistory_ChainGlued` — без изменений кода, зелёный
  на Release (устранение — механика §3.1).

Бюджеты фаз — по канону (BrokerBootSec ≤ 100 с, `[PHASE]`-телеметрия фаз
длиннее 60 с, MarkFailed-семантика teardown).

## 5. Ограничения и границы

- НЕ меняются: инвариант подтверждения-по-доставке (t27); layout S3
  (`wal/<segment>`, `wal/<tli>.history`); имя слота; правила
  непрерывности/`CheckWithRestart`/BROKEN/ретенции; механика джобов
  полных/verify/restore/drill; механика restore-промоута (AC4 t05);
  KafkaWorker/ValkeyWorker; env-контракт агента.
- Зазор внутри одного TLI (слот потерял, сегменты срезаны, TLI не менялся) —
  НЕ предмет tli-gap-маркера: обычная дыра → существующий BROKEN-путь.
- Досыпка не даёт гарантий при `max_slot_wal_keep_size`-инвалидации слота —
  это и есть fallback-прыжок; потолок удержания не меняется.
- `.history` для TLI 1 не существует и не запрашивается (T > tli_tail ≥ 1 →
  T ≥ 2).
- Панель НЕ запускает никаких действий по `gap` (действие — воркер:
  пересъём; панель — только алерт).
- E2E-ассерты — только финальная сходимость (§3.7): промежуточные события
  механики (58P01/прыжок/stdout-маркеры/метка `gap` в моменте/timing) в E2E
  не ассертируются — они гоночные (пересоздание агентов надзором — свойство
  среды, §3.2); ветки механики покрываются юнитами.
- Метка `gap` — грань наблюдаемости, не условие корректности: архивация
  восстанавливается приёмником (§3.1) независимо от того, успел ли контроль
  прочитать маркер; незакрытый зазор вскрывается drill/restore-валидацией.

## 6. Принятые решения (закрытые развилки)

| # | Развилка | Решение | Основание |
|---|---|---|---|
| 1 | Механика 58P01: прыжок (буква roadmap) vs досыпка старого TLI | **Досыпка + прыжок-fallback** (§3.1) | Выбор пользователя: байты доступны на оставшейся ноде (sync-репликация, слот держит) — терять их не нужно; RPO=0 в основном сценарии. Roadmap-минимум расширен осознанно |
| 2 | Досыпка vs «старт от доставки второго агента» | Досыпка от ОБЩЕГО хвоста S3 c явным TIMELINE | Хвост S3 общий (max доставки двух агентов); позиция ниже форка недостижима на новом TLI от ЛЮБОЙ позиции без явного TIMELINE — именование протокола, не источник байтов (разобрано с пользователем) |
| 3 | Реакция на зазор при прыжке: BROKEN (стоп агентов) vs марка + форс | **DEGRADED + gap-поле + форсированный пересъём; агенты живут** | Выбор пользователя. Анализ: BROKEN-стоп циклит (агент после заживления стартует от старого хвоста → снова 58P01 → снова BROKEN); стоп замораживает архивацию даром |
| 4 | Канал сигнала о зазоре: маркер агента vs детект по объектам | **stdout-маркер `tli_jump` → контроль персистентно в etcd** | Приёмник — единственный свидетель события; объектный детект неотличим от легитимного restore-промоута (AC4 t05); персистентность — в etcd, не в логе контейнера |
| 5 | Окно видимости маркера в логе | Хвост лога 200 строк (сейчас 50) | Streaming-маркеры 1/5 с вымывают однократный маркер; окно дополнительно обрезается пересозданием контейнера надзором — свойство среды, принято (п.6/п.15) |
| 6 | Пропуск чтения маркера контролем | Принято как свойство канала: после фейловера пересоздание агентов (смена ролей/env-дрейф, REBUILD ноды) стирает лог с маркером до чтения контроля — метка может не встать | Последствия — только наблюдаемость (метка/алерт); корректность архивации не зависит: досыпка/прыжок — внутри приёмника; зазор вскрывают drill/restore-валидации; E2E от метки не зависит (ассерты финальные, п.15). Персистентный S3-канал (маркерный объект) отвергнут пользователем; union логов всех агентов отвергнут — не даёт гарантий (пересоздание стирает и его) |
| 7 | Стартовая позиция прыжка | **Начало сегмента, содержащего xlogpos** (не сам xlogpos) | Сегмент доставится целиком (меньше потери на до 16 МиБ); текущий записываемый сегмент существует всегда; сборщик начинает ровно с границы |
| 8 | `.history` нового TLI при tli-процедуре | Приёмник грузит немедленно при детекте (T > tli_tail), ДО досыпки | Канон §3 «.history загружается обязательно»; переход не будет наблюден в потоке (prevTli инициализируется); fallback-контроль остаётся страховкой |
| 9 | Распознавание 58P01 | `PostgresException.SqlState == "58P01"` (типизированный `WalStartRefused` наружу) | Матч по SqlState, не по тексту; сейчас SqlState теряется в обёртке |
| 10 | Формат gap в ключе wal | Отдельное опциональное JSON-поле `"gap":{from,to,tli}` + текст `tli-gap:` в error | Прецедент маркера-префикса в error (`s3-pool-exhausted`) — для панели/журнала; типизированное поле — для планировщика (не парсить текст); backwards-compat правилом канона |
| 11 | Серьёзность панельного алерта | **Новый `backup-wal-tli-gap`, critical** (снимается автоматически) | Выбор пользователя; RPO-событие состоялось (не «само пройдёт»); образец backup-chain-broken (Remedy WorkerAuto) |
| 12 | Verify/drill/restore при зазоре | Код без изменений; семантика фиксируется в каноне | WalChain.Check/CheckRange уже дают permanent-отказы с границами; verify полных вне диапазона зазора честно зелёный |
| 13 | CheckWithRestart/BROKEN-семантика | Не меняется: TLI-граничный зазор — не BROKEN (t05 AC4); внутри-TLI зазор — обычная дыра → BROKEN | Существующий канон; tli-gap — надстройка видимости, не замена |
| 14 | Коды выхода приёмника | Без новых permanent-кодов; 58P01 — transient-механика внутри агента | Агент продолжает работу; супервиз не участвует |
| 15 | Семантика E2E на механику зазора | **Оба кейса в серии: t24a (досыпка) и t24b (сходимость после индуцированного среза) + зелёный ChainGlued. Ассерты кейсов — ТОЛЬКО финальная сходимость: доставка завершилась и догнала, цепь в S3 цела/склеена через TLI-границу, COMPLETED-полный после индуцирования (каталог здоров), кластер Active, живого `gap`-поля нет. Промежуточные события (58P01, прыжок, stdout-маркер `tli_jump`, метка `gap` в моменте, timing «прыжок → контроль») НЕ ассертируются** | Выбор пользователя. Цель теста — «всё сошлось», а не воспроизведение ошибки: тест проверяет консистентный итог при любом пути (прыжок с зазором + пересъём / досыпка без зазора / зазор не возник) — ошибка PG есть или нет, не важно. Мотивировка отказа от промежуточных ассертов — их гоночная природа: свойство среды (пересоздание агентов надзором после фейловера стирает лог/состояния раньше наблюдения, §3.2). Несходимость в бюджет — сигнал к новому расследованию (штатный процесс). Канал сигнала (stdout-маркер → контроль) не меняется |
| 16 | Индукция среза сегментов в t24b | drop слота на новом мастере + записные `pg_switch_wal` (INSERT-нагрузка) суммарно за `wal_keep_size`=2048MB (128 сегментов) | PG перекручивает сегменты ниже удержания; ensure воркера пересоздаст слот на высокой позиции; записная генерация — 2 ГБ WAL, `[PHASE]`-телеметрия фазы, бюджет по канону |
| 17 | Гонки повторного промоута в tli-процедуре | Без счётчиков; каждая итерация конвергентна (§3.1 п.5) | Идемпотентность; START с историческим TIMELINE безопасен |

## 7. Критерии приёмки

- **AC1 (досыпка — RPO=0)**: E2E t24a
  `WalStream_TliBackfill_ClosesGap_NoRpoLoss`: после индуцированной ситуации
  цепочка непрерывна (`CheckWithRestart`), `.history` нового TLI в S3, ключ
  ACTIVE, `gap`-поля нет, BROKEN нет; юнит-покрытие ветки фейк-источником.
- **AC2 (прыжок-fallback)**: юниты tli-процедуры на фейк-источнике:
  TLI-граничный прыжок (маркер `tli_jump`, `.history` put, старт от границы
  сегмента xlogpos с явным TIMELINE, стрим продолжается, подтверждение
  только после put), внутри-TLI прыжок, гонки повторного промоута; E2E t24b
  `WalStream_TliJump_GapMarked_FullRetaken` — финальная сходимость при
  любом пути (§3.7: кластер Active, ключ ACTIVE, цепь склеена, COMPLETED-
  полный после индукции, доставка догнала) — без ассертов на промежуточные
  события.
- **AC3 (метка и заживление)**: юниты `WalStreamProcessTests`/
  `BackupPlannerTests`: фиксация `gap` по маркеру (DEGRADED + error + поле,
  journal-фаза), снятие покрытием (COMPLETED-полный с
  `wal_start ≥ gap.to`), форс-пересъём `IsDue`, внутри-TLI игнор,
  идемпотентность WriteIfChanged, HasActive/бэкофф не сломаны; E2E t24b
  подтверждает итоговый инвариант: живого `gap`-поля нет (не возник или
  снят покрытием) при финальном ACTIVE.
- **AC4 (внутри-TLI зазор)**: юнит — прыжок `from_tli == to_tli` не ставит
  gap; контроль по объектам даёт BROKEN → существующее лечение.
- **AC5 (панель)**: правило `backup-wal-tli-gap` (critical) на живом gap
  живого Active-кластера, гаснет при снятии; ключ без `gap` читается без
  parseErrors (backwards-compat, юниты панели).
- **AC6 (ChainGlued)**: `WalStream_Promote_TliHistory_ChainGlued` зелёный на
  свежем Release.
- **AC7 (регресс-гейт)**: полные серии юнитов/интеграций/E2E на свежем
  Release зелёные (0 warnings); кейс-маркер `Scale_AddEmptyShard`;
  E2ePrepare перед серией; зачистка контейнеров/сетей/томов/ключей между
  сериями (0 остатков); телеметрия E2E по канону (`[PHASE]`, артефакты
  teardown, MarkFailed-семантика).
- **AC8 (канон)**: правки §8 слиты ДО кода (фаза Ф0); расхождений
  arch↔код нет (ревью-чек).

## 8. Правки канона (arch-first, фаза Ф0)

`arch/19-backups.md`:

1. **§3 «Возобновление»** — новый абзац «58P01 tli-переход»: механика
   досыпки (TIMELINE хвостового TLI до точки переключения) и
   прыжка-fallback (TIMELINE текущий от границы сегмента xlogpos), маркеры
   `tli_backfill`/`tli_jump`, инвариант подтверждения не меняется.
2. **§3 «.history при TLI-переходе»** — дополнение: при tli-процедуре
   `.history` нового TLI грузится приёмником немедленно (до досыпки);
   fallback-контроль остаётся.
3. **§3 «Правила непрерывности»** — семантика зазора: сегменты между хвостом
   и точкой старта прыжка в S3 не появятся (RPO-зазор); зазор на
   TLI-границе — НЕ BROKEN (CheckWithRestart), живёт маркером `gap` в ключе
   wal + форсированным пересъёмом полного (агенты не останавливаются);
   зазор внутри TLI — обычная дыра → BROKEN.
4. **§4 ключ `wal`** — опциональное поле
   `"gap":{"from","to","tli"}` (границы зазора; пишет контроль по маркеру
   приёмника, снимает покрытием — COMPLETED-полный с `wal_start ≥ to`);
   текст `tli-gap:` в `error`. Маркер приёмника читается из хвоста лога
   мастер-агента; чтение ретраится периодически — пересоздание агентов
   надзором может стирать лог до чтения, метка в этом случае не встаёт
   (наблюдаемость, не корректность: архивация восстанавливается приёмником,
   зазор вскрывают drill/restore).
5. **§2 планировщик** — сигнал пересъёма: живой непокрытый `gap` в wal-ключе
   (симметрично BROKEN-правилу покрытия).
6. **§3.5 restore / §3.6 drill** — видимость зазора: валидация
   WalChain даёт permanent-отказ с границами (восстановление от полных ниже
   зазора невозможно до переснятия — честное RPO-окно); verify полных вне
   диапазона зазора не затрагивается.
7. **§10 риски** — строка: «58P01 после фейловера при хвосте ниже форка» →
   закрытие: досыпка/прыжок §3.

`arch/adminpanel/02-etcd-contract.md` (§2.3.1): поле `gap` ключа wal —
толерантное чтение. `arch/adminpanel/03-panels.md`: правило
`backup-wal-tli-gap` (critical, границы зазора, Remedy WorkerAuto, снимается
заживлением).

## 9. Риски

| Риск | Пути закрытия |
|---|---|
| Сервер не отдаёт исторический TIMELINE (нет в истории — чужая ветка) | Ошибка старта → retry-цикл; фейк-юнит ветки; в прод-контуре невозможно (хвост писали мы сами на цепи истории сервера) |
| Npgsql-перегрузка `StartReplication(slot, lsn, ct, timeline)` ведёт себя иначе (например, требует lsn ≥ точки старта таймлайна) | Ф1 проверяет на живом PG интеграцией/спайком; E2E t24a/t24b — главный вердикт (сходимость); fallback — прыжок (механика одна) |
| CopyDone-завершение досыпки не отражается как конец enumerator'а Npgsql | Ф1: юнит + интеграция; в худшем случае сервер держит соединение до точки переключения и завершает — наблюдаемо; обрыв-ветка уже корректна (переподключение от хвоста) |
| Маркер `tli_jump` стирается пересозданием агента до чтения контроля (после фейловера надзор пересоздаёт агентов) | Принято (§3.2, п.6/п.15): метка — наблюдаемость, не корректность; архивация восстанавливается приёмником независимо; зазор вскрывают drill/restore-валидации; прод-механика — периодические перечитывания хвоста и ретраи; E2E от метки не зависит — ассерты финальные |
| Записная генерация 128 сегментов (2 ГБ WAL) в t24b медленная под нагрузкой | `[PHASE]`-телеметрия фазы; бюджет сценария по канону; несходимость в бюджет — расследование по телеметрии (расширение бюджетов не допускается) |
| Прыжок-старт гонит подтверждение слота вперёд (restart_lsn = точка старта) — сегменты ниже точки старта становятся срезаемыми | Осознанно: они уже недоставаемы (58P01); инвариант «restart_lsn ≤ доставленного в S3» сохранён (подтверждение только после put) |
| Ложный tli-gap при restore-промоуте (AC4 t05: агент прыгает по той же механике) | Заживление тем же правилом покрытия (новый полный снимается сразу после restore — COMPLETED → метка снята); окно ложного алерта = окно переснятия, закрывается автоматически |
| Поле `gap` в ключе ломает старые парсеры | Опциональное JSON-поле; правило backwards-compat канона §4 (юнит-проверка AC5) |
