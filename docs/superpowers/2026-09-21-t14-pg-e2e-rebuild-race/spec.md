# t14-pg-e2e-rebuild-race — фикс тест-рейса «stale-RUNNING» в pg-E2E (ac5-rebuild)

## 1. Цель

Устранить детерминированный FAIL pg-E2E-сценария
`Acceptance_Scenario_Ac2_To_Ac7` в фазе `ac5-rebuild`
(`AssertFailoverRebuildAsync`,
`src/tests/PgWorker.IntegrationTests/E2e/E2eScenarios.cs`): условие фазы
(`state == "RUNNING"`) истинно на до-стоповом значении etcd-ключа ноды, после
чего одиночный `docker inspect` видит остановленный сценарием контейнер
(`exited`) → ассерт «контейнер пересоздан» падает. Тест обязан проверять
факт перехода ноды `REBUILDING→RUNNING` (AC5, spec задачи 26 §11.5), а не
мгновенно-истинное условие на stale-значении.

Код воркера/движка НЕ меняется: разбор мерж-гейта t07 (2026-09-20)
подтвердил — движок в упавшей цепочке не участвует (stop/inspect — docker
CLI теста, записи state — супервизор домена, промоушен — patroni образа);
соседние серии на том же движке зелёные; подтверждено код-ревью t07.
Артефакты разбора: teardown-дамп
`/tmp/pgw-e2e-artifacts-c471a894eb7b41b18dd85973fdd75ef5/`, лог прогона
`/tmp/t07-pg-e2e.log`.

## 3. Корневая причина (таймлайн рейса, по коду и логам t07)

E2e-окружение: `ScanIntervalSec=1`, `NodeDeadSec=6`
(`E2eEnvironment.StartHostAsync`, env-сжатие таймингов).

1. `t0` — тест делает `docker stop` контейнера лидера шарда
   (`masterBefore.Node`, резолв по пробам Patroni `/primary`).
2. `t0+~1.2 с` — Patroni промоутит реплику (graceful demote по SIGTERM);
   фаза `ac5-failover` (детерминированная — по пробам `/primary`, бюджет
   10 с, жёсткий ассерт ≤5 с) возвращает `true`.
3. Супервизорный тик ещё не отработал смерть ноды: `NodeSupervisor`
   (`src/PgWorker.Provisioning/Processes/NodeSupervisor.cs`,
   `SuperviseShardAsync`) пишет `UNREACHABLE` только в первом тике, где
   проба ноды мертва. До этого момента ключ ноды — `RUNNING` с
   provisioning-времени (в установившемся режиме гвард
   `node.State is not (…)` запрещает перезапись `RUNNING` → ревизия ключа
   стабильна).
4. `E2eFixture.WaitForAsync` (полл 500 мс) проверяет условие ДО первой
   задержки → фаза `ac5-rebuild` видит stale-`RUNNING` и возвращает `true`
   мгновенно (~0.3 с), не простояв бюджет 300 с.
5. Одиночный `ContainerStatusAsync(container)` → `exited`: это ИСХОДНЫЙ
   контейнер, остановленный самим сценарием на шаге 1; пересоздание ещё не
   произошло → `Should().Be("running")` FAIL. Сценарий падает за ~2 мин.

Фактический порядок записей ключа ноды после `docker stop` (по
`NodeSupervisor`): `UNREACHABLE` (первый тик надзора, ≤1–2 с) →
`REBUILDING` (rebuild-ветка: `!isLeader && quorum && expired`, через
`NodeDeadSec=6` с dead-трекинга; `RemoveNode`+`EnsureNode`) → `RUNNING`
(alive-путь, только когда пересозданная нода жива пробой). Каждая запись —
`PutAsync`, растит `ModRevision` ключа; `RUNNING` для мёртвой пробы
невозможен (alive-путь пишет только живым, dead-путь — только
`UNREACHABLE`/`REBUILDING`).

## 4. Принципы

1. **Детерминизм ожидания**: условие фазы обязано быть ложным на
   до-стоповом значении ключа — закрытие рейса без вероятностных окон
   («промахнуться опросом» исключено конструкцией).
2. **Буква AC5**: проверяется переход `REBUILDING→RUNNING`, а не голый факт
   `RUNNING`.
3. **Телеметрия** (docs/e2e-launch.md §1/§2): падающий ассерт — с контекстом
   (дамп состояния на момент падения, по образцу `ac6-quarantine`); фазы —
   только через `WaitPhaseAsync`.
4. **Минимальность**: правка локальна в `AssertFailoverRebuildAsync`;
   код воркера/движка, бюджеты фаз, изоляция/teardown — без изменений.
   Запрещённый путь — «просто увеличить таймаут» (AGENTS.base.md, диагностика
   зависаний): причина рейса понятна, лечится условие, а не бюджет.

## 5. Решение: ModRevision-гейт фазы ac5-rebuild

### 5.1 Механизм

В `AssertFailoverRebuildAsync`:

1. **Фиксация ревизии до stop**: сразу после резолва `masterBefore` и до
   `docker stop` — прочитать ключ
   `/clusters/{cluster}/shards/{shard}/nodes/{masterBefore.Node}/state`
   (существующий хелпер `GetOrNullAsync` возвращает `Kv` с `ModRevision`);
   запомнить `revAtStop = kv.ModRevision`. Ассерт предусловия: ключ есть и
   значение `RUNNING` (лидер до failover работает — уже есть ассерт
   статуса контейнера `running`).
2. **Условие фазы ac5-rebuild**: `state == "RUNNING" && kv.ModRevision >
   revAtStop` (тот же бюджет 300 с). Stale-`RUNNING` имеет ревизию ≤
   `revAtStop` → отсекается безусловно. Новая запись `RUNNING` с ревизией >
   `revAtStop` возможна только после реального цикла восстановления
   (см. §3: порядок записей строго `UNREACHABLE`→`REBUILDING`→`RUNNING`;
   `RUNNING` пишется только живым пробой нодам).
3. **Диагностика при `!rebuilt`**: вместо голого
   `rebuilt.Should().BeTrue(...)` — `Assert.Fail` с дампом: текущее
   значение ключа ноды (state + ModRevision), `revAtStop`, статус
   контейнера (`ContainerStatusAsync`). Образец — `ac6-quarantine`
   (строки с `Assert.Fail($"…journal: …; статусы контейнеров: …")`).
4. **Комментарий-обоснование** (русский, по стилю файла): почему гейт по
   ревизии — расшифровка порядка записей супервизора и ссылка на
   `NodeSupervisor`/arch/14 §5 C; почему одиночный inspect после
   детерминированного `rebuilt` корректен: `RUNNING` пишется только когда
   нода жива пробой → контейнер уже `running`; повторная смерть сразу после
   — реальный сбой, тест обязан упасть.

Ассерт «контейнер пересоздан» (`ContainerStatusAsync == "running"`) после
`rebuilt` остаётся одиночным (ретраи не вводятся — см. §5.3, альтернатива 2).

### 5.2 Почему корректно

- `ModRevision` ключа в etcd монотонно растёт с каждой записью;
  `EtcdGateway` наполняет его из ответа Range/Get (`Shared.Etcd/Client/
  EtcdGateway.cs`) — тесту ничего нового не требуется.
- В установившемся режиме до stop ключ ноды не перезаписывается (гварды
  `NodeSupervisor`); любая запись между фиксацией ревизии и stop (гипотетический
  флап) лишь увеличивает ревизию — гейт остаётся корректным (строже).
- После stop перезапись `RUNNING` без реального восстановления невозможна
  (§3), значит условие истинно ⇔ нода реально прошла восстановление.
  Двусмысленности «старое/новое RUNNING» нет по построению.

### 5.3 Альтернативы (рассмотрены)

1. **Двухфазное ожидание перехода**: фаза 1 ждёт `state != "RUNNING"`
   (уход в `UNREACHABLE`/`REBUILDING`, ≤1–2 с), фаза 2 — возврат в
   `RUNNING`. Соответствует формулировке roadmap («ждать факт перехода
   UNREACHABLE/REBUILDING → RUNNING»); окно «перепрыгнуть» переход между
   опросами ничтожно (переход живёт ≥ `NodeDeadSec=6` с при полле 0.5 с),
   но не ноль; +1 фаза в телеметрии.
2. **Ретраи docker-inspect** (второй вариант roadmap): одиночный inspect
   заменить на `WaitPhaseAsync`-ожидание статуса `running` (образец
   `ac5-replica-catchup`). Минимальная правка, но фаза ac5-rebuild
   вырождается в мгновенно-истинную на stale-значении — etcd-факт
   «REBUILDING→RUNNING» фактически не проверяется; семантика слабее AC5.

**Статус выбора**: вопрос выбора механизма задан пользователю через
`AskUserQuestion` (2026-09-21) и остался без ответа; принята рекомендация —
ModRevision-гейт (детерминирован, без вероятностных окон, точнее всех
соответствует AC5). Подтверждение/смена подхода — на гейте ревью настоящего

## 9. Критерии приёмки

1. Фаза `ac5-rebuild` конструктивно не может пройти на до-стоповом значении
   ключа ноды (гейт `ModRevision > revAtStop`); в коде — комментарий с
   обоснованием.
2. При честном прохождении: `[PHASE] ac5-rebuild` в журнале показывает
   фактическое время восстановления (~15–120 с: `UNREACHABLE` ≤2 с +
   `NodeDeadSec=6` + пересоздание/basebackup), а не ~0.3 с; после фазы
   контейнер `running`, `ac5-replica-catchup` зелёный (без изменений
   поведения).
3. При неудаче (баг движка: нода не восстановилась за 300 с) — падение с
   контекстом: state+ModRevision ключа, `revAtStop`, статус контейнера
   (телеметрия §1, без обрезок).
4. Полный прогон `Acceptance_Scenario_Ac2_To_Ac7` на свежем Release —
   зелёный (мерж-гейт §7.3); упавший прогон разбирается по логам без
   перезапуска.
5. `dotnet build src/PgWorker.slnx -c Release` — 0 warnings; тесты с
   AAA-комментариями (правило пользовательское: AAA — для новых тестов;
   здесь правится тело существующего сценария — AAA-структура метода уже
   задокументирована в его заголовочном комментарии).
6. После серии — зачистка контейнеров/сетей; повторные прогоны серий —
   только поверх зачищенного хоста (AGENTS.md).
