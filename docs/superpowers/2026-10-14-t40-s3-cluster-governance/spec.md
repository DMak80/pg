# t40-s3-cluster-governance — спецификация

Управление и контроль кластеров ownS3: backend-часть (UI — отдельная
задача t34). PKI репликации per-cluster в etcd, инстансы с произвольными
именами, декларативный граф репликации, deny-list кластера; применяет всё
S3Worker.

## 1. Контекст и цель

S3Worker (канон [arch/24-s3worker.md](../../../arch/24-s3worker.md)) —
оркестратор S3-кластеров по декларативному контракту etcd
([arch/23-s3-clusters.md](../../../arch/23-s3-clusters.md)). Платформа
нод — ownS3 (arch/22); mesh-репликация с peer-PKI, join-handshake и
deny-list — канон
[arch/owns3/07-replication.md](../../../arch/owns3/07-replication.md)
(механика t39 реализована в `src/OwnS3.{Replication,Protocol}`, CLI
`OwnS3.Pki`). До задачи: ноды именуются `node<k>` (генерирует панель),
PKI-материал выпускается вручную CLI и передаётся env вне контура
управления, mesh-доводки нет (P4 — no-op), deny-list — локальные файлы
инстансов без источника истины.

Цель задачи — замкнуть управление кластером полностью на S3Worker:

1. **PKI репликации per-cluster в etcd**: CA кластера (ECDSA P-256) и
   выданные им сертификаты инстансов генерирует S3Worker и хранит в etcd;
   ключи переживают provision/переезд контейнера (контейнер пересоздаётся
   с тем же сертификатом).
2. **Инстансы — уникальные произвольные имена** (не `node<k>`; паттерн
   как у кластера); имя = ключ etcd = имя target/коммуникации. Кластер
   может иметь **0 и более инстансов** (декларация без развёртывания
   валидна — при создании).
3. Placement-привязка по атрибутам хостов — без изменений (arch/23 §4).
4. **Граф репликации задается декларативно в etcd** (ключ `links`) —
   произвольный набор связей между инстансами; full-mesh НЕ инвариант
   (частичный/незеркальный состав нормален).
5. **Deny-list кластера — источник истины в etcd** (ключ `denylist`);
   воркер доводит его до всех инстансов. Операция «инстанс в deny-list» =
   отзыв его ключа.
6. Применяет всё S3Worker: декларации etcd → targets/join/deny инстансов;
   ключи выпускает по мере надобности.
7. Клиентские root-креды S3-грани остаются env-профилями (arch/23 §6 —
   PKI репликации в etcd их не заменяет). UI нет: управление ключами
   полностью скрыто бэком.

## 3. Ключевые решения дизайна

### 3.1. Инстансы: произвольные имена, допустимость 0

- Имя инстанса `<I>` — `^[a-z][a-z0-9_]{0,62}$` (паттерн кластера),
  уникально в кластере, задаётся в заявке (панель/оператор); генерация
  `node<k>` НЕ используется. Имя служит: сегментом ключа etcd
  `nodes/<I>/…`, именем docker-объектов `s3w-<C>-<I>[-data]`,
  `TargetRecord.Name` ownS3 (имя target/коммуникации: подпись Credential,
  резолв sourceName, ключи курсоров/reconcile-маркеров).
- **Сегмент ключа `nodes/` сохранён** (решение user-review: «инстанс» и
  «нода» — синонимы, «ноды» короче; переименование в `instances/` не
  нужно). Меняются значения имён, не структура префикса; терминология UI
  не предрешается (t34).
- Имя `orchestrator` зарезервировано (сертификат оркестратора PKI —
  §3.2); валидация API — 400.
- Кластер может иметь 0..9 инстансов; `config.nodes` — 0..9
  (поддерживается фактическим составом). **0 инстансов валиден только
  декларацией при создании кластера** (создание с `instances=[]` —
  provisioning проходит без docker-мутаций: P1–P4 пустые → P5 commit;
  `endpoints` при 0 инстансов не пишется). **Вывод последнего инстанса из
  кластера с ≥1 инстансов запрещён гвардой** (API → 409; процесс E —
  отказ фазы): осознанный перевод работающего кластера в «пустой»
  операцией вывода не допускается — путь к кластеру без инстансов один:
  снос кластера целиком (`TO_REMOVE`). Гварда сохранена по решению
  user-review (изначальное каноническое поведение arch/24 §5 E).
- Перечисление docker-объектов кластера (сироты X2, занятость) — по
  префиксу `s3w-<C>-` + label `s3worker` (перебор детерминированных имён
  невозможен).

### 3.2. PKI репликации per-cluster в etcd

Ключи (форматы — arch/23 §2/§2.1, раздел «PKI репликации» §6):

| Ключ | Значение | Кто пишет |
|---|---|---|
| `/s3/clusters/<C>/pki/ca` | `{"name":"<C>","publicKeyPem":…,"private_key_pem":…}` — CA кластера ECDSA P-256 | воркер, лениво, txn put-if-absent |
| `/s3/clusters/<C>/pki/orchestrator` | `{"certificate":<PeerCertificate JSON>,"private_key_pem":…}` — сертификат оркестратора (имя `orchestrator`, подписан CA кластера) | воркер, лениво вместе с CA |
| `/s3/clusters/<C>/nodes/<I>/pki` | `{"certificate":<PeerCertificate JSON>,"private_key_pem":…}` — материал инстанса (имя = `<I>`) | воркер, лениво, txn put-if-absent |

Свойства:

- **Генерация и хранение — S3Worker в etcd**; криптомеханика — библиотека
  peer-PKI ownS3 (`PeerCertificateAuthority.CreateCa/IssueServer`,
  ECDSA P-256, подпись P1363 over SHA-256) — переиспользуется через
  ProjectReference `S3Worker.Core → OwnS3.Protocol` (копирование
  крипты запрещено).
- **Имя CA = имя кластера** `<C>`: trust-домены кластеров изолированы
  (сертификат кластера C1 не проходит trust-anchor C2 — `caName` не
  совпадает).
- **Бессрочные сертификаты** (`expiresAtUnixMs = 0`,
  `IssueServer(expiresDays ≤ 0)`): ключи переживают provision/переезд
  без плановой ротации; отзыв компрометации — deny-list (мгновенный,
  §3.4); плановая ротация ключей/CA — вне задачи (roadmap, owns3/07 §12).
- **Ленивый выпуск, txn put-if-absent**: pki/ca + pki/orchestrator — при
  первом необходимом использовании (первый инстанс кластера, deny-list,
  links); `nodes/<I>/pki` — при подготовке env инстанса (P2/D/надзор).
  Повторный вызов на существующем ключе возвращает существующий материал
  (идемпотентность; проигрыш txn → re-read, первый записавший — истина,
  arch/17 S5).
- **Orchestrator-сертификат** — ключ S3Worker для до-join контура ownS3
  (`PUT /replication/denylist`: доверие ⟺ сертификат подписан CA ∧
  имя/ключ не отозваны, owns3/07 §6). S3Worker не числится соседом ни в
  одном mesh — используется только подпись этого контура.
- **Удаление**: `nodes/<I>/pki` сносится процессом E вместе с инстансом
  (имя освобождается; повторное создание инстанса с тем же именем — новый
  выпуск); `pki/*` кластера — X3 вместе с префиксом кластера.
- Приватные ключи читает только воркер; панель управление ключами не
  показывает (t34 — PKI вне проекции UI).
- **Клиентские root-креды S3-грани — без изменений**: env-профили
  `S3W_NODE_SECRETS__<PROFILE>__*` (arch/23 §6); PKI репликации их не
  заменяет и не расширяет.

### 3.3. Граф репликации `links`

- Ключ `/s3/clusters/<C>/links` = JSON-массив пар
  `[{"a":"<I1>","b":"<I2>"},…]`; замена целиком через API
  (`PUT /api/s3/clusters/{c}/links`, 202). Валидация: имена существуют,
  `a≠b`, пары уникальны (400).
- **Семантика связи — пара, реализуемая join-механикой ownS3
  двусторонне**: рабочая доставка требует target-записей у обеих сторон
  (приёмник отвергает неизвестного пира — 403, owns3/07 §6), join
  добавляет записи обеим сторонам (owns3/07 §2). Направленный поток
  «только a→b» механикой ownS3 не выражается — частичность/незеркальность
  графа достигается составом пар: не все пары связаны, составы соседей у
  разных инстансов различаются (full-mesh НЕ инвариант; зонд t33
  контролирует только настроенные линки).
- Применение — доводчик G (§3.5): `links` → фактические targets
  инстансов.
- Битый JSON/имена (ручная правка etcd) — parseError-поля парсера без
  падения тика (arch/23 §9); G пишет диагностику в journal и не применяет
  битую часть.

### 3.4. Deny-list кластера — отзыв ключа

- Ключ `/s3/clusters/<C>/denylist` = JSON-массив имён инстансов
  `["<I>",…]`; мутируется API deny/allow.
- **Доведение до всех инстансов** — полная перезапись `PUT
  /replication/denylist` (до-join контур ownS3) телом
  `{entries:[{name, publicKeyPem}]}`: для каждого имени — публичный ключ
  из `nodes/<I>/pki` (выпускал воркер — ключ известен). Подпись запроса
  — схема OWNS3-PEER ключом оркестратора, сертификат в заголовке
  `X-OwnS3-Peer-Certificate` (по образцу `JoinPeerService.JoinAsync`).
- **Семантика — полная изоляция** (решение user-review, подтверждено):
  deny-инстанс (а) не сможет join (сертификат в deny у всех — 403),
  (б) его существующие связи сносятся доводчиком (имя не входит в
  желаемый состав соседей). Deny-list платформы закрывает только будущие
  join (owns3/07 §6) — снос текущих линков делает доводчик своими
  `DELETE /admin/replication/targets/{name}`.
- Недоступный инстанс — deny-перезапись откладывается (transient,
  следующий тик); доступность определяется по state (RUNNING) и
  health-факту надзора.
- `allow` — имя удаляется из denylist; доведение той же перезаписью
  (пустые entries на инстансе снимают все отзовы).
- E при удалении инстанса убирает имя из `denylist` (иначе доведение
  потеряет publicKeyPem — ключа нет).

### 3.5. Доводчик состава — процесс G (MeshGovernance)

Новый процесс Active-ветки (после E, до F); та же логика — фаза P4
provisioning'а. Все операции — под клэймом `<C>`,
journal-before-manipulations (`op=mesh-governance`), идемпотентны.

Вход: снапшот деклараций (`links`, `denylist`, состав и state инстансов,
portalloc-адреса) + фактический состав targets инстансов
(`GET /admin/replication/status`, SigV4 root-кредами профиля).

Желаемый состав target-записей инстанса X = `{соседи по links}` минус
denylist минус несуществующие и не-RUNNING имена.

Шаги за один тик (порядок фиксирован; одна структурная операция mesh за
тик — join-пара или delete-пара; deny-перезапись — всем живым сразу,
операция дешёвая и идемпотентная):

1. **Deny-доведение** (см. §3.4).
2. **Сверка и доводка состава**:
   - недостающая связь {a,b} → `POST /admin/replication/join`
     `{"endpoint": "http://<b-advertised>:<port>"}` на a (root-креды
     профиля). Join двусторонний; join не ставит событий и не рвёт
     курсоры (owns3/07 §2). Исходы: 200 — готово; 409 (имя числится с
     другим ключом) → `DELETE /admin/replication/targets/{name}` на
     конфликтующей стороне, повтор следующим тиком; 403/502/транспорт —
     transient, ретрай тиком.
   - лишняя запись (сосед не в желаемом составе: убран из links, deny,
     инстанс выведен) → `DELETE /admin/replication/targets/{name}` на
     каждой стороне пары (курсор сохраняется — возврат соседа продолжится
     с места, owns3/07 §2).
3. **Диагностика**: journal-фазы (`waiting-join`, `cleaned-targets`,
   `deny-pushed`, ошибки — last_error); метрики `s3worker_mesh_*`
   (join/delete/deny-счётчики исходов — arch/24 §7).

Границы G:

- Advertised-endpoint для join — из portalloc
  (`AdvertisedHost ?? host` + S3-порт — то же правило, что `endpoints`).
- Смена per-install advertised-адресов (конфиг `AdvertisedHost`) — вне
  штатных операций: target-записи держат прежние endpoint'ы; лечение —
  переприсвоение пары в `links` (снос + повторный join обновляет endpoint
  идемпотентно). Риск R5 arch/24 §9.
- G не управляет данными (курсоры/очереди/reconcile — внутренняя
  механика ownS3): только состав и deny.

### 3.6. env инстанса

При создании (P2) и любом пересоздании (надзор C, ротация секретов)
контейнер ownS3 получает (общий сборщик env — единая точка сборки для
всех процессов):

- клиентская грань (без изменений): `OWNS3_ROOT_USER`,
  `OWNS3_ROOT_PASSWORD`, `OWNS3_ACCESS_KEYS__<i>__*`, `OWNS3_DATA_DIR=/data`;
- репликация (значения, не пути — прецедент owns3/07 §11):
  - `OWNS3_REPLICATION_CERT` — JSON сертификата инстанса;
  - `OWNS3_REPLICATION_PRIVATE_KEY` — PEM приватного ключа;
  - `OWNS3_REPLICATION_TRUST_CA` — trust-anchor JSON
    `{"name","publicKeyPem"}` из `pki/ca`;
  - `OWNS3_REPLICATION_ADVERTISED_ENDPOINT` —
    `http://<advertised-host>:<s3-port>`.
- Состав mesh env'ом НЕ передаётся (env-seed ownS3 — legacy-only,
  owns3/07 §2): только join/админ-грань через G.

Пересоздание контейнера (снесён/ротация/лимиты) использует тот же
материал из etcd — сертификат инстанса неизменен («ключи переживают
provision/переезд»). volume сохраняется: targets/cursors инстанса на
томе переживают пересоздание, mesh самовосстанавливается.

### 3.7. HTTP API воркера (arch/24 §1.1)

Изменения/дополнения (mTLS-грань — без изменений):

| Эндпоинт | Поведение |
|---|---|
| `POST /api/s3/clusters` | тело: `{name, platform, secretProfile, instances:[{name, placement, resources}]?, resources?}`; `instances` 0..9 (0/отсутствие — кластер без инстансов); config `nodes=len(instances)`; пакет PUT config + instances × {placement, resources, state=NOT_INITIALIZED}; клэйм-txn `version(config)==0`, сбой — компенсация `del --prefix` |
| `POST /api/s3/clusters/{c}/nodes` | тело `{name, placement, resources}` — имя инстанса из запроса; клэйм-txn `version(nodes/<I>/state)==0`; 409 при коллизии имени |
| `DELETE /api/s3/clusters/{c}/nodes/{n}` | маркер TO_REMOVE; гварды: не последний инстанс кластера — вывод последнего → 409 (0 инстансов валиден только созданием; путь к «пустому» кластеру — снос кластера целиком); already TO_REMOVE → 204 |
| `PUT /api/s3/clusters/{c}/links` | замена графа `{links:[{a,b}…]}` → 202; валидация §3.3 |
| `POST /api/s3/clusters/{c}/nodes/{n}/deny` | отзыв ключа: имя в `denylist` → 202; 404 если инстанса нет; already → 200/204 идемпотентно |
| `POST /api/s3/clusters/{c}/nodes/{n}/allow` | снятие отзыва → 202 |
| `DELETE /api/s3/clusters/{c}`, `PUT …/resources`, `POST …/rotations`, `POST …/sync-probe` | без изменений |

Валидация имени инстанса (сервер — источник истины): паттерн
`^[a-z][a-z0-9_]{0,62}$`, не `orchestrator` (400), уникальность в
кластере (409).

### 3.8. Жизненный цикл и процессы (arch/24 §5)

- **A. Provisioning (P0–P5)**: P2 — ленивый выпуск PKI
  (ca/orchestrator/инстансов) + env §3.6; P4 — доводка mesh по links
  (логика G, не no-op); P5 — endpoints (0 инстансов — ключ не пишется);
  0-инстансовый provisioning — P1–P4 пустые, сразу P5.
- **B. Deprovisioning (X0–X3)**: без изменений по механике (X2 снос
  `s3w-<C>-*`; X3 del префикса — уносит `pki/*`, `links`, `denylist`).
- **C. Надзор**: пересоздание — тот же PKI-материал (env из etcd),
  volume/targets сохраняются.
- **D. AddNode**: подъём нового инстанса по A (PKI/placement/portalloc/
  volume/контейнер/bucket) + RMW endpoints; включение в mesh — G по
  links.
- **E. RemoveNode**: гварды (не последний инстанс кластера; при мёртвых
  остальных — нет живой RUNNING-ноды кроме выводимой — отказ фазы: вывод
  не рвёт последнюю точку записи пула) → снос контейнера/volume → чистка
  `nodes/<I>/…` (включая pki), portalloc, имени из denylist → RMW
  endpoints; связи выводимого — G (записи «лишние» после исчезновения
  имени).
- **G. MeshGovernance** — §3.5 (новый, седьмой процесс).
- **F. SyncProbe** — без изменений (t33).

### 3.9. Ролевая модель доступа доводчика

- Admin-грань инстансов (`/admin/replication/*`: join, targets, status) —
  SigV4 root-креды профиля кластера (уже есть у воркера).
- До-join контур (`PUT /replication/denylist`) — сертификат оркестратора
  кластера + подпись OWNS3-PEER (§3.2).
- Никаких новых кредов/env у воркера не появляется: PKI — из etcd,
  root-креды — из профиля.

## 8. Критерии приёмки

### 8.1. Юнит-тесты

1. Парсер: канонические примеры arch/23 §2.1 (links, denylist, pki,
   config nodes=0) → модель; битые значения → parseError без падения;
   неизвестные ключи → unknownKeys.
2. Валидаторы API: имя инстанса (паттерн/резерв `orchestrator`/
   уникальность), links (существование имён, a≠b, уникальность пар),
   deny/allow (404 несуществующего).
3. `PkiStore`: повторный выпуск на существующем ключе возвращает тот же
   материал (if-absent); сертификат проходит `PeerCertificateAuthority.
   Verify` против trust-anchor своего CA и НЕ проходит против чужого
   (изоляция кластеров); сертификат ↔ ключ соответствуют.
4. `InstanceEnvComposer`: полный набор `OWNS3_*` (клиентская грань +
   репликация §3.6); advertised-endpoint из portalloc/AdvertisedHost.
5. `MeshGovernance` (фейк-клиент): план доводки — недостающая пара →
   join; лишняя запись → delete на обеих сторонах; deny-инстанс → нет
   join + снос записей; 409 → delete + повтор; не-RUNNING сосед →
   ожидание; deny-перезапись шлётся всем RUNNING.
6. Подпись `PUT /replication/denylist` проходит верификацию
   `PeerRequestVerifier` ownS3 (обратная совместимость контуров).

### 8.2. Интеграционные тесты (API + etcd)

1. Создание кластера с 0 инстансов → config nodes=0, state снят
   воркером, endpoints отсутствует.
2. Создание с 2 инстансами по именам; коллизия имени → 409; имя
   `orchestrator` → 400.
3. `PUT links` валидный/невалидный (несуществующее имя → 400).
4. deny/allow: 202, 404; denylist-значение в etcd.
5. Удаление инстанса из кластера с ≥2 инстансами → 202; удаление
   последнего инстанса → 409 (гварда сохранена).

### 8.3. E2E (docker, Release; каноны изоляции/телеметрии AGENTS.md)

1. **PKI-провижининг**: кластер 2 инстанса + links(пара) → контейнеры с
   `OWNS3_REPLICATION_*`; статус инстансов: связь установлена (join
   прошёл); объект, записанный в инстанс A, появляется на B (репликация
   доставлена) в пределах бюджета теста.
2. **Переживание переезда**: снос контейнера инстанса (`docker rm -f`)
   → надзор пересоздал; сертификат тот же (env/inspect); связь жива;
   объекты не потеряны.
3. **Deny**: deny инстанса → его связи снесены (статусы targets),
   denylist доведён всем; повторный join невозможен (403); allow →
   связь восстанавливается доводкой.
4. **Частичный граф**: 3 инстанса, links только {a,b},{a,c} → у b и c
   нет связи друг с другом; это не дефект (проверка состава targets).
5. **0 инстансов**: создание пустого кластера → Active, endpoints нет;
   добавление инстанса в живой кластер → links+join работают.
6. Полный teardown + ассерт чистоты контура сценария (guid-имена,
   динамические порты, артефакты `/tmp/pgw-e2e-artifacts-<guid>/`).

### 8.4. Регрессии

- Существующие сценарии S3Worker (provision/deprovision/supervise/
  add/remove/ротация) зелёные; форматы etcd — по обновлённому канону.
- `TreatWarningsAsErrors`, `dotnet build` без предупреждений.

## 9. Решения user-review (вопросы закрыты, зафиксированы)

1. **Сегмент ключа PKI** — `nodes/<I>/pki` (переименование в
   `instances/` отклонено: «инстанс»/«нода» — синонимы, «ноды» короче).
   Отражено: §3.1, arch/23 §2.
2. **Семантика deny** — полная изоляция: снос текущих связей доводчиком
   + блокировка будущих join. Отражено: §3.4/§3.5, arch/23 §2
   (`denylist`), arch/24 §5 G.
3. **Гварда «не последний инстанс»** — сохранена: 0 инстансов валиден
   только декларацией при создании; вывод последнего инстанса из
   работающего кластера запрещён (API 409 / отказ фазы E); путь к
   «пустому» кластеру — снос кластера целиком. Отражено: §3.1/§3.7/
   §3.8/§8.2, arch/23 §2 (`config.nodes`, `endpoints`), arch/24 §1.1/
   §5 E/§9 R2.
4. **«Недостающая доработка грани ownS3»** — не требуется: существующих
   граней достаточно (доведение deny — существующий
   `PUT /replication/denylist`); отдельная задача трека owns3 не
   оформляется. Отражено: §4 п.3.
