# t09-e2e-release-regression — регрессия E2E-тестов PgWorker на свежем Release-бинаре

Спецификация фазы spec (dev-flow). Полная формулировка задачи —
`arch/roadmap/pgworker.md`, тег `t09-e2e-release-regression`. Код не пишем —
дизайн и методика; исполнение — фазы plan/code.

## 1. Цель

Устранить регрессию PgWorker.App, найденную 2026-09-02: на свежесобранном
Release стабильно падают 4 кейса E2eFixture (в т.ч. изолированно):

- `Scale_TakeoverMidAdd_SecondInstanceFinishesNoDuplicates`
  (`src/tests/PgWorker.IntegrationTests/E2e/E2eScaleScenarios.cs`);
- `Scale_AddEmptyShard_BlockedRemoveThenAutoDismantle_NameReused` (там же);
- `Acceptance_Ac2_To_Ac7` (`E2eScenarios.cs`);
- `Move_Lifecycle_Chain` (`E2eMoveScenarios.cs`).

И устранить саму возможность маскировки: E2eFixture запускает готовый
`bin/Release/net10.0/PgWorker.App.dll`, не пересобирая его (fail-fast есть
только на *отсутствие* файла, `E2eFixture.cs:46-49`) — устаревший зелёный
бинарь скрывал регрессию с 29.08 по 02.09, при том что docker-образ
`pgworker-node:e2e` фикстура пересобирает на каждом прогоне (`E2eFixture.cs:80`).

Результат задачи: (а) найден коммит-виновник бисектом, (б) дефект починен
(логика или фикстура — по критерию §6), (в) E2eFixture всегда гоняет
актуальный Release, (г) регрессия такого класса больше не зреет незамеченной
(правило мерж-гейта).

## 3. Принципы

- **arch-first**: если виновник — дефект логики, затрагивающий контракт
  (порт-аллокация/provisioning/adoption/moves — `arch/14-pgworker.md` §5 A,
  §5 J, §6), контракт обновляется ПЕРВЫМ, затем код. Если код контракту
  соответствует, а тест полагался на незаконтрактованное поведение — фикс
  теста/фикстуры, контракт не меняется (кроме случаев, где контракт сам
  неточен — тогда уточняем). Канона тестирования в `arch/` нет — правило
  пересборки и мерж-гейта канонизируются в коде фикстуры и `AGENTS.md`
  проекта, новый arch-файл не заводим.
- **Доказательство, не догадка**: виновник определяется только прогоном
  (bisect), не чтением diff; diff-анализ волн (факт 4) — для приоритизации и
  объяснения, не для назначения виновника.
- **Маскировка недопустима**: любой прогон E2E обязан тестировать код,
  который в репозитории сейчас, — бинарь собирается фикстурой автоматически.
- **Изоляция эксперимента**: каждый прогон бисекта — своя пересборка Release
  и свой docker-контур фикстуры (очистка `pgw-*` уже встроена в
  `InitializeAsync`); никаких хардкодов портов (фикстура уже на `FreePort()`).
- **Язык**: документация и комментарии — русский; идентификаторы — английский.

## 5. Фазы исполнения

### Фаза А. Репро на текущем HEAD

Прогон всех 4 кейсов на свежем Release текущего HEAD (`21ca8b4`+):
`dotnet build src/PgWorker.slnx -c Release` → `PGW_TEST_DOCKER=1 dotnet test
--filter` по 4 кейсам.

- **А1 (падают)** → фаза Б (бисект по окну из факта 4).
- **А2 (не падают — t90/t07 закрыли регрессию попутно)** → виновник всё равно
  устанавливается: bisect по `55e2962..2161f33` с прогоном кейса-маркера
  (та же методика фазы Б) даёт коммит-виновника «исторически»; фикс-фаза
  сводится к подтверждению, что текущий код дефект не содержит (все 4 кейса
  зелёные), и к обязательным фазам Г/Д. Отдельного реверс-фикса не делаем —
  только если бисект вскроет дефект, никак не связанный с t90 (решение
  фиксировать по критерию §6).

### Фаза Б. Бисект

Методика (решения согласованы с пользователем):

1. **Кейс-маркер**: `Scale_AddEmptyShard_BlockedRemoveThenAutoDismantle_NameReused`
   — один кейс на шаг бисекта: покрывает provision с нуля + add-shard +
   teardown (максимум подозреваемых подсистем), без kill/takeover-фаз
   (наиболее детерминирован).
2. **Шаг 0 — верификация good-границы**: checkout `55e2962` → сборка Release →
   прогон маркера. Зелёный → good подтверждён. Красный → окно расширяется
   назад по PgWorker-коммитам 28.08 (`8318995` и старше) тем же методом до
   последнего зелёного.
3. `git bisect start`; good = верифицированный коммит шага 0; bad = `2161f33`.
   `git bisect run <скрипт>`: на каждом шаге — `dotnet build
   src/PgWorker.slnx -c Release` + прогон маркера с `PGW_TEST_DOCKER=1`;
   exit-коды: падение кейса → bad (1), зелёный → good (0), сбой окружения
   (docker/сеть недоступны, фиксстура не поднялась не по вине кода) →
   `git bisect skip` (125). Ориентир ~5–6 шагов (log2 22).
4. **Финальная верификация**: все 4 кейса на найденном виновнике (red) и на
   его родителе (green) — коммит-виновник считается установленным только при
   этой паре прогонов.

Критерии виновника: (а) маркер стабильно красный на коммите и зелёный на
родителе; (б) из четырёх исходных кейсов на виновнике красные ≥1 (гипотеза:
все 4, единый корень; расхождение фиксируется в журнале как факт);
(в) симптом объясним изменениями коммита (механизм сформулировать словами —
без этого фикс не начинается).

### Фаза В. Фикс

Выбор «логика vs фикстура/тест» — по контракту:

- **Сценарий А (дефект логики)**: наблюдаемое поведение нарушает
  `arch/14-pgworker.md` (или другой затронутый контракт). Порядок: контракт →
  код → тесты. Фикс минимальный (реверт причины, а не симптома); регресс-тест
  на корень дефекта (юнит/интеграционный, воспроизводящий механизм без
  полного E2E, где возможно).
- **Сценарий Б (дефект теста)**: код контракту соответствует, тест полагался
  на незаконтрактованное поведение (например, тайминги/порядок тиков,
  изменившиеся бэкоффом `4ca780f` или portalloc-клэймом t90). Фикс теста;
  если вскрылась неточность контракта — уточнить `arch/14` первым.
- Смешанный случай (тест уязвим И логика менялась) — чиним оба: логику по
  контракту, тест — на детерминированное ожидание.

### Фаза Г. Автосборка Release в E2eFixture (решение согласовано)

`E2eFixture.InitializeAsync` перед проверкой `File.Exists(AppDll)` вызывает
`dotnet build src/PgWorker.slnx -c Release` (инкрементальный msbuild: no-op
при актуальном бинаре — секунды). Требования:

- env `PGW_TEST_E2E_NOBUILD=1` отключает автосборку (обходной путь для
  бисекта/отладки конкретного бинаря); при NOBUILD и отсутствующем бинаре —
  существующий fail-fast с сообщением о команде сборки.
- Ошибка сборки → ясный `ApplicationException` фикстуры («сборка Release
  не удалась: <хвост вывода>»), а не молчаливый запуск старого бинаря.
- Сборка — до docker-очистки и старта контейнеров (быстрый fail).
- XML-doc комментария на методе фиксирует правило и причину (маскировка
  29.08→02.09).

### Фаза Д. Регресс-защита (решение согласовано)

1. **Правило мерж-гейта** — в `AGENTS.md` проекта (pg), раздел ⚠️: задачи,
   меняющие `src/PgWorker.App|Core|Provisioning|Etcd` (и аналоги KafkaWorker),
   в мерж-гейте обязаны прогнать docker-E2E серию на свежем Release — минимум
   кейс-маркер фазы Б, полный прогон E2eFixture — при изменении
   provisioning/portalloc/moves-процессов.
2. **Финальный прогон задачи**: все E2E-кейсы PgWorker зелёные на свежем
   Release текущего HEAD (после фаз В–Г), полные юнит/интеграционные серии
   (`dotnet test`) без регрессий.
3. Roadmap-гигиена: тег `t09-e2e-release-regression` удаляется из
   `arch/roadmap/pgworker.md` тем же мерж-коммитом.

## 6. Ограничения

- Кода в spec-фазе не пишем; спека не предопределяет виновника — только
  методику его установления.
- PgWorker в E2E остаётся хост-процессами фикстуры (осознанное решение задачи
  26 — не переводим App в docker).
- Тестовые правила проекта незыблемы: динамические порты (FreePort), без
  хардкодов портов/диапазонов, короткие таймауты, `TreatWarningsAsErrors`.
- Бисект не «перематывает» уже влитые t07/t90 — работаем на текущем main;
  проверка исторического окна — в отдельном временном рабочем каталоге
  (worktree git bisect), main не трогаем.
- Обходной путь до мержа фикса (из roadmap): прогон E2E только после явной
  пересборки Release.
