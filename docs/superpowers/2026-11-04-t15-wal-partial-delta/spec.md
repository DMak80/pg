# Spec: t15-wal-partial-delta — инкрементальная доставка RPO-хвоста WAL дельтами

Пункт роадмапа: [`arch/roadmap/backup.md`](../../../arch/roadmap/backup.md),
t15-wal-partial-delta (решения владельца в пункте, вкл. п.6 «номер жизни

`arch/backups/02-wal-archive.md` + `arch/pgnode/03-wal-receiver.md` +
`arch/backups/05-etcd-contract.md` (счётчик `wal-life`) + новый процесс

внесены в дерево — источник истины).
Дата: 2026-11-04. Worktree: `worktrees/feat-t15-wal-partial-delta`.

## 1. Цель

Заменить перезаливку всего растущего префикса (t14: `.partial`-версии
каждые 3 с) ИНКРЕМЕНТАЛЬНОЙ доставкой: кумулятивная база-компак + дельты
прироста — экономия трафика и ресурса SSD хранилища. По канону:

1. **Дельта-куски** с байтовыми диапазонами в имени
   `wal/<segment>.partial_<start>_<end>_<life>_<role>_<md5>`; выкладка
   параллельно стриму; границы — только по целым WAL-записям.
2. **Разрешение пересечений** диапазонов сборкой читателя (fetch-wal):
   листинг фильтруется по текущему номеру жизни (куски чужих номеров не
   рассматриваются вовсе — ДО каскада кандидатов); порядок кандидатов:
   master над replica → более ранний start; побайтовое совпадение в
   пересечении → union (источник с бóльшим `end`); несовпадение байтов —
   алерт + режим выживания (кандидаты по возрастанию checksum, каждый
   применённый кусок сканер-проверяется, первый полностью валидный
   побеждает); сканер проверяет и CRC каждой записи (`xl_crc`) — расширение
   сканера t14; штатная сборка всегда завершается скан-валидацией.
3. **Дыра в середине покрытия** — фолбэк последней надежды: восстановить
   всё до дыры, после дыры отбросить (+алерт); «хвост не дописан» — не
   дыра, берётся закрытое покрытие.
4. **Компакция base+delta**: раз в `Wal:PartialCompactIntervalSec`
   (дефолт 1 ч) приёмник перезаливает кумулятивный префикс одним
   объектом, если был инкремент; инкременты ниже базы/финала чистит
   wal-sweeper (pgWorker).
5. **Проверки целостности**: сверка start/end из имени с фактическим
   размером объекта; Content-MD5 на put дельт; checksum куска в имени;
   подтверждение слота и RPO-инварианты — только по финалам; dual-gate
   пампа поверх дельт; листинги с пагинацией.
6. **Номер жизни цепочки** (`<life>`): счётчик per-shard в etcd
   (`/pgworker/backups/<C>/<X>/wal-life`) рядом с состоянием WAL-потока,
   единственный писатель — PgWorker; приёмник получает номер с
   конфигурацией сессии и кладёт в имя каждого куска и кумулятива;
   инкремент ТОЛЬКО при разрыве цепочки: пересоздание шарда, restore/DR в
   тот же префикс кластера, детект чужой цепочки гвардом приёмника
   (гвард фиксирует смену жизни); штатный failover/promote номер НЕ меняет;
   сборка дельт и контроль цепи фильтруют листинг по текущему номеру;
   задание restore несёт номер жизни выбранного полного; wal-sweeper чистит
   куски чужих номеров сразу, не дожидаясь cutoff; смена номера — событие
   алерта в панель.

**Цель-критерий**: restore/drill читают RPO-хвост из кусков (база+дельты)
без потери данных против t14; трафик выкладки хвоста падает с
O(кумулятив²) до O(прирост); номер жизни различает последовательные жизни
цепочки в одном префиксе (куски чужих жизней невидимы сборке/контролю и
выметаются сразу); три новых E2E (дыра / конфликт пересечений / failover
источника между дельтами) зелёные; регрессий серии нет.

### 1.1. Не-цели

- Без изменений: стоп-семантика/гейты, слоты, планировщик полных (кроме
  фиксации `chain_life` в записи полного), дубль `pg_wal` полного,
  verify-полконтроль, RestoreProcess-автомат (кроме `chain_life` заявки и
  инкремента при demolished), etcd-ключ `wal` (формат не меняется).
- В ОБЛАСТИ задачи по заданию владельца (п.6) — новые контракты: etcd-ключ
  `wal-life` (счётчик жизни), поле `chain_life` записи полного и
  restore-заявки, номер в конфигурации сессии приёмника (чтение ключа),
  событие алерта панели (`backup-wal-life-changed`). Новых Prometheus-метрик
  и новых состояний приёмника НЕТ (наблюдаемость сборки — stderr fetch-wal +
  `restored_to_lsn`; канон процесса сборки §6).
- Бюджеты не меняются: fetch-wal `CallDeadline=45 с`, транспортные
  попытки 3×2 с, breaker 45 с, `PutAttemptTimeout`, Job-бюджеты — прежние.
- P/Invoke запрещён; комментарии в коде — русские; идентификаторы —
  английские.

## 2. Принципы

- **arch-first**: правки канона внесены до кода (раздел 3); код зеркалит.
- **Инвариант RPO не ослабляется**: подтверждение слота — только после
  успешного put финала; куски никогда не двигают `restart_lsn`;
  неподтверждённое удерживается слотом. Дельты — ускоритель доставки
  хвоста, не источник гарантий.
- **Номер жизни пишет только PgWorker**: приёмник/сборка/контроль/панель
  номер только читают; инкремент — исключительное событие разрыва цепочки
  (три причины, канон 05 §1); идемпотентность инкремента на заявку/факт.
- **Идемпотентность каждого шага** (arch/17): повтор put куска тем же
  ключом — те же байты (ключ детерминирован диапазоном+md5); повтор
  прохода sweeper — идемпотентный batch-delete; повтор сборки — тот же
  результат; повторный тик bump'а — не инкрементирует (маркер
  времени/reason-гейт).
- **Один источник истины прогресса — объекты S3**: контроль считает
  покрытие по именам без чтения байтов; сборка читателя — отдельный
  процесс с собственными правилами (g-wal-delta-assembly).
- **Консервативность сканера**: любая аномалия записей (границы/CRC) —
  усечение префикса до конца последней валидной записи; короткий
  результат теряет лишь часть хвоста, финал восстанавливает полный.

## 4. Структура и компоненты (изменения по коду)

Каталоги: `src/PgWorker.Backups` (модель/воркер), `src/PgWorker.PgNode`
(приёмник, fetch-wal), `src/PgWorker.App` (конфиг), `src/PgWorker.Core` /
`src/PgWorker.Docker` (env нод), `src/PgWorker.Provisioning`
(g-add-shard), `src/AdminPanel.*` (алерт), `src/tests/*`.

### 4.1. Модель (`PgWorker.Backups/Model`)

- **`WalDeltaName`** (новый, рядом с `WalPartialName`): канон ключа
  `wal/<segment>.partial_<start>_<end>_<life>_<role>_<md5>`:
  `<segment>` 24 hex строчных; `partial_` литерал; `<start>`/`<end>` —
  LSN, РОВНО 16 hex строчных каждый; `<life>` — номер жизни цепочки
  (u32), РОВНО 8 hex строчных; `<role>` — `m`|`r`; `<md5>` — 32 hex.
  Диапазон полузакрытый `[start, end)`. Чистые функции:
  `Key(WalFileName segment, ulong start, ulong end, uint chainLife, bool
  isMaster, string md5Hex)`, `TryParse(string name)` → запись со всеми
  полями (вкл. `ChainLife`), `SegmentPrefixOf(string segmentName)` →
  `"<segment>."` (узкий префикс листинга). Длина ключа худшая ~160 байт
  (префикс `<C>/<X>/wal/` ~50 + суффикс ~110) при лимите S3 1024.
  Лексикографическая сортировка кусков сегмента = порядок по start.
- **`WalFileName.IsPartial`**: `EndsWith(".partial")` → **`Contains`**
  (кусочное имя — partial-семейство: `WalChain.Collect`, ре-доклады
  инвентаря, локальные фильтры — дельты не попадают в цепь финалов ни при
  каком парсинге).
- **`WalPrefixScanner`** — расширение CRC (решение владельца: сканер
  проверяет не только границы, но и CRC каждой записи): новая функция
  `ValidatedPrefixLength(byte[] buffer, int count)` → длина префикса до
  конца последней записи, ЦЕЛОСТНОЙ по `xl_crc`; существующая
  `ValidPrefixLength` сохраняется (границы — hot-path писателя и
  сборочные эвристики). CRC-математика: `xl_crc` — LE u32 @20 заголовка
  записи; алгоритм CRC-32C (Castagnoli, reflected-полином 0x82F63B78,
  init 0xFFFFFFFF, xorout 0xFFFFFFFF, без отражения байтов — .NET
  `System.IO.Hashing.Crc32C` недоступен без пакета: реализация таблицей,
  управляемый код); диапазон CRC — ЛОГИЧЕСКИЙ образ записи: байты
  `[pos..pos+20)` заголовка (до `xl_crc`) плюс байты `[pos+24..recordEnd)`
  (после заголовка), собираемые постранично МИНУС вставленные short
  (24 б) заголовки страниц и МИНУС MAXALIGN-добивку записи. Несовпадение
  CRC — стоп на конце последней CRC-валидной записи (консервативно).
- **`WalChain.TailOf`** — хвост = покрытие по именам (без байтов) С
  ФИЛЬТРОМ ПО НОМЕРУ ЖИЗНИ: сигнатура расширяется параметром
  `uint chainLife` (контроль передаёт текущее значение счётчика);
  candidates строятся из финала, legacy `.partial`-версий и кусков;
  куски с `ChainLife != chainLife` отбрасываются ДО каскада покрытия;
  безномерные legacy-версии учитываются ТОЛЬКО если у сегмента нет ни
  одного куска номера `chainLife` (правило переходного окна); по
  сегменту: coverage = max(end) баз (компаков и учитываемых
  legacy-версий), затем куски с `start ≤ coverage < end` расширяют
  coverage до `max(end)` (многократный проход по отсортированным по
  start кускам до фиксации); при равной позиции сегмента финал
  авторитетен.
- **`RetentionPlanner.SelectPartialForDeletion`** — кусочная гигиена
  (вход — имена листинга + текущий `chainLife`; парсится и
  `WalPartialName`, и `WalDeltaName`):
  (а) поглощено финалом сегмента — всё кусочное семейство;
  (б) куски ниже базы: `end` ≤ max(end) баз сегмента (в т.ч. все
  legacy-версии ниже лучшей базы/компака);
  (в) устаревшие базы живого сегмента: среди кусков с `start == 0`
  (компаки) остаётся длиннейшая (max end), прочие компаки — мусор;
  (г) всё кусочное семейство сегмента ниже cutoff (порог прежний);
  (д) куски чужих номеров жизни (`ChainLife != chainLife`) И
  безномерные legacy-версии сегмента, у которого есть кусок номера
  `chainLife`, — мусор НЕЗАВИСИМО от cutoff (смена жизни). Дельты выше
  базы (живое покрытие) — НЕ мусор.
- **`WalLifeStateJson`** (новый, `Job/`): сериализация значения ключа
  `wal-life` `{"chain_life","bumped_unix","reason"}` — roundtrip
  writer/reader (паттерн `BackupStatusJson`); reason — enum
  `ShardRebuilt|Restore|ForeignChain` → строки
  `shard-rebuilt|restore|foreign-chain`.

### 4.2. Приёмник: дельта-памп (`PgWorker.PgNode`)

- **`WalReceiverOptions`** + `PartialCompactIntervalSec` (int, дефолт
  3600); **`WalReceiverLoop`** читает env
  `PGW_WAL_PARTIAL_COMPACT_INTERVAL_SEC` (отсутствует/мусор → 3600;
  клэмп ≥ 60). `ServerIdentity` НЕ расширяется (tli-процедура — прежняя;
  IDENTIFY_SYSTEM как источник номера куска УДАЛЁН решением владельца).
- **`WalReceiverTargets.ResolveAsync`** — конфигурация сессии несёт номер
  жизни: новый шаг чтения ключа `/pgworker/backups/<C>/<X>/wal-life`
  (failover-перебор endpoints, паттерн `ReadPasswordAsync`); результат
  `WalReceiverTargetsResult` + `uint ChainLife` (отсутствие ключа → 0 —
  первая жизнь; транспортный отказ etcd → transient-ожидание с текстом
  (тот же класс, что policy) — ретрай следующим циклом). Перечитывается
  на КАЖДОМ цикле подключения (креды/цели не протухают — номер тоже:
  смена жизни подхватывается без пересоздания контейнера).
- **`WalReceiverCore.RunSessionAsync`** — partial-памп переписывается
  (механика канона pgnode/03 §2); номер сессии `chainLife` (из targets)
  кладётся в имя КАЖДОГО куска и кумулятива:
  - состояние пампа на сегмент: `coverage` (ulong, Volatile) — конец
    своего выложенного покрытия сессии, инициализируется по list узкого
    префикса сегмента при первом тике (union лежащего ТЕКУЩЕГО номера:
    базы+дельты по правилам TailOf-покрытия по именам; куски чужих
    номеров и безномерные legacy игнорируются — писатель не опирается на
    чужие жизни);
  - тик (таймер `PartialIntervalSec` ИЛИ сигнал прироста ≥ 4 МиБ от
    `LastAppendedLsn`): `PartialSnapshot()` → нет/null → skip;
    `EndLsn ≤ coverage` → skip (нулевым приростом куски не
    пере-выкладываются, LastModified не дёргается — «тишина» честна);
    list узкого префикса (первая доступная read-нода) → лежащий финал
    сегмента → skip навсегда (поглощение/чистка удаляют); отказ list →
    skip тика (стрим не рвём, хвост доедет следующим тиком/финалом);
    пересчёт coverage по лежащим именам ТЕКУЩЕГО номера (симметрично
    TailOf);
  - выкладка: `coverage == 0` → БАЗА-компак `[0..EndLsn)` (кусок с
    start=0); иначе ДЕЛЬТА `[coverage..EndLsn)`; put обычный (без
    гварда) с Content-MD5 (см. 4.4); байты — копия снимка префикса,
    срез `[coverage-StartOfSegment .. EndLsn-StartOfSegment)`; успешный
    put: `coverage = EndLsn`, `events.PutSuccess` (флаг
    pool_exhausted снимается — прежняя семантика);
  - **компакция**: таймер `PartialCompactIntervalSec` от первой выкладки
    сегмента (или от последней компакции); на срабатывании — если после
    последнего компакта была ≥ 1 дельта — put базы `[0..coverage')`
    ТЕКУЩЕГО номера, где `coverage'` — свежий `PartialSnapshot` (при
    нулевом приросте база не перезаливается); после компакции счётчик
    инкрементов сбрасывается; компакция НЕ удаляет дельты (чистит
    sweeper); рестарт сессии обнуляет таймеры (первая выкладка нового
    сегмента — снова база);
  - подтверждение слота не двигается (только финалы, шаг 7 сессии
    без изменений).
- **Поглощение при финале** (после успешного финального put): list
  узкого префикса `wal/<seg>.` → batch-delete ВСЕГО кусочного семейства
  ЛЮБЫХ номеров (`WalPartialName`-версии + `WalDeltaName`-куски, вкл.
  чужие жизни), best-effort; отказ — diagnostic (докладывает sweeper).
- Ре-доклады инвентаря — без изменений (`IsPartial`-фильтр теперь
  отсекает и куски).

### 4.3. fetch-wal: сборка (`FetchWalCommand`)

`FetchOnceAsync` — финальная ветка (нет финала нигде) заменяется
сборкой покрытия по процессу g-wal-delta-assembly (чистые функции —
отдельными методами для юнитов). Вход номера жизни — env
`PGW_WAL_CHAIN_LIFE` restore-команды (`ParseEnv` расширяется: отсутствие/
мусор → null — DR-orphan-режим, фильтр по номеру не активен):

1. **инвентарь**: list узкого префикса `wal/<seg>.` ПО ВСЕМ нодам
   (перебор; транспортный отказ ноды — пропуск; ни одна не ответила —
   транспортная ошибка, НЕ «конец WAL»); дедуп по имени (куски дублей
   разных нод — тот же объект);
2. **фильтры до скачивания**: парс имени (legacy `WalPartialName` —
   валидный безномерный кандидат-база); `ChainLife != входного номера` →
   отброс ДО каскада (чужие не рассматриваются вовсе); безномерные
   legacy — отбрасываются, если у сегмента есть хотя бы один кусок
   входного номера; `end − start == Size` из листинга (несовпадение —
   битый, отброс + stderr-факт); диапазон внутри сегмента;
3. **пусто после фильтров** → exit 1 (конец WAL);
4. **порядок кандидатов**: (`m` над `r`) → (start asc); база-компак
   (`start == 0`) стартует первой в своей группе;
5. **скачивание**: параллельно (константа `DeltaDownloadParallelism = 8`,
   internal), GET байтов в память с ноды, где объект числится (перебор
   до найденного); после скачивания md5 байтов сверяется с именем
   (несовпадение — битый, отброс + факт); безномерная legacy-версия
   сверяется по ETag/md5 одиночного put (GET возвращает ETag); общий
   дедлайн вызова прежний (`CallDeadline`);
6. **штатная сборка**: жадное применение от `coverage = 0` в порядке
   кандидатов: кусок применяется, если `end > coverage` и
   `start ≤ coverage` и байты пересечения `[start..coverage)` совпали с
   собранным буфером → `coverage = end`; `end ≤ coverage` — молча
   пропускается; `start > coverage` — фиксируется минимальный такой
   start (кандидат на дыру), кусок не применяется; несовпадение байтов
   в пересечении — конфликт: stderr-факт (алерт) + режим выживания;
7. **режим выживания**: пересборка с нуля, кандидаты в порядке
   ВОЗРАСТАНИЯ md5 (hex-строка, Ordinal — детерминизм; безномерные
   legacy — по ETag, при его отсутствии — после всех md5-кандидатов);
   каждый применяемый кусок сразу проверяется `WalPrefixScanner.
   ValidatedPrefixLength` на затронутой области (границы+CRC):
   несовпадение байтов пересечения ИЛИ невалидные записи после
   применения — кусок отбрасывается без ретрая; по исчерпании
   кандидатов результат — первая (единственная) полностью валидная
   сборка;
8. **дыра**: после сборки остались неприменённые куски со
   `start > coverage` (и их start меньше конца какого-то другого
   отброшенного/непригодного) — фолбэк последней надежды: результат —
   закрытое покрытие `[0..coverage)`, всё после дыры отбрасывается,
   stderr-факт (алерт); «хвост не дописан» (выше coverage кусков нет) —
   не дыра, обычный результат;
9. **результат**: собранный префикс → финальная скан-валидация
   (`ValidatedPrefixLength`, усечение при CRC-аномалии + факт) →
   `TryWritePaddedSegment` (добивка нулями до `wal_segment_size`) →
   exit 0;
10. **локальная копия набора**: `LocalSetCoversPartial` сравнивает
    последний ненулевой байт копии не с лучшей версией, а с СОБРАННЫМ
    покрытием (`coverage` после шага 6/7): копия не короче — exit 1
    (postgres читает layout сам), покрытие длиннее — отдаётся покрытие.

### 4.4. S3-клиент (`IBackupS3`/`BackupS3`)

- Новый метод `PutObjectMd5Async(string key, byte[] data, string md5Hex,
  CancellationToken)` — put с `MD5Digest` (Content-MD5, base64):
  транспорт отвергает битое (решение владельца); md5 вычисляет
  вызывающий (имя куска строится из того же значения — один расчёт).
- Новый метод `GetObjectBytesAsync(cluster, shard, key)` → `byte[]` +
  ETag (байты куска в память сборщика; существующий `GetObjectAsync` —
  текстовый, `GetObjectToFileAsync` — файловый).

### 4.5. Контроль воркера (`WalStreamProcess.ControlDueAsync`)

- чтение счётчика `wal-life` тем же тиком (текущий `chainLife`; отсутствие
  ключа → 0);
- `last_uploaded`/`last_uploaded_unix` — через обновлённый
  `WalChain.TailOf(…, chainLife)` (покрытие по именам с фильтром);
  `last_uploaded_segment` — имя сегмента без суффикса (формат etcd-ключа
  не меняется);
- непрерывность/дыры/WAL_CHAIN_ERROR — только по финалам (без
  изменений); union-листинги уже пагинированы; объём листинга с кусками
  покрывается пагинацией (юнит-инъекция `maxKeysPerTest`);
- **смена жизни по гварду**: свежий факт `failed_permanent` с причиной
  «foreign WAL chain» в статус-ключе приёмника (чтение уже выполняется
  контролем — `WalReceiverStatusReader`) → инкремент `wal-life` (см.
  4.6; reason-гейт: текущая причина счётчика ≠ `foreign-chain`; после
  инкремента — событие видно панели алертом).

### 4.6. Счётчик жизни (воркер, `PgWorker.Backups`)

- **`WalLifeStore`** (новый, `BackupNames.WalLifeKey(C, X)`):
  `ReadAsync` → `uint` (отсутствие ключа/битый JSON → 0 + diagnostic);
  `BumpAsync(cluster, shard, WalLifeReason, long startedUnix)` →
  инкремент с идемпотентностью-маркером времени: читает текущее значение,
  если `bumped_unix ≥ startedUnix` — чужой/свой свежий bump уже сделан,
  инкремента нет; иначе put `{"chain_life":N+1,"bumped_unix":now,
  "reason":…}`; для `ForeignChain` — reason-гейт: текущая reason ==
  `foreign-chain` → инкремента нет (повторный детект той же лежащей
  чужой цепочки). Пишет только держатель клэйма `<C>`.
- **`RestoreProcess`**: создание заявки — `chain_life` выбранного полного
  (из full-статуса; DR-orphan — поле отсутствует; `RestoreStatusJson` /
  `RestoreOperationState` + `ChainLife`); первый переход заявки в фазу
  `demolished` — `BumpAsync(..., Restore, startedUnix заявки)`
  (журнальная фаза — естественный идемпотентный маркер; повторные
  тики/takeover фазой `demolished`+ уже не инкрементируют).
- **`AddShardProcess`** (A1): ключ `wal-life` существует →
  `BumpAsync(..., ShardRebuilt, startedUnix процесса)` ДО старта нод;
  отсутствует — первое создание шарда, инкремента нет.
- **Планировщик полных** (`BackupPlanner`/`BackupProcess`): при создании
  записи `full/<id>` фиксирует `chain_life` текущего счётчика
  (`FullBackupState` + `BackupStatusJson` + поле `chain_life`).
- **`WalStreamProcess`**: инкремент по гварду (4.5) —
  `BumpAsync(..., ForeignChain, …)` с reason-гейтом.

### 4.7. Конфиг/env-доставка

- `BackupsOptions`/`BackupsRuntimeOptions` (воркер): +
  `Wal { PartialCompactIntervalSec = 3600 }` (биндинг
  `PgWorker:Backups:Wal:PartialCompactIntervalSec`; валидация: < 60 —
  fail-fast старта);
- `NodeBackupEnv` + `PartialCompactIntervalSec`; `Program.cs` (воркер)
  передаёт из конфига; `ClusterDriver.EnsureNode` ставит env
  `PGW_WAL_PARTIAL_COMPACT_INTERVAL_SEC` (паттерн
  `PGW_WAL_PARTIAL_INTERVAL_SEC`); значение применяется при создании
  ноды (живые ноды — дефолт 3600 приёмника);
- `RestoreOperation` (приёмник): команда POST `/api/ops/restore` +
  `chain_life` (ApiContracts); рендер restore_command → env
  `PGW_WAL_CHAIN_LIFE` процесса postgres (вместе с `PGW_S3_*`; секретов
  не несёт); `DrillProcess` передаёт `chain_life` выбранного полного
  тем же полем.

### 4.8. Панель (`AdminPanel.*`)

- `AdminPanel.Etcd` (парсер `BackupsInfo`): чтение ключей
  `/pgworker/backups/<C>/<X>/wal-life` (внутри уже читаемого range
  `/pgworker/backups/`; отдельный список, не unknownKeys; битый JSON —
  parseError-запись, толерантно; отсутствие = жизнь 0);
- `AlertEngine`: НОВОЕ правило `backup-wal-life-changed` per-shard —
  свежесть `bumped_unix` < `Alerts:Backups:WalLifeChangedSec` (дефолт
  3600; гаснет возрастом); severity по `reason`: `restore`/
  `shard-rebuilt` — info (штатная смена), `foreign-chain` — warning
  (в префиксе чужая цепочка, приёмник заморожен — разбор); reason и
  номера from→to — в тексте/атрибутах; Remedy: WorkerAuto для restore,
  OperatorRunbook для foreign-chain;
- лента событий `/events`: state-change ключа `wal-life` (change
  `chain_life` N→N+1) — автоматически из диффов снапшота (ключ в
  снапшоте).

## 5. Фазы (порядок исполнения)

- **Ф0 — arch-правки** — ВЫПОЛНЕНЫ при написании спеки (раздел 3,
  arch-first); мерж-гейт сверяет соответствие.
- **Ф1 — модель + юниты**: `WalDeltaName` (формат/парсинг/префикс, поле
  `life` 8 hex), `IsPartial`-семантика, `WalPrefixScanner.
  ValidatedPrefixLength` (CRC: эталонные байтовые фикстуры валидных/
  покорёженных записей, продолжения через страницы, MAXALIGN-добивка),
  `WalLifeStateJson` (roundtrip, reason-строки), `TailOf`-покрытие
  (база+дельты, примыкание/пересечение по именам, фильтр чужих номеров,
  безномерные до первого куска текущего номера, финал авторитетен),
  `SelectPartialForDeletion` (все ветки кусочной гигиены, вкл. (д)
  чужие/безномерные-при-наличии-текущих, cutoff=null).
- **Ф2 — писатель**: опции/env, `ChainLife` в конфигурации сессии
  (`WalReceiverTargets`), дельта-памп (база→дельты с номером, skip-правила,
  list-сверка, компакция, флаг исчерпания), поглощение семейства при
  финале; юниты с фейками IBackupS3/IXLogReplicationSource (первый кусок —
  база с номером сессии; прирост — дельта; сосед длиннее — ждём; финал —
  куски не выкладываются; компакция только при инкременте; рестарт сессии
  с новым номером — новые куски с новым номером, coverage чужих не
  наследуется; стоп-гейт гасит памп; подтверждение слота не двигается).
- **Ф3 — сборка fetch-wal**: номер из env (`PGW_WAL_CHAIN_LIFE`:
  парсинг/отсутствие → null), инвентарь/фильтр по номеру/порядок/жадная
  сборка/сверка пересечений/режим выживания/дыра-фолбэк/скан-валидация/
  локальная копия; чистые функции + интеграционная правка `FetchOnceAsync`;
  юниты (пересечение с совпавшими байтами → union; конфликт → выживание
  по md5 asc; дыра → до дыры; битые size/md5; безномерная legacy-база
  без кусков текущего номера; безномерная отбрасывается при появлении
  куска текущего номера; куски чужого номера невидимы при заданном
  номере; номер не задан (DR) — все куски кандидаты).
- **Ф4 — воркер/чистка/панель**: `WalLifeStore` (юниты: инкремент
  идемпотентен маркером времени; reason-гейт ForeignChain; отсутствие
  ключа → 0; bump от restore/add-shard не повторяется тиками),
  `RestoreProcess` (`chain_life` заявки: own-source — из full-статуса,
  DR-orphan — нет; bump при первом demolished — юнит повторного тика),
  `AddShardProcess` (bump только при существующём счётчике — юнит),
  планировщик полных (`chain_life` в full/<id> — юнит roundtrip),
  `TailOf` в контроле с фильтром номера (юнит), инкремент по гварду в
  `WalStreamProcess` (юнит: свежий foreign-chain факт → bump; повторный
  при reason=foreign-chain → нет), sweeper/ретенция кусочной гигиены
  (юнит batch-delete состава, вкл. чужие сразу + скип при активном
  restore), env-доставка (конфиг+валидация fail-fast), панель (парсер
  wal-life + правило AlertEngine — юниты: info/warning по reason,
  гашение по возрасту, молчание без ключа).
- **Ф5 — E2E-гейт**: статическая подготовка одним процессом
  (`dotnet run --project src/tests/PgWorker.E2ePrepare -c Release`),
  затем двумя отдельными командами: сборка `src/PgWorker.slnx -c
  Release`; тесты `--no-build`. Новые сценарии: (1)
  `Restore_Latest_WalDeltaHoleCoversPrefix` — прямая выкладка кусков с
  дырой в S3 + restore: данные до дыры восстановлены, после — нет, факт
  в логах; (2) `Restore_Latest_WalDeltaConflictSurvival` — куски с
  конфликтными пересечениями (порча байтов копии) → сборка режима
  выживания восстанавливает консистентный префикс; (3)
  `Restore_Latest_WalDeltaSourceFailover` — живой поток, patroni
  switchover между выкладками дельт (куски от обеих ролей ОДНОГО номера
  жизни) → restore latest доезжает до конца хвоста, номер жизни не
  меняется. Смена жизни покрыта СУЩЕСТВУЮЩИМ сценарием
  `Restore_Latest_RebuildsDestroyedShard` (пересоздание шарда): расширить
  ассерты — после restore счётчик `wal-life` инкрементирован (причина
  restore), новые куски несут новый номер, куски прежней жизни выметаются
  sweeper'ом; алерт `backup-wal-life-changed` — юнит-покрытие AlertEngine
  Ф4 (панель в E2E-контуре PgWorker не поднимается — E2E проверяет
  счётчик/куски, не панель; осознанное решение). Далее полная серия
  E2eFixture (регрессии); зачистка
  контейнеров/сетей между сериями по канону.

## 6. Ограничения

- Бюджеты не меняются молча: `CallDeadline=45 с`, попытки 3×2 с,
  breaker 45 с, `PutAttemptTimeout=15 с`, Job-бюджеты, `BrokerBootSec
  ≤ 100 с` — прежние; параллелизм скачивания кусков — НОВАЯ константа
  (8), не таймаут.
- P/Invoke запрещён; CRC-32C — управляемая табличная реализация
  (System.IO.Hashing не подключается без нового пакета — при желании
  план может использовать `Crc32C` из уже подключённых; проверяется на
  Ф1).
- Тесты docker: динамические порты, полный teardown, изоляция по канону
  AGENTS.md; никаких скипов.
- Комментарии в коде — русские (AAA в тестах), идентификаторы —
  английские; `TreatWarningsAsErrors=true`.
- Никаких отчётных .md кроме spec/plan (dev-flow файлы).
- При мерже в main — удалить пункт t15 из `arch/roadmap/backup.md` тем
  же мерж-коммитом (правило роадмапа).

Остальное — решения спеки (из канона/кода/надёжности); спорное для
владельца — легко переоткрыть на гейте user-review.

1. **Точный формат ключа куска** →
   `wal/<segment>.partial_<start:x16>_<end:x16>_<life:x8>_<role>_<md5:32>`,
   разделители `_`, все hex строчные. → [В] каркас
   `wal/<segment>…partial_<start>_<end>…` + фиксированные ширины +
   алфавит `[a-z0-9._-]`; суффикс куска лексикографически ПОСЛЕ любых
   hex-суффиксов (legacy-версий), сортировка внутри сегмента = по start.
2. **Координаты диапазонов** → абсолютные LSN (16 hex), полузакрытый
   `[start, end)`; `Size == end − start`. → Единая система координат с
   `WalPartialName.EndLsn` и `S3TailResolver`; полузакрытость даёт
   размер вычитанием — сверка из имени тривиальна [В: сверка start/end
   с размером].
3. **Источник номера `<life>`** → etcd-счётчик per-shard
   `/pgworker/backups/<C>/<X>/wal-life` (рядом с состоянием WAL-потока),
   единственный писатель — PgWorker; приёмник получает номер с
   конфигурацией сессии (чтение в `WalReceiverTargets` на каждом цикле
   подключения). Прежнее решение спеки «инкарнация = system_id из
   IDENTIFY_SYSTEM» ОТМЕНЕНО владельцем (п.6 задания): `ServerIdentity`
   не расширяется, IDENTIFY_SYSTEM-механика из задачи удалена. → [В п.6]
   дословно; счётчик в etcd переживает ноды (в отличие от system_id
   ноды), инкрементируем осознанно и редко, писатель один — гонок нет.
4. **Роль источника** → один символ `m`|`r` (primary|sync-standby) на
   момент выкладки. → [В] «роль master/replica на момент выкладки»;
   приёмник уже знает роль (REST-проба); алфавит имени допускает одну
   букву.
5. **Checksum куска** → md5 (32 hex строчных в имени; Content-MD5 на
   put; сверка после скачивания). → [В] «кандидат md5, закрыть в спеке»
   + «Content-MD5 на put дельт»: один хэш и для имени, и для транспорта;
   ETag одиночного put = md5 — порча при хранении ловится без чтения
   тела; md5 быстрее sha256 на мелких кусках. FIPS-режим не включается.
6. **Формат базы-компака** → кусок того же формата с `start = 0` (номер
   жизни/роль/md5 в имени); t14-версия `wal/<seg>.<endLsn>.partial` —
   безномерный legacy-кандидат-база переходного окна t14→t15. →
   Единый формат делает номер жизни базы видимой из имени; переходное
   окно закрыто legacy-чтением (решение 39); гигиена sweeper'а убирает
   legacy ниже базы/при появлении куска текущего номера.
7. **Первый кусок сегмента** → всегда база-компак `[0..end)` (не дельта
   от нуля чужого покрытия). → Покрытие каждой жизни автономно от 0;
   сборка не смешивает жизни молча; «конкурирующие байты исключены по
   построению» для исправного PG [В п.1 «любая склейка валидна»].
8. **Триггеры выкладки (dual-gate)** → таймер `PartialIntervalSec=3 с`
   ИЛИ накопление неподтверждённого прироста ≥ 4 МиБ; выкладывается
   ОДНА дельта всего накопленного прироста `[coverage..end)`. → [В]
   «dual-gate пампа поверх дельт» = механика t14, применённая к дельтам;
   новых настроек не вводит.
9. **Skip-правила пампа** → нулевой прирост (`EndLsn ≤ coverage`) —
   skip без list; list-отказ — skip тика; лежащий финал — куски не
   выкладываются. → Прямой перенос t14-правил «только длиннее лежащей»
   на покрытие; «тишина» контроля на idle честна.
10. **Компакция** → таймер `PartialCompactIntervalSec` (дефолт 3600) от
    первой выкладки сегмента, срабатывает при наличии ≥ 1 дельты после
    последней компакции; перезаливается база `[0..coverage')` свежим
    снимком ТЕКУЩЕГО номера; дельты компакция НЕ удаляет; рестарт
    сессии/сегмента обнуляет таймер. → [В] «раз в
    PartialCompactIntervalSec … если был инкремент»; чистка —
    исключительная прерогатива sweeper [В]; идемпотентность put базы.
11. **Границы кусков** → только по целым WAL-записям: граница выкладки —
    конец валидного префикса `WalPrefixScanner.ValidPrefixLength`. → [В]
    «любая склейка валидна»; t14-сканер уже даёт такие границы.
12. **Подтверждение слота и RPO** → только по финалам: подтверждение,
    `restart_lsn`, `S3TailResolver` — без изменений. → [В] «дельты —
    ускоритель доставки хвоста, не источник гарантий»; старт с середины
    сегмента лишил бы сборщик TLI-заголовка (t14-решение №15
    сохраняется).
13. **Сверка пересечений в штатной сборке** → всегда, между КАЖДЫМ
    применяемым куском и уже собранным буфером; совпало → union
    (`coverage = max(end)`); несовпадение — конфликт. → [В п.2]; сверка
    дешёвая (байты в памяти), детерминизм порядка делает union
    однозначным.
14. **Порядок кандидатов и фильтр жизней** → листинг фильтруется по
    текущему номеру жизни ДО каскада (чужие не рассматриваются вовсе);
    порядок: (`m` над `r`) → (start asc). → [В п.2 в ред. 8ab6a484]:
    «свежая инкарнация desc» УДАЛЕНО из задания — жизнь одна (текущая),
    сравнивать нечего; безномерные legacy — решением 39.
15. **Режим выживания** → пересборка с нуля: кандидаты по возрастанию
    md5 (Ordinal hex; безномерные — по ETag, без него — в конце), каждый
    применяемый кусок немедленно проверяется
    `ValidatedPrefixLength` (границы+CRC) затронутой области; кусок с
    несовпадением байтов пересечения ИЛИ невалидными записями
    отбрасывается без ретрая; итог — единственная детерминированная
    сборка. → [В п.2]: формализация «каждый применённый кусок
    проверяется сканером»; инкрементальная проверка эквивалентна полной
    по результату и не комбинаторна.
16. **Дыра vs «хвост не дописан»** → дыра = неприменённый кусок со
    `start > coverage` при наличии кусков выше; фолбэк: закрытое
    покрытие `[0..coverage)`, хвост после дыры отбросить; хвостов выше
    нет — обычный результат. → [В п.3] дословно; fetch-wal исполняется,
    когда источник мёртв, фолбэк легитимен всегда.
17. **Скан-валидация результата** → обязательна для ЛЮБОЙ сборки:
    `ValidatedPrefixLength` по всему префиксу; CRC-аномалия — усечение
    до последней валидной записи + факт. → [В п.2] «штатная сборка
    всегда завершается скан-валидацией».
18. **CRC-математика** → `xl_crc` = CRC-32C (Castagnoli, reflected
    0x82F63B78, init/xorout 0xFFFFFFFF) по логическому образу записи:
    `[pos..pos+20)` + `[pos+24..recordEnd)` постранично минус short
    заголовки страниц и MAXALIGN-добивка; `xl_crc` LE u32 @20. →
    Формат XLogRecord PostgreSQL; управляемая реализация; консервативное
    усечение.
19. **Контроль цепочки (хвост потока)** → покрытие ПО ИМЕНАМ без байтов
    С ФИЛЬТРОМ по текущему номеру счётчика: чужие куски не учитываются,
    безномерные legacy — только без кусков текущего номера у сегмента;
    непрерывность/дыры — только по финалам. → [В п.6] «контроль цепи
    фильтруют листинг по текущему номеру»; контроль не может качать
    байты (объём/лаг); лаг/тишина считают честное расширение.
20. **Гигиена sweeper/ретенции** → ветки (а) поглощено финалом; (б)
    кусок ниже лучшей базы; (в) устаревшие компаки — остаётся
    длиннейшая; (г) семейство ниже cutoff; (д) чужие номера И
    безномерные-при-наличии-куска-текущего-номера — СРАЗУ, без cutoff,
    КРОМЕ жизни L последнего полного шарда (`full/<id>`, последний по id;
    verify-OK не требуется; у полных без `chain_life` гейта нет): пока L —
    жизнь последнего полного, куски L НЕ выметаются — это RPO-хвост
    повторного restore/drill выбранного полного в окне до пересъёма;
    появился полный с более новой жизнью — ветка (д) для L открывается;
    дельты выше базы — живые. Вход чистки — текущий номер из счётчика и
    жизнь последнего полного; при активном restore-ключе ветка (д)
    скипается (куски жизни заявки читает fetch-wal наката), гейт жизни
    последнего полного действует и после терминала заявки. → [В п.6]
    «wal-sweeper чистит куски чужих номеров сразу»; гейт жизни последнего
    полного сужает ветку (д) до «чужих относительно ЖИВОЙ цепи»; гвард —
    расширение существующего гварда исключения restore (F §3).
21. **Листинги с пагинацией** → уже обеспечены общим кором `BackupS3`
    во всех листингах `wal/`; юнит-инъекция `maxKeysPerTest` на кусочные
    объёмы. → [В п.5]; объём между компакциями ограничен компакцией +
    поглощением финала.
22. **Content-MD5 и новые операции S3** → `IBackupS3.PutObjectMd5Async`
    (MD5Digest) для кусков; `GetObjectBytesAsync` (байты+ETag) для
    сборщика; прочие операции без изменений. → Решение владельца п.5;
    отдельные методы вместо флагов — обратная совместимость и читаемые
    тесты.
23. **Скачивание кусков параллельно** → пул 8 (константа
    `DeltaDownloadParallelism`, internal), память — куски одного
    сегмента. → Дедлайн 45 с [не меняем] при худшем ~2400 GET: пул 8 —
    секундные; дедуп по имени до скачивания.
24. **Наблюдаемость конфликтов/дыр/смены жизни** → факты сборки — stderr
    fetch-wal (postgres транслирует в лог контейнера) + честный
    `restored_to_lsn`; смена номера жизни — СОБЫТИЕ АЛЕРТА панели
    `backup-wal-life-changed` через существующий механизм (воркер пишет
    `bumped_unix`/`reason` в ключ `wal-life` → AlertEngine панели
    вычисляет алерт над etcd-снапшотом — тот же путь, что
    `backup-chain-broken`/`backup-wal-tli-gap`); НОВЫХ Prometheus-метрик
    и состояний приёмника нет. → [В п.6] «смена номера — событие
    алерта в панель»; прежнее решение спеки «панель без правок»
    отменено заданием.
25. **`IsPartial`** → `Contains(".partial")` вместо `EndsWith`. →
    Кусочные имена заканчиваются md5-hex; `WalChain.Collect` и фильтры
    инвентаря обязаны классифицировать их как partial-семейство.
26. **Валидация конфига** → `PartialCompactIntervalSec < 60` — fail-fast
    старта воркера; приёмник клэмпит к ≥ 60. → Компакция чаще минуты
    разрушает инкрементальность; симметрия §9 fail-fast (t14); приёмник
    не падает на мусорный env живой ноды.
27. **Ширина поля `<life>`** → u32, РОВНО 8 hex zero-padded. → [В]
    «фиксированной ширины zero-padded»; инкременты редки (разрывы
    цепочки), u32 = 4×10⁹ жизней с огромным запасом; ключ короче
    прежнего расчёта (~160 байт худший).
28. **Куски от второй ноды двойной архивации** → писатель НЕ выкладывает
    прирост, уже покрытый лежащими кусками ТЕКУЩЕГО номера
    (`end ≤ coverage` после list-пересчёта — skip); пересечения возможны
    только в окне гонки двух тиков — разрешаются сборкой. → Правило
    «только длиннее лежащей» t14 на покрытие; обе ноды-источники одной
    жизни (номер общий) — экономия трафика сохраняется.
29. **Кусок-дельта нулевой длины / вырожденные** → не выкладываются
    (`start == end` запрещён конструированием; skip при нулевом
    приросте). → Сверка `Size == end − start` из имени; пустые объекты
    бессмысленны.
30. **E2E-механика сценариев** → дыра и конфликт создаются ПРЯМОЙ
    выкладкой кусков в S3 тестом (BackupS3/MinIO-клиент фикстуры,
    синтетический сегмент поверх живого префикса или scratch-префикс
    restore-цели; выкладка с номером жизни текущего счётчика тестового
    шарда); failover — patroni switchover живого кластера с записью между
    дельтами; смена жизни — существующий Restore_Latest_RebuildsDestroyedShard
    с расширенными ассертами. → Детерминированная укладка без
    искусственных снов; изоляция/teardown по канону E2E.
31. **Ключ/формат счётчика `wal-life`** →
    `/pgworker/backups/<C>/<X>/wal-life`, значение
    `{"chain_life":N,"bumped_unix":T,"reason":…}`; отсутствие ключа =
    жизнь 0 (запись не создаётся); D2 deprovisioning чистит вместе с
    префиксом, remove-shard НЕ удаляет (счётчик переживает демонтаж —
    критерий пересоздания). → [В] «счётчик per-shard в etcd рядом с
    состоянием WAL-потока»: ОТДЕЛЬНЫЙ ключ (не поле wal-ключа) —
    контроль перезаписывает wal-ключ целиком каждый тик, счётчик с
    редким инкрементом жил бы в чужом цикле перезаписи; «рядом» = тот же
    per-shard префикс.
32. **Триггеры инкремента и разрыв рекурсии** → ровно три: (а)
    `shard-rebuilt` — AddShard на позиции с существующим счётчиком
    (пересоздание шарда); (б) `restore` — первый переход restore-заявки
    в фазу `demolished` (покрывает restore/DR в тот же префикс и
    восстановление разрушенного шарда; до возможного старта стрима
    восстановленных нод); (в) `foreign-chain` — свежий факт
    failed_permanent «foreign WAL chain» (гвард фиксирует смену жизни),
    с reason-гейтом: подряд два foreign-chain-инкремента невозможны
    (повторные детекты той же лежащей чужой цепочки не считают; лежащая
    цепочка та же — новая жизнь уже свежая). Инкремент идемпотентен:
    AddShard/Restore маркерят bump временем (`bumped_unix` ≥ старта
    заявки — уже сделано), foreign-chain — reason-гейтом. → [В п.6]
    «инкремент ТОЛЬКО при разрыве цепочки: пересоздание шарда, restore/DR
    в тот же префикс, детект чужой цепочки гвардом»; момент (б) — до
    старта стрима REJOINING-нод (приёмник новой сессии обязан прочитать
    уже свежий номер); после (в) заморозка гварда сохраняется (лечение —
    существующий путь восстановления/демонтажа).
33. **Полный хранит номер жизни** → поле `chain_life` в etcd-записи
    `full/<id>` (воркер фиксирует при создании записи из текущего
    счётчика) — «манифест полного» = etcd-запись полного. → [В п.6]
    «задание restore несёт номер жизни выбранного полного… полный
    обязан сохранять номер»: DR-выбор полных — по list-S3
    backup_manifest, метаданные — в etcd; S3-набор полного не
    расширяется (лишний файл ломает pg_verifybackup — manifest свериет
    каталог в обе стороны).
34. **Номер в задании restore и DR-режим** → воркер подставляет
    `chain_life` из full-статуса выбранного полного; DR-orphan (полный
    БЕЗ etcd-статуса, etcd источника стёрт) — поля нет: fetch-wal при
    отсутствии номера фильтр по номеру НЕ активирует (все куски —
    кандидаты, арбитраж — побайтовая сверка + скан-валидация + режим
    выживания, механика та же). → Задание не может нести то, чего нет в
    живых метаданных; для мёртвого источника «текущего номера» не
    существует (счётчик умер вместе с кластером) — фильтр жизней
    механика ЖИВОГО контура; сборка деградирует корректно (чужие байты
    ловит сверка).
35. **Доставка номера в fetch-wal** → env `PGW_WAL_CHAIN_LIFE` процесса
    postgres (рендер restore-команды; вместе с `PGW_S3_*`); restore и
    drill передают `chain_life` выбранного полного полем команды
    POST /api/ops/restore. → Существующий канал параметров
    restore_command (секреты не в argv — номер не секрет, но канал
    один); отсутствие env = DR-режим (решение 34).
36. **Фильтр номера в TailOf** → сигнатура `TailOf` расширяется
    параметром `uint chainLife` (контроль передаёт значение счётчика);
    сигнатура кусочного Sweeper/RetentionPlanner — аналогично. → [В]
    «сборка дельт и контроль цепи фильтруют листинг по текущему номеру
    (чужие отбрасываются до каскада)» — фильтр обязан быть общим
    элементом всех потребителей листинга.
37. **Гонка «bump во время живой сессии»** → куски, выложенные приёмником
    со СТАРЫМ номером до инкремента, после инкремента становятся чужими:
    контроль их не видит, sweeper выметает; RPO не страдает (гарантии —
    финалы; сессии с двумя номерами не смешиваются в сборке). → Все три
    триггера bump'а сопровождаются разрывом/перезапуском сессий
    (demontаж нод, заморозка гварда); окно гонки короткое и безопасное.
38. **Панельный алерт** → `backup-wal-life-changed`: зажигается свежестью
    `bumped_unix` < `Alerts:Backups:WalLifeChangedSec` (дефолт 3600),
    гаснет возрастом (событие, не перманентное состояние — смена при
    restore штатна); severity: info (restore/shard-rebuilt), warning
    (foreign-chain — приёмник заморожен, нужен разбор). → Существующий
    механизм AlertEngine над etcd (прецеденты `backup-wal-tli-gap`,
    `backup-deleting-stuck` с возрастным порогом); алерт не спамит
    (одна запись ключа — один час видимости).
39. **Безномерные t14-версии (переоткрытое решение №6)** →
    учитываются (покрытие контроля, сборка fetch-wal, гигиена как
    «лучшая версия» прежним порядком t14) ТОЛЬКО пока у сегмента НЕТ
    кусков текущего номера жизни; появился кусок текущего номера —
    безномерное семейство сегмента перестаёт учитываться и выметается
    sweeper'ом сразу (класс «чужих»). → Переходное окно t14→t15 (живые
    сегменты с версиями t14 на момент обновления): RPO-хвост обязан
    быть видим до первой выкладки базы нового номера, иначе наблюдаемость
    и сборка теряют хвост; после появления куска текущего номера база
    `[0..end)` покрывает всё, что давали legacy-версии — дубль смысла не
    несёт; вариант «безномерные = чужие всегда» ломает переходное окно,
    вариант «безномерные = равноправные» смешивает старую жизнь с новой
    (имена сегментов TLI совпадают при пересоздании).
40. **Куски чужих жизней в S3-инвентаре панели** → карточка «Место»
    честно включает их до зачистки sweeper'ом (панель пишет/чистит
    ничего нового). → Инвентарь — live-факт; чистка — домен sweeper
    (ветка (д) гигиены).

## 8. Критерии приёмки

1. **Канон соответствует коду**: все файлы раздела 3 в дереве, ревью
   сверяет механику писателя/сборки/гигиены/счётчика с arch (arch-first).
2. **Инкрементальность**: при живой записи в `wal/` появляется
   база-компак `[0..end)` и далее ТОЛЬКО дельты прироста (юнит:
   последовательность объектов = база + дельты с растущими start;
   суммарный трафик выкладки ≈ суммарный прирост байт); компакция раз в
   интервал при наличии инкремента (юнит таймера).
3. **Номер жизни** (юниты): инкремент ТОЛЬКО при разрыве — restore
   (первый demolished), пересоздание шарда (счётчик существовал),
   foreign-chain (свежий факт + reason-гейт); штатный стрим, рестарт
   сессии, tli-процедура, failover/promote номер НЕ меняют (юнит
   WalLifeStore: лишние вызовы Bump не инкрементируют); приёмник кладёт
   номер сессии в имя каждого куска/компака (юнит Ф2); идемпотентность
   повторных тиков (юнит).
4. **RPO-инвариант не ослаблен**: подтверждение слота — только после
   финальных put (юнит: confirmed == EndLsn финала при активных
   дельтах); приёмник продолжает работать при недоступности S3
   (backpressure, слот держит).
5. **Сборка читателя** (юниты на чистых функциях + E2E):
   - непересекающиеся дельты поверх базы склеиваются до конца хвоста;
     postgres принимает собранный сегмент (restore latest доезжает до
     строк, закоммиченных после полного, без закрытия сегмента);
   - пересечение с совпавшими байтами → union;
   - конфликт байтов → алерт-факт + сборка режима выживания валидна;
   - дыра → покрытие до дыры, хвост отброшен, факт в логах;
   - битые куски (size ≠ end−start; md5 ≠ имени) отброшены с фактом;
   - куски чужого номера НЕ рассматриваются при заданном номере (юнит);
     номер не задан (DR) — все куски кандидаты (юнит);
   - сборка всегда заканчивается CRC-валидацией (усечение префикса).
6. **Failover источника между дельтами** (E2E): куски ролей `m`/`r`
   ОДНОГО номера жизни собираются в непрерывный хвост; restore latest
   зелёный; счётчик жизни не изменился.
7. **Смена жизни при пересоздании шарда** (E2E
   Restore_Latest_RebuildsDestroyedShard): после restore счётчик
   инкрементирован (reason restore); новые куски несут новый номер;
   куски прежней жизни выметаются sweeper'ом; задание restore несло
   номер выбранного полного (fetch-wal собирал хвост жизни полного).
8. **Гигиена**: sweeper одним batch-delete удаляет куски ниже
   базы/финала/cutoff, устаревшие компаки и чужих номеров/безномерные-
   при-наличии-текущих (СРАЗУ, без cutoff), НЕ трогая живое покрытие
   (юнит); при активном restore ветка чужих номеров скипается (юнит);
   финал поглощает семейство best-effort (юнит приёмника).
9. **Контроль**: `last_uploaded`/lag/тишина считаются по покрытию кусков
   с фильтром по текущему номеру (юнит TailOf с чужими кусками);
   ложных WAL_CHAIN_ERROR нет; листинги пагинированы.
10. **Панель**: алерт `backup-wal-life-changed` — info на restore,
    warning на foreign-chain, гаснет по возрасту, молчит без ключа
    (юнит AlertEngine; панель в E2E-контуре PgWorker не поднимается —
    алерт E2E-ится осознанно НЕ); лента /events отражает смену N→N+1
    автоматически (ключ `wal-life` в снапшоте, клиентские диффы
    prev→next — arch/adminpanel/02 §5; отдельной проверки не требует).
11. **Нет регрессий**: полная серия E2eFixture зелёная (внеобластные
    фейлы — роадмап bugs.md, не фикс здесь); юниты PgWorker.* зелёные;
    сборка Release без ворнингов.
12. **Мерж-гейт**: пункт t15-wal-partial-delta удалён из
    `arch/roadmap/backup.md` тем же мерж-коммитом; `← t15`
    зависимостей других пунктов нет (проверить grep).

## 9. Риски и их закрытие

| Риск | Закрытие |
|---|---|
| Число объектов `wal/` между компакциями (~2400 на живой сегменто-час ×2 писателя) | Компакция раз в час + поглощение финалом; листинги пагинированы; узкие префиксы в пампе/sweeper/fetch-wal |
| Сборка не укладывается в `CallDeadline=45 с` при худшем числе кусков | Параллельное скачивание (пул 8), дедуп имён до скачивания, фильтр size по листингу без GET; дедлайн НЕ меняется |
| CRC-реализация разошлась с PG (порядок байтов, диапазон) | Эталонные байтовые фикстуры Ф1 (записи реального WAL из E2E-контура); консервативное усечение теряет только хвост, финал восстанавливает |
| Смешение жизней в префиксе (гвард финалов не успел/окно перехода) | Номер жизни в имени каждого куска + фильтр листинга до каскада; сборка не смешивает молча; байтовая сверка + режим выживания + CRC-сканер — арбитраж |
| Рекурсия инкрементов foreign-chain (гвард гибнет повторно на той же чужой цепочке) | Reason-гейт: подряд два foreign-chain-bump невозможны; повторные детекты молчат; смена жизни фиксируется один раз |
| Куски старого номера от гонки «bump посреди живой сессии» | После bump они чужие: контроль не видит, sweeper выметает; RPO — по финалам; окно короткое (триггеры bump'а рвут сессии) |
| Sweeper выметает куски жизни restore-заявки до конца наката | Гвард исключения restore: ветка чужих номеров скипается при активном restore-ключе (F §3) |
| DR-orphan без номера: смешение кусков всех жизней источника | Фильтр off — арбитраж побайтовой сверки + скан-валидация + режим выживания (механика не ослаблена); диапазоны чужих жизней ниже wal_start полного перекрыты финалами/полным |
| Двойное пересоздание шарда (remove+add дважды): вторая жизнь = номер первой | Маркер времени: bump второй заявки валиден (bumped_unix < её старта); счётчик не «залипает» на причине (reason-гейт — только у foreign-chain) |
| Память сборщика (куски сегмента в памяти) | Короткоживущий процесс restore_command; десятки МиБ; добивка на диск сразу после валидации |
| Самоперекрытие кусков писателем после рестарта сессии | coverage реинициализируется list'ом лежащего семейства ТЕКУЩЕГО номера; дельта от фактического покрытия; идемпотентный put того же ключа |
| Компакция чаще инкрементов (пустые перезаливы) | Гейт «была ≥ 1 дельта после последней компакции» (юнит) |
| Legacy t14-версии живых сегментов на момент обновления | Правило решения 39: безномерные видны только до первого куска текущего номера; sweeper выметает после; окно закрывается первой выкладкой базы |
