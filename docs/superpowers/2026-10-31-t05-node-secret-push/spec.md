# t05-node-secret-push — нода без секретов в env: доставка от воркера через агента (PgNode)

Спецификация Фазы 1 (dev-flow). Источник истины — `arch/` (arch-first правки
этой задачи уже внесены в worktree: arch/14 §2.1/§3.2/§4/§5 C/§5 I,
arch/13 §2/§4/§5/§6, arch/18 §2.8/§5, arch/19, arch/25 — см. §10).
Этот документ не пересказывает arch/, а фиксирует объём, решения и приёмку.

---

## 1. Цель

Контейнер PG-ноды кластера создаётся БЕЗ секретов в env: `docker inspect`
ноды не раскрывает ничего конфиденциального (сегодня там PGPASSWORD_*,
PEM-серты, SPILO_CONFIGURATION с rest_password, DOORMAN_CONFIG с
SuPassword). Секреты доставляет агент ноды:

- supervisord автостартует ТОЛЬКО агента (программа `pgnode`); spilo и
  pg_doorman — `autostart=false`, их поднимает агент после рендера конфигов;
- агент (переименованный компонент **PgNode**, прежнее имя
  walreceiver) забирает per-cluster/пер-нодовые данные из etcd сам, а два
  per-install пароля PG получает прямой передачей от воркера по mTLS-каналу;
- воркер — единственный инициатор канала; нода про PgWorker ничего не знает
  и ничего не инициирует;
- PgNode — менеджер пулера: ведёт конфиг/серты pg_doorman, применяет
  замены по сигналу воркера (семантика применения — по материалу,
  решение 29);
- ротация per-cluster секретов — порядок ETCD-FIRST: NEW в etcd в
  начале окна, rolling-применение нод (rest_password — без пересоздания
  контейнеров и без рестарта Patroni: перезапись bootstrap-данных +
  команда применения → reload Patroni, решение 29), финальный ALTER
  pg_authid последним.

В ту же задачу входит переименование компонента walreceiver → **PgNode**
(решение пользователя): у агента уже много обязанностей (приём WAL, mTLS-
сервер, менеджер doorman, доставка секретов, рендер конфигов, старт
spilo/pg_doorman), а не только работа с WAL.

Ненулевые цели (анти-цели): не менять механику приёма WAL (arch/19),
порт-аллокацию, процессы переездов бакетов, модель данных кластера; не
вводить второй etcd-контур или внешние secret-manager'ы (t02 — отдельная
задача); не реализовывать шифрование секретов на диске (кэша на диске нет
вовсе — п. 8.7).

## 2. Принципы

1. **Arch-first**: канон — arch/14 §4 («Доставка секретов в ноду»), §2.1,
   §3.2 (ключ bootstrap), §5 C (шаг конвергенции), §5 I (ротация);
   arch/13 §2/§4/§5/§6 (firewall-строка, серт-схема, экспозиция); arch/25
   №23 (канал доставки); arch/18 (Meter/джоба/file_sd). Код зеркалит их.
2. **Инициатор — всегда воркер**: нода не инициирует коммуникацию к
   воркеру. Чтение агентом etcd — пассивное получение данных (канон
   приёмника: гейты/цели/креды он уже читает сам), не «инициатива».
3. **Нет кэша секретов на диске** (решение пользователя): секреты живут
   только в tmpfs `/run/pgw` (память контейнера, 0600) и в памяти
   процессов; рестарт контейнера — секреты утрачены, нода НЕ поднимается
   сама — воркер тиком доставляет заново. Осознанная граница: нода без
   воркера не перезапускается.
4. **Per-install пароли PG не попадают ни в etcd, ни в docker-env** (Д7 —
   arch/14 §4 гр.2 сохраняется): только прямая передача по mTLS-каналу.
5. **Одна модель доставки** — легаси-кластеров с секретами в env нет
   (система в разработке, решение пользователя): без волн миграции,
   без маркеров поколения, без двойной поддержки сборки env.
6. Идемпотентность каждого шага (arch/17): повторный push/сигнал/put
   безопасны; конвергенция — тиком надзора.
7. Бюджеты (таймауты) существующих фаз не меняются; новые сетевые вызовы —
   в рамках тика (~5 с) и существующих HttpClient-таймаутов (10 с).

## 3. Структура: целевое состояние компонентов

### 3.1. Docker-env контейнера ноды (только неконфиденциальное)

Остаются (значения не секретны):

| env | Зачем |
|---|---|
| `SCOPE`, `ETCD3_HOSTS`, `PGW_ETCD` | идентификация Patroni-DCS и адреса etcd |
| `PGW_MASTER_KEY`, `PGW_NODE_HOST`, `PGW_NODE_NAME`, `PGW_DOORMAN_PORT` | lease-скрипт мастер-ключа (P11) |
| `USE_DATA_DIR_FOR_WAL` | пути Spilo |
| `PGW_BACKUP_CLUSTER/SHARD/NODE`, `PGW_BACKUP_S3_BUCKET/CA_PEM/STAGING_DIR` | идентичность агента PgNode и цели бэкапов (arch/19 §7) |
| `SSL_RESTAPI_CA` | публичный CA REST-слоя (верификация клиентами без hostname — arch/13 §4); также им пользуется REST-проба роли агента |
| `DOORMAN_CONFIG_TEMPLATE` | шаблон конфига пулера с плейсхолдером пароля (п. 3.5) |
| `PGW_AGENT_CLIENT_CA` | публичный CA верификации клиентских сертов воркера на mTLS-канале `:8081` |
| `PGW_NODE_TOOL` | tool-режим (t26), без изменений |

Удаляются из env (секретны или несут секреты): `PGUSER_SUPERUSER`,
`PGPASSWORD_SUPERUSER`, `PGUSER_STANDBY`, `PGPASSWORD_STANDBY`,
`PGW_BUCKET_ADMIN_USER`, `PGW_BUCKET_ADMIN_PASSWORD`,
`PGW_BUCKET_MOVER_PASSWORD`, `SSL_RESTAPI_CERTIFICATE`,
`SSL_RESTAPI_PRIVATE_KEY`, `PGW_REST_PASSWORD_HASH`,
`SPILO_CONFIGURATION`, `DOORMAN_CONFIG` (заменён шаблоном).
Потребителей bucket-паролей внутри контейнера нет (проверено grep'ом —
их читает только сам воркер из своего env); SuPassword/StandbyPassword
получает агент по каналу (п. 3.4).

### 3.2. Образ ноды (docker/node)

- `supervisord.conf`: `[program:pgnode]` — единственный с автостартом;
  `[program:spilo]`, `[program:pg_doorman]` — `autostart=false`
  (паттерн надёжности прежний: рестарты только падений проработавшего
  процесса, старт-отказ — без ретраев). Конфиг pg_doorman — позиционный
  аргумент `/run/pgw/doorman/pg_doorman.yaml`; `user=postgres`.
- `docker-entrypoint.sh`: проверки fail-fast (бинарник doorman,
  непустой `DOORMAN_CONFIG_TEMPLATE`) остаются; openssl-генерация
  self-signed серта пулера УДАЛЯЕТСЯ (серт доставляет агент); написание
  `pgw-node.env` (неконфиденциальное) и CA-файла — без изменений;
  tool-ветка `PGW_NODE_TOOL=1` — только новый путь бинаря.
- `spilo-supervised.sh` (обёртка spilo): перед штатной логикой —
  экспорт секретных env ПРОЦЕССА из tmpfs-файлов агента: `set -a; .
  /run/pgw/spilo-env; set +a` + `export SPILO_CONFIGURATION="$(cat
  /run/pgw/spilo-configuration.yml)"`, `export
  SSL_RESTAPI_CERTIFICATE=…`/`SSL_RESTAPI_PRIVATE_KEY=…` из файлов.
  Файлов нет (доставка не выполнена) — немедленный отказ старта с
  диагностикой «ожидается доставка от воркера» (supervisord не лупит:
  старт — только по команде агента).
- Пути бинаря агента: `/opt/pgw-wal/walreceiver` → `/opt/pgw-node/pgnode`
  (Dockerfile: build-arg `WAL_PUBLISH_DIR` → `PGNODE_PUBLISH_DIR`, COPY,
  chmod; скрипты сборки образов в `src/tests/PgWorker.E2ePrepare` —
  синхронно).
- Docker-спецификация контейнера: tmpfs-монтаж `/run/pgw`
  (`rw,noexec,nosuid,size=16m`) — добавляется в ContainerSpec драйвера
  (plain и swarm-шаблон).
- `restore_command` (arch/19 §3.5): `/opt/pgw-node/pgnode fetch-wal %f %p`.

### 3.3. Bootstrap-ключ etcd (пер-нодовый, пишет ТОЛЬКО воркер)

`/clusters/<C>/shards/<X>/nodes/<n>/bootstrap` — JSON:

```json
{
  "spilo_configuration": "<string, НЕпустой YAML SPILO_CONFIGURATION (rest_password внутри)>",
  "cert_pem": "<string, НЕпустой PEM серта ноды>",
  "key_pem": "<string, НЕпустой PEM ключа>"
}
```

Три поля — других нет; валидность для старта (агент): пара cert/key
парсится X509-провайдером, YAML непуст; невалидный/битый ключ агент
перечитывает (воркер перезапишет). Канон — arch/14 §3.2.

- Серт ноды — ОДИН на три серверные роли: REST `:8008` (Spilo),
  pg_doorman `:6432`, mTLS-листенер агента `:8081`. Выпускает воркер из
  per-install REST-CA (`PGW_REST_TLS_CA/CA_KEY`) через существующий кеш
  `RestCertificateCache` (SAN — канон arch/14 §2.4 п.6: короткий alias,
  полное имя `pgw-<C>-<X>-<n>`, IP `127.0.0.1`).
- Ключ пишется каждым EnsureNode-путём (provision P-фазы, add-shard,
  надзор-ensure/rebuild, усыновление — НЕ для `object`-нод) и при ротации
  `rest_password`; удаляется с префиксом кластера (D2) и ноды (S3).
- Класс экспозиции — per-cluster секреты (etcd без per-key ACL), класс не
  расширяется: `rest_password` и серты уже имели этот класс.
- Ревизия применения — `mod_revision` ключа; применённая ревизия
  публикуется агентом в статусном ключе (`applied_revision`, п. 3.6) —
  воркер сверяет в тике, не опрашивая ноду.

### 3.4. Канал доставки (mTLS, `:8081`, инициатор — воркер)

- Листенер Kestrel `https://0.0.0.0:8081` рядом с существующим
  `http://0.0.0.0:8080` (второй листенер того же процесса PgNode); порт
  внутри docker-сети кластера, на хост НЕ публикуется.
- ГРАНИЦА КАНАЛА — ПОРТ (MR-ревью #1): маршруты `/api/bootstrap*`
  обслуживаются ТОЛЬКО листенером `:8081`; по plaintext `:8080`
  (metrics/ops-API) — `404`. Единый роутер процесса границей доверия
  не является: иначе любой контейнер docker-сети подсовывает пароли в
  окне `not_initialized`.
- Серверный серт листенера — `cert_pem/key_pem` из bootstrap-ключа:
  агент при старте читает ключ сам (канон: чтение etcd — не инициатива),
  поднимает листенер и ждёт доставки паролей; etcd недоступен —
  внутренний ретрай-цикл чтения (листенер поднимется по появлении ключа).
- Клиентская верификация (MR-ревью #5): `ClientCertificateMode.
  RequireCertificate`, валидатор — публичный CA из docker-env
  `PGW_AGENT_CLIENT_CA` (это тот же per-install REST-CA: его публичная
  часть) + **EKU ClientAuth + CN=pgworker** — серверные серты нод того
  же CA клиентом канала НЕ являются (иначе компрометация одной ноды
  открывала канал ко всем). Отдельный клиентский валидатор канала —
  по прецеденту roadmap t04; общий TlsChain.ValidateChain не трогаем.
- Клиентский серт воркера: выпускает сам воркер при старте из REST-CA
  (RestPki, EKU ClientAuth, CN по роли), кеш процесса; верифицирует
  серверный серт агента по CA и SAN имени ноды (воркер ходит по alias в
  docker-сети кластера — `EngineFor(host)` того хоста, где контейнер).
- Эндпоинты (оба — только для клиента с валидным сертом воркера; статус
  ноды воркер читает из etcd — п. 3.6, канал только команды):
  - `POST /api/bootstrap` (команда доставки, хендшейк старта) — тело
    `{"su_password": "...", "standby_password": "...", "is_tool_start":
    false}` (`is_tool_start` — умолчание false; true — tool-контур,
    п. 3.6-3). Агент получает
    и ПРОВЕРЯЕТ все аргументы (пара паролей непуста + bootstrap-ключ
    etcd читается и валиден: серты парсятся, YAML непуст) и атомарно
    переводит статус `not_initialized → initializing` (txn etcd compare
    по value — п. 3.6). Состояние уже НЕ `not_initialized` — команда
    повторно НЕ отрабатывает: ответ `200 ok` («пинок состоялся»), без
    действий. Неполные/невалидные аргументы — `400` с диагностикой,
    статус остаётся `not_initialized` (воркер ретраит тиком); `503` —
    etcd недоступен агенту.
  - `POST /api/bootstrap/apply` (команда применения, ТОЛЬКО для
    `ready`-ноды — ротации/замены, тело пустое): агент перечитывает
    bootstrap-ключ, при изменении ревизии — перерендер и точечное
    применение (п. 3.6); ответ `200 ok`. На не-`ready` ноде — `409`
    (воркер не шлёт: он различает состояния по статусу).
- HTTP-коды канала — ЗАКРЫТЫЙ набор (канон arch/25 №23): доставка
  `200` (принято/`ok`-пинок) | `400` (аргументы неполны/невалидны —
  статус не меняется) | `503` (etcd недоступен агенту); применение
  `200` (принято, применение/публикация статуса — фон) | `409` (нода
  не `ready`) | `503`.
- Тело запроса с per-install паролями существует только в TLS-канале и
  памяти агента: в логи не пишется (как и значения env — существующий
  паттерн «значения в тексты ошибок не включаются»).

### 3.5. Рендер конфигов агентом (tmpfs `/run/pgw`, 0600, postgres)

| Файл | Источник | Потребитель |
|---|---|---|
| `/run/pgw/spilo-env` | `PGUSER_SUPERUSER=postgres`, `PGPASSWORD_SUPERUSER=<push>`, `PGUSER_STANDBY=standby`, `PGPASSWORD_STANDBY=<push>` (пары KEY=VALUE, экранирование значений — GenerateEnvironmentVariable) | обёртка spilo (export) |
| `/run/pgw/spilo-configuration.yml` | `spilo_configuration` из bootstrap-ключа | обёртка spilo (export SPILO_CONFIGURATION) |
| `/run/pgw/rest-cert.pem`, `/run/pgw/rest-key.pem` | `cert_pem`/`key_pem` | обёртка spilo (export SSL_RESTAPI_*) |
| `/run/pgw/doorman/pg_doorman.yaml` | `DOORMAN_CONFIG_TEMPLATE` из docker-env с заменой плейсхолдера `${PGW_SU_PASSWORD}` на пароль из push | pg_doorman (аргумент командной строки) |
| `/run/pgw/doorman/tls.crt`, `tls.key` | `cert_pem`/`key_pem` | pg_doorman (пути в конфиге) |

`DOORMAN_CONFIG_TEMPLATE` рендерит воркер: `DoormanConfigBuilder.Build`
меняет сигнатуру — пароль убирается, вместо него литеральный плейсхолдер
`${PGW_SU_PASSWORD}` (конфиг детерминирован между reconcile'ами; бюджет
P15 и формат v3.11.0 — без изменений; InstallSecretsGuard остаётся
гвардом алфавита для подстановки в YAML-строку).

### 3.6. Статусная машина агента и хендшейк старта (цикл жизни)

**Статусный ключ etcd** — `/pgworker/nodes/<C>/<X>/<N>/status` (arch/14
§3.3): пишет ТОЛЬКО агент lease-сессией TTL 15 c / keepalive 5 c (паттерн
статуса приёмника `/pgworker/backups/.../agent/<N>` — смерть процесса
гасит ключ, статус не «застревает»); воркер читает-мониторит poll-тиком;
панелью не разбирается. Значение:

```json
{"state":"not_initialized|initializing|ready|start_failed",
 "applied_revision": <mod_revision>|null,
 "components":{"pg":"starting|ready|failed|stopped|prepared",
               "doorman":"starting|ready|failed|stopped|prepared"},
 "updated_unix":N, "error"?:"<однострочная диагностика без секретов>"}
```

Закрытые множества и правила присутствия полей (канон — arch/14 §3.3,
фактический код `PgNodeStatus`/`PgNodeMachine`):

- `state` — ТОЛЬКО `not_initialized|initializing|ready|start_failed`;
- `applied_revision` — null в `not_initialized` и `initializing`;
  = `mod_revision` применённого bootstrap-ключа в `ready`, а также в
  `start_failed`, когда сбой произошёл после начала применения (рендер,
  старт компонентов, применение замен);
- `components` — фиксированный набор ключей `pg` и `doorman` (других
  компонент нет); значение каждой — ТОЛЬКО из
  `starting|ready|failed|stopped|prepared` (`starting` — фаза
  старта/ожидания SELECT 1; `ready` — SELECT 1 успешен (не используется
  в tool-пути); `failed` — исчерпаны 3 попытки старта; `stopped` — не
  запускался (рендер-ошибка/применение); `prepared` — параметры готовы,
  запуск за tool-командой (`is_tool_start=true`, обе компоненты)); в
  `not_initialized` и сразу после txn-перехода в `initializing` —
  пустой объект `{}`;
- `error` — null/отсутствует всегда, кроме `start_failed` (причина
  сбоя) и `ready` после упавшего применения замены (факт в `error`,
  машина остаётся `ready`).

Машина: `not_initialized → initializing → ready | start_failed`
(решение пользователя, arch/14 §4).

1. **Старт процесса** (supervisord): identity из docker-env (невалидный
   набор — прежний старт-отказ exit 1); mTLS-листенер `:8081` поднимается
   после успешного чтения bootstrap-ключа (серт листенера оттуда; etcd
   недоступен — внутренний ретрай-цикл чтения); HTTP `:8080` — как
   сейчас. Готов принимать ключи → публикация `not_initialized`.
2. **Хендшейк**: воркер мониторит статус (надзорный тик / фаза
   provisioning), видит `not_initialized` → put bootstrap-ключа (при
   устаревании) + `POST /api/bootstrap` с per-install паролями. Агент
   проверяет аргументы и атомарно (txn etcd `[compare
   state==not_initialized] [put state=initializing]`) переводит машину;
   compare проигран — `200 ok` («пинок состоялся») без действий; провал
   проверки аргументов — `400`, статус не меняется.
3. **initializing** — ДВЕ независимые фазы (уточнение пользователя —
   не смешиваются):
   - **(а) старт процессов компонентов** (`is_tool_start=false`,
     умолчание): агент рендерит tmpfs-файлы (3.5) и стартует компоненты
     (`supervisorctl start pg_doorman`, `start spilo` — параллельно) с
     надзором СТАРТА ПРОЦЕССА: процесс упал при старте — перезапуск, ДО
     3 попыток на компонент; исчерпаны — компонент `failed`
     (`components.<x>="failed"`), ОСТАЛЬНЫЕ компоненты не блокируются.
     `is_tool_start=true` (команде предварительный запуск не нужен —
     tool-контур, напр. restore): агент ТОЛЬКО готовит параметры
     запуска (tmpfs-файлы 3.5), компоненты НЕ запускает — запуск и его
     ретраи выполняет сама tool-команда. Терминальный успех ЭТОГО пути
     (уточнение пользователя) — подготовленность ПАРАМЕТРОВ, не select 1:
     успешный рендер всех tmpfs-файлов → **ready** («инициализирована —
     параметры готовы»; `components.<x>="prepared"`, фаза (б) select 1
     в этом пути агентом НЕ выполняется — контроль старта/готовности
     компонентов — зона tool-команды и её владельца, их статусы —
     штатные статусы ops-API/arch/19 §3.5/§3.6); ошибка рендера →
     **start_failed** (потребитель статуса — владелец tool-контура;
     общий надзор restore-шарды не пересоздаёт — §5 C-гварды).
     Штатный порядок: «сначала старт компонентов, потом доп
     tool-команды» — команды без `is_tool_start` идут по готовности
     компонентов.
   - **(б) ожидание готовности — БЕЗ бюджета**: проба `SELECT 1` со
     стороны ноды: PG — `127.0.0.1:5432` под postgres/SuPassword;
     doorman — клиентский вход `:6432` (`sslmode=require`) под
     app-ролью (app_password — per-cluster ключ etcd, читает агент;
     проверяет и цепочку auth_query). Живой процесс может
     инициализироваться долго (восстановление из бэкапа) — таймаута
     инициализации НЕТ: select 1 ждёт готовности сколь угодно долго;
     бюджеты владельцев процессов (фазы provisioning/restore воркера) —
     свои, без изменений.
   Итог (оба пути): все компоненты готовы (`is_tool_start=false`) ИЛИ
   параметры подготовлены (`is_tool_start=true`) → **ready**
   (`applied_revision` = mod_revision применённого ключа); компонент
   `failed` — исчерпание 3 попыток фазы (а) агентского запуска, либо
   ошибка рендера параметров в tool-пути → **start_failed** (+`error`);
   ошибки СТАРТА компонентов в tool-пути — зона tool-команды/её
   владельца (агент не отслеживает).
4. **Ротации/замены на ready-ноде**: `POST /api/bootstrap/apply` — агент
   перечитывает bootstrap-ключ; ревизия изменилась → перерендер и
   точечное применение ПО МАТЕРИАЛУ (решение 29): `spilo_configuration`
   изменился → rest-пара: reload Patroni (SIGHUP процессу patroni ИЛИ
   REST POST /reload — эквивалентны; PG не останавливается, рестарт
   Patroni-процесса/контейнера для пароля запрещён); перегенерация
   /run/postgres.yml идёт с env SSL_RESTAPI_CERTIFICATE_FILE/
   SSL_RESTAPI_PRIVATE_KEY_FILE = пути рест-серт ноды /run/certs/* —
   без них configure_spilo теряет restapi certfile/keyfile и первое
   перечитывание пересоздаёт REST-листенер в plain (t05probe2, arch/14
   §5 I); rest-серт:
   рестарт Patroni-программы (reload SSL-материал не применяет —
   patroni 4.1.0; PG ноды останавливается на секунды рестарта, Patroni
   усыновляет локальный PG по DCS) — только на РЕПЛИКЕ; мастер сертом
   агентом не применяется — его пересоздаёт воркер (R3-серт,
   arch/14 §5 I); только doorman-файлы → `restart pg_doorman`;
   машина остаётся `ready`, обновляется `applied_revision`. Ревизия
   без изменений — no-op. Неудавшееся применение (сбой команды — факт в
   `error`, ревизия старая) агент ПОВТОРЯЕТ САМ: фон-задача применения
   циклит ретрай с паузой анти-дребезг-коулдауна до успеха/смены
   материала/остановки процесса; коулдаун гейтится МАТЕРИАЛОМ
   (отпечаток YAML+серт+ключ), не ревизией — переписывание ключа тем же
   контентом (растущий mod_revision) коулдаун не снимает; ключ, переписанный
   тем же контентом, догоняется фиксацией ревизии без рестартов.
5. **Рестарт контейнера/смерть агента** (кто угодно): tmpfs и память
   пусты, lease истёк — ключ исчез; новый процесс публикует
   `not_initialized` → хендшейк заново (данные PG в volume переживают:
   initializing завершается штатным стартом PG по существующему PGDATA).
6. Стрим WAL (WalReceiverLoop) и операции бэкапов живут как раньше:
   их гейты/цели — из etcd, от машины состояний не зависят (до доставки
   PG не поднят — цикл штатно уходит в waiting-состояния).

### 3.7. Сторона воркера (Ensure-хвост и конвергенция)

1. `BuildSpec` (PlainClusterDriver; Swarm использует тот же шаблон):
   env — только неконфиденциальное (3.1); серты из RestCertificateCache
   идут НЕ в env, а в bootstrap-ключ; tmpfs `/run/pgw` в спеке контейнера.
2. Каждый EnsureNode-путь после create/start (и для живого контейнера в
   идемпотентной ветке): put bootstrap-ключа (сверка содержимого —
   перезапись только при изменении; сериализация — симметричная, без
   дребезга mod_revision), затем хендшейк по статусу: `not_initialized`
   → `POST /api/bootstrap` с per-install паролями (InstallSecrets из env
   воркера); `ready` с `applied_revision != mod_revision` → `POST
   /api/bootstrap/apply` — ОДИН пин на ревизию ключа (delivered-факт per
   нода: пин той же ревизии повторно не отправляется; повтор — только по
   транспорт-фейлу доставки или по новой ревизии; re-пины каждый тик
   при не-applied запрещены — arch/14 §5 C/§5 I R3: применение
   неудавшегося материала повторяет сам агент коулдауном по материалу).
   `initializing` — ждать (машина конечна).
   Недоступность канала — transient фазы (journal-факт с адресом), не
   провал всего EnsureNode, если контейнер создан; фазы, ждущие Patroni
   (WaitPatroni), падают по своим бюджетам при недоставке — ретрай тиком.
3. NodeSupervisor (§5 C — шаг хендшейка и конвергенции, по статусному
   ключу `/pgworker/nodes/<C>/<X>/<N>/status`): ключа нет — ничего не
   делать (агент стартует, следующий тик увидит статус);
   `not_initialized` — доставка (п.2); `initializing` — ждать;
   `ready` + расхождение `applied_revision` — команда применения
   (дисциплина пинов — п.2);
   **`start_failed` — пересоздание ноды С НОВЫМ ДИСКОМ** с правилами
   (дефект финального прохода: снос лидера до failover уничтожал
   авторитетную копию, чистка scope делала пару невосстановимой):
   (1) failover-first — лидер (DCS leader-ключ) сносится ТОЛЬКО после
   ФАКТА перехода лидерства (leader-ключ сменил владельца; witness-гвард
   — необходимое, не достаточное); failover невозможен — сноса НЕТ,
   тик ждёт (журнальная фаза `start-failed-waiting-quorum`),
   сигнализация; одноузловой шард — снос только через restore-контур
   (arch/19 §3.5), не «в пустоту»; (2) RemoveNode НЕ чистит
   Patroni-scope живого кластера (`initialize`/`leader`/смежные) —
   чистка scope только D2/S3, новая нода бутстрапается по
   существующему scope (репликой), пара восстановима. Данные ноды не
   сохраняются — живой шард восстанавливает реплику
   репликацией/бэкапом; `object`-усыновлённые (R9) и
   restore/TO_REMOVE-шарды реакция не касается. `RecreateRestTlsNodesAsync`
   и env-критерий (`SSL_RESTAPI_CERTIFICATE`/`PGW_REST_PASSWORD_HASH`)
   УДАЛЯЮТСЯ; `InspectNodeEnvAsync` из IClusterDriver удаляется
   (потребителей после удаления шага нет — проверить grep'ом).
   RecreateMarkedNodes (TO_RECREATE оператора) — без изменений.
4. ClusterSecretRotator (§5 I, порядок ETCD-FIRST — решение
   пользователя): R2 = txn-коммит NEW-четвёрки в etcd В НАЧАЛЕ окна
   (compare OLD / put NEW `app_password`+`mover_password`+
   `bucket_admin_password`+`rest_password` / перезапись dsn / del
   заявки; put work-ключа с `rest_window_open=true` — ТОЙ ЖЕ txn:
   атомарность «заявка снята ⇔ флаг стоит» (MR-ревью #3: отдельный put
   после txn мог потеряться — вечный дрейф NEW/OLD без следов; журнальная
   фаза rotate-etcd-committed — обычной записью после, её сбой не
   фатален)) — etcd несёт NEW, окно открыто: маркер окна — ПЕРЕНОСИМЫЙ
   флаг `rest_window_open` журнала работы (carry-forward всеми
   писателями — надзор пишет supervise-записи каждый тик, фазовый
   маркер last-write-wins затирался бы; true при rotate-etcd-committed,
   false при done; предикат окна/гварды — от флага, фазы `rotate-*` —
   только прогресс, включая failure-фазы — на предикат не влияют);
   takeover-продолжение по флагу — пара NEW читается из etcd,
   `rest_pending`-поле умирает; R3 = rolling-применение rest-пары
   каналом агента БЕЗ пересоздания контейнеров И БЕЗ рестарта Patroni
   (решение 29): рендер bootstrap-ключей нод с NEW из etcd, команда
   применения `ready`-нодам последовательно — агент применяет
   конфигурацию patroni reload'ом (SIGHUP / REST POST /reload:
   перечитывает restapi-аутентификацию, postmaster PID/start_time
   неизменны — PG не останавливается; рестарт Patroni-процесса и
   контейнера для пароля запрещён — основания и факты в
   arch/14 §5 I); реплики вперёд, лидер последним (консервативный
   порядок: при сбое применения лидер остаётся на старой рабочей
   конфигурации; ≤1 нода/тик;
   restore/TO_REMOVE-шарды
   и `object`-ноды гейт пропускает), прогресс — факт `applied_revision`;
   R4 = финальный ALTER ROLE app/bucket_admin/bucket_mover PASSWORD NEW
   на мастере каждого шарда («etcd — источник, PG следует»); вход R4 —
   полное схождение R3 ИЛИ лайвлок-гвард (MR-ревью #2: нода, ВОШЕДШАЯ в
   initializing во время окна, пробует doorman с NEW из etcd против
   pg_authid OLD — 28P01 без бюджета, ready недостижим, полный-схождением
   R4 заблокирован навсегда): при отсутствии прогресса R3 N=3 тика
   подряд (carry-счётчик тихих тиков, любой прогресс обнуляет) И все
   неприменившие — initializing/not_initialized/unreachable
   (меньшинство, не отказывающиеся) → ALTER выполняется, окно ОСТАЁТСЯ
   открытым (флаг не гаснет, гварды действуют), R3 продолжается до
   полного схождения; после ALTER пробы initializing-нод сходятся →
   done (флаг false) → снапшот + journal done — окно закрыто. В открытом окне отказ
   аутентификации app (28P01: pg_authid ещё OLD при etcd NEW) —
   ТРАНЗИЕНТ: проба агента не мешает initializing→ready и не роняет
   ready; за окном несовпадение — честный инцидент. Гварды окна (skip
   PATCH `/config` и RecreateMarked-soft — ПОКА окно открыто) — по
   флагу `rest_window_open`.
5. Валидация старта воркера: пара `PGW_REST_TLS_{CA,CA_KEY}` уже
   обязательна; клиентский серт канала выпускается из неё автоматически
   (новых env-секретов НЕ появляется).

### 3.8. Переименование walreceiver → PgNode (граница — решение пользователя)

Переименовывается КОМПОНЕНТ; имена, описывающие ФУНКЦИЮ приёма WAL,
остаются. Целевые переименования в коде:

«приёмник WAL» — только как описание функции стрима.

## 4. Фазы реализации (для плана Фазы 2)

1. **Arch-правки** — уже внесены в worktree этим spec-этапом (§10).
2. **Переименование** (3.8): проект/namespace/бинарь/имена образов
   сборки/тесты/скрипты E2E-prepare; сборка зелёная, юниты на
   месте (переименованы).
3. **Агент PgNode**: bootstrap-модуль (чтение ключа, mTLS-листенер :8081,
   команды доставки/применения, рендер tmpfs, старт/контроль сервисов,
   статусная машина с lease-ключом `/pgworker/nodes/<C>/<X>/<N>/status` —
   атомарный txn-переход, 3 попытки/компонент, пробы SELECT 1),
   интеграция в Program (после fetch-wal/identity-ветки).
4. **Воркер**: BuildSpec (env 3.1, tmpfs), DoormanConfigBuilder без
   пароля, put bootstrap-ключа + клиент канала (POST доставки/применения,
   клиентский серт из REST-CA), Ensure-хвост во всех путях,
   NodeSupervisor-шаг хендшейка/конвергенции по статусному ключу
   (доставка, применение, пересоздание с новым диском по `start_failed`;
   удаление RecreateRestTlsNodesAsync/InspectNodeEnvAsync),
   ClusterSecretRotator R2-rest.
5. **Образ ноды**: supervisord (autostart), entrypoint (без openssl),
   обёртка spilo (экспорт из tmpfs), Dockerfile (пути, build-arg).
6. **Тесты**: юниты (рендер, канал-контракты, BuildSpec-env без секретов,
   шаблон doorman, ротация R2), интеграции (доставка живого контура,
   конвергенция рестарта), E2E (ниже).

Порядок фаз допускает перекрытие, но arch/ уже консистентен на каждом
шаге (канон описан как целевое состояние).

## 5. Ограничения

- P/Invoke запрещён; только управляемый .NET (Kestrel/SocketsHttpsConnection).
- Таймауты/бюджеты существующих фаз не меняются (правило AGENTS.md).
- Docker-E2E: только динамические порты; тик 5 с; `BrokerBootSec` ≤100 с;
  зачистка контуров по канону docs/e2e-isolation.md.
- Образы для E2E — publish на хосте, в контейнер только артефакты.
- Продовые Dockerfile поставки не трогаем (кроме deploy, если сломается
  сборка стендового образа ноды — её и правим).
- Tool-режим `PGW_NODE_TOOL` — вне scope: только пути бинаря.
- Санитарный снос legacy `pgw-backup-wal-*` — вне scope (не удалять).
- Swarm-режим: канал доставки режимно-симметричен (листенер в контейнере);
  InspectNodeEnv-заглушка умирает вместе с интерфейсом — swarm НЕ теряет
  функцию (конвергенция доставки работает через канал, не через env).

## 6. Ключевые сценарии (проверяются тестами/приёмкой)

1. Provision: создание кластера — ноды поднимаются через доставку
   (bootstrap-ключ + push), Patroni/doorman живы, бакеты ACTIVE.
2. `docker restart` ноды: lease-ключ статуса исчез, сервисы стоят;
   новый процесс публикует `not_initialized`, тик (< ~10 с) доставляет
   (хендшейк заново) — нода возвращается в строй по конвергенции.
2a. Хендшейк: агент публикует `not_initialized` → воркер доставляет
   ключи → атомарный переход `initializing` (повторная команда доставки
   при ином состоянии — `ok`-пинок без действий) → пробы `SELECT 1`
   (PG 5432 postgres/SuPassword; doorman 6432 app-роль) → `ready`.
2b. `start_failed`: компонент не поднялся после 3 попыток (например,
   битый образ doorman) → статус `start_failed` с диагностикой → воркер
   пересоздаёт ноду с НОВЫМ диском (volume удалён, контейнер новый,
   хендшейк заново) — StartedAt и volume-имя меняются. На лидере —
   failover-first: снос только после факта смены владельца leader-ключа
   DCS; без живых реплик — `start-failed-waiting-quorum` (сноса нет);
   scope-ключи живого кластера не чистятся, новая нода бутстрапается
   репликой по существующему scope (E2E RestTls (е) — кейс гарантии).
2c. Restore (параллельная доставка, arch/19 §3.5): демонтаж → подъём
   первички (tool-доставка параметров → восстановление) И ПАРАЛЛЕЛЬНО —
   EnsureNode+bootstrap-ключи+хендшейк rejoin-нод (их Patroni ждут
   initialize/лидера — initializing без бюджета легитимен; после
   промоута первички — pg_basebackup, ready). Ожидаемый эффект: срез
   пути ожидания воркера (~40+ с факта прогона ef351387: реплика
   not_initialized в 05:39:10, доставка в 05:39:52 — пока шард
   восстанавливал первичку ~80 с); шаги restore по одной ноде
   доставкой других не блокируются; первичка — в собственном порядке
   (параметры её старта зависят от восстановленного состояния).
3. Ротация per-cluster секретов (процесс I, ETCD-FIRST): etcd-коммит
   NEW в начале окна → rolling-применение rest-пары без пересоздания
   контейнеров и рестарта Patroni — reload'ом (StartedAt контейнеров и
   postmaster PID/start_time не меняются) → финальный ALTER pg_authid
   под NEW — окно закрыто; в окне пробы нод с NEW-кредами из etcd
   получают 28P01-транзиент (ready не роняется, initializing доходит
   до ready); после done шард согласованный (нет пост-apply «No
   standbys available»). Проверка применённости пары — на мутирующем
   эндпоинте (PATCH /config: old → 401, new → 200), не GET / (публичен).
4. Замена серта ноды (смена REST-CA → перезапуск воркера): новый серт в
   bootstrap-ключах → применение по R3-серт (arch/14 §5 I, решение 29):
   реплики — рестарт Patroni-программы по одной (между шагами —
   возвращение реплики в кластер), мастер — пересоздание контейнера с
   failover'ом на обновлённую реплику (PGDATA сохраняется).
5. Негативный: `docker inspect` ноды — нет запрещённых env-ключей (3.1) и
   нет значений фактических секретов прогона (подстрочный ассерт от
   SuPassword/StandbyPassword/rest_password контура).
6. Doorman-клиентский путь: SELECT через опубликованный `:6432`
   (`sslmode=require`) — ac2-doorman-sql остаётся зелёным.
7. Стрим WAL: агент гейтится по etcd как раньше; после доставки стрим
   поднимается, статус-ключ агента жив.

## 7. Риски и их закрытие

- **Обёртка spilo ждёт tmpfs-файлы**: старт spilo — ТОЛЬКО командой
  агента после успешного рендера; отказ рендера не порождает
  «спинящийся» spilo (обёртка падает с диагностикой, supervisord
  не перезапускает старт-отказы — паттерн pg_doorman).
- **Потеря ноды при падении воркера**: рестарты нод требуют воркера —
  принято (граница п. 2.3); отказ SINGLE-хоста воркера не стопает бегущие
  ноды (доставка нужна только для стартов/замен).
- **Расхождение ревизий (агент применил, воркер не увидел)**: applied_
  revision возвращается синхронно в ответе POST — окно расхождения
  минимально; повторный POST — no-op.
- **Применение ротаций на Patroni** (решение 29): rest-пароль —
  reload (SIGHUP/POST /reload): PG и DCS-лидерство не затрагиваются
  (postmaster PID/start_time неизменны), switchover не требуется;
  рестарт Patroni-процесса/контейнера для пароля запрещён (TERM-логика
  Patroni гасит управляемый PG). Rest-серт — reload не применяет
  (свойство patroni 4.1.0: TLS-handshake зависает, материал — только
  рестартом): реплики — рестарт Patroni-программы по одной (PG реплики
  останавливается на секунды), мастер — пересоздание контейнера с
  failover'ом на обновлённую реплику. Права файлов сертов обеспечивает
  поставщик (0600 postgres): root-владелец — PermissionError Patroni
  на reload.
- **Plaintext-доступ к командам канала**: исключён конструктивно —
  `/api/bootstrap*` только на `:8081` (mTLS), `:8080` → `404`
  (решение 23); тест-негатив обязателен.
- **Лайвлок окна ротации** (инициализирующаяся нода в окне): закрыт
  лайвлок-гвардом R4 (решение 24) — ALTER при 3 тихих тиках и
  меньшинстве неготовых, окно остаётся открытым до схождения.
- **`start_failed` → потеря данных ноды** (новый диск): отказ старта
  уже означает недоступность данных этой ноды; реплика/бэкап — источник
  восстановления; для единственной ноды шарда данные теряются —
  осознанное решение пользователя («чистый передел»), бэкапы обязательны
  до экспериментов (arch/19).
- **Снос лидера до failover / чистка scope живого кластера** (дефект
  финального прохода): лидер сносился при живом свидетеле БЕЗ факта
  перехода лидерства (уничтожение авторитетной копии), а RemoveNode
  чистил scope-ключи (initialize/leader) → пара невосстановима
  («waiting for leader to bootstrap» навсегда). Закрыто решением 27:
  failover-first (факт смены владельца leader-ключа до сноса;
  недостижим — waiting-quorum без сноса) и неприкосновенность scope
  живого кластера (чистка — только D2/S3).
- **Долгое `initializing`**: фаза (б) намеренно без бюджета
  (восстановление из бэкапа может идти долго — уточнение пользователя);
  фаза (а) конечна (≤3 попытки старта на компонент). Зависание ПРОЦЕССА
  агента гасит lease-ключ статуса — тик трактует как рестарт
  (`not_initialized` появится); «вечного» `initializing` от мёртвого
  агента в etcd не существует; владельцы процессов (provisioning/
  restore) держат СВОИ бюджеты фаз — без изменений.
- **Экспозиция bootstrap-ключа**: класс per-cluster секретов etcd,
  панелью не разбирается (префикс `clusters/…/nodes/…` вне панельных
  парсеров — проверить при реализации; при необходимости — явный
  exclusion в читателях панели, без UI).

## 8. Принятые решения (все развилки закрыты)

1. **Роль агента**: тот же процесс-агент (переименован в PgNode);
   отдельный бинарник не вводится (решение пользователя — прежний
   walreceiver, новое имя PgNode).
2. **Per-install пароли PG (SuPassword/StandbyPassword)**: прямая
   передача телом mTLS-запроса от воркера (решение пользователя);
   исключение-ключ в etcd отвергнуто (Д7 сохраняется).
3. **Per-cluster секреты/серты**: etcd bootstrap-ключ, агент забирает
   сам (решение пользователя; «per-cluster секреты — кандидат на тот же
   путь» из дизайна — принят).
4. **Bootstrap Spilo без PGPASSWORD_SUPERUSER в docker-env**: обёртка
   spilo-supervised.sh экспортирует секретные env ПРОЦЕССА из tmpfs-файлов
   агента (upstream Spilo читает env — отход только от docker-env, не от
   механизма Spilo). SPILO_CONFIGURATION — файлом, доставляется целиком.
5. **Кэш секретов**: кэша на диске НЕТ вообще; tmpfs `/run/pgw` 0600
   postgres (решение пользователя: «не должна кешировать ключи в файловой
   системе»); шифрование не вводится (домашняя система, правила п.9
   базовые).
6. **Серт ноды**: per-install REST-CA с SAN (кандидат роадмапа принят);
   один серт на REST/doorman/mTLS-агент; клиенты doorman остаются
   `sslmode=require` (канон P17 arch/13 §4 не меняется); верификация в
   mTLS-канале двусторонняя (воркер — CA+SAN, агент — клиент-серт по
   публичному CA из docker-env).
7. **Watch vs триггер**: только инициатива воркера (канал GET/POST);
   агент ничего не watch'ит (канон «Poll, без watch», arch/14 §3) и не
   инициирует; чтение bootstrap-ключа при старте процесса — часть
   собственного старта агента (нужно для листенера), не «инициатива».
8. **Ротация rest_password**: без rolling-recreate (решение пользователя:
   легаси-кластеров нет — env-механика RecreateRestTlsNodes не нужна);
   перерендер bootstrap-ключей + применение reload'ом Patroni
   (решение 29); порядок всего прохода — ETCD-FIRST (решение 19a):
   etcd-коммит NEW в начале окна, ALTER — последним.
9. **Миграция живых кластеров**: не требуется — таких нет (решение
   пользователя); стендовые/тестовые контуры пересоздаются provisioning'ом
   заново.
10. **Граница переименования** (решение пользователя): компонент →
    PgNode/pgnode (проект, namespace, бинарь, программа supervisord,
    идентичность/статус-классы, Meter, джоба/file_sd прометheus);
    wal-функции — как есть (метрики `walreceiver_*`, `fetch-wal`,
    стрим-классы, env-выключатель стрима).
11. **Порт канала**: 8081 внутри контейнера (не занят: 5432/8008/6432/
    8080), на хост не публикуется; имя DOORMAN-шаблона —
    `DOORMAN_CONFIG_TEMPLATE`, плейсхолдер `${PGW_SU_PASSWORD}`.
12. **Убранные из env bucket-пароли**: потребителям внутри контейнера не
    нужны (проверено) — доставка не вводится, ключи исчезают из env.
13. **Сертификат листенера до доставки**: агент сам читает bootstrap-ключ
    при старте (данные в etcd уже лежат — их положил воркер при создании
    контейнера); push-пароли — единственное, чего агент ждёт от воркера.
14. **Статусная машина + хендшейк** (требования пользователя): состояния
    `not_initialized → initializing → ready | start_failed`; воркер
    мониторит статус при старте, по `not_initialized` доставляет ключи;
    агент по получении/проверке всех аргументов атомарно переводит в
    `initializing` (txn compare по value), держит его до готовности
    PG+doorman, затем `ready`; повторная команда доставки при состоянии
    ≠ `not_initialized` — `ok` без действий («пинок состоялся»).
15. **Где живёт статус**: etcd-ключ `/pgworker/nodes/<C>/<X>/<N>/status`,
    lease TTL 15 c (реплицированный источник истины — multi-host канон;
    у агента доступ к etcd уже есть; воркер мониторит poll-тиком —
    канон «Poll, без watch» arch/14 §3; lease исключает «застрявший»
    статус мёртвого процесса). Пишет только агент; панелью не
    разбирается.
16. **Атомарность перехода**: txn etcd `[compare state==not_initialized]
    [put initializing]` — единственный writers-путь агента; проигранный
    compare = повторная команда → `200 ok` без повторной инициализации.
17. **Пробы SELECT 1 при initializing** (креды): PG — `127.0.0.1:5432`
    под postgres/SuPassword (доставлен); doorman — клиентский вход
    `:6432` под app-ролью с `app_password` из etcd-ключа кластера
    (sslmode=require) — проба заодно валидирует цепочку auth_query
    пулера. Бюджеты проб — в пределах тика/фазы, новых таймаут-констант
    проекту не добавляется (кроме кратных интервалов опроса внутри
    попытки; численно — план Фазы 2, существующие бюджеты не меняются).
18. **Надзор старта компонентов**: до 3 попыток на компонент
    (pg_doorman, spilo независимо — сбой одного не блокирует другой);
    итог в любом исходе: все готовы → `ready`, иначе `start_failed`
    (требования пользователя; bounded-попытки делают машину конечной —
    воркеру отдельный таймаут на `initializing` не нужен).
19. **Реакция на `start_failed` — пересоздание с новым диском** (буква
    пользователя: «старую убить новую поднять с новым диском»): remove
    контейнера + volume, ensure заново. Данные ноды не сохраняются —
    осознанное лечение «чистый передел»: отказ старта уже означает
    недоступность данных этой ноды, живой шард восстанавливает реплику
    репликацией/бэкапом. Границы: `object`-усыновлённые (R9),
    restore/TO_REMOVE-шарды — вне реакции (владельцы — свои процессы).
19a. **Порядок ротации app-пароля — ETCD-FIRST** (решение
    пользователя): NEW-креды коммитятся в etcd В НАЧАЛЕ окна (б. R3 →
    R2), ноды применяют rest-пару каналом (rolling, б. R2-rest → R3),
    финальный ALTER pg_authid — ПОСЛЕДНИМ (б. R2-Alter → R4, «etcd —
    источник, PG следует», прецедент — выравнивание ролей P1.5').
    Проба нод в окне с NEW из etcd против OLD pg_authid (28P01) —
    транзиент: не мешает initializing→ready, не роняет ready; окно
    закрывается ALTER'ом, пост-apply «No standbys available» не
    возникает. Маркер окна — переносимый булев флаг `rest_window_open`
    журнала работы (ревью шага 11: журнал last-write-wins, надзор
    пишет supervise-записи каждый тик — фазовый маркер затирался бы;
    флаг carry-forward всеми писателями, true при rotate-etcd-committed
    R2 / false при done R4; предикат окна и гварды — от флага, фазы
    rotate-* — прогресс, failure-фазы на предикат не влияют; заявка
    удалена R2-txn, takeover продолжает по флагу, пара NEW — в etcd;
    `rest_pending`-поле журнала упразднено).
19b. **Backup-креды — ВНЕ тикета ротации t05** (следствие 19a:
    ETCD-FIRST-тикет ротирует app/bucket_admin/bucket_mover/rest + dsn;
    `/clusters/<C>/backup_password` и pg_authid `backup_exec` он НЕ
    трогает — пароль статичен с ensure, arch/19 §7 синхронизирован).
    Ротация backup-кредов — отдельная задача t06-rotate-backup-creds
    (arch/roadmap/pgworker.md), тем же каноном ETCD-FIRST после t05.
20. **Развод bootstrap vs ротация**: команда доставки (тело с паролями)
    действует только из `not_initialized`; команда применения (без
    тела) — только на `ready`. Воркер различает по статусному ключу —
    смешение команд исключено конструктивно.
21. **3 попытки — надзор СТАРТА процесса, не select 1** (уточнение
    пользователя): попытка = запуск процесса компонента; упал при
    старте — перезапуск, ≤3 на компонент; исчерпание → компонент
    `failed` → `start_failed`. Ожидание готовности (`SELECT 1`) —
    отдельная фаза БЕЗ бюджета инициализации (живой процесс может
    инициализироваться долго, особенно восстановление из бэкапа);
    существующие бюджеты проекта не меняются.
22. **`is_tool_start`** (уточнения пользователя): параметр команды
    доставки; false (умолчание) — агент готовит параметры И запускает
    компоненты (фаза (а) — его ретраи ≤3, затем фаза (б) select 1);
    true — агент ТОЛЬКО готовит параметры запуска (tmpfs), запуск и
    ретраи выполняет сама tool-команда, которой предварительный запуск
    не нужен (например, restore — пишет PGDATA до старта).
    Производные решения tool-пути (зафиксированы): терминальный успех —
    ПОДГОТОВЛЕННОСТЬ ПАРАМЕТРОВ: успешный рендер → `ready`
    (`components` = `prepared`), фаза (б) select 1 в этом пути агентом
    НЕ выполняется (контроль компонентов — зона tool-команды и её
    владельца); ошибка рендера → `start_failed` (потребитель — владелец
    tool-контура, не общий надзор — restore-шарды §5 C не пересоздаёт);
    повторный пинок при состоянии ≠ `not_initialized` — `ok` без
    действий (атомарная защита едина для обоих путей); рестарт
    контейнера — lease гасит статус, подготовка повторяется по новому
    хендшейку (tool-команда обязана ждать `ready` перед чтением
    параметров — упорядочивание делает владелец, он же пинает).
    Штатный порядок — «сначала старт компонентов, потом доп
    tool-команды» (команды без `is_tool_start` идут по готовности).
23. **Граница канала — ПОРТ, не роутер** (MR-ревью #1, блокер):
    `/api/bootstrap*` обслуживаются ТОЛЬКО листенером `:8081` (mTLS,
    клиентский серт обязателен); обращения по plaintext `:8080` → `404`
    — иначе любой контейнер docker-сети подсовывает пароли в окне
    `not_initialized` (su-доступ атакующего). Канон — arch/13 §2,
    arch/14 §4, arch/25 №23; негативный тест «8080 → 404» — плану.
24. **Лайвлок-гвард R4** (MR-ревью #2, блокер): вход R4 — полное
    схождение R3 ИЛИ отсутствие прогресса R3 N=3 тика подряд (carry-
    счётчик, любой прогресс обнуляет) при неприменивших в статусах
    initializing/not_initialized/unreachable (меньшинство, не
    отказывающиеся); в лайвлок-ветке ALTER выполняется, окно остаётся
    открытым (флаг/гварды действуют), R3 продолжается до схождения;
    после ALTER пробы initializing-нод сходятся. N=3 — канонизировано
    (arch/14 §5 I).
25. **Флаг окна — в txn R2** (MR-ревью #3): put work-ключа с
    `rest_window_open=true` в ops той же txn (NEW×4/dsn/del
    заявки/флаг неразделимы); фаза rotate-etcd-committed — обычной
    записью после (сбой не фатален — флаг уже в etcd); §3.3-строка
    work говорит «true кладётся ТОЙ ЖЕ txn R2».
26. **Клиент канала — только воркер** (MR-ревью #5): валидация
    клиентского серта агентом = цепочка к CA + EKU ClientAuth +
    CN=pgworker (серверные серты нод того же CA клиентом НЕ являются);
    отдельный клиентский валидатор канала по прецеденту roadmap t04,
    общий TlsChain.ValidateChain не трогаем. Канон — arch/13 §2/§4.
27. **Failover-first для лидера, scope живого кластера
    неприкосновенен** (дефект финального прохода, канон arch/14 §5 C):
    (а) start_failed на текущем лидере обслуживается сносом ТОЛЬКО
    после факта перехода лидерства (DCS leader-ключ сменил владельца;
    witness-гвард дополняется фактом failover — свидетель жив, но
    лидерство ещё не ушла — сносить нельзя); failover невозможен —
    сноса нет, журнальная фаза `start-failed-waiting-quorum`,
    сигнализация; одноузловой шард (лидер = единственная копия) —
    только через restore-контур; (б) RemoveNode старт-реакции не чистит
    Patroni-scope-ключи живого кластера (`initialize`/`leader`/
    смежные) — чистка scope только при демонтаже кластера/шарда
    целиком (D2/S3); после сноса пара восстановима живыми членами,
    новая нода бутстрапается репликой по существующему scope.
28. **Параллельная доставка при restore** (прямое указание
    пользователя — «уменьшение времени работы при правильной логике —
    обязательная оптимизация»; канон arch/19 §3.5): доставка
    bootstrap-ключей и хендшейк ПЕРЕЗАЖИМАЕМЫХ/rejoin-нод (реплик и
    не-восстанавливаемых членов) выполняется ПАРАЛЛЕЛЬНО
    восстановлению первички шарда — ноды независимы (scope-
    неприкосновенность решения 27 это обеспечивает: реплики
    бутстрапаются репликой к живому/восстанавливаемому scope);
    initializing-ожидание фазы (б) SELECT 1 без бюджета — легитимное
    состояние ждущих лидера реплик. Первичка — доставка/хендшейк
    ПОСЛЕ восстановления её данных (параметры её старта зависят от
    восстановленного состояния — tool-порядок restore unchanged).
    Эффект: срез последовательного ожидания воркера (факт ef351387:
    ~40+ с на реплике при ~80 с восстановления первички).
29. **Применение ротаций на Patroni — по материалу** (решение
    пользователя; факты — живой эксперимент t05-reload-probe на
    spilo-18:4.1-p2/patroni 4.1.0; канон arch/14 §5 I). Прежняя
    формулировка «рестарт Patroni-процесса — PG не останавливается»
    внутренне противоречива (штатное завершение Patroni по TERM гасит
    управляемый PG) — упразднена этой правкой. Две ветки:
    (а) **rest-пароль (частое событие, R3 процесса I)** — reload:
    SIGHUP процессу patroni ИЛИ REST POST /reload (эквивалентны,
    выбор за реализацией). Рестарт Patroni-ПРОЦЕССА и рестарт
    контейнера для применения пароля ЗАПРЕЩЕНЫ (рестарт процесса =
    остановка PG; постмастер демонизирован, PPID=1 — механика
    TERM-логика Patroni, не дерево процессов). Факты эксперимента:
    reload перечитывает restapi-аутентификацию (старая пара 401,
    новая 200; POST /reload 202), postmaster PID/start_time
    неизменны. Верификация: GET / публичен — аутентификация
    проверяется на мутирующих эндпоинтах (PATCH /config и др.);
    пробы живости GET'ом доказательством аутентификации не являются.
    Права доставляемых файлов сертов обязан обеспечивать поставщик
    (tmpfs 0600 postgres): root-владелец — PermissionError Patroni
    на reload. Если reload на образе какой-то материал не применяет —
    реализация докладывает владельцу (новая развилка), не молчит.
    (б) **rest-серт ноды (редкое событие — смена per-install REST-CA;
    reload серт НЕ применяет — факт эксперимента: restapi зависает на
    TLS-handshake, материал подхватывается только рестартом patroni —
    свойство patroni 4.1.0)**: (i) все реплики рестартуются ПО
    ОЧЕРЕДИ (rolling, по одной: рестарт Patroni-процесса → PG реплики
    останавливается на секунды рестарта → patroni стартует и
    усыновляет локальный PG по DCS; между шагами — ожидание
    возвращения реплики в кластер); (ii) затем мастер —
    ПЕРЕСОЗДАНИЕ контейнера (kill+remove+ensure; новый диск НЕ
    требуется — PGDATA сохраняется; НЕ рестарт: пересоздание
    гарантирует переезд лидерства failover'ом на уже обновлённую
    реплику; после failover старый лидер возвращается в кластер
    репликой уже с новым сертом). Порядок «реплики вперёд» обязателен:
    к моменту пересоздания мастера все реплики уже несут новый серт —
    failover идёт на обновлённую реплику. Граница запрета (а) —
    ТОЛЬКО rest-пароль R3: R3-серт (рестарт реплик, пересоздание
    мастера), restore-контур arch/19 §3.5 (stop/return Patroni
    ноды) и start_failed-пути §5 C — отдельные легитимные пути,
    запрет на них не переносится.

## 9. Критерии приёмки (мерж-гейт)

1. Сборка: `DOTNET_CLI_UI_LANGUAGE=en dotnet build src/PgWorker.slnx -c
   Release --nologo` — 0 warnings (TreatWarningsAsErrors)/0 errors.
2. Юнит-тесты и целевые интеграции — зелёные (полный список — план;
   обязательные: env-сборка без секретов, рендер шаблона, контракт
   канала (доставка/применение, ok-пинок при состоянии ≠
   `not_initialized`, атомарный txn-переход; негатив «:8080 → 404» и
   «серверный серт ноды отвергается как клиентский» — решения 23/26),
   машина состояний
   (`not_initialized → initializing → ready`, 3 попытки/компонент →
   `start_failed`, пробы SELECT 1), ротация R2-rest, конвергенция
   статусов, пересоздание с новым диском по `start_failed`).
3. Статическая подготовка E2E одним процессом ДО тестов:
   `DOTNET_CLI_UI_LANGUAGE=en dotnet run --project
   src/tests/PgWorker.E2ePrepare -c Release`.
4. docker-E2E на свежем Release, сборка и тесты ОТДЕЛЬНЫМИ командами:
   минимум `DOTNET_CLI_UI_LANGUAGE=en dotnet test
   src/tests/PgWorker.E2eTests -c Release --no-build --filter
   FullyQualifiedName~Scale_AddEmptyShard`; ПОЛНЫЙ прогон E2eFixture —
   обязателен (затронуты provisioning/надзор/ротация).
5. Негативная проверка гейта (в составе E2E, сценарий §6.5): `docker
   inspect` контейнеров нод — отсутствие запрещённых env-ключей и
   фактических секретных значений прогона.
6. Позитивные E2E: кластер поднят и работоспособен через хендшейк
   (not_initialized → initializing → ready; doorman-SELECT ac2-doorman-sql
   зелёный), рестарт ноды восстанавливается конвергенцией тика,
   инжекция сбоя старта компонента → `start_failed` → пересоздание ноды
   с новым диском (новый volume), ротация `rest_password` завершается
   без изменения StartedAt контейнеров.
7. Arch/-документы и код согласованы (правки §10); grep-контроль:
   в arch/ нет «walreceiver» как имени компонента (функциональные
   упоминания приёма WAL — допустимы), в `docker inspect` нод нет
   секретов.
8. Роадмап: тег `t05-node-secret-push` удаляется из
   `arch/roadmap/pgworker.md` мерж-коммитом (правило AGENTS.md).
