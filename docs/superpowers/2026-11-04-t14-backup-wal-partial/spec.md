# Spec: t14-backup-wal-partial — RPO-хвост WAL (`.partial`) и фоновая чистка `wal/`

Пункт роадмапа: [`arch/roadmap/backup.md`](../../../arch/roadmap/backup.md), t14-backup-wal-partial.
Канон: [`arch/19-backups.md`](../../../arch/19-backups.md) (правки t14 уже в дереве — источник истины).
Дата: 2026-11-04. Worktree: `worktrees/t14-backup-wal-partial`.

---

## 1. Цель

Реализовать по канону `arch/19-backups.md` пять подпунктов t14:

1. **`.partial`-доотправка** — приёмник WalReceiver каждые
   `Wal:PartialIntervalSec` (дефолт 3 с) и/или по порогу байт выгружает
   валидный префикс незакрытого сегмента объектом
   `wal/<segment>.<endLsn>.partial` (версия выкладывается только длиннее
   лежащей; финал при закрытии поглощает версии); гвард байт-сверки —
   только на финальных объектах (§3).
2. **Дубль `pg_wal` полного — только закрытые сегменты**: в `wal/`
   дублируются сегменты набора, закрытые в источнике на момент заливки
   (строго ниже текущего активного wal-файла источника); последний живой
   сегмент набора остаётся только в `full/<id>/pg_wal/` (§2). Устраняет
   гонку «срез дубля против финала стрима».
3. **Читатели `wal/`** (контроль цепи, restore/fetch-wal, панель) — хвост
   потока = максимальный валидный префикс (финал или лучший `.partial`)
   (§3/§3.5).
4. **Фоновая чистка `wal/` — wal-sweeper глобального лидера**: per-shard,
   оценка `.partial`-гигиены не реже раза в минуту на шард, срез финальных
   ниже cutoff, список → один batch-delete, метрики живости цикла и
   per-shard свежести + алерты (§4).
5. **Retention-гигиена `.partial`** — поглощение финалом и срез ниже
   cutoff в ретенционном проходе (§4 п.5).

**Цель-критерий**: довести до зелёного 3 известных красных E2E —
`Restore_TargetTime_PitrRollback` / `Drill_Failed_OnCorruptedWal` /
`Restore_Latest_RebuildsDestroyedShard` — НЕ ТЕРЯЯ ДАННЫЕ (RPO-гарантии
канона: инвариант подтверждения-по-доставке не ослабляется).

### 1.1. Механика гонки (почему 3 теста красные)

`pg_basebackup -X stream` завершается записью end-of-backup в ПОСЛЕДНЕМ
сегменте набора. Этот сегмент в кластере ещё ЖИВ: PG продолжает дописывать
в него же до ближайшего switch. Текущий код дубля
(`FullBackupOperation`, шаг 6) кладёт в `wal/` ВСЕ сегменты набора, включая
живой последний. Далее две ветви, обе фатальны:

- срез дубля лёг раньше стрим-финала: объект `wal/<segment>` занят байтами
  набора (записи до end-of-backup + добивка нулями до полного размера
  файла), а финал стрима несёт РЕАЛЬНЫЕ записи, дописанные источником после
  среза → цепь `wal/` формально «непрерывна» по именам, но объект
  усечён/нулевой в хвосте → restore не докатывается до цели
  (target_time не достигнут / latest теряет строки / drill висит в
  recovering);
- финал стрима лёг раньше дубля: дубль кладёт те же имена с ДРУГИМИ
  байтами → гвард чужой цепочки (ETag/md5) даёт wal-archive-conflict →
  полный FAILED либо приёмник `failed_permanent`.

Канон t14 закрывает корень: дубль кладёт только сегменты, закрытые в
источнике на момент заливки; байты живого сегмента доезжают финалом стрима
(а до закрытия — `.partial`-префиксом, п.1).

### 1.2. Не-цели

- Никаких новых etcd-ключей (канон §4 их не вводит; наблюдаемость
  wal-sweeper — метрики).
- Никаких изменений стоп-семантики/гейтов, слотов, планировщика полных,
  дрила, restore-машины заявок (RestoreProcess), панели.
- Таймауты/бюджеты существующих операций не меняются
  (`Restore:RecoveryTimeoutSec`, `Job:*`, fetch-wal `CallDeadline=45 с` и
  транспортные попытки 3×2 с — без изменений).
- P/Invoke запрещён; комментарии в коде — русские; идентификаторы —
  английские.

## 2. Принципы

- **arch-first**: сперва минимальные правки `arch/18`/`arch/19` (раздел 3),
  затем код.
- **Инвариант RPO не ослабляется**: подтверждение слота — только после
  успешного put ФИНАЛЬНОГО объекта; `.partial` никогда не двигает
  `restart_lsn`; неподтверждённое удерживается слотом (§3).
- **Идемпотентность каждого шага** (arch/17): повтор put финала — no-op по
  гварду; повтор выкладки `.partial` — skip при нестрогом приросте; повтор
  прохода sweeper/ретенции — идемпотентный batch-delete.
- **Один источник истины прогресса — объекты S3**: контроль читает листинг
  (union) и вычисляет хвост (финал или лучший `.partial`); статус
  приёмника для этого не используется.
- **`.partial` — мусор по построению**: финал поглощает; «длиннее
  выигрывает» исключает конкурирующие байты (физическая репликация strict-
  sync: префиксы мастера и sync-реплики идентичны) — гвард на `.partial` не
  нужен и не ставится.
- Изменения production-ready; внешние взаимодействия (S3-пул) — по
  существующим паттернам (перебор целей, breaker 45 с, `MaxErrorRetry=0`).

## 4. Структура и компоненты (изменения по коду)

Каталоги: `src/PgWorker.Backups` (воркер), `src/PgWorker.PgNode`
(агент ноды/приёмник), `src/PgWorker.App` (циклы), `src/PgWorker.Core`
(env нод), `src/PgWorker.Docker` (ClusterDriver env).

### 4.1. Модель (`PgWorker.Backups/Model`)

- **`WalPartialName`** (новый, рядом с `WalFileName`): канон ключа
  `wal/<segment>.<endLsn>.partial` — `<segment>` 24 hex строчных,
  `<endLsn>` ровно 16 hex строчных (LSN конца префикса; фиксированная
  ширина → лексикографический порядок суффикса = числовой). Чистые
  функции: `Key(string segmentName, ulong endLsn)`, `TryParse(string
  name)` → `(WalFileName Segment, ulong EndLsn)?`,
  `SegmentPrefixOf(string segmentName)` (узкий
  S3-префикс листинга версий: `"<segment>."`). `.history`/финалы — null.
- **`WalPrefixScanner`** (новый): валидный префикс буфера сегмента — до
  конца последней ПОЛНОЙ WAL-записи, без нулей-добивки. Страничная
  механика PG: страница 8 КиБ (XLOG_BLCKSZ); первая страница сегмента —
  long header 40 байт, прочие — short 24; запись НЕ пересекает границу
  страницы (не влезает → остаток страницы добит нулями, запись целиком на
  следующей); заголовок записи: `xl_tot_len` LE u32 @4, минимум 24 байта.
  Правила: на границе страницы — пропуск заголовка страницы; в остатке
  страницы < 24 байт или `tot_len==0` (нули) или `tot_len` > остатка
  страницы или запись выходит за накопленный буфер — стоп; префикс = конец
  последней полной записи. Возвращает длину префикса в байтах (0 — ни одной
  полной записи/нет валидного long-заголовка).
- **`SegmentAssembler.PartialSnapshot()`** (добавить): `(string Name, byte[]?
  Prefix, ulong EndLsn)?` — имя текущего незакрытого сегмента (вычисляется
  той же математикой, что `Close()`: TLI из long page header буфера,
  валидация xlp_pageaddr; невалиден — null), копия ВАЛИДНОГО префикса
  буфера (буфер — исключительное владение hot-path, отдаётся копия) и
  `EndLsn = _segmentStart + prefixLen`. Префикс 0 / заголовка нет — null.
- **`WalChain`**: новая чистая функция **`TailOf(WalFileName?
  chainLastFinal, IEnumerable<string> objectNames)`** → `WalTailFact?`
  (`record WalTailFact(string SegmentName, string ObjectName)`; unix
  времени объекта контроль берёт в месте вызова из листинга по
  `ObjectName`) — хвост потока = максимальный валидный префикс: максимум
  по (Tli, Log·256+Seg) между `chainLastFinal` (результат
  `Check`/`CheckWithRestart` — финал; авторитетен при равной позиции) и
  лучшим `.partial` (схлопывание версий по сегменту, учитывается
  длиннейшая по EndLsn). Существующие `Check`/`CheckRange`/`Collect` не
  меняются (`IsPartial` уже отсекает `.partial` от цепочки).
- **`WalChain.CheckRange`** — правка вызова (не сигнатуры):
  verify-полконтроль передаёт UNION имён `wal/` + `full/<id>/pg_wal/`
  (см. 4.4); текст ошибки Walk'а «missing in wal/» → «missing in wal/ or
  the backup set».
- **`RetentionPlanner`**: новая чистая функция
  **`SelectPartialForDeletion(IReadOnlyList<string> objectNames,
  WalFileName? cutoff)`** → мусорные `.partial`:
  (а) поглощённые: лежит финал `wal/<seg>` → все `wal/<seg>.*.partial`;
  (б) устаревшие версии живого сегмента: среди `wal/<seg>.*.partial` без
  финала остаётся длиннейшая (max EndLsn), прочие — мусор;
  (в) `.partial` сегмента ниже cutoff (cutoff есть): сегмент ниже по
  правилу `SelectWalForDeletion` (TLI ниже / тот же TLI с позицией ниже) →
  все версии. `cutoff == null` — ветка (в) не выполняется. Существующий
  `SelectWalForDeletion` (финалы) не меняется.

### 4.2. Приёмник: `.partial`-доотправка (`PgWorker.PgNode`)

- **`WalReceiverOptions`** + `PartialIntervalSec` (int, дефолт 3);
  **`WalReceiverLoop`** читает env `PGW_WAL_PARTIAL_INTERVAL_SEC`
  (невалидное/отсутствующее → дефолт 3) и передаёт в опции; приёмник
  продолжает работать при любом значении ≥1 (клэмплит снизу к 1).
- **`WalReceiverCore.RunSessionAsync`**: фоновая задача сессии
  «partial-памп» (linked CTS сессии — стоп-гейты/отмена замирают её вместе
  со стримом):
  - триггеры: таймер `PartialIntervalSec` ИЛИ сигнал из `Append`-цикла при
    приросте валидного префикса ≥ 4 МиБ от последней выкладки
    (TaskCompletionSource-триггер; порог — константа
    `PartialThresholdBytes = 4 MiB`, internal для тестов);
  - шаг тика: `PartialSnapshot()` → нет/нулевый прирост против последней
    выложенной этой сессией версии → skip (одинаковые версии не
    пере-clayутся, LastModified не дёргается — «тишина» контроля честна);
  - сверка с S3: list узкого префикса `wal/<seg>.` (read-семантика —
    первая доступная нода) → лежащая лучшая версия; новая короче либо
    равна → skip; list-отказ (transient) → skip тика (стрим не рвётся,
    хвост доедет следующим тиком либо финалом);
  - put: `PutObjectAsync` (БЕЗ гварда) ключа
    `wal/<seg>.<endLsn:x16>.partial` с SHA256 транспорта; put-ретраи — тот
    же `PutWithRetryAsync`-паттерн (исчерпание → флаг pool_exhausted,
    маркеры прежние; конфликт невозможен — гварда нет);
  - подтверждение слота НЕ двигается (только финалы).
- **Поглощение при финале**: после успешного put финального объекта
  (существующий шаг 6 сессии) — best-effort: list `wal/<seg>.` → все
  версии → один `DeleteKeysAsync`; отказ — diagnostic-log (докладывает
  sweeper, §4 п.5/§4).
- Ре-доклады инвентаря (`RedeliverWalInventory`/`RedeliverHistoryInventory`)
  — без изменений (открытый сегмент не грузится; `.partial`-имена локальных
  файлов `pg_wal` отфильтрованы уже).

### 4.3. Дубль `pg_wal` полного — только закрытые (`FullBackupOperation`)

Шаг 6 (дублирование) меняется:

- перед циклом дубля — IDENTIFY_SYSTEM на свежем replication-соединении
  `127.0.0.1:5432` (креды операции; `IXLogReplicationSource` фабрикой как у
  стрима) → `xlogpos` → позиция активного сегмента источника
  `xlogpos / SegmentBytes`;
- дублируются только сегменты набора с позицией СТРОГО ниже активной
  (гвард дубля: «закрытость — по источнику на момент заливки», §2);
  последний живой сегмент набора остаётся только в `full/<id>/pg_wal/`
  (самодостаточность полного — recovery дочитывает из layout, финал доедет
  стримом);
- IDENTIFY_SYSTEM отказ → операция FAILED с однострочной причиной
  (транзиент; переснятие новым id — семантика §2 «резюмов нет»);
- put дубля прежний: `PutWalSegmentFileAsync` (гвард) с нормализацией
  регистра; финал стрима, закрытый ДО дубля, совпадает байтами →
  идемпотентно по гварду.

### 4.4. Verify-полконтроль цепи (`BackupVerifyProcess`)

`CheckRange` получает UNION имён: `walList` (union-листинг `wal/`) +
`setList` (union-листинг `full/<id>/pg_wal/`) — оба листа уже снимаются,
объединяются имена. End-сегмент набора (живой на момент заливки — в `wal/`
не дублируется) валидируется из набора. Иначе — ложный permanent
verify-FAILED «segment from the backup set is missing in wal/» на каждом
полном с живым хвостом. Checksums-проверка (`pg_verifybackup`) не меняется
(manifest перечисляет `pg_wal/` набора целиком).

### 4.5. Контроль цепи воркера (`WalStreamProcess.ControlDueAsync`)

- при живом (непрерывном) ключе вычисления `last_uploaded_segment` /
  `last_uploaded_unix` / lag-зонда / «тишины» переходят на
  `WalChain.TailOf(objects)`: хвост = финал или лучший `.partial`
  (формат ключа etcd не меняется — `last_uploaded_segment` остаётся именем
  СЕГМЕНТА без суффикса; парсеры панели толерантны);
- непрерывность/дыры — по-прежнему ТОЛЬКО по финалам (`.partial` в цепь не
  входит: `Collect` их отбрасывает) — CheckWithRestart/WAL_CHAIN_ERROR-путь
  без изменений;
- «тишина» (`Wal:StaleSec`): обновление `.partial` каждые 3 с обновляет
  LastModified лучшего объекта → ложная тишина на активно пишущем шарде
  уходит; idle (нет записей) — тишина честная (прироста нет, версии не
  пере-clayутся).

### 4.6. fetch-wal (`FetchWalCommand`)

`FetchOnceAsync` расширяется (чистые функции — отдельными методами для
юнитов):

1. точный GET финала `wal/<segment>` по всем read-нодам (как сейчас);
2. везде NotFound → list узкого префикса `wal/<segment>.` ПО ВСЕМ нодам
   (сбор лучших версий; транспортный отказ ноды — пропустить ноду, хотя бы
   одна ответила — работаем) → лучшая (max EndLsn) → GET найденного ключа с
   ноды, где он числится; ничего нигде → exit 1 (конец WAL);
3. транспорт/дедлайн — прежние (`MaxErrorRetry=0`, попытки 3×2 с,
   `CallDeadline=45 с` — не менять).

Скачанный `.partial` кладётся в запрошенный `%p` путь как есть: postgres в
recovery остановится в конце валидных записей (префикс валиден по
построению 4.1), следующий сегмент отсутствует → конец WAL → promote
(`recovery_target_action=promote`; latest) либо достигнут target
(target_time). Валидация restore-заявки (`WalChain.Check` от wal_start) не
меняется — она не требует end-сегмента в `wal/`.

### 4.7. Ретенция `.partial` (`RetentionProcess.TickShardAsync`, шаг 4)

После среза финальных ниже cutoff — тот же list используется для
`SelectPartialForDeletion(names, cutoff)` (поглощённые + версии + ниже
cutoff) → ключи добавляются в тот же batch-delete. Cutoff отсутствует
(нет verify-OK) — только поглощённые/версии (cutoff=null). Канон §4 п.5:
«.partial-объекты чистятся двумя путями … мусор этого же прохода».

### 4.8. wal-sweeper — фоновый цикл глобального лидера

- **`WalSweeperProcess`** (`PgWorker.Backups/Supervisor/`, новый — паттерн
  `BackupOrphanSweeper`): один проход:
  1. гвард: глобальный лидер `/pgworker/leader`; `Enabled=false` → no-op;
  2. перебор живых кластеров (`/clusters/`, State ≠ ToRemove) и их шардов
     (не ToRemove): per-shard независимо, ошибка/пропуск шарда не
     останавливает остальные (journal-факт при ошибке);
  3. резолв пула кластера (policy.s3): нет/Failed → шард skip (ретенция
     молчит симметрично);
  4. list `wal/` шарда — соло, первая доступная нода (инвентарная
     семантика §5; повторные проходы досматривают лаг mesh);
  5. cutoff = `RetentionPlanner.LatestVerifiedWalStart(полных ИЗ
     оставляемых)` — отбор оставляемых повторяет `SelectKeep` (те же
     входы: COMPLETED-полные шарда из etcd-снапшота + policy; «по факту
     ретенционного отбора»); нет OK-полного → cutoff=null;
  6. список на удаление = `SelectWalForDeletion` (финалы ниже cutoff;
     cutoff=null → пусто) + `SelectPartialForDeletion` (.partial-гигиена:
     поглощённые, устаревшие версии, ниже cutoff) → ОДИН batch-delete на
     шард (пусто — no-op); идемпотентно;
  7. per-shard метрика успешного прохода (Р20).
- **`WalSweeperLoop`** (`src/PgWorker.App/Loops/`, новый hosted-сервис —
  образец `BackupOrphanSweeperLoop`): лидерство /pgworker/leader (пере-захват
  ≤ TTL), интервал **60 с** (константа, internal для тестов; канон «не реже
  раза в минуту»), сон Task.Delay с токеном отмены (цикл вне
  LoopsVitality/HealthState — живость только метрики
  LoopTick/LoopDuration), отмена по потере
  leader-lease (гвард arch/17 S5). Врезка в `Program.cs` рядом с
  BackupOrphanSweeperLoop. НЕ встраивается в существующий цикл
  orphan-sweeper (его `Supervisor:IntervalSec=600 с` нарушает «раз в
  минуту»).
- **Метрики** (`Shared.Metrics.Worker`, arch/18 §2.2 — правка раздела 3):
  `LoopTick/LoopDuration` для `loop="wal-sweeper"` + gauge
  `worker_wal_sweep_shard_last_success_timestamp_seconds{cluster,shard}`
  (обновляется по факту успешного per-shard прохода; серия исчезает, когда
  шард исчез из живых); алерты WalSweepStalled/WalSweepShardStale — панель
  (AlertEngine-паттерн OrphanSweepStalled; свечение — как у прочих
  worker-алертов панели).

### 4.9. Конфиг/env-доставка

- `BackupsOptions`/`BackupsRuntimeOptions` (воркер): + `Wal
  { PartialIntervalSec = 3 }` (биндинг
  `PgWorker:Backups:Wal:PartialIntervalSec`; валидация: значение < 1 —
  fail-fast старта, как у прочих отрицательных порогов §9);
- `NodeBackupEnv` + поле `PartialIntervalSec`; `Program.cs` (воркер)
  передаёт из конфига; `ClusterDriver.EnsureNode` ставит env
  `PGW_WAL_PARTIAL_INTERVAL_SEC` (паттерн `PGW_BACKUP_STAGING_DIR`):
  значение применяется при создании ноды (смена конфига — при пересоздании
  нод; дефолт 3 в приёмнике покрывает живые ноды).

### 4.10. Панель

Без правок: панель читает etcd wal-ключ (формат не меняется) и S3-инвентарь
«Место» (сумма размеров честно включает `.partial` до зачистки sweeper'ом).
Толерантность парсеров не задевается.

## 7. Принятые решения (развилки) — ПОЛНЫЙ СПИСОК

Формат: **развилка → решение → обоснование** (канон/код/надёжность).

1. **Формат ключа `.partial`** → `wal/<segment>.<endLsn>.partial`;
   `<segment>` — 24 hex строчных, `<endLsn>` — РОВНО 16 hex строчных (LSN
   конца префикса). → Канон §3 задаёт форму `<segment>.<endLsn>.partial`;
   строчные — канон ключей `wal/` (§2/§3); фиксированная ширина суффикса
   делает лексикографический максимум = числовому (лучший выбирается без
   числового парсинга в сортировках).
2. **Что считать «валидным префиксом»** → конец последней ПОЛНОЙ WAL-записи
   по страничному парсеру (8 КиБ страницы, заголовки 40/24, записи не
   пересекают страницу, нули-добивка отсекаются). → Канон §3 дословно
   («до конца последней полной записи, без нулей-добивки»); postgres в
   recovery сам останавливается на конце валидных записей — частичная
   запись в объекте бессмысленна и ломала бы идентичность префиксов
   мастера/реплики.
3. **Значение порога байт** → 4 МиБ (1/4 сегмента), константа приёмника
   `PartialThresholdBytes` (internal, инъекция в тестах), конфигурации
   нет. → Канон называет порог без числа; §9 параметра не вводит; 4 МиБ
   ограничивает невыгруженный хвост при бурной записи, не плодя объекты;
   RPO-окно всё равно определяется интервалом 3 с.
4. **Доставка `Wal:PartialIntervalSec` в приёмник** → конфиг воркера
   `PgWorker:Backups:Wal:PartialIntervalSec` (дефолт 3, §9) → `NodeBackupEnv`
   → env ноды `PGW_WAL_PARTIAL_INTERVAL_SEC` → приёмник (дефолт 3 при
   отсутствии). → Канон называет параметр в стиле конфига воркера, а
   «конфигурации приёмника отдельной нет» (§9); образец — существующая
   доставка `PGW_BACKUP_STAGING_DIR`/`PGW_BACKUP_S3_CA_PEM` (код:
   NodeConfigBuilders/ClusterDriver/Program).
5. **Триггеры выкладки** → таймер 3 с И мгновенный сигнал из Append при
   приросте ≥ порога (TaskCompletionSource); памп — фоновая задача сессии
   (linked CTS). → Канон «каждые PartialIntervalSec и/или по порогу байт»;
   памп вне hot-path — стрим не блокируется ни на list, ни на put.
6. **Сверка «длиннее лежащей»** → перед каждым put версии — list узкого
   префикса `wal/<seg>.` (лучшая лежащая); новая ≤ лежащей → skip;
   list-отказ → skip тика (НЕ рвёт сессию). → Канон §3 «только ДЛИННЕЕ
   лежащей (сравнение по endLsn)»; фактическая сверка закрывает и версию
   соседа двойной архивации; skip при отказе — RPO-хвост доедет следующим
   тиком/финалом, стрим важнее.
7. **Гвард на `.partial`** → не ставится: put через `PutObjectAsync` без
   IWalSegmentGuard; `.history`-путь — без изменений (гвард остаётся:
   байты статичны, идемпотентно; вне буквы приказа). → Канон §3 «гвард —
   только на ФИНАЛЬНЫХ объектах», «правило "длиннее выигрывает" исключает
   конкурирующие байты по построению».
8. **Подтверждение слота и `.partial`** → подтверждение НЕ двигается
   (write/flush = конец последнего доставленного ФИНАЛЬНОГО сегмента). →
   Канон §3 «Инвариант подтверждения-по-доступности» не меняется;
   `.partial` — кэш-хвост без durability-гарантий.
9. **Поглощение версий финалом** → при закрытии сегмента приёмник удаляет
   все `wal/<seg>.*.partial` best-effort (list + batch-delete) ПОСЛЕ
   успешного финального put; докладывает sweeper. → Канон §3 «приёмник
   удаляет best-effort при закрытии; докладывает ретенционный проход».
10. **Копия байтов префикса** → снимок-копия из сегментного буфера (буфер
    остаётся в исключительном владении hot-path/пула). → Копия ≤16 МиБ раз
    в 3 с вне hot-path; передача буфера в async-put сломала бы инвариант
    владения SegmentBufferPool.
11. **Критерий закрытости дубля** → позиция сегмента набора СТРОГО ниже
    позиции активного сегмента источника (IDENTIFY_SYSTEM, свежее
    replication-соединение 127.0.0.1:5432) на МОМЕНТ ЗАЛИВКИ дубля. → Канон
    §2 дословно («сегмент набора, имя которого СТРОГО ниже текущего
    активного wal-файла источника», «по источнику на момент заливки»).
12. **IDENTIFY_SYSTEM отказ при дубле** → операция FAILED (однострочная
    причина; переснятие новым id). → Семантика §2 «резюмов нет — FAILED →
    переснятие»; источник только что отдал basebackup — отказ
    экстраординарен; молчаливый «пропустить дубль последнего» резал бы
    PITR-окно без следа.
13. **Verify и недублированный end-сегмент** → CheckRange принимает UNION
    имён `wal/` + `full/<id>/pg_wal/`; текст ошибки Walk'а уточнён. →
    Канон §5 п.2 уже снимает оба листа («list wal/ + list full/<id>/pg_wal/»);
    без union каждый полный с живым хвостом получал бы ложный permanent
    verify-FAILED «end missing in wal/» (регрессия Ф3/Ф0-инварианта
    «verify-цепь сходится»).
14. **Контроль: хвост потока** → `WalChain.TailOf`: max по
    (Tli,Log,Seg) между финальным LastSegment и лучшей `.partial`
    (схлопывание версий по сегменту); при равной позиции финал авторитетен;
    `last_uploaded_segment` — имя сегмента БЕЗ суффикса; непрерывность/дыры
    — только по финалам. → Канон §3 «Истина прогресса»: «хвост потока —
    максимальный валидный префикс: финальный объект сегмента либо лучший
    .partial… версии в дедупе схлопываются по сегменту»; дыры — домен
    финалов (`.partial` в цепь не входит, WalChain.Collect).
15. **resume приёмника и `.partial`** → БЕЗ изменений: старт от конца
    последнего ФИНАЛА (S3TailResolver игнорирует `.partial`). → Канон §3
    «Возобновление» — «граница закрытого сегмента»; старт с середины
    лишил бы сборщик TLI-заголовка сегмента; перечитка у источника
    идемпотентна, финал перекроет `.partial`.
16. **fetch-wal: поиск лучшей `.partial`** → финал по всем read-нодам
    (как сейчас) → везде NotFound → list `wal/<seg>.` ПО ВСЕМ нодам
    (union-максимум), GET найденного. → Канон §3.5/§5: чтение «где данные
    есть», максимум префикса; лаг mesh допускается — лучший по всем нодам
    даёт максимальный хвост; дедлайн 45 с покрывает узкие листинги
    (MaxErrorRetry=0).
17. **Ретенция и `.partial`** → ретенционный проход шага 4 чистит и
    `.partial` (SelectPartialForDeletion тем же list'ом, тот же
    batch-delete). → Канон §4 п.5 «.partial-объекты чистятся двумя
    путями: поглощение финалом… и общий порядок ниже cutoff» — «этого же
    прохода».
18. **Цикл wal-sweeper** → ОТДЕЛЬНЫЙ hosted-цикл WalSweeperLoop (глобальный
    лидер, интервал 60 с — константа), не в BackupOrphanSweeperLoop. →
    Канон §4 «отдельным ФОНОВЫМ циклом вне тиков», «НЕ РЕЖЕ раза в минуту
    по каждому шарду»; цикл orphan-sweeper тикает 600 с — интервал не
    подходит.
19. **Листинг и cutoff sweeper'а** → list соло-первой-доступной (инвентарная
    семантика §5); cutoff = LatestVerifiedWalStart(оставляемых по
    SelectKeep); cutoff нет → только поглощение/версии; шард без пула —
    skip; один batch-delete на шард; отказ шарда не валит остальные. →
    Канон §4 wal-sweeper + §5 семантика листингов; ложных удалений соло-лаг
    не даёт (поглощение безопасно: финал в листинге — версии мусор
    независимо от лага; ниже cutoff — направление среза не зависит от
    полноты листа).
20. **Метрики/алерты sweeper'а** → `worker_loop_last_success_timestamp_seconds{loop="wal-sweeper"}`
    + `worker_wal_sweep_shard_last_success_timestamp_seconds{cluster,shard}`
    + алерты WalSweepStalled / WalSweepShardStale (порог 180 с = 3×
    интервала). → Канон §4 «живость цикла — серия … плюс per-shard свежесть
    … паттерн OrphanSweepStalled» (arch/18 §2.2 — правка Ф0).
21. **Панель** → без правок. → Панель читает etcd wal-ключ (формат
    неизменен) и инвентарь «Место»; «панель» в списке читателей `wal/`
    закрывается контролем (хвост — в etcd) и инвентарём (сумма размеров);
    новых полей/ключей нет — толерантность парсеров не задета.
22. **Мало байт/нет валидного long-заголовка** → `.partial` не
    выкладывается до первой полной записи сегмента. → Имя сегмента требует
    TLI из long-заголовка; «нулевой» префикс бессмыслен; финал ниже уже
    держит цепь.
23. **Нулевой прирост против лежащей версии** → skip put (версии не
    пере-clayются, LastModified не дёргается). → Канон «только ДЛИННЕЕ
    лежащей»; «тишина» контроля на idle-шарде остаётся честной (и это
    корректно: новых байт нет).
24. **Стоп-гейты и partial-памп** → памп — часть сессии (linked CTS):
    STOPPED/WAL_CHAIN_ERROR/backups-disabled замирают его вместе со
    стримом. → Канон §3 «стоп-семантика приёмника»; отдельных состояний
    статус-ключа не вводится.
25. **Валидация конфига** → `PartialIntervalSec < 1` — fail-fast старта
    воркера; в приёмнике клэмп к ≥1. → Симметрия §9 «отрицательные пороги —
    fail-fast»; приёмник не падает на мусорный env (живая нода без
    пересоздания).

Ниже — решения уровня реализации, зафиксированные при детальном разборе кода
на этапе планирования (Фаза 3):

26. **(добавлено в Фазе 3) Потокобезопасность SegmentAssembler** → доступ к
    сегментному буферу сериализуется внутренним `lock` сборщика: `Append`
    (стрим-поток) и `PartialSnapshot` (памп-поток) выполняются под общим
    `private readonly object _sync`. → Памп — фоновая задача сессии, читает
    буфер параллельно с Append; без блокировки — гонка данных; копии
    ≤16 МиБ под lock — миллисекунды, вне hot-path критического пути
    подтверждения.
27. **(добавлено в Фазе 3) Тестовый шов источника в FullBackupOperation** →
    опциональный параметр конструктора
    `Func<WalReceiverOptions, IXLogReplicationSource>? sourceFactory = null`
    (дефолт `o => new NpgsqlXLogSource(o)`); прод-фабрика
    FullBackupOperationFactory не меняется. → Образец — `_sourceFactory`
    WalReceiverLoop; IDENTIFY_SYSTEM дубля покрывается юнитом без живого PG.
28. **(добавлено в Фазе 3) Ретраи put `.partial` без гварда** →
    `PutWithRetryAsync` получает параметр `bool useGuard = true`; `.partial`
    кладётся с `useGuard: false` (обычный `PutObjectAsync` пула). →
    Существующий метод при `IWalSegmentGuard`-цели погонял бы `.partial`
    через гвард байт-сверки, который для `.partial` каноном отменён.
29. **(добавлено в Фазе 3) Триггер порога — по LastAppendedLsn** → сигнал
    «приросло ≥ 4 МиБ» вычисляется по приросту `assembler.LastAppendedLsn`
    от последней выкладки, без сканирования записей в hot-path. → Скан
    валидного префикса на каждый чанк дорог; расхождение LSN/префикса ≤
    одной записи — триггер приблизительный, сама выкладка всё равно идёт по
    валидному префиксу (PartialSnapshot).
30. **(добавлено в Фазе 3) Локальный гейт прироста пампа** → в сессии живёт
    `lastPartialEndLsn` (Volatile): после list-сверки принимает
    max(собственная выкладка, лучшая лежащая версия); put выполняется только
    при EndLsn снимка строго больше. → Версия соседа двойной архивации
    глушит бесполезные put'ы до превышения; «только длиннее лежащей»
    выполняется и против соседа, и против себя.
31. **(добавлено в Фазе 3) Снятие per-shard серий исчезнувших шардов** → два
    метода метрик: `WalSweepShardUnix(cluster, shard, long? unix)` (null —
    удалить серию; образец `BackupWalLag`) и
    `WalSweepShardRetain(IReadOnlySet<(string, string)> live)` — проход
    удаляет серии шардов вне живых. → Иначе WalSweepShardStale ложно горит
    на удалённом шарде вечно.
32. **(добавлено в Фазе 3) Снапшот бэкапов в WalSweeperProcess** → процесс
    сам читает etcd: Range `/pgworker/backups/<C>/` →
    `BackupsParser.Parse(kvs, out _)`; policy —
    `backups?.Policy ?? new BackupPolicy(options.PolicyRetentionDays, …)`
    (образец RetentionProcess). → Процесс — фоновый цикл вне ReconcileLoop;
    ClusterBackups ему никто не передаёт.
33. **(добавлено в Фазе 3) Кодовое имя per-shard серии** → в коде

## 8. Критерии приёмки

1. **3 целевых E2E зелёные** (docker, Release, две отдельные команды
   сборки/прогона + E2ePrepare перед ними):
   - `E2eRestoreScenarios.Restore_TargetTime_PitrRollback`;
   - `E2eRestoreScenarios.Restore_Latest_RebuildsDestroyedShard`;
   - `E2eDrillScenarios.Drill_Failed_OnCorruptedWal`.
2. **Данные не теряются (RPO)**:
   - `.partial`-версия появляется в `wal/` не позднее ~3×`PartialIntervalSec`
     после записи в живой сегмент и растёт (каждая длиннее предыдущей);
   - restore latest по живому потоку доезжает до конца лучшего `.partial`
     (строки, закоммиченные после полного, восстанавливаются без закрытия
     сегмента — E2E-гейт фактом Restore_Latest + юнит-покрытие
     fetch-wal/TailOf);
   - подтверждение слота по-прежнему только после финальных put (юнит:
     confirmed = EndLsn финала).
3. **Гонка дубля устранена**: дубль не кладёт сегмент, живой в источнике
   (юнит: IDENTIFY_SYSTEM-фикстура); verify полного с живым хвостом — OK
   (union; юнит CheckRange); повторный put финала дублем — идемпотентен по
   гварду (существующее поведение сохранено).
4. **Чистка**: sweeper удаляет поглощённые/устаревшие/ниже-cutoff
   `.partial` одним batch-delete на шард (юнит); ретенция чистит `.partial`
   «этого же прохода» (юнит); Enabled=false → no-op обоих (юнит цикла).
5. **Наблюдаемость**: пер-шард серия свежести — юнит метрик-вызовов
   (`WalSweepShardUnix`/`WalSweepShardRetain`); серия
   `loop="wal-sweeper"` — LoopTick-механика, общая с orphan-sweep (юнит
   паттерна — существующий BackupOrphanSweeperLoopTests; отдельный юнит
   не заводится), проверяется по метрикам/логам E2E-прогона; алерты
   описаны в arch/18 §2.2.
6. **Нет регрессий**: полная серия E2eFixture (PgWorker.E2eTests) зелёная,
   кроме заведомо известных внеобластных фейлов (если появляются — роадмап
   `arch/roadmap/bugs.md`, не фикс здесь); юниты PgWorker.* зелёные;
   сборка Release без ворнингов (TreatWarningsAsErrors).
7. **arch-правки Ф0 закоммичены до кода** (arch-first; ревью сверяет
   соответствие).

## 9. Риски и их закрытие

| Риск | Закрытие |
|---|---|
| Парсер префикса разошёлся с форматом WAL конкретной PG-версии | Парсер консервативен: любая аномалия (нулевая длина, выход за буфер, остаток страницы < 24) — стоп на конце последней полной записи; неверный «короткий» префикс теряет лишь часть хвоста RPO, финал восстанавливает полный; юниты на эталонных байтовых фикстурах |
| list-сверка версии на каждый тик — лишний S3-трафик | Узкий префикс `wal/<seg>.` (1–2 ключа), тик 3 с; skip при нулевом приросте до list'а (локальная сверка первой) |
| Двойная архивация: одновременный put одной версии двумя приёмниками | Байты идентичны (strict-sync), ключ (endLsn) совпадает — идемпотентный put; правило «длиннее» на следующем тике сходится к одной лучшей |
| sweeper удаляет `.partial`, нужный читателю (restore идёт) | `.partial` не датирован «последним чтением», но: поглощение — только при живом финале (эквивалент по байтам начала); ниже cutoff — вне PITR-окна канона; версии — длиннейшая остаётся; restore/fetch-wal перечитывает по требованию |
| Много `.partial`-объектов между проходами sweeper'а (минута) | Копится ограниченно (версии одного-двух живых сегментов ×2 приёмника), поглощаются финалом немедленно (best-effort приёмника); объём квитируется ключом storage |
| фейк-позитив verify на union: сегмент набора «прикрывает» дыру в wal/ | Union только для диапазона [wal_start..end] (CheckRange); сегменты выше end игнорируются Walk'ом; дыры внутри диапазона детектируются как раньше |
| fetch-wal дедлайн 45 с пробит листингами | Листинги узкие, MaxErrorRetry=0; порог попыток прежний; повторные вызовы restore_command компенсируют моргания (канон §3.5) |
