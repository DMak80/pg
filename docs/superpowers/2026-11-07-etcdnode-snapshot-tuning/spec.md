# Spec: EtcdNode — точная настройка DR-слепков (ретенция 3 в S3, пауза внеочередных 5 с, подтверждение лидерных инвариантов)

Дата: 2026-11-07. Ветка: `feat-etcdnode-snapshot-tuning`. База: `main`
@ `e906f6d9` (компонент EtcdNode слит). Канон компонента:
`arch/etcdnode/` — обновляется этой задачей (arch-first).

## 1. Цель

Три точечные правки канонических значений и два подтверждаемых инварианта
существующей механики. Источник изменений значений — **приказ
пользователя** (пункты задачи; правило AGENTS.md «бюджеты/таймауты не
меняются молчаливо» соблюдено — значения меняются по явному приказу).

1. **Хранить не более 3 последних бэкапов в S3**: `RetentionObjects`
   28 → 3 (пар db+meta в bucket `etcd-backups`, префикс `etcd/`).
   Локальный кэш доводки `RetentionFiles=10` НЕ меняется (том
   `/snapshots` — кэш доставки, не бэкап; источник истины для
   восстановления — S3).
2. **Снимать слепки не чаще раз в 5 секунд**: `MinIntervalSec`
   300 → 5 — троттлинг ТОЛЬКО внеочередных слепков (пауза от последней
   подтверждённой выгрузки до следующего внеочередного снятия по важному
   изменению). Плановый интервал тишины `IntervalMin=360` и остальные
   бюджеты НЕ меняются.
3. **Снятие только на лидере** — существующее поведение, изменений кода
   НЕТ: слепок снимает lease-лидер `/etcdnode/leader`
   (канон `arch/etcdnode/01-agent.md` §4,
   `processes/c-snapshot-export.md` C0; код `AgentLoop.ExecuteAsync` —
   тик C1–C5 исполняет только `claims.IsLeader`, снятие — `SnapshotJob`
   c `http://localhost:2379` внутри тика лидера). Задача фиксирует это в
   каноне как явный инвариант и закрывает ассертом (§3.4).
4. **Смена лидера → СРАЗУ новый бэкап** — существующее поведение,
   изменений кода НЕТ: эталонная карта (`_baseline`) — память процесса
   лидера; у нового лидера эталона нет → первый тик внеочередной
   (RPO-консервативно, канон `arch/etcdnode/02-snapshots.md` §2/§3,
   C2 «нет эталона — важно»); гейт — только `MinIntervalSec` от последней
   выгрузки (с новым значением 5 с — секунды). CatchUp-доводка тут не
   конкурент: том нового лидера пуст (не-лидер не снимал). Задача
   фиксирует требование явно и закрывает ассертом (§3.4).
5. **Все бэкапы — ТОЛЬКО полные** — свойство механики
   `/v3/snapshot/save` (полный дамп пространства ключей;
   инкрементальных форм не существует): каждый хранимый бэкап автономен
   и полон — восстановление из ЛЮБОГО одного слепка, без цепочек. Канон
   фиксирует явно (§3.1), ассерт — согласованность пары db+meta (§3.4).

## 2. Принципы

- **Arch-first**: сначала `arch/`, затем код/конфиги/тесты. Канон —
  единственный источник значений.
- **Единая цепочка значений**: appsettings воркера →
  `EtcdProvisioningOptions` → env узла (`EtcdNodeSpecBuilder`) →
  дефолты `EtcdNodeEnv`. Все звенья и канонические листинги меняются
  согласованно, одни и те же числа везде.
- Подтверждаемые инварианты (пп. 3–5 цели) НЕ трогают механику: код
  расписания/диффа/ретенции не меняется, добавляются только ассерты.
- Миграций нет: система не запущена (решение пользователя), новые
  значения — просто новые канонические дефолты.

### 3.4. Тесты — ассерты инвариантов (пп. 3–5 цели) + сопутствующая правка

Все — в `src/tests/EtcdNode.IntegrationTests/SnapshotAgentTests.cs`
(окружение коллекции `EtcdNodeEnvironment` уже даёт 3 узла с живыми
агентами, ownS3-цель и хелперы `DockerAsync`/`ListDbObjectsAsync`);
механика агента/экспортёра при этом не меняется:

1. **Лидерное снятие (п. 3)** — проверка ВНУТРИ кейса
   `LeaderDown_StatusFrozenUntilTtl_ThenTakeover`, до `KillNodeAsync`
   (отдельный кейс НЕ заводится): после определения лидера по ключу
   `/etcdnode/leader` (Arrange-фаза кейса: посев цели, статус OK,
   тихая фаза уже пройдены) проверить, что локальный том `/snapshots`
   КАЖДОГО не-лидера не содержит файлов `snapshot-*.db` — слепки
   снимает только лидер. Обоснование места: порядок кейсов xUnit v3 не
   фиксирован, но единственный источник смены лидера в коллекции — kill
   внутри этого же кейса, поэтому на момент его Arrange лидер неизменен
   с сотворения контура и тома не-лидеров гарантированно пусты при
   любом порядке исполнения кейсов. Проверка — `docker exec <container>
   ls /snapshots` по контейнерам не-лидеров (публичный хелпер
   окружения, обёртка над `DockerAsync`; имена контейнеров — как в
   телеметрии teardown).
2. **Смена лидера → свежий бэкап (п. 4)** — дополнить тот же кейс
   `LeaderDown_StatusFrozenUntilTtl_ThenTakeover` явным ассертом
   свежести: после takeover в S3 появляется НОВАЯ пара
   `snapshot-*.db`+`.meta.json` с `taken_unix` новее момента смерти
   лидера (`kill`-времени), `instance` меты — имя узла нового лидера
   (по значению `/etcdnode/leader` после takeover). Существующий
   ассерт роста mod_revision статус-ключа остаётся.
3. **Полные/самодостаточные бэкапы (п. 5)** — дополнить кейс
   `Leader_Elected_StatusWritten_ObjectsInS3`: для свежей пары скачать
   `.db`-объект и ассертить согласованность меты: `size_bytes` ==
   фактический размер скачанного `.db`; `sha256` меты == sha256
   скачанных байтов; `revision` меты не null и > 0 (полный слепок
   несёт ревизию кластера; пара db+meta самодостаточна).
4. **Сопутствующая правка (следствие `RetentionObjects=3` в общем
   bucket коллекции)** — кейс `ImportantChange_Triggers_Snapshot`:
   заменить счётный ассерт (рост числа `.db` «after > before») на
   детекцию НОВОГО `.db`-ключа вне отсечки известных (паттерн кейса
   `Leader_Elected_StatusWritten_ObjectsInS3`: `knownKeys` до Act →
   поллинг ≤ 30 с). Причина: bucket один на коллекцию, экспортёр-кейсы
   (вкл. `Retention_RemovesOldestPair`) оставляют ≥3 пар, ретенция
   агента (N=3) сносит старейшую при новой выгрузке — рост счётчика не
   детерминирован, возможен ложный падёж.

## 4. Ограничения

- НЕ меняются: `IntervalMin=360`, `RetryIntervalSec=300`,
  `TimeoutSec=30`, `RetentionFiles=10`, `MaintenanceIntervalMin=60`.
- НЕ меняются: механика расписания (`SnapshotSchedule`), фильтр
  важности (`ChangeMapDiff`/`PulseKeys`), S3-ретенция
  (`EtcdExportRetention.Select` — логика), форматы объектов/меты/
  статус-ключа, `backups/06-s3-layout.md`.
- Fail-fast валидация env не меняется (3 ≥ 1 и 5 > 0 — валидны).
- Миграционных шагов для установок/стенда НЕТ (система не запущена —
  решение пользователя); env узлов иммутабелен, новые узлы создаются с
  новыми значениями.
- `RetentionFiles=10` остаётся и в каноне, и во всех звеньях.

## 5. Принятые решения (все развилки закрыты)

1. «Не более 3 бэкапов» → ТОЛЬКО S3-пары (`RetentionObjects=3`);
   локальный кэш `RetentionFiles=10` не трогаем (кэш доводки, не
   бэкап). — ответ пользователя.
2. «Не чаще раз в 5 секунд» → ТОЛЬКО `MinIntervalSec` (внеочередной
   троттлинг) 300 → 5; плановый `IntervalMin=360` не трогаем. — ответ
   пользователя.
3. Применимость к существующим установкам → миграции НЕТ, система не
   запущена; новые значения — новые канонические дефолты без
   переходных шагов. — ответ пользователя.
4. Лидерное снятие → существующее поведение (код/канон уже реализуют);
   изменений кода нет; добавляется интеграционный ассерт пустоты тома
   не-лидеров. — по природе пункта (подтверждение).
5. Смена лидера → свежий бэкап → существующее поведение
   (`_baseline`-память процесса: у нового лидера эталона нет — первый
   тик внеочередной, гейт только `MinIntervalSec`); изменений кода нет;
   takeover-кейс дополняется ассертом новой пары с `taken_unix` новее
   смерти лидера. — по природе пункта (подтверждение); «СРАЗУ»
   понимается как первым тиком нового лидера в пределах троттлинга
   `MinIntervalSec` (с 5 с — секунды).
6. «Только полные» → свойство `/v3/snapshot/save`; фиксируется в каноне
   (`02-snapshots.md` §2) и ассертом согласованности пары db+meta
   (size/sha256/revision). Отдельный «формат полноты» не вводится —
   форматов других нет.
7. Тестовое окружение `EtcdNodeEnvironment`: `RETENTION_OBJECTS`
   приводится к канону (3); `MIN_INTERVAL_SEC=1` остаётся осознанным
   ускорением поведенческих кейсов. — решение по канону (окружение
   эмулирует реальные узлы; ускорение интервалов — прецедент этого же
   окружения).
8. Явные кортежи `EtcdProvisioningOptions` в тестах EtcdWorker
   обновляются к каноническим значениям (ассерты от старых чисел не
   зависят, кроме `AgentEnvPresent` — обновляется вместе). — решение по
   канону (консистентность).
9. Пассаж RPO в `03-restore.md` п.6 («≈5 мин») синхронизируется с
   новым `MinIntervalSec=5` («≈5 с»). — следствие решения 2.

## 6. Критерии приёмки

1. **Канон**: `grep -rn "MinIntervalSec=300\|MIN_INTERVAL_SEC=300\|RetentionObjects=28\|RETENTION_OBJECTS=28\|N=28\|≈5 мин" arch/` — пусто (в `arch/` не остаётся ни старых значений, ни пассажей «≈5 мин»: правятся `03-restore.md` п.6 и `06-operability.md` §3; «−5 мин»/«~25 мин» в других документах паттерном не матчатся); в `arch/etcdnode/02-snapshots.md` §2 есть явный инвариант полных/автономных бэкапов и немедленного слепка нового лидера.
2. **Код/конфиги**: `MinIntervalSec=5` и `RetentionObjects=3` в `src/EtcdNode.App/Options.cs` (класс и `EtcdNodeEnv.Load`), `src/EtcdWorker.App/Options.cs`, `src/EtcdWorker.App/appsettings.json`; `RetentionFiles=10` и `IntervalMin=360` нетронуты везде.
3. **Юниты**: `EtcdNode.UnitTests` и `EtcdWorker.UnitTests` зелёные (вкл. обновлённые ассерты дефолтов и `AgentEnvPresent` → `"3"`).
4. **Интеграции EtcdNode** (ПОСЛЕ пересборки образа — см. п.6): зелёные, вкл. три ассерта инвариантов: том не-лидеров пуст (проверка внутри takeover-кейса до kill); после takeover — новая пара с `taken_unix` новее kill и `instance` = новый лидер; мета свежей пары согласована со скачанным `.db` (size/sha256/revision); переработанный `ImportantChange_Triggers_Snapshot` (детекция нового `.db` вне отсечки `knownKeys`) зелёный.
5. **Интеграции EtcdWorker** (после той же пересборки): зелёные (вкл. `MembershipProcessTests` с обновлённым кортежем).
6. **Пересборка образа узла**: интеграционные серии EtcdNode/EtcdWorker гейтятся на ГОТОВЫЙ `pgworker/etcdnode:dev` — после правки `Options.cs` образ ПЕРЕСОБРАТЬ (команды из шапки `docker/etcdnode/Dockerfile`: `dotnet publish src/EtcdNode.App -c Release -r <rid> --self-contained -o artifacts/etcdnode` + `docker build -f docker/etcdnode/Dockerfile --build-arg ETCDNODE_PUBLISH_DIR=artifacts/etcdnode -t pgworker/etcdnode:dev .`), иначе контейнеры продолжат работать со старым бинарём.
7. **Серии — с зачисткой** между прогонами (AGENTS.md: контейнеры/сети/тома; сети per-cluster ryuk не подбирает). PgWorker-E2E серия НЕ требуется — код PgWorker не меняется, изменённые компоненты покрыты своими юнит/интеграционными сериями.
8. Тестовые значения обновлены: `EtcdNodeEnvironment` (`RETENTION_OBJECTS=3`, `MIN_INTERVAL_SEC=1` с комментарием), `EtcdNodeEnvTests` (5/3), `EtcdNodeSpecBuilderTests`/`MembershipProcessTests` (5/3).
