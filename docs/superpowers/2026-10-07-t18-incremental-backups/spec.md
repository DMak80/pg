# Spec: t18 (переопределена) — целевая схема бэкапов: суточный полный + WAL, три GFS-точки, WAL-pruning после verify

Тег roadmap: `t18-incremental-backups` (трек reliability). Исходная
формулировка t18 (инкрементальные полные PG17+ `pg_incremental_backup` /
`pg_combinebackup`) ОТКЛОНЕНА пользователем 2026-10-07: инкрементальных
бэкапов в системе НЕ будет. Задача переопределена на сверку системы с
целевой схемой бэкапов пользователя; по критерию пользователя («нужны
доработки — спека; нет — закрыть») сверка дала расхождения — этот документ
описывает доработки. Канон подсистемы: `arch/19-backups.md`.

## 1. Целевая схема пользователя (требования 1–5, дословно)

1. Полный бэкап — КАЖДЫЙ ДЕНЬ (ежесуточно).
2. Храним ровно ТРИ полных: последний + один полный 7-дневной давности +
   один полный месячной давности (на недельной позиции — ОДИН полный, на
   месячной — ОДИН; промежуточные суточные НЕ хранятся).
3. В течение дня бэкапятся ТОЛЬКО WAL-файлы (непрерывная архивация);
   восстановление — накат WAL поверх полного.
4. Инкрементальных бэкапов НЕТ и НЕ ДЕЛАЕМ.
5. WAL-файлы старше последнего полного ДОЛЖНЫ БЫТЬ УДАЛЕНЫ ПОСЛЕ создания
   полного И ЕГО ПРОВЕРКИ (verify): прунинг WAL без успешно пройденного
   verify нового полного запрещён.

Прочтение «7-дневной/месячной давности» закреплено уточнением самого
пользователя «на недельной позиции — ОДИН полный, на месячной — ОДИН»:
это GFS-ПОЗИЦИИ — недельная точка = последний полный предыдущей
календарной ISO-недели (возраст 1–14 сут), месячная = последний полный
предыдущего календарного месяца. Храним ровно три ПОЗИЦИИ: суточную
(последний), недельную, месячную.

Сопутствующее (вытекает из правки 5): стартовая точка контроля непрерывности
цепочки (`chain_start`, §3) сегодня = min `wal_start` всех COMPLETED-полных
(`WalStreamProcess` → `WalChain.RatchetedStart`). После переноса cutoff на
последний полный сегменты старейшего оставляемого будут удалены — контроль,
стартующий от них, увидит «дыру» и даст ЛОЖНЫЙ `BROKEN` (останов агентов +
шторм пересъёмов). Старт контроля обязан перескочить на ту же точку, что и
cutoff ретенции.

## 3. Цель

Система бэкапов шардов работает по целевой схеме 1–5 из коробки, без
ручных policy-ключей: ежесуточный полный (уже есть), три GFS-точки
хранения по умолчанию, WAL-прунинг по последнему верифицированному полному
с жёстким гвардом «без успешного verify — не срезать». Прежними остаются
guard последнего COMPLETED, идемпотентность/DELETING-фаза, R4
(«данные дороже места» — ретенция остаётся единственным удаляющим).

## 4. Принципы

- **Arch-first**: сначала правки канона `arch/19-backups.md` (§3, §4, §5,
  §9), затем код, зеркалящий его.
- **Минимальная поверхность**: меняются только дефолт ретенции, точка
  WAL-cutoff (+ гвард verify) и связанная с ней стартовая точка контроля
  цепочки. Механика GFS-отбора, DELETING-доводка, guard последнего,
  приёмник WAL, verify-джоб, restore — БЕЗ изменений.
- **Verify как ключ ретенции WAL**: cutoff = `wal_start_segment` новейшего
  COMPLETED-полного с `verify.state=OK` ИЗ ОСТАВЛЯЕМЫХ — кандидат удаления
  текущего прохода точкой cutoff не якорит (переходное окно без RPO-дыры).
  Это одновременно и «срезаем после создания полного и его проверки»
  (новый полный с OK поднимает cutoff), и «прунинг без успешного verify
  запрещён» (PENDING/FAILED/нет verify — cutoff держится на предыдущем
  OK-полном; OK-полного нет вовсе — WAL не чистится).
- **Одна точка отсчёта**: cutoff ретенции и `chain_start` контроля цепочки
  вычисляются от ОДНОЙ точки (новейший verify-OK полный из оставляемых).
  Ложный BROKEN даёт расщепление точек только в одну сторону — контроль
  НИЖЕ cutoff; переходное окно допускает безопасное расщепление в
  обратную сторону (контроль выше cutoff — якорится на кандидате удаления
  текущего прохода, нижележащий cutoff режет меньше).
- **Осознанное следствие схемы** (фиксируется в каноне): недельный и
  месячный полные восстановимы ДО СОБСТВЕННОЙ точки съёма (WAL их
  `-X stream`-набора лежит при них в `full/<id>/pg_wal/`); накат WAL поверх
  них невозможен — WAL ниже последнего полного срезан. PITR с накатом —
  только от последнего валидного полного. Restore-заявка от старого
  полного с целью позже его точки честно падает на валидации цепочки
  (permanent-отказ с границами) — существующее поведение, не регресс.

## 5. Структура изменений

### 5.1. Канон `arch/19-backups.md`

1. **§9 (конфигурация)** — дефолт ретенции: `Retention { Days=1, Weeks=1,
   Months=1 }` (было `Days=7, Weeks=4, Months=6`). Той же правкой — пример
   policy-ключа в таблице §4: `{"retention":{"days":1,"weeks":1,"months":1},…}`.
   Семантика counters НЕ меняется (weeks/months — счётчики позиций
   предыдущих недель/месяцев; при 1/1/1 — ровно по одной).
2. **§4 п.5 «Чистка WAL»** — новая формулировка правила: cutoff =
   `wal_start_segment` новейшего COMPLETED-полного с `verify.state=OK`
   ИЗ ОСТАВЛЯЕМЫХ — кандидат удаления текущего прохода (Delete[0]
   GFS-отбора) точкой cutoff не якорит: в переходном окне, где новейший
   OK-полный сам стал кандидатом удаления, привязка cutoff к нему срезала
   бы WAL между предыдущим OK-полным и ним (RPO-дыра после доводки
   DELETING); удаляются сегменты строго ниже cutoff (сравнение по позиции
   при равном TLI, весь TLI ниже стартового, вкл. `.history` тех TLI —
   как сейчас); verify-OK-полного нет → WAL не чистится (нет безопасной
   точки привязки). Явный запрет: прунинг WAL ниже точки полного, не
   прошедшего verify (PENDING/FAILED), не выполняется.
3. **§3 (правила непрерывности)** — стартовая точка контроля цепочки:
   `chain_start` = `wal_start_segment` новейшего COMPLETED-полного с
   `verify.state=OK` из оставляемых (было — «старейшего COMPLETED»);
   контроль НИЖЕ cutoff = ложный BROKEN; обратное расщепление переходного
   окна (контроль выше cutoff — по кандидату удаления текущего прохода)
   безопасно — нижележащий cutoff режет меньше; полных нет → первый
   сегмент потока (как сейчас); ratchet (`chain_start` не понижается)
   сохраняется. Строка «Ретенция (t06) чистит сегменты ниже стартовой
   точки старейшего ОСТАВЛЯЕМОГО полного» переформулируется на новую точку
   cutoff; фраза «chain_start поднимается автоматически при следующем
   контроле» остаётся верной.
4. **§5 (ретенционная чистка)** — синхронное обновление формулировки
   cutoff (та же точка, что §4 п.5: новейший verify-OK полный из
   оставляемых).
5. **§10 (риски) или §4** — осознанное следствие: старые GFS-точки
   (недельная/месячная) восстановимы только на собственную точку съёма;
   PITR-накат — от последнего валидного полного (см. §4 принципов).

### 5.2. Код (`src/PgWorker.Backups`)

1. **`Options.cs`** — дефолты `PolicyRetentionDays 7→1`,
   `PolicyRetentionWeeks 4→1`, `PolicyRetentionMonths 6→1`.
2. **`Retention/RetentionProcess.cs`** (шаг 4, чистка WAL) — cutoff:
   вместо `min(wal_start оставляемых COMPLETED)` — `wal_start` новейшего
   по `started_unix` COMPLETED-полного с `Verify is { State: Ok }` ИЗ
   ОСТАВЛЯЕМЫХ (remaining — исключая Delete[0] текущего прохода: кандидат
   удаления точкой cutoff не якорит); такого
   нет → шаг no-op (WAL не трогаем). Выбор кандидата GFS-отбора и
   DELETING-доводка — без изменений.
3. **`WalStreamProcess.cs`** — `chain_start`: в `RatchetedStart`
   передаются wal_start только COMPLETED-полных с `verify.state=OK`
   (новейшего по ratchet-правилу, по всем полным — в переходном окне
   контроль может якориться выше cutoff ретенции: безопасное расщепление,
   нижележащий cutoff режет меньше, ложного BROKEN нет); ratchet не
   понижается — как сейчас.
   Логика BROKEN/DEGRADED, `CheckWithRestart`, history-fallback — без
   изменений.
4. **`Retention/RetentionPlanner.cs`** — `SelectWalForDeletion` без
   изменений (cutoff приходит аргументом); при необходимости — чистый
   хелпер выбора «новейшего verify-OK полного» (юнит-тестируемый, общий
   для RetentionProcess и WalStreamProcess).
5. **Панель** — правок нет: policy читается nullable-полями, панельных
   дефолтов ретенции нет; алерты не зависят от точки cutoff.

### 5.3. Тесты

- Юнит `RetentionProcess`/`RetentionPlanner`:
  - дефолт 1/1/1: в установившемся ряду суточных полных остаются ровно
    три позиции (последний + недельная + месячная), промежуточные — в
    Delete;
  - cutoff: последний полный verify=PENDING/FAILED → WAL ниже его
    wal_start НЕ удаляется; verify=OK → удаляется всё строго ниже;
    OK-полного нет → прунинг no-op;
  - недельная/месячная точки (вне дневного окна) НЕ влияют на cutoff.
- Юнит `WalStreamProcess` (контроль цепочки): после среза WAL ниже
  последнего verify-OK полного контроль стартует от него — ложный BROKEN
  отсутствует; ratchet не понижается при появлении нового OK-полного.
- Существующие тесты ретенции/цепочки — прогон, актуализация fixtures под
  новые дефолты (было 7/4/6 — теперь 1/1/1 в ожиданиях).

## 8. Ограничения

- Переходные окна GFS (смена недели/месяца, один DELETING за проход
  `Retention:IntervalSec`) кратковременно дают 4 COMPLETED-записи до
  доводки удаления — норма механизма, «ровно три» — про позиции.
- Дефолт 1/1/1 — выбор этой спеки: целевая схема пользователя обязана
  работать из коробки; per-cluster policy-ключ по-прежнему перекрывает
  дефолт (механизм сохранён для будущих кластеров с иными потребностями).
- Guard «последний COMPLETED не удаляется НИКОГДА» сохраняется без
  изменений (даже просроченный по GFS).
- verify-перепроверка по `verify.interval_sec` (тихая порча S3) остаётся:
  полный, чей verify перешёл OK→FAILED при перепроверке, перестаёт быть
  точкой cutoff (cutoff откатывается к предыдущему OK) — прунинг WAL
  запрещён, пока не появится новый OK-полный; уже срезанный WAL не
  вернуть (RPO-риск тихой порчи последнего полного принят существующим
  алертом `backup-verify-failed` + переснятием планировщиком).
- Код фазы 1 не трогался (только чтение для сверки).

## 9. Критерии приёмки

- **AC1** (ретенция 1/1/1): юнит — на ряду суточных COMPLETED-полных
  старше трёх месяцев Keep = {последний, недельная позиция, месячная
  позиция}, все промежуточные суточные — в Delete; дефолт конфига
  `Days=1, Weeks=1, Months=1`.
- **AC2** (cutoff по последнему verify-OK): юнит — при последнем полном
  `verify=OK` к удалению отметаются все WAL-сегменты строго ниже его
  `wal_start` (вкл. `.history` низких TLI), сегменты от cutoff и новее не
  трогаются; недельный/месячный полные на cutoff не влияют.
- **AC3** (гвард verify): юнит — последний полный `verify=PENDING` или
  `FAILED` → прунинг WAL ниже его `wal_start` НЕ выполняется (cutoff на
  предыдущем OK); ни одного OK-полного → WAL-чистка no-op.
- **AC4** (контроль цепочки): юнит — после среза WAL ниже cutoff контроль
  непрерывности стартует от `wal_start` новейшего verify-OK полного,
  `BROKEN` не ставится; ratchet `chain_start` не понижается.
- **AC5** (регресс restore): существующий путь restore latest (новейший
  полный + накат WAL) проходит на актуальных тестах без правок механики.
- **AC6** (канон и roadmap): `arch/19-backups.md` отражает новые дефолт и
  правило cutoff/гварда verify + стартовую точку контроля; пункт t18 снят
  из `arch/roadmap/reliability.md` и `reliability-report.md` мерж-коммитом.
