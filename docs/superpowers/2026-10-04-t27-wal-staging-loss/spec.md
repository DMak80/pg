# t27-wal-staging-loss — собственный WAL-приёмник с подтверждением по доставке + двойная архивация

Спецификация фазы 1 (dev-flow). Канон — [`arch/19-backups.md`](../../../arch/19-backups.md) §2/§3/§4/§6/§9/§10, обновлён этой задачей arch-first (правки канона — часть данной фазы, см. §7). Исходная формулировка — [`arch/roadmap/reliability.md`](../../../arch/roadmap/reliability.md), пункт `t27-wal-staging-loss`.

## 1. Контекст и цель

### 1.1 Ошибочная ситуация (сегодня)

Wal-агент — bash-контейнер (`pg_receivewal --slot` в staging-том +
`find → mc cp → rm`, `src/PgWorker.Backups/WalAgentCommand.cs`): слот
подтверждается по факту ЗАПИСИ в staging (fsync), staging-том — единственная
копия недоставленного в S3. При любом пересоздании агента воркер удаляет
контейнер вместе с томом (`ClusterDriver.RemoveBackupAgentsAsync` — rm
`{agent}-staging`), новый `pg_receivewal` возобновляет со позиции слота
(`restart_lsn` уже ушёл за потерянные сегменты) — закрытые, но недоставленные
сегменты теряются безвозвратно: цепочка в S3 получает дыру, контроль
переводит ключ `wal` в `BROKEN`, лечение — пересъём полного бэкапа (RPO WAL
на всё окно пересъёма). Пересоздание — штатные операции супервиза: exited,
смена мастера (failover), устаревшие креды, стоп-семантика `Enabled=false`,
QUARANTINED; в multi-host при потере docker-хоста агент пересоздаётся на
другой машине — staging-том исходного хоста недоступен в принципе.

### 1.2 Цель (две ортогональные оси, вместе — RPO=0 подтверждённых транзакций при потере любой одной машины)

1. **Подтверждение по доставке, не по записи** — `restart_lsn` слота никогда
   не уходит за последний фактически доставленный в S3 сегмент: подтверждение
   приёмника — успешный put в S3. Любой рестарт агента возобновляет стрим от
   хвоста S3 и досыпает дыру из удерживаемого слотом WAL. Механика —
   СОБСТВЕННЫЙ WAL-приёмник (физическая репликация, COPY-протокол
   `START_REPLICATION`) вместо `pg_receivewal`.
2. **Двойная архивация (вариант (б) оси избыточности источника)** — агенты на
   мастере И sync-standby пишут в один префикс `wal/`: имена сегментов
   детерминированы (WAL обеих нод одной цепочки идентичен), put идемпотентен,
   дедуп не нужен; контроль склеивает union без изменений. Инвариант нод
   `synchronous_mode=true` (arch/05): WAL подтверждённого изменения физически
   в `pg_wal` обеих нод — потеря любой ОДНОЙ машины (мастер, реплика,
   docker-хост агента) не рвёт цепочку.

Граница гарантий: WAL после последнего sync-подтверждения физически есть
только на мастере — незакоммиченные транзакции, вне RPO durable.

Выбор комбинации согласован с пользователем: обе оси реализуются в t27;
вариант оси 2 — двойная архивация; приёмник — отдельный образ; staging-том
у агентов упраздняется.

## 2. Принципы

- **Arch-first**: `arch/19` — источник истины; код зеркалит его. Правки
  канона выполнены в этой фазе (§7) до кода.
- **Durability только от реплицированного S3** (AGENTS.md «multi-host»):
  локальное состояние агента (буфер сегмента в памяти) — кэш без гарантий;
  гарантии строятся от объектов S3 и подтверждений ПОСЛЕ фактического put.
  Вопрос ревью «что теряется при отключении машины X» — ответ: ничего из
  подтверждённого (сегменты в S3; недоставленное удерживается слотами всех
  нод-источников).
- **Истина прогресса — S3**: агент пишет только объекты; etcd-ключ `wal`
  пишет только воркер из list-наблюдений (без изменений).
- **Идемпотентность каждого шага, transient vs permanent** (arch/17): put
  идемпотентен по имени; ensure слота/агента идемпотентны; обрывы —
  transient с циклическим переподключением.
- **Протокол агента — env-параметры + stdout-JSON-маркеры** (как джобы §2):
  агент etcd не знает; секреты только в env.
- Ставка на собственный приёмник: `pg_receivewal` не позволяет подтвердить
  слот по внешнему событию (S3-put) — расширению не подлежит, заменяется.

## 3. Структура и компоненты

### 3.1 WAL-приёмник — новый проект `src/PgWorker.WalReceiver`

Консольное .NET-приложение (entrypoint образа агента, §3.2). Зависимости:
`Npgsql` (10.0.3, физическая репликация COPY-протоколом), `AWSSDK.S3`
(put/list — тот же стек, что `BackupS3` воркера); ProjectReference на
`PgWorker.Backups` — реюз `WalFileName` (LSN-математика имён сегментов),
`WalChain` (непрерывность/хвост), `IBackupS3` (put/list). Ссылка тянет и
оркестрационные зависимости Backups (Docker/Provisioning) — осознанная плата
за единую математику сегментов с контролем воркера (без дублирования
WalFileName; усечение зависимостей — отдельная задача, не t27).

Механика (главный цикл):

1. **Старт**: подключение к источнику (replication-соединение, роль
   `backup_exec`, sslmode=require); сверка `wal_segment_size` (SHOW) с
   `WalFileName.SegmentBytes` (16 МиБ, канон arch/14) — расхождение →
   permanent-выход с ошибкой (математика имён не должна молча врать).
2. **Резолв хвоста S3**: list префикса `<C>/<X>/wal/` → последняя
   непрерывная позиция цепочки (`WalChain`) → стартовая LSN = конец
   последнего закрытого сегмента. Пустой префикс (первый старт) — от
   `restart_lsn` слота (читается из `pg_replication_slots` по replication
   или SQL-соединению). Стартовая позиция передаётся в `START_REPLICATION
   SLOT <slot> PHYSICAL <lsn>` явно; `restart_lsn` для старта после первого
   сегмента не используется.
3. **Приём**: чтение XLogData, буфер текущего незакрытого сегмента в памяти
   (≤ `SegmentBytes`); границы сегментов — из LSN сообщений
   (walStart/конец данных), имя — `WalFileName` от LSN. Сегмент закрыт —
   **put `wal/<segment>`** (checksum SHA256 с серверной сверкой —
   `PutObjectAsync`); `.history` при наблюдении первого сегмента нового
   TLI — запрос `TIMELINE_HISTORY` протокола → put `wal/<tli>.history`
   (если Npgsql не экспонирует запрос — см. §7 риски, fallback: воркер
   докладывает docker-exec'ом ноды по факту контроля «TLI-переход без
   history-объекта»).
4. **Подтверждение (инвариант оси 1)**: standby status update
   (write=flush=applied) с LSN = конец последнего доставленного в S3
   закрытого сегмента — ТОЛЬКО после успешного put; периодические keepalive
   с той же позицией. Пока put невозможен (S3-отказ) — чтение потока
   остановлено (backpressure: сервер ждёт подтверждения), ничего не
   теряется, слот удерживает.
5. **Обрывы**: обрыв соединения/рестарт источника — transient: циклическое
   переподключение (задержка ≤ 5 с) с повтором резолва хвоста S3; процесс
   не завершается. Permanent (несовместимый segment size, невалидные
   env/креды конфигурации) — выход с ненулевым кодом и result-JSON;
   супервиз воркера реагирует пересозданием со свежими env.

Контракт env (все параметры; секреты — только env, в argv/логи не попадают):
`PG_HOST, PG_PORT, PG_USER, PG_PASSWORD, PG_DBNAME, SLOT, CLUSTER, SHARD,
S3_ENDPOINT, S3_REGION?, S3_BUCKET, S3_ACCESS_KEY, S3_SECRET_KEY,
S3_PATHSTYLE`. Прогресс — stdout-JSON-маркеры
(`{"phase":"starting"|"streaming"|"delivering", ...}`, heartbeat с текущей
позицией, result-JSON при выходе) — по образцу протокола джобов §2; воркер
парсирует только свои строки.

### 3.2 Образ `pgworker-wal` — `docker/PgWorker.Wal.Dockerfile`

База — `mcr.microsoft.com/dotnet/runtime` (образ уже в локальном registry
стенда по правилам зеркалирования; если базового образа нет — добавить в
`dev-stand/images/images.txt` + `mirror-image.sh`). Внутри — опубликованный
бинарь `PgWorker.WalReceiver`; ENTRYPOINT — приёмник (без shell-обёртки).
Сборка — `pgworker-wal:dev` (локально собираемый, в registry НЕ класть —
канон AGENTS.md). Образ джобов `pgworker-backup` (bash+mc+postgres-утилиты)
не меняется — полные/verify/restore/drill остаются на нём.

### 3.3 Оркестрация воркера — `WalStreamProcess` (переработка)

Шаги тика шарда (порядок сохраняется из текущей реализации):

1. Гварды без изменений: restore-гвард, креды `/clusters/<C>/backup_password`,
   QUARANTINED-стоп, Enabled=false-стоп.
2. **Резолв ДВУХ источников**: мастер (существующий `ResolveMasterAsync`) +
   sync-standby (новый резолв по образцу `ResolveBackupSourceAsync`:
   Patroni `GET /cluster`, member `role=replica, state=running, sync=true`;
   отсутствует — только мастер, второй агент поднимется тиком при
   появлении). Оба — из portalloc; canonical alias :5432 в сети нод.
3. **Ensure слотов per-instance**: имя `pgw_bkp_<C>_<X>` одно и то же на
   КАЖДОЙ ноде-источнике (слоты разных инстансов независимы); ensure
   идемпотентен (существующий `EnsureSlotAsync`). Инвалидация/BROKEN-правило
   «слот исчез» применяется к слотам ВСЕХ нод-источников (живой слот на
   любой ноде — не BROKEN).
4. Контроль цепочки (`ControlDueAsync`) — без изменений (list S3, ratchet,
   дыра → BROKEN, lag/тишина → DEGRADED); поле `agents` в ключ — §3.5.
5. **Ensure ДВУХ контейнеров-агентов**: per-node имена
   `pgw-backup-wal-<C>-<X>-<N>` (N — имя ноды); образ — `Wal:AgentImage`
   (новая опция, дефолт `pgworker-wal:dev`); env — контракт §3.1; сеть нод
   (как сейчас); без портов; **БЕЗ volume** (`ContainerSpec.VolumeName =
   null` — staging-том упразднён); restart-политика `no` (переподключение —
   внутри приёмника; exited — только permanent, супервиз пересоздаёт).
   Супервиз per-node: running → пропуск; exited → пересоздание; источник
   сменился (мастер/sync) → пересоздание соответствующего агента на новом
   источнике (догон от хвоста S3, смена TLI склеивается `.history`).

### 3.4 Docker-драйвер и имена

- `BackupAgentNames`: `Container(cluster, shard, node)` →
  `pgw-backup-wal-<C>-<X>-<node>`; `Prefix(cluster)` без изменений
  (`pgw-backup-wal-<C>-` — чистка D1/deprovisioning работает).
- `ClusterDriver.EnsureBackupAgentAsync`: валидация «VolumeName обязан быть
  `<agent>-staging`» — УДАЛЯЕТСЯ (тома нет); создание без volume.
- `ClusterDriver.RemoveBackupAgentsAsync`: без удаления volume (нечего);
  выборка агентов per-node по префиксу. Остаточные `-staging`-томы старых
  агентов сносится миграцией (§3.6).

### 3.5 Контракт etcd и панель

- Ключ `wal` расширяется опциональным полем
  `"agents":[{"node":"<n>","state":"running|exited|absent"}]` — супервиз-факты
  per-node; `master_node` сохраняется. Новый JSON обратно совместим: парсеры
  панели читают известные поля (канон §4, backwards-compat-правило дрилла —
  тот же принцип).
- Панель: новых граней НЕТ (отображение `agents` — опционально, не блокирует
  приёмку); правила алертов (`wal-stream-lag` и др.) не меняются.

### 3.6 Миграция с pg_receivewal-агентов (бесшовная)

Тик WalStreamProcess находит агента старого формата (имя без суффикса ноды,
не соответствует per-node формату) → снос контейнера И его `-staging`-тома
→ подъём per-node агентов по новым правилам. Недоставленное старым агентом
досыпается новым от хвоста S3 (ось 1 работает с первого дня); имя слота не
менялось — ensure уже зелёный. Отдельных флагов совместимости/конфигов
миграции НЕ вводится.

## 4. Фазы реализации

- **Ф1. Приёмник** (`PgWorker.WalReceiver` + юниты): математика сегментов
  (границы/имена от LSN, сверка с `WalFileName`), буфер, резолв хвоста S3
  (фейк-листы), feedback-инвариант (подтверждение только после успешного
  put — фейк S3), TLI-переход, env-парсинг, stdout-маркеры. TDD: тесты
  фейковых транспортов без docker.
- **Ф2. Интеграционные тесты приёмника** (docker: тестовый PG + MinIO,
  динамические порты): генерация WAL (INSERT + `pg_switch_wal`),
  доставка сегментов в S3, непрерывность, `restart_lsn ≤` доставленного
  хвоста (SQL-зонд), обрыв S3 → backpressure → восстановление без дыр,
  рестарт приёмника → дозасылка от хвоста S3 без дыр.
- **Ф3. Оркестрация**: образ `pgworker-wal`, `WalStreamProcess` (два
  источника, per-node агенты, миграция §3.6), драйвер/имена, конфиг
  `Wal:AgentImage`, поле `agents` в ключ, юниты `WalStreamProcessTests`
  (FakeBackupDeps/FakeBackupEngine — расширить под per-node) + интеграции
  WalStream (двое агентов, слоты per-instance, смена мастера).
- **Ф4. E2E** (docker, свежий Release, каноны изоляции/телеметрии):
  раскарантин `WalStream_UploadsSegmentsContinuously`; новые сценарии —
  пересоздание агента под нагрузкой без дыры; двойная архивация (двое
  агентов, один префикс); смерть мастера → агент реплики продолжает
  (failover, склейка `.history`). Каждый сценарий — свой guid-контур,
  полный teardown, ассерт чистоты.
- **Ф5. Мерж-гейт**: юниты + интеграции + E2E Release зелёные; кейс-маркер
  `Scale_AddEmptyShard` на свежем Release; зачистка контейнеров/сетей
  (`docker network prune -f` — страховочно) между сериями; удаление тега
  t27 из `arch/roadmap/reliability.md` + обновление
  `reliability-report.md` тем же мерж-коммитом.

## 5. Ограничения и границы

- НЕ меняются: механика джобов полных/verify/restore/drill (остаются на
  `pgworker-backup`, bash+mc); S3-layout (`wal/<segment>`,
  `wal/<tli>.history`, `full/<id>/`); имя слота; правила
  непрерывности/BROKEN/ретенции; панельные алерты; KafkaWorker/ValkeyWorker.
- `.partial`-объекты не появляются (незакрытый сегмент — только в памяти
  приёмника, не подтверждается, не выгружается).
- RPO-граница: незакоммиченный хвост WAL (после последнего
  sync-подтверждения) — только на мастере, гарантий нет (осознанно).
- Кластер без sync-standby (переходное окно failover, single-нода): агент
  мастера один, второй — тиком при появлении; защитой не считается,
  наблюдаемость — поле `agents`.
- Ставка на `synchronous_mode=true` нод (канон arch/05) — двойная архивация
  опирается на него; отключение sync-режима оператором выводит ось 2 из
  строя молча — фиксируется риском §7, конфиг-гварда НЕ вводится (YAGNI).

## 6. Критерии приёмки

- **AC1 (инвариант подтверждения)**: интеграционный тест — при живом потоке
  SQL-зонд `pg_replication_slots.restart_lsn` каждого источника ≤ конец
  последнего доставленного в S3 сегмента (проверяется после ≥2 доставленных
  сегментов и после искусственной паузы S3).
- **AC2 (пересоздание без потери — ядро задачи)**: E2E — под WAL-нагрузкой
  `docker rm -f` контейнера агента: агент пересоздан супервизом, цепочка S3
  непрерывна (`WalChain`), ключ `wal` остаётся/возвращается в `ACTIVE`,
  `BROKEN` не возникает.
- **AC3 (двойная архивация)**: интеграционный тест — у шарда ДВА
  running-агента (мастер + sync-standby, per-node имена), оба пишут в один
  префикс `wal/`, ключ `wal` `ACTIVE`, поле `agents` отражает обе ноды;
  слоты `pgw_bkp_<C>_<X>` существуют на ОБОИХ нодах.
- **AC4 (потеря источника)**: E2E — остановка мастера: агент sync-реплики
  продолжает цепочку без дыр; после promote воркер пересоздаёт агентов на
  новых ролях; ключ не `BROKEN`.
- **AC5 (failover/TLI)**: E2E — promote реплики: цепочка склеивается через
  `.history` (объект в S3, `WalChain.CheckWithRestart` непрерывен), ключ
  `ACTIVE`.
- **AC6 (S3-обрыв)**: интеграция — MinIO недоступен ≥1 мин: агенты живы,
  не подтверждают; восстановление S3 → доставка доигрывается, дыр нет,
  `restart_lsn` не ушёл (AC1-проверка после восстановления).
- **AC7 (совместимость/миграция)**: юниты парсеров — wal-ключ с/без
  `agents` читается без `parseErrors`; сценарий миграции §3.6 — старый
  агент+staging-том снесены, per-node подняты, цепочка не рвётся.
- **AC8 (карантин)**: `WalStream_UploadsSegmentsContinuously` раскарантинен
  (Assert.Skip удалён) и зелёный на Release.
- **AC9 (регресс-гейт)**: полные серии юнитов/интеграций/E2E на свежем
  Release зелёные (0 warnings, `TreatWarningsAsErrors`); кейс-маркер
  `Scale_AddEmptyShard`; зачистка 0 остатков (контейнеры/сети/тома/ключи);
  телеметрия E2E по канону (артефакты teardown, `[PHASE]`).
