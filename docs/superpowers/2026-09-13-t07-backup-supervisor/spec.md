# t07-backup-supervisor — супервизор-цикл PgWorker над подсистемой бэкапов (spec)

Дата: 2026-09-13. Канон — [`arch/19-backups.md`](../../../arch/19-backups.md)
(правки контракта — фаза 0 этого плана, см. §5). Контекст сервиса —
[`arch/14-pgworker.md`](../../../arch/14-pgworker.md). Roadmap-текст задачи —
`arch/roadmap/backup.md` (снимается из roadmap мерж-гейтом этого же коммита).

Решения пользователя (2026-09-13, зафиксированы):

1. **Сироты S3 — гибрид**: мусор живого шарда (`full/<id>/` в S3 без etcd-ключа)
   — авто-удаление сразу; сироты исчезнувших владельцев (кластер
   deprovisioned / шард удалён) — алерт панели + авто-удаление по TTL
   (`OrphanTtlSec`, default 7 сут; `0` — только алерт, без авто-удаления).
2. **Признак разрыва цепочки — новое значение `state=BROKEN`** в etcd-ключе wal
   (`ACTIVE|DEGRADED|STOPPED|BROKEN`): машиночитаемо одним полем, переживает
   рестарт воркера, заменяет in-memory маркер `_chainBroken` в WalStreamProcess.
3. **Бюджет зависших джобов — полный**: `FullJobTimeoutSec` (default 6 ч) на
   PLANNED/RUNNING/UPLOADING полных → kill контейнера + FAILED + переснятие по
   бэкоффу; verify-джобы и restore-джобы — симметрично тем же механизмом.

---

## 1. Цель

Замкнуть подсистему бэкапов (t02–t06) самовосстанавливающимся контуром:
воркер reconcil-ит желаемое состояние бэкапов («у каждого живого шарда Active-
кластера — валидная цепочка full+WAL и свежий полный») с фактическим (etcd-
статусы ↔ S3-объекты ↔ docker-контейнеры) и сам устраняет расхождения.
Конкретно:

- **Самолечение разрыва WAL-цепочки**: дыра цепочки / исчезновение слота
  переводят wal-ключ шарда в `BROKEN` (etcd-факт, не строка error), планировщик
  полных реагирует пересъёмом, после которого шард сам возвращается в `ACTIVE`.
  Сегодня (t05-регресс 2026-09-13) `BackupPlanner.IsDue` смотрит только на
  отсутствие wal-ключа и возраст полного: `DEGRADED`-ключ навсегда даёт
  `walKeyExists=true`, полный не планируется, шард из разрыва не выходит;
  in-memory маркер `_chainBroken` к тому же теряется при рестарте воркера, и
  агент поднимается поверх дырной цепочки.
- **Неуспех по любой причине → пересоздание**: зависшие навсегда джобы
  (PLANNED/RUNNING/UPLOADING полный, verify-джоб, restore-джоб) получают
  возрастной бюджет → kill + FAILED/transient-ретрай по общим правилам.
  Сегодня зависший `pg_basebackup`-контейнер держит статус RUNNING вечно и
  навсегда блокирует инвариант «один активный полный на шард».
- **Сверка хранилища с etcd**: объекты S3 без etcd-владельца не копятся —
  мусор живых шардов чистится сразу, сироты исчезнувших владельцев видны панели
  (ключ-реестр) и удаляются по TTL (гибрид из решения 1).
- **Каждый сбой и действие — алерт в панель**: по канону arch/19 §4 воркер
  пишет только статусы; панель получает новые вычислительные правила
  (`backup-chain-broken`, `backup-orphan`), показывающие и сбой, и действие
  воркера («переснимает полный», «удалит по TTL»).

Пограничные случаи из roadmap и их статус (не дублируем уже реализованное):

| Случай | Статус до t07 | Что делает t07 |
|---|---|---|
| Рестарт PgWorker посреди бэкапа | takeover уже работает (etcd-статусы + детерминированные имена, t02) | BROKEN переносит маркер разрыва в etcd (маркер переживает рестарт); таймаут-FAILED — тот же путь |
| Смена мастера посреди операций | WalStream: `masterChanged` → пересоздание агента; BackupProcess: смерть источника → FAILED джоба → переснятие (t02/t03) | не дублируем — закрываем регрессионными тестами |
| Удаление шарда (судьба бэкапов) | RemoveShardProcess: агент вниз, restore-заявки `cancelled-by-remove`, `del --prefix /pgworker/backups/<C>/<X>/`; S3-объекты остаются осознанно (t05/t06) | префикс `<C>/<X>` без владельца попадает в сиротский реестр глобального прохода → алерт + TTL |
| Эвакуация шарда (QUARANTINED) | WalStream: STOPPED, ключ жив (t03) | без изменений (осознанное поведение канона) |
| Deprovisioning кластера | D2 чистит etcd-префикс, S3 остаётся (t05/t06) | префикс `<C>` — в сиротский реестр → алерт + TTL |

## 2. Принципы

- **Arch-first**: изменения контракта — сначала в `arch/19-backups.md`
  (фаза 0), затем код; spec↔arch расхождений нет (риск «Расхождение spec↔arch»
  §10 канона).
- **Пишет только PgWorker под клэймом**: per-cluster часть супервизора — под
  клэймом `<C>` (exclusivity мутаций — внутри кластера ReconcileLoop
  последовательный, гонки «S3-list vs etcd-put» нет); глобальная часть
  (сироты исчезнувших владельцев) — под глобальным лидером `/pgworker/leader`
  (прецедент — SnapshotLoop; клэйма мёртвого кластера не существует).
- **Идемпотентность каждого шага, journal-before-manipulations, transient vs
  permanent** (arch/17): transient-отказы (S3/etcd/docker-транспорт) — статус
  не меняем, следующий тик повторяет; удаления — через наблюдаемый факт
  (list-проверка) с journal-записью.
- **Один источник истины**: прогресс — объекты S3; разлады — etcd-статусы;
  воркер алерты не пишет — панель вычисляет над снапшотом (все новые алерты —
  правила AlertEngine, канон §4).
- **Минимальная площадь контракта**: без новых полей там, где хватает
  существующих (точка разрыва живёт в `chain_start_segment` — ratchet;
  `checked_unix` verify — квота попыток после таймаута).
- **Не трогаем уже работающее**: takeover t02, смена мастера t03, стоп-семантика
  remove-shard/QUARANTINED/restore, DELETING-доводка и гигиена FAILED t06,
  restore-гварды t05 — только регрессионно закрываются тестами.
- **Удаляющие воркера консервативны**: мгновенно удаляется только мусор,
  который восстановление гарантированно не выберет (`full/<id>/` без etcd-
  ключа при живом шарде); всё, что может иметь DR-ценность, — TTL + алерт
  (R4-симметрия arch/14: автоматика не уничтожает потенциально ценные данные).

## 3. Структура и компоненты

### 3.1. Контракт: `BROKEN` в wal-ключе (arch/19 §4)

`/pgworker/backups/<C>/<X>/wal` получает четвёртое значение state:

```
{"state":"ACTIVE|DEGRADED|STOPPED|BROKEN", "slot":…, "master_node":…,
 "chain_start_segment":…, "last_received_segment":…, "last_uploaded_segment":…,
 "last_uploaded_unix":…, "lag_segments":…, "error":…}
```

- `BROKEN` — **разрыв цепочки** (дыра WalChain / исчезновение слота при живой
  цепочке): permanent-деградация, агент стоит, лечение — НОВЫМ полным бэкапом.
  Пограничная семантика `chain_start_segment` в BROKEN-записи — **граница
  разрыва** (последний непрерывный сегмент контроля; для «слот исчез» —
  `last_uploaded_segment` на момент обнаружения).
- `DEGRADED` — только transient-деградации (lag/тишина), как сегодня: агент
  жив, ретраи тиками, пересъём НЕ триггерят (pitfall из roadmap закрыт
  разделением состояний, а не разбором строки error).
- `STOPPED` — без изменений (воркер сознательно остановил: Enabled=false,
  QUARANTINED).
- **Ratchet `chain_start_segment`**: записанное значение никогда не
  понижается. При контроле цепочки стартовая точка = `min(wal_start_segment`
  COMPLETED-полных `с wal_start ≥ записанного chain_start)` — полные со
  стартом ниже границы разрыва игнорируются для контроля (их собственная цепь
  до их точки бэкапа может быть цела и легитимно хранится ретенцией; дыра
  выше). Это закрывает гонку «новый полный COMPLETED, а verify старых ещё не
  провален» и вечный цикл «контроль от старого полного снова видит дыру».
- Модель: `WalStreamStatus` += `Broken`; `WalStatusWriter` — маппинг
  `"BROKEN"` (сериализация/парсинг); панельная модель `WalStreamInfoState` +=
  `Broken`.

### 3.2. Самолечение цепочки (WalStreamProcess + BackupPlanner)

**WalStreamProcess** (`src/PgWorker.Backups/WalStreamProcess.cs`):

- Ветви `DegradeAsync` (дыра контроля; слот исчез при известной цепочке)
  пишут `BROKEN` (вместо DEGRADED): слот при «слот исчез» **пересоздаётся
  immediate+reserved сразу же** — к моменту старта пересъёма полного слот уже
  держит позицию `restart_lsn ≤ wal_start` нового полного, дыра между концом
  `-X stream`-набора и позицией слота не образуется (механика первого старта
  t03 — воспроизведена для восстановления).
- In-memory `_chainBroken` **удаляется**: решение «агента не поднимать» —
  чтение ключа (`wal.State == BROKEN`); переживает рестарт воркера и takeover.
  Гварды при `BROKEN`: агент вниз (идемпотентно), слот ensure (жив — не
  трогаем, копит WAL в пределах `max_slot_wal_keep_size`; исчез — создаём).
- Контроль (`ControlDueAsync`) при `BROKEN` выполняется **каждый тик** (без
  `VerifyIntervalSec`-расписания — скорость заживления; list дырного
  `wal/`-префикса дёшев, BROKEN — редкая аномалия), цепочка проверяется от
  ratchet-точки (§3.1): появился COMPLETED-полный со стартом ≥ границы и
  цепь от него непрерывна → `ACTIVE` (обычный путь записи статуса), агент
  поднимается этим же тиком (AC4c-паттерн «восстановление одним тиком»).
- Transient-деградации — без изменений (`DEGRADED`, агент жив, ChainBroken
  отсутствует как класс — состояние кодирует).

**BackupPlanner.IsDue** (`src/PgWorker.Backups/Process/BackupPlanner.cs`):
сигнатура расширяется признаком разрыва (чистая функция):

```csharp
public static bool IsDue(
    IReadOnlyList<FullBackupState> fulls, bool walKeyExists, long fullMaxAgeSec,
    long nowUnix, long? lastRestoreFinishedUnix = null, bool walChainBroken = false)
```

`walChainBroken=true` → due (пересъём) безусловно; `BackupProcess` передаёт
`shardBackups?.Wal is { State: Broken }`. Инвариант «один активный на шард» и
`BackoffPassed` работают как есть (ложных пересъёмов нет: BROKEN-шард без
активного полного получает PLANNED; после FAILED-попытки — бэкофф серии).
Старые дырные полные НЕ инвалидируются специально: их судьба — verify t04
(периодическая перепроверка链 цепочки от их wal_start; дыра выше их точки —
verify OK, данные частично восстановимы до target_time) и ретенция t06 (GFS);
guard «≥1 COMPLETED» держится как всегда.

### 3.3. Бюджеты зависших джобов (неуспех «по любой причине»)

Чистые решения — планировщиком (юнит-тестируемы), применение — супервизией
существующих процессов:

- **Полный бэкап** (`BackupProcess.SuperviseActiveAsync`): возраст активного
  (`now − started_unix`) > `Job:FullTimeoutSec` (default 21600 = 6 ч) →
  docker kill+rm контейнера и staging-volume → `FAILED` с
  `error="job-timeout: <age> с > FullTimeoutSec"` + journal → переснятие по
  общему правилу (бэкофф серии FAILED). PLANNED без контейнера — просто
  `FAILED` (kill не нужен), с живым контейнером — kill+rm.
- **Verify-джоб** (`BackupVerifyProcess`): verify-контейнер running дольше
  `Job:VerifyTimeoutSec` (default 21600; источник возраста — docker-факт
  `StartedAt` инспекта: в etcd-статусе кандидата времени запуска джоба нет) →
  kill+rm, статус кандидата остаётся `PENDING`, но `checked_unix = now`
  (попытка зачтена — следующий due через `verify.interval_sec`, лив-лок с
  бесконечными немедленными перезапусками исключён; данные не виноваты —
  вердикт FAILED по таймауту не ставим).
- **Restore-джоб** (`RestoreProcess`, фаза RUNNING): возраст
  (`now − started_unix`) > `Job:RestoreTimeoutSec` (default 86400 = 24 ч:
  канон §10 допускает «restore-джоб часами»; сутки — явный завис) → kill+rm
  restore-джоба → `FAILED` `error="restore-job-timeout …"` с существующей
  чисткой щита initialize (fd5342e-механика). `RecoveryTimeoutSec` внутри
  джоба остаётся ( recovering-фаза завершится раньше сама); статусный бюджет —
  страховка фаз downloading/демонтажа. REJOINING не таймаутим (бюджеты
  Patroni-проб — свои, P2.2-паттерны).

Таймаут-FAILED пишется обычным put статуса — takeover-совместим; панель видит
его существующими правилами (`backup-full-stale` серию «нет валидного полного»
покрывает; новых правил не нужно).

### 3.4. Reconcile S3↔etcd: `BackupSupervisorProcess` (новый)

Периодический проход `Supervisor:IntervalSec` (default 600, как ретенция).
Две части:

**Per-cluster (клэйм `<C>`, только Active, Enabled)** — для каждого шарда
снапшота (без `TO_REMOVE`), не в активном restore (гвард «restore владеет
шардом»):

1. List S3 `full/`-префиксов шарда (`ListFullsAsync`) + list объектов каждого
   кандидата → сравнение с etcd-ключами `full/<id>`: префикс `full/<id>/` в
   S3 **без ключа вовсе** → **немедленное batch-delete** + journal
   `supervisor/swept-full/<X>/<id>` (мусор упавших UPLOADING-джобов и
   осиротевшие объекты после гигиены FAILED-ключей t06; восстановление их не
   выберет — выбора кандидатов нет без etcd-ключа; WAL-префикс не трогаем —
   контроль цепочки t03 и чистка t06 владеют им). Идемпотентность: повторный
   list подтверждает пустоту (образец `FinishDeletionAsync`).
2. Таймауты активных операций (§3.3) применяются в их процессах, не здесь —
   супервизор только сверка хранилища.

**Глобальная (лидер `/pgworker/leader`, Enabled)** — list ВСЕГО bucket
(пагинация, образец storage-монитора t06):

1. Группировка по префиксам `<C>/<X>/`; владелец жив, если кластер `<C>` есть
   в `/clusters/` (не `TO_REMOVE`) и шард `<X>` есть в его снапшоте.
   Непокрытые префиксы (кластер исчез / шард удалён) — сироты.
2. **Реестр сирот** — глобальный ключ `/pgworker/backups/orphans` (вне
   per-cluster префиксов, как `storage`; пишет только лидер-проход):

```json
{"orphans":[{"prefix":"<C>/<X>","kind":"shard|cluster","size_bytes":N,
             "first_seen_unix":T,"state":"OBSERVED|DELETING"}],"updated_unix":T}
```

   `first_seen_unix` переносится из предыдущей записи (merge — TTL отсчитывается
   от первого наблюдения, не от каждого прохода). Владелец воскрес (кластер/шард
   появился в etcd) → запись удаляется из реестра; `DELETING`-доводка при
   воскресении владельца отменяется (частично удалённое — осознанный остаточный
   риск, §7).
3. **TTL-удаление**: `OBSERVED` с возрастом `first_seen_unix` >
   `Supervisor:OrphanTtlSec` (default 604800 = 7 сут; `0` — авто-удаление
   выключено, только алерт) → `DELETING` (journal) → batch-delete префикса →
   list-подтверждение → del записи. За один проход — один префикс (тик
   короткий, образец ретенции). `OrphanTtlSec=0` — реестр живёт, удаления нет.

### 3.5. Алерты панели (канон: панель вычисляет над снапшотом)

- **`backup-chain-broken`** (critical): wal-ключ шарда живого Active-кластера
  `state=BROKEN` → «разрыв WAL-цепочки (<error>), воркер переснимает полный
  бэкап» — показывает и сбой, и действие воркера; `AlertRemedy.WorkerAuto`.
- **`backup-orphan`** (warning): записи реестра `/pgworker/backups/orphans` →
  «сирота S3 <prefix> (<size>), удаление по TTL через <осталось>/идёт»
  (OBSERVED/DELETING); при `OrphanTtlSec=0` — «удаление вручную».
- Модель панели: `WalStreamInfoState` += `Broken`; парсер снапшота читает
  `/pgworker/backups/orphans` (новая модель `BackupOrphansInfo`).
- Существующие правила не меняются (`backup-full-stale` покрывает таймаутные
  FAILED-серии, `backup-verify-failed` — вердикты verify, `backup-deleting-stuck`
  — зависшие DELETING ретенции).

### 3.6. Конфигурация (arch/19 §9)

Секция `PgWorker:Backups` пополняется (дефолты — §4 ответов пользователя):

```
Supervisor { IntervalSec=600, OrphanTtlSec=604800 }   # период сверок; TTL сирот
                                                       # (0 = только алерт)
Job { Image=…, FullTimeoutSec=21600, VerifyTimeoutSec=21600,
      RestoreTimeoutSec=86400 }                        # бюджеты зависших джобов
```

`BackupsRuntimeOptions` += соответствующие поля; валидация старта: отрицательные
таймауты/TTL — fail-fast.

### 3.7. Точки врезки

- `ReconcileLoop` (Active-ветка): после `backups-retention`, до
  `backup-restore` — `RunClusterOpAsync("backup-supervisor", …)` под
  `Backups.Enabled`-гвардом (per-cluster часть; вызов
  `BackupSupervisorProcess.TickAsync(snap, backups, ct)` через
  `IClusterProcesses.SuperviseBackupsAsync`).
- Глобальная часть — в `SnapshotLoop`-паттерне: лидерный фоновый цикл
  (переиспользует `ClaimStore.IsLeader`; собственный BackgroundService
  `BackupOrphanSweeperLoop` с тем же `Supervisor:IntervalSec`), чтобы не
  расширять per-cluster тик глобальными list-ами.

## 4. Что НЕ входит (границы)

- Управление MinIO/bucket-ми и ручной просмотр объектов — t08-backup-minio-panel.
- Изменение механики verify t04 (вердикты/периодика), ретенции t06 (GFS/guard/
  DELETING-доводка/гигиена FAILED/WAL-чистка) и restore t05 (фазы/щиты/гварды) —
  только точки таймаутов из §3.3.
- Автоудаление `wal/`-сегментов супервизором: владелец WAL — контроль цепочки
  t03 (истина list) и ретенция t06 (cutoff оставляемых полных); сиротство
  WAL-объектов = сиротство их префикса (§3.4).
- Реакции на `max_slot_wal_keep_size`-инвалидацию слота сверх существующей
  ветки «слот исчез» → BROKEN (механика PG вне наших изменений).
- Метрики Prometheus — существующий словарь arch/18 (новых метрик не вводим;
  journal/статусы достаточны).

## 5. Фазы (порядок исполнения; фаза 0 — обязательная первая)

**Фаза 0 — arch/19 (правки контракта, до кода)**:
- §3 (WAL-агент): «Дыра → DEGRADED» заменяется на «Дыра/слот исчез → BROKEN
  (лечение — пересъём полного, планировщик §2)»; семантика ratchet
  `chain_start_segment`; слот при BROKEN (ensure/пересоздание до пересъёма);
  контроль при BROKEN каждый тик.
- §2 (планировщик): due-условие дополняется «wal-ключ в BROKEN».
- §4 (контракт): таблица ключа wal — `state=ACTIVE|DEGRADED|STOPPED|BROKEN`
  + ratchet-семантика; новый глобальный ключ `/pgworker/backups/orphans`
  (формат, писатель — лидер-проход, merge first_seen, TTL-механика и
  `OrphanTtlSec=0`); уточнение абзаца Deprovisioning-сирот (гибрид: мусор
  живого шарда — авто, исчезнувшие владельцы — реестр+TTL).
- §6 (ресурсы): бюджеты зависших джобов (Full/Verify/Restore TimeoutSec).
- §8 (карта задач): строка t07 — «reconcile S3↔etcd, сироты (реестр+TTL),
  BROKEN-самолечение цепочки, бюджеты зависших джобов, рестарт-устойчивость
  (§4, §6)».
- §9 (конфиг): `Supervisor { IntervalSec, OrphanTtlSec }`,
  `Job { FullTimeoutSec, VerifyTimeoutSec, RestoreTimeoutSec }`.
- §10 (риски): строки — «таймаут ложноположителен на очень медленных
  бэкапах» (дефолт 6 ч с запасом; конфиг), «DELETING-сирота vs воскресший
  владелец (DR в окне удаления)» (TTL-окно 7 сут; гвард вычёркивания;
  остаточный риск зафиксирован), «ratchet vs restore» (restore удаляет
  wal-ключ целиком — ratchet сбрасывается вместе с ним, противоречия нет).

**Фаза 1 — BROKEN-самолечение**: модель (`WalStreamStatus.Broken`,
`WalStatusWriter`), `WalStreamProcess` (BROKEN-ветви, ratchet, слот, отказ от
`_chainBroken`), `BackupPlanner.IsDue` + `BackupProcess` (передача признака),
юниты (планнер-движок ratchet/IsDue/заживление одним тиком — чистые функции),
интеграция (FakeBackupDeps-паттерн: дыра → BROKEN → пересъём → ACTIVE; слот
исчез → BROKEN → пересоздание слота → пересъём → ACTIVE).

**Фаза 2 — бюджеты джобов**: `SupervisionTimeouts` (чистые решения: выбор
кандидата таймаута по статусу/возрасту), применение в BackupProcess /
BackupVerifyProcess / RestoreProcess (kill+rm, статусы, journal,
checked_unix-квота verify), юниты + интеграция (зависший контейнер → FAILED →
переснятие; verify-таймаут → PENDING с checked_unix).

**Фаза 3 — сверка S3↔etcd**: `BackupSupervisorProcess` (per-cluster чистка
мусора) + `BackupOrphanSweeperLoop` (лидер; реестр, merge, TTL, DELETING-
доводка, гвард воскресения), конфиг `Supervisor`/`Job`, врезка в
ReconcileLoop/DI, юниты (отбор сирот/мусора — чистые функции над списком
объектов и etcd-моделью), интеграция (мусор удаляется; сирота в реестре; TTL
истёк (тестовое сжатое время) → удаление; владелец воскрес → запись гаснет).

**Фаза 4 — панель**: модель (`WalStreamInfoState.Broken`, `BackupOrphansInfo`
+ парсер), правила `backup-chain-broken`, `backup-orphan` (+ юниты правил по
образцу существующих), при необходимости — строка в UI-инвентарь бэкапов.

**Фаза 5 — E2E и гейт**: docker-E2E на свежем Release: обязательный кейс-маркер
`Scale_AddEmptyShard` (AGENTS, мерж-гейт кода воркеров) + новый сценарий
`Backup_ChainBroken_SelfHeals` (живой кластер → дыра в MinIO (rm сегмента
внутри цепочки) → контроль → wal=BROKEN → планировщик переснимает полный →
цепь непрерывна от нового полного → wal=ACTIVE, агент жив) и
`Backup_OrphanRegistry_TtlDelete` (shard-префикс без владельца → реестр →
сжатый TTL → объекты удалены, запись гаснет). Изоляция E2E —
`docs/e2e-isolation.md` (guid-имена, own-only teardown, ассерт чистоты),
телеметрия — `docs/e2e-launch.md`. Roadmap: тег `t07-backup-supervisor` снимается
из `arch/roadmap/backup.md` мерж-гейтом (тем же коммитом).

## 6. Ограничения и риски

| Риск | Митигация |
|---|---|
| Ложный таймаут медленного валидного бэкапа (большая база/медленный S3) | дефолт 6 ч с запасом поверх «часовых» бэкапов канона; конфиг `Job:FullTimeoutSec`; FAILED по таймауту проходит общий бэкофф — шторм пересъёмов исключён |
| Ratchet против restore/PITR-назад | restore COMPLETED удаляет wal-ключ целиком (t05 AC4) — ratchet уходит вместе с ключом; новая цепочка строится планировщиком с нуля |
| DELETING-сирота vs воскресший владелец (DR-restore в окне удаления) | TTL-окно 7 сут покрывает разбор; гвард: владелец появился в etcd → доводка DELETING отменяется, запись гаснет; остаточный риск (частично удалённое при самом старте DR) зафиксирован в arch/19 §10 |
| Гонка «S3-list увидел объекты, etcd-ключ ещё не написан» | journal-before-manipulations (PLANNED пишется до контейнера/upload) + клэйм-последовательность внутри кластера: «объекты без ключа» при живом шарде = ключ был и удалён (гигиена FAILED) или мусор — оба случая безопасны к удалению |
| Двойной писатель orphan-реестра | пишет только глобальный лидер (`/pgworker/leader`, lease TTL 15 с) — паттерн SnapshotLoop; смерть лидера → takeover ≤ TTL, записи реестра в etcd переживают |
| BROKEN-зацикливание (пересъём не завершается) | общий бэкофф серии FAILED (планировщик) + суточный `backup-full-stale` + critical `backup-chain-broken` — панель видит затяжное лечение |
| Шум списка сирот (чужие объекты bucket) | реестр только по префиксам `<C>/<X>` нашей формы; посторонние корневые объекты — вне реестра (storage-монитор t06 уже считает занятость всего) |

## 7. Критерии приёмки

1. **AC1 (самолечение дыры)**: в живом кластере с валидной цепочкой удалён
   сегмент внутри цепочки → следующий контроль пишет `wal.state=BROKEN` с
   `error` границ; планировщик в пределах нескольких тиков запускает новый
   полный; после его COMPLETED + контроля цепь непрерывна от его
   `wal_start_segment` → `wal.state=ACTIVE`, агент pg_receivewal жив; юниты
   покрывают: IsDue по BROKEN, ratchet (полные ниже границы игнорируются для
   chain_start), заживление одним тиком.
2. **AC2 (слот исчез)**: слот удалён вручную при живой цепочке → `BROKEN` +
   слот пересоздан (immediate+reserved) агент НЕ поднимается до пересъёма;
   после нового COMPLETED-полного — `ACTIVE` (интеграционный тест).
3. **AC3 (transient не триггерит)**: `DEGRADED` по lag/тишине НЕ даёт IsDue
   (юнит: IsDue с walChainBroken=false при несвежем полном → false);
   `_chainBroken`-словаря в коде WalStreamProcess больше нет (решение —
   чтение ключа).
4. **AC4 (рестарт-устойчивость маркера)**: BROKEN-статус переживает рестарт
   процесса (интеграционный тест: BROKEN → пересоздание процесса/фабрики →
   агент не поднимается, пересъём идёт).
5. **AC5 (таймауты)**: RUNNING-полный с «вечным» контейнером старше бюджета →
   контейнер/volume удалены, статус FAILED `job-timeout…`, переснятие по
   бэкоффу; verify-джоб старше бюджета → kill, кандидат PENDING с
   `checked_unix=now` (следующий due через interval); restore RUNNING старше
   бюджета → FAILED, щит initialize снят (юниты решений + интеграция).
6. **AC6 (мусор живого шарда)**: объекты `full/<id>/` без etcd-ключа у живого
   шарда удаляются первым же проходом супервизора, journal пишет
   `supervisor/swept-full/<X>/<id>`; повторный проход — no-op (интеграция).
7. **AC7 (сироты)**: префикс исчезнувшего шарда/кластера → запись в
   `/pgworker/backups/orphans` (OBSERVED, first_seen переносится), панель
   выдаёт `backup-orphan`; после истечения TTL (сжатое время в тесте) —
   DELETING → объекты удалены → запись удалена; `OrphanTtlSec=0` — удаления
   нет; воскресение владельца (shard снова заявлен) — запись гаснет (юниты
   отбора + интеграция).
8. **AC8 (контракт)**: `arch/19` обновлён первой фазой (§2/§3/§4/§6/§8/§9/§10
   по §5-фазе-0); `WalStatusWriter` и панельный парсер симметричны
   (`BROKEN`); воркер алертов не пишет — оба новых алерта — правила панели
   (юниты правил).
9. **AC9 (регресс пограничных)**: смена мастера (агент пересоздан с нового),
   remove-shard (агент вниз, ключи удалены, S3-сирота в реестре),
   restore-гварды (supervisor-процесс скипает шард в активном restore) —
   интеграционные тесты зелёные.
10. **AC10 (E2E-гейт)**: docker-E2E на свежем Release: кейс-маркер
    `Scale_AddEmptyShard` зелёный + сценарии `Backup_ChainBroken_SelfHeals`,
    `Backup_OrphanRegistry_TtlDelete` зелёные; изоляция/телеметрия по
    `docs/e2e-isolation.md`/`docs/e2e-launch.md`; зачистка контейнеров/сетей
    между сериями (AGENTS).
11. **AC11 (гигиена проекта)**: `dotnet test` юниты+интеграция зелёные
    (`TreatWarningsAsErrors=true`); roadmap-тег `t07-backup-supervisor` снят
    тем же мерж-коммитом; документация (§5-фаза-0 arch-правки + runbook-
    упоминание сирот в `docs/backup-restore.md`: «удалённый кластер жив в S3
    TTL 7 сут») обновлена.
