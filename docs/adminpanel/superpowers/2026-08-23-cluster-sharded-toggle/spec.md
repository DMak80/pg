# Спецификация cluster-sharded-toggle — переключатель «шардированная / нешардированная БД» при создании кластера

Дата: 2026-08-23. Фаза dev-flow: spec. Задача выдана пользователем напрямую
(автономный режим: бланкетный апрув сессии, все проектные решения приняты
исполнителем и зафиксированы в §8). Источники истины: `arch/02-etcd-contract.md`
**§9** (контракт записи — §9.1 дополнен семантикой нешардированной БД, §9.3 —
полем `sharded`; правки внесены этой задачей до написания кода),
`arch/03-panels.md` **§1.1** (DTO запроса/ответа — дополнен `sharded`, также
внесено этой задачей). База — влитая фича t12 (`2026-08-23-cluster-create`,
merge d2549ba). CQRS-команда — референс `../Puzzle docs/01.03-cqrs.md`
(без изменений: команда уже существует, меняется только DTO).

Фактическое состояние кода: `CreateClusterRequest` — позиционный record из 7
полей без `sharded`; `CreateClusterValidator` валидирует buckets/shards всегда;
`ClusterCreatePlan.Build` строит ключи из полей запроса напрямую; фронт —
`ClusterCreateModal` с рядом `Group grow` [Бакеты, Шарды, Реплики]
(NBSP-заглушки description — фикс d2549ba) и зеркальной валидацией; e2e-чек
`dev-stand/checks/15-cluster-create.sh` шлёт тело без `sharded`.

## 1. Цель

В модалке создания кластера добавить переключатель типа БД:
**«Шардированная» / «Нешардированная»**. Поля «Бакеты» и «Шарды» вынести в
отдельный визуальный блок «Шардирование», который отображается **только** при
выборе шардированной БД. Для нешардированной БД эти поля не запрашиваются
вовсе (в HTTP-запрос не попадают), а сервер нормализует параметры в
вырожденную структуру 1 бакет × 1 шард. Остальные поля (имя, реплики,
cpu/память/диск) — общие для обоих типов, без изменений.

Требования пользователя дословно: «сделать переключатель шардированная бд или
не шардированая бд создается»; «только для шардированной запрашивать кол-во
бакетов и кол-во шардов, нужно вынести в отдельный блок шардирования который
включается/отображается по выбору шардированной бд».

Не входит (границы): формат etcd-ключей §9.1 не меняется; протокол записи
§9.2 (клэйм/пакет/компенсация) не меняется; поле `sharded` в инспекционных
DTO (`ClusterDto`, `ClusterSummaryDto`, overview) не добавляется — после
записи тип БД неразличим и не нужен (§8.7); редактирование/удаление кластеров,
поднятие нод — вне scope, как и в t12.

## 2. Принципы

- **arch/-first**: `arch/02 §9.1/§9.3` и `arch/03 §1.1` обновлены этой задачей
  до кода; код не может противоречить им (расхождение = правка arch тем же PR).
- **Нешардированная = вырожденный случай контракта**: buckets=1, shards=1.
  Никаких новых ключей/полей в etcd — читатели (инспектор панели, будущий
  provisioning, система `../pg`) правок не требуют. Обоснование выбора против
  альтернатив — §4.1, §8.1.
- **Обратная совместимость API**: поле `sharded` опционально; отсутствует или
  `null` = `true` — старые клиенты и e2e-чек 15 работают без изменений.
- **Сервер — источник истины**: нормализация `sharded=false → 1/1` выполняется
  на сервере до валидации; фронт лишь не отправляет поля и не валидирует их
  для нешардированной (зеркало — как в t12 §2).
- **Состояние формы не теряется**: значения бакетов/шардов живут в состоянии
  формы и переживают переключение типа туда-обратно (блок скрывается, значения
  сохраняются).
- Идентификаторы английские; комментарии и тексты UI русские; тесты — с
  комментариями по AAA; `TreatWarningsAsErrors=true` — сборка без warnings.

## 3. Структура и компоненты

### 3.1. Контракт (arch/02 §9.1/§9.3, arch/03 §1.1 — уже внесено в arch)

- `CreateClusterRequestDto`: новое поле `sharded` (bool, опционально:
  отсутствует/`null` = `true`); `buckets`/`shards` передаются только при
  `sharded=true`, при `sharded=false` не требуются и игнорируются (сервер
  нормализует в 1/1 до валидации).
- `ClusterCreatedDto`: новое поле `sharded` (bool); для нешардированной —
  `bucketsCount=1`, `shardsTotal=1`, `sharded=false`.
- §9.1: нешардированная БД — вырожденный случай: `config.buckets=1`, один
  `shard1` с нодами и заявками, один `bucket_0 → shard1`. Отдельного признака
  «тип БД» в etcd нет.
- §9.2 (без правок): клэйм имени `version==0` + пакет PUT + компенсация —
  для 1/1 ключей работают идентично.

### 3.2. Сервер: DTO и нормализация (`src/AdminPanel.Etcd/Writing/`)

`CreateClusterRequest` — новый хвостовой параметр с default:

```csharp
public sealed record CreateClusterRequest(
    string Name,
    int Buckets,
    int Shards,
    int Replicas,
    decimal RequestCpu,
    int RequestMem,
    int RequestDisk,
    bool? Sharded = null);   // отсутствует/null = true (arch/03 §1.1)
```

- `bool?` + `= null`: System.Text.Json при отсутствии поля в JSON использует
  default конструктора; nullable-тип явно кодирует трёхзначность
  «не передано / true / false» (обоснование против `bool Sharded = true` — §8.3).
- Хвостовой default сохраняет компилируемость существующих вызовов
  `new CreateClusterRequest(...)` с 7 аргументами (тесты t12).

Новый метод записи — `Normalize()` на record (чистая, идемпотентная):

```csharp
// Нешардированная: buckets/shards игнорируются → 1/1 (arch/02 §9.3);
// отсутствующий sharded трактуется как true. Вызывается ДО Validate.
public CreateClusterRequest Normalize()
{
    var sharded = Sharded ?? true;
    return sharded
        ? this with { Sharded = sharded }
        : this with { Sharded = sharded, Buckets = 1, Shards = 1 };
}
```

Порядок конвейера в `CreateClusterCommandHandler.Handle` (единственная правка):
`request = request.Normalize();` первой строкой — далее `Validate`, `Build`,
DTO-ответ читают нормализованный запрос без `??`-развязок. Требование
«Normalize до Validate» симметрично существующему «Build — только после
Validate» и фиксируется комментарием. `CreateClusterValidator` и
`ClusterCreatePlan` **не меняются**: валидатор видит уже нормализованные
1/1 (правила buckets/shards для них проходят тривиально), план строит
вырожденную структуру естественным образом (S=1 → shard1; N=1 → bucket_0,
round-robin `0 % 1 + 1 = shard1`).

`ClusterCreatedDto` — новое поле `bool Sharded` (после `DbName`):
`new ClusterCreatedDto(request.Name, request.Name, request.Sharded!.Value, …)`.

`OperationsModule` не меняется (маппинг 400/409/503 тот же).

### 3.3. Фронтенд: DTO (`frontend/src/api/dto.ts`)

```ts
export interface CreateClusterRequestDto {
  name: string;
  sharded: boolean;     // фронт передаёт всегда; сервер: отсутствует = true
  buckets?: number;     // только при sharded=true
  shards?: number;      // только при sharded=true
  replicas: number;
  requestCpu: number;
  requestMem: number;
  requestDisk: number;
}
```

`ClusterCreatedDto` — добавить `sharded: boolean`. Опциональность
`buckets?/shards?` — не discriminated union: для одной формы это избыточно,
наличие полей при `sharded=true` гарантирует зеркальная валидация (§8.6).

### 3.4. Фронтенд: модалка (`frontend/src/pages/clusters/ClusterCreateModal.tsx`)

Состояние формы — собственный тип (значения бакетов/шардов живут всегда,
переключение их не сбрасывает):

```ts
interface FormState {
  name: string;
  sharded: boolean;
  buckets: number;
  shards: number;
  replicas: number;
  requestCpu: number;
  requestMem: number;
  requestDisk: number;
}
const EMPTY: FormState = {
  name: '', sharded: true, buckets: 16, shards: 2,
  replicas: 2, requestCpu: 2, requestMem: 8, requestDisk: 100,
};
```

Сборка тела запроса в `submit()` — DTO строится, а не отправляется состояние
напрямую:

```ts
const body: CreateClusterRequestDto = form.sharded
  ? { ...form }
  : { name: form.name, sharded: false, replicas: form.replicas,
      requestCpu: form.requestCpu, requestMem: form.requestMem,
      requestDisk: form.requestDisk };
```

Зеркальная валидация: проверки `buckets`/`shards` выполняются только при
`form.sharded === true`; остальные правила — без изменений. Тело запроса при
`sharded=true` валидно всегда (поля обязательны по построению формы).

Раскладка (порядок сверху вниз):

1. `TextInput` «Имя кластера» — как сейчас.
2. `SegmentedControl` с `label="Тип базы данных"`, данные
   `[{value:'sharded', label:'Шардированная'}, {value:'single', label:'Нешардированная'}]`,
   value ↔ `form.sharded`. Выбор SegmentedControl против Switch/RadioGroup — §8.4.
3. Условный блок шардирования (`{form.sharded && (…)}`): `Box withBorder
   radius="md" p="sm"` с заголовком `Text size="sm" fw={500}` «Шардирование» и
   `Group grow` из `NumberInput` «Бакеты» и «Шарды» (границы и `error` — как
   сейчас). Показывается **только** при шардированной.
4. `NumberInput` «Реплики» (description «2 = мастер + реплика») — отдельный
   элемент общего стека, вне блока шардирования.
5. Секция «Ресурсы нод» — как сейчас, без изменений.

NBSP-заглушки description (фикс d2549ba) удаляются: ряды разнесены, «Бакеты»
и «Шарды» — пара одинаковой высоты внутри блока, «Реплики» — в своём ряду;
выравнивание больше не зависит от соседей, прыжков нет (§8.8). При скрытии
блока шардирования форма закономерно короче на высоту блока — остальные поля
сохраняют взаимное расположение.

Сброс после успеха и `onClose` — как сейчас (`setForm(EMPTY)`; дефолт
переключателя — «Шардированная», §8.5).

## 4. Рассмотренные альтернативы

### 4.1. Семантика нешардированной БД в etcd

- **A (выбрано): вырожденный случай buckets=1, shards=1.** Формат §9.1 не
  меняется вообще; все читатели контракта работают по построению (round-robin
  для N=1, S=1 даёт единственный `bucket_0 → shard1`). Меняются только DTO,
  валидация и UI. Проверено: инспектор и UI-страницы корректно показывают 1/1.
- B: отдельное поле `sharded` в `config`-JSON. Отвергну: меняет формат §2.1/§9.1,
  требует правок парсера и будущих потребителей (provisioning, `../pg`),
  при нулевой новой информации — структура 1×1 самодостаточна.
- C: для нешардированной не писать routing/status/buckets вовсе. Отвергну:
  читатели трактуют «N из config без routing» как дыру карты (§2.1) — пришлось
  бы писать `buckets=0` и менять инспектор; больше Breaking-изменений, чем в A.

### 4.2. Прочие развилки — см. §8 (решения 8.2–8.8): место нормализации,
тип поля `sharded` в C#/TS, выбор контрола UI, дефолт переключателя, термин
«Нешардированная», опциональные поля TS-DTO, судьба NBSP-хака.

## 6. Ограничения и риски

- Формат etcd-ключей §9.1 и протокол §9.2 не меняются — regression-поверхность
  сервера ограничена DTO/нормализацией.
- Биндинг `bool? Sharded = null` через конструктор Minimal API: optional-
  параметры STJ поддерживает; при неожиданном поведении план Б —
  `[JsonConstructor]` или биндинг из `JsonElement` (не ожидается).
- Поле `sharded` в JSON-ответе добавляется — старые TS-клиенты игнорируют
  лишнее поле (обратно совместимо).
- e2e-чек 15 и существующие клиенты не меняют тела запросов — обратная
  совместимость проверяется ими автоматически.
- Фронтенд-юнит-тестов в проекте нет (инфраструктура отсутствует) — UI
  покрывается e2e-чеком и ручной проверкой; вводить тест-раннер в этой задаче
  не будем (YAGNI, вне scope).

## 7. Критерии приёмки

1. Модалка: `SegmentedControl` «Шардированная | Нешардированная», дефолт —
   «Шардированная»; блок «Шардирование» (Бакеты + Шарды) виден только при
   шардированной; переключение туда-обратно сохраняет введённые значения;
   «Реплики» и ресурсы всегда видимы и не меняют взаимного расположения.
2. `POST /api/clusters` с `{"name":"solo","sharded":false,"replicas":…,
   request…}` без buckets/shards → 201; в etcd ровно вырожденная структура:
   `config {"buckets":1,…,"state":"NOT_INITIALIZED"}`, `shards/shard1/…`
   (replicas+nodes), `buckets/routing/bucket_0 = "shard1"`,
   `buckets/status/bucket_0`, `/service/solo-shard1/request_{cpu,mem,disk}`;
   ответ: `sharded:false`, `bucketsCount:1`, `shardsTotal:1`.
3. `POST` без поля `sharded` (тело t12) → 201, ответ `sharded:true`,
   структура как в t12 (обратная совместимость; существующие тесты и чек 15
   проходят без правок тел).
4. `POST` с `sharded:false` и произвольными (в т.ч. невалидными) buckets/shards
   → 201 с вырожденной структурой (значения игнорируются).
5. Валидация: при `sharded=true` правила buckets (1..8192) и shards
   (1..128, ≤ buckets) — как в t12, ошибки 400 по полям; фронт-зеркало не
   проверяет buckets/shards при нешардированной.
6. Список кластеров, детали (вкладки Шарды/Бакеты/Переезды/Heals) и overview
   отображают `solo` без ошибок: 1 бакет, 1 шард, бейдж «не инициализирован».
7. `dotnet build` — 0 warnings; `dotnet test` — зелёные (unit + integration);
   чек `15-cluster-create.sh` на dev-стенде — зелёный (оба кейса: smoke и solo).
8. `arch/02 §9.1/§9.3`, `arch/03 §1.1` соответствуют реализации (правки arch
   уже внесены этой задачей; расхождений нет).

## 8. Решения автономного режима

- **8.1. Нешардированная = вырожденный случай 1×1** — альтернативы §4.1
  (новое поле в config / не писать routing) отвергнуты: больше изменений
  контракта при нулевой новой информации.
- **8.2. Нормализация — единая точка `CreateClusterRequest.Normalize()`**,
  вызывается хендлером до `Validate`. Альтернатива «валидатор пропускает
  buckets/shards при sharded=false, план берёт 1/1» отвергнута: распыляет
  знание о 1/1 по двум местам и оставляет план зависеть от непронормализованного
  запроса.
- **8.3. `bool? Sharded = null` (а не `bool Sharded = true`)** — nullable явно
  кодирует «поле не передано» и обрабатывается одним `?? true` в `Normalize`;
  literal `null` в JSON трактуется так же, как отсутствие поля.
- **8.4. `SegmentedControl`** (а не `Switch`/`RadioGroup`): тип БД — выбор
  одного из двух равнозначных режимов, а не «включение опции» (Switch
  двусмыслен: «включить шардирование» при скрытии полей выглядит как
  отключение функции); RadioGroup громоздок для двух опций. Сегмент-контрол
  компактен и визуально очевиден в модалке (паттерн Mantine).
- **8.5. Дефолт — «Шардированная»**: сохраняет текущее поведение модалки
  (UX-обратная совместимость) и соответствует семантике API
  (отсутствие `sharded` = true).
- **8.6. `buckets?/shards?` опциональны в TS-DTO** (а не discriminated union
  и не «всегда слать 1/1»): прямое выражение «для нешардированной поля не
  запрашиваются вовсе»; дискриминированное объединение для одной формы —
  избыточно; отправка 1/1 с клиента дублировала бы серверную нормализацию.
- **8.7. Поле `sharded` не добавляется в инспекционные DTO**: после записи
  нешардированная БД структурно совпадает с шардированной 1×1 — признак
  неразличим и не нужен читателям; добавление поля в `ClusterDto` потребовало
  бы эвристики (`buckets>1||shards>1`), дающей неверный ответ для осознанно
  созданной 1×1 шардированной. YAGNI.
- **8.8. NBSP-заглушки d2549ba удаляются**: «Реплики» выносятся из ряда
  бакетов/шардов в собственный ряд (description больше не ломает выравнивание
  соседей); внутри блока «Шардирование» пара полей одинаковой высоты. Хак
  устаревает вместе с разнесением рядов — не восстанавливать.
- **8.9. Термин «Нешардированная»** (а не «Одиночная»): точное слово из
  запроса пользователя; «Одиночная» двусмысленна рядом с полем «Реплики»
  (можно прочитать как «без реплик»).
