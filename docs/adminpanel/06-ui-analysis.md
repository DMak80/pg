# 06. Анализ системы и целевая модель интерфейса

> Назад: [INDEX.md](INDEX.md)

Документ отвечает на три вопроса, нужные для доработок интерфейса:
какие секции образуют систему и как они зависят; где какие параметры
задаются и на каком этапе жизненного цикла; какие в системе есть состояния,
события и алерты. На этом основании фиксируется **целевая модель интерфейса**
(разбиение по секциям/смыслу для обзора состояния и управления) и **набор
задач на доработку**.

Текущий интерфейс — фактический снимок (§6), не эталон. Канон поведения —
`arch/` (изменение интерфейса = правка `arch/adminpanel/03-panels.md` тем же
коммитом, что код); этот документ — аналитика и план, при запуске задач их
формулировки уходят в треки [`arch/adminpanel/roadmap/`](../../arch/adminpanel/roadmap/README.md).

## 1. Карта секций системы и зависимости

### 1.1. Секции

| Секция | Назначение | Канон |
|---|---|---|
| **etcd-контур** | Единственный источник истины (DCS): 3 узла, кворум 2/3, один контур на все домены. Декларации кластеров, координация воркеров (leader/claims/lease TTL 15 с), DCS Patroni, клиентский дискавери. Данные кластеров в etcd не живут — только метаданные | [arch/01](../../arch/01-architecture.md), [arch/17](../../arch/17-synchronization-principles.md) |

Единственный писатель `/clusters/`, `/pgworker/`, `/service/<C>-<X>/request_*` | [arch/14](../../arch/14-pgworker.md) |
| **KafkaWorker** | Оркестратор Kafka-кластеров (KRaft): жизненный цикл брокеров, SASL/PKI, автосинк топиков, reassignment партиций, mutable-конфиги. Единственный писатель `/kafka/`, `/kafkaworker/` | [arch/16](../../arch/16-kafkaworker.md) |
| **ValkeyWorker** | Оркестратор Valkey-кластеров (standalone-кеш, 1 нода, persistence off): контейнер, ACL-креды, TLS, ротации. Единственный писатель `/valkey/`, `/valkeyworker/` | [arch/21](../../arch/21-valkeyworker.md) |
| **S3Worker** | Оркестратор пулов S3-хранилища бэкапов (ownS3): инстансы по placement-селекторам, mesh-репликация (`links`), PKI, deny-list, зонд синхронности. Единственный писатель `/s3/`, `/s3worker/` | [arch/24](../../arch/24-s3worker.md), [arch/23](../../arch/23-s3-clusters.md) |

| **PG-нода** (`pgworker-node`) | Контейнер Spilo (PG + Patroni) + pg_doorman + приёмник WAL (стрим в S3, полные бэкапы, verify, restore, drill) — один процесс, API `alias:8080` без публикации на хост | [arch/14 §2.1](../../arch/14-pgworker.md), [arch/19](../../arch/19-backups.md) |
| **Patroni / HA-контур шарда** | Репликация и failover внутри нод; DCS `/service/<scope>/`; Patroni-callback — единственный писатель `shards/X/master` (lease TTL 5 с) | [arch/01 §1.2](../../arch/01-architecture.md), [arch/11 §2](../../arch/11-bucket-sharding.md) |
| **Подсистема бэкапов** | Хозяин PgWorker: полные + WAL (двойная архивация мастер+sync-реплика), verify, restore/PITR, drill, GFS-ретенция, реестр сирот, DR-слепки etcd → S3. Контракт `/pgworker/backups/*` | [arch/19](../../arch/19-backups.md) |
| **S3-хранилище (OwnS3)** | Durability-хранилище: бэкапы шардов (`<C>/<X>/full|wal`), слепки etcd; избыточность — mesh-репликация внутри пула. Внешний репозиторий `../OwnS3` | [arch/19 §5](../../arch/19-backups.md), [arch/23](../../arch/23-s3-clusters.md) |
| **Docker-движки (plain/swarm)** | Исполнитель размещения: контейнеры/сети/тома через Engine API; воркер — строго управление запуском + проверка факта | [arch/25 §2–3](../../arch/25-component-communications.md) |
| **Мониторинг** | Prometheus + Grafana + Alertmanager; таргеты — file_sd из portalloc. Канал наблюдения, независимый от панели | [arch/18](../../arch/18-metrics.md) |
| **etcdworker** (план, t32) | Будущий оркестратор etcd-контура: состав узлов/кворум, бэкапы etcd (перенос `Snapshots:Export` из PgWorker), per-install ключ бэкапа etcd. Не реализован | [arch/roadmap/reliability t32](../../arch/roadmap/reliability.md) |

### 1.2. Зависимости (кто кого создаёт, читает, слушает)

- **Панель → воркеры**: все мутации через HTTP API воркеров (mTLS, дискавери по
  lease-ключам `/…worker/api/<id>`); воркеры умерли → мутации недоступны
  (503, critical-алерт `worker-api-unreachable`).
- **Воркеры → etcd**: каждый — единственный писатель своих префиксов; панель
  читает всё, пишет только `/workers/api_tls/*`. Транспорт — HTTP JSON gateway
  `/v3/*`, poll без watch.
- **Воркеры → docker**: Engine API (создание/старт/стоп/удаление, сети, тома).
- **Patroni → etcd**: DCS `/service/<scope>/` + master-ключ шарда.
- **PgWorker → S3-домен**: читатель `/s3/clusters/<C>/{config,endpoints,secrets}`
  (ключ `backups`) + `/s3worker/portalloc` — резолв пула бэкапов; не пишет.
- **Бэкапы → S3**: приёмники WAL нод пишут объекты напрямую; PgWorker
  командует приёмниками через их HTTP API.
- **Приложение → etcd**: клиентский дискавери всех доменов — только etcd.
- **Prometheus → все**: скрейп `/metrics` (mTLS), Patroni `:8008`, приёмники `:8080`.

Отказоустойчивость: отказ etcd замораживает контроль-плейн (данные живут);
смерть инстанса воркера — takeover ≤ TTL 15 с (деплой 2 инстанса); смерть
PG-ноды — Patroni-выборы (бюджет ≤5 с) + rebuild; смерть шарда — эвакуация
бакетов + карантин; недоступность S3-пула — backpressure (слот держит WAL,
RPO-инвариант «подтверждение по доставке»).

### 1.3. Сквозной жизненный цикл (одинаков для всех доменов)

```
заявка (панель → API воркера)
  → декларация в etcd, state=NOT_INITIALIZED
  → клэйм инстансом воркера → provisioning (docker, сети, порты, секреты)
  → endpoints/dsn, state снят = Active
  → надзор: converge/rebuild/ротации/переезды/бэкапы
  → TO_REMOVE → deprovisioning (docker → etcd)
```

Инварианты: владелец префикса один; мутации под живым клэймом;
идемпотентность; «нет status-ключа = Active»; journal-before-manipulations.

## 2. Параметры: где задаются и на каком этапе

Архитектурная граница для интерфейса: **кластерные параметры = заявки через
API воркеров** (живое etcd, применяется тиками/rolling); **параметры
установки = env/appsettings воркера** (рестарт контейнера); **серт API
воркера = гибрид** (панель пишет etcd-ключ, применение рестартом через панель).

### 2.1. Этапы

| Этап | Что фиксируется | Носитель | Изменяемость |
|---|---|---|---|
| **0. Подготовка хоста** | sysctl/limits/диски/NTP/образы | ОС хоста | вручную, вне системы |
| **1. etcd-контур** | PEERS/CLUSTER_TOKEN/адреса, тайминги raft (250/2000), квота 8 GiB | `deploy/etcd/etcd.env` + compose-флаги | runbook member add/remove |
| **2. Деплой воркеров** | секреты per-install, endpoints etcd, advertise-URL/порты API, TLS-пакет, сети контура, образы/диапазоны портов (pg 15000–15999, kafka 16000–16999, valkey 17000–17999, s3 18000+), PGTune-профиль, флаги подсистем (Backups/Snapshots.Export), `S3W_BUCKET`, бюджеты/пороги/тики (`Thresholds`, `Loops`, `Moves`, `Parallelism`, бэкап-бюджеты) | `deploy/.env` + `appsettings` воркеров | рестарт контейнера |
| **3. Саморегистрация** | lease-ключи `/…worker/api/<id>`, `/instances/<id>`, leader/claims | пишет воркер | автоматически |
| **4. Создание кластера (заявка)** | pg: имя, `buckets` (навсегда, P18), dbname, replicas, `request_{cpu,mem,disk}` per-нода (→ лимиты + вход PGTune при provisioning), strict-режим; kafka: brokers/RF/minISR/partitions/retention + ресурсы брокера; valkey: maxmemory/policy + ресурсы; s3: placement-селекторы, ресурсы, links, etcdBackup | декларации etcd через API воркера | pg-ноды: без пересоздания нельзя (конвергенции лимитов нет); kafka/valkey/s3 ресурсы — rolling; kafka config и valkey maxmemory — dynamic; pg strict — runtime |
| **5. Рантайм** | per-cluster policy бэкапов (retention/full_max_age/verify/drill/s3-пул), заявки (переезды/ротации/rebalance/зонды/recreate), рестарты, серты API | etcd (ключи заявок/policy) | живое, тиками воркера |

Каталоги параметров: pg — [arch/14 §8](../../arch/14-pgworker.md), бэкапы —
[arch/19 §4](../../arch/19-backups.md), kafka — [arch/16 §8](../../arch/16-kafkaworker.md),
valkey — [arch/21 §8](../../arch/21-valkeyworker.md), s3 — [arch/24 §8](../../arch/24-s3worker.md),
панель — `src/AdminPanel.Api/appsettings.json`.

### 2.2. Что пользователь может задать из UI сегодня

Полный реестр мутаций — [arch/adminpanel/03 §1](../../arch/adminpanel/03-panels.md)
(pg 13, kafka 17, valkey 6, s3 10, воркеры 4 + сироты бэкапов 3). Всё
остальное панель немая. Зашитые константы (формула раскладки бакетов, канон
PG P3/P4, TTL lease, порт-тройки, env брокеров/нод, тайминги etcd, сроки
сертов) — не параметризованы нигде.

### 2.3. Меняется только руками — кандидаты на вынос в панель

1. Глобальный стоп бэкапов (`/pgworker/backups-disabled` + `Backups:Enabled`).
2. Глобальные дефолты policy бэкапов и квота bucket (`Backups:Policy`,
   `Quota{Bytes,Warn,Crit}` — кормит алерт `backup-storage-quota`).
3. Бюджеты бэкапов `Job:{Full,Verify,Restore}`, `Retry`, `Wal:{LagMaxSegments,StaleSec}`.
4. Пороги/таймауты надзора и тиков (`Thresholds`, `Moves:*`, `Loops:*`,
   `Parallelism`) — естественная «страница настроек воркера» (паттерн рестарта
   уже есть).
5. PGTune-профиль установки (`PGW_PGTUNE_*`) — влияет на все новые ноды.
6. Экспорт etcd-слепков (`PGW_SNAPSHOTS_*`) — статус виден, управления нет.
7. `AppParams:Default` (`sslmode=require`) — per-node параметры подключения.
8. Пины образов и диапазоны портов (`Images:Node`, `PortRange`).
9. Пороги алертов и проб панели (`AdminPanel:Alerts:*`, `Probes:*`).
10. Отмена живых заявок ротаций kafka/valkey — сегодня только etcdctl;
    правка стоящих заявок переездов — runbook.
11. `garbage_min_age_sec` — есть в arch/19 §4, отсутствует в форме policy
    панели (§3.8) — пробел контракта.
12. Состав etcd-контура (member add/remove) — runbook; панель показывает health.

Вынос каждого пункта — arch-first решение (изменение зон ответственности),
не только UI-работа.

## 3. Состояния, нотификации, алертинг

### 3.1. Автоматы состояний (сводно; каталоги — в arch)

| Домен | Автоматы |
|---|---|
| **pg** | Кластер `NOT_INITIALIZED→Active→TO_REMOVE`; шард `Active→TO_REMOVE` (guard'ы G1–G7); нода `NOT_INITIALIZED→PROVISIONING→RUNNING / REBUILDING / UNREACHABLE / QUARANTINED / REMOVING / TO_RECREATE`; бакет `Active (нет ключа) / NOT_INITIALIZED / SYNCING / FROZEN / ABORTING` (фазы ddl/frozen/flip/…); заявки переездов `move\|rollback\|finalize\|abort`; HA-scope Patroni (leader/members, master-lease 5 с) — [arch/14](../../arch/14-pgworker.md), [arch/11](../../arch/11-bucket-sharding.md) |
| **бэкапы** | Полный `PLANNED→RUNNING→UPLOADING→COMPLETED\|FAILED→DELETING`; verify `PENDING/OK/FAILED`; WAL-поток `ACTIVE/DEGRADED/STOPPED/WAL_CHAIN_ERROR` (+gap); приёмник `starting/waiting_*/streaming/paused/failed_permanent` (lease 15 с); restore `PLANNED→RUNNING→REJOINING→COMPLETED\|FAILED`; drill `RUNNING/SUCCEEDED/FAILED`; сироты `OBSERVED/DELETING`; хранилище `OK/WARN/CRIT`; выгрузка etcd-слепков `OK/FAILED` — [arch/19](../../arch/19-backups.md) |
| **kafka** | Кластер state; брокер `NOT_INITIALIZED→PROVISIONING→RUNNING / UNREACHABLE / REMOVING / TO_REMOVE` + role (навсегда); ротации app/admin/CA; reassignment (drain/balance, прогресс); регенерация; топики (факт + desired + lifecycle create/delete); ticket_outcomes `done\|expired` — [arch/16](../../arch/16-kafkaworker.md) |
| **valkey** | Кластер state; нода (v1 — одна); ротации кредов (окно двух паролей) и CA; TLS-миграция; ticket_outcomes — [arch/21](../../arch/21-valkeyworker.md) |
| **s3** | Кластер state; инстанс (state + placed_on + usage); connectivity `OK/DEGRADED/DOWN`; sync `SYNCED/LAGGING/DIVERGED`; denylist; ротации — [arch/24](../../arch/24-s3worker.md) |

Общий паттерн: **«нет status-ключа = штатное состояние»**; статус-ключи —
переходные; «последняя фаза побеждает» (журналы не копят историю — S6 arch/17).

### 3.2. События/нотификации: носители и видимость

| Событие | Носитель | Видно в панели |
|---|---|---|
| Фаза процесса воркера (provision/move/rotate/…, last_error, серия фейлов) | `/pgworker/work/<C>` (последняя фаза) | да (блок «Журнал воркера», алерт `provision-stuck`) |
| Failover/rebuild (cause, duration, ongoing) | `last_failover`/`last_rebuild` в work-ключе | да (грань «Надёжность», RTO) |
| Эвакуация шарда (план, карантин, возврат) | `/pgworker/evacuations/<C>/<X>` | **нет** (косвенно: QUARANTINED-ноды) |
| Завершение/отвержение заявки | исчезновение ключа заявки; причина — work.last_error; kafka/valkey — `ticket_outcomes` | частично |
| Само-починка карты бакетов (heal) | `/clusters/<C>/heals/<bucket>` | да (вкладка Heals) |
| Ротация секретов pg (фазы R0–R4) | `/pgworker/rotations/<C>` + work | косвенно |
| healthz воркеров (etcd/docker/loops/claims/snapshot/watchdog) | `GET /healthz` | агрегированно (healthy/degraded) |
| Пробы (Patroni/SQL/kafka/valkey/PING/S3-инвентарь) | память панели | да (runtime/live-поля) |
| Watchdog, takeover, свип сирот, исходы операций | host-логи + Prometheus `worker_*` | нет |
| etcd (alarms, лидер, raft) | maintenance API | да |

**Ключевой разрыв**: событийного слоя нет — журналы перезаписываются, истории
нет нигде, кроме host-логов и Prometheus-серий; панель видит только «сейчас».

### 3.3. Алертинг

- **Панель** — 4 движка (pg+бэкапы ~48 правил, kafka 22, valkey 11, s3 17),
  единая механика `id=kind:target` + `sinceUnix`; каждый алерт несёт **Hint**
  (что не так) и **Remedy** (движитель: `WorkerAuto` — починит воркер /
  `OperatorApi` — конкретная мутация / `OperatorRunbook` — руками). Каталог:
  [arch/adminpanel/03 §4, §7.4, §8.4, §12.4](../../arch/adminpanel/03-panels.md);
  пороги — `AdminPanel:Alerts` (appsettings, рестарт).
- **Prometheus/Alertmanager** — независимый канал: `WorkerLoopStalled`,
  `SnapshotStale`, группа `backups` (FullStale/WalLag/VerifyFailed/…),
  ServiceDown. Панель метрики не потребляет (граница по [arch/18](../../arch/18-metrics.md)).

### 3.4. Присутствует в системе, но не наблюдаемо из панели

1. Координация воркеров: `/pgworker/leader`, `/claims/<C>`, `/instances` —
   панель не знает, какой инстанс держит кластер.
2. Журналы эвакуаций `/pgworker/evacuations/*`.
3. Статусы приёмников WAL per-node `/pgworker/backups/<C>/<X>/agent/<N>`
   (waiting_password/waiting_slot/failed_permanent, tli_jump).
4. `/pgworker/backups/orphan-journal`.
5. Глобальный стоп бэкапов `/pgworker/backups-disabled` — префикс читается,
   индикации/алерта нет.
6. work-журналы kafka/valkey/s3 — «что воркер делает сейчас» в этих доменах
   видно лишь косвенно (заявки/прогресс/исходы).
7. Вся метрика Prometheus, host-логи, детали healthz (docker-hosts per-host).
8. Patroni-события вне work-фактов (switchover, pending_restart, paused).
9. История событий (см. §3.2).

## 4. Целевая модель интерфейса

### 4.1. Принципы разбиения

1. **Секция = домен источника истины.** Каждому воркеру — свой раздел
   (PostgreSQL, Kafka, Valkey, S3, etcd-контур). Грани, агрегирующие несколько
   доменов (алерты, надёжность, события, воркеры), — отдельные сквозные
   разделы, не примешанные к доменам.
2. **Обзор → список → сущность.** Три уровня детализации на домен; сущность
   адресуема (страница шарда/бакета/ноды — не только свёртка в JSON деталей
   кластера).
3. **Обзор отвечает на три вопроса**: «всё ли живо» (etcd, воркеры, домены),
   «что происходит» (активные операции), «что требует меня» (алерты по
   движителю Operator*).
4. **Управление — при своей сущности** (контекстные действия), зеркалит
   жизненный цикл: заявка → очередь → исполнение → исход; у стоящей заявки —
   отмена, у начатой — её операция (abort).
5. **Единый шаблон доменной страницы**: шапка-статус (state-бейджи, режимы,
   заявки в полёте) → вкладки сущностей → журнал воркера. Одинаковые по
   смыслу действия (удалить кластер, ротация, ресурсы) — одни компоненты.
6. **Параметры показываются с семантикой этапа**: что фиксировано при
   создании — read-only поля деталей; что живое — формы; что env — пометка
   «применяется рестартом воркера» (панель показывает где менять, но не
   меняет сама).
7. **Связи явные и двусторонние**: шард ↔ HA-скоп, кластер ↔ его бэкапы/RPO,
   алерт ↔ целевая сущность, бакет ↔ его переезд. Никаких неявных конвенций
   только на клиенте.
8. **Пять доменных снапшотов — одна модель свежести**: per-домен stale-бейдж.

### 4.2. Дерево навигации

```
ОБЗОР
  Дашборд                         сводные карточки: etcd, воркеры, 4 домена,
                                  бэкапы, надёжность; активные операции;
                                  алерты, требующие оператора
```

### 4.4. Сквозные элементы

Шапка: per-домен свежесть снапшотов (сейчас один общий stale-бейдж);

константы повторены в 4+ модалах и DTO).

## 5. Сопоставление с текущим интерфейсом

| Целевое | Текущее | Разрыв |
|---|---|---|
| Дашборд: активные операции, алерты по движителю | карточки + activeMoves + лента алертов | активные операции только по pg-переездам; kafka/s3 сводки есть, valkey-карточки нет (`OverviewDto.valkey` приходит, не отображается) |
| 5 разделов, домены вместе | плоское меню из 11 пунктов вперемешку | перегруппировка без новых страниц |
| Шард = страница с HA-блоком | HA — отдельный пункт; связь шард↔скоп ссылками, сущность «шард» не адресуема | слияние навигации |
| Журнал воркера per домен | только pg (`work`) | kafka/valkey/s3 work не читаются |
| События | нет | новый событийный слой |
| Координация воркеров на /workers | только инстансы/health/серты | leader/claims не читаются |
| Эффективный конфиг воркера | нет | read-only просмотр |
| Бэкапы кластера — срез в деталях кластера | грани разрознены (кластер / бэкапы / надёжность), обратных ссылок нет | навигация + серверные поля |

## 6. Задачи на доработку

Порядок — по смыслу Dependencies `←`. Каждая задача при запуске заводится
своим пунктом в трек `arch/adminpanel/roadmap/` (frontend/sharding/etcd) по
правилам роадмапа; изменяющая контракт — сначала правка `arch/adminpanel/`.

**Структура и навигация**

- **u01** — группировка навигации в 5 разделов (Обзор / Домены / Данные и
  защита / Наблюдение / Инфраструктура) и единый шаблон доменной страницы
  (шапка-статус → вкладки → журнал). Без новых данных, чистый UI.
- **u02** — общие компоненты действий (удалить кластер, ротация пароля/CA,
  изменить ресурсы, confirm-модалы) вместо 4 копий по каталогам доменов;
  единый источник границ валидации полей.
- **u03** ← u01: слияние HA в pg-домен: страница шарда с HA-блоком
  (leader/members/recreate), `/ha` — глобальный срез «репликация».
- **u04** — двусторонние связи: алерт → целевая сущность (deep-link);
  кластер → его бэкапы/RPO; бакет → переезд; RPO-строка → детали шарда
  (частично есть).
- **u05** — карточка Valkey на дашборде; заголовок `valkeyworker` на
  `/workers` (`WORKER_TITLES`).

**Обзор состояния**

- **u06** — серверная агрегация Overview: поля HA/бэкапов/надёжности в
  `OverviewDto` вместо клиентских доборов трёх API.
- **u07** — блок «Активные операции» на дашборде: инициализации, переезды,
  ротации, restore/drill, reassignment/регенерация — из заявок, статус-ключей
  и work-журналов всех доменов.
- **u08** — свежесть снапшотов per-домен (5 refresher'ов): per-домен
  stale-бейджи в шапке и на дашборде.
- **u09** ← u07: лента событий `/events` — клиентский событийный слой из
  диффов снапшотов (переходы состояний, исходы заявок, heals, эвакуации,
  ticket_outcomes). Историю НЕ хранит: живёт с открытой вкладкой.

**Пробелы наблюдаемости** (arch-first: расширение читаемых префиксов 02-etcd-contract)

- **u10** — глобальный стоп бэкапов: чтение `/pgworker/backups-disabled`,
  баннер на дашборде + грань бэкапов, алерт `backups-disabled`.
- **u11** — статусы приёмников WAL per-node (`agent/<N>`) в деталях шарда
  бэкапов: роль, waiting_*, failed_permanent, tli_jump.
- **u12** — эвакуации: чтение `/pgworker/evacuations/<C>/<X>`, блок в
  деталях кластера (план, карантин, возврат) + событие в ленте u09.
- **u13** — work-журналы kafka/valkey/s3 (`/…worker/work/`): блок «что делает
  воркер» в деталях кластера этих доменов (по образцу pg).
- **u14** — координация воркеров на `/workers`: leader, per-cluster claims,
  инстансы — «кто держит кластер» (read-only).

**Параметры**

- **u15** (arch-first решение) — «эффективный конфиг воркера» на `/workers`:
  read-only просмотр параметров установки (Thresholds/Loops/Moves/Parallelism,
  флаги подсистем, PGTune-профиль, Snapshots.Export), получаемых от воркера
  через его API; пометки «env, применяется рестартом». Мутации — НЕ входят
  (изменение зон — отдельное решение владельца, см. §2.3 п.1–5).
- **u16** — `garbage_min_age_sec` в форму policy бэкапов (пробел контракта
  §3.8/arch 02 §9.12).
- **u17** — отмена живых заявок ротаций kafka/valkey (сейчас только etcdctl):
  DELETE-эндпоинты + кнопка у бейджа «ротация…» (arch-first: протокол 02 §10/§11).

**Алертинг и контракт**

- **u18** — группировка алертов по Remedy-движителю (WorkerAuto /
  OperatorApi / OperatorRunbook) и фильтр по домену; вью «что требует меня».
- **u19** — синхронизация контракта с кодом: маршрут ротации pg
  (`secrets/rotate` в коде против `app-password/rotate` в arch/03 §1.6),
  каталог алертов §4 (в коде ~48 правил) и docs/adminpanel/03 (устаревшие
  «25 правил»); актуализация — тем же коммитом, что связанные UI-правки.

**Будущее (после roadmap t32-etcdworker)**

- **u20** — секция etcd-контура под etcdworker: состав узлов/кворум, перенос
  карточки etcd-слепков и алертов `etcd-snapshot-export-*` из грани бэкапов,
  DR-статус контроль-плейна.

## Чек-лист при изменениях

- Меняешь страницы/навигацию — обнови дерево §4.2 и таблицу §5.
- Появился новый читаемый префикс etcd — правка `arch/adminpanel/02` тем же
  коммитом, §3.4 здесь — снять пункт.
- Реализована задача uNN — её пункт удаляется из §6 тем же мерж-коммитом
  (правила roadmap).
- Новая мутация — сначала `arch/adminpanel/03 §1`, потом код, потом таблица
  §4.3.

## Грабли

- Пять независимых refresher'ов: «свежесть снапшота» ≠ одно число — каждый
  домен может отставать по-своему (u08).
- `OverviewDto` не содержит HA/бэкапов/надёжности — агрегация на клиенте
  плодит лишние запросы и TS-логику (u06).
- Журналы воркеров перезаписываются: UI не должен обещать «историю» — только
  текущую фазу и события, построенные из диффов (u09).
- `sharded` в DTO — вычисляемое поле (1×1 = нешардированный): вкладка Бакеты
  скрывается по нему, не по признаку в etcd.
- NOT_INITIALIZED/TO_REMOVE — штатная тишина: пробы/алерты по ним
  подавляются, UI красит серым, не красным.
