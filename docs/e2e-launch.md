# E2E: правила запуска и телеметрии (ПОСТОЯННЫЕ)

Правила действуют для **всех** E2E-прогонов (`E2e*` в
`src/tests/{PgWorker,KafkaWorker,ValkeyWorker,S3Worker}.E2eTests/`).
Архитектура контура (класс-фикстура поднимает своё окружение, изолированная
сеть, SUT-воркер-контейнер, тело факта — на хосте) —
[docs/e2e-isolation.md](e2e-isolation.md); этот файл — про «запустил, упало,
что делать».

## 0. Статика E2E — отдельная фаза подготовки ДО тестов

Publish-выводы и docker-образы PgWorker-контура (pgworker:e2e-{ветка},
pgworker-node:e2e-{ветка}, sdgenerator:e2e-{ветка}; owns3:dev) собирает
**один процесс до запуска тестов** — утилита подготовки:

```
dotnet run --project src/tests/PgWorker.E2ePrepare -c Release
```

- Тестовые процессы PgWorker статику **не строят** — только проверяют
  готовность: штамп `artifacts/e2e/.prepared` (JSON `{"stampMs"}`) новее
  всех исходников (`src/`, `docker/`, корневые props), ключевые образы — в
  docker. Иначе — fail-fast с подсказкой запустить подготовку (пачка-фейл,
  не скип и не автосборка).
- **Лок подготовки** `artifacts/e2e/.prepare.lock`: конкурентные подготовки
  одного worktree сериализуются (поллинг шагом 5 с, общий бюджет 10 минут;
  НЕ глобальный лок запуска серий — тестовые процессы лок не берут).
- Причина лока: конкурентный `dotnet publish` двух процессов в общий
  каталог ломает вывод (падение подготовки на старте).
- После правки исходников подготовку нужно перезапустить (штамп сверяется
  со свежестью исходников); повторный прогон инкрементален (десятки секунд).
- E2E-образы Kafka/Valkey/S3 (`kafkaworker`/`valkeyworker`/`s3worker`
  :e2e-{ветка}) утилита НЕ собирает — их E2E-проекты собирают сами
  once-per-process при первом старте окружения.
- `PGW_TEST_E2E_NOBUILD=1` — бисект-режим: publish/сборка пропускаются,
  используется существующий per-branch тег; отсутствие образа — fail-fast
  с подсказкой.
- Теги pg-собираемых образов — **per-branch** `e2e-{ветка}` (fallback
  `{хэш8}` пути worktree при git-недоступности/detached;
  `Shared.TestInfra.E2eImageTags`): разные ветки не перезаписывают образы
  друг друга. Слои docker-кэша общие — пересборка тега инкрементальна.
- Метки сборки — `[PHASE] e2e-static …`; журналы — per-process:
  `/tmp/pgw-e2e-static-phase-{ветка}-{pid}.log` (фазы) и
  `/tmp/pgw-e2e-static-process-{ветка}-{pid}-*.log` (полный вывод шагов);
  параллельные процессы пишут в разные файлы.
- Авто-уборка: после успешной подготовки теги `e2e-*` своих репозиториев
  старше 24 ч снимаются (`docker rmi` по одному, отказы игнорируются,
  текущий тег исключён).

## 1. Логи максимально полные — всегда

По логам прогона агент обязан уметь ответить «что произошло» **без
перезапуска тестов**. Поэтому:

- docker-логи и `inspect` **всех** контейнеров окружения (etcd, ownS3,
  SUT-воркеры) снимаются в teardown **до любого удаления** —
  `E2eEnvironment.CollectDiagnosticsAsync` (каталог телеметрии:
  `/tmp/pgw-e2e-artifacts-{guid}/`, выводится в журнал строкой
  `e2e[slug]: телеметрия … → …`); docker-логи снимаются **объединённо**:
  stdout-блок, затем stderr-блок (docker logs разделяет потоки контейнера
  по потокам CLI);
- тест исполняется в хост-процессе — журнал фактов и ассертов это vstest-вывод
  самого прогона (`dotnet test …`); логи воркеров — `docker logs` их
  контейнеров;
- вывод внешних процессов переживает таймаут: kill по бюджету оставляет
  хвост вывода (~40 строк) в исключении `RunProcessAsync`, полный вывод — в
  `process-*.log` (build-вызовы подключены);
- диагностика в сообщениях ассертов — **без обрезок**; исключения,
  проглатывающие вывод, в E2E-коде не вводить: всё, что падает, падает с
  контекстом;
- каталог телеметрии читается с хоста — фазовый журнал, дампы и маркеры
  упавшего сценария доступны для разбора.

## 2. Отчёт по любой фазе дольше 60 с

Бюджеты фаз (PatroniBootSec=120 и т.п.) не освобождают от объяснения: если
фаза заняла **больше 60 с** — нужен отчёт «почему», даже если тест зелёный.

- Фазовые ожидания — через единый `E2ePhase.WaitAsync`: итоговая строка
  строго формата
  `[PHASE] <phase>: ok=<bool>, elapsed=<N.N>s, budget=<N>s[, progress=<снимок>]`,
  прогресс-тики `[PHASE-TICK] <phase> t=<N.N>s: <снимок>` каждые 5 с.
  Копии `WaitPhaseAsync` в restore/supervisor-классах — легальный прецедент
  до отдельной миграции.
- Прогресс-делегаты — только дешёвые снапшоты (etcd-чтения, лёгкие
  SQL-скаляры, S3-листинг не чаще 1 раза в 5 с); docker-CLI в тиках
  запрещён — docker-картина попадает в slow/failed-phase-сбор.
- Пересечение 60 с → немедленный сбор docker-логов окружения в артефакты
  (`CollectDiagnosticsAsync($"slow-phase-…")`).
- Провал окна (ok=False) → немедленный сбор `CollectDiagnosticsAsync($"failed-phase-…")`
  до возврата управления сценарию.
- Каждая `[PHASE]`/`[PHASE-TICK]`-строка дублируется в
  `<ArtifactsDir>/phases.log` с UTC-меткой — наблюдение за «тихими» фазами
  онлайн (каталог телеметрии на хосте).
- Новое ожидания-участок в сценарии обязан идти через `E2ePhase.WaitAsync`.
- Подъём окружения и сборка образов — с `[PHASE] e2e-static …`-метками и
  таймингом (per-process журнал `/tmp/pgw-e2e-static-phase-{ветка}-{pid}.log`):
  «тихих» фаз нет.

## 3. Упал тест → контейнеры ОСТАНОВИТЬ, не удалить

- Фейл факта/класса → `DisposeAsync` окружения выполняется в stop-режиме:
  контейнеры (вкл. etcd/ownS3/воркеров) `docker stop`, тома и сети
  остаются как есть — разбор по живым объектам и снятым логам.
- Сценарий может помечать упавшее окружение и раньше: `fx.MarkFailed()` в
  catch (телеметрия фазы честно пишет маркер).
- Команды зачистки — `README-cleanup.txt` в каталоге телеметрии (own-only,
  по guid/тегу прогона). Зачистка — когда стало понятно, что данные для
  отчёта больше не нужны (решает пользователь).
- Ассерт чистоты в stop-режиме не применяется (объекты остаются намеренно).

## 4. Перезапуск после падения — только после полного анализа

- **Перезапуск тестов для выяснения «что было» запрещён без согласия
  пользователя.**
- Повторный прогон допустим только после **полного** анализа логов упавшего
  прогона (vstest-журнал, docker-логи воркеров/нод из артефактов, состояние
  etcd/S3 в дампах) и формулировки **всех** правдоподобных причин с
  проверяемыми следствиями; гипотеза перезапуска названа явно (и
  пользователь согласовал).
- «Погоняю ещё раз, авось зелёное» — нарушение и тогда, когда прогон
  формально нужен «для проверки фикса»: сначала отчёт по причинам, потом
  прогон.

## 5. Параллелизм и нагрузка (канон прогона серии)

Классы E2E-проектов параллельны: каждый E2E-проект — `xunit.runner.json`
`maxParallelThreads: 5`; PgWorker дополнительно — **Guard-слот**
`E2eParallelismGuard`: жёсткий SemaphoreSlim, дефолт **3 контура** —
стабильный старт параллельности (5 контуров на docker-VM 7.7GB перегружали
демон — каскад таймаутов docker CLI/etcd). Настраивается env
**`PGW_E2E_MAX_CONTOURS`** (5/8 — подъём без правок кода после наращивания
ресурсов хоста). Слот захватывается в `InitializeAsync` класс-фикстуры ДО
создания первого docker-объекта окружения, освобождается в `DisposeAsync`
при любом исходе. Kafka/Valkey/S3 — без семафора: параллельность
регулируется только `maxParallelThreads` (их контуры существенно легче
PgWorker-PG-контуров). Факты внутри класса последовательны (делят окружение
класса). Превышение дефолта — громкая пометка `[E2E-PARALLELISM]`
(результаты вне стабильного канона требуют пометки).

Отчётность: каждый факт завершается **Passed/Failed** — `Skipped: 0` —
норма штатного прогона серии (единственный допускаемый скип — условное
предусловие TLI-сценария `_prepareSkip`). Упавший факт — `Failed` с хвостом
телеметрии; stop-режим и `README-cleanup.txt` — §3. Прогон E2E-проекта
PgWorker без подготовки статики — мгновенный пачка-фейл fail-fast с
подсказкой запустить подготовку (не скип).

Сетевой слой — единая сеть окружения (контур-режим: ноды/джобы/агенты в ней
же, per-cluster `pgw-net-<C>` не создаётся); портовой слой —
непересекающиеся per-контур окна PortRange для продуктовых публикаций нод;
публикации тестовой инфраструктуры — только динамические (e2e-isolation §2).
Не-E2E тесты последовательны всегда: `[Collection]`-группа `NonE2eCollection`
(`DisableParallelization=true`).

Правила окружения docker-хоста (внешнее — не предмет тестов):

- серию не запускать поверх другого тяжёлого docker-прогона; чужие E2E-серии
  и поднятый dev-стенд — учитывать перед запуском; K=0-прогоны (базлайны,
  приёмка) — только после гейта тишины;
- переопределение потолка — временная правка `maxParallelThreads` в
  runner.json с ОБЯЗАТЕЛЬНЫМ возвратом и контролем канонического значения
  (диагностические прогоны N>5 легальны, но громки).

Признаки деградации (что смотреть в логах):

- серийные `getaddrinfo … empty` / `failed to resolve host` в docker-логах
  PG-нод (DNS-контур: сверять advertise-лист и сеть контейнера — алиас чужой
  сети в advertise недопустим, arch/04 §8 п.3);
- мгновенные (~0,3 с) фейлы коннекта в transient-циклах воркера (docker logs
  воркеров);
- рост `[PHASE] … elapsed` у фаз, которые в тишине проходят быстро.

Действия при фейле параллельной серии: разбор по телеметрии teardown БЕЗ
перезапуска (§4); отложить прогон до тишины хоста / пересмотреть N и
повторять ТОЛЬКО после анализа и с гипотезой.

## Где что лежит после прогона

| Что | Где |
|---|---|
| docker-логи контейнеров (`container-*.log` (stdout+stderr), `container-*.json`, вкл. воркеров) | `/tmp/pgw-e2e-artifacts-<guid>/` |
| фазовый журнал (`phases.log`, UTC-метки) | там же |
| отметки медленных фаз (`*-slow-phase-*.txt`) | там же |
| сбор в момент провала фазы (`*-failed-phase-*.txt`) | там же |
| полный вывод процессов при таймауте и build-вызовов (`process-*.log`) | там же |
| дампы Wal-сценариев (`wal-diag-<cluster>.txt`) | там же |
| команды зачистки упавшего прогона | `README-cleanup.txt` там же |
| полный вывод статических build/publish | `/tmp/pgw-e2e-static-process-{ветка}-{pid}-*.log` (рядом с журналом статических фаз `/tmp/pgw-e2e-static-phase-{ветка}-{pid}.log` — статические ассеты процесса живут до окружений) |
| журнал прогона тестов (факты, ассерты) | stdout `dotnet test …` |

Состояние реализации: `E2eContourFixture` (класс-фикстура: Guard-слот до
подъёма, `E2eEnvironment.StartAsync` в `InitializeAsync`, teardown +
телеметрия + stop-режим в `DisposeAsync`), воркер — контейнер
`pgworker:e2e-{ветка}` (`StartHostAsync`), канон фазовых ожиданий —
`E2ePhase` (`[PHASE]`/`[PHASE-TICK]`, `phases.log`, пороги 60 с /
failed-phase); `RunProcessAsync` сохраняет вывод при kill по бюджету и
пишет полные логи build-вызовов.
