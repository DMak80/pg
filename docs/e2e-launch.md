# E2E: правила запуска и телеметрии (ПОСТОЯННЫЕ)

Правила действуют для **всех** E2E-прогонов (`E2e*` в
`src/tests/PgWorker.IntegrationTests/E2e/`). Архитектура контура (две фазы,
изолированная сеть, SUT-воркер-контейнер) —
[docs/e2e-isolation.md](e2e-isolation.md); этот файл — про «запустил, упало,
что делать».

## 1. Логи максимально полные — всегда

По логам прогона агент обязан уметь ответить «что произошло» **без
перезапуска тестов**. Поэтому:

- docker-логи и `inspect` **всех** контейнеров окружения (etcd, ownS3,
  SUT-воркеры, раннер) снимаются в teardown **до любого удаления** —
  `E2eEnvironment.CollectDiagnosticsAsync` (каталог телеметрии:
  `/tmp/pgw-e2e-artifacts-{guid}/`, выводится в журнал строкой
  `e2e[slug]: телеметрия … → …`);
- полный stdout/stderr раннера (тестовый журнал, `[PHASE]`-строки,
  диагностика ассертов) — `runner.log` там же (вывод `docker logs` раннера);
  логи воркеров — `docker logs` их контейнеров (хост-процессов и host.log
  в контуре нет);
- вывод внешних процессов переживает таймаут: kill по бюджету оставляет
  хвост вывода (~40 строк) в исключении `RunProcessAsync`, полный вывод — в
  `process-*.log` (build-вызовы подключены);
- диагностика в сообщениях ассертов — **без обрезок**; исключения,
  проглатывающие вывод, в E2E-коде не вводить: всё, что падает, падает с
  контекстом;
- `/artifacts` раннера смонтирован на каталог телеметрии хоста: фазовый
  журнал, дампы и маркеры упавшего сценария видны с обеих сторон.

## 2. Отчёт по любой фазе дольше 60 с

Бюджеты фаз (PatroniBootSec=120 и т.п.) не освобождают от объяснения: если
фаза заняла **больше 60 с** — нужен отчёт «почему», даже если тест зелёный.

- Фазовые ожидания — через единый `E2ePhase.WaitAsync`: итоговая строка
  строго формата
  `[PHASE] <phase>: ok=<bool>, elapsed=<N.N>s, budget=<N>s[, progress=<снимок>]`,
  прогресс-тики `[PHASE-TICK] <phase> t=<N.N>s: <снимок>` каждые 5 с.
  Копии `WaitPhaseAsync` в restore/supervisor-классах — легальный прецедент
  до отдельной миграции.
- Прогресс-делегаты — только дешёвые снапшоты (etcd-чтения, лёгкие
  SQL-скаляры, S3-листинг не чаще 1 раза в 5 с); docker-CLI в тиках
  запрещён — docker-картина попадает в slow/failed-phase-сбор.
- Пересечение 60 с → немедленный сбор docker-логов окружения в артефакты
  (`CollectDiagnosticsAsync($"slow-phase-…")`).
- Провал окна (ok=False) → немедленный сбор `CollectDiagnosticsAsync($"failed-phase-…")`
  до возврата управления сценарию.
- Каждая `[PHASE]`/`[PHASE-TICK]`-строка дублируется в
  `<ArtifactsDir>/phases.log` с UTC-меткой — наблюдение за «тихими» фазами
  онлайн (в том числе из контейнера раннера: `/artifacts` — общий volume).
- Новое ожидания-участок в сценарии обязан идти через `E2ePhase.WaitAsync`.
- Подъём окружения и сборка образов — с `[PHASE] e2e-static …`-метками и
  таймингом (файл `/tmp/pgw-e2e-static-phase.log`): «тихих» фаз нет.

## 3. Упал тест → контейнеры ОСТАНОВИТЬ, не удалить

- Exit code раннера ≠ 0 → teardown фазы 1 выполняется в stop-режиме:
  контейнеры (вкл. etcd/ownS3/воркеров/раннер) `docker stop`, тома и сети
  остаются как есть — разбор по живым объектам и снятым логам.
- Сценарий внутри раннера может помечать упавшее окружение и раньше:
  `fx.MarkFailed()` в catch (телеметрия фазы честно пишет маркер).
- Команды зачистки — `README-cleanup.txt` в каталоге телеметрии (own-only,
  по guid/тегу прогона). Зачистка — когда стало понятно, что данные для
  отчёта больше не нужны (решает пользователь).
- Ассерт чистоты в stop-режиме не применяется (объекты остаются намеренно).

## 4. Перезапуск после падения — только после полного анализа

- **Перезапуск тестов для выяснения «что было» запрещён без согласия
  пользователя.**
- Повторный прогон допустим только после **полного** анализа логов упавшего
  прогона (журнал раннера, docker-логи воркеров/нод из артефактов, состояние
  etcd/S3 в дампах) и формулировки **всех** правдоподобных причин с
  проверяемыми следствиями; гипотеза перезапуска названа явно (и
  пользователь согласовал).
- «Погоняю ещё раз, авось зелёное» — нарушение и тогда, когда прогон
  формально нужен «для проверки фикса»: сначала отчёт по причинам, потом
  прогон.

## 5. Параллелизм и нагрузка (канон прогона серии)

Потолок живых контуров — **дроссель E2eParallelismGuard**: жёсткий
SemaphoreSlim, дефолт **3 контура** — стабильный старт параллельности
(5 контуров на docker-VM 7.7GB перегружали демон — каскад таймаутов
docker CLI/etcd). Настраивается env **`PGW_E2E_MAX_CONTOURS`** (5/8 —
подъём без правок кода после наращивания ресурсов хоста).
`xunit.runner.json maxParallelThreads=5` — потолок ПОТОКОВ фактов
(намеренно выше дросселя: потоки ждут слот контура). Превышение дефолта —
громкая пометка `[E2E-PARALLELISM]` (результаты вне стабильного канона
требуют пометки). Внутри раннера параллелизма нет: факт прогоняет один
сценарный метод.

Отчётность двухфазного прогона: факт-оркестратор завершается **Skipped**
(Assert.Skip после зелёного раннера — реальный результат в
`runner.log`) или **Failed** (с хвостом журнала раннера). Зелёный прогон
серии: `Failed: 0`, `Skipped: N`; результат каждого сценария — в
`runner.log` его окружения («Total: 1 … Failed: 0»). Прогон, в котором
раннер не нашёл ни одного теста по фильтру, — ошибка оркестрации (fail-safe).

Сетевой слой — единая сеть окружения (контур-режим: ноды/джобы/агенты в ней
же, per-cluster `pgw-net-<C>` не создаётся); портовой слой — непересекающиеся
per-контур окна PortRange для продуктовых публикаций нод; хост-публикаций
тестовой инфраструктуры нет. Не-E2E тесты последовательны всегда:
`[Collection]`-группа `NonE2eCollection` (`DisableParallelization=true`).

Правила окружения docker-хоста (внешнее — не предмет тестов):

- серию не запускать поверх другого тяжёлого docker-прогона; чужие E2E-серии
  и поднятый dev-стенд — учитывать перед запуском; K=0-прогоны (базлайны,
  приёмка) — только после гейта тишины;
- переопределение потолка — временная правка `maxParallelThreads` в
  runner.json с ОБЯЗАТЕЛЬНЫМ возвратом и контролем канонического значения
  (диагностические прогоны N>5 легальны, но громки).

Признаки деградации (что смотреть в логах):

- серийные `getaddrinfo … empty` / `failed to resolve host` в docker-логах
  PG-нод (DNS-контур: сверять advertise-лист и сеть контейнера — алиас чужой
  сети в advertise недопустим, arch/04 §8 п.3);
- мгновенные (~0,3 с) фейлы коннекта в transient-циклах воркера (docker logs
  воркеров);
- рост `[PHASE] … elapsed` у фаз, которые в тишине проходят быстро.

Действия при фейле параллельной серии: разбор по телеметрии teardown БЕЗ
перезапуска (§4); отложить прогон до тишины хоста / пересмотреть N и
повторять ТОЛЬКО после анализа и с гипотезой.

## Где что лежит после прогона

| Что | Где |
|---|---|
| docker-логи контейнеров (`container-*.log`, `container-*.json`, вкл. воркеров и раннера) | `/tmp/pgw-e2e-artifacts-<guid>/` |
| полный тестовый журнал раннера (`runner.log`) | там же |
| фазовый журнал (`phases.log`, UTC-метки) | там же |
| отметки медленных фаз (`*-slow-phase-*.txt`) | там же |
| сбор в момент провала фазы (`*-failed-phase-*.txt`) | там же |
| полный вывод процессов при таймауте и build-вызовов (`process-*.log`) | там же |
| дампы Wal-сценариев (`wal-diag-<cluster>.txt`) | там же |
| команды зачистки упавшего прогона | `README-cleanup.txt` там же |
| полный вывод статических build/publish (`/tmp/pgw-e2e-static-process-*.log`) | `/tmp` (рядом с журналом статических фаз `/tmp/pgw-e2e-static-phase.log` — статические ассеты процесса живут до окружений) |
| журнал факта-оркестратора (vstest-вывод хоста) | stdout прогона `PGW_TEST_DOCKER=1 dotnet test …` |

Состояние реализации: `E2eEnvironment` (фаза 1: сеть/etcd/ownS3 без
publish, teardown + телеметрия + stop-режим), `E2eContour` (двухфазный
запуск: хост-оркестрация + раннер-контейнер), воркер — контейнер
`pgworker:e2e` (`StartHostAsync`), канон фазовых ожиданий — `E2ePhase`
(`[PHASE]`/`[PHASE-TICK]`, `phases.log`, пороги 60 с / failed-phase);
`RunProcessAsync` сохраняет вывод при kill по бюджету и пишет полные логи
build-вызовов.
