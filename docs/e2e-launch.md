# E2E: правила запуска и телеметрии (ПОСТОЯННЫЕ)

Правила заданы пользователем 2026-09-13 и действуют для **всех** E2E-прогонов
(`E2e*` в `src/tests/PgWorker.IntegrationTests/E2e/`). Изоляция окружений —
[docs/e2e-isolation.md](e2e-isolation.md); этот файл — про «запустил, упало,
что делать».

## 1. Логи максимально полные — всегда

По логам прогона агент обязан уметь ответить «что произошло» **без перезапуска
тестов**. Поэтому:

- docker-логи и `inspect` **всех** контейнеров окружения снимаются в teardown
  **до любого удаления** — `E2eEnvironment.CollectDiagnosticsAsync`
  (каталог телеметрии: `/tmp/pgw-e2e-artifacts-<guid>/`, выводится в журнал
  теста строкой `e2e[slug]: телеметрия … → …`);
- туда же копируются `host.log` воркеров (полный stdout/stderr инстанса);
- вывод внешних процессов переживает таймаут: kill по бюджету оставляет хвост
  вывода (~40 строк) в исключении `RunProcessAsync`, полный вывод — в
  `process-*.log` (build-вызовы подключены);
- диагностика в сообщениях ассертов — **без обрезок** (`DumpDiagnosticsAsync`
  отдаёт журнал воркера целиком);
- исключения, проглатывающие вывод, в E2E-коде не вводить: всё, что падает,
  падает с контекстом.

## 2. Отчёт по любой фазе дольше 60 с

Бюджеты фаз (PatroniBootSec=120 и т.п.) не освобождают от объяснения: если
фаза заняла **больше 60 с** — нужен отчёт «почему», даже если тест зелёный.

- Фазовые ожидания t29-классов и все новые сценарии — через единый
  `E2ePhase.WaitAsync`: итоговая строка строго формата
  `[PHASE] <phase>: ok=<bool>, elapsed=<N.N>s, budget=<N>s[, progress=<снимок>]`,
  прогресс-тики `[PHASE-TICK] <phase> t=<N.N>s: <снимок>` каждые 5 с (короткие
  окна 10–15 с дают 2–3 строки динамики). Restore-сценарии используют свои
  `WaitPhaseAsync`/`WaitRestoreAsync` — легальный прецедент до отдельной
  миграции.
- Прогресс-делегаты — только дешёвые снапшоты (etcd-чтения, лёгкие
  SQL-скаляры, S3-листинг не чаще 1 раза в 5 с); docker-CLI в тиках
  запрещён — поллинг демона искажает измеряемую нагрузку; docker-картина
  попадает в slow/failed-phase-сбор, не в тики.
- Пересечение 60 с → немедленный сбор docker-логов окружения в артефакты
  (`CollectDiagnosticsAsync($"slow-phase-…")`), не дожидаясь teardown'а.
- Провал окна (ok=False) → немедленный сбор `CollectDiagnosticsAsync($"failed-phase-…")`
  **до возврата управления сценарию** (контейнеры ещё живые, teardown ещё не
  мутировал): флейк-окна 10–30 с порогом 60 с не покрывались.
- Каждая `[PHASE]`/`[PHASE-TICK]`-строка дублируется в
  `<ArtifactsDir>/phases.log` с UTC-меткой — онлайн-наблюдение за «тихими»
  фазами без остановки теста и «последний успешный шаг» при разборе; метки
  сопоставимы с `docker logs --timestamps`.
- Новый ожидания-участок в сценарии обязан идти через `E2ePhase.WaitAsync`.

## 3. Упал тест → контейнеры ОСТАНОВИТЬ, не удалить

- Сценарий в `catch` помечает окружение: `fx.MarkFailed()`
  (обёртка `RunScenarioAsync` делает это сама).
- Тогда teardown **не удаляет** docker-объекты: контейнеры (вкл. etcd/MinIO)
  `docker stop`, тома и сети остаются как есть — разбор по живым объектам и
  снятым логам.
- Команды зачистки тест пишет сам: `README-cleanup.txt` в каталоге телеметрии
  (own-only, по guid/тегу прогона). Зачистка — после того как стало понятно,
  что данные для отчёта больше не нужны (решает пользователь).
- Ассерт чистоты в stop-режиме не применяется (объекты остаются намеренно).

## 4. Перезапуск после падения — только после полного анализа

- **Перезапуск тестов для выяснения «что было» запрещён без согласия
  пользователя.**
- Повторный прогон допустим только после **полного** анализа логов упавшего
  прогона (журнал теста, `host.log` воркеров, docker-логи из артефактов,
  состояние etcd/S3 в дампах) и формулировки **всех** правдоподобных причин
  с проверяемыми следствиями; гипотеза, которую проверяет перезапуск, названа
  явно (и пользователь согласовал).
- «Погоняю ещё раз, авось зелёное» — нарушением является и тогда, когда прогон
  формально нужен «для проверки фикса»: сначала отчёт по причинам, потом прогон.

## 5. Параллелизм и нагрузка (канон прогона серии)

Канон параллелизма полной E2E-серии — **5 контуров** (`maxParallelThreads=5`
в `src/tests/PgWorker.IntegrationTests/xunit.runner.json` — единственный
источник потолка; xunit.v3 читает конфиг из output). Канон выбран приёмкой
(серии N=3/5/6 на целевой конфигурации — разбитые классы, сетевые и портовые
митигации; критерий «максимально быстрое и стабильное», измерения приёмки —
в архиве задачи в `docs/superpowers/`): N=5 даёт лучшее время (~19–22 мин против
30,9 при N=3), зелёная точка 41/41 подтверждена. AC5 (failover ≤5 с) при N=5
нагрузочно-чувствителен (флейк 1/3 серий на загруженном docker-хосте) —
прод-требование проверяется малопараллельным прогоном.

Сетевой слой — per-cluster (arch/14 §2.1): сети нод `pgw-net-<C>` создаются
движком и удаляются демонтажем; DNS-зоны контуров изолированы; advertise etcd
— только URL, резолвимые из сетей потребителей (arch/04 §8 п.3). Портовой
слой — per-contour окна 200 портов с bind-резервом (arch/14 §2.4 п.2).
Не-E2E тесты последовательны всегда: `[Collection]`-группа
`NonE2eCollection` (`DisableParallelization=true`).

Правила окружения docker-хоста (внешнее — не предмет тестов):

- параллельность серии — канонический потолок 5 контуров; чужие E2E-серии
  и поднятый dev-стенд на том же хосте — учитывать перед запуском серии;
- серию не запускать поверх другого тяжёлого docker-прогона — дождаться
  завершения; K=0-прогоны (базлайны, приёмка) — только после гейта тишины;
- рельса: `E2eEnvironment` при фактическом превышении канона пишет громкое
  `[E2E-PARALLELISM]` (диагностические прогоны с переопределённым потолком
  легальны, но громки; переопределение — временная правка `maxParallelThreads`
  в runner.json с ОБЯЗАТЕЛЬНЫМ возвратом и контролем канонического значения).

Признаки деградации (что смотреть в логах):

- серийные `getaddrinfo … empty` / `failed to resolve host` в docker-логах
  PG-нод (DNS-контроль канона: подсчёт по этим логам; Patroni-клиент etcd:
  сверять advertise-лист и сеть контейнера — алиас чужой сети в advertise
  недопустим, arch/04 §8 п.3);
- мгновенные (~0,3 с) фейлы коннекта в transient-циклах воркера (`host-*.log`);
- рост `[PHASE] … elapsed` у фаз, которые в тишине проходят быстро.

Действия при фейле параллельной серии:

- разбор по телеметрии teardown БЕЗ перезапуска (§4): этап смерти соединения
  (резолв / TCP / хендшейк) по Patroni-логам/docker-логам PG-нод + host.log;
- отложить прогон до тишины хоста (чужие контуры) / пересмотреть N и
  повторять ТОЛЬКО после анализа и с гипотезой.

## Где что лежит после прогона

| Что | Где |
|---|---|
| docker-логи контейнеров (`container-*.log`, `container-*.json`) | `/tmp/pgw-e2e-artifacts-<guid>/` |
| `host.log` воркеров (`host-<name>.log`) | там же |
| фазовый журнал (`phases.log`, UTC-метки) | там же |
| отметки медленных фаз (`*-slow-phase-*.txt`) | там же |
| сбор в момент провала фазы (`*-failed-phase-*.txt`) | там же |
| полный вывод процессов при таймауте и build-вызовов (`process-build-<tag>.log`) | там же |
| дампы Wal-сценариев (`wal-diag-<cluster>.txt`) | там же |
| команды зачистки упавшего прогона | `README-cleanup.txt` там же |
| полный вывод статических build/publish (`/tmp/pgw-e2e-static-process-*.log`) | `/tmp` (рядом с журналом статических фаз `/tmp/pgw-e2e-static-phase.log`, вне каталогов прогонов: статические ассеты процесса живут до окружений) |
| журнал теста (vstest-вывод) | stdout прогона / `dotnet test ... --logger "console;verbosity=detailed"` |

Состояние реализации: `E2eEnvironment` (сбор логов в teardown, stop-режим
`MarkFailed`, probe-контур с телеметрией попыток), канон фазовых ожиданий —
`E2ePhase` (t29-классы мигрированы: `[PHASE]`/`[PHASE-TICK]`, `phases.log`,
пороги 60 с / failed-phase); копии `WaitPhaseAsync` в restore/supervisor-классах
— легальный прецедент до отдельной миграции. `RunProcessAsync` сохраняет вывод
при kill по бюджету и пишет полные логи build-вызовов.
