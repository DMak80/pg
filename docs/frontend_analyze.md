# Анализ бизнес-функционала AdminPanel

Данный документ описывает функциональные возможности, основные разделы и бизнес-процессы интерфейса управления (AdminPanel). Анализ сфокусирован на операционной деятельности администратора системы, а не на технической реализации кода.

## 1. Назначение системы
AdminPanel является централизованной панелью управления (Control Plane) для эксплуатации распределённых высокодоступных (HA) систем: шардированных PostgreSQL-кластеров, Kafka-кластеров, Valkey-кластеров и S3-хранилищ.

**Основная задача оператора:** обеспечение непрерывности работы (Availability), сохранности данных (Durability) и управление жизненным циклом сервисов.

## 2. Основные функциональные домены

### 2.1. Управление базами данных (Postgres/Sharding)
Центральный блок управления, где происходит работа с основными бизнес-данными.
- **Управление жизненным циклом кластера:** создание новых кластеров, перевод существующих в режим удаления (TO_REMOVE).
- **Масштабирование (Elasticity):** добавление или удаление шардов (узлов распределения данных) для изменения мощности системы.
- **Перемещение данных (Rebalancing):** процесс переноса бакетов (логических сегментов данных) между шардами для выравнивания нагрузки или эвакуации узлов.
- **Контроль целостности:** мониторинг состояния бакетов (активен, синхронизируется, заморожен) и управление процессами переезда.

### 2.2. Высокая доступность (HA)
Инструментарий для контроля за отказоустойчивостью.
- **Мониторинг лидеров:** отслеживание наличия активного лидера (Master) в каждом «scope» (области ответственности).
- **Здоровье участников:** контроль состояния реплик, лага репликации и соответствия конфигурации ожиданиям.

### 2.3. Инфраструктурный контроль (Etcd & Workers)
Мониторинг «фундамента» системы.
- **Здоровье Etcd:** контроль доступности узлов кластера конфигураций, отслеживание алармов и состояния кворума. Без работающего Etcd управление системой невозможно.
- **Управление исполнителями (Workers):** мониторинг инстансов воркеров (PgWorker, KafkaWorker, S3Worker, ValkeyWorker), которые фактически выполняют команды.
- **Безопасность коммуникаций:** управление сертификатами API-интерфейсов воркеров (генерация, загрузка, отзыв) для обеспечения mTLS-защиты между панелью и исполнителями.

### 2.4. Наблюдаемость и алертинг (Observability)
Система раннего оповещения о проблемах.
- **Автоматические пробы:** активный опрос (SQL, Patroni, S3, API) для обнаружения проблем «в поле» (недоступность порта, разрыв репликации, потеря кворума).
- **Умный алертинг:** классификация инцидентов по критичности (Critical/Warning/Info) с предоставлением оператору конкретных инструкций (Hint) и способов исправления (Remedy).

### 2.5. Жизненный цикл данных (Backups/S3)
Управление резервным копированием.
- **Мониторинг хранилища:** контроль доступности S3, заполненности дисков и целостности инвентаря бэкапов.
- **Управление политиками:** настройка правил ретенции (хранения) и периодичности проверок (drills) целостности бэкапов.

### 2.6. Специализированные сервисы (Kafka, Valkey, S3)
Выделенные интерфейсы для управления специфическими распределёнными системами:
- **Kafka:** управление топиками, брокерами и ребалансировкой партиций.
- **Valkey:** управление конфигурацией памяти и нодами кэш-кластера.
- **S3:** управление графом репликации и связностью узлов хранилища.

## 3. Ключевые бизнес-процессы и состояния

### 3.1. Жизненный цикл кластера
Объекты проходят через строго определённые фазы:
1. **NOT_INITIALIZED:** Кластер заявлен, но инфраструктура ещё поднимается. Оператор видит это как «ожидание».
2. **ACTIVE:** Рабочее состояние. Все функции управления (масштабирование, переезды) доступны.
3. **TO_REMOVE:** Режим демонтажа. Кластер помечается на удаление, оператор ждёт завершения очистки ресурсов оркестратором.

### 3.2. Процесс перемещения данных (Move)
Это многостадийный процесс, требующий контроля:
- **Заявка:** Оператор инициирует переезд бакета.
- **Очередь:** Заявка встает в очередь и выполняется воркером последовательно.
- **Статус:** Оператор видит фазу (синхронизация, заморозка, финализация) и может отменить процесс (Abort) на ранних стадиях.

## 4. Взаимосвязи между разделами

### 4.1. Overview — центральный хаб
Это первая страница, на которую попадает оператор. Она **агрегирует сводки со всех остальных разделов**:
- Карточки «etcd», «Кластеры», «Kafka», «S3», «Бэкапы», «Надёжность», «HA» — каждая ведёт на свой раздел.
- Лента алертов в Обзоре — это сводка из раздела «Алерты».
- Таблица «Активные переезды» — это сводка из разделов «Кластеры → Переезды».

Таким образом, **Overview зависит от всех остальных разделов** — без данных из любого из них карточка становится пустой или показывает предупреждение.

### 4.2. Кластеры (Postgres) → HA
- Внутри **деталей конкретного Postgres-кластера** поле scope (из HA) позволяет перейти на страницу **HA → детали скопа**.
- На странице **HA** каждый скоп показывает, к какому (cluster, shard) он привязан.
- Таким образом, **HA зависит от данных из раздела «Кластеры»** — без известных кластеров скопы в HA отображаются как «unmatched» (нераспознанные).

### 4.3. Кластеры (Postgres) → Workers
- **Раздел «Workers»** показывает все запущенные инстансы PgWorker, KafkaWorker, S3Worker, ValkeyWorker.
- Каждый воркер управляет своим доменом: PgWorker — Postgres-кластеры, KafkaWorker — Kafka-кластеры, и т.д.
- **Кластеры зависят от воркеров** — если воркер недоступен (нет живого lease-ключа), панель не может выполнить мутации (создание/удаление/перемещение) и показывает алерт «worker-api-unreachable» (critical).

### 4.4. Кластеры (Postgres) → Бэкапы
- **Раздел «Хранилище бэкапов»** показывает данные по бэкапам для **каждого Postgres-кластера**.
- У каждого кластера можно выбрать «Пул бэкапов» — это **связь с S3-кластером** (см. 4.5).
- **Бэкапы зависят от Postgres-кластеров** — без кластера нет данных для мониторинга бэкапов.

### 4.5. Бэкапы → S3
- **Пул бэкапов** — это фактически S3-кластер (или его часть), через который пишутся бэкапы Postgres.
- **Раздел «S3»** показывает инфраструктуру S3-кластеров и их ноды.
- Таким образом, **бэкапы Postgres косвенно зависят от S3-кластеров**: если S3-кластер недоступен, бэкапы не пишутся.

### 4.6. Бэкапы → Надёжность
- **Раздел «Надёжность»** показывает RPO-потенциал и RTO-факты — все эти данные **выводятся из данных бэкапов**.
- **Надёжность зависит от Бэкапов**: если бэкапы не настроены, карточка показывает «нет данных».
- На обзоре (Overview) карточка «Надёжность» агрегирует: worst RPO, длительность последнего failover — всё берётся из `/api/reliability`, который в свою очередь агрегирует данные из всех бэкапов и кластеров.

### 4.7. Кластеры (Postgres) → Etcd
- **Etcd — это фундамент системы**. Все Postgres-кластеры, HA-скопы, заявка на ресурсы и все индексы данных хранятся в Etcd.
- **Все разделы зависят от Etcd** — без работающего Etcd панель показывает устаревший снапшот и алерт «etcd-unreachable» (critical).
- На обзоре (Overview) карточка «etcd» показывает статус доступности и количество рабочих endpoints.

### 4.8. Алерты → все домены
- **Раздел «Алерты»** объединяет алерты из **всех доменов**: Postgres, Kafka, Valkey, S3, Etcd, Workers, бэкапы.
- **Алерты зависят от данных всех остальных разделов** — без данных из кластеров, проп/HA, Etcd, Workers алерты не могут быть сгенерированы.
- На обзоре (Overview) логика сортировки — критичные сверху, самые свежие сверху.

### 4.9. Etcd-снапшоты и Воркеры (инструментальный домен)
- **Etcd-снапшоты** (в разделе «Хранилище бэкапов») — это автоматические экспорт-файлы базы данных, хранящиеся в S3.
- **Воркеры** (PgWorker, KafkaWorker и т.д.) — это исполнители, которые делают эти снапшоты, обрабатывают бэкапы, управляют переездами и т.д.
- Таким образом, **Воркеры пишут данные, которые потом отображаются в Etcd-снапшотах**.

### 4.10. HA → Postgres (детальная связь)
- **HA-скоп `<cluster>-<shard>`** привязан к конкретному Postgres-шарду.
- На **странице «HA»** оператор видит сводку по скопам (лидер, роль, лаг).
- На **странице «HA → детали скопа»** можно увидеть конкретные ноды (мастер, standby), их роли и лаги.

## 5. Зависимости между разделами — сводная карта

### 5.1. Зависимости «данные» (что зависит от кого, для чего)

| Зависимый раздел | Что использует | Зачем |
|---|---|---|
| **Overview** | **Все разделы** (кластеры, HA, алерты, бэкапы, S3, Kafka, надёжность) | Сводка всей системы в одном месте |
| **HA** | Данные Postgres-кластеров из etcd | Отобразить HA-скопы привязанными к реальным шардам |
| **Workers** | Инспекция всех кластеров (Postgres, Kafka, S3, Valkey) | Показывать доступных исполнителей и их статус |
| **Бэкапы** | Инспекцию Postgres-кластеров | Показывать состояние бэкапов для каждого кластера |
| **Надёжность** | Бэкапы (RPO-данные) и HA (RTO-данные) | Рассчитать и показать фактическую надёжность системы |
| **Алерты** | **Все разделы** (кластеры, HA, Workers, бэкапы, S3, Kafka) | Давать актуальные предупреждения |
| **S3** | Инспекцию HA-скопов и Postgres-кластеров | Определять контекст для каждого S3-кластера |

### 5.2. Зависимости «исполнение» (кто что делает)

| Исполняет | Зависит от | Для чего |
|---|---|---|
| **PgWorker** | Postgres-кластеры (etcd) | Выполнять все мутации над Postgres-кластерами |
| **KafkaWorker** | Kafka-кластеры (etcd) | Выполнять все мутации над Kafka-кластерами |
| **S3Worker** | S3-кластеры (etcd) | Выполнять все мутации над S3-кластерами |
| **ValkeyWorker** | Valkey-кластеры (etcd) | Выполнять все мутации над Valkey-кластерами |
| **Панель** | Etcd | Иметь актуальный «снимок» всей системы |
| **Панель** | Workers | Иметь возможность управлять системой |

### 5.3. Зависимости «визуальные» (переходы по страницам)

| Откуда | Куда | Через что |
|---|---|---|
| **Overview** | **Все разделы** | Карточки «etcd», «Кластеры», «Kafka», «S3», «Бэкапы», «Надёжность», «HA» |
| **Кластеры** | **HA → детали скопа** | Ссылка из скопа в деталях Postgres-кластера |
| **Кластеры → детали** | **Workers** | Информация о воркерах (PgWorker, KafkaWorker, S3Worker, ValkeyWorker) в деталях Postgres-кластера |
| **Кластеры → детали** | **Бэкапы** | Детальная информация о бэкапах (Postgres-кластер) |
| **Надёжность** | **Бэкапы** | Клик на полное (вкладку «Полные») открывает детали шарда в разделе «Бэкапы» |
| **Алерты** | **Кластеры** | Клик по алерту «bucket-lost» или «bucket-no-routing» в алерте в деталях Postgres-кластера |
| **Алерты** | **HA** | Клик по алерту «ha-member-not-streaming» в алерте в деталях HA |
| **S3** | **Бэкапы** | Информация о S3-кластере в деталях Postgres-кластера |
| **S3** | **Workers** | Информация о воркерах в деталях Postgres-кластера |

### 5.4. Зависимости «технические» (инфраструктура)

| Зависимый | Что использует | Зачем |
|---|---|---|
| **Панель** | **Etcd** | Иметь актуальный «снимок» всей системы |
| **Панель** | **Workers** | Иметь возможность управлять системой |
| **PgWorker** | **Postgres-кластеры** (etcd) | Выполнять все мутации над Postgres-кластерами |
| **KafkaWorker** | **Kafka-кластеры** (etcd) | Выполнять все мутации над Kafka-кластерами |
| **S3Worker** | **S3-кластеры** (etcd) | Выполнять все мутации над S3-кластерами |
| **ValkeyWorker** | **Valkey-кластеры** (etcd) | Выполнять все мутации над Valkey-кластерами |

### 5.5. Резюме для оператора
Интерфейс спроектирован для обеспечения **максимальной прозрачности**. Любое действие (переезд, ротация, удаление) сопровождается проверками и предупреждениями, а любая проблема (отказ ноды, разрыв репликации) сопровождается не просто фактом ошибки, а руководством к действию.
