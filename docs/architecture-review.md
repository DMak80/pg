# Архитектурный аудит: логичность и усложнённость

Проверка канона `arch/` на внутреннюю логичность и соответствие цели проекта:
**платформа для лёгкой интеграции разных компонентов между собой с высокой
надёжностью данных, управляемостью и наблюдаемостью**. Основание — чтение
`arch/README`, `01`, `11`–`14`, `16`–`21`, `23`–`25`, `arch/adminpanel/01–02`,
`arch/roadmap/README`, `reliability-report`. Правки только к документам; код
не затронут. Формат: находка → где в `arch/` → почему против цели → направление
закрытия. Расхождение проекта с `arch/` — блокирующее замечание ревью
(AGENTS), поэтому фактические расхождения перечислены первыми.

## 1. Что логично и работает (фундамент)

- **Один etcd — один контур истины** (arch/17 S1): панель, все воркеры,
  Patroni-ноды, приёмники WAL и диагностические инструменты работают с одним
  кластером; принципиально снижает класс ошибок «каждый видит свою картину
  мира».
- **Декларативный контракт и единый писатель**: панель только заявляет
  (через HTTP API воркера), воркер — единственный писатель своего домена
  (arch/14 §1, 16 §1, 21 §1, 24 §1). Ответственность разделена предсказуемо.
- **Порт схемы воркера**: клэймы (lease TTL 15 с), журнал фаз, portalloc,
  дискавери API, заявки ротаций — одинаковая механика у PgWorker/KafkaWorker/
  ValkeyWorker/S3Worker (arch/15 §4, 23 §8). Новый компонент интегрируется по
  готовому шаблону.
- **Флап ≠ смерть, деструктив — по положительному свидетельству** (arch/17
  S7); идемпотентность «по факту» во всех процессах; takeover без оператора.
- **Durability по построению**: sync-режим Patroni с per-cluster
  `synchronous_mode_strict` (дефолт durability-first), бэкапы с
  подтверждением слота по факту доставки в S3, DR-слепки etcd в отдельном
  bucket, restore-drill по расписанию (arch/14 §2.1, 19, reliability-report).
- **Наблюдаемость каркасом, а не разрозненными экспортерами**: единый
  `Shared.Metrics`, словарь имён, file_sd из portalloc, Prometheus/Grafana/
  Alertmanager (arch/18).

## 2. Нелогичности и внутренние расхождения

### A1. Два канона клиентского входа в PG: doorman vs прямой порт

- **Где**: arch/11–13 канонизируют вход приложений через `pg_doorman :6432`
  (master-ключ `host:6432`, firewall-матрица P17); arch/14 §2.1 вводит
  `EnableDoorman=false` — нода без пулера, клиентский вход — прямой pg-порт
  `:5432` из portalloc, dsn строится по pg-портам.
- **Противоречие**: в стендах и сборках без doorman мастер-ключ вырождается
  в `host:0` — недискриминантен (arch/14 §2.4 п.5, arch/17 S4): смысл ключа
  меняется от «адрес мастера» до «на шарде есть живой primary». Две
  топологии одного входа — источник спец-веток в коде и непонимания для
  интегратора: какую точку входа читать из etcd?
- **Направление**: выбрать один канон. Либо образ всегда с doorman (вход
  `:6432`, master-ключ полноценный), либо doorman убирается из канона
  11/12/13 вместе с веткой master-ключа `host:<doorman>` — и dsn становится
  единственной точкой дискавери.

### A2. HAProxy остаётся каноном слоя бакетов, которого нет в реальной топологии PgWorker

- **Где**: arch/11 §4, arch/12 (референс топологии), arch/13 (матрица
  «межшардовое только нода↔нода через HAProxy», «HAProxy-синкеры») — HAProxy
  обязателен как точка входа репликационного трафика переездов; arch/14
  §2.1 — HAProxy в образе не поднимается (конфликт `:5432` с PG в одном
  netns), write-вход — прямой порт master-ноды, генератор конфига
  `HaproxyConfigBuilder` живёт в Core «для отдельного фронтенд-слоя».
- **Противоречие**: переезды (MoveProcess, arch/14 §5 F) строят подписки по
  dsn multi-host напрямую к нодам — HAProxy в data path переездов фактически
  отсутствует, а три документа канонизируют топологию, которую PgWorker не
  строит. Генератор конфига поддерживается без потребителя.
- **Направление**: arch-first решение: либо HAProxy возвращается в канон как
  отдельный фронтенд-слой (тогда он должен появиться и в arch/14 как
  провиженерируемый воркером объект), либо выпиливается из 11/12/13 вместе с «синкерами»,
  а подписки канонизируются на dsn multi-host.

### A3. adminpanel/01 противоречит контракту панели 02 и воркерным канонам

- **Где**: arch/adminpanel/01 «Правила потоков» — «Панель пишет в etcd ТОЛЬКО
  декларативные ключи: provisioning §9 и серверные серты API воркеров»;
  arch/adminpanel/02 (шапка, §9) — «Панель в etcd не пишет ничего», все
  мутации — через HTTP API воркера, воркер пишет ключи сам.
- **Противоречие**: две противоположные модели писателя деклараций в одном
  каноне. Для нового компонента непонятно, куда интегрироваться: в etcd
  напрямую или через API исполнителя.
- **Направление**: правка adminpanel/01 по канону 02/14/16/21/24 (панель —
  только чтение + proxy-команды; исключение — серверные серты API воркеров
  `/workers/api_tls/*`, где писатель — панель).

### A4. arch/25 №15: журнал джобов KafkaWorker указан в доменном префиксе PgWorker

- **Где**: arch/25 §4 №15 — «KafkaWorker-джобы → KafkaWorker: etcd-журнал
  (`/pgworker/work/<C>`, WorkJournal)». Координационный префикс KafkaWorker —
  `/kafkaworker/` (arch/15 §4, журнал `/kafkaworker/work/<C>`).
- **Противоречие**: реестр каналов — эталон границ; ссылка на чужой префикс
  либо опечатка, либо ложный сигнал, что домены делят один журнал.
- **Направление**: исправить на `/kafkaworker/work/<C>`.

### A5. arch/18 §3 противоречит mTLS-канону граней воркеров

- **Где**: arch/18 §3 — «метрики открыты в доверенной docker-сети»
  (осталась логика упразднённого ApiKey); arch/14 §1.1 и arch/18 §5.2 — вся
  грань воркера, включая `/metrics` и `/healthz`, mTLS-only, скрейп
  Prometheus по клиентскому серту per-install API-CA.
- **Противоречие**: в одном каноне метрики одновременно «открыты» и «за
  mTLS».
- **Направление**: привести §3 arch/18 к канону mTLS (14 §1.1).

### A6. Два параллельных пути управления PG-кластерами: скрипты и PgWorker

- **Где**: arch/11 §4.5 / arch/14 §1.1 — ручной скриптовый путь
  (`init-cluster.sh`, `move-bucket.sh`, …) остаётся «для стендов без
  PgWorker», с правилом «не смешивать в одном окне переезда»; репарация
  брошенных переездов (arch/14 §5 K, риск R10) прибивает скриптовый переезд,
  не тикающий `updated_unix`.
- **Противоречие**: платформа декларирует «одного писателя» на домен, но
  допускает второго писателя того же формата статус-ключей без клэйма.
  Репарация воркера не отличит живой скриптовый переезд от брошенного —
  автоматика может вступить в конфликт с оператором.
- **Направление**: понизить скрипты до «legacy для стендов без воркера» с
  явной меткой в arch/11/14 (или исключить их из канона живой системы); в
  целевом состоянии — один путь мутаций.

### A7. Три писателя мастер-ключа и их вырожденные состояния

- **Где**: ключ `shards/X/master` пишут (1) Patroni-callback через
  lease-скрипт в образе ноды (arch/14 §2.1), (2) `MasterKeyReconciler`
  воркера как коррекция (P11), (3) внешний HA-контур для усыновлённых
  шардов (arch/14 §5 C, R8). Семантика значения зависит от
  `EnableDoorman` (см. A1).
- **Противоречие**: правилом S4 истина о роли вынесена на пробы `/primary`,
  а ключ объявлен «маршрутизацией/кэшем», — но вокруг кэша построены два
  постоянных механизма записи и сверка. Это усложнение, оправданное только
  потребностью приложения в быстром дискавери; при усыновлении приходится
  поддерживать два формата значения (`host:doorman` и `node:port`).
- **Направление**: описать в arch/14 статус ключа как «согласованный кэш с
  тремя классами писателей» (сейчас это размазано по §2.1/§5 C/R8), а при
  решении A1 — сократить число форматов.

## 3. Усложнения (осознанные и спорные)

### C1. Четыре воркера дублируют машинерию процессов

Клэймы, журнал, portalloc + глобальный portalloc-клэйм, дискавери API,
заявки ротаций, watchdog, словарь метрик — общий порт схемы, но реализован
отдельно в каждом сервисе (arch/14/16/21/24). Shared-сборки (`Shared.Docker`,
`Shared.Etcd`, `Shared.Metrics`, `Shared.Tls`, `Shared.Core`) закрыли
транспорт и каркас, но 7–11 процессов каждого воркера — отдельный код.
Для цели «лёгкая интеграция нового компонента» следующий домен (пятый воркер)
потребует вновь ~1000 строк канона и сервис. Направление: общий воркер-фреймворк
(машина состояний + клэйм + журнал + portalloc + API-дискавери как библиотека)
— кандидат в roadmap; выигрыш — целостность исправлений паттерна (правки S5/S6
сейчас вносятся четырежды).

### C2. Двухуровневая схема блокировок

Per-cluster клэйм `<C>` + глобальный portalloc-клэйм (arch/14 §2.4 п.2, 15 §4,
20 §3, 23 §8). Обоснование корректно (пер-кластерные клэймы не видят
кросс-кластерную гонку портов), но это самая тонкая часть системы: две
разные модели взаимоисключения, каждая со своими гвардами. Направление: единый
менеджер аллокаций (одна секция «читай-выбери-запиши» под одним клэймом
в общем фреймворке, см. C1) вместо четырёх независимых реализаций.

### C3. «Воркер — хозяин» + усыновление: согласование факта и плана каждый тик

AD2' (инвариант portalloc = факт живых контейнеров), перепланирование занятых
портов (Д1), репарация dsn, MERGE-логика P1 — полноценная машина поддержания
эквивалентности «etcd ↔ docker» (arch/14 §5 A/J). Это платит надёжностью
(самолечение), но стоит сложностью: гварды «факт над записью» против
«portalloc переживает rebuild» взаимодействуют нетривиально. Направление:
оставить как есть (это сознательный актив), но вынести инварианты AD2'/Д1/Д2
в отдельный раздел arch/14 «инварианты согласования» — сейчас они распределены
по трём подразделам, и полный набор гвард виден только при полном чтении.

### C4. Двойной механизм жизненного цикла топиков Kafka

Реестр `topics/<T>` несёт факт + `desired` (конвергенция автосинком), при этом
создание/удаление — отдельные claim-ключи `desired.create`/`desired.delete`
(arch/15 §3/§3.1). Два канала заявок на один объект, порядок разбора
зафиксирован (чистка коллизии → delete → create → факт-синк), но канал
можно было бы сделать одним (desired с op-полем). Направление: не менять без
необходимости (работает и описано), но при развитии kafka-домена учесть, что
это второй по тонкости протокол после portalloc.

### C5. Полная воркер-механика для standalone-кеша Valkey

Семь процессов, клэймы, журнал, portalloc, ротации — для ноды без реплик, без
тома, без persistence (arch/21 §2). Механика нужна ради однородности
платформы, но соотношение «инфраструктура/полезная нагрузка» здесь худшее из
четырёх доменов. Аргумент «за»: единый шаблон интеграции; аргумент «против»:
поддержка четырёх полных стеков ради одного контейнера. Не действие, а
осознанный выбор — зафиксировать его в arch/21 §2 одной строкой
(«однородность платформы важнее минимизации каркаса»), чтобы будущий ревьюер
не считал это недосмотром.

### C6. Отдельный контейнер sd-generator для file_sd

Перевод ключей `/pgworker/portalloc/` в JSON file_sd — отдельный сервис
(arch/18 §5.4). Работает, но для одной трансляции ключ→файл есть более
лёгкие каналы (endpoint Prometheus'а, генерация из воркера). Направление:
только при пересмотре стека мониторинга; самостоятельная переделка не
оправдана.

## 4. Соответствие цели платформы

| Цель | Оценка | Комментарий |
|---|---|---|
| Лёгкая интеграция компонентов | **частично** | Шаблон интеграции (etcd-контракт + воркер + дискавери) выстроен и однороден; но клиентская библиотека дискавери — в roadmap, интеграция пока ручная (чтение ключей + конструирование DSN/endpoints); барьер входа нового домена — дублирование машинерии (C1). |
| Надёжность данных | **сильная** | Sync-репликация с durability-first дефолтом, WAL-стрим с подтверждением по факту доставки в S3, drill/verify/PITR, DR-слепки etcd, карантин эвакуации. Открытые разрывы известны и ведомы roadmap (шифрование/второе хранилище бэкапов, Swarm без ускоренного failover, сценарии потери хоста/DC). |
| Управляемость | **хорошая** | Декларативная модель, один писатель на домен, заявки с 202/409-семантикой, graceful self-restart. Минус — двойной путь PG (A6) и расхождение админпанельных доков (A3): «один канал мутаций» декларируется, но каноном не вычитан до конца. |
| Наблюдаемость | **хорошая** | Единый словарь метрик, healthz-секции, журналы фаз в etcd, ~50 алертов панели с Hint/Remedy, file_sd. Известные разрывы — отсутствие внешней нотификации и истории деградаций (roadmap reliability). Наблюдаемость фаз — «последняя запись побеждает», история событий строится метриками (arch/17 S6) — приёмлемо, но требует дисциплины: события без счётчиков теряются. |

## 5. Приоритеты

1. **A1 + A2 (один канон входа PG и судьба HAProxy)** — самое видимое
   расхождение «канон ↔ топология»; решение снимает спец-ветки master-ключа,
   firewall-матрицы и doorman-бюджета.
2. **A3 + A4 + A5** — точечные arch-правки: adminpanel/01, arch/25 №15,
   arch/18 §3. Низкая стоимость, закрывают «блокирующие» по правилам ревью.
3. **A6** — зафиксировать скриптовый путь как legacy (или вывести из канона)
   тем же коммитом, что и решение по A1/A2, чтобы не тащить два канона дальше.
4. **C1 (+C2)** — общий воркер-фреймворк в roadmap как задача трека
   «интегрируемость»: главный рычаг цели «лёгкая интеграция».
5. **C3** — не менять поведение; консолидировать инварианты AD2'/Д1/Д2 в
   один раздел arch/14.
6. **C5** — одна строка-фиксация решения в arch/21.

## 6. Итог

Каркас архитектуры логичен и однороден: один источник истины, декларативные
домены с единым писателем, единый шаблон воркера, durability-first и
наблюдаемость каркасом. Целостность нарушена не в механике, а на стыках
«канон ↔ фактическая топология» (вход PG/HAProxy) и «канон ↔ канон»
(писатель деклараций, журнал джобов, статус метрик) — это правится
arch-first правками. Структурное усложнение одно и главное — дублирование
воркер-машинерии в четырёх сервисах; его закрытие общим фреймворком
одновременно служит цели лёгкой интеграции следующих компонентов.
