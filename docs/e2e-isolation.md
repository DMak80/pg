# Изоляция E2E-тестов: принципы и реализация

Как пишутся docker-E2E тесты PgWorker (контур «Вариант A»): тест — две фазы,
всё окружение живёт в изолированной docker-сети, тестовый раннер — контейнер
внутри той же сети. Правила обязательные — они же в
[AGENTS.base.md](../AGENTS.base.md) (блок «ЦЕЛЕВАЯ АРХИТЕКТУРА E2E»); здесь —
их канонизация с указанием реализации. Эталон:
`src/tests/PgWorker.IntegrationTests/E2e/E2eEnvironment.cs` (фаза 1 — подъём
окружения, teardown), `E2eContour.cs` (двухфазный запуск),
`E2eRetentionScenarios.cs` (сценарий).

## Зачем так строго

Каждое из правил здесь — не эстетика, а закрытие известного класса проблем:

- **Чужие джобы в общем etcd** — окружение целиком своё, etcd в т.ч.; смерть
  etcd-контейнера уносит ключи.
- **Исчерпание подсетей docker** — осиротевшие сети `pgw-net-*`/контуров
  копятся и кончают пул подсетей; лечение — самоочистка при любом исходе
  плюс контур-режим (per-cluster `pgw-net-<C>` в контуре не создаётся вовсе).
- **Остаточные контейнеры** — прерванная серия оставляет `pgw-*` контейнеры;
  ассерт чистоты краснеет сразу, stop-режим упавшего сценария делает
  разбор по живым объектам.
- **«Воркер-призрак»** — SUT-воркер как хост-процесс способен пережить
  teardown теста: процесс жив, указывает etcd-endpoint на освободившийся
  динамический порт, при следующем прогоне коллизия портов приводит призрака
  в чужой etcd — он выигрывает гонку provisioning и поднимает ноды со своей
  per-install CA (чужой CA на нодах, SSL-fail проб). В контуре «Вариант A»
  воркер — контейнер в сети окружения: teardown удаляет его вместе с сетью,
  класс проблем устранён архитектурно.
- **Коллизии host-портов** — хост-порты тестовой инфраструктуры (etcd, ownS3,
  SUT-воркер, раннер) не существуют: публикаций нет, гонок bind'ов нет.

## 1. Тест — две фазы; всё общение внутри изолированной сети

Тестовый факт состоит из двух фаз.

**Фаза 1 — создание изолированного окружения (хост)**: docker-сеть
`pgw-en-{guid}`, etcd-контур (1 или 3 узла), опционально ownS3-нода с бакетом.
Вся инфраструктура окружения — БЕЗ публикации портов на хост: участники
общаются только внутри сети по DNS-именам контейнеров и статичным
контейнерным портам. Хост-часть минимальна: сборка артефактов (publish) и
оркестрация docker.

**Фаза 2 — прогон сценария внутри окружения**: тестовый раннер — контейнер
`pgw-er-{guid}` (образ `pgw-e2e-runner:e2e`) в той же сети. Тестовая сборка
собирается на хосте (`dotnet publish`), в образ — готовые артефакты. Раннер
запускается с фильтром не шире одного сценарного метода
(`-method <FQN>`), исполняет тело факта, ассерты ходят по внутренним именам
сети (mc/psql/curl — паттерн mc-контейнера), результаты — exit code + stdout
(docker logs) + volume `/artifacts` (смонтирован на
`/tmp/pgw-e2e-artifacts-{guid}/` на хосте). После завершения раннера хост
выполняет teardown и ассерт чистоты.

Идентификатор прогона — полный guid:

```csharp
var runId = Guid.NewGuid().ToString("N");
var netName = $"pgw-en-{runId}";          // сеть
// etcd: pgw-ee{N}-{guid}, ownS3: pgw-eo-{guid}, воркер: pgw-ew-{name}-{guid},
// раннер: pgw-er-{guid}
public string ClusterTag => _runId[..8];  // 8 hex — в имени кластера сценария
var cluster = $"bkret{Fx.ClusterTag}";    // уникальное имя кластера
```

Кодировка «префикс + guid» (`pgw-en-`, `pgw-ee-`, `pgw-eo-`, `pgw-ew-`,
`pgw-er-`) даёт читаемость в `docker ps` и точный опознавательный признак.

Ключ к полноте изоляции: **имена ВСЕХ движковых объектов содержат имя
кластера** (`pgw-<C>-*` ноды, `pgw-backup-*-<C>-*` джобы/тома). Уникальное
имя кластера ⇒ уникально всё окружение целиком, включая то, что создаёт не
тест, а PgWorker.

| Объект | Имя | Кто создаёт |
|---|---|---|
| Сеть контура | `pgw-en-{guid}` | тест (фаза 1) |
| etcd-узлы | `pgw-ee{N}-{guid}`, алиасы `e2e-etcd{N}` | тест |
| ownS3 | `pgw-eo-{guid}`, алиас `e2e-owns3` | тест |
| Раннер | `pgw-er-{guid}` | тест (фаза 2) |
| SUT-воркер | `pgw-ew-{name}-{guid}`, алиас `pgw-ew-{name}` | раннер (сценарий) |
| Кластер сценария | `{slug}{tag}` (напр. `bkret1a2b3c4d`) | сценарий |
| Ноды кластера | `pgw-{C}-*` | PgWorker |
| Бэкап-джобы/тома | `pgw-backup-*-​{C}-*` | PgWorker |

## 2. Ноль publish на хост для тестовой инфраструктуры

etcd, ownS3, SUT-воркер и раннер создаются **без `--publish`**: портов на
хосте нет, межконтурных коллизий bind'ов нет, зонд свободных портов и
физический bind-резерв портового окна упразднены. Advertise-URL —
внутрисетевые (`http://e2e-etcd1:2379`, `http://e2e-owns3:9000`,
`https://pgw-ew-w1:8443`): все потребители записей — в сети контура.

Продуктовые ноды (`pgw-<C>-*`) публикуют портовую тройку pg/patroni/doorman
на хост — это канон продукта (arch/14 §2.1/§2.4: portalloc-записи резолвимы
клиентами, moves-подписки ходят по публикациям). Тесты тройки не используют:
адресация теста — внутрисетевые имена нод (`pgw-<C>-<X>-<n>:5432`,
`:8008` — совпадают с SAN серверных сертов REST-TLS).

Порт-план нод — per-контур окно 200 портов (см. §6).

**Единственное исключение из ноль-publish — AdminPanel**: в тестовом контуре,
где панель поднимается, её порт публикуется на хост динамическим маппингом —
пользователь проверяет состояние контура браузером во время прогона;
фактический выделенный порт выводится в `[PHASE]`-метку и журнал сразу после
старта панели. Параллельные контуры безопасны: docker выделяет свободные
динамические порты, каждый контур — свой.

## 3. SUT-воркер — контейнер в сети контура

PgWorker никогда не запускается хост-процессом: `StartHostAsync` стартует
контейнер `pgworker:e2e` (образ собирается на хосте `dotnet publish` →
runtime-слой с COPY готового вывода; sdk-стадии и COPY исходников в
E2E-образах запрещены).

- `/var/run/docker.sock` смонтирован — воркер провижинит ноды в сеть
  контура (`PgWorker__Docker__ContourNetwork=pgw-en-{guid}`, arch/14 §2.1:
  ноды, wal-агенты и ephemeral-джобы бэкапов создаются в одной сети;
  `pgw-net-<C>` не создаётся).
- env воркера — внутрисетевые адреса: etcd по алиасам `e2e-etcd{N}:2379`
  (и AdvertisedEndpoints — те же: Patroni-ноды тоже в контуре); API воркера
  слушает `https://0.0.0.0:8443`, advertise — `https://pgw-ew-{name}:8443`.
- mTLS-серты: per-run CA окружения передаётся раннеру env (PEM), раннер
  выпускает воркеру серверный серт с SAN=алиасом; клиентские серты
  (health-пробы, policy-API) раннер выпускает из той же CA — hostname
  сверяется честно (SAN = DNS-имя в сети).
- Жизненный цикл в руках сценария: подъём, мгновенный `docker kill`
  (смерть контроллера), рестарт; teardown убирает контейнер вместе с
  окружением.

## 4. Чистка строго по своим (own-only), никаких широких фильтров

Фильтр «своё» — имя содержит полный guid **или** тег кластера:

```csharp
private bool OwnName(string name)
    => name.Contains(_runId, StringComparison.Ordinal)
       || name.Contains(ClusterTag, StringComparison.Ordinal);
```

- Широкие фильтры (`pgw-*`) в тестовом коде **запрещены**: на общем демоне
  живут контейнеры чужих прогонов и dev-стенда.
- `docker network prune -f` между сериями — страховка на уровне хоста
  (AGENTS.md), не механизм изоляции; основной механизм — самоочистка.
- Контур-режим не создаёт per-cluster сетей `pgw-net-<C>`; own-only чистка
  сохраняет их удаление как страховку для не-контурных артефактов.

## 5. Teardown при любом исходе + ассерт чистоты

Teardown — в `DisposeAsync` (фаза 1, хост), выполняется при любом исходе:

1. телеметрия ДО любых удалений: docker logs + inspect всех СВОИХ
   контейнеров (etcd, ownS3, воркеры, раннер) — в `/tmp/pgw-e2e-artifacts-{guid}/`;
2. успех: rm контейнеров по одному → rm томов с ретраем → rm сети →
   страховка own-only для пер-кластерных сетей → **ассерт чистоты** (не
   осталось ни одного контейнера/тома/сети своего идентификатора);
3. упавший сценарий (exit≠0 раннера): контейнеры **останавливаются**, тома/
   сети остаются — разбор по живым объектам и снятым логам; команды зачистки
   — `README-cleanup.txt` в каталоге артефактов.

Ассерт чистоты — часть теста: регрессия изоляции краснеет сразу.

## 6. Порт-план нод — per-контур окно без физического резерва

Публикации нод (продукт) идут из PortRange воркера: окружение выдаёт каждому
контуру непересекающееся окно 200 портов (счётчик процесса: параллельные
контуры одного прогона получают разные окна; база 15100, вне дефолтов
dev-стенда). Физический bind-резерв окна и ретрай bind-фейлов упразднены —
тестовая инфраструктура портов на хост не публикует; фактические коллизии
троек с чужими публикациями аллокатор воркера обходит штатной проверкой
занятости (arch/14 §2.4). Старт-ретрай окружения остаётся только для
гонки сети (`network … not found` — чужой глобальный prune).

## 7. Готовность — wait-стратегиями, не сном

- **`sleep` в Cmd контейнеров запрещён.**
- Готовность сервисов — wait-стратегии/поллинг с конечным бюджетом: etcd
  `/health` (+ лидер для HA), ownS3 `/healthz`, воркер — mTLS `/healthz`
  по внутрисетевому имени. Бюджеты короткие: бут контура ≤ 100 с.
- Внутритестовый поллинг условия — `Task.Delay(500)` в цикле (канон репо).

## 8. Общие только статические ассеты

Собираемый один раз на процесс — не мутабельный рантайм-стейт: PKI-шаблоны
(per-run CA генерируется фазой 1), docker-образы (`pgworker-node:e2e`,
`pgworker-backup:e2e`, `pgworker-wal:e2e`, `owns3:e2e`, `pgworker:e2e`,
`pgw-e2e-runner:e2e`, `sdgenerator:e2e`), publish-выводы app/тестов.
Всё, что сценарий меняет в рантайме, — только внутри своего окружения.
Образы локально собираемые — в registry не кладутся.

## 9. Изоляция от dev-стенда и параллельных серий

- Параллельные прогоны E2E не пересекаются ни по одному объекту: guid во
  всех именах, DNS-зона каждой контуры своя (контур-сеть окружения),
  порт-окна непересекающиеся, публикаций тестовой инфраструктуры нет.
- Dev-стенд (`as-*`, `adminpanel`) — не тестовый контур: тесты его не
  трогают, страховочная чистка хоста его обходит.
- Страховочный гейт между сериями: `docker rm -f` остатков серии (кроме
  контейнеров стенда) + `docker network prune -f`. Сетка безопасности —
  за пределами тестов; тест не имеет права полагаться на неё.

## Чек-лист нового E2E-сценария

1. Тело факта — обычное: `await using var fx = await E2eEnvironment.StartAsync(…)`
   (на хосте StartAsync оркестрирует двухфазный прогон текущего факта, в
   раннере — возвращает подключение к контуру). Класс-фикстуры (окружение
   на класс) оркестрируются `E2eContour.OrchestrateClassAsync(classFqn, …)
   в InitializeAsync — фильтр раннера «-class».
2. Имя кластера сценария — `{slug}{Fx.ClusterTag}`; никаких константных имён.
3. Адресация — только внутрисетевые имена: ноды `pgw-<C>-<X>-<n>:5432/:8008`,
   ownS3 `e2e-owns3:9000`, etcd `e2e-etcd{N}:2379`, воркер
   `pgw-ew-{name}:8443`. Хост-портов, `localhost`-адресов и
   `host.docker.internal` в ассертах нет.
4. В Cmd контейнеров нет `sleep`; готовности — поллинг с бюджетом ≤ 100 с.
5. Teardown и ассерт чистоты — в хелпере; сценарий не оставляет хвостов
   мимо окружения.
6. Прогон на Release: `PGW_TEST_DOCKER=1 dotnet test … --filter
   FullyQualifiedName~<Class>`; после серии — проверка `docker ps -a` на
   остатки своего guid и `docker network prune -f`.
