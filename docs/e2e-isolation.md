# Изоляция E2E-тестов: принципы и реализация

Как пишутся docker-E2E тесты PgWorker (контур «Вариант A»): единица окружения —
тестовый класс — поднимает себе ПОЛНОСТЬЮ СВОЮ изолированную docker-сеть со
всем контуром и полностью её удаляет; тело факта исполняется в хост-процессе
теста. Правила обязательные — они же в
[AGENTS.base.md](../AGENTS.base.md) (блок «ЦЕЛЕВАЯ АРХИТЕКТУРА E2E»); здесь —
их канонизация с указанием реализации. Эталоны:
`src/tests/PgWorker.E2eTests/E2e/E2eContourFixture.cs` (класс-фикстура:
Guard-слот → подъём → teardown), `E2eEnvironment.cs` (контур окружения),
`E2eRetentionScenarios.cs` (сценарий).

## Зачем так строго

Каждое из правил здесь — не эстетика, а закрытие известного класса проблем:

- **Чужие джобы в общем etcd** — окружение целиком своё, etcd в т.ч.; смерть
  etcd-контейнера уносит ключи.
- **Исчерпание подсетей docker** — осиротевшие сети `pgw-net-*`/контуров
  копятся и кончают пул подсетей; лечение — самоочистка при любом исходе
  плюс контур-режим (per-cluster `pgw-net-<C>` в контуре не создаётся вовсе).
- **Остаточные контейнеры** — прерванная серия оставляет `pgw-*` контейнеры;
  ассерт чистоты краснеет сразу, stop-режим упавшего сценария делает
  разбор по живым объектам.
- **«Воркер-призрак»** — SUT-воркер как хост-процесс способен пережить
  teardown теста: процесс жив, указывает etcd-endpoint на освободившийся
  динамический порт, при следующем прогоне коллизия портов приводит призрака
  в чужой etcd — он выигрывает гонку provisioning и поднимает ноды со своей
  per-install CA (чужой CA на нодах, SSL-fail проб). В контуре «Вариант A»
  воркер — контейнер в сети окружения: teardown удаляет его вместе с сетью,
  класс проблем устранён архитектурно.
- **Коллизии host-портов** — хост-порты тестовой инфраструктуры (etcd, ownS3,
  API SUT-воркера) только динамические: docker выделяет свободные, гонок
  bind'ов нет; редкие гонки «зонд свободного порта → docker bind» с соседним
  процессом закрывает старт-ретрай окружения (§6).

## 1. Единица окружения — тестовый класс; тест исполняется на хосте

Окружение E2E поднимает класс-фикстура (`IAsyncLifetime`):

**Подъём контура — `InitializeAsync` (хост)**: Guard-слот
`E2eParallelismGuard.Acquire` (ДО создания первого docker-объекта окружения) →
docker-сеть `pgw-en-{guid}` → etcd-контур (1 или 3 узла) → опционально
ownS3-нода с бакетом → per-run CA → окно портов 15100+. Хост-часть:
publish артефактов статики (отдельная фаза подготовки, e2e-launch §0) и
оркестрация docker.

**Исполнение — тело факта в хост-процессе**: раннер-контейнер и двухфазный
запуск упразднены; факт — обычный код хост-процесса, ассерты ходят по
динамическим публикациям (`localhost:{динамический порт}`, §2) и
внутрисетевым именам через `docker exec`. Факты класса последовательны и
делят окружение класса; разным фактам нужны разные контуры — класс делится
на два класса.

Идентификатор прогона — полный guid:

```csharp
var runId = Guid.NewGuid().ToString("N");
var netName = $"pgw-en-{runId}";          // сеть
// etcd: pgw-ee{N}-{guid}, ownS3: pgw-eo-{guid}, воркер: pgw-ew-{name}-{guid}
public string ClusterTag => _runId[..8];  // 8 hex — в имени кластера сценария
var cluster = $"bkret{Fx.ClusterTag}";    // уникальное имя кластера
```

Кодировка «префикс + guid» (`pgw-en-`, `pgw-ee-`, `pgw-eo-`, `pgw-ew-`) даёт
читаемость в `docker ps` и точный опознавательный признак.

Ключ к полноте изоляции: **имена ВСЕХ движковых объектов содержат имя
кластера** (`pgw-<C>-*` ноды, `pgw-backup-*-<C>-*` джобы/тома). Уникальное
имя кластера ⇒ уникально всё окружение целиком, включая то, что создаёт не
тест, а PgWorker.

| Объект | Имя | Кто создаёт |
|---|---|---|
| Сеть окружения | `pgw-en-{guid}` | класс-фикстура |
| etcd-узлы | `pgw-ee{N}-{guid}`, алиасы `e2e-etcd{N}` | класс-фикстура |
| ownS3 | `pgw-eo-{guid}`, алиас `e2e-owns3` | класс-фикстура |
| SUT-воркер | `pgw-ew-{name}-{guid}`, алиас `pgw-ew-{name}` | сценарий |
| Кластер сценария | `{slug}{tag}` (напр. `bkret1a2b3c4d`) | сценарий |
| Ноды кластера | `pgw-{C}-*` | PgWorker |
| Бэкап-джобы/тома | `pgw-backup-*-​{C}-*` | PgWorker |

## 2. Динамические publish обязательны, фиксированные хост-порты запрещены

etcd-узлы, ownS3 и API SUT-воркера публикуют порты на хост ТОЛЬКО
динамическими маппингами (`-p 127.0.0.1::<контейнерный>` — docker выделяет
свободный хост-порт; `assignRandomHostPort` в testcontainers). Фиксированные
хост-порты тестовой инфраструктуры запрещены. После старта фактический порт
читается `docker port`; адресация теста — `localhost:{динамический порт}`,
адресация контейнеров — `host.docker.internal:{динамический порт}` и
внутрисетевые имена (`http://e2e-etcd1:2379`, `http://e2e-owns3:9000`,
`https://pgw-ew-w1:8443`). Меняется только путь ТЕСТА: внутрисетевые
DNS-имена остаются для контейнерных потребителей (SAN серверных сертов,
advertise нод).

Продуктовые ноды (`pgw-<C>-*`) публикуют портовую тройку pg/patroni/doorman
на хост — это канон продукта (arch/14 §2.1/§2.4: portalloc-записи резолвимы
клиентами, moves-подписки ходят по публикациям). Тест ходит по
`localhost:{порт окна PortRange}`.

Порт-план нод — per-контур окно 200 портов (см. §6).

AdminPanel в тестовом контуре, где панель поднимается, публикует порт
динамическим маппингом — пользователь проверяет состояние контура браузером
во время прогона; фактический выделенный порт выводится в `[PHASE]`-метку и
журнал сразу после старта панели. Параллельные контуры безопасны: docker
выделяет свободные динамические порты, каждый контур — свой.

## 3. SUT-воркер — контейнер в сети окружения

PgWorker никогда не запускается хост-процессом: `StartHostAsync` стартует
контейнер `pgworker:e2e-{ветка}` (per-branch тег, §9; образ собирается на
хосте `dotnet publish` → runtime-слой с COPY готового вывода; sdk-стадии и
COPY исходников в E2E-образах запрещены).

- `/var/run/docker.sock` смонтирован — воркер провижинит ноды в сеть
  окружения (`PgWorker__Docker__ContourNetwork=pgw-en-{guid}`, arch/14 §2.1:
  ноды (с приёмниками WAL внутри) и ephemeral-джобы бэкапов создаются в
  одной сети; `pgw-net-<C>` не создаётся).
- env воркера — `host.docker.internal` для опубликованных динамических
  портов etcd и собственный advertise `https://pgw-ew-{name}:8443`
  (внутрисетевые потребители); API слушает `https://0.0.0.0:8443`.
- mTLS-серты: per-run CA окружения; фикстура выпускает воркеру серверный
  серт с SAN `[алиас, "localhost"]` (второй элемент покрывает адрес хоста
  для тестовых mTLS-проб по `https://localhost:{динамический порт}`);
  клиентские серты (health-пробы, policy-API) выпускаются из той же CA —
  hostname сверяется честно.
- Жизненный цикл в руках сценария: подъём, мгновенный `docker kill`
  (смерть контроллера), рестарт; teardown убирает контейнер вместе с
  окружением.

## 4. Чистка строго по своим (own-only), никаких широких фильтров

Фильтр «своё» — имя содержит полный guid **или** тег кластера:

```csharp
private bool OwnName(string name)
    => name.Contains(_runId, StringComparison.Ordinal)
       || name.Contains(ClusterTag, StringComparison.Ordinal);
```

- Широкие фильтры (`pgw-*`) в тестовом коде **запрещены**: на общем демоне
  живут контейнеры чужих прогонов и dev-стенда.
- `docker network prune -f` между сериями — страховка на уровне хоста
  (AGENTS.md), не механизм изоляции; основной механизм — самоочистка.
- Контур-режим не создаёт per-cluster сетей `pgw-net-<C>`; own-only чистка
  сохраняет их удаление как страховку для не-контурных артефактов.

## 5. Teardown при любом исходе + ассерт чистоты

Teardown — в `DisposeAsync` окружения, выполняется при любом исходе:

1. телеметрия ДО любых удалений: docker logs + inspect всех СВОИХ
   контейнеров (etcd, ownS3, воркеры) — в `/tmp/pgw-e2e-artifacts-{guid}/`;
2. успех: rm контейнеров по одному → rm томов с ретраем → rm сети окружения →
   страховка own-only для пер-кластерных сетей → **ассерт чистоты** (не
   осталось ни одного контейнера/тома/сети своего идентификатора);
3. упавший сценарий (`MarkFailed()`): контейнеры **останавливаются**, тома/
   сети остаются — разбор по живым объектам и снятым логам; команды зачистки
   — `README-cleanup.txt` в каталоге артефактов.

Ассерт чистоты — часть теста: регрессия изоляции краснеет сразу.

## 6. Порт-план нод — per-контур окно без физического резерва

Публикации нод (продукт) идут из PortRange воркера: окружение выдаёт каждому
контуру непересекающееся окно 200 портов (счётчик процесса: параллельные
контуры одного прогона получают разные окна; база 15100, вне дефолтов
dev-стенда). Физический bind-резерв окна и ретрай bind-фейлов упразднены —
продуктовый аллокатор сам проверяет занятость; фактические коллизии троек с
чужими публикациями аллокатор воркера обходит штатной проверкой занятости
(arch/14 §2.4). Старт-ретрай окружения — для гонки сети (`network … not
found` — чужой глобальный prune) И занятости зондируемого хост-порта
(`already allocated`, `address already in use` — в ретрай: 3 попытки,
пересоздание контейнеров с новыми динамическими портами; FreePortWindow
не меняется).

## 7. Готовность — wait-стратегиями, не сном

- **`sleep` в Cmd контейнеров запрещён.**
- Готовность сервисов — wait-стратегии/поллинг с конечным бюджетом: etcd
  `/health` (+ лидер для HA), ownS3 `/healthz`, воркер — mTLS `/healthz`
  по `https://localhost:{динамический порт}`. Бюджеты короткие: бут
  контура ≤ 100 с.
- Внутритестовый поллинг условия — `Task.Delay(500)` в цикле (канон репо).

## 8. Инструментальные контейнеры — переиспользуемые per-окружение

CLI-инструменты (mc) — ОДИН контейнер на окружение: `pgw-em-{guid}` в сети
окружения, поднимается вместе с ownS3, все вызовы — `docker exec`
(RunMcAsync). Per-вызовные `docker run --rm` копят безымянные контейнеры
вне own-only чистки (автоимена, ryuk их не знает) — утечка, запрещена.
Контейнер-держатель живёт осмысленно: создаётся и удаляется жизненным
циклом окружения (teardown + ассерт чистоты), `sleep infinity` — тело
держателя, а не забытый keepalive.

## 9. Статика — per-branch теги; рантайм-запись — per-process

Собираемый один раз — не мутабельный рантайм-стейт: PKI-шаблоны (per-run CA
генерируется подъёмом окружения), docker-образы (`pgworker-node:e2e-*`
(включая приёмник WAL и tool-режим внутри), `owns3:dev`, `pgworker:e2e-*`,
`sdgenerator:e2e-*`; образы Kafka/Valkey/S3-контуров — `kafkaworker:e2e-*`,
`valkeyworker:e2e-*`, `s3worker:e2e-*`), publish-выводы app.

- **Теги всех e2e-образов — PER-BRANCH `e2e-{ветка}`** (одна ветка — один
  набор образов; git-инвариант «одна ветка — один checkout»; fallback
  `{хэш8}` пути worktree при git-недоступности/detached —
  `Shared.TestInfra.E2eImageTags`). Разные ветки не пересекаются ни по
  одному образу.
- **Publish-каталоги записи и /tmp-телеметрия статики — per-process**:
  журналы `/tmp/pgw-e2e-static-phase-{ветка}-{pid}.log` и
  `/tmp/pgw-e2e-static-process-{ветка}-{pid}-*.log`; S3 publish-каталог —
  `{root}/artifacts/e2e/s3worker-{pid}-{s6}`.
- **Лок подготовки** `artifacts/e2e/.prepare.lock`: взаимное исключение
  ЗАПИСИ в publish-каталоги статики одного worktree (НЕ глобальный лок
  запуска серий); занят — поллинг шагом 5 с, бюджет 10 минут.
- **Авто-уборка**: после успешной подготовки теги `e2e-*` своих
  репозиториев старше 24 ч снимаются (`docker rmi` по одному; отказы —
  «image is being used by running container» — игнорируются; текущий тег
  исключён).
- Всё, что сценарий меняет в рантайме, — только внутри своего окружения.
  Образы локально собираемые — в registry не кладутся.

## 10. Изоляция от dev-стенда и параллельных серий

- Параллельные прогоны E2E не пересекаются ни по одному объекту: guid во
  всех именах, DNS-зона каждой контуры своя (сеть окружения), порт-окна
  непересекающиеся, динамические публикации — docker выделяет свободные.
- **Рантайм per-process/per-run; статические образы per-branch — разные
  ветки не пересекаются ни по одному образу.**
- Dev-стенд (`as-*`, `adminpanel`) — не тестовый контур: тесты его не
  трогают, страховочная чистка хоста его обходит.
- Страховочный гейт между сериями: `docker rm -f` остатков серии (кроме
  контейнеров стенда) + `docker network prune -f`. Сетка безопасности —
  за пределами тестов; тест не имеет права полагаться на неё.

## Чек-лист нового E2E-сценария

1. Единица окружения — тестовый класс: класс-фикстура (`IAsyncLifetime`,
   база `E2eContourFixture`) — полный контур класса в `InitializeAsync`
   (Guard-слот → сеть → etcd → ownS3 → CA → окно портов), тело факта —
   обычный код хост-процесса; никаких `E2eContour.OrchestrateClassAsync` и
   per-fact `await using var fx = E2eEnvironment.StartAsync(…)`.
2. Имя кластера сценария — `{slug}{Fx.ClusterTag}`; никаких константных имён.
3. Адресация: тест ходит `localhost:{динамический порт}` (etcd/ownS3/API
   воркера) и `localhost:{порт окна}` (ноды); контейнеры —
   `host.docker.internal:{динамический порт}` и внутрисетевые имена
   (`pgw-<C>-<X>-<n>:5432/:8008`, `e2e-owns3:9000`, `e2e-etcd{N}:2379`,
   `pgw-ew-{name}:8443`). Фиксированных хост-портов и хардкода портов в
   ассертах нет — только фактические значения `docker port`.
4. В Cmd контейнеров нет `sleep`; готовности — поллинг с бюджетом ≤ 100 с.
5. Teardown и ассерт чистоты — в хелпере; сценарий не оставляет хвостов
   мимо окружения.
6. Прогон на Release — двумя отдельными командами: сначала
   `dotnet build … -c Release`, затем
   `dotnet test … -c Release --no-build --filter FullyQualifiedName~<Class>`
   (env-гейтов больше не существует); после серии — проверка `docker ps -a`
   на остатки своего guid и `docker network prune -f`.
7. Guard-слот (`E2eParallelismGuard.Acquire`) захватывается ДО создания
   первого docker-объекта окружения.
