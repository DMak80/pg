# Изоляция E2E-тестов: принципы и реализация

Как пишутся docker-E2E тесты в монорепо (PgWorker/KafkaWorker). Правила
обязательные — они же в [AGENTS.base.md](../AGENTS.base.md) (блок
«ЦЕЛЕВАЯ АРХИТЕКТУРА E2E ТЕСТОВ»); здесь — их канонизация с ссылкой на
эталонную реализацию. Проверено задачей t06: параллельные прогоны E2E и
dev-стенд на одном хосте не мешают друг другу, после любого исхода теста
хост остаётся чистым.

Эталон: `src/tests/PgWorker.IntegrationTests/E2e/E2eEnvironment.cs`
(поднятие/teardown), `E2eRetentionScenarios.cs` (сценарий).

## Зачем так строго

Каждое из правил здесь — не эстетика, а закрытый инцидент:

- **Чужие джобы в общем etcd** — сценарии на общем etcd ловили джобы
  соседних прогонов; на Release это падало «на ровном месте»
  (инцидент t02). Лечение — окружение целиком своё, etcd в т.ч.
- **Исчерпание подсетей docker** — осиротевшие сети `kfw-net-*` от убитых
  прогонов копились (ryuk их не подбирает: сети создаёт движок, а не
  testcontainers), пул ~30 user-сетей кончался, следующая серия падала на
  `POST /networks/create` (инцидент мерж-гейта t05: 18/58 интеграционных
  падали на зелёном коде).
- **Остаточные контейнеры** — прерванная серия оставляла десятки `pgw-*`
  контейнеров, которые искажали следующий прогон (авто-подъём «чужих»
  контейнеров, коллизии портов).
- **Глобальный prune на живом прогоне** — страховочная чистка хоста из
  параллельной задачи снесла только что созданную сеть окружения
  (`network not found` при старте etcd).

## 1. Окружение — полностью своё, уникальный идентификатор во всём

Каждый сценарный класс (минимальная граница изоляции; если методы внутри
мешают — per-method) поднимает себе **новое** окружение: свою docker-сеть,
свой etcd, опционально свой MinIO. Пользоваться уже поднятыми контейнерами
запрещено ни при каких обстоятельствах.

Идентификатор прогона — полный guid:

```csharp
var runId = Guid.NewGuid().ToString("N");
var netName = $"pgw-en-{runId}";          // сеть
// etcd: pgw-ee-{runId}, MinIO: pgw-em-{runId}
public string ClusterTag => _runId[..8];  // 8 hex — для имени кластера сценария
var cluster = $"bkret{Fx.ClusterTag}";    // уникальное имя кластера
```

Slug в имени не нужен — guid короче и уникальнее. Кодировка «префикс из
одного-двух символов + guid» (`pgw-en-`, `pgw-ee-`, `pgw-em-`) даёт
читаемость в `docker ps` и точный опознавательный признак.

Ключ к полноте изоляции: **имена ВСЕХ движковых объектов содержат имя
кластера** (`pgw-<C>-*` ноды, `pgw-backup-*-<C>-*` джобы, тома
`pgw-backup-<C>-*`). Уникальное имя кластера ⇒ уникально всё окружение
целиком, включая то, что создаёт не тест, а PgWorker.

| Объект | Имя | Кто создаёт |
|---|---|---|
| Сеть | `pgw-en-{guid}` | тест |
| etcd | `pgw-ee-{guid}` | тест |
| MinIO | `pgw-em-{guid}` | тест |
| Кластер сценария | `{slug}{tag}` (напр. `bkret1a2b3c4d`) | сценарий |
| Ноды кластера | `pgw-{C}-*` | PgWorker |
| Бэкап-джобы/тома | `pgw-backup-*-​{C}-*` | PgWorker |

## 2. Чистка строго по своим (own-only), никаких широких фильтров

Фильтр «своё» — имя содержит полный guid **или** тег кластера:

```csharp
private bool OwnName(string name)
    => name.Contains(_runId, StringComparison.Ordinal)
       || name.Contains(ClusterTag, StringComparison.Ordinal);
```

- Широкие фильтры (`pgw-*`) в тестовом коде **запрещены**: на общем демоне
  живут контейнеры чужих прогонов и dev-стенда — кто чистит широким
  фильтром, тот чистит чужое.
- `docker network prune -f` между сериями — страховка на уровне хоста
  (AGENTS.md), не механизм изоляции теста; основной механизм —
  самоочистка.
- Глобальные `docker rm -f $(docker ps -aq)` из теста — запрещены.

## 3. Teardown при любом исходе + ассерт чистоты

Teardown — в `DisposeAsync` (фикстура в `await using` тела Fact):
выполняется при успехе, падении ассерта и исключении. Порядок:

1. kill воркеров (хост-процессы PgWorker, идемпотентно);
2. dispose etcd/MinIO (ключи etcd умирают вместе с контейнером — отдельная
   чистка ключей не нужна);
3. `docker rm -f` своих контейнеров по одному; `removal … is already in
   progress` — не ошибка (контейнер уже удаляется, например testcontainers
   в шаге 2);
4. `docker volume rm -f` своих томов с ретраем (демон освобождает ссылки
   асинхронно; бюджет ~30 с);
5. удаление своей сети; попытка снести общесистемную сеть нод движка
   (`pgw-net`) — docker сам откажет, если в ней живы чужие endpoints;
6. **ассерт чистоты**: после teardown не осталось ни одного КОНТЕЙНЕРА/
   ТОМА/СЕТИ своего окружения — иначе тест падает
   (`teardown окружения неполный`). Чужие объекты в ассерт не включаются.

Ассерт чистоты — часть теста, а не пожелание: регрессия изоляции краснеет
сразу, а не когда кончатся подсети.

## 4. Retry старта против внешних гонок

Только что созданная сеть без контейнеров может быть снесена чужим
глобальным prune до старта etcd. `StartAsync` — обёртка из 3 попыток с
пересозданием окружения целиком; ретрай только на распознанную гонку
(`network` + `not found` в сообщении). Ретраится именно **подъём заново**,
а не «продолжить с половиной окружения».

## 5. Динамические порты везде

- Хост-порты — зонд свободного порта (`bind :0` → закрыть) или
  `assignRandomHostPort: true` + `GetMappedPublicPort`. Литералов `:16000`
  в asserts нет.
- Advertise-URL строится от **фактического** published порта
  (`host.docker.internal:{порт}` — для контейнеров, `localhost:{порт}` —
  для хост-процессов).
- Зонд закрывает листенер до старта процесса — в окне порт может занять
  исходящее соединение: ретрай зонда до 3 попыток на `address already in
  use`.
- Диапазоны портов, выдаваемые движку в e2e, не должны пересекаться с
  поднятым dev-стендом.

## 6. Готовность — wait-стратегиями, не сном

- **`sleep` в Cmd контейнеров запрещён** — keepalive-контейнер вида
  `["sleep","60"]` висит после завершения полезного процесса и ломает
  и ассерт чистоты, и демона.
- Готовность сервисов — wait-стратегии testcontainers
  (`UntilHttpRequestIsSucceeded` для etcd `/health`, MinIO
  `/minio/health/live`), блокирующий `docker run` для разовых утилит (mc) —
  без поллинга.
- Бюджеты короткие: бут брокера ≤ 100 с, поднятие инстанса ≤ 30 с. Упавший
  прогон обязан падать быстро, с диагностикой (tail логов в сообщении
  исключения), а не висеть.
- Внутритестовый поллинг условия — `Task.Delay(500)` в цикле с проверкой
  (канон репо); бюджет любого ожидания внутри теста конечен и короток.

## 7. Общие только статические ассеты

Собираемый один раз на процесс — не мутабельный рантайм-стейт, шарить его
можно: PKI-пакет (CA + серты), docker-образы (`pgworker-node:e2e`,
`pgworker-backup:e2e`), Release-бинарь PgWorker.App. Всё, что сценарий
меняет в рантайме (контейнеры, ключи, тома, порты), — только внутри своего
окружения.

## 8. Изоляция от dev-стенда и параллельных серий

- Параллельные прогоны E2E не пересекаются ни по одному объекту (guid во
  всех именах) — взаимные помехи исключены конструкцией, а не дисциплиной.
- Dev-стенд (`as-*`, `adminpanel`) — не тестовый контур: тесты его не
  трогают, страховочная чистка хоста его обходит.
- Страховочный гейт между сериями (по AGENTS.md): `docker rm -f` остатков
  серии (кроме контейнеров стенда) + `docker network prune -f`; networks
  prune не трогает живые (не присоединённые) сети. Это сетка безопасности
  за пределами тестов — тест не имеет права полагаться на неё.

## Чек-лист нового E2E-сценария

1. Фикстура наследует `E2eEnvironment`; окружение поднимается
   `StartAsync(slug, withMinio: …)` — guid генерируется сам.
2. Имя кластера сценария — `{slug}{Fx.ClusterTag}`; никаких константных
   имён кластеров.
3. Все порты — из зонда/`GetMappedPublicPort`; advertise — от фактических.
4. В Cmd контейнеров нет `sleep`; готовности — wait-стратегии/поллинг с
   конечным бюджетом ≤ 100 с.
5. Teardown не пишется руками — он в `DisposeAsync` фикстуры; сценарий
   только не оставляет после себя хвостов мимо окружения (временные файлы —
   в каталог снапшотов инстанса).
6. Прогон на Release; после серии — проверка `docker ps -a` на остатки
   своего guid и `docker network prune -f`.
