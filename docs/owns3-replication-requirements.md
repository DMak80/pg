# Требования к репликации ownS3 (mesh между серверами пула)

Требования к межсерверной репликации ownS3 — вход для канона
(`arch/owns3/07-replication.md`, создаётся задачей трека) и реализации.
Сегодня ownS3 — single-сервер (XL Single / XL Erasure внутри одного
хоста), репликации нет (arch/22, глава 06 — границы этапа).

Контекст: изыскания и уроки альтернативных платформ —
[`docs/s3-replication.md`](s3-replication.md) (MinIO bucket replication,
Garage consistent/dangerous: все измеренные штрафы и блокировки ниже —
оттуда); целевая схема пула и клиентская часть — трек
[`arch/roadmap/s3.md`](../arch/roadmap/s3.md).

## Целевая схема (рамка, где ownS3)

- Пул ownS3-серверов на нескольких docker-хостах (гео). Клиент
  (подсистема бэкапов) **пишет в любой доступный** сервер — перебор с
  per-попыточным таймаутом; восстановление читает **по приоритетам**
  (per-cluster настройки и отдельная пара для etcd-слепков — клиентская
  часть, трек s3; приоритеты записи не нужны: в mesh принимает любой).
- Синхронизация между серверами — **внутренняя механика ownS3**
  (mesh-репликация), для клиентов каждый сервер — полный S3. Клиенты о
  репликации не знают.

## R1. Запись без штрафов — главное требование

- PUT подтверждается после **локальной фиксации** (существующий
  атомарный xl-коммит на диске сервера), **без синхронного ожидания
  удалённых серверов** — ни подтверждений, ни inline-проверок целей на
  пути запроса.
- Латентность PUT **не зависит от числа и состояния удалённых целей**:
  при отказе/таймауте/изоляции любого числа целей поток записи не
  деградирует. Целевые показатели: PUT p99 как в текущем single-режиме;
  серия 10 PUT суммарно **≤1 с при ЛЮБЫХ отказах целей** (включая
  изолированный сервер, у которого недоступны все) — приёмочный бюджет.
- Антипримеры (измерено, docs/s3-replication.md): MinIO — штраф
  первого PUT 2–5 с при одной недоступной цели, блокировка минутами
  при 2+ TIMEOUT-целях (включая расколы пополам); Garage consistent —
  висения 70–110 с при потере кворума; Garage dangerous — то же для
  невладеющих половин. ownS3 обязан не повторять ни один из этих
  паттернов: отказ цели — событие фонового доставщика, никогда —
  пути записи.

## R2. Локальный журнал доставки (outbox)

- Каждый подтверждённый объект попадает в очередь доставки per-target
  (журнал на диске, переживает рестарт сервера).
- Доставка — фоновая: ретраи с бэкоффом, идемпотентный put на приёмнике
  (ключи объектов детерминированы; содержимое wal-сегментов идентично
  от всех источников — перезапись безопасна).
- Глубина очереди и лаг доставки per-target — наблюдаемы.

## R3. Быстрая детекция недоступности (серверная обязанность)

- Сервер отвечает быстро и всегда: health-грань ≤1 с; S3-грань не
  «зависает» при потере целей — клиентский детект «сервер недоступен»
  строится на PUT-таймауте и переборе, и сервер обязан давать быстрый
  успех/отказ, а не молчание (урок MinIO: health жив, PUT виснет).
- Изолированный от всех сервер остаётся полноценным S3 для локальных
  клиентов (запись+чтение) — расхождения закроет доставка (R4).

## R4. Доливка и срастание

- После восстановления связи расхождения доставляются **автоматически,
  без рестарта процесса** (антиурок Garage: не самолечилось, спасал
  рестарт ноды). Бюджет: полный догон тестового контура ≤5 мин.
- Backfill: сервер, добавленный в mesh, получает существующие объекты
  фоном, не останавливая приём записи.
- Удаления досылаются наравне с записями: чистки (ретенция клиентов,
  служебные) не рассинхронизируют mesh; физическая чистка локальных
  данных — локальная политика, не мешающая доставке.
- Конкурирующая запись одного ключа на разных серверах (split-brain):
  разрешение — **LWW по времени локальной фиксации**, проигравшая
  версия не хранится (versioning в ownS3 отсутствует по канону), факт
  слияния журналируется с обеих сторон (наблюдаемость). Для
  детерминированных ключей wal идентичные байты делают конфликт
  безопасным; для полных бэкапов конфликт означает запись через
  разных серверов — разрешается верифицируемостью манифеста (клиентская
  сторона).

## R5. Честная наблюдаемость

- Метрики per-target: состояние линка, лаг доставки (возраст старейшего
  недоставленного объекта), глубина очереди, счётчики исходов
  доставки/ретраев.
- Штатные метрики обязаны отражать фактическое расхождение
  (антипример MinIO: `Queued: 0` при живом отставании данных);
  контрольный механизм — сверка листингов пары серверов (админ-грань
  ownS3: стартовая позиция/хвост префикса per-target), внешний зонд
  синхронности трека s3 опирается на неё.
- Алерт-события: цель офлайн >N с, лаг >порога, очередь доставки
  растёт/переполняется.

## R6. Топология, безопасность, ресурсы

- Состав mesh — конфигурация сервера per-install (env/конфиг ownS3,
  канон owns3/05): список целей с адресами (hostname:port, advertised —
  multi-host/гео), идентификация соседа. Управление составом живого
  пула (добавление/вывод сервера) — оркестрация трека s3; ownS3
  обязан поддерживать изменение состава без даунтайма S3-грани
  (перечитывание конфига/админ-команда — фиксируется каноном).
- Межсерверные соединения аутентифицируются (per-install
  credentials/mTLS — по канону доступа owns3/05); транспорт —
  TLS-опция per-install.
- Доставка — ограниченный фон: настраиваемые скорость/параллелизм,
  отсутствие критичной конкуренции с S3-гранью за диск/CPU. Дисковый
  бюджет журнала доставки bounded; переполнение — алерт, не отказ
  записи.

## Приёмочная матрица (методика — docs/s3-replication.md)

Тестовый контур 2–5 серверов ownS3, сценарии stop/раскол/серии/срастание:

| Сценарий | Требование |
|---|---|
| серия 10 PUT при отказе любого числа целей (stop и сетевой изолят) | суммарно ≤1 с, 0 блокировок, 0 отказов записи |
| health/GET/S3 изолированного сервера | ≤1 с всегда |
| срастание после раскола/флапа | доставка расхождений сама, ≤5 мин, без рестартов |
| backfill нового сервера | полный, фоновый, запись не останавливается |
| конкурирующий ключ в двух половинах | LWW-разрешение, журналирование с обеих сторон |
| метрики при живом расхождении | лаг >0 отражён (сверка с листингами) |
| удаления/чистки на одном сервере | досылаются, mesh сходится |
